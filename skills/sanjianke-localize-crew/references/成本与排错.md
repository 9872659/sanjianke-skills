# 成本与排错

---

## 一、成本口径

### 只出 token，不编金额

- 文本模型网关**不公布单价**：`GET /api/v1/pricing` 实测只有 6 条规则，
  全是图像/视频类，**不含文本大模型**
- `GET /api/v1/models` 的 75 条记录里**没有任何价格字段**
- `POST /api/v1/chat/completions` 的成功响应里 `usage` 只有
  `prompt_tokens` / `completion_tokens` / `total_tokens`，**没有点数**

所以**拿不到可信的文本模型单价，本包拒绝凭空编一个**。
token 数我们估（同族实测标定），**金额必须由你给单价**（`--price-in` / `--price-out`，
单位「点 / 百万 token」）。

### 字符 → token 标定（同族实测值，**是估算不是账单**）

| 方向 | 标定值 |
|---|---|
| 输入 | 1 token ≈ **1.61** 字符（1 字符 ≈ 0.621 token） |
| 输出 | 1 字符 ≈ **1.11** token |

平台口径：**1 元 = 100 点**。

### 一次 `run` 的调用构成

| 阶段 | 调用数 |
|---|---|
| 术语表 | 1（给了 `--glossary` 就 0） |
| 初译 | 1 |
| 文化适配 | 1 |
| 合规 | 1 |
| 术语官 | **0**（纯本地判定） |
| **合计** | **4** |

每多一轮（被打回就重译一轮）再加 **3 次**：重译 + 文化适配 + 合规。

### 真机实测（本包唯一一次完整 run，请以此为准）

材料 **187 字**中文 → 英文（美国），`--rounds 1`：

| 调用 | token | 约点数（按 1000/2000 点每百万 token） | 耗时 |
|---|---|---|---|
| 术语表 | 1122 | 1.459 | 2.2s |
| 译文（第 1 轮） | 2247 | 2.951 | 3.6s |
| 文化适配 | 1643 | 2.003 | 2.8s |
| 合规裁决 | 1859 | 2.404 | 3.5s |
| **合计** | **6871**（入 4925 / 出 1946） | **8.817 点 ≈ 0.088 元** | — |

> 这 8.817 点**不是账单**：它按上面那对数算出来的，真实计费口径由平台决定。
> 本包只报 token；金额永远是你给的单价算出来的。

### 报价与核算

```bash
# 跑之前：估算
python3 scripts/run.py cost --file 源文.md --rounds 1 --price-in 1000 --price-out 2000

# 跑之后：读真实 usage 核算（不是估算）
python3 scripts/run.py cost --from-result /tmp/lc/run.json --price-in 1000 --price-out 2000
```

### 预算硬上限

```bash
python3 scripts/run.py run --file 源文.md --target-lang en --market us \
    --rounds 1 --price-in 1000 --price-out 2000 --budget 40 \
    --outdir /tmp/lc --json
```

- `--budget` 是**硬上限**：每次调用**之前**都检查一次，超了就地中止（退出码 5），
  **不会把下一次的钱花出去**
- 给了 `--budget` 就必须给单价，否则**退出码 2**（没有单价，预算上限没有意义）
- 每个会花钱的子命令的**第一步**都做这个校验 —— 参数错不允许花掉任何一次调用

## 二、退出码

| 码 | 含义 | 怎么处置 |
|---|---|---|
| `0` | 四席全部放行，无硬闸门命中 | 可以发 |
| `1` | **未预料异常**（代码 bug） | `--json` 下 stdout 有 `kind:"internal"` 信封，**完整 traceback 在 stderr**。报 bug，不藏 bug |
| `2` | 用法 / 配置错 | 文件不存在、市场名错、语言代码错、`--outdir` 在包内、`--budget` 没配单价、术语表与源文对不上、`--rounds` 越界 |
| `3` | **硬闸门命中** | 合规 / 占位符 / 照抄示例 / 锚点 / 术语不一致 / 数字单位 / 裁决不完整 / **信息隔离被破坏** |
| `4` | 调用失败 | 网络 / 鉴权 401 / 点数 402 / 模型名 404 |
| `5` | **预算超限，已就地中止** | 未发起下一次调用 |
| `6` | **轮次用尽仍有打回/否决** | 这不是错误：分歧如实报出，产出带未决项落盘。人工决定改还是不发 |
| `130` | 用户中断 | — |

`3` 与 `6` 的区别很实在：
**`3` 是"这一稿有确定性问题"**（能指出是哪条规则、哪一处引文）；
**`6` 是"机器这一侧没有收敛"**（能指出是哪一席在第几轮否了什么，但要不要接受由人定）。

## 三、断点续跑

`--outdir` 里有一个 `localize-state.json`。每个角色的产出都按 **key** 缓存，
key 命中就跳过，打印"跳过（零成本）"。

### 断点 key 含哪些维度

**必须含全部影响产出的维度**，否则改了东西却静默复用（同族踩过）：

| 维度 | 为什么必须在 key 里 |
|---|---|
| `source_sha` / `source_chars` | 源文改了 |
| `target_lang` | **换目标语言当然要重跑** |
| `market` | **换市场就换了文化规则包与合规法域** —— 这是最危险的一种静默复用 |
| `glossary_sha` + `glossary_version` | 术语表改了 |
| `role_version` / `prompt_version` / `ruling_version` | 角色提示词或裁决规则改了 |
| `glossary_rules` / `culture_rules` / `unit_rules` | 判定口径改了 |
| `model` / `temperature` | 换模型 / 换采样 |
| `round_no` | 第几轮 |
| `feedback_sha` | 这一轮的**打回要求**变了（同样的源文，不同要求 → 不同译文） |
| `target_multiple` | 目标长度系数变了 |

自测已验证：上面七类关键维度任一变一个，key 都会变。

### 术语表复用的额外核对

`--glossary` 指的术语表会核对**源文摘要**与**目标语言**，对不上**直接拒绝**（退出码 2）：

```
术语表针对的不是这一版源文（术语表 sha `a344bbae` ≠ 当前源文 sha `4aa580eb`）
—— 拒绝复用。重新跑 `glossary`，或换一份配套的术语表。
```

**为什么要拒绝**：拿一份别的源文的术语表来续跑，产出会看起来完全正常、
实际上术语完全对不上 —— 这类"静默复用"最难查。

`--force` 忽略断点从头重跑（key 没命中就会重新花钱）。

## 四、真机踩过的坑（都写进了代码）

### 4.1 上游返回的 JSON 坏了（最重要的一条）

**现象**：HTTP 200、`choices` 齐全、`usage` 齐全，`content` 却不是一个可用的 JSON。

**实测到三种坏法**（形态不同，处置也不同）：

| # | 形态 | `finish_reason` | content 收尾 | 实测证据 | 加大 `--max-tokens` 有用吗 |
|---|---|---|---|---|---|
| ① | **输出被 `max_tokens` 截断** | `length` | **没有**（停在字符串中间） | 探针 `max_tokens=200`：430 字符，末尾 `…"genre":"穿越"},`，配平 depth=2 | **有用** |
| ② | **模型偶发吐出语法错的 JSON** | `stop` | **有**（以 `}]}` 结束），坏在中间 | 外部对照实测：`{"id":40","title":…` 多吐一个引号，位置约 1200 字符 | **没用** |
| ③ | **响应在传输层被切断** | 可能仍报 `stop` | **没有** | 本包留下两份原始返回（EOF 处 `depth=1, in_str=True`，2739 / 2781 字符），但**当时没记 `finish_reason`**，分不清它与 ② | **没用** |

**判据是结构 + `finish_reason`，不是长度**：

- 结构：能不能按**括号配平**切出一个完整的顶层值
- `finish_reason`：`length` → 是 ①；`stop` / `None` → 是 ②/③

> ⚠️ **本节撤回过一个错误归因，留在这里当反面教材。**
> 本节原先的标题是「响应被截断」，正文写着"**实测**响应在 **2600~2900 字符**附近被截断，
> 6 次里出现 6 次，与 `--max-tokens`（8192）无关"。**那个说法是错的。**
>
> - 错在哪：我只看到"JSON 解析失败"，就**推断**成"网关在某个固定长度处截断"，
>   然后把它当**实测**写进了文档 —— 而我从头到尾**没有记录 `finish_reason`**，
>   手里唯一的数据是"content 长度"。**用长度解释一个结构问题，方向一开始就错了。**
> - 被什么推翻：同一端点做对照探针，**要 40 条长内容时拿到了 3984 字符的完整内容**
>   （`finish_reason='stop'`，以 `}]}` 正常收尾，`json.loads` 通过）。
>   而本包自己失败的那几次长度各不相同（**1921~2781**）——
>   **固定长度这条线根本不存在**。
> - 教训（比这个 bug 本身值钱）：**"我观测到 X 失败"不等于"我知道 X 为什么失败"。**
>   把推断写成"实测"，是文档里最难被读者发现的一种错 —— 因为它看起来有数据支撑。

**处置（机制本身是对的，保留）**：

1. `chat()` 检测到坏 JSON 就**当场重试**（最多 4 次）—— 对 ②/③ 重试常常就好了
2. 重试时按 `finish_reason` **分别给提示**：`length` 说"加大 `--max-tokens` 才管用"，
   其余情况明说"**加大 `--max-tokens` 没用**，换模型或拆段"
3. 各席提示词**强制写短**（最多 6 条、每条 ≤30 字）
4. `back_translation` 只要求含数字/单位/术语的句子填（减少响应长度）
5. **`finish_reason` 进调用台账**（`REPORT.md` 的成本表里有这一列），事后可复核
6. 仍失败就把材料**拆成几段分别跑**

**`finish_reason` 为什么必须记**：它是区分"该调上限"与"模型写错了"的**唯一**依据。
本包最初漏了它，于是只能拿长度去凑解释 —— **错误归因就是这么来的**。

**上限不是越大越好**：目标不是"输出越长越好"，而是"刚好够写短"。
输出越长，撞上 ① 的概率越高、碰上 ② 的机会也越多。

### 4.2 `parse_first_json` 从嵌套对象解出东西

**现象**：报「译审返回里没有可用的译文」，但原始返回看起来写得好好的。

**根因**：旧实现逐个 `{` 试 `raw_decode`。外层 JSON **坏掉**时（截断或语法错都可能），
外层的 `{` 解不出来，循环往后挪，**从 `"pairs": [` 里的那个 `{` 解出第一个 sentence 对象**
交出去 —— 一个只有 `source` / `target` / `back_translation` 三个键的字典。
上层报"没有译文"，**真因（外层 JSON 坏了）被"成功解出一个对象"盖住了**。
这个 bug 的真正危害不是"少了一个字段"，而是**报错指向了错误的方向** ——
调试的人会去查提示词、查模型，而不会去看响应本身完不完整。

**修复**：先按**括号配平**切出第一个完整的顶层值再解（字符串里的括号不计数）；
切不出来才退回逐个 `{` 试。兜底层仍可能拿到嵌套对象，所以上层
`normalize_translate_output` 会把"既没有 `body` 也没有 `pairs[].target`"判为不合格，
并在报错里**打出顶层键是哪几个 + 本次 `finish_reason`**，
直接指向"外层 JSON 坏了，而且告诉你是哪种坏法"。

### 4.3 各席产出随市场变大而变长

**现象**：市场规则块给得越详细（每条带 20~30 字解释 × 6~7 条），
模型输出也越长，越容易撞上 `max_tokens`（`finish_reason=length`）或碰上坏 JSON。

**修复**：合规那一席的市场规则块**只给类别名**，不给解释。
类别名足够让模型开始查；真要判"为什么"时它自己知道（那是它的专业）。

### 4.4 `--outdir` 在包内

产出落在包内，下一次打包就会把上一次的产物（译文、术语表、日志）一起打进去，
包会莫名其妙变大、还可能带上不该发的内容。
所以 `--outdir` 指到包内一律**退出码 2**。

### 4.5 `--out` 被静默吃成 `--outdir`

同族真机踩过：子命令上同时有 `--outdir` 时，argparse 默认允许**前缀缩写**，
于是用户写 `--out report.json` 想输出结果文件，结果**产出目录变成了一个叫
`report.json` 的目录，而且不报任何错**。

所以本包 `ArgumentParser(allow_abbrev=False)`，且**父级与每个子命令都要设**
（argparse 的缩写开关是每个 parser 各自的属性，只在父级设一遍不够）。
现在写 `--out` 会直接报 `unrecognized arguments`（退出码 2），一眼看出问题。

### 4.6 `sys.dont_write_bytecode = True` 必须在 import 之前

实测记录（CPython 3.11.9，干净临时目录里逐格对照）：

| 情形 | 结果 |
|---|---|
| `python run.py`（正常直跑） | 一个 `.pyc` 都不生成 |
| `import run`（**先**设 flag） | 一个 `.pyc` 都不生成 |
| `import run`（**没设** flag） | `__pycache__/run.cpython-311.pyc` |
| `python -m py_compile run.py` | `__pycache__/run.cpython-311.pyc` |

三条结论：

1. `sys.dont_write_bytecode = True` 有效，**只要它设在被 import 的模块之前**。
   迟一行，那个模块就已经落盘了。
2. **入口脚本作为 `__main__` 永远不会被字节码缓存。**
3. 会生成 `run.pyc` 的只有两种情形：有工具把入口 `import` 当模块用了
   （自检脚本 / 测试框架最常见），或者跑了 `py_compile`。

> ⚠️ 另外要纠正一个常见的说法：**`.pyc` 不会导致上传被拒** ——
> `__pycache__` 与 `*.pyc` 本来就在 CLI 的排除清单里，不会被打包。
> 这一行是"让包保持干净"，不是上传的硬前提。
> 真正该做的两件事：自检脚本别 `import` 入口（非要 import 就先设这个 flag），
> 以及跑完 `py_compile` 之后清掉 `__pycache__`。

### 4.7 `a7w._request(raw=True)` 的 `raw` 不是"要原始响应"

`_request` 的 `raw` 参数是**原始请求体字节**（用于 multipart 上传），
**不是**"返回原始响应"。同族有人把它当成后者用过，结果**崩在钱已经扣之后**。

本包 `chat()` **故意不走** `a7w._request`，一律自己发 urllib 请求，
语义只有一种，不给误用的机会。

### 4.8 `deepseek-chat` 不在 `models` 列表里，但能用

- `deepseek-chat` 实测可用，**路由到 `deepseek-flash`**（看响应的 `model` 字段）
- 但它**不在** `/api/v1/models` 的返回列表里（列表给的是 `DeepSeek-V4-Pro` /
  `DeepSeek-V4-Flash` / `DeepSeek-V3.2` 这类**版本号名**，响应里又变成小写）
- 所以「列表里没有」**不等于**「不能用」，而且**列表名、请求名、响应名三者不一定一致**
- 反过来：**`deepseek-flash` 当请求名用是失败的** —— 实测 HTTP 200，
  但 `model:null`、内容为空、`usage` 也为空（**静默失败**）。它只是路由的目标名
- `DeepSeek-V4-Pro` 与 `DeepSeek-V3.2` 是**推理模型**，会先花 completion token
  出思维链再给答案（实测一句两字回复：前者 54 个 reasoning token，后者 105 个）。
  用它们就把 `--max-tokens` 提高到 1.5~2 倍

## 五、常见报错速查

| 报错 / 现象 | 原因 | 怎么办 |
|---|---|---|
| `Missing or invalid relay API key`（401） | Key 无效、过期或写错 | 到 https://api.a7w.cn/ 重新领取；确认没把 `Bearer` 重复写进环境变量 |
| 点数不足（402） | 账号点数用完 | 到 https://api.a7w.cn/ 充值 |
| 模型不存在（404） | 模型名写错或已下架 | `run.py models` 现查 |
| 上游 502 / 503 / 504 | 网关到上游的瞬时抖动，**实测很常见** | 脚本已退避重试 4 次；连续失败换模型 |
| `上游返回的 JSON 坏了`（报错带 `finish_reason`） | 见 4.1（三种坏法） | 脚本自动重试；**只有 `finish_reason=length` 才加大 `--max-tokens`**，其余情况加大它没用 → 换模型或拆段跑 |
| `译审返回里没有可用的译文` | 见 4.2 | 看 `<outdir>/raw/` 里的原始返回；报错里会提示顶层键 |
| `!! 信息隔离被破坏` | 某一席的提示词里出现了别的席位的结论标记词 | **代码 bug**，不是模型问题。报出来 |
| `术语表针对的不是这一版源文`（2） | 拿别的源文的术语表续跑 | 它该做的：**拒绝静默复用**。重跑 `glossary` |
| `术语表是给 `ja` 用的，当前目标语言是 `en``（2） | 语言不匹配 | 用配套的术语表 |
| 术语一致性标红（3） | 同一源词在不同位置用了不同译法 | 看 `glossary_check` 的**全部出现位置**；改完重跑（零成本） |
| 数字与单位标红（3） | 数字丢了，或没按目标市场换算 | 看报告里 `present` 与 `number_as_source` 两栏分开判断 |
| 锚点到句子标红（3） | 意见里的引文在原文里找不到（编造引文） | 看 `unanchored_*` 里被剔出的引文；反复出现说明该模型不擅长引用原文，换模型 |
| `定位失败`（3） | 未锚定率 > 40% | 同上 |
| `给了 --budget 就必须给 --price-in 与 --price-out`（2） | 没有单价，预算上限没有意义 | 补单价 |
| `成本超过 --budget`（5） | 预估或真实累计超了 | 跑单席、调低 `--max-tokens`、提高预算 |
| 退出码 6 | 轮次用尽仍有打回/否决 | **设计行为**。看 `REPORT.md` 的未决项，人工决定 |
| `unrecognized arguments: --out`（2） | 本包不允许长选项前缀缩写 | 写全 |
| Windows 下中文乱码 | 控制台代码页不是 UTF-8 | `chcp 65001`，或 `PYTHONIOENCODING=utf-8` |
| 原稿第一个字是乱码 / 字数偏 1 | UTF-8 BOM | 脚本已自动剥 BOM；仍异常就另存为「UTF-8 无 BOM」 |

### 收集排错信息时请附上

1. 完整命令
2. `--dry-run` 的输出（提示词长什么样）
3. 原始报错文本与退出码
4. `<outdir>/raw/` 里的**原始返回**（这是最有价值的一份）
5. `REPORT.md`（如果已经产出）

**不要在报错信息或截图里带上你的 API Key。**
