# 角色与职权

本包是**产品线 L3（多智能体协作型）**。L3 的判据不是"调了几次模型"，而是四件事：

1. 每个角色有**自己的目标函数与产出物**
2. 角色之间**会互相否掉**（不是各写各的）
3. **信息不对称**是结构性的，不是口头约定
4. 有**裁决与终止机制**，且**不许假装谈拢**

---

## 一、四个角色

| id | 角色 | 目标函数 | 产出物 | 否决权 | 折在什么上 |
|---|---|---|---|---|---|
| `translator` | **译审** | 意思准不准、有没有漏译错译 | 译文 + 逐句回译对照 | **能打回**：意思错、漏译、增译、术语表里的词没按规范译法来 | 打回 → 重译；轮次用尽仍打回 → 带未决项产出（退出码 6） |
| `terminologist` | **术语官** | 术语全篇一致、与行业惯例一致 | 术语表定稿 + 不一致清单（**每条给出全部出现位置**） | **能打回**：同一源词多译、术语表里的规范译法没落地 | 不一致 → 打回；轮次用尽仍不一致 → 带未决项产出 |
| `culture` | **文化适配** | 目标市场的文化能不能接受 | 文化风险清单（禁忌 / 宗教 / 颜色 / 数字 / 幽默失效 / 政治敏感） | **能否决**：踩红线必须改，不接受"综合评估后放行" | 否决 → 重译或改文案；轮次用尽仍否决 → 带未决项产出 |
| `compliance` | **合规** | 目标市场的广告法 / 平台规则 | 风险裁决 `pass` / `fix` / `send_back` / `veto` | **一票否决**：判 `veto` 直接终止，不换词硬发 | 打回/veto → 修订；用尽仍不放行 → 带未决项产出 |

零成本看这张表（含隔离白名单与支持的市场语言）：

```bash
python3 scripts/run.py roles
python3 scripts/run.py roles --json          # 给流水线消费
```

> `models` 六个**完全不花钱**：`glossary_check` 与 `check` 是纯本地判定，
> 改完译文反复跑的就是它们。

### 为什么"术语官"不是译审的一个子任务

因为它们的目标函数会**冲突**。译审要的是"这一句意思对"，术语官要的是"全篇用词一致"。
真实场景里这两种判断经常指向相反的方向：某一句换个说法读起来更自然（译审会赞成），
但那个说法破坏了全篇一致（术语官会打回）。合成一个角色，这种冲突就被内部消化掉了
—— 而"内部消化"正是本包要消灭的东西。

### 为什么"文化适配"要有独立的否决权

因为**一句完全准确的译文照样可能是不能用的**。举个例子：

> 源文：「一袋米 3 斤」
> 直译：「a bag of rice weighs 3 *jin*」—— 译审挑不出错（忠实、无漏译）
> 文化适配否决：`jin` 在美国市场无人识别，读作人名或拼写错误，
> 而且**等于没本地化**。要求换算成 pounds。

译审没有立场否定这一条，因为从它的目标函数看这句话是对的。
**这就是为什么需要第二个立场，而不是让一个角色"顺便也考虑一下文化"。**

## 二、信息隔离（本包是 L3 而不是"一个模型演四个角色"的关键）

`ROLES[...]["inputs"]` 是**允许进入该角色上下文的字段白名单**，
`ROLES[...]["forbidden"]` 是被显式排除的字段。这两栏不是文档：
`build_*_prompt()` 按它拼提示词，`assert_isolation()` 按它验证。

| 角色 | 看得到（白名单） | 看不到（被显式排除） | 隔离标记词个数 |
|---|---|---|---|
| 译审 | `source` / `target_lang` / `market` / `glossary` / `feedback` | `culture_risks` / `culture_verdict` / `compliance_verdict` / `compliance_risks` | 14 |
| 术语官 | `source` / `translation` / `glossary` / `target_lang` / `market` | 同上 | 14 |
| 文化适配 | `source` / `translation` / `market` / `target_lang` | `glossary_issues` / `terminology_verdict` / `compliance_verdict` / `compliance_risks` | 13 |
| 合规 | `source` / `translation` / `market` / `target_lang` | `glossary_issues` / `terminology_verdict` / `culture_risks` / `culture_verdict` / `translation_issues` | 16 |

> **术语官是纯本地判定**（`glossary_check` 不调模型），所以它的隔离标记词个数在
> 真机报告里会显示 0 —— 它根本没有提示词要扫。这不是漏检，是这一席不需要模型。

### `assert_isolation()` 怎么工作

在每个角色**调用之前**，对将发送的提示词做一次文本级扫描：

```python
ISOLATION_MARKERS = {
    "culture_risks":    ["文化风险清单", "文化适配的", "culture_risks", "宗教红线"],
    "compliance_verdict": ["合规裁决", "合规已放行", "compliance_verdict", "一票否决"],
    "glossary_issues":  ["术语不一致清单", "术语官的", "glossary_issues"],
    ...
}
```

本角色不该看到的字段，其标记词一个都不许出现在提示词里。**出现就抛异常、退出码 3、
一分钱不花**（检查在花钱之前）。判定结果（`excluded` / `markers_checked` / `leaked`）
逐条写进产出与流程日志，可复核。

**为什么要在调用前扫而不是在文档里写"我们做到了"**：
隔绝一个字段靠的不是"我模板里没写"，而是"调用前真的扫过一遍"。
模板会被人改，扫描不会。

### 真机实测结果

| 角色 | 扫过的标记词 | 泄漏 |
|---|---|---|
| 译审 | 14 | 0 ✅ |
| 术语官 | 0（纯本地，无提示词） | 0 ✅ |
| 文化适配 | 13 | 0 ✅ |
| 合规 | 16 | 0 ✅ |

## 三、有向反馈：打回怎么生效，同时不破坏隔离

这是本包最容易被做错的地方。两种错误做法：

- **错误做法 A**：打回时把"谁说了什么、为什么"整段塞进下一轮 —— 下一轮的译审
  就顺着别人的结论走了，四席退化成一个声音。
- **错误做法 B**：打回只记在报告里，不真的改 —— 那就是走过场。

本包的做法是**去立场化的可执行要求**（`_feedback_block()`）：

```
上一轮被打了回来，**下面这些要求必须在这一版全部落实**
（要求来自质量把关，不提是哪一席提的，也不提它的理由）：
  1. 要求：把 `短剧` 统一成 `short drama`（这一处现在没用规范译法）
     涉及位置（原文/译文引文）：…parts of making mini-series…
  2. 要求：把数字 3（单位 斤）补回译文，别丢数字
     涉及位置（原文/译文引文）：…一袋米 3 斤，那台相机 2 公斤…
```

带的是**"改成什么"（`ask`）**与**位置引文**，不带提要求的席位名、不带它的理由。
于是：

- **打回真的生效**：要求必须落实，且译审要在 `feedback_applied` 里逐条交代落实了哪几条
- **下一轮仍然独立**：译审不知道是谁提的，也就不会"因为合规说了所以照办"

自测已验证：第 2 轮的提示词（含反馈块）**仍然通过全部隔离检查**，
且反馈块里不出现任何席位名（`文化适配` / `术语官` / `合规` / `译审`）。

## 四、裁决与终止

### 单席裁决完整性（`verdict_gate`）

- 裁决值必须可识别（只能是 `pass` / `fix` / `send_back` / `veto` 或登记过的同义词）
- **打回/否决必须留可读理由**（空、`无`、`N/A`、`-`、`见上` 都不算理由）

### 全局裁决闭合（`decision_closure`）—— 四条交叉核对，专治"假装谈拢"

1. 最终裁决值必须可识别
2. **有人判打回/否决，最终却写"放行" → 拦**（少数派被抹平）
3. **还有未决项，最终却写"放行" → 拦**
4. **还有未决项，最终裁决里出现"综合评估后放行"这类措辞 → 拦**

第 4 条盯的是一类具体的话术：把"没解决"说成"综合判断后可以接受"。
`FAKE_AGREE_RE` 里登记的形态包括「综合评估后放行」「综合来看没有问题」
「总体上可以接受」「基本符合要求」「已基本解决」「不影响发布」「可以发布」「视为通过」。

### 四种显式出口

| 出口 | 触发条件 | 退出码 |
|---|---|---|
| 全部放行 | 四席都不在 `send_back` / `veto` | 0 |
| 硬闸门命中 | 合规/占位符/照抄示例/锚点/术语不一致/数字单位/裁决不完整 | 3 |
| **轮次用尽仍有未决** | 打完最后一轮仍有席位打回或否决 → **带未决项产出**，逐条写明是哪一席在第几轮否了什么、引用了哪句 | **6** |
| 连续两轮没有实质改动 | 重译后译文与上一版二元组相似度 ≥ 0.90 → 判定"改不动"，升级给人看 | 6 |

**这四种出口都必须留下可读信息。** 退出码 6 不是错误，是**如实报告的行状态**：
意思是"这件事在机器这一侧没有收敛，需要人来决定"。

## 五、成本形状（报价用）

`run` 一次的最少调用数：

| 阶段 | 调用 |
|---|---|
| 术语表 | 1（给了 `--glossary` 就 0） |
| 初译 | 1 |
| 文化适配 | 1 |
| 合规 | 1 |
| 术语官 | **0**（纯本地） |
| **合计** | **4**（或 3，复用术语表时） |

每多一轮（被打回就重译一轮）再加 **3 次**（重译 + 文化适配 + 合规）。
`run.py cost` 会按 `--rounds` 与经验重译概率给出期望调用数。

**先报价再跑**：

```bash
python3 scripts/run.py cost --file 源文.md --rounds 1 --price-in 1000 --price-out 2000 --budget 40
```
