# 三剪客 · 超轻量中文 OCR（命令行 + Web 服务）

手里有一堆截图、票据、证件、路牌、海报要变成能复制的文字，而图片又不方便传到别人的服务器上——这就是它上场的场景。模型体积小、纯 CPU 用 ONNX Runtime 就能推，所以老机器、内网机器、树莓派级别的环境都能跑得起来。

它同时给了两种入口：命令行适合被脚本和 Agent 调用（结果是结构稳定的 JSON，带文本块、置信度和四点框坐标），网页服务适合给人用（上传图片直接看效果）。仓库另外附带 C++、JVM、Android、.NET 的多端示例和一套 NCNN 模型，方便把同一套能力搬到别的语言栈里。

**上游项目**：`chineseocr_lite`　**仓库**：https://github.com/DayBreak-u/chineseocr_lite

## 什么时候用 / 不用

**用它**：

- 用户说「把这张图里的字抠出来」，而且是**印刷体中文**为主的图片：截图、扫描页、发票、证件、菜单、海报、屏幕翻拍。
- 要把 OCR 结果**喂给程序继续处理**，需要结构化输出而不是一段乱文本：`chineseocr <图片>` 直接吐 JSON，字段是全文、文本块数组、每块置信度、每块四点框坐标和耗时。
- **图片出不了内网**、或者机器没有 GPU：推理是本地 CPU 的 ONNX Runtime，运行期不联网、不需要显卡。
- 想**十秒内搭一个网页版 OCR** 给同事用：仓库自带服务和前端页面，起一条命令就能在浏览器里传图看结果。
- 要在 **C++ / Java / Kotlin / Android / .NET** 项目里内嵌同一套模型：仓库里对应端都有参考实现，还配套一份 NCNN 格式模型给移动端和带 GPU 加速目标的端侧用。

**不要用它**：

- **手写体，以及中文之外的多语种**。这套轻量识别模型不是为手写训练的，手写稿、签名、处方一类内容不要指望它；日韩、阿拉伯、泰文等语种的精度也没有保证。
- **版面分析、表格结构还原、公式识别**。它只回答「图上有哪些文本块、分别是什么、框在哪」，不回答「这是表头还是表体」「这个单元格属于第几行」。
- **直接喂 PDF**。输入是图片，PDF 得先用别的方式渲染成图（或者用专门的 PDF 解析工具），它不替你做这一步。
- **对精度有硬指标的正式文档数字化**。这是「超轻量」路线的取舍：速度快、体积小、依赖少，代价是复杂版面、小字、密集排版的准确率不如体量更大的模型。量一大的正式项目，先做几十张真实样本的对比测试再决定。
- **需要极高吞吐的在线服务**。当前分支的 ONNX 路径是 CPU 推理，QPS 上限取决于机器核数；高并发场景要考虑端侧 NCNN/GPU 路线或换推理后端。

## 安装

上游 README 给出的推荐环境是 Python 3.6，跑在 Windows / Linux / macOS 上，CPU 推理，不需要 CUDA。实际可用的 Python 版本区间请以仓库 `requirements.txt` 与当前说明为准。

```bash
# 1) 跑源码：装依赖
pip install -r requirements.txt
```

```bash
# 2) 当命令行工具用：以包的方式安装（这一步会把 models/*.onnx 一起装进去）
pip install -e .
```

```bash
# 3) 装完确认入口在 PATH 里（没有输出说明没装上）
chineseocr --help
```

```bash
# 4) 不想装入口脚本，也可以走模块方式运行
python -m chineseocr_lite --help
```

关于 Docker：仓库当前 README 没有给出官方镜像或现成的容器构建文件。需要容器化的话，自己写一份 Dockerfile（基础镜像 + `requirements.txt` + `models/` 一起拷进去），镜像里的端口与启动方式参照下面的网页服务一节；不要假设存在某个官方镜像名。

模型文件随仓库分发，装成包时 `models/*.onnx` 会被一起安装，CLI 开箱可用。`models_ncnn/` 下的 `.bin` / `.param` 只服务于 NCNN 的端侧示例，不是 CLI 的必需资源。

## 常用操作

**1. 识别单张图片并打印 JSON**

```bash
chineseocr test_imgs/res.jpg
```

输出结构稳定，适合管道下游直接 `json.load`：

```json
{
  "text": "识别出的全文",
  "blocks": [
    {
      "text": "单个文本块",
      "score": 0.93,
      "box": [[12, 30], [210, 31], [209, 60], [11, 59]]
    }
  ],
  "elapsed": 1.24
}
```

`box` 是该文本块的四个角点坐标，`score` 是这一块的识别置信度，`elapsed` 是本次耗时（秒）。

**2. 结果落盘成 JSON 文件**

```bash
chineseocr test_imgs/res.jpg --output result.json
```

**3. 同时导出一张画了检测框的图**（排查漏检、错框最直观的抓手）

```bash
chineseocr test_imgs/res.jpg --output result.json --draw result.jpg
```

**4. 大图先压短边再检测**（CPU 上提速最有效的一招）

```bash
chineseocr test_imgs/res.jpg --compress 960
```

检测前会把图片短边缩到指定尺寸。手机直出照片动辄四五千像素，不压的话大部分时间都耗在检测网络上。

**5. 用模块方式跑**（入口脚本没装进 PATH，或者在别的 Python 环境里）

```bash
python -m chineseocr_lite test_imgs/res.jpg
```

**6. 起网页服务给人用**

```bash
cd chineseocr_lite
python backend/main.py
```

服务默认监听 `8089`，启动后终端会打印形如 `server is running: 192.168.x.x:8089` 的地址，浏览器打开即可上传图片识别。要长期在后台跑，用你惯用的进程守护方式托管这条命令。

Python 侧调用（把 OCR 嵌进自己的脚本里）请以仓库 `model.py`、`config.py` 当前暴露的接口为准；这两个文件是推理入口与模型/推理配置，版本演进时签名可能变化，用之前先读一眼。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 一张手机照片要跑十几秒，慢到没法批量 | 图片没做缩放，全分辨率进检测网络 | 用 `--compress` 把检测短边压到 960 一类可控值；批量任务里这一步几乎是必开的 |
| 装了 `chineseocr` 命令，运行时报找不到模型文件 | 模型只在「以包方式安装」时才随包进 site-packages；直接跑源码目录、或把脚本复制到别处执行，就找不到仓库里的 `models/` | 用 `pip install -e .` / `pip install .` 安装，或从仓库根目录运行；不要把单文件脚本抠出来单独用 |
| 想把 `models_ncnn/` 也打进去当 CLI 依赖 | 那批 `.bin` / `.param` 只给 NCNN 端侧示例用，不属于 CLI 必需资源 | 端侧集成时按对应 Demo 的说明单独取模型，别混进 CLI 部署包 |
| 以为能吃到 GPU 加速，结果一直是 CPU | 当前分支的主线是 ONNX Runtime **CPU** 推理，没有 CUDA 依赖 | 要 GPU 就看 NCNN 路线的端侧 Demo（含 Vulkan 版），或者接受 CPU 吞吐 |
| 网页打不开 / 局域网里别人访问不了 | 服务监听在 8089，且要放行防火墙；终端打印的那个 `ip:port` 才是实际监听地址 | 先看终端输出的地址，再看本机防火墙与端口占用；8089 被占就改服务配置里的端口 |
| 传 PDF 进去没反应 | 它只处理图片，不做 PDF 解析与渲染 | 先用 PDF 转图工具把页面导成 PNG/JPG，再喂给 OCR |
| 识别结果错字多、置信度普遍偏低 | 图片本身质量问题：倾斜、反光、低对比度、小字、复杂背景，轻量模型对这类输入很敏感 | 先做图片预处理——纠偏、裁掉无关区域、提高对比度、必要时放大；把 `--draw` 导出的图看一眼，确认是不是框本身就框歪了 |
| 中英混排里的英文单词被拆碎或串行 | 版面密集时文本块切分不稳，识别模型的字符集也有限 | 段落级重排要靠后处理：按 `box` 的纵坐标聚类成行、再按横坐标排序拼接，不要直接把 `blocks` 顺序当阅读顺序 |
| 想把训练权重、wheel、构建产物一股脑提交进 Git | 仓库 README 明确不建议这么做 | 大文件放 Releases、对象存储或 Git LFS，仓库里只留代码与推理用的小模型 |

参数名与可选值随版本会变，执行前用 `chineseocr --help`、`python -m chineseocr_lite --help` 或仓库当前 README 核对一遍，不要照搬旧版本的写法。

## 能力边界

**覆盖**：

- 中文印刷体文字检测与识别，输出全文、文本块、每块置信度与四点框坐标。
- 文字方向分类：处理横向翻转/旋转的文本行，检测与识别之间的常规环节。
- 命令行入口，输出结构稳定的 JSON，便于脚本与 Agent 解析。
- Tornado 网页服务与前端展示页面，浏览器内上传图片直接看结果。
- 纯 CPU 推理（ONNX Runtime），无 CUDA 依赖，适合内网与低配机器。
- 自带基础推理模型，随包安装即可跑；另附一份 NCNN 格式模型。
- 多端参考实现：C++（ONNX Runtime / NCNN / MNN）、JVM（JNI 封装）、Android、.NET（C# 与 VB.NET）。

**不覆盖**：

- 不做手写体识别。
- 不做版面分析、阅读顺序还原、表格结构化、公式识别。
- 不解码 PDF、Office 文档或视频帧——只吃图片。
- 不做图片预处理增强（纠偏、去噪、超分），需要时自行在前置环节完成。
- 不做多语种通用识别，日韩等语种不在保证范围内。
- 不提供训练/微调流程——仓库给的是推理代码与模型，不是训练框架。
- 不提供官方 Docker 镜像与云服务；多端 Demo 的「完整源码工程」上游提到可通过其社区渠道获取，本 Skill 不代为分发。

## 依赖条件

- 一个可用的 Python 环境。仓库 README 给出的推荐版本是 Python 3.6，实际可跑区间以 `requirements.txt` 为准。
- Windows / Linux / macOS 皆可；**CPU 推理，不需要显卡**。
- `requirements.txt` 里的依赖（推理运行时、数值计算、图像处理、Web 框架等，具体清单以文件当前内容为准）。
- 仓库自带的 `models/` 目录（`dbnet.onnx` 做文字检测、`crnn_lite_lstm.onnx` 做文字识别、`angle_net.onnx` 做方向分类）。
- 不需要账号、Token、API Key，也没有调用额度限制。
- 多端集成额外需要对应语言的工具链（C++ 编译器、JDK、Android SDK、.NET SDK）与相应推理运行时。

## 已知限制

- 精度定位是「够用且轻」，不是「最准」。复杂版面、小字、密集排版的识别质量会明显下降。
- CPU 推理的吞吐上限受核数限制，大批量任务要做好排队与限流。
- 只处理图片输入，PDF / 文档 / 视频需要自己在前面加一层转换。
- 输出是文本块级别，阅读顺序、段落合并、表格还原都要靠调用方后处理。
- 推理入口与配置（`model.py` / `config.py`）面向源码调用，参数签名随版本演进，不承诺稳定 API。
- 上游仓库在持续更新；参数名、模型文件名、目录结构都可能变化。执行前请以仓库当前 README、`--help` 输出与 `requirements.txt` 为准。本 Skill 不断言具体版本号、发布日期与 star 数。

## 自检清单

- [ ] 确认这次输入是**图片**；PDF 已提前渲染成图。
- [ ] 确认内容是印刷体中文；手写、表格结构、公式这类需求已经排除。
- [ ] Python 环境与 `requirements.txt` 依赖装全，`models/` 三个 ONNX 模型都在位。
- [ ] CLI 入口可用（`chineseocr --help` 或 `python -m chineseocr_lite --help` 有输出）。
- [ ] 大图已设 `--compress`，没有让全分辨率原图直接进检测网络。
- [ ] 需要给人看效果时用了 `--draw`，必要时人工核对框选位置。
- [ ] 批量任务是循环单张调用、还是走网页服务，已按吞吐需求选定。
- [ ] 后处理考虑了按框坐标做行聚类与阅读顺序重排，没有直接拿 `blocks` 顺序当段落顺序。
- [ ] 网页服务对外提供服务时，确认端口、防火墙与访问范围符合预期，不无意中把内网服务暴露出去。
- [ ] 结果里出现的个人信息（证件号、手机号、票据信息）按实际合规要求处理，没有随手外传。
