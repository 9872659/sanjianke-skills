# 三剪客 · 任务票据拆分

把需求或方案拆成一张张可跟踪、可独立交付的任务票据，写清边界、依赖与验收条件

需求交不出去，很少是因为写不出代码，多半是因为**没人说得清什么叫「做完了」**。一句话需求丢进群里，三个人理解成三件事，做完之后互相扯皮；或者一张票挂了六周，谁也不知道它卡在谁那儿。

这套 Skill 把「拆票」当成一门可以练的手艺：先给**判据**——一张票多大才合适、什么时候必须拆、什么时候拆了反而更贵；再给**字段规范**——标题、背景、范围、不做的事、依赖、验收条件、预估；然后用最多的篇幅讲**验收条件怎么写才可判定**，以及**依赖怎么表达**才不会变成一张永远打不开的结。三份参考资料分别对应判据与粒度、模板与示例、依赖与典型错误。

**读完你会拿到**：1 套拆票判据（拆/不拆各 6 条）、1 张粒度体检表、1 份七字段票据模板、验收条件可判定性四级标尺、依赖四类型与三种表达方式、18 条常见错误的识别信号与修法。

这套东西的价值不在于格式好看，而在于**换个人接手也能照着走完，且走完之后由第三方判定是否完成**。

## 触发场景

- 「这个需求一句话就丢过来了，我不知道从哪儿开始拆。」
- 「这张票挂了三个星期，谁也不知道卡在谁那儿。」
- 「做完了，但对方说『不是这个意思』，验收标准根本没写清。」
- 「一张票太大，拆完发现还得拉一个协调岗盯着。」
- 「两张票互相依赖，A 等 B、B 等 A，怎么切都切不开。」
- 「帮我看看这张票写得行不行，能不能直接派给同事。」

## 快速开始

最小可用路径是**先过三道闸，再落字段**。单张票 10 分钟，一个中等需求（5~8 张票）大约 40 分钟。

**第 1 步 · 判断要不要拆（3 分钟）**

拿手上这件事，先问三个问题：

| 闸门 | 问法 | 不过关的表现 |
|---|---|---|
| 可独立交付吗 | 这张票做完，能不能**单独合入主干 / 单独上线 / 单独给人看**？ | 做完必须等另一张一起才算数 → 这两张其实是一张 |
| 可独立验收吗 | 有没有一个人能在**不读你代码**的前提下判定它完成了？ | 判定要靠「你跟我说一声」→ 验收条件还没写 |
| 值不值得建票 | 它比**一次 15 分钟的口头同步**更贵吗？ | 更便宜 → 别建票，写条消息就行 |

三道闸全过才建票。任何一道不过，先回到 `references/splitting-criteria.md` 查拆票信号。

**第 2 步 · 按七字段落内容（5 分钟）**

七字段固定顺序，缺一个都别派出去：

```text
标题     ——  一句话，动作 + 对象 + 结果（≤ 40 字）
背景     ——  为什么现在做；不做的代价是什么（3 句以内）
范围     ——  这次动哪几个模块 / 哪几条路径 / 哪几类数据
不做的事 ——  显式列出这次明确不碰的相邻事项（至少 2 条）
依赖     ——  阻塞项与前置条件，写清「等谁、等什么、等不到会怎样」
验收条件 ——  逐条可判定，每条带判定方式和数据来源
预估     ——  量级 + 不确定性（如「2~3 天，偏大；接口未定」）
```

字段写法、正反例、完整填好的示例票见 `references/ticket-template.md`。

**第 3 步 · 给验收条件做可判定性体检（2 分钟）**

对每一条验收条件问三句，三句都能答上来才算过关：

1. **谁判**？—— 判定人是谁，他需要什么权限或工具才能看到结果。
2. **判什么**？—— 看的是哪个可测的量，或哪个可看见的产物。
3. **什么算不过**？—— 反例长什么样。写不出反例的条件，通常也不可判定。

四级判定标尺（L0 不可判定 → L3 自动判定）和 10 类含糊表述的改写见 `references/ticket-template.md` 的验收条件一节。

**第 4 步 · 画依赖，找环（贯穿全程）**

拆完一组票之后，把所有依赖箭头画出来：

- **有环**（A→B→A）说明切分错了，不是排期错了。修法见 `references/dependency-and-pitfalls.md`。
- **只有一个出口**（所有票都等同一张）说明那张票是**关键路径上的契约票**，它应该最薄、最先做。
- 把箭头方向统一成「本票等谁」，禁止双向标注，否则图一复杂就没人看。

**第 5 步 · 出口检查**

派票前逐条过 `## 自检清单`。任何一条打不上勾，先别派——一张含糊的票放出去，返工成本是写清它的十倍。

## 能力边界

**覆盖**：

- 判断一件事该不该建成票据，给出可复述的理由，而不是「感觉该拆」
- 按可独立交付 / 可独立验收的判据切分需求，控制单票粒度
- 提供五种切分维度的适用面与失效面（按用户路径、按数据流、按契约、按风险、按环境）
- 提供七字段票据模板、字段级正反例、3 张填好的完整示例票
- 提供验收条件的可判定性四级标尺、10 类含糊表述的改写方式
- 提供依赖四类型、三种表达方法、检测与拆解循环依赖的流程
- 提供 18 条拆票与依赖管理的常见错误：识别信号、代价、修法

**不覆盖**：

- **不替你做业务判断。** 它能告诉你「这张票的验收条件不可判定」，不能告诉你「这个功能该不该做」。做什么由业务侧负责。
- **不替代产品需求文档。** 票据是**执行单元**，不是需求本身。需求的价值、优先级、市场判断，票据承载不了。
- **不替你估算工期。** 它给的是「量级 + 不确定性」的表达规范，不是估点方法（扑克、三点估算一类）。真实工时取决于你们团队的历史数据。
- **不接入任何项目管理平台。** 不登录、不创建、不同步 Jira / 飞书 / TAPD / GitHub Issues。产出是文本，落地靠人。
- **不做排期与人天分配。** 谁做、做几天、并行几条，属于资源调度，本 Skill 只给依赖顺序这一层信息。
- **不负责组织流程改造。** 拆票能不能起作用，取决于团队是否真的按验收条件判定完成；这个前提本 Skill 保证不了。
- **不含任何脚本。** 判断与体检全靠人按清单走，避免把「格式填满了」误当成「票写对了」。

## 依赖条件

- **必需**：能读写 Markdown 或 CSV 文件。纯文本即可，不需要额外工具链。
- **必需**：需求或方案的原文（一句话也好）。没有原文就只能靠追问，产出质量会明显下降。
- **推荐**：已有票据列表的导出（哪怕只有标题）。用来查重、识别口径冲突和既有依赖。
- **推荐**：一个能画箭头的载体（白板、文本、表格都行）。依赖关系画出来和只在脑子里想，是两种结果。
- **不需要**：网络、API Key、数据库、Docker、任何项目管理平台的账号或付费服务。

## 已知限制

1. **验收条件的可判定性有天花板。** 涉及审美、体验、文案语气一类的交付物，最多做到「由指定人以书面标准判定」，做不到自动化。硬要写成布尔条件，只会得到一句自欺欺人的假精确。
2. **拆票救不了模糊的需求。** 如果需求本身没有结论（要解决谁的什么问题），拆出来的每张票都会继承这份模糊。这种情况应该先回去把需求问清楚，拆票只会把不确定性复制成更多份。
3. **粒度标准是经验值，不是物理定律。** 「一到三天」「一次能合入主干」这类锚点来自大量团队实践的中位数，你们团队的合理区间可能明显不同（比如强监管行业更小、内部工具更大）。用锚点起步，用你们自己的返工数据校准。
4. **依赖图会腐化。** 拆完当天画的图，一周后就有一半不准。依赖必须跟着票据状态更新，否则它会从沟通工具变成误导工具。
5. **票据格式不解决动机问题。** 如果团队不按验收条件判定完成、不按依赖顺序排期，再规范的票据也只是多了一层仪式。格式的价值只在被真正使用时才兑现。
6. **示例票是脱敏的合成案例。** 为了让字段结构清楚，示例里的项目、指标、人名都是构造的。请照着**结构**套，不要照抄数字。

## 自检清单

派票前逐条打勾；任何一条打不上，先别派。

- [ ] **标题自足**：只看标题就知道动作和对象，不需要点进去读背景
- [ ] **单票可交付**：这张票能单独合入主干 / 单独上线 / 单独给人看，不必等另一张
- [ ] **单一意图**：标题里没有「和」「以及」「顺便」。有的话，那就是两张票
- [ ] **背景有代价**：写清了「不做会怎样」，不是复述需求原文
- [ ] **范围有边界**：指明了动哪几个模块 / 路径 / 数据类型，不是「相关代码」
- [ ] **不做的事非空**：至少 2 条，且是真正容易被误以为包含在内的相邻事项
- [ ] **依赖有方向**：每条依赖都写清「等谁、等什么、等不到会怎样」，方向统一
- [ ] **无环**：依赖图里没有 A→B→A，也没有隐性互相等待
- [ ] **验收条件逐条可判定**：每条都能回答「谁判、判什么、什么算不过」
- [ ] **验收条件与实现解耦**：写的是可观察结果，不是「按某方案实现」
- [ ] **有反例**：至少一条验收条件写明了「什么情况算失败」或边界输入
- [ ] **预估带不确定性**：不只写天数，还写了偏大 / 偏小及原因
- [ ] **过三道闸**：可独立交付、可独立验收、值得建票，全部通过
- [ ] **不与既有票重复**：查过现有票据列表，没有覆盖同一交付物的票
- [ ] **脱敏**：没有真实密钥、Token、内网地址、客户名、未公开的价格
