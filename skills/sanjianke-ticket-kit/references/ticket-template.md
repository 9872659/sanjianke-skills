# 票据模板与示例

> 这份资料给三样东西：**七字段的填写规范（含正反例）**、**验收条件的可判定性标尺与改写方法**、
> **3 张填好的完整示例票**（实现类 / 探索类 / 契约类）。

---

## 一、七字段模板

固定顺序，缺一个都别派出去。每一节都可以直接复制去用。

```markdown
### 标题
<动作 + 对象 + 结果，≤ 40 字，不含并列连词>

### 背景
<为什么现在做；不做会怎样。3 句以内。>

### 范围
<这次动哪几个模块 / 哪几条路径 / 哪几类数据。列出可勾选的清单。>

### 不做的事
<显式列出这次明确不碰的相邻事项，至少 2 条。>

### 依赖
| 类型 | 对象 | 内容 | 等不到会怎样 |
|---|---|---|---|
| 阻塞 | <票号 / 人 / 系统> | <等什么> | <后果> |

### 验收条件
| # | 条件 | 判定方式 | 数据来源 | 判定人 |
|---|---|---|---|---|
| 1 | <可观察的结果> | <怎样算通过> | <在哪看> | <谁> |

### 预估
<量级 + 不确定性 + 最大的不确定来自哪里>
```

**关于顺序的一个细节**：`不做的事` 必须紧跟在 `范围` 之后。这不是排版偏好——写范围的时候脑子里正装着一堆「相关但这次不做」的东西，隔了几节再回来写，它们就跑了，然后它们会在执行期重新长回来变成范围蔓延。

---

## 二、字段规范与正反例

### 字段 1 · 标题

**要求**：动作 + 对象 + 结果。≤ 40 字。**不含并列连词**。

| | 例子 | 问题 |
|---|---|---|
| ❌ | 订单模块优化 | 没有动作，「优化」没有结果 |
| ❌ | 处理一下导出的事 | 不可执行，谁是「处理」 |
| ❌ | 导出改造和邮件模板调整 | 并列，是两张票 |
| ❌ | 重构 OrderService | 只有动作，没有对外的结果 |
| ✅ | 订单列表支持按手机号后四位搜索 | 动作 + 对象 + 结果，可演示 |
| ✅ | 导出接口的 P99 延迟从 8s 降到 2s 以内 | 结果带可测的量 |
| ✅ | 存量用户手机号字段完成加密回填 | 完成态明确 |

**自检**：只看标题，一个不了解上下文的人能说出「做完之后什么会不一样」吗？

### 字段 2 · 背景

**要求**：写**代价**，不写需求复述。3 句以内。

需求原文是「要支持搜手机号后四位」——这不需要在背景里重复。背景要回答的是「为什么现在必须做」。

| | 例子 |
|---|---|
| ❌ | 运营希望能搜索手机号后四位。（这是需求复述，不是背景） |
| ✅ | 客服每天处理约 40 单「用户记不住订单号」的求助，平均耗时 6 分钟；只能靠人工翻列表，日均约 4 人时。运营已提了三次。 |

**背景里必须有**：现状是什么、代价是什么（时间、钱、风险、投诉）、为什么是现在（触发事件）。

**背景里不该有**：解决方案（那是范围的事）、历史沿革（超过 3 句就该单独写设计文档）。

### 字段 3 · 范围

**要求**：可勾选的清单，指明具体的模块 / 路径 / 数据类型。

| | 例子 |
|---|---|
| ❌ | 相关代码、订单相关的部分 |
| ❌ | 前后端都要改（这不是范围，是废话） |
| ✅ | - [ ] `order-query` 服务的搜索条件解析<br>- [ ] 订单列表页的搜索框（仅 Web，不含 App）<br>- [ ] 新增索引 `idx_phone_suffix`<br>- [ ] 接口 `GET /orders` 新增可选参数 `phoneSuffix` |

**判据**：执行者看完 `范围`，能不能列出他要打开哪几个文件 / 哪几个后台页面？不能就不合格。

### 字段 4 · 不做的事

**要求**：至少 2 条。必须是**真正容易被误以为包含在内**的相邻事项。

这是最容易被敷衍掉的字段。写「不做的事：其他需求」等于没写。有效的「不做」必须满足：**读者看到范围时，真的会犹豫「这个算不算在里面」。**

| | 例子 |
|---|---|
| ❌ | 其他不相关的事情 |
| ❌ | 超出本次需求范围的内容 |
| ✅ | - 不做**模糊搜索**（只做精确匹配后四位）<br>- 不做 **App 端**（App 走另一套列表组件，下个迭代）<br>- 不做**权限收紧**（本次任何有订单查看权限的人都能搜）<br>- 不做**历史订单的索引重建**（只对新数据生效，存量下周单独处理） |

**额外价值**：`不做的事` 也是**评审的抓手**。评审时最有效的一个问题是：「这条『不做』，产品同意吗？」如果答案是犹豫，说明范围还没谈拢。

### 字段 5 · 依赖

**要求**：表格化，每条写清四件事——**类型 / 对象 / 内容 / 等不到会怎样**。

详细规范（依赖四类型、三种表达方式、环的拆法）见 `dependency-and-pitfalls.md`。这里只强调两点：

1. **方向统一**：全项目统一用「本票等谁」。禁止一半票写「本票等 A」、另一半写「A 被本票阻塞」，图一复杂就没人看。
2. **必须写后果**：「等不到会怎样」这一列不能空。写不出后果的依赖，大概率不是真依赖，只是「顺便提一下」。

| | 例子 |
|---|---|
| ❌ | 依赖后端接口 |
| ✅ | 阻塞 ｜ 票 #1042（契约票）｜ 等 `phoneSuffix` 参数名与错误码冻结 ｜ 等不到就没法定字段，客户端对接会返工 |

### 字段 6 · 验收条件

这是全篇最重要的字段，单独用第三节整节讲。

**一句话规范**：每条验收条件都必须能回答 **谁判、判什么、什么算不过**。

### 字段 7 · 预估

**要求**：量级 + 不确定性 + 不确定来自哪里。**只写天数是不合格的**。

| | 例子 |
|---|---|
| ❌ | 3 天 |
| ❌ | 2 天（乐观估） |
| ✅ | 1~2 天，偏小；不确定来自索引在千万级表上的建立耗时，若超过 30 分钟需要走 DBA 窗口 |
| ✅ | 3 天 ±1；不确定来自第三方接口的错误码是否覆盖全部失败场景 |

**为什么必须写不确定性**：一个不带不确定性的预估会被当成承诺。写下「不确定来自哪里」，等于提前告诉了排期者：这张票需要留缓冲，且缓冲区在什么位置。

## 三、验收条件怎么写才可判定

### 3.1 可判定性四级标尺

给每条验收条件定级。**L2 是最低合格线**，L0 和 L1 都不能派出。

| 级别 | 名称 | 特征 | 例子 |
|---|---|---|---|
| **L0** | 不可判定 | 靠主观感觉、靠当事人自述 | 「体验流畅」「代码质量好」「功能正常」 |
| **L1** | 弱可判定 | 有方向，但没有量、没有边界 | 「性能有明显提升」「错误提示更友好」 |
| **L2** | 可判定（合格线） | 有可观察的产物或可测的量，且写明了通过线 | 「搜索后四位 `1234`，返回 3 条以内结果，耗时 < 1s（在 1000 万行数据上）」 |
| **L3** | 自动判定（理想） | 有可重复执行的断言，无需人工判断 | 「CI 中 `npm run test:order-search` 全绿；该用例覆盖 4 类输入边界」 |

**重要**：不是所有条件都能到 L3，追求全部 L3 会导致形式主义（比如为了「自动化」写一堆永远不跑的空测试）。**合理分布大致是：L3 若干、L2 为主、L0/L1 为零。** 涉及审美、文案语气、体验类交付物，达到「L2 + 指定判定人 + 书面判定标准」就是上限，这是诚实的边界。

### 3.2 可判定性的三问

对每一条条件问：

**问 1 · 谁判？**
判定人是谁，他需要什么才能看到结果？

- 如果需要你有空的时候给他演示 → 不合格，改成「判定人可自行访问 <地址> 查看」
- 如果判定人就是你自己 → 大概率不合格，自证不算验收

**问 2 · 判什么？**
看的是哪个**可测的量**，或哪个**可看见的产物**？

- 可测的量：条数、耗时、成功率、金额、覆盖率、数量
- 可看见的产物：一个页面、一份文件、一条日志、一张报表、一段可运行的命令

**问 3 · 什么算不过？**
反例长什么样？边界输入是什么？

- 「搜索无结果时显示空状态而非报错」——反例是「报错 / 显示上一次的结果 / 白屏」
- 「并发 50 时不超时」——反例是「其中任意一个请求返回 5xx 或耗时 > 3s」

**写不出反例的条件，通常也不可判定。** 因为反例写不出来，说明你自己还没想清边界在哪。

### 3.3 三种验收口径（按交付物选）

| 口径 | 适用于 | 写法要点 | 常见陷阱 |
|---|---|---|---|
| **看物**（产物验收） | 有可见产物的交付：页面、接口、文档、报表 | 指明产物在哪、长什么样、包含哪些必要元素 | 只写「产出文档」，不写文档要回答什么问题 |
| **看数**（量化验收） | 性能、容量、准确率、成本类 | 指明量的定义、测量条件、通过线 | 不写测量条件（「耗时 < 1s」——在什么数据量、什么并发下？） |
| **看序**（过程验收） | 有顺序要求的操作流程、迁移、发布 | 指明每个节点的状态，以及中途失败的处置 | 只写终态，不写「中途失败怎么办」 |

### 3.4 十条判定模式的句式

不同性质的交付物，用不同的句式。下面十条基本能覆盖绝大多数情况。

| # | 模式 | 句式 | 示例 |
|---|---|---|---|
| 1 | **精确相等** | 输入 X 时，输出恰为 Y | 输入 `phoneSuffix=1234`，返回订单数恰为 3，订单号为 `A001/A007/A019` |
| 2 | **阈值区间** | 指标 M 在条件 C 下，满足 `>= / <= N` | 100 万行数据下，P99 延迟 ≤ 1s；10 万行下 ≤ 300ms |
| 3 | **集合包含** | 结果集合包含 / 不包含某元素 | 结果中不包含任何手机号明文；每条结果都带 `masked_phone` 字段 |
| 4 | **序列顺序** | 出现顺序为 A→B→C | 日志顺序为 `received` → `validated` → `persisted`，且不存在跳步 |
| 5 | **计数** | 某事件发生 N 次 / 某数量恰好为 N | 连续调用 3 次同参数接口，只产生 1 条订单记录（幂等） |
| 6 | **存在性 / 不存在性** | 某物存在 / 不存在 | 数据库表中不存在明文手机号列；`/healthz` 返回 200 |
| 7 | **状态迁移** | 状态从 S1 经操作后变为 S2 | 订单状态由 `PAID` 经退款操作变为 `REFUNDING`，且触发一条通知记录 |
| 8 | **回归保护** | 原有 N 项行为不变 | 现有 47 个订单相关用例全部通过；不加参数时返回结果与改动前逐字节一致 |
| 9 | **结论质量** | 结论回答了 M 个问题，且每个都有数据支撑 | 调研结论包含：3 个候选方案的延迟与成本对比表、推荐方案及理由、明确的不可行情形 |
| 10 | **人判标准** | 由指定人按书面标准判定 | 由 UI 负责人按《视觉走查清单》逐项判定，清单 12 项全部通过并留签字记录 |

**模式 9 和 10 是对付「不可判定」的救命句式**。探索票和体验票并非注定不可判定，只要把「谁来判、按什么标准判」写死，它们就是 L2。

### 3.5 十条含糊表述的改写速查

| 含糊表述 | 为什么不可判定 | 改写 |
|---|---|---|
| 功能正常 | 没有定义「正常」 | 覆盖表 A 的 6 种输入，其中 4 种正常返回 200、2 种返回 400 且错误码分别为 `E001`/`E002` |
| 性能有提升 | 没有基线，没有目标 | 同一数据集（1000 万行）下，P99 从 8s 降到 ≤ 2s |
| 兼容老版本 | 没说什么叫兼容 | 用 v1.2 客户端调用新接口，返回结构不变；v1.0 客户端调用返回 200 且忽略新增字段 |
| 体验流畅 | 主观 | 首屏可交互时间 ≤ 1.5s（4G，中端机型基准），且埋点上报 `first_interactive` 事件 |
| 尽量少改动 | 没有边界 | 变更文件数 ≤ 5 个，且不修改公共库 `common/*` |
| 错误处理完善 | 没有枚举 | 网络超时、鉴权失败、参数非法三种情形分别返回明确提示且不丢失用户已填内容 |
| 数据准确 | 没有口径 | 与对账系统比对，差异条数为 0；抽样 1000 条人工核对，准确率 ≥ 99.9% |
| 文档齐全 | 没有清单 | 文档包含：接口定义、错误码表、3 个调用示例、迁移步骤；且新人按文档能独立调用成功 |
| 界面友好 | 主观 | 由设计负责人按《视觉验收清单》12 项判定，全部通过 |
| 稳定可靠 | 没有条件 | 连续 24 小时压测（QPS 200），错误率 < 0.1%，无内存增长趋势（每小时增长 < 1%） |

### 3.6 验收条件的四条禁忌

1. **忌写成实现步骤**：「用 Redis 缓存查询结果」是实现，不是验收。验收应该是「相同查询 1 秒内 200 次，命中率 ≥ 90%」——至于用 Redis 还是本地缓存，是实现自由。
   - **判据**：如果换一种实现方式也能满足这条条件，它才是验收条件；如果换了实现就不成立，它是实现约束，该放进 `范围` 或设计说明。
2. **忌一条塞多个判定**：「搜索快、结果准、界面好看」——拆成三条。
3. **忌没有判定人**：没有判定人的条件，最后都会变成「做的人说做完了」。
4. **忌只写正向**：至少一条写失败路径或边界输入。只写正向条件的票，上线后出问题的概率明显更高——因为没人想过「如果……会怎样」。

### 3.7 一张票几条验收条件合适

经验区间 **3 ~ 7 条**。

- **少于 3 条**：先自查是不是漏了边界和回归。很多票的验收看起来只有一条，实际是因为「不存在性」和「回归保护」没写（模式 6、模式 8）。
- **多于 10 条**：大概率是票太大了（回到 `splitting-criteria.md` 的粒度体检表），或者把测试用例清单抄进了验收条件。验收条件是**判据**，不是测试用例全集——后者应该另附。

## 四、三张填好的示例票

示例都是构造的脱敏案例。**请照着结构套，不要照抄数字。**

### 示例 1 · 实现类（看物 + 看数）

```markdown
### 标题
订单列表支持按手机号后四位搜索

### 背景
客服每天处理约 40 单「用户记不住订单号」的求助，只能人工翻列表，单次约 6 分钟，
日均消耗约 4 人时。近一个月同类求助增长约 30%，运营已提三次。

### 范围
- [ ] `order-query` 服务新增可选查询参数 `phoneSuffix`，精确匹配后四位
- [ ] 订单列表页（仅 Web）新增搜索输入框，长度限制 4 位数字
- [ ] 新增索引 `idx_order_phone_suffix`
- [ ] 接口文档更新：`GET /orders` 参数说明与错误码

### 不做的事
- 不做模糊搜索（只做精确匹配后四位）
- 不做 App 端（App 走另一套列表组件，下个迭代处理）
- 不做权限收紧（本次任何有订单查看权限的人都能搜）
- 不做存量订单的索引重建（只对新数据生效，存量下周单独排票）

### 依赖
| 类型 | 对象 | 内容 | 等不到会怎样 |
|---|---|---|---|
| 阻塞 | 票 #1042 | 等 `phoneSuffix` 参数名与错误码冻结 | 客户端字段会返工 |
| 环境 | DBA 窗口 | 千万级表建索引需在低峰窗口执行 | 索引建不上，验收条件 3 无法满足 |

### 验收条件
| # | 条件 | 判定方式 | 数据来源 | 判定人 |
|---|---|---|---|---|
| 1 | 输入存在的后四位，返回结果只包含该后四位的订单 | 用 4 组已知数据比对，结果集与预期完全一致 | 测试环境接口响应 | 测试负责人 |
| 2 | 输入不存在的后四位，返回空列表且 HTTP 200，不返回错误 | 传 `0000`，响应体 `items: []`，状态码 200 | 测试环境接口响应 | 测试负责人 |
| 3 | 1000 万行数据下，该查询 P99 ≤ 1s | 压测工具单条件查询，取 P99 | 压测报告 | 后端负责人 |
| 4 | 不传 `phoneSuffix` 时，返回结果与改动前完全一致 | 拉取改动前后各 20 条响应逐字段比对 | 灰度环境 | 测试负责人 |
| 5 | 结果中不出现手机号明文，仅出现后四位或掩码字段 | 全量响应体正则扫描明文手机号 | 测试环境 | 安全负责人 |
| 6 | 输入非 4 位数字（如 `12a`、`12345`）时返回 400 及错误码 `E1042` | 传 5 组非法输入，逐条核对错误码 | 测试环境接口响应 | 测试负责人 |

### 预估
2~3 天，偏大；不确定来自索引在千万级表上的建立耗时。
若超过 30 分钟需走 DBA 低峰窗口，可能顺延一天。
```

**这张票为什么合格**：标题单一意图；背景有代价和触发；范围可勾选；`不做的事` 的 4 条都是评审时真会犹豫的；依赖写了后果；验收 6 条覆盖了正向、空结果、性能、回归、安全、边界六类，且每条都有判定人和数据来源。

### 示例 2 · 探索类（结论质量，模式 9）

```markdown
### 标题
完成三套候选缓存方案的对比并给出推荐结论

### 背景
查询服务当前无缓存，P99 延迟 8s 已影响客服使用。团队对方案有分歧，
其中两套需要引入新的中间件。需要一份带数据的结论来定方案，避免按直觉选型后返工。

### 范围
- [ ] 候选方案：本地缓存 / 集中式缓存 / 查询结果预计算
- [ ] 每个方案给出：延迟、成本、运维复杂度、故障影响面
- [ ] 用同一份生产数据抽样（100 万行）做基准测试
- [ ] 产出一份对比结论文档

### 不做的事
- 不做任何方案的落地实施（本票只出结论）
- 不做线上环境的真实部署（在预发环境做基准）
- 不评估与缓存无关的数据库优化手段

### 依赖
| 类型 | 对象 | 内容 | 等不到会怎样 |
|---|---|---|---|
| 前置 | 运维 | 预发环境开通集中式缓存的试用实例 | 该方案无法测，结论只能覆盖两套 |
| 数据 | 数据组 | 提供脱敏后的 100 万行生产数据抽样 | 基准测试只能用合成数据，说服力下降 |

### 验收条件
| # | 条件 | 判定方式 | 数据来源 | 判定人 |
|---|---|---|---|---|
| 1 | 结论覆盖全部 3 个候选方案，每个方案都有独立小节 | 逐节核对，缺一即不通过 | 结论文档 | 技术负责人 |
| 2 | 每个方案给出同一口径下的延迟数据（P50/P99） | 三个方案使用同一数据集、同一压测脚本 | 压测报告 | 技术负责人 |
| 3 | 每个方案给出月度成本量级估算，并注明估算依据 | 检查是否写明单价来源与假设 | 结论文档 | 技术负责人 |
| 4 | 给出明确的单一推荐方案，并说明其余方案被排除的具体原因 | 检查是否存在「都行」「视情况而定」的表述 | 结论文档 | 技术负责人 |
| 5 | 写明推荐的方案在什么条件下会失效（容量、一致性、故障场景） | 至少 3 条失效条件，每条带可观察的信号 | 结论文档 | 技术负责人 |
| 6 | 结论允许「三套都不可行并给出替代方向」——该结论同样视为完成 | 检查是否给出了替代方向 | 结论文档 | 技术负责人 |

### 预估
3~4 天，不确定性高；主要风险是预发环境的缓存实例开通时间不可控。
若实例无法开通，将按 2 个方案出结论并在文档中标明缺口。
```

**这张票为什么合格**：交付物是「结论」而不是代码，但验收条件仍然逐条可判定——因为写清了「结论必须回答哪 6 个问题」。条件 6 尤其重要：**给探索票留了一个合法失败的出口**，避免「探索失败 = 什么都没有」。

### 示例 3 · 契约类（维度 3，消环用）

```markdown
### 标题
冻结订单搜索接口契约并提供 mock 服务

### 背景
搜索能力需要客户端与服务端并行开工。如果等服务端实现完再对接，串行等待约 5 天。
先把契约定下来，双方可以同时开工，联调只在最后一天。

### 范围
- [ ] 定义 `GET /orders` 的完整请求参数与响应结构
- [ ] 冻结错误码表（至少覆盖：参数非法、无权限、超时、内部错误）
- [ ] 明确幂等语义与超时约定
- [ ] 提供可运行的 mock 服务，覆盖正常与 3 类异常响应
- [ ] 契约写入接口文档，并标注版本号

### 不做的事
- 不做真实的服务端实现（那是本票的下游票）
- 不做性能与容量验证
- 不做鉴权方案调整（沿用现有鉴权）

### 依赖
| 类型 | 对象 | 内容 | 等不到会怎样 |
|---|---|---|---|
| 前置 | 产品 | 确认搜索结果的字段范围与排序规则 | 契约可能少字段，下游返工 |
| 决策 | 技术负责人 | 错误码编号段的分配确认 | 错误码可能与他人冲突 |

### 验收条件
| # | 条件 | 判定方式 | 数据来源 | 判定人 |
|---|---|---|---|---|
| 1 | 契约中的每个字段都有类型、是否必填、示例值、边界说明 | 逐字段核对四要素，缺一即不通过 | 接口文档 | 技术负责人 |
| 2 | 每个错误码都有对应的触发条件与响应示例 | 逐个错误码检查，共 ≥ 4 个 | 接口文档 | 技术负责人 |
| 3 | mock 服务可本地启动，正常请求返回符合契约的响应 | 执行 `npm run mock` 后调用一次，响应通过契约校验 | mock 服务 | 客户端负责人 |
| 4 | mock 可模拟 3 类异常响应，由请求参数触发 | 传 `__mock=error_400/403/500` 分别得到对应响应 | mock 服务 | 客户端负责人 |
| 5 | 客户端按契约开发的代码在 mock 上可直接跑通，无需改动 | 客户端负责人用 mock 完成一次端到端调用 | 联调记录 | 客户端负责人 |
| 6 | 契约文档带版本号，且冻结后任何变更需记录变更原因 | 检查文档头部版本号与变更记录表 | 接口文档 | 技术负责人 |

### 预估
0.5~1 天；不确定性来自错误码编号段的协调，通常当天可确认。
```

**这张票为什么合格**：它极薄（半天到一天），但**解锁了所有下游的并行**。验收条件 5 是这类票的灵魂——它验证的不是「文档写好了」，而是「契约真的能让别人在没有真实服务的情况下干活」。

**契约票的反面**：写成「讨论一下搜索接口怎么设计」。没有交付物、没有冻结动作、没有 mock，下游票依然要等，环也没消掉。

## 五、从需求到票据的最小操作序列

```text
1. 抄下需求原文          —— 不要改写，先保留原话
2. 问出代价              —— 「不做会怎样？现在怎么凑合的？」→ 填进「背景」
3. 数可观察产物          —— 做完之后有几个不同的东西可以看？
                             > 1 个 → 候选拆分点
4. 过三道闸              —— 可独立交付 / 可独立验收 / 值得建票
5. 选切分维度            —— 用户路径 / 数据流 / 契约 / 风险 / 环境（只选一个）
6. 逐票写七字段          —— 顺序不要变
7. 给验收条件定级        —— 逐条检查 L0/L1，有就改写
8. 画依赖箭头            —— 统一方向，找环
9. 过粒度体检表 + 自检清单 —— 派票前的最后一道
```

第 6 步到第 7 步之间的顺序不要颠倒。先写范围再写验收，验收条件会自然地围绕「我打算怎么做」；如果先想清验收再写范围，范围会更聚焦在「什么算完成」上——后者产出的票质量明显更高。
