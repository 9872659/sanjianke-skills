# 自托管与云托管选型

这份文件解决一个具体问题：**在你动手之前，先把路线定死**。

选错的代价不是「慢一点」，而是几个月后推倒重来 —— 数据在云上、合规要求在本地、
或者反过来：自建了一套没人维护的 Docker 栈，出了故障只有一个人会修。

---

## 一、先纠正三个前提

绝大多数选型翻车，根因是把这三件事搞混了。

### 1. 本地开发栈 ≠ 自托管

命令行工具起的那一套（`init` + `start`）是**开发测试场**：

- 带固定开发凭据，不加固
- 上游明确说明它不面向生产、**不得暴露到外部流量**
- 数据放在本地 Docker 卷里，随意 `reset` 重建

自托管是另一条路径（Docker Compose 或社区部署方案），有真实的密钥管理、TLS、备份要求。

**判断口径**：如果你的部署命令里出现的是 `npx supabase start`，那它就不是生产环境。
生产要么用 `docker compose up -d`，要么用云托管。

### 2. 自托管 = 单项目

自托管的可视化管理台**不支持多组织 / 多项目**。整个栈就是一个项目，
绝大多数配置通过**环境变量**下发，而不是在界面上点。

这意味着：

| 你的诉求 | 自托管能给吗 |
|---|---|
| 一套环境跑一个产品 | 能，而且很合适 |
| 一套环境给 5 个业务线各开一个「项目」 | 给不了。要么开 5 套栈，要么自己做 schema 级隔离 |
| 类生产分支（branching） | 给不了 |
| 平台管理 API（自动化建项目、改配置） | 给不了 |

多项目管理是云托管的核心价值之一，自托管这块是空白。

### 3. 它不是一个数据库，是一圈服务加一个数据库

理解架构，选型时才知道自己会在维护什么。所有服务最终都打同一个 Postgres：

| 组件 | 角色 | 语言 / 形态 |
|---|---|---|
| Postgres | 核心，唯一的状态源 | C |
| Studio | 可视化管理台（表编辑、SQL 编辑器、策略构建器） | TypeScript |
| GoTrue | 认证服务，签发 JWT，与 RLS 联动 | Go |
| PostgREST | 把 Postgres 直接变成 RESTful API | Haskell |
| pg_graphql | 在 REST 之上再给一层 GraphQL | Postgres 扩展 |
| Realtime | WebSocket 引擎：在线状态、广播、数据变更流 | Elixir |
| Storage | S3 兼容对象存储，元数据存 Postgres | Node.js / TypeScript |
| Edge Functions | 边缘函数运行时 | TypeScript / Rust |
| postgres-meta | 给管理台用的 Postgres 元数据 REST API | Node.js / TypeScript |
| Supavisor | 多租户 Postgres 连接池 | Elixir |
| API 网关 | 统一入口，做鉴权与路由 | 见下方「网关换代」 |

**真实含义**：自托管你要维护的是 10 个左右有状态 / 无状态服务，
不是一个 `docker run postgres`。内存 4 GB 是能跑起来的底线，8 GB 才舒服；
不要实时、存储、函数的话可以从 compose 里删掉对应段落来降配。

## 二、两条路的端口与配置来源

**这一节的价值只有一个：让你不再背端口。** 端口会随发行版调整，
判断「真值在哪」比记住数字重要。

### 命令行本地栈

默认是 5432x 段，`supabase status` 会直接把结果打给你：

```
         API URL: http://localhost:54321
          DB URL: postgresql://postgres:postgres@localhost:54322/postgres
      Studio URL: http://localhost:54323
     Mailpit URL: http://localhost:54324
        anon key: eyJh......
service_role key: eyJh......
```

网关下面的路径前缀是固定的，两套环境一致：

| 服务 | 路径前缀 |
|---|---|
| 数据 REST API | `/rest/v1/` |
| 认证 | `/auth/v1/` |
| 存储 | `/storage/v1/` |
| 实时 | `/realtime/v1/` |
| 边缘函数 | `/functions/v1/` |
| GraphQL | `/graphql/v1` |

几个容易踩的点：

- 本地**没有真实短信**，验证码邮件落到 Mailpit 的 Web 界面里，别去邮箱找。
- 从容器里访问宿主机的本地栈，要把 `localhost` 换成 `host.docker.internal`。
- 不想一个个查端口，用机器可读输出：
  ```bash
  npx supabase status -o env          # 输出的键值可直接 source
  npx supabase status -o json
  ```

### Docker 自托管

自托管**不是** 5432x 段，别照抄上面的数字。真值在这里：

```bash
cd supabase-project
grep -nE "PORT|URL" .env            # 端口与地址配置
docker compose ps                   # 实际映射到宿主机的端口
docker compose port api-gw 8000     # 单个服务的映射结果
```

`docker-compose.yml` 里暴露到宿主机的端口，通常通过 `.env` 变量控制。
**关键是先确认 `.env` 里这些键的值，再决定端口要不要改**：

| 变量 | 作用 |
|---|---|
| `POSTGRES_PORT` | Postgres 映射到宿主机的端口 |
| `KONG_HTTP_PORT` / 网关 HTTP 端口 | API 网关与 Studio 的入口端口 |
| `KONG_HTTPS_PORT` | 网关 HTTPS 端口 |
| `POOLER_PROXY_PORT_TRANSACTION` | 连接池的事务模式端口 |
| `POOLER_PROXY_PORT_SESSION` | 连接池的会话模式端口 |
| `ANALYTICS_PORT` | 分析服务端口（启用分析叠加文件时） |

认证与密钥类变量（**这些才是自托管的真实工作量的来源**）：

| 变量 | 说明 |
|---|---|
| `POSTGRES_PASSWORD` | 数据库超级用户密码 |
| `JWT_SECRET` | JWT 签名密钥。改了它，**所有已签发的 key 全部失效**，必须重新生成 |
| `ANON_KEY` / `SERVICE_ROLE_KEY` | 旧式 HS256 JWT，用 `JWT_SECRET` 签出 |
| `SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY` | 新式不透明 key（`sb_publishable_*` / `sb_secret_*`） |
| `ANON_KEY_ASYMMETRIC` / `SERVICE_ROLE_KEY_ASYMMETRIC` | 非对称（ES256）版本的 anon / service_role |
| `DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD` | 管理台的基础认证账号 |
| `SUPABASE_PUBLIC_URL` / `API_EXTERNAL_URL` / `SITE_URL` / `PROXY_DOMAIN` | 对外地址，影响邮件链接、OAuth 回调、签名校验 |

**新式 key 的格式**（发布前对一下，别把 key 类型搞混）：

```
sb_publishable_<22 位随机>_<8 位校验>
sb_secret_<22 位随机>_<8 位校验>
```

语义映射，务必记牢：

| key | 等价于 | 是否绕过 RLS | 能放前端吗 |
|---|---|---|---|
| `ANON_KEY` / `sb_publishable_*` | 匿名角色 | 否 | **能**（设计如此，靠 RLS 兜住） |
| `SERVICE_ROLE_KEY` / `sb_secret_*` | 服务角色 | **是** | **绝对不能** |

旧式与新式**可以并存**。自托管里有一套脚本负责生成新 key 与 JWKS，
并自动打开 compose 文件里对应的环境变量段；切换后要重建容器让配置生效。
注意一个坑：**若用 `podman-compose`，嵌套变量插值（`${A:-${B}}`）需要较新版本**，
老版本会解析失败，届时按 compose 文件里的注释改成直接写变量。

### 网关换代

较新的自托管发行版默认用 **Envoy** 做 API 网关，监听一个统一端口，
同时**保留 `kong` 作为网络别名**方便老配置过渡。

网关做三件事：路由、校验 `apikey`、把不透明 key 翻译成内部 JWT。
它还会：

- 对管理台那条兜底路由启用基础认证，并且**剥掉进来的 `Authorization` 头**，
  凭据不会流到下游
- 对 `/pg/`（元数据接口）与 `/rest/v1/` 根路径**只放行 secret key 等级**
- **默认拒绝** `/mcp` 与 `/api/mcp` 路由；要开得手动改 RBAC 规则

**判断口径**：你的 compose 文件里服务名与端口写的是哪个，就以哪个为准。
看到别人文章里写 Kong 不必困惑，但改文件时要改对文件。

## 三、云托管拿走了什么、留下了什么

自托管的**能力缺口**（这部分只能靠云托管或自己补）：

- 分支（branching）
- 托管备份与时间点恢复（PITR）
- 日志之外的进阶指标
- 分析与向量桶
- ETL
- 平台管理 API
- 多组织 / 多项目管理

自托管的**优势**：

- 数据不出你的机房，合规审计好过
- 内网部署，可以完全断外网
- 单机成本可控（一台 8 GB 的机器就能扛中小流量）
- 想改哪个组件就改哪个，没有黑盒

另外两个容易忽略的事实：

- **自托管 Docker 版本不上报遥测**，不会回传任何数据。
- **命令行工具会采集使用遥测**（用于改进开发体验）。两者不是一回事，
  如果合规同学问「它会不会回传」，要分开回答，并说明命令行工具有关闭方式。

## 四、取舍维度：按这个顺序问自己

按重要性排序，**前面几条一旦是否定答案，后面的比较就没意义了**。

### 第 1 问：有没有硬性合规要求？

「数据必须留在境内 / 自己机房 / 指定 VPC」——如果有，直接自托管，后面不用比了。

如果没有，也不要默认云托管：先看下面第 2 问。

### 第 2 问：有没有人能长期维护它？

自托管的真实成本不在搭建（半天能起来），在**长期**：

| 你要负责的 | 不做会怎样 |
|---|---|
| 操作系统与容器镜像更新 | 漏洞长期暴露 |
| Postgres 主版本升级与大版本迁移 | 被锁死在老版本，将来迁移更痛 |
| 备份与**恢复演练** | 出事时备份不可用 |
| 监控与告警 | 故障靠用户投诉发现 |
| 容量与连接数管理 | 流量一涨就连接打满 |
| 高可用 | 单机挂了就全挂 |

**判断口径**：如果这个问题你答不上来「谁负责、每周投入多少小时」，选自托管就是在给自己挖坑。
自托管被官方定义为**社区支持**，不包含商业 SLA。

### 第 3 问：用不用得上平台级能力？

分支、PITR、多项目、平台管理 API —— 团队规模一大，这几个的替代成本极高。
自己实现一套等价的分支与 PITR，比省下的托管费贵得多。

### 第 4 问：成本怎么算才对

不要只算机器钱。完整的对比口径：

| 成本项 | 云托管 | 自托管 |
|---|---|---|
| 订阅 / 实例费 | 按用量或套餐 | 0（软件本身免费） |
| 服务器 | 0 | 机器 + 带宽 + 快照存储 |
| 人力 | 低（但要有接触点） | **主要成本，且随服务数量放大** |
| 备份存储 | 含 | 自购并自己验证 |
| 故障损失 | 有 SLA 兜底 | 自己承担 |
| 迁移成本 | 出站相对方便 | 进出一视同仁，标准工具可迁 |

**经验口径**：小团队自托管要真正省下钱，得把「人」的成本压到很低
（也就是第 2 问答得漂亮）。否则总账常常是自托管更贵，只是贵在了看不见的地方。

### 第 5 问：需不需要隔离环境

自托管天然适合「一套内网环境 + 一套完全断网环境」这种硬隔离诉求。
云托管的多环境要靠多个项目或分支实现，隔离度不如物理分机房。

## 五、决策路径

```
有硬性合规 / 数据落地要求？
├─ 是 ── 自托管（Docker Compose 或社区方案）
│        └─ 且确认：有明确维护负责人 + 接受社区支持
└─ 否 ── 需要分支 / PITR / 多项目 / 平台 API？
         ├─ 是 ── 云托管
         └─ 否 ── 有人长期维护 + 规模不大 + 想省钱？
                  ├─ 是 ── 自托管
                  └─ 否 ── 云托管（把人力留给业务）
```

## 六、混合形态：几条常见且好用的组合

**1. 本地开发 + 云托管生产**（最主流）

本地用命令行栈跑迁移与测试，生产用云托管。表结构与策略都走迁移文件，
两个环境用同一批 SQL，差异只在密钥与地址。

**2. 本地开发 + 自托管生产**

同上，只是发布目标换成自己的 Docker Compose。要额外做的是：
`.env` 与密钥管理、TLS 反向代理、备份脚本、镜像更新流程。

**3. 云托管做非敏感业务 + 自托管放敏感数据**

拆开的代价是跨环境一致性（两套策略要分别维护），收益是核心数据不出内网。
做这个选择前先确认：业务能不能真的拆得干净。

**4. 开发 / 预发 / 生产三套自托管栈**

三套 `.env`、三套密钥、三套备份。注意**密钥绝不能跨环境复用**，
预发用生产密钥是最常见的越权路径。

## 八、四个最常见的选型错误

1. **把命令行本地栈当生产用**。端口开放到公网，凭据是默认值。
   这是最危险也最常见的一种。

2. **先搭自托管，发现没人维护，又整体迁云**。
   来回两次的迁移成本远高于一开始就选云托管。第 2 问没答清楚就别开工。

3. **以为自托管能省掉全部托管成本**。省的是订阅费，花的是人力。

4. **在同一套环境里想跑多个「项目」**。自托管给不了，
   硬用 schema 隔离去做业务线隔离，最终会在权限与备份粒度上付出代价。
