# 三剪客 · Postgres 应用后端 Skill

Supabase 自托管选型、表设计与 RLS 权限落地

---

## 前置条件

| 项 | 要求 |
|---|---|
| Docker | Docker Engine + Compose v2（`docker compose`，不是 `docker-compose`）；自托管路线必需 |
| Node.js | 20 或更高 —— 用 `npx supabase` 跑 CLI 的硬要求，16 会直接失败 |
| 客户端 | `psql` 或任意 Postgres 客户端，排查策略时必用 |
| 资源 | 自托管最低 4 GB 内存 / 2 核 / 40 GB 盘；推荐 8 GB+ / 4 核+ / 80 GB+ |
| 网络 | 拉镜像、安装 CLI、访问云托管 API |

## 使用

这个 Skill 是给 Agent 读的作业规范。三种用法：

**1. 选路线（动手之前）**

问它「我这个项目该自托管还是云托管」。它会按合规要求、维护人力、平台能力需求、
成本口径四个维度逐条问，最后给出决策路径与一张信息收集表。

**2. 建表与配权限（最常用）**

问它「帮我加一张 XX 表，只有本人能读写」。它会输出一份**同时包含**
建表、索引、开启 RLS、收窄授权、四条策略的完整迁移，并附上验证用的自检 SQL。

**3. 上线前体检与排错**

问它「上线前我要检查什么」，它会给出 9 条可直接粘贴执行的漏权检查清单。
出故障时按决策表排查：`42501` 查授权、「空数组」查策略、
「能查到别人的数据」跑完整清单。

Agent 在本项目里的十条防错规则，见 `references/deploy-and-troubleshoot.md` 第六节。

## 依赖

- 无 Python / Node 运行时依赖，本 Skill **不附带可执行脚本**，全部是 SQL 与 shell 命令
- 涉及的能力都由你自己的环境提供：Docker、命令行工具、`psql`
- 所有示例中的密钥一律用占位符或环境变量表示

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | **仅核对事实时** | 查询镜像标签、组件端口分配、发布说明与许可证页面；不调用业务接口、不上传数据 |
| 读取文件 | 仅读取你指定的目录 | 读 `config.toml`、迁移 SQL、compose 文件、`.env`（只看键名） |
| 写入文件 | 默认不写；仅在你明确要求时 | 生成迁移 SQL 或配置模板；不覆盖已有迁移 |
| 凭证 | **不读取、不打印** | 不接触 `POSTGRES_PASSWORD` / `JWT_SECRET` / `service_role` key / `sb_secret_*` |
| 子进程 / 后台常驻 | 仅在你要求时执行只读命令 | `docker compose ps` / `logs`、`supabase status` / `db lint`、`psql -c`（只读） |

本 Skill **不内嵌任何密钥、Token 或 Cookie**，不代持你的数据库账号。

> **一条必须知道的事实**：`service_role` 与 `sb_secret_*` key 会**完全绕过行级安全**。
> 它们只能出现在服务端。任何一次把它们打进前端产物、贴进聊天记录或写进日志，
> 都等同于交出整库。

## 安全

- 不内嵌任何密钥
- 不主动把任何内容发往外部地址
- 若正文涉及联网或读写文件，权限范围已在上面「权限与用途说明」中逐项列明
- 检查清单里的全部 SQL **只读**，不改数据、不改配置
- 模拟身份的语句（`set local role ...`）一律要求在**本地或预发**执行，禁止在生产库上切角色
- 不执行生产变更：不写生产库、不改线上 `.env`、不重启你的服务
- `docker compose down -v` 这类会删数据卷的命令只输出、不执行

## 能力边界

**覆盖**：自托管与云托管选型、两套端口与配置来源对照、表设计规范、
GRANT 与 POLICY 两层权限模型、RLS 策略写法与漏权检查清单、RLS 性能优化、
连接池选择、备份升级回滚、故障排查决策表、Agent 十条防错规则。

**不覆盖**：不搬运上游文档与代码；不替你拍板选型；不写你的业务代码；
不做企业级 HA 与容量规划；不涉及 ETL 与向量检索；不执行任何生产变更。
