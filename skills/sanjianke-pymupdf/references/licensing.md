# 许可证：AGPL 与商业授权的分界

> 这份文件是对上游许可条款的**整理与解读**，不是法律意见。最终以官方 `COPYING` 文件、AGPL-3.0 原文与 Artifex 的授权条款为准；拿不准请咨询法务。

---

## 一、基本事实

PyMuPDF 与它底层的 MuPDF 都由 **Artifex Software, Inc.** 维护，采用**双授权**：

| 授权方式 | 适用于 | 成本 |
|---|---|---|
| **GNU AGPL v3** | 开源项目 | 免费 |
| **Artifex 商业许可证** | 专有 / 闭源应用 | 需向 Artifex 付费购买 |

官方 README 的原话口径是：AGPL「对开源项目免费」，商业许可证「面向专有应用」。

仓库里的 `COPYING` 文件承载 AGPL 全文，PyPI 上的许可证字段写的是 **"Dual Licensed - GNU AFFERO GPL 3.0 or Artifex Commercial License"**。

**注意**：本 Skill 包自身的 `LICENSE.md` 是 MIT，那是**这份文档的许可**，与 PyMuPDF 的许可无关。装 PyMuPDF 时生效的是它的 AGPL / 商业双授权。

---

## 二、AGPL 与 GPL 的关键差别

很多人对 GPL 有直觉，但 AGPL 多了一条**专门针对网络服务**的条款（AGPL-3.0 第 13 节），这是最容易踩的地方：

| 场景 | GPL 的典型效果 | AGPL 的效果 |
|---|---|---|
| 分发二进制给他人 | 必须提供对应源码 | 必须提供对应源码 |
| 只在自己服务器上跑，用户通过网络访问 | 不触发分发义务（因为没分发二进制） | **可能触发源码提供义务**——AGPL 第 13 条要求：若用户通过网络与该程序交互，应向其提供获取对应源码的机会 |
| 内部平台给其他团队用 | 一般不算分发 | 需要评估是否构成「网络交互」 |

**所以「我们不分发，只做 SaaS」不是 AGPL 的安全港。**

## 三、判定场景清单

按「风险从低到高」排列。请对号入座。

### 通常无额外负担

- 开源项目（本身以 AGPL 兼容的许可证发布），并且合规地提供了源码。
- 个人研究脚本、内部一次性数据分析，不对外提供服务也不分发。
- 完全内部使用、不通过网络暴露给外部用户，且不向外分发二进制。

**注意**：即使是内部使用，一旦公司政策或客户合同要求「不得引入 AGPL 代码」，仍然要另行评估。

### 需要认真评估

- **SaaS / Web 服务**：程序跑在你的服务器上，用户通过 HTTP 接口间接使用。AGPL 第 13 条的射程覆盖这里。
- **内部平台**：产品团队用你搭的 PDF 处理服务，服务由别的团队消费。是否构成「网络交互」取决于具体形态，按保守口径应当评估。
- **打进对外提供的 Docker 镜像**：镜像分发本身就是分发行为；如果镜像还对外提供服务，两种义务叠加。
- **闭源桌面应用**里静态 / 动态链接 PyMuPDF，然后分发给客户。

### 通常必须商业许可证

- 闭源商业产品直接分发 PyMuPDF 或包含它的镜像，且不愿意以 AGPL 开放对应源码。
- 上述任何场景中，公司政策明确禁止 AGPL 依赖。

## 四、商业之外的三条出路

如果评估结论是「AGPL 不合适」，有三条路：

**1. 买 Artifex 商业许可证。**
最直接。授权范围、报价、覆盖的产品形态，都向 Artifex 确认。官方 README 指向他们的 licensing 页面。

**2. 换成宽松许可的替代方案。**

| 方案 | 许可证 | 代价 |
|---|---|---|
| `pdfplumber` | MIT | 只能读不能写；性能远低于 PyMuPDF（官方自己承认 PyMuPDF「substantially faster」）；表格提取可调性更强，但速度是瓶颈 |
| `pdfminer.six` | MIT | 只做解析与文本提取；没有表格提取、没有可视化调试 |
| `pypdf` / `PyPDF2` | BSD | 能拆分、合并、裁剪、旋转、加元数据、设密码；文本提取能力弱，没有形状对象、没有表格提取 |
| `camelot` / `tabula-py` / `pdftables` | MIT / BSD | 专注表格提取，某些表格上效果更好；不覆盖其他 PDF 操作 |
| Poppler 系工具（`pdftotext` / `pdftoppm`） | GPL 系 | 命令行工具，许可同样要评估；通过子进程调用会引入新问题 |
| Ghostscript / `qpdf` | AGPL / Apache-2.0 | 各自不同，要单独看。Gotenberg 就是把 qpdf、pdfcpu、pdftk 等打包成服务 |

**3. 拆分成独立进程 + 明确接口。**
把 PyMuPDF 封成一个独立可执行程序，主程序通过命令行或 IPC 调用它，只在内部使用。这**可能**把 AGPL 的传染范围限制在那个独立程序里——但这属于「聚合」与「衍生作品」的边界判断，**风险自负，必须咨询法务**。不要以为换个进程边界就万事大吉。

## 五、PyMuPDF Pro 与 PyMuPDF4LLM

**PyMuPDF Pro** 是独立销售的产品，增加 Office（DOC / DOCX / XLS / XLSX / PPT / PPTX）与韩文 Office（HWP / HWPX）格式支持。

- 用 `pymupdf.pro.unlock("你的许可证Key")` 解锁。
- **不带 Key 调用 `unlock()` 时有明确限制**：任意文档**只能访问前 3 页**，并且功能在评估期结束后失效。
- Pro 的能力与 AGPL 开源版是分开授权的——**开源许可证不覆盖 Pro**。

```python
import pymupdf.pro

pymupdf.pro.unlock("YOUR-LICENSE-KEY")

doc = pymupdf.open("presentation.pptx")
pdf_bytes = doc.convert_to_pdf()
```

**PyMuPDF4LLM** 是另一个独立的包（`pip install pymupdf4llm`），提供面向 RAG 的 Markdown / JSON / 文本输出。它由同一方维护，**其授权条款需单独确认**——不要假设和核心包一样，也不要假设它自动包含在你的商业许可证里。

## 六、实务建议

1. **选型第一件事就查许可**，不要等上线前才发现。把「许可证」写进技术选型文档的一栏，和性能、功能并列。
2. **在自己的代码库里显式记录**你用了 PyMuPDF、用途是什么、走的是哪种授权。日后审计时这一条能省很多事。
3. **依赖扫描工具配置规则**：把 AGPL 设为需要人工复核的级别，别让它被自动批准。
4. **别把「能跑起来」当成「能商用」**。`pip install pymupdf` 一句话就装好了，没有任何弹窗提醒你许可问题——这是最容易翻车的地方。
5. **区分「用」和「分发」**：同一个库，用在内部脚本和打进对外镜像里，合规结论完全不同。按最坏的那个场景做规划。
6. **保留证据**：如果买了商业许可证，把授权文件放在显眼位置并记录覆盖范围（哪些产品、哪些版本、多少席位）。
7. **AGPL 不等于不能碰**。它只是要求你在特定条件下开放源码。如果项目本身开源，或者你能接受开放相应源码，它就是免费的。
