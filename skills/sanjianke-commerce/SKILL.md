# 三剪客 · Next.js 电商前端模板

做电商前台时，首页、商品列表、商品详情、分类、搜索、购物车、结算这些页面几乎每家都一样，真正费时间的不是画页面，而是**「数据从哪来、怎么写到哪去」**。这个模板把前者提前写好了（用 App Router 的服务端渲染），并把后者收敛成一个可以被替换的数据层——你对接哪家电商平台，就实现哪一层。

它的产品属性要认清：这是一个**前端起点**，不是电商平台本身。商品、库存、价格、订单、支付都来自你配置的那家外部平台。仓库当前版本默认对接的是 Shopify，其他平台由各自的第三方实现分支提供，做法是替换数据层实现、保留其余模板结构。

还有一条时效性信息很关键：上游说明未来的精力只投在默认那一家平台的实现上，所以选它之前要先确认你打算对接的平台有没有人在维护对应的实现。

**上游项目**：`commerce`　**仓库**：https://github.com/vercel/commerce

## 什么时候用 / 不用

**用它**：

- 要做一个**面向消费者的电商前台**，并且接受「商品和订单托管在外部平台、自己只做展示与交互」这件事。
- 团队已经是 Next.js / React 技术栈，想直接拿到一份用 App Router + 服务端组件写成的电商骨架，而不是从零设计目录结构。
- 需要一个**可替换的数据层**：先用默认平台跑通，之后再换到别家时只重写一层，页面基本不动。
- 要参考一份现代电商前端的工程实践：流式渲染、局部预渲染、乐观更新、图片远程域名与尺寸处理都配好了。
- 想把前台部署到支持 Next.js 的托管平台，走「拉代码 → 配环境变量 → 部署」这条最短路径。
- 需要一个能改的起点：模板里的组件与样式都可以直接改，不依赖某个可视化建站后台。

**不要用它**：

- **不想写代码只想开店**。这是开发者模板，装完不会自动拥有一个能卖货的店铺，还要接平台、配密钥、部署。
- **需要后台管理系统**。它只有消费者侧的前台，没有商品上架、订单处理、退款审核这类管理界面。
- **需要一个完整电商后端**。订单、库存、支付、履约全在外部平台，模板不提供这些能力，也不改变它们的规则。
- **打算对接的平台不在已维护列表中**。默认只持续维护一个平台的实现，其余是第三方分支，选错平台等于自己要接一大堆。
- **没有外部平台账号**。本地连跑起来都需要平台的店铺域名与访问令牌，拿不到就只能看到一个空架子。

## 安装

**前置**

- Node.js，以及 pnpm 作为包管理器（仓库脚本与说明都按 pnpm 写）。
- 一个电商平台店铺（当前默认实现对应的是 Shopify）与其访问令牌。
- 部署或本地拉取环境变量时需要一个托管平台账号与其命令行工具。

**第 1 步：拿到代码并安装依赖**

```bash
pnpm install
```

**第 2 步：准备环境变量**

仓库里给了 `.env.example` 作为字段清单，按它准备一份 `.env`。当前版本需要填的键是：

| 变量 | 用途 |
|---|---|
| `COMPANY_NAME` | 站点归属主体名称 |
| `SITE_NAME` | 站点名称 |
| `SHOPIFY_STORE_DOMAIN` | 平台店铺域名（形如 `<子域>.myshopify.com`） |
| `SHOPIFY_STOREFRONT_ACCESS_TOKEN` | 店面访问令牌 |
| `SHOPIFY_REVALIDATION_SECRET` | 缓存失效回调的校验密钥 |

上游明确提醒：**这个文件不要提交到仓库**，否则等于把店铺的控制权限公开出去。

**第 3 步：把环境变量拉到本地（推荐做法）**

```bash
npm i -g vercel
vercel link          # 关联本地目录与托管平台项目
vercel env pull      # 把远端环境变量拉到本地
```

**第 4 步：启动**

```bash
pnpm dev
```

起来之后应用默认在 `http://localhost:3000`。

**部署**

仓库 README 顶部提供了一键部署入口：把仓库克隆到你自己的托管平台项目，安装时带上平台集成与两个基础环境变量。也可以自己走「关联项目 → 配环境变量 → 部署」。具体流程以托管平台当前的界面与官方文档为准。

## 常用操作

**1. 本地开发**

```bash
pnpm dev
```

脚本内部走的是带 Turbopack 的开发模式。

**2. 生产构建与启动**

```bash
pnpm build
pnpm start
```

**3. 格式化检查（仓库当前把它当作测试入口）**

```bash
pnpm test
```

这条实际执行的是格式一致性检查，不跑单元测试；要写入格式化结果用 `pnpm prettier`。

**4. 让平台侧变更即时反映到页面**

模板里已经有一个 `/api/revalidate` 路由，它会调用数据层里的失效逻辑。真实用法是在平台侧配置回调（Webhook）指向这个地址，并用 `SHOPIFY_REVALIDATION_SECRET` 做签名校验。请求体格式与签名算法**以平台侧文档为准**，不要凭猜构造请求体验证。

**5. 换一家电商平台**

做法是替换数据层里对应平台的实现文件，其余模板结构基本不用动。上游列出了若干由第三方维护的实现，选之前先确认它跟得上模板当前版本。

**6. 看一眼当前依赖基线**

```bash
node -p "JSON.stringify(require('./package.json').dependencies, null, 2)"
```

模板依赖 Next.js、React、Tailwind CSS 等，具体版本以你 `package.json` 里锁定的为准；`next.config.ts` 里还开了图片远程域名（平台 CDN）与几项实验特性开关，改之前先确认目标部署环境支持。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 页面能开但商品全空 / 接口报鉴权错误 | 店铺域名、访问令牌缺失或令牌范围不足 | 逐项核对 `.env.example` 里的键，确认令牌是为店面访问签发的且范围正确 |
| 回调地址一直校验失败 | 缓存失效回调的校验密钥与平台侧配置不一致 | 两侧用同一个 `SHOPIFY_REVALIDATION_SECRET`，并按平台文档实现签名校验，不要自己简化 |
| 把环境变量文件提交上去了 | 该文件没有被忽略 | 立刻在平台侧轮换令牌与密钥，并把它加进忽略列表；上游明确警告过这一条 |
| 本地 `pnpm dev` 起不来，提示找不到环境变量 | 只在远端配了变量，没拉到本地 | 用托管平台命令行工具先关联项目再拉取环境变量 |
| 换成另一家平台后大部分页面报错 | 只改了配置没有实现对应的数据层 | 数据访问是单独一层，换平台要实现这一层；页面组件本身不含平台逻辑 |
| 依赖装完行为跟文档不一致 | 用了别的包管理器，依赖树与锁文件不一致 | 统一用 pnpm，别在同一个仓库里混用包管理器 |
| 生产环境图片不显示 | 图片远程域名白名单只放行了默认平台 CDN | 在 `next.config.ts` 的图片配置里按目标平台域名调整 |
| 上线后平台侧改价 / 改库存，页面很久才更新 | 缓存失效回调没有真正接上 | 在平台侧配置 Webhook 指向 `/api/revalidate`，并确认密钥与签名都对 |
| 关掉实验特性后构建报错 | 模板用到了流式渲染与局部预渲染相关的实验开关 | 保持模板给出的配置，或按 Next.js 文档确认当前版本对应用法后再改 |

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 拉取 npm 依赖；向电商平台接口读取商品、购物车与结算数据；向托管平台拉取环境变量 |
| 读取文件 | 是 | 读取项目源码、配置、`.env` 环境变量文件与锁文件 |
| 写入文件 | 是 | 安装依赖、生成构建产物与缓存目录、格式化命令改写源码 |
| 凭证 | 是 | 平台店面访问令牌、缓存失效校验密钥、托管平台账号登录态。**本 Skill 不内嵌任何密钥**，请用环境变量或托管平台的变量管理功能 |
| 子进程 / 后台常驻 | 是 | 开发服务器与构建命令都是可中断的前台进程；部署后由托管平台常驻运行 |

## 触发场景

- 「用 Next.js 做一个电商前台」
- 「接 Shopify 但想自己控制前端」
- 「想参考一份用服务端组件写的电商架构」
- 「想换个电商平台，怎么改代价最小」
- 「上线后商品改了页面不更新」
- 「本地跑不起来，环境变量在平台那边」

## 能力边界

**覆盖**：

- 面向消费者的商城页面：首页、商品列表与详情、分类与集合、搜索、购物车、结算入口、内容页与页脚等。
- 现代渲染与交互实践：App Router、服务端组件、服务端操作、流式渲染、局部预渲染、乐观更新、图片优化与远程域名白名单。
- 可替换的数据层：把「怎么跟平台说话」收敛在一层里，换平台主要改这一层。
- 缓存与回填：提供缓存失效回调路由，配合平台 Webhook 让平台侧变更反映到页面。
- 部署配套：托管平台一键部署入口、环境变量清单与拉取流程。
- 工程配套：TypeScript、格式化与样式工具链配置。

**不覆盖**：

- 不含任何电商后端能力：商品、库存、价格、订单、支付、履约、退款都不由它提供。
- 不含商家侧管理后台与运营工具。
- 不含真实支付通道与收款资质，支付由外部平台与其集成负责。
- 不产出商品图片、详情文案、营销素材等内容。
- 不代你申请平台账号、域名、证书与托管资源。
- 不保证非默认平台的第三方实现与模板最新版本同步。

## 依赖条件

- Node.js 运行环境；包管理器用 pnpm。
- 一个电商平台店铺（当前默认实现对应 Shopify）及其店面访问令牌与店铺域名。
- 部署或本地拉取环境变量时，需要托管平台账号与它的命令行工具。
- 商品图片依赖平台 CDN，需要网络可访问其域名。
- 若走一键部署，需要在托管平台侧完成平台集成的授权。

## 已知限制

- 上游明确只持续维护默认平台的实现，其他平台由第三方分支提供，兼容性与跟进速度不受保证。
- 仓库里锁定的 Next.js 是 canary 版本，升级依赖时容易碰到行为变化。
- 模板开启了若干实验性渲染特性，更换运行环境或降级框架版本时可能不兼容。
- 没有后端就没有数据，本地开发必须接一个真实店铺，无法离线自造数据。
- 上游迭代较快，环境变量键名、脚本名与目录结构都可能变化；**执行前请以仓库当前版本与实际拉到的文件为准**。
- 本 Skill 不对具体版本号与发布日期做断言。

- [ ] 生产部署前已轮换过一切在开发期用过的令牌，并按最小权限重新签发。
