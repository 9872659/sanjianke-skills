# 三剪客 · 工程师技能体系

把工程经验沉淀成可复用 Agent Skill：怎么切分、怎么写、怎么在团队里落地。

团队里总有几个「只有老张知道」的坑：发版前必须改哪个开关、这个报错八成是缓存没清、这类需求要先问谁。这些经验现在散在聊天记录、Wiki 的角落和某个人的脑子里，Agent 也一概不知道——所以每次都得重新问一遍、重新踩一遍。

这套 Skill 解决的就是这件事：给你一套**判据**决定什么值得沉淀、一套**切法**决定怎么拆、一套**模板**决定怎么写、一套**门禁**决定怎么收进主干，最后按阶段在团队里铺开。它不是某份文档的摘要，是一套可以直接在周会上落地的作业规范。

**读完你会拿到**：4 份参考文件（切分、写作、落地、反模式）、2 个可复制的正文模板、1 张九问判据表、1 张反模式速查表。

## 快速开始

最小可用路径是**先想清楚，再动手写**。整个流程 15 分钟，产出是一张判据表和一个目录骨架，不是一篇长文。

**第 1 步 · 过九问判据（5 分钟）**

拿你脑子里的那件事，逐条问。**有 4 条答不上「是」，就还不该写成技能**——先把它留在文档或注释里。

| # | 问题 | 答「是」的样子 |
|---|---|---|
| 1 | 这件事**重复发生**吗？（每月 ≥1 次） | 每次发版前都要走一遍 |
| 2 | 它需要**步骤纪律**，而不只是背景知识吗？ | 有先后顺序，跳步会出错 |
| 3 | 新人和 Agent **都会做错**吗？ | 带过 3 个人，3 个人都踩了同一个坑 |
| 4 | 你能说出**触发词**吗？ | 用户会说「我要发版」「帮我上线」 |
| 5 | 步骤**可验证**吗？结尾有明确的「做完了」的样子吗？ | 能跑一条命令看到绿灯 |
| 6 | 它**稳定**吗？半年内不会推倒重写吧？ | 流程本身变了才需要改 |
| 7 | 它**不依赖某个人**吗？换个人照着走也能做完？ | 不需要「问老张」这一步 |
| 8 | 现有技能里**没有**覆盖它吗？ | 查过了，最接近的那个只覆盖了前半段 |
| 9 | 它**属于工程流程**，而不是某次业务决策吗？ | 讲的是怎么做事，不是做不做某个功能 |

**第 2 步 · 选切法（3 分钟）**

按「谁能在什么时候触发它」来切，不要按文件、不要按人、不要按技术栈。四种切法见 `references/skill-splitting.md`。最稳的默认是**一个触发词 = 一个技能**。

**第 3 步 · 建骨架（5 分钟）**

```text
<repo>/skills/<category>/<skill-name>/
├── SKILL.md          # 必需。触发面 + 主体流程
├── references/       # 可选。长资料、表、清单
├── scripts/          # 可选。可运行的检查脚本
└── CHANGELOG.md      # 可选。有对外承诺时加
```

```bash
# 1) 先列出仓库现状，确认没有重名和重复覆盖
ls -R <repo>/skills | head -50
# 2) 再建目录，避免手抖建在错误的分支上
mkdir -p <repo>/skills/<category>/<skill-name>/references
# 3) 写正文时照抄 references/writing-a-skill.md 里的模板
```

**第 4 步 · 过门禁**

写完不要直接发。走 `references/team-rollout.md` 里的五道评审门禁：触发面、长度、可执行性、边界、可验证性。任何一道不过就打回。

**第 5 步 · 标版本、进主干**

`version` 从 `1.0.0` 起步。此后只在**行为变了**的时候升位：改错别字和排版不动版本号，改步骤顺序、改判据、改边界要动。破坏性改动（老用法会失效）走 `2.0.0`。

## 能力边界

**覆盖**：

- 判断一件事值不值得沉淀成 Agent Skill，并给出可复述的理由
- 按触发面切分技能：一个触发词一个技能，控制单个技能的长度与职责
- 提供 `SKILL.md` 正文骨架、触发面写法、`references/` 分流规则与命名约定
- 提供团队落地的五道评审门禁、四周铺开排期与角色分工
- 提供 10 条常见反模式的识别信号与修法
- 提供权限与用途说明、能力边界的**写法示例**，让新技能如实交代自己动了什么

**不覆盖**：

- **不替你判断工程实践本身对不对。** 它能告诉你「这个技能切得不对」，不能告诉你「你们该不该用 TDD」。领域真理得由你们自己负责——技能只是把已经认可的做法固化下来。
- **不生成具体业务技能的内容。** 不会替你写出「发版流程」的实际步骤，那是你们运维的活；它只给框架和检查点。
- **不替代代码评审与 CI。** 技能是给 Agent 读的指令，不是门禁系统。真正拦得住错误提交的是 CI、类型检查和测试，不是文档。
- **不做技能运行时的强制约束。** 技能是提示词层的约定，Agent 理论上可以不遵守。需要硬约束的行为请落到脚本、钩子或 CI 上。
- **不涉及技能市场发布、账号、计费与分发。** 只管仓库内自建自用的体系。
- **不做跨仓库的技能同步。** 多仓库共享技能的组织方式需要你们自己定分发机制。

## 依赖条件

- **必需**：一个本地代码仓库，且有写权限（技能要跟着代码一起版本化，不要放私人网盘）。
- **必需**：能读写 Markdown 文件。纯文本即可，不需要额外工具链。
- **推荐**：git。技能的演化历史是它最有价值的部分——能看见「哪条规则是什么时候、因为什么事故加进来的」。
- **推荐**：一个读技能的 Agent 运行时（能加载 `SKILL.md` 的任意客户端）。没有的话这套体系仍然可以给人类新人读，但投入产出比会低一些。
- **不需要**：网络、API Key、数据库、Docker、任何付费服务。

## 已知限制

1. **长度与遵守率非线性。** 技能越长，Agent 越可能只读到一半或挑着执行。经验阈值是正文 500 行为上限，超过就该拆——但这是经验值，不是物理定律。
2. **触发面写得再好也会漏触发。** Agent 是否自动调用，取决于客户端实现和当前上下文。重要流程不要指望自动触发，在 `AGENTS.md` / `CLAUDE.md` 里显式指路更可靠。
3. **技能之间会互相污染。** 两个技能覆盖同一场景时，Agent 可能各取一半，产出比只用其中一个更差。这只能靠人工审查发现，本 Skill 给的是审查方法，不是自动检测。
4. **对「隐性经验」无能为力。** 有些判断（什么时候该停下来问人、什么算「够好了」）很难写成步骤。硬写会得到一份看似完整、实际不可执行的技能。
5. **模板会过时。** 本 Skill 的目录结构和字段建议基于当前主流的 Agent Skill 约定；不同客户端对 frontmatter 字段的支持有差异，接入前请以你所用客户端的文档为准。
6. **不含任何自动化脚本。** 判断与评审全靠人按清单走，本 Skill 不带校验工具（避免把「格式合规」误当成「内容合格」）。

## 自检清单

写完一个技能，逐条打勾；任何一条没打上，先别进主干。

- [ ] **触发面**：能在 3 句话内说清「什么时候该用它」，且用的是用户真会说的话，不是技术名词堆
- [ ] **长度**：正文 ≤ 500 行；超出的内容已分流到 `references/`
- [ ] **职责单一**：这个技能只干一件事；把标题念给同事听，他不会问「那另一件事呢」
- [ ] **可执行**：每个步骤都有明确的动作和结束判定，没有「适当处理」「视情况而定」这类空话
- [ ] **边界成对**：同时写了「覆盖」和「不覆盖」，且「不覆盖」不是敷衍的「其他」
- [ ] **权限如实**：权限与用途说明表逐项填了，没申请的能力如实写「否」，没漏报网络/写入/凭证
- [ ] **无凭证**：正文、模板、示例里没有任何真实密钥、Token、内网地址、客户名
- [ ] **无冲突**：搜过仓库里所有技能，没有第二个技能覆盖这个触发面
- [ ] **可验证**：结尾有能让执行者自证的检查点，不是「完成后告知用户」
- [ ] **版本分明**：改动属于哪一类（排版 / 步骤 / 破坏性）已经判断过，`version` 已相应更新
- [ ] **不重复已有**：确认不是在抄已有技能，也不是把三段已有的东西重贴一遍
