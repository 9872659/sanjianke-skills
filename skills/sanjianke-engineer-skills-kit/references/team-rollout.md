# 团队落地

技能写得再好，没人用就等于零。这份文件讲两件事：**怎么把技能收进主干**（五道门禁），和**怎么在团队里铺开**（四周排期）。

## 一、五道门禁

每个新技能、每次改动，都要过这五道。**顺序不能换**——后面的门禁假设前面的已经过了。

落地方式：把五道门禁做成代码评审的**检查清单**，挂在 PR 模板里。不要指望评审人凭记忆记得五条。

| # | 门禁 | 一句话判据 | 不过的后果 |
|---|---|---|---|
| 1 | 触发面 | 换个没参与写作的人，能凭描述判断该不该用吗？ | 技能永远不被调用 |
| 2 | 长度 | 正文 ≤ 500 行，超出部分已分流并留了带条件的指针 | 执行者只读一半 |
| 3 | 可执行性 | 非作者照着实跑一遍，中途没有需要来问的地方 | 技能看起来完整、实际不可用 |
| 4 | 边界 | 「覆盖」和「不覆盖」成对存在，且「不覆盖」指向了替代方案 | 误命中后无人知道该找谁 |
| 5 | 权责 | 权限如实申报、有明确 owner、版本变更有依据 | 出事无人负责，或事后才发现越权 |

### 门禁 1 · 触发面

**评审提问单**（逐条念，答不上就是不过）：

1. 这个技能在**什么时刻**被需要？用用户的原话复述一遍。
2. 描述里列了几个触发说法？少于 4 个，覆盖不够。
3. 谁**不该**用这个技能？它和哪个技能最容易被搞混？
4. 仓库里搜一遍，有没有第二个技能覆盖同一个触发面？
5. 如果这个技能永远不被自动触发，只有人手点才能用，团队里**谁会记得它存在**？（用来判断该不该设成仅人工触发）

**最容易犯的错**：触发描述写成分类标签。「一个关于 CI 的技能」不是触发描述，是标题的重复。

### 门禁 2 · 长度

**硬指标**：

- 正文 ≤ 500 行
- 标题层级 ≤ 3 层
- 单个步骤 ≤ 15 行

**超过之后先别删，先分流。** 分流的判据是「这个东西是每次都要执行，还是只在某些分支才需要」。后者移入 `references/`。

**分流后必须留带条件的指针**：

```markdown
若校验返回非 0，错误码对照表见 `references/error-codes.md`。
```

不写条件的「详见 references/」，等于把执行者扔进一个没有索引的抽屉。

**顺带查一件事**：如果分流之后正文还是超过 500 行，问题不在写作，在**切分**。回去看 `skill-splitting.md`，你多半把一个该拆的技能合成了一份。

### 门禁 3 · 可执行性

**这是五道门禁里唯一不能靠读完成的。** 必须做一次干跑。

**干跑协议**：

1. 找**没参与写作**的人（或另一个 Agent 会话），只给他 `SKILL.md`，不给任何口头补充
2. 让他照着走，**遇到第一个卡住的地方就停**
3. 记录卡在哪一步，以及他当时的猜测是什么
4. 修改，重跑，直到全程不卡

**要收集的不是「对不对」，是「卡不卡」。** 他猜对了但理由错了，也是问题——下一个执行者未必猜得对。

**干跑常见的三个卡点**：

| 卡点 | 症状 | 修法 |
|---|---|---|
| 缺前置 | 「我不知道从哪开始」 | 补「前置条件」一节 |
| 缺完成标志 | 「我做完了吗？可以下一步了吗」 | 给每步加可观测的完成标志 |
| 缺停手条件 | 「这里不太确定，但我继续了」 | 显式写「遇到 X 就停下问人」 |

最后一条最重要。**静默做错比停下来问人贵得多。**

### 门禁 4 · 边界

检查两件事：

**第一，边界成对。** 只有「覆盖」没有「不覆盖」的技能，边界是假的。评审时念一遍「不覆盖」那几条，问：**如果用户要做被排除的这件事，他会去哪？** 答不上来，说明缺一个技能，或者缺一个指路。

**第二，不覆盖要具体。** 这一条最常被敷衍：

```markdown
差：不覆盖其他情况。
好：不覆盖生产环境的数据修复——那属于运维流程，走 oncall 工单。
```

### 门禁 5 · 权责

**权限如实申报。** 检查表里有没有出现这几项，如实填了的才算过：

- 网络访问：真的不发任何请求吗？
- 读取文件：读的是工作区内的，还是伸到了工作区外（家目录、系统路径）？
- 写入文件：会不会覆盖已有文件？覆盖前有没有让人确认？
- 凭证：有没有读取、转发、写进日志的可能？
- 子进程 / 后台常驻：会不会留下守卫进程、定时任务、系统配置改动？

**「否」也是答案，但必须是诚实的否。** 一个写「不申请网络访问」却在正文里教用户 curl 外部接口的技能，是在骗评审。

**owner 明确。** 每个技能指定一个 owner。**owner 不是作者，是那个负责让它不腐烂的人**——包括在依赖的流程变了之后主动来改它。技能没有 owner，半年内一定变成误导性文档。

**版本变更有依据。** 改了什么、为什么改，写进 PR 描述。判断标准：

| 改动性质 | 版本位 |
|---|---|
| 错别字、排版、链接 | 不动 |
| 补充边界情况、细化步骤 | `1.x.0` |
| 步骤顺序变化、判据变化、切分调整 | `1.x.0` 或 `2.0.0`（看老用法是否失效） |
| 触发面变化、老用法不再生效 | `2.0.0` |

**触发面变化一律算破坏性**——依赖它的其他技能可能就调不到了。

## 二、四周落地排期

不要一次铺完。**技能体系的失败模式是「第一周涌进二十个技能，第三周没人维护」。** 按下面分四周走，每周有明确的产出。

### 第 1 周 · 立规矩，不写技能

**产出**：

- 仓库里加一个 `skills/README.md`，写明**目录约定 + 分组规则 + 命名规则 + 门禁清单**
- PR 模板里加上五道门禁的检查项
- 定下 owner 的分配规则（谁能被指为 owner，一个 owner 最多背几个）

**这一周不写任何技能。** 先有规矩再有内容，否则第一批技能会各自长成不同形状，后面要么全改要么全留。

KPI：新人看完 `skills/README.md`，能自己判断「这件事该不该写成技能」。

### 第 2 周 · 只沉淀两个

**产出**：两个技能，必须选**痛感最强、重复频率最高**的那两件。

**怎么选**：翻最近一个月的聊天记录/工单，数「同一个问题被问了几次」。排前两名的就是它们。

**这一周的关键约束**：只做两个，不许加。目的是**跑通一遍门禁流程**，让团队看到一次完整的「从痛点到技能」是怎么走的。做五个技能但不走门禁，等于没立规矩。

KPI：两个技能都完成了一次非作者干跑，且干跑者全程没来问人。

### 第 3 周 · 让别人写第一个

**产出**：至少一个**非发起人**写的技能，走完全部门禁。

**这一步是分水岭。** 前两周的技能是发起人写的，规矩能不能生根，取决于别人写的时候是不是也走得通。

**要做的事**：

- 发起人**只做评审，不代笔**（代笔一次，规矩就废了）
- 评审时把卡点记录下来，用来改规矩——规矩第一次被真实使用，一定会暴露问题
- 如果被卡住，先改规矩，再改技能

KPI：非发起人独立完成一个技能，且不需要发起人在旁边口述步骤。

### 第 4 周 · 清理与建档

**产出**：

- 全量走查一遍已有技能，处理冲突（见 `anti-patterns.md`）
- 建 `skills/README.md` 的总索引：**技能 → 一句触发场景 → 调用方式 → owner**
- 定下复查节奏（见下）
- 把「什么时候该写新技能」的判据贴进 `AGENTS.md` / `CLAUDE.md`，让 Agent 也知道体系存在

KPI：索引表里每个技能都有 owner；任意两人对同一场景会指向同一个技能。

## 三、持续运转

铺开之后靠三个机制维持，缺一个都会慢慢烂掉。

### 机制 1 · 复查节奏

| 频率 | 动作 | 谁做 |
|---|---|---|
| 每月 | 抽查 3 个技能的干跑，看还走不走得通 | owner 轮值 |
| 每季 | 全量对账：**被依赖的流程变了吗？技能跟上了吗？** | 发起人 |
| 出事时 | 任何一次「照着技能做错了」都触发一次修订 | 当事 owner |

第三行是重点。**技能出错的现场，是它最有价值的修订输入。** 不要只修问题，要顺手修技能——否则同一个坑会再踩。

### 机制 2 · 淘汰

技能要有退出机制。连续两季没人调用 + owner 已离职 + 对应流程已废弃，就该删。

**删除不是失败，留着才是。** 一个过期的技能会主动误导 Agent，比没有更差。删的时候在 PR 里写清「它被什么取代了」，让后来搜到历史的人有落点。

### 机制 3 · 冲突巡查

技能之间打架不会自己暴露，只会表现为「Agent 有时候对有时候不对」。所以要有主动巡查：

- 用触发描述里的关键词互相搜一遍，找出重叠
- 重叠的成对技能，必须指定**唯一权威**，另一个改成指路或删掉
- 指路写法：`<被替代的技能>` 正文只留一句「本场景请用 `<权威技能>`」，不要留半份内容

## 四、工具边界：技能不替代什么

推行时一定会有人问「这个和我们的 CI / 代码评审 / Wiki 什么关系」。答案要一次讲清，否则技能体系会被要求去干它干不了的活。

| 工具 | 管什么 | 技能管不管 |
|---|---|---|
| CI / 类型检查 / 测试 | **强制**。不过就是不过，没有商量 | 不管。技能是提示词层的，理论上可被忽略 |
| 代码评审 | **判断**。人对代码质量做主观决定 | 不管。技能固化的是「怎么做」，不是「做得好不好」 |
| Wiki / 设计文档 | **解释**。为什么这样做、当时考虑了什么 | 不管。但可以指过去 |
| `AGENTS.md` / `CLAUDE.md` | **常驻指路**。项目级的稳定约定 | 互补。技能是被调用的，这里是被一直读的 |
| Skill | **执行纪律**。某件事按什么顺序、做到什么算完 | 就是它 |

**一句话**：需要被**强制执行**的规则，不要写成技能，写成脚本或 CI 检查。技能管的是流程与判断，管不住「必须」。

把这条讲在前面，能省掉后面大量的期望错位。

## 五、给推行者的三条实话

1. **前两周一定慢。** 立规矩、走门禁、做干跑，都比「直接写个 md」慢得多。慢的这部分正是全部价值所在——不慢下来，三个月后你会得到二十份互相打架的文档。
2. **别追求覆盖率。** 体系的价值来自**被反复使用的那几个技能**，不是技能总数。十个没人用的技能，比三个天天被调用的技能差。
3. **发起人要能退场。** 如果四周之后每个技能还得你亲自审，说明规矩没立起来，只立了你这个人。第 3 周让非发起人独立写完一个，就是为这件事设计的。
