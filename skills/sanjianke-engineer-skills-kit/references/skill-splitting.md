# 技能怎么切分

切分是自建技能体系里最贵的一个决定。**切错了不是写得难看，是 Agent 用错**：两个技能各覆盖一半场景，它就各取一半执行，产出比只用其中一个更差。而且切错的代价是复利的——后来每加一个技能，冲突面都再翻一倍。

## 一、切分的唯一主轴：触发面

一句话：**一个触发词，一个技能。**

不要按技术栈切（`react-skill`、`node-skill`），不要按文件切（`utils-skill`），不要按人切（`zhang-skill`）。按**「用户在什么时刻、说什么话的时候，需要它」**切。

判据很直接——给你要沉淀的事，填这句话：

> 当用户说「______」或者正在做「______」的时候，就该用这个技能。

空格填不出来，说明它不是一个技能，是一堆知识的集合。填出来有两个不同的答案，说明它是两个技能。

### 为什么按触发面切

技能的成本结构决定了一切。把一个技能做出来有三笔成本：

1. **常驻上下文成本**——只要技能能被 Agent 自动发现，它的触发描述就一直在上下文里。技能越多，这笔钱越贵，而且是每轮对话都付。
2. **冲突成本**——两个技能覆盖同一场景，Agent 会犹豫、会混用。
3. **维护成本**——一个技能改一次要重新过一遍评审门禁。

按触发面切，冲突成本趋近于零：触发面互斥，就永远不会打架。这是唯一能让技能数量增长而体系不崩的切法。

## 二、四种切法

按优先级从上往下试，能用上面那条就别用下面的。

### 切法 1 · 触发词切（默认，最稳）

**规则**：一个技能对应一组同义或近义的触发表达。

判定动作：把候选人说的话写成一列。如果两句话**可能出现在同一个任务里但不会互相触发**，它们属于同一个技能；如果一句话会让 Agent 在两者之间选，拆开。

```text
「帮我发版」          → 发版技能
「这个报错怎么回事」    → 排障技能
「帮我 review 一下」   → 代码评审技能
```

三条互不干扰，Agent 永远不会犹豫。这就是好的切法。

### 切法 2 · 阶段切

**规则**：同一个大流程里的**相邻但互斥的阶段**，各成一技。

拆的信号是「上一步做完了，下一步才可能开始，而且下一步有自己独立的纪律」。典型如：需求成文 → 拆工单 → 实现 → 评审 → 发布。它们属于同一个大流程，但每个阶段有自己的输入输出和错误模式，混在一个技能里 Agent 会跳到中间。

**注意**：阶段切有个陷阱——阶段太多会得到一串没人记得住的碎片。经验上限是**一条主流程切 3~5 段**，超过就说明你在按文档目录切，不是按阶段切。

### 切法 3 · 共享资料切

**规则**：多份技能都要用的同一批资料（长表、字段字典、清单），单独成一份**只能被调用、不能独立完成一件事**的技能。

判据：它有没有独立的触发面？如果用户永远不会说「我要用字段字典」，那它就不该有面向用户的触发面，而应该是被别的技能**显式点名调用**的引用技能。这样参考资料只有一份，改一处所有引用方都同步。

反过来的做法是把参考资料复制进每个技能——这是自建体系最常见的腐化起点，见 `anti-patterns.md` 的 AP-04。

### 切法 4 · 调用方式切

**规则**：按「谁能触发」切，而不是按内容切。

只有两类，二选一：

- **模型可触发**：带触发描述，Agent 能自己判断该用，别的技能也能点名调用。代价是描述常驻上下文。
- **仅人工触发**：不带触发描述，只有人打出名字才能用，别的技能也调不到它。代价是**你自己得记住它存在**。

选法只有一条：**这个技能需要 Agent 自己想起来吗？**

- 需要 → 模型可触发
- 只在人手点时才用 → 仅人工触发，省下常驻成本
- 别的技能要调它 → 必须是模型可触发（仅人工触发的技能，谁也叫不动）

一条硬规矩：**仅人工触发的技能不能调用另一个仅人工触发的技能**——没有描述就没有指针，链不起来。仅人工触发的技能可以调用模型可触发的技能。

### 关于「路由器技能」

当一个仓库里仅人工触发的技能多到你记不住时，别去背——写一个**路由器技能**：唯一一个仅人工触发的技能，内容是「有哪些技能、各自什么时候用」。

它只能**提示**，不能**代为触发**（仅人工触发的技能没有描述，除了人谁也点不动）。所以路由器的正文要写成给人看的指路，写成「请用户运行 X」而不是「调用 X」。

## 三、该拆的信号

出现任意两条，就该考虑拆：

1. 正文超过 500 行，或标题层级超过 3 层
2. 存在两个明显互斥的触发面（一半的步骤在解决 A 场景，另一半在解决 B 场景）
3. 读技能的人需要先读另外半篇才能用当前半篇
4. 两个团队/两个角色分别只关心其中一部分（各自都嫌另一半是噪音）
5. 你写触发描述时，用了「或者」来连接两个不相干的场景
6. 最近三次修订分别改的是完全无关的部分

## 四、该合的信号

反过来，出现任意两条，说明你切碎了：

1. 一个技能正文不到 30 行，且没有任何可独立执行的步骤（只是背景说明）
2. 两个技能的触发描述有 50% 以上的词重叠
3. 每次用 A 都必然紧接着用 B，从无例外
4. 两个技能总是成对改动（改一个必须改另一个，否则失效）
5. 你得在某个技能里写「注意：这个技能必须配合 X 一起用」

第 5 条是最刺眼的信号——**技能之间的强制搭配，说明它们本来就是一个技能**。真正独立的技能，单独用也应该是完整的。

## 五、目录与命名约定

```text
<repo>/skills/
├── <category>/                  # 按用途分组，不按技术栈
│   ├── README.md               # 这一组的索引：技能 → 一句触发场景 → 调用方式
│   ├── <skill-name>/
│   │   ├── SKILL.md            # 必需
│   │   ├── references/         # 长资料（表、清单、字段字典）
│   │   ├── scripts/            # 可运行的检查脚本
│   │   └── CHANGELOG.md        # 有对外承诺时加
```

**分组名用用途**：`engineering`（写代码用的）、`operations`（部署运维）、`team`（协作流程）、`misc`（留着但不主推）。不要用 `react`、`python` 这种技术栈名当顶层分组——技术栈会过时，用途不会。

**技能名用 kebab-case 动词短语**：

| 好 | 差 | 差在哪 |
|---|---|---|
| `diagnose-failing-test` | `testing-utils` | 后者是名词堆，说不清触发时刻 |
| `write-release-notes` | `release-stuff` | 后者太模糊，无法判断职责 |
| `review-pull-request` | `pr-review-v2-final` | 后者带版本号和情绪，版本属于 frontmatter |

**命名三禁**：

- 不带版本号（`-v2`、`-final`、`-new`）——版本在 `version` 字段里
- 不带团队或人名（`-zhang`）——技能属于体系，不属于个人
- 不用缩写（`cfg`、`impl`）——触发描述要跟用户的口语对齐，不是跟命名习惯对齐

**分组的数量控制在 3~6 个**。超过 6 个说明你在按「文件夹思维」组织，而不是按「用户什么时候会想起它」组织。新人第一次进仓库，应该能在 30 秒内从 README 定位到该用哪个技能。

## 六、一个有始有终的示例

假设团队口头流传着一句「发版前必须做的那堆事」，你想把它沉淀下来。

**第一版（错的）**：建一个 `release` 技能，把构建、检查清单、灰度、回滚、写发版说明、通知相关人全塞进去。正文 700 行。

**问题**：触发面其实是四个——「我要准备发版」「发版挂了要回滚」「帮我写发版说明」「发完通知谁」。Agent 收到任何一个，都得在 700 行里找对应段落，很容易串台（比如滚回流程还没到就先去改通知话术）。

**第二版（对的）**，按切法 2 + 切法 3 拆：

```text
skills/operations/
├── preflight-release/        # 触发：「准备发版」→ 门禁检查清单
│   ├── SKILL.md
│   └── references/checks.md
├── rollback-release/         # 触发：「发版挂了」「怎么回滚」
│   └── SKILL.md
├── write-release-notes/      # 触发：「写发版说明」
│   └── SKILL.md
└── release-communication/    # 触发：「发完通知谁」
    ├── SKILL.md
    └── references/audience-matrix.md   # 三处都要用 → 但只在这一处
```

**第三版（再收一次）**：跑一遍合的信号，发现 `write-release-notes` 每次都被紧接着调用，但也能被单独用于「补一条上周的发版说明」——不满足合的第 3 条。保留。

而 `release-communication` 里的受众矩阵被 `write-release-notes` 也需要。此时**不要把矩阵复制两份**，也不要让它独立成一个面向用户的技能，而是：在 `release-communication` 里保留它作为引用资产，让 `write-release-notes` 的正文写一句「调用 `release-communication` 技能取受众矩阵」。这样矩阵只有一份，且改动自动同步。

**最终形态**：4 个技能，每个 60~150 行，触发面互斥，谁也不跟谁打架。Agent 收到「帮我回滚」时不需要在 700 行里挑段落——它只会命中一个技能。

这就是切分要的结果：**不是文件整齐，是 Agent 不犹豫。**

## 七、切分检查表

- [ ] 每个技能都能填出「当用户说 ___ 时用它」，且空格里只有一种场景
- [ ] 任意两个技能的触发描述，重叠词不超过 30%
- [ ] 没有任何技能需要写「必须配合 X 使用」
- [ ] 仅人工触发的技能，没有被别的技能点名调用
- [ ] 顶层分组是用途，不是技术栈，数量在 3~6 之间
- [ ] 技能名是 kebab-case 动词短语，不含版本号、人名、缩写
- [ ] 共享资料只有一份，其他技能靠点名调用获取，没有复制
