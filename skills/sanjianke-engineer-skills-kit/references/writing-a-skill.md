# 写好一个工程技能

## 一、先认清：技能里其实住着两份文档

一份技能文件同时服务两个完全不同的场景，这是它所有写法规则的来源：

| | 第一份 | 第二份 |
|---|---|---|
| 内容 | 触发描述 | 正文流程 |
| 读者 | 正在**决定要不要用它**的 Agent | 已经**决定用它**的 Agent |
| 何时被读 | 每轮对话都在上下文里 | 只在被调用后 |
| 成本 | 常驻，越贵越要省字 | 一次性，可以写细 |
| 目标 | 被正确命中，且不被误命中 | 照着做完就能得到结果 |

**九成的技能不好用，坏在第一份上。** 正文写得再好，触发描述说不清什么时候用，它就是一份没人打开的文件。新手的精力全花在正文，这是最常见的分配错误。

## 二、触发描述怎么写

### 三条规则

**规则 1 · 写「用户会说的话」，不写「这个技能是什么」**

| 差 | 好 |
|---|---|
| 一个关于类型安全的技能 | 用户想给 TS 项目加严格类型检查、遇到 `any` 泛滥、要配置 lint 规则时使用 |
| 处理部署相关事宜 | 用户说要发版、要上线、要发布新版本，或问「怎么部署到生产」时使用 |
| 代码质量工具集合 | 用户抱怨代码难改、说要重构、要清理技术债、要拆一个过大的模块时使用 |

差的那一列是**分类标签**——它告诉一个已经知道你存在的人「我属于哪一类」。好的那一列是**指纹**——它让不知道你存在的人能凭自己说的话把你匹配上。

**规则 2 · 枚举触发分支，不要概括**

触发描述的价值在于覆盖用户真实说法的**变体**。「涉及部署时使用」只覆盖了字面说「部署」的人。真实的说法是散的：

```text
用户说要发版、要上线、要 publish、要 release，
或者问「这次改动怎么给用户」，
或者提到灰度、回滚、发布窗口时使用。
```

一句话里塞进 4~6 个变体，命中率会有肉眼可见的提升。但别堆成词表——读起来要像一句人话。

**规则 3 · 也要写清什么时候**不**用**

负向触发是省成本的。写明「不要用于 X」，能挡掉一类误命中，比事后让人删掉一次错误执行便宜得多。尤其当你的技能和另一个技能名字接近、领域相近时，这条几乎必须写。

```text
本技能只处理发布动作本身；要不要发布、发什么内容属于需求评审，不在本技能范围。
```

### 长度

触发描述控制在 **40~120 字**。短于 40 字几乎一定覆盖不全变体；长于 120 字会稀释信号，模型容易抓不住重点。

## 三、正文骨架模板

复制下面这份，按注释填写。**方括号里的都是要替换的内容，不要原样保留。**

```markdown
---
name: <kebab-case-技能名>
description: "<谁在什么情况下用：枚举 4~6 个用户说法>。<负向边界：不要用于……>。"
version: 1.0.0
---

# <技能名：一个动词短语>

<开场 2~4 句：这个技能替用户解决什么问题。
不要复述标题，不要写「本技能旨在」，直接说痛点。>

## 何时用 / 何时不用

**用**：
- <场景 1，用用户的说法>
- <场景 2>

**不用**：
- <最容易误命中的那个场景> → 应该用 <另一个技能名>

## 前置条件

<开始之前必须成立的事。没有就写「无」。>

## 步骤

1. **<动作名>**
   <具体做什么。给命令、给文件路径、给判定标准。>
   **完成标志**：<怎么知道这一步过了>

2. **<动作名>**
   ...

## 边界情况

| 情况 | 怎么处理 |
|---|---|
| <不常见的输入> | <明确的处理动作> |

## 自检

- [ ] <可验证的检查项>
- [ ] <可验证的检查项>

## 参考

| 文件 | 用途 |
|---|---|
| `references/<x>.md` | <什么时候需要翻它> |
```

## 四、正文写作规则

### 规则 1 · 每一句都要能变成动作

技能正文不是文档，是**待执行的指令**。删掉所有不能改变行为的句子。

| 删掉 | 因为 |
|---|---|
| 「良好的测试非常重要」 | 没有动作 |
| 「要注意性能」 | 没有动作，也没说注意什么 |
| 「这一步很关键」 | 强调不产生行为差异 |
| 「根据实际情况灵活处理」 | 把判断推回给执行者，等于没写 |

**替换写法**：把「要注意性能」改成「查询超过 100ms 就在日志里记一条 `slow_query`」。具体、可测、能执行。

### 规则 2 · 不要解释「为什么」

技能被调用时，执行者已经决定要做了，不需要被说服。原理、背景、历史原因属于设计文档，不属于技能。

**唯一例外**：当「为什么」会直接影响执行时的决策，才用**一句话**在括号里带上。

```markdown
1. 先跑一遍失败的测试确认它确实失败（不要跳过：确认失败原因是你以为的那个，是这个流程唯一的价值来源）。
```

括号里那句不是说服，是防止执行者偷懒跳过。

### 规则 3 · 用执行者已有的词汇

技能正文里出现的名词，应该是这个仓库里已经在用的词——代码里的类名、README 里的流程名、团队日常的口头称呼。

写「物料化级联」不要写「把部分数据落盘的过程」。前者执行者一读就知道指代码里哪块，后者它得猜。**先在仓库里搜一遍你要用的词有没有既有说法，有就用既有的。**

### 规则 4 · 动作写在前面，条件写在后面

```text
差：如果当前分支有未提交的改动，那么先 stash。
好：先 stash 未提交的改动（若工作区是干净的，跳过本步）。
```

执行者是逐句读的。条件前置会让它在还没读到动作时就开始判断，多一次往返。

### 规则 5 · 每一步都要有完成标志

没有完成标志的步骤，执行者不知道什么时候可以往下走，于是要么提前走，要么反复确认。

**完成标志必须可观测**：一条命令的输出、一个文件的存在、一个状态的变化。不要写「确认无误后继续」——谁确认、怎么算无误，都没说。

### 规则 6 · 明确写「停下来问人」的条件

Agent 最大的风险不是做错，是**在不该继续的时候继续**。凡是存在「不确定但可以硬着头皮往下做」的地方，都要显式写明停下：

```text
若上一步的输出里出现 `multiple candidates`，停止执行，把候选项列给用户选。不要自行挑选。
```

这类句子看起来在降低自动化程度，实际上是在保护可用性——一个偶尔停下问人的技能，比一个偶尔静默做错的技能可信得多。

## 五、长度预算与 references 分流

### 预算

| 部分 | 上限 | 超了怎么办 |
|---|---|---|
| 触发描述 | 120 字 | 砍掉最不常用的变体 |
| 开场 | 4 句 | 移到「何时用」里，或直接删 |
| 正文总长 | 500 行 | 分流到 `references/` |
| 单个步骤 | 15 行 | 拆成子步骤，或把细节移出正文 |
| 标题层级 | 3 层 | 第 4 层几乎一定是该移出的内容 |

500 行不是硬性规定，是**遵守率的经验拐点**。正文越长，执行者越可能只读前半段然后开始猜后半段。宁可拆成两个技能（见 `skill-splitting.md`），也不要写一份没人读完的长文。

### references 分流规则

正文只留**每次都要执行**的东西。以下内容一律移出：

| 内容类型 | 去处 | 理由 |
|---|---|---|
| 长清单、字段字典、枚举表 | `references/` | 只在特定分支才需要 |
| 背景知识、原理说明 | `references/` 或删掉 | 不影响执行 |
| 完整命令参考、参数大全 | `references/` | 正文只留最常用的那一条 |
| 历史决策记录 | 版本控制历史 | 仓库已经存了 |
| 示例代码全文 | `references/` | 正文留 3 行示意 + 指路 |
| 只在 10% 的情况下需要的分支 | `references/` | 正文写「若遇到 X，见 references/y.md」 |

**分流后必须在正文留指针**，否则等于删掉。指针要写清**什么时候**去翻：

```markdown
若校验失败，错误码对照表见 `references/error-codes.md`。
```

不要写「详见 references/」——不写条件，执行者不知道要不要翻。

## 六、改写示例

同一件事，两版对照。

### 改写前（不可执行）

```markdown
## 关于数据库迁移

数据库迁移是一件需要谨慎对待的事情。在开始之前，
请确保你了解当前的 schema 状态。迁移脚本应当经过
充分的测试，并且在生产环境执行前需要做好备份。

如果迁移出现问题，应该及时回滚，避免造成数据不一致。
```

问题：每一句都是「应当」「需要」，没有一个是动作。「谨慎对待」是什么动作？「充分测试」测几遍？执行者读完不知道第一步做什么。

### 改写后（可执行）

```markdown
## 数据库迁移

1. **记下当前 schema 版本**
   运行 `npm run db:version`，把输出贴进工单。
   **完成标志**：工单里出现一行形如 `schema@2026.09.13-01` 的版本号。

2. **在本地库跑一遍迁移**
   先 `npm run db:reset`，再 `npm run db:migrate`。
   **完成标志**：两条命令都以 0 退出。

3. **验证可回滚**
   运行 `npm run db:rollback`，然后 `npm run db:version` 确认回到了第 1 步记下的版本。
   **完成标志**：版本号与第 1 步一致。不一致就停止，不要执行第 4 步。

4. **生产备份**
   执行 `scripts/backup-db.sh <env>`，等它打印出备份文件路径。
   若脚本报 `permission denied`，停下找 DBA 加权限，**不要**改用 `sudo`。
```

差别不在文笔，在于第二版**每一步都能被判对错**：有命令、有输出、有停止条件。

## 七、自检：这份正文合格了吗

- [ ] 触发描述里有 4~6 个**用户真实会说的话**，不是分类标签
- [ ] 写明了「不用」的场景，且指向了正确的替代技能
- [ ] 通读一遍，没有一句话是可以删掉而不影响执行的
- [ ] 没有「注意」「应该」「要谨慎」这类不产生动作的句子
- [ ] 每个步骤都有**可观测**的完成标志
- [ ] 存在不确定分支的地方，都写了「停下来问人」
- [ ] 用词与仓库既有说法一致（搜过了，不是自己新造的名词）
- [ ] 正文 ≤ 500 行，长内容已分流且留了带条件的指针
- [ ] 没有任何真实密钥、Token、内网地址、客户名
- [ ] 让一个没参与写作的同事照着走一遍，他不会来问你「这一步什么意思」
