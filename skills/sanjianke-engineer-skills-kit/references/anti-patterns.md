# 常见反模式

十条。每条的结构一样：**识别信号 → 代价 → 修法 → 例子**。

用法：**先看信号，别先看名字。** 名字是给人记的，信号是给人指认的。翻一遍自己的技能，命中了哪个信号就跳过去看修法。

十条里有六条的共同根因是同一个：**技能被当成文档写**。文档的读者是有耐心的人，技能的读者是逐句执行的 Agent。记住这一条，能提前避开大半。

---

## AP-01 · 大杂烩

**信号**
- 标题是个名词，不是动词短语（`{项目}规范`、`{技术栈}最佳实践`）
- 正文超过 500 行，或标题超过 3 层
- 触发描述里出现了「或者」连接两个不相干的场景
- 目录里有 `01-`、`02-` 这样的章节编号

**代价**：执行者只会读完前半段。更糟的是，它可能在不同时候读到不同的半段，同样的输入得到不同的输出——问题表现得像「Agent 时好时坏」，没人会想到是文档结构的问题。

**修法**：回到 `skill-splitting.md`，按触发面拆。检验标准是**每个拆出来的技能都能单独填出「当用户说 ___ 时用它」**。填不出来，说明拆的方式还是按章节走的。

> **例子**：一个叫「数据处理规范」的技能，300 行，前半讲导入 CSV 的字段映射，后半讲导出报表的格式约定。实际是两个场景，两个人都只关心一半。拆成「导入数据」和「导出报表」之后，两个技能各 80 行，谁都不会读到无关内容。

## AP-02 · 复制粘贴的规范

**信号**
- 全仓库搜同一句话，出现在 2 个以上技能里
- 改了一处规则，得记得去改另外 N 处
- 某段内容在两个技能里的表述已经不一致了

**代价**：**分叉后互相矛盾，Agent 各取一半。** 这是自建体系里最具破坏力的一种腐化，因为它在很长时间里是隐形的——两份内容在复制那天是相同的，直到某一处被单独修改。

**修法**：共享内容只留一份，放在**拥有它最自然的那个技能**里，其他地方靠显式点名调用：

```markdown
受众分类见 `release-communication` 技能。
```

**关键细节**：如果两边都只是「偶尔用到」这批资料，那就不要把它塞进任何一边，而是单独建一个**引用技能**——只被调用，不独立对应任何用户触发场景。

> **例子**：`preflight-release` 和 `rollback-release` 各自复制了一份「环境清单」。三个月后有人往发布检查里加了一个新环境，回滚技能里的清单还是旧的——回滚到不存在的环境，现场才发现。

## AP-03 · 作者才知道

**信号**
- 正文里出现了只有作者懂的简称（`走一下 V2 流程`、`按上次那个方式`）
- 步骤里写着「按惯例」、`参照 `{某个内部系统}``，但没给路径
- 有「视情况而定」，且没说视什么情况
- 干跑时执行者问出「这里指的是哪个？」超过一次

**代价**：技能实际上没有脱离作者。它看起来进了主干，实际每次用还得找作者确认——比不写更差，因为它给了「已经沉淀好了」的错觉。

**修法**：**把作者脑子里的补全写出来。** 具体做法：作者照着技能做一遍，凡是自己「不假思索就知道」的地方，全部显式化。

三条硬规则：

1. 出现的每个内部系统名，后面跟一个路径或入口
2. 删掉所有「按惯例」「视情况」——要么写出判据，要么改成一个分支
3. 用仓库里已有的词。先在仓库搜一遍，有既有说法就用既有的，不要新造名词

> **例子**：`「先按线上口径核对一遍」`——「线上口径」是团队口头语，没有定义。改成 `「核对线上库（连接串见 ops/config/canary.env）里 order 表的 status 字段与本地 fixture 一致」`，新人能执行了。

## AP-04 · 有格式没内容

**信号**
- 每个章节都有，但「步骤」一节写的是「按需执行相关操作」
- 权限表里全是「否」，但正文教用户调外部接口
- 「自检清单」的每一条都是「确认无误」「检查正确性」
- 技能是照着模板填完的，但填进去的句子换到任何技能里都成立

**代价**：**门禁全过，实际不可用。** 这是最危险的一种——它消耗了完整的评审流程，得到一份谁都不敢说它不合格的东西。而且它是可复制的坏榜样：别人会照着它的形状写。

**修法**：用**置换测试**。把技能名换成另一个技能名，如果正文依然读得通，那这些话就是空话，删掉重写。

然后用**干跑**兜底：非作者照着走，卡住的地方就是空话所在的位置。

> **例子**：一份「数据备份」技能的步骤是「1. 评估备份范围 2. 执行备份 3. 验证备份完整性」。三步都没有动作、没有命令、没有完成标志。干跑者在第 1 步就卡住了——「评估范围」是看什么？

## AP-05 · 只写覆盖，不写不覆盖

**信号**
- 「能力边界」一节只有「覆盖」，或者「不覆盖」写的是「其他情况」「暂不支持」
- 有个技能和它场景相邻，但两个都没提对方
- 用户误用后，没人知道正确的那个是哪个

**代价**：误命中。Agent 会拿一个不该用的技能去处理场景，而且**做出来的东西看起来合理**——因为它确实按某个流程走了，只是不是对的那个流程。错得安静，是最贵的错。

**修法**：「不覆盖」必须**成对且具体**，并且指向替代方案：

```markdown
**不覆盖**：生产环境的数据修复。走 oncall 工单，由值班同学执行。
```

评审时念一遍「不覆盖」，问：**如果用户要做被排除的这件事，他去哪？** 答不上来就是缺技能或缺指路。

> **例子**：`staging-deploy` 只写了「覆盖预发环境部署」。有人拿它去发生产，Agent 照做了——因为它写的命令里环境参数是个变量。补上「不覆盖生产环境；生产发布走 `production-release`」之后，这个错误才有可能被拦住。

## AP-06 · 孤岛技能

**信号**
- 同一个人提交了 8 个技能，别人一个都没写
- 技能没有 owner，或者 owner 是「团队」
- 问「这个技能怎么用」，得到的回答是「问小王」
- 技能半年没动过，但它依赖的流程已经改了两次

**代价**：**单点依赖 + 停滞。** 作者在的时候，技能是作者的口头补充；作者一走，技能就是一份没人敢改也不敢删的历史文件。

**修法**：

1. 每个技能**指定一个 owner**——是「负责让它不腐烂的人」，不是「写它的人」
2. 一个 owner 最多背 3~5 个技能，超了就是形式主义
3. 起草人 ≠ 最终 owner，允许移交
4. 按 `team-rollout.md` 的第 3 周，**强制让非发起人独立写一个**——这一步是防孤岛的唯一有效手段

> **例子**：某团队有 12 个技能，全部由同一人在两个月内写完。他转岗后，其中 5 个依赖的接口已经改版，技能里的命令全部失效。三个月后新同事照着执行，把测试数据写进了预发库。

## AP-07 · 版本号游戏

**信号**
- 目录名或技能名里带 `-v2`、`-final`、`-new`、`-old`
- 两个技能内容 90% 相同，只有版本后缀不同
- 错别字修正也升了版本号，或者破坏了老用法还是 `1.0.1`
- `CHANGELOG` 里写着「优化」「完善」「改进」，没说改了什么

**代价**：两件事同时发生——**该动版本的时候没动**（使用方无法判断是否受影响），和**不该动的时候动了一堆**（版本号失去信号价值）。带 `-v2` 的目录更是直接制造了两份需要同时维护的真相。

**修法**：

- 版本号只在 frontmatter 的 `version` 字段里。**目录名和技能名永远不带版本**
- 升位判据：

| 改了什么 | 版本位 |
|---|---|
| 错别字、排版、链接 | 不动 |
| 补边界情况、细化步骤 | `1.x.0` |
| 步骤顺序/判据变化，老用法仍可用 | `1.x.0` |
| 触发面变化、老用法失效 | `2.0.0` |

- 旧版本靠 **git 历史**保留，不靠并存目录。真要并存，走分支，不要在主干放两份

**触发面变化一律算破坏性**，因为依赖它的其他技能可能就调不到了。

> **例子**：仓库里同时有 `db-migrate` 和 `db-migrate-v2`。新人不知道该用哪个，Agent 各次调用命中不同的那个，一半的迁移没跑 rollback 校验。

## AP-08 · 触发描述写成分类标签

**信号**
- 描述里是名词短语：「XX 规范」「XX 工具集」「关于 XX」
- 描述里没有一句用户会说的原话
- 统计下来技能几乎从不被自动触发，只有人手点才用
- 描述和技能标题几乎是同一句话

**代价**：**技能等于不存在。** 触发描述是它唯一的入口。写成分类标签，只有已经知道它存在的人才能用——那就不需要技能了，直接问你更快。

**修法**：按 `writing-a-skill.md` 的规则重写：

1. 枚举 4~6 个**用户真实会说的话**（去翻聊天记录找原话，别自己编）
2. 写清「不用」的场景和替代技能
3. 控制在 40~120 字

对照检查：

```markdown
差：一个帮助管理数据库迁移的技能。
好：用户要改表结构、加字段、写迁移脚本、问「这次 schema 变更怎么上」，
    或者迁移跑失败了要回滚时使用。不覆盖生产环境的数据修复，那走 oncall。
```

> **例子**：某技能描述写的是「前端工程化最佳实践集合」。三个月里被自动触发 0 次。改成「用户要配构建、说打包变慢了、要加 lint 规则、问为什么本地能跑 CI 挂掉时使用」之后，一周内被命中 6 次——技能一个字都没改，改的只是入口。

## AP-09 · 密码和内部信息

**信号**
- 正文、示例、`references/` 里出现形如 `sk-`、`AKIA`、`ghp_` 的字符串
- 出现真实内网域名、IP、数据库连接串
- 出现真实客户名、订单号、用户手机号
- 出现「我们的密钥是 ___」「密码放在 ___」这类指路

**代价**：技能会跟着代码进版本控制、被克隆、被同步到别人的环境，**而且它的读者是所有能拉到仓库的人，包括未来的 Agent 会话**。一次泄漏是不可撤回的，只能紧急轮换。

**修法**：

1. **占位符化**：所有凭证位置写成 `<YOUR_API_KEY>`、`<DB_URL>`
2. **指路不指值**：写「密钥从环境变量 `X_API_KEY` 读取」，不写「密钥是 xxx」
3. **提交前扫一遍**：`rg -n "sk-|ghp_|AKIA|BEGIN .*PRIVATE KEY" skills/`
4. **示例数据脱敏**：客户名换成 `acme-corp`，手机号换成 `138****0000`
5. 在技能的「权限与用途说明」里如实申报是否接触凭证——写了「不接触」却又在正文里要求填密钥，是自相矛盾

> **例子**：一份「对接第三方支付」的技能，示例请求里贴了沙箱密钥——而沙箱和生产的密钥前缀相同。半年后有人以为沙箱密钥可以公开，把生产密钥贴进了同一个位置。

## AP-10 · 宣言式版本说明

**信号**
- `CHANGELOG` 或 PR 描述写着「优化流程」「完善细节」「体验改进」
- 改动理由是「感觉更清晰了」
- 提交者在被问「为什么改」时，回答的是「更好的实践」
- 一次改动同时动了触发面和三个步骤，但版本号只动了 patch

**代价**：**技能体系失去反馈回路。** 技能最有价值的信息不是当前内容，而是「哪条规则是什么时候、因为哪次事故加进来的」。丢掉这个，下一个人会把它改回去，事故再来一次。

**修法**：版本说明写**三要素**——改了什么、为什么改、影响谁。

```markdown
## 1.2.0

**改了什么**：迁移前增加一次 rollback 验证（新增步骤 3）。
**为什么**：9 月 12 日生产迁移后无法回滚，根因是没有在预发验证过 rollback 路径。
**影响谁**：所有执行数据库变更的人；不改变原有命令，只是多一步。
```

**「为什么」那行是必须的**，而且必须指向一件**真实发生过的具体事情**（事故、工单号、评审结论）。指向不出具体事情，说明这次改动没有依据，应该先讨论要不要改。

> **例子**：某技能的「为什么」写的是「补充更完整的检查」。三个月后另一位同学清理「冗余步骤」时把它删掉了——因为没人知道它是为了一次数据事故加的。事故复发。

## 怎么用这份清单

**别指望一次清干净。** 反模式是自然积累的，清理也该是渐进的。

建议节奏：

1. **新技能**：写的时候对着这十条过一遍，成本最低
2. **评审时**：把速查表挂进 PR 模板，评审人逐条打勾
3. **每季一次**：拿速查表左边的十条扫一遍全部技能，记录命中数，**只修最严重的两个**

第 3 条刻意限制数量。一次全改必然改不完全，改一半的状态比不改更危险——一半技能是新规矩，一半是旧习惯，执行者无法预期。

**优先修哪两个**：先修 AP-02（复制粘贴）和 AP-05（边界只写一半）。这两条直接导致**输出错误**，其余八条更多是「不好用」。错误比难用严重。
