# 三剪客 · 自建 S3 对象存储

你的程序里到处在找「一个放文件的地方」：上传的图片、生成的视频、模型权重、日志归档。用公有云的对象存储要按量付费、要出网、数据在别人机房；直接挂一个共享目录又顶不住并发、不好做权限。MinIO 补的就是这个位置——在你自己的一台或几台机器上跑起来，对外提供**和 S3 兼容的 HTTP API**，现成的 S3 SDK、AWS CLI、各种备份工具不用改代码就能连上。

它只有一个服务端二进制加一个命令行客户端，部署成本低；带一个网页控制台，建桶、传文件、看用量都能点出来。要注意的是：社区版目前**只发源码**，不再提供预编译二进制包，拿它之前先把获取方式确认清楚。

**上游项目**：`MinIO`　**仓库**：https://github.com/minio/minio

## 什么时候用 / 不用

**用它**：

- 你要在自己的机器/NAS/内网服务器上有一个 S3 兼容的对象存储端点，让程序用标准 S3 SDK 读写。
- 应用代码已经按 S3 API 写好了，只是在找一个能自托管的实现，不想改代码。
- 想给 AI 训练/推理流程、备份任务、日志归档准备一块集中的「桶存储」，并且能自己控制数据在哪台机器上。
- 需要单节点起步、以后能扩成多节点的对象存储，且希望管理界面开箱可用。
- 需要给不同调用方发不同的访问凭证（应用账号、只读账号），而不是共享一个系统账号。

**不要用它**：

- 你要的是**网盘/共享盘**：要挂载成盘符、多人协同编辑、在线预览 Office 文档——那不是它的定位。
- 你要的是**文件系统语义**：随机写、改名、目录遍历、文件锁。对象存储是「整对象 PUT/GET」，没有这些。
- 你要的是**数据库**：对象存储不是块存储，不要指望它承载数据库的数据目录。
- 数据量很小、只有一个进程用、就在一台机器上：直接写本地目录更简单，引入一个服务端只是多一个故障点。
- 你需要**商业 SLA 与厂商支持**：社区版按源码分发、按现状提供，要承诺得走它的商业版路线。
- 你打算**转售或改包分发**：许可证是 AGPLv3，商业闭源转售要先解决合规问题。

## 安装

社区版目前的获取方式以官方文档为准：**源码安装**或**自行构建容器镜像**，历史预编译二进制仍可下载但已不再维护。

**方式一：从源码安装（需要 Go 工具链）**

```bash
go install github.com/minio/minio@latest
```

装完确认可执行文件在 `PATH` 里：

```bash
minio --version
```

**方式二：Windows 包管理器**

```powershell
winget install --id MinIO.Server -e
winget install --id MinIO.Client -e
```

**方式三：容器（镜像里的启动动作是 `server`，你补参数即可）**

```bash
docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=admin \
  -e MINIO_ROOT_PASSWORD='替换成强口令' \
  -v /srv/minio/data:/data \
  minio/minio server /data --console-address ":9001"
```

镜像标签与推荐用法以官方容器文档为准。

**命令行客户端 `mc`**

```bash
# macOS / Linux 常用包管理器
brew install minio-mc
# 也可以直接下载对应平台的二进制
mc --version
```

**多节点起步**：把多个数据目录/多个节点地址一起传给 `server` 子命令；分布式部署对时间同步、磁盘、网络的要求比单机高得多，规模化和故障域设计请以官方分布式部署文档为准，不要凭单机经验直接扩。

装完先做一件事：把 root 凭证从默认值换掉。默认 root 账号密码是 `minioadmin:minioadmin`，暴露在网络上等于没有认证。

## 常用操作

**1. 前台启动单节点，指定数据目录与固定控制台端口**

```bash
MINIO_ROOT_USER=admin MINIO_ROOT_PASSWORD='强口令' \
  minio server /srv/minio/data --console-address ":9001"
```

服务端 API 默认在 `:9000`，控制台默认端口是随机的——不指定 `--console-address` 时，启动日志里才会告诉你控制台落在哪个端口。

**2. 客户端加一个别名（后续命令都用它）**

```bash
mc alias set local http://127.0.0.1:9000 admin '强口令'
mc admin info local
```

**3. 建桶、传文件、列表**

```bash
mc mb local/media
mc cp ./demo.mp4 local/media/
mc ls local/media/
mc ls --recursive --summarize local/media
```

**4. 桶之间/本地与桶之间整树同步（做镜像，不是双向同步）**

```bash
mc mirror ./exports local/media
mc mirror --overwrite local/media local/media-backup
```

`mc mirror` 默认只做「源 → 目标」方向的补齐与覆盖，删不删目标端多余文件取决于你是否加对应删除开关——动手前先看 `mc mirror --help`。

**5. 生成给应用用的有限权限凭证**

```bash
mc admin user add local appuser '应用侧口令'
mc admin policy attach local readwrite --user appuser
mc admin user list local
```

策略名与可用策略以 `mc admin policy list local` 的输出为准。

**6. 排查用：看服务端状态与桶占用**

```bash
mc admin info local
mc du local/media
mc admin trace -v local
```

**7. 用任意 S3 工具连接（不改代码的验证方式）**

```bash
aws --endpoint-url http://127.0.0.1:9000 s3 ls
```

`aws` 需要预先配置好 Access Key / Secret Key 与区域字段（自建端点的区域字段通常填空或默认值即可，具体以你所用 SDK 的要求为准）。

**8. 以服务方式常驻（Linux）**

用你所用发行版的 init 系统把它注册成服务，或直接用容器编排；服务定义文件以官方部署文档给出的版本为准，注意数据目录权限要交给运行用户。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 浏览器打不开控制台，API 却是通的 | 控制台端口默认随机分配，且和 API 端口不是一个 | 启动时显式指定 `--console-address ":9001"`，并在防火墙/安全组放行该端口 |
| 用默认的 `minioadmin:minioadmin` 就跑起来了 | 没有设置 root 凭证环境变量 | 立刻换成强口令并重启；已经暴露过的实例按「凭证已泄露」处理 |
| 升级到新版本后想降级，起不来或数据异常 | 新版本写入的格式旧版本不认识，官方不建议降级 | 升级前先确认回滚路径与备份；生产环境先在小规模上验证再推 |
| 老教程里的 `gateway` 用法在新版本上执行不了 | 该用法已从社区版移除 | 别照抄旧教程；需要对接外部存储就直接用它的 S3 客户端工具，不要指望网关模式 |
| 把数据目录放在 NFS / SMB 网络共享上 | 对象存储对文件锁与并发写语义有要求，网络文件系统不满足 | 数据目录必须是本地直连磁盘或块设备；共享盘只能作为客户端侧的搬运用途 |
| 往已有部署里直接加一块硬盘期望扩容 | 单机下的目录集合与分布式池的扩展规则都不是「随便加盘」 | 扩容方式按官方文档操作；实在要加就评估新建部署再迁移数据 |
| 桶里同名对象被覆盖，历史版本找不回 | 没有开启桶版本控制 | 需要留历史就对该桶开启版本控制；旧版本会持续占用空间，配合生命周期规则清理 |
| 权限配得太宽，应用拿到了全库读写 | 直接给应用 root 凭证，或策略给成了管理员 | 一律为应用单独建用户并只授予所需策略；root 凭证只用于管理操作 |
| 上传大文件时连接断开、留下分片垃圾 | 分片上传（multipart）中断后分片不会自动消失 | 定期用 `mc admin` 相关命令清理未完成的分片上传；客户端侧配好重试 |
| 并发上传报时间偏差/签名错误 | 服务端与客户端时钟不一致，签名校验失败 | 在所有节点上启用时间同步服务，把时钟偏差压到秒级以内 |
| 单机部署被当成高可用使用 | 单节点就是单点：机器挂了服务就不可用 | 真正要可用性就按官方分布式方案部署多节点，并接受随之而来的运维复杂度 |
| 直接抓了历史二进制用于生产 | 社区版已改为源码分发，历史二进制不再更新，含已知问题也不修 | 生产用源码构建或自行构建的镜像；把「不再维护」这个前提写进你的部署说明 |
| 把控制台直接暴露到公网 | 管理面暴露等于把配置与用户管理交出去 | 控制台只开给内网或经跳板/反向代理加鉴权；API 也建议限制来源 |
| 对象存储当本地目录用（频繁改名、随机写） | S3 语义里「改名」是复制+删除，随机写也不成立 | 这类负载用文件系统或块存储；对象存储只放整份写整份读的数据 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 服务端监听 API 与控制台端口对外提供服务；客户端命令需要能连到服务端 |
| 读取文件 | 是 | 服务端读取数据目录中的对象分片与元数据；客户端读取要上传的本地文件 |
| 写入文件 | 是 | 服务端写入对象数据与元数据；客户端下载/镜像会写本地目标目录 |
| 凭证 | 是 | root 账号口令（环境变量传入）与各应用用户的 Access Key / Secret Key；`mc` 客户端把这些存在自己的配置目录里 |
| 子进程 / 后台常驻 | 是 | 服务端必须常驻才能提供存储；通常交给容器或 init 系统托管 |

## 能力边界

**覆盖**：

- 提供 S3 兼容的 HTTP API 端点，现有 S3 SDK / CLI / 备份工具可直接对接。
- 对象与桶的管理：建桶、上传下载、列举、整树镜像、用量统计。
- 用户与策略管理：为应用创建独立凭证、按策略限定权限。
- 桶版本控制与生命周期规则（用于留存历史与清理旧版本）。
- 单节点起步到多节点分布式的部署形态，以及容器与 Kubernetes 下的部署途径。
- 内置网页控制台，便于人工建桶、浏览对象、查看服务状态。

**不覆盖**：

- 不做文件系统语义：没有随机写、改名、目录遍历、文件锁；对象只能整份读写。
- 不做网盘/协同编辑/在线文档预览。
- 不做数据库或块存储，不能承载数据库的数据目录。
- 不做跨站点容灾与备份策略设计；桶复制、备份编排要你另行规划。
- 不提供商业 SLA 与厂商级技术支持；社区版按「源码分发 + 按现状」提供。
- 不做数据内容处理（转码、压缩、识别），只负责存与取。

## 依赖条件

- **部署形态二选一**：从源码构建（需要 Go 工具链），或自行构建/使用容器镜像（需要容器运行时）。
- **操作系统**：主流 Linux 发行版、Windows、macOS 均可跑单机；生产建议 Linux。
- **磁盘**：数据目录必须是本地直连存储；容量按对象总量与版本/分片开销预留。
- **时间同步**：多节点部署必须启用时钟同步，否则签名校验会失败。
- **网络**：对客户端开放 API 端口（默认 `9000`）与控制台端口（建议显式指定，如 `9001`）；分布式部署还需节点间互通。
- **凭证**：root 账号口令必须自设；应用侧凭证按需创建。无需任何云端账号，也**不涉及大模型或算力调用**。
- **许可证**：AGPLv3。自用与二次开发前先确认你的分发与商业化方式是否满足其义务。

## 已知限制

- 社区版当前按源码分发，历史预编译二进制不再更新，安全修复不会回补到旧二进制上。
- 不支持版本降级：新版本写入的数据格式旧版本可能无法识别。
- 单节点是单点故障，不具备高可用；要多节点就得接受分布式部署的运维成本。
- 对象存储语义限制导致「改名」「随机写」类负载效率很低，甚至不可用。
- 控制台默认随机端口，初次部署最容易在这里卡住。
- 分布式部署对磁盘、网络、时钟的一致性要求高，不能按单机经验线性外推。

## 自检清单

执行前：

- [ ] 确认获取方式（源码构建 / 容器镜像），并确认拿到的是仍在维护的版本。
- [ ] 确认数据目录在本地直连磁盘上，不是网络共享目录。
- [ ] 规划好端口：API 与控制台分别用哪个，防火墙/安全组是否放行。
- [ ] 准备好 root 强口令，并决定应用侧需要几个用户、各自什么权限。

执行后：

- [ ] `mc admin info <别名>` 能正常返回服务端信息与磁盘状态。
- [ ] 控制台用规划好的地址能打开，且**没有**用默认 `minioadmin:minioadmin`。
- [ ] 建一个测试桶，`mc cp` 上传并 `mc cp` 下载，内容一致，然后清理。
- [ ] 应用用户用其自己的凭证能读写成，且访问未授权的桶会被拒绝。
- [ ] 确认服务能随机器重启自动拉起，数据目录权限正确。
- [ ] 明确记录：当前是单节点还是有高可用能力，别在文档里含糊。
