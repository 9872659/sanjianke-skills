# 三剪客 · 电商后台管理前端

`mall-admin-web` 是一套开箱可跑的电商后台管理前端：商品、订单、营销、权限、会员这些日常运营要用到的页面它都已经画好了，接口层也接好了，只要把后端地址指过去就能登录干活。它解决的是"我不想从零写后台"这件事——你拿到的是一个能直接改成自己业务的运营工作台，而不是一个 UI 组件库。

**上游项目**：`mall-admin-web`　**仓库**：https://github.com/macrozheng/mall-admin-web

## 什么时候用 / 不用

**用它**：

- 你要给一套已存在的电商后端（尤其是 mall / mall-swarm 系的后端）配一个可直接登录使用的运营后台，不想从零排商品列表、订单列表、富文本编辑这些页面。
- 你想快速看懂一个成熟的电商后台长什么样：菜单结构、权限路由、接口封装、表格与表单的交互范式，拿它当参照物改自己的项目。
- 团队没有专职前端，但需要马上把"商品上架、订单发货、优惠券配置"这几条运营链路跑起来验收后端。
- 你要做的是纯前端工作：调接口、改字段、换品牌色、增删菜单项，而不是重写后端业务。
- 你需要一个 Vue 3 + Vite 的现成项目骨架，方便在里面继续加自己的业务页面。

**不要用它**：

- 你的后端不是它认识的接口协议。它的页面是按固定接口路径和返回结构写的，后端字段对不上时改造成本可能高于自己写。
- 你要的是 C 端商城（消费者下单页面）而不是运营后台——那是另一个项目（`mall-app-web`），拿这个改等于重新做。
- 你只有静态页面需求、不需要真实登录与权限：它整套路由和菜单是跟着后端权限走的，没有后端就跑不通主流程。
- 你打算把它当 API 网关或后端服务用——它纯粹是浏览器端的前端工程，不处理任何业务逻辑。
- 你需要在没有 Node.js 工具链的环境里直接改一个 HTML 文件就上线：它必须经过依赖安装与构建。
- 你要做的是小程序或移动端 App。

## 安装

前置：本机已装 Node.js，**需要 v20 以上版本**（官方建议用 v20.x 的 LTS 版）。

```bash
# 1. 取代码
git clone https://github.com/macrozheng/mall-admin-web.git
cd mall-admin-web

# 2. 按需切换 npm 镜像源（国内网络建议）
npm config set registry https://registry.npmmirror.com
# 想换回官方源：
# npm config set registry https://registry.npmjs.org

# 3. 安装依赖
npm install
```

改用 yarn 也可以，命令以仓库当前 `package.json` 里的 scripts 为准：

```bash
yarn install
yarn dev
```

也可以不跑源码，直接下载 GitHub Releases 里的发行包，解压到 Nginx 的 `html` 目录后访问。发行包地址以仓库 Releases 页当前内容为准。

## 常用操作

**1. 指定后端接口地址（启动前必做）**

编辑项目根目录的 `.env.development`，把后端 API 基础路径改成你自己的：

```bash
# 后端API基础路径
# 不搭建后端、只想看看界面，可以先用在线 API（仅有查看权限）
VITE_BASE_SERVER_URL = http://localhost:8080
```

**2. 本地启动开发服务器**

```bash
npm run dev
```

启动后访问 http://localhost:5173 。登录一次，然后在浏览器开发者工具的网络面板里核对请求路径，确认确实打到了 `.env.development` 里配置的地址。

**3. 生产构建**

```bash
npm run build
```

构建产物默认在 `dist/` 下，把它作为静态资源目录交给 Nginx 或任意静态服务器托管。具体的构建脚本名与输出目录以 `package.json` 的 `scripts` 段当前内容为准。

**4. 用 Nginx 部署发行包**

把解压出来的目录放到 Nginx 的 `html` 目录下，命名为 `admin`，启动 Nginx 后访问：

```bash
# 访问地址形如
http://localhost/admin/
```

这个路径规则来自官方部署说明；你自己的站点路径以 Nginx 配置为准。

**5. 核对 Node 版本**

```bash
node -v
npm -v
```

版本低于 v20 时先升级 Node.js 再装依赖，否则容易在安装/启动阶段报错。

**6. 后端换成了微服务版时，接口要走网关**

如果你的后端是微服务架构而不是单体应用，接口入口是网关而不是某个业务服务的端口。此时 `.env.development` 里的地址要写成网关地址加后台服务的前缀，而不是直接指到业务服务的端口上。具体网关端口与前缀以你后端实际的网关路由配置为准。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `npm install` 卡住或大量超时 | 默认走官方源，国内网络不稳 | 先 `npm config set registry https://registry.npmmirror.com` 再重装；必要时删掉 `node_modules` 重来 |
| 装依赖或启动时报 Node 版本相关错误 | Node.js 低于 v20 | 升级到 v20 以上（建议 v20.x 的 LTS 版），再重新 `npm install` |
| 页面能打开但所有请求都失败 | `.env.development` 里的 `VITE_BASE_SERVER_URL` 还指向默认地址，或指向了没启动的后端 | 改成自己后端的真实地址，确认后端已启动、端口可达 |
| 登录后立即被弹回登录页 | 后端返回的鉴权信息没被前端接住，或接口跨域被浏览器拦了 | 先在开发者工具网络面板看登录请求的响应与是否有 CORS 报错，再回到后端排查跨域与鉴权配置 |
| 改了 `.env.development` 但地址没生效 | 开发服务器只在该文件被改动时重新读取，有时没热更新到 | 停掉 `npm run dev` 重新启动一次 |
| 直接双击 `dist/index.html` 打不开页面 | 构建产物是给静态服务器托管的，`file://` 协议下路由和资源路径都不成立 | 用 Nginx 或其他静态服务器托管 `dist/`，不要用文件协议打开 |
| 部署到 Nginx 的子路径后刷新页面 404 | 前端路由需要服务端把所有未匹配路径回落到 `index.html` | 在 Nginx 配置里加 `try_files $uri $uri/ /index.html;` 一类的回落规则 |
| 报错里出现不认识的接口字段 | 前端页面按固定接口结构渲染，后端返回的字段名或层级不一致 | 对照后端接口文档逐个字段核对；字段差异大时优先改前端适配层，而不是硬改页面组件 |
| 后端换成微服务版后所有接口 404 | 接口入口是网关，配置里却直接指向了某个业务服务的端口 | 把地址改成网关地址加后台服务前缀，前缀与端口以你后端的网关路由配置为准 |
| `npm run build` 成功但线上白屏 | 资源基础路径与实际部署子目录不匹配 | 检查构建配置里的基础路径，确认与 Nginx 里的实际访问路径一致 |

## 依赖条件

- Node.js **v20 及以上**（官方建议 v20.x LTS）。
- 一个可访问的、与前端页面接口协议匹配的后端服务；默认按 `http://localhost:8080` 联调。
- 可用的 npm 源（国内建议切镜像源）。
- 浏览器（现代 Chromium / Firefox / Safari 均可）。
- 可选：Nginx 或其他静态文件服务器，用于生产托管。

## 已知限制

- 工程按固定的接口路径与返回结构编写，换后端需要评估适配改造量，不能保证即插即用。
- 官方更重的笔墨在配套后端项目上，前端代码的更新节奏与后端不完全同步，遇到差异以仓库当前代码为准。
- 默认配置面向本地开发，直接暴露到公网前必须自行处理鉴权、HTTPS、跨域白名单等问题。
- 依赖版本与构建脚本会随仓库演进变化，本文给出的命令如与仓库当前 `package.json` 不一致，以仓库为准。
- 不承诺任何性能指标与并发能力，它是前端工程，性能瓶颈通常在它所调用的后端。
