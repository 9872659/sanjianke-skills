# 三剪客 · 关系图可视化引擎

它把"一堆点和线"的关系数据变成可看、可拖、可缩放的关系图：节点、连线、分组（combo）、布局算法、交互行为、主题与插件都在一套引擎里。适合做关系分析（谁和谁有联系、网络结构长什么样）、拓扑与链路图、组织与依赖关系图；不适合拿它画柱状图、折线图那类统计图表。

**上游项目**：`G6`　**仓库**：https://github.com/antvis/G6

## 什么时候用 / 不用

**用它**：

- 数据本身是"节点 + 边"的关系结构：社交关系、资金往来、设备拓扑、依赖关系、知识图谱、血缘图。
- 要在 Web 上做可交互的关系图：拖拽节点、缩放平移画布、点击选中高亮、展开收起邻居、悬停看详情。
- 需要现成的图布局算法：力导向、环形、网格、树 / 层次等，不想自己实现布局求解。
- 需要分组（combo）、节点徽标、边标签、自定义节点图形这类元素层面的能力。
- 需要主题与配色方案（内置明暗主题与多套色板），或需要插件扩展（如缩略图、工具栏这类）。
- 需要在 Canvas / SVG / WebGL 之间选择渲染方式，或需要 Node.js 侧渲染。

**不要用它**：

- 要画的是常规统计图表（柱状、折线、饼图）。那是图形语法可视化库的领域，用 G6 是走错门。
- 要画的是流程图、泳道图、BPMN 这类"可编辑的图形编辑器"。这类场景更适合面向图编辑的库。
- 数据是地理空间数据（地图、轨迹）。用地理可视化方案。
- 只需要列出节点和边的表格，或者用文字描述关系。上可视化引擎是过度设计。
- 节点 / 边数量极大（几十万级）且要求全量实时交互。图渲染的成本与布局计算量会先撑不住，需要先做裁剪或换专门的大图方案。
- 团队不接受引入一套图可视化依赖与相应的学习成本。

## 安装

**npm / yarn（v5 系列）**

```bash
npm install @antv/g6
```

```bash
yarn add @antv/g6
```

**注意版本分叉**：仓库有 `v5` 与 `v4` 两套并行的大版本，API 完全不同（v4 用 `new G6.Graph({...})` 加 `graph.data()` / `graph.render()`；v5 用 `import { Graph } from '@antv/g6'` 加配置式 `data`、`layout`、`behaviors`）。npm 上的 `latest` 标签当前指向 5.x 系列。老项目升级前务必确认自己在哪一版。

**浏览器直接引入**：包内提供 UMD 产物（`dist/g6.min.js`），通过 `<script>` 引入后从全局命名空间取 `Graph`。具体全局变量名与产物路径以实际版本文件为准。

**本地开发仓库（改源码时才需要）**

```bash
pnpm install
pnpm build
pnpm site        # 起文档站 / 示例站
```

## 常用操作

**1. 最小可用：两个节点一条边**

```html
<div id="container"></div>
```

```js
import { Graph } from '@antv/g6';

const data = {
  nodes: [
    { id: 'node1', label: '节点 1' },
    { id: 'node2', label: '节点 2' },
  ],
  edges: [{ source: 'node1', target: 'node2' }],
};

const graph = new Graph({
  container: 'container',
  data,
  layout: { type: 'force' },           // 力导向布局
  behaviors: ['drag-canvas', 'zoom-canvas', 'drag-element'],
});

graph.render();
```

**2. 换布局**

`layout` 配置项的 `type` 决定布局算法。内置了多套常用布局（力导向、环形、网格、树 / 层次等），部分布局依赖 GPU 或并行计算。可选值与各布局的自有参数以官方文档的布局章节为准：

```js
const graph = new Graph({
  container: 'container',
  data,
  layout: { type: 'circular' },
});
graph.render();
```

**3. 用 palette 做分组配色**

节点 / 边 / combo 支持按字段映射颜色，常用于把同一类别的节点染成同一色：

```js
const graph = new Graph({
  container: 'container',
  data,
  node: {
    palette: {
      type: 'group',
      field: 'cluster',
    },
  },
  layout: { type: 'force' },
});
graph.render();
```

**4. 配置交互行为**

`behaviors` 是一个字符串数组，内置了十多种交互行为（画布拖拽、缩放、节点拖拽、点击选中、悬停高亮等）：

```js
const graph = new Graph({
  container: 'container',
  data,
  behaviors: ['drag-canvas', 'zoom-canvas', 'drag-element', 'click-select'],
});
graph.render();
```

**5. 更新数据并重新渲染**

拿到新数据后用 `setData` 替换数据源，再调用绘制 / 渲染方法刷新画布：

```js
graph.setData({
  nodes: [...],
  edges: [...],
});
graph.render();
```

在已有图上做增量更新时，先看官方文档给出的 API 与生命周期说明，别直接改原对象里的数组然后指望它自动刷新。

**6. 切换主题 / 调整样式**

节点、边、combo 的样式通过 `node` / `edge` / `combo` 配置项逐层设置；主题与配色可通过主题相关 API 或 `node.palette` 切换（内置明暗主题与多套社区色板）。具体键名以官方文档为准。

**7. 注册并使用自定义元素**

需要自定义节点形状、边样式、布局或交互时，走引擎的扩展注册机制（注册扩展 → 在配置里按注册名引用）。注册分类、方法签名与示例以官方文档的扩展章节为准：

```js
import { register } from '@antv/g6';

register('node', 'my-node', {
  // 自定义节点绘制逻辑，具体接口以官方文档为准
});
```

**8. 销毁图实例**

```js
graph.destroy();
```

单页应用里路由切换或组件卸载时必须销毁，否则画布、事件监听与布局计算会残留。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 照抄仓库 README 的示例跑不通 | 默认分支上的示例属于 v4，而目前 npm `latest` 是 v5，两者 API 完全不同 | 先 `npm ls @antv/g6` 确认实际大版本，再看对应版本官方文档；v5 用 `new Graph({ container, data, layout, behaviors })` 的配置式写法 |
| 图画不出来，容器是空白 | 容器选择器取不到元素，或容器宽高为 0（未显式设置、父级隐藏） | 确认容器存在且宽高非 0；容器尺寸变化后需要通知图实例重新计算 |
| 节点全部堆在左上角一个点上 | 没有配置 `layout`，节点缺少初始坐标 | 配置一个布局（如 `{ type: 'force' }`），或在数据里为节点显式提供坐标 |
| 拖拽 / 缩放没反应 | `behaviors` 没配，或配的行为名写错 | 在 `behaviors` 里按官方文档的行为名配置，例如画布拖拽、缩放、节点拖拽、点击选中 |
| 数据更新后画面没变化 | 直接在原对象上改数组，没有走更新 API | 用 `setData` 替换数据源后再调用渲染方法；大图增量更新按官方文档的 API 处理 |
| 页面切来切去后越来越卡 | 每次进入都新建图实例，旧的没 `destroy()` | 组件卸载 / 路由离开前调用 `graph.destroy()`，或复用同一实例并更新数据 |
| 大量节点时布局算很久或页面卡死 | 布局算法复杂度与节点规模相关，部分布局开销较大 | 控制节点规模、先做裁剪 / 聚合，或换更轻的布局；GPU / 并行布局需要相应的运行环境支持 |
| 节点文字在不同机器上错位 | 字体度量差异或未等字体加载完成就渲染 | 等字体就绪后再渲染，或使用内置文本元素并留足边距 |
| 服务端 / Node 环境渲染报错 | 默认走浏览器渲染路径 | 服务端渲染需要额外的渲染环境配置，具体按官方文档的服务端渲染方案来做 |
| React 项目里状态更新后图错乱 | 图实例与组件生命周期没对齐，重复渲染 | 用官方 React 生态里的封装方案，或在 effect 里规范创建 / 更新 / 销毁 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 不需要（除非关系数据由你的应用远程拉取） | 本包自身不联网；安装依赖时需要访问 npm 源 |
| 读取文件 | 不需要 | 数据由调用方在内存中提供 |
| 写入文件 | 不需要 | 只操作页面 DOM 与画布 |
| 凭证 | 不需要 | 不涉及账号或密钥 |
| 子进程 / 后台常驻 | 不需要 | 前端运行时库，无守护进程；大型布局可能在浏览器内占用较多 CPU / GPU |
| 浏览器 DOM / Canvas | 间接需要 | 关系图需要挂载到页面容器，并使用 Canvas / SVG / WebGL 之一渲染 |

## 触发场景

- "我有一份节点和边的数据，想画成关系网络图"
- "怎么让关系图里的节点能拖拽、画布能缩放"
- "图里的节点都挤在一起了，怎么自动布局"
- "想按类别给节点上色，或者把一组节点圈成一个分组"
- "要自定义节点的形状 / 图标怎么做"
- "关系图数据量很大，怎么优化渲染性能"

## 能力边界

**覆盖**：

- 关系图 / 网络图的渲染：节点、边、combo（分组）、标签、徽标等元素，样式可配置，支持数据回调
- 十多种内置布局算法（力导向、环形、网格、树 / 层次等），部分布局支持 GPU / 并行加速，支持自定义布局
- 十多种内置交互行为（画布拖拽、缩放、元素拖拽、选中、悬停等），并提供事件机制以便扩展
- 主题与色板：内置明暗主题，集成多套社区色板
- 多环境渲染：Canvas、SVG、WebGL，以及 Node.js 侧渲染能力
- 插件机制：内置插件与自定义插件扩展
- 扩展注册机制：自定义节点 / 边 / combo / 布局 / 交互 / 插件
- 与 React 生态的集成方案（官方生态中有对应封装）

**不覆盖**：

- 常规统计图表（柱状图、折线图、饼图、散点图）的绘制
- 可编辑的流程图 / 泳道图 / BPMN 图形编辑器
- 地理空间可视化（地图、轨迹、行政区划）
- 图数据的采集、存储、图算法服务端计算（引擎负责可视化，不负责数据源）
- 超大规模图的专用存储与分布式渲染方案
- 业务后台、权限、任务调度

## 依赖条件

- 运行环境：现代浏览器；服务端渲染需按官方文档配置 Node 侧渲染环境
- 前端工程：Node.js 与 npm / yarn / pnpm 等包管理器
- 渲染上下文：一个存在且宽高非 0 的 DOM 容器
- 版本约束：v4 与 v5 API 不兼容；npm `latest` 当前指向 5.x 系列，接入前必须确认目标大版本
- 可选：GPU / WASM 加速布局需要相应的运行环境支持
- 数据格式：至少需要 `nodes` 与 `edges` 两个数组，节点需有 `id`，边用 `source` / `target` 指向节点 id

## 已知限制

1. v4 与 v5 API 不兼容，跨大版本迁移基本等于重写图表配置，不能靠改几个参数完成。
2. 官方默认分支 README 的示例属于 v4，与 npm 上 latest（v5）不一致，照抄容易踩空。
3. 布局算法与节点规模强相关；节点量上去之后，布局计算和交互流畅度都会明显下降。
4. 颜色、主题、色板、行为的具体名称随版本演进，写代码时应以所装版本官方文档为准，不要凭记忆写。
5. 它是可视化引擎，不是图数据库或图计算框架；图分析算法的服务端能力需要另找方案。

## 自检清单

执行前：

- [ ] 确认数据是"节点 + 边"的关系结构，不是统计数据或地理数据
- [ ] 用 `npm ls @antv/g6` 或 `package.json` 确认目标大版本（v4 / v5），再去看对应文档
- [ ] 确认节点有唯一 `id`，边的 `source` / `target` 都能对上已有节点
- [ ] 容器元素存在且宽高非 0
- [ ] 评估节点规模，提前决定是否需要裁剪或聚合

执行后：

- [ ] 确认所有节点都渲染出来且分布合理（不是全挤在一个点）
- [ ] 试一遍拖拽、缩放、选中，确认 `behaviors` 生效
- [ ] 更新数据的场景下确认画面确实刷新了
- [ ] 组件卸载 / 路由离开时确认调用了 `destroy()`
- [ ] 大数据量场景实测一下布局耗时与交互帧率
- [ ] 记录实际使用的版本号，便于后续排查
