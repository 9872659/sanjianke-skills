# 成本与排错

---

## 一、成本：怎么算、怎么控

### 调用构成

处置是**一条直线**（不是循环），所以一次 `run` 固定是 **4 次调用**：

```text
接报 → 技术判断 → 授权 → 复盘
  1        1         1       1
```

没有"打回重跑"这一说 —— 稿子可以改十遍，一笔补偿批出去就收不回来了。
所以本包不做循环，只做**一次到底 + 每步都过闸门**。

### 字符 → token 的标定

| 方向 | 系数 | 说明 |
|---|---|---|
| 输入 | `chars_per_token_in = 1.61` | 1 token ≈ 1.61 个原始字符（含换行） |
| 输出 | `tokens_per_char_out = 1.11` | 1 个原始输出字符 ≈ 1.11 token |

**这是同族真机实测的标定值，不是厂商文档里的数字。**
用 `cost` 子命令可以按你自己的工单长度现算：

```bash
python3 scripts/run.py cost --file 工单.md
python3 scripts/run.py cost --file 工单.md --price-in 1 --price-out 2
```

### 实测数据

一张 626 字的真实工单（"批量出片 12 条只成功 3 条"）：

| 阶段 | prompt | completion | finish_reason |
|---|---|---|---|
| 接报 | 1463 | 605 | `stop` |
| 技术判断 | 1287 | 1089 | `stop` |
| 授权 | 1790 | 987 | `stop` |
| 复盘 | 1099 | 1219 | `stop` |
| **合计** | **5639** | **3900** | **9539 token / 4 次调用 / 约 22 秒** |

同一张工单跑三次：**9119 / 9365 / 9539 token**（4 次调用是固定值，波动来自生成）。

可以看到 **prompt 侧是逐步增长的**（1463 → 1283 → 1790 → 1094）；
授权比技术判断大，是因为它的提示词里带**整张权限矩阵**与工单卡 + 技术判定。

### 金额怎么算

**本包只报 token，不编价格。**

文本模型网关**不公布单价**（`GET /api/v1/models` 的返回里没有价格字段），
所以给不出金额。要折算请自己传单价：

```bash
python3 scripts/run.py run --file 工单.md --price-in <点/百万token> --price-out <点/百万token>
```

单位是**点/百万 token**，平台口径 1 元 = 100 点。

### 预算闸门

```bash
python3 scripts/run.py run --file 工单.md --budget 30      # 单位是「点」，不是元
```

- 超预算 → **不发起那次调用**，退出码 `5`
- 校验写在**每个会花钱子命令的第一步** —— 不会先报价、跑一半才发现超预算
- 给了 `--budget` 但没给单价 → 会提示"金额无法折算、预算也无法核验"，
  但**不拦**（金额本来就不可知，假装在预算内比不核更糟）

### 断点续跑能省多少

同一份工单 + 同一套权限矩阵 + 同一层级再跑一遍 → **4 步全部断点命中，0 次调用、0 token**。

断点 key 含**全部影响产出的维度**：

| 维度 | 为什么要进 key |
|---|---|
| 工单原文摘要 | 换了工单当然要重跑 |
| 层级 | 换了身份口径就不同 |
| **实际可批额度** | `--grant-cap` 改了就变了（不改会拿旧权限的产物当已完成 —— 可能是一次越权） |
| policy 版本 | 口径改了要重跑 |
| **整张权限矩阵** | 矩阵一改，旧产物就不可信了 |
| 各上游产物摘要 | 上游一改，下游必须跟着重跑 |

### 想更省

| 办法 | 效果 |
|---|---|
| `--max-tokens 2048` | 输出侧封顶更紧（本包每个角色的产出都不长，2048 通常够） |
| 分步跑并人工检查中间 JSON | 某一步不满意就不用把后面的钱也花了 |
| `--dry-run` | **完全免费**：只打印将发送的提示词 |
| 先 `cost` 再决定 | 零成本报价 |

## 二、`finish_reason`：怎么判断"是不是被截断了"

本包把每次调用的 `finish_reason` 记进台账与报告：

```
| 调用     | prompt | completion | finish_reason |
| 接报     | 1463   | 605        | `stop`        |
| 技术判断 | 1287   | 1089       | `stop`        |
| 授权     | 1790   | 987        | `stop`        |
| 复盘     | 1099   | 1219       | `stop`        |
```

**判据只有一条**：

| `finish_reason` | 含义 | 该做什么 |
|---|---|---|
| `length` | 输出被 `max_tokens` **截断** | **加大 `--max-tokens` 才管用** |
| `stop` | 上游说它写完了 | 若 JSON 坏了，是**模型自己写错了** —— **加大 max-tokens 没用** |
| `None` / 其它 | 响应可能在路上断了 | 同上：**加大 max-tokens 没用**，换模型重试或把工单拆短 |

> ⚠️ **不要用 content 长度判断是哪一种。**
> 同族踩过这个坑：只看到"解析失败"，就推断"网关在 2600~2900 字符处有固定上限"，
> 还把那个推断当**实测**写进了文档 —— 那是错的，已撤回。
> 证据：同一端点实测能拿到 3984 字符的完整内容（`finish_reason='stop'`），
> 而失败的那几次长度各不相同（1921~2781），**根本没有固定长度这条线**。
>
> 正确判据是**结构**（能不能按括号配平切出一个完整顶层值）+ `finish_reason`。

## 三、常见错误与处置

### 退出码速查

| 码 | 含义 | 先查什么 |
|---|---|---|
| `0` | 跑完且全过闸门 | —— |
| `2` | 参数/配置错 | 文件路径、`--outdir` 是否在包内、`--policy` 是否合法、`--budget` 是否 ≤ 0 |
| `3` | **硬闸门命中** | 看 stderr 汇总（标红那几行） |
| `4` | 调用失败 | Key、余额、模型名、网络 |
| `5` | 预算超限 | 加大 `--budget`，或先 `--dry-run` |
| `130` | 用户中断 | —— |

### 逐条排错

**`失败：鉴权失败（401）：Key 无效或已过期`**

三种配 Key 的方式，任选一种：

```bash
python3 scripts/run.py run --file 工单.md --key sk-xxxx
export A7W_API_KEY=sk-xxxx          # PowerShell: $env:A7W_API_KEY="sk-xxxx"
python3 scripts/a7w.py login --key sk-xxxx      # 写进 ~/.a7w/config.json
```

**`失败：点数不足（402）`**
到 https://api.a7w.cn/ 充值。注意：**本包不代付，也不内嵌任何 Key。**

**`失败：模型不存在（404）`**
模型名会变。用 `python3 scripts/run.py models` 现查在架的模型名。
另外：默认的 `deepseek-chat` 实测可用（路由到 deepseek-flash），
但它**不在** `models` 的返回列表里 —— 所以"列表里没有"不等于"不能用"。

**`闸门五 · 越权拦截（本包核心）`**

这是**设计如此**，不是 bug。看这几行：

```
权限矩阵结论：本级 L1_一线客服 上限 5000 点 ≈ ¥50，本单合计 19800 点 ≈ ¥198 → **超出，必须升级**
应升级给：L2_二线主管
```

三条可能：

| 情形 | 处理 |
|---|---|
| 确实该升 | 走升级流程；上一级用 `--as-role L2_二线主管` 重跑 |
| 该赔的没那么多 | 检查技术判断的归因是否过宽（比如把 `environment_issue` 当成 `product_defect` 赔） |
| 想试闸门 | 这是预期行为。`--grant-cap 0` 可以让任何一笔补偿都被拦下 |

**`[unknown_compensation] 补偿项「送定制玩偶」不在枚举里`**
补偿项是**8 项枚举**，不许自创。要么改用枚举内的一项，
要么把这笔补偿走**线下审批**（本包不管线下流程）。

**`[missing_escalate_to] 越权了却没在处置方案里写 escalate_to`**
拦下越权之后必须说清升给谁，否则这张工单挂死。
重跑一次通常就好（提示词里写清了这条要求）；连续出现可以 `--model` 换一个。

**`闸门六 · 时效` / `[sla_not_from_policy]`**
工单卡声明的时限与权限矩阵不一致。这是模型自己编了一个通用时限（比如 1440）。
重跑；若反复出现，检查 `--policy` 覆盖文件里 `sla_minutes` 是否给全了 P0~P3。

**`[sla_breach] **超时**：P1 用了 138 分钟处置，承诺时限（L1_一线客服）是 60 分钟`**
处置太慢。看 `handled_at` 是怎么来的 ——
如果工单里没写时间，本包会标 `timing_checked=false` 而不是判超时；
如果时间写错了格式，也解析不出来。

**`闸门七 · 处置完整性`**
三种形态：

| issue | 含义 |
|---|---|
| `missing_compensation_items` | 判"需要补偿"却没写补偿项 → 用户什么也没拿到，工单却被关了 |
| `missing_no_compensation_reason` | 判"无需补偿"却没写理由 → 拒了用户，但没人知道凭什么 |
| `voice_too_long` | 面客话术超过 600 字 |

**`闸门四 · 锚点到工单原文` / `未锚定率过高`**
模型在编引文。看报告里那张"⚠️ 编造的引文（已剔出）"表。
常见原因：工单太短（信息量不足，模型只能编）、或工单里用户原话被改写过。
**别关闸门** —— 把工单原文逐句保留贴进去就好。

**`闸门一 · 合规`**

两种口径要知道：

- **面客字段**（`voice_to_user`）零豁免 —— 命中就是命中
- **审类字段**（内部说明/复盘）开了引用/提到排除 —— 被排除的会列在
  `gates.compliance.quoted_from_material` / `mentioned_as_warning` 里，
  带 `not_counted_reason`，**不静默丢弃**

另外会看到这一行提示：

```
提示：**工单原文**里有 N 处违禁/承诺类表述 —— **只报不拦**
```

那是**用户写的字**，不是我们要发出去的，所以只报不拦。

`「最X」`被放过时也会提示：

```
提示：本地放过 N 处「最X」疑似命中（判为普通中文用法 / SLA 口径，**不静默丢弃**）
```

**假警报：合规闸门把「第一，」当成排他性宣称**

真机全跑抓到过一次：话术写「现在给你两件事：**第一**，那 9 条失败的任务……**第二**，……」，
`第一` 被判成「第一类排他性表述」。那是**列举序号**，不是宣称。
现在同段里出现后续序号（第二/第三…）即豁免；「行业第一。」没有后续序号，照拦。

**假警报：「100%」把内部指标当成效果承诺**

真机全跑抓到过一次：复盘写「失败任务自动退点**率** 100%。」被判成绝对化承诺。
那是**监控指标的目标值**。现在「指标名词 + 100%」与「100% + 指标名词」两种形态都豁免；
「100% 有效 / 100% 恢复 / 100% 保证」照拦。

> 这两条都是被真机逼出来的口径，不是事先想好的。误报的代价比漏报大 ——
> 假警报会让人把整个闸门关掉。所以宁可先放过正常中文与内部指标口径。

**`PackagePathError: --outdir ... 在 Skill 包内`**
产出不许进包。换到包外：

```bash
python3 scripts/run.py run --file 工单.md --outdir D:/support
```

**`--budget 必须大于 0（给的是 0.0）。单位是**点**，不是元`**
单位是点。0.5 元 = 50 点。

**`失败：--price-in 与 --price-out 要么都给、要么都不给`**
只给一个算不出金额，所以直接拒。

## 四、`--policy` 覆盖文件的坑

```bash
python3 scripts/run.py policy --policy 我的矩阵.json
```

**合法的覆盖文件**（只收窄，结构完整）：

```json
{
  "policy_version": "acme-2026-02",
  "compensation_types": {
    "free_retry": "免费重试一次",
    "grant_credit": "赠额",
    "apology_only": "仅致歉不改动"
  },
  "authority_levels": {
    "L1_一线客服": {
      "rank": 1, "cap": 3000, "need_below": 3000, "escalate_to": "L2_二线主管",
      "sla_minutes": {"P0": 10, "P1": 45, "P2": 180, "P3": 720}
    },
    "L2_二线主管": {
      "rank": 2, "cap": 20000, "need_below": 20000, "escalate_to": "",
      "sla_minutes": {"P0": 10, "P1": 30, "P2": 120, "P3": 720}
    }
  }
}
```

### 三类会被拒的写法（全部 `exit=2`）

**① 新增补偿项**

```json
{"compensation_types": {"refund_full": "全额退款", "送定制玩偶": "安慰礼"}}
```

```
失败：补偿项枚举**不许扩充**（覆盖文件里新增了 送定制玩偶）。
能新增就等于把「不许自创补偿」这条硬闸门关掉了；只能从包里写死的这 8 项里收窄。
```

**② `sla_minutes` 缺档**

```json
{"authority_levels": {"L1_一线客服": {"rank": 1, "cap": 100, "escalate_to": "",
                                      "sla_minutes": {"P0": 5}}}}
```

```
失败：authority_levels.L1_一线客服.sla_minutes 缺 P1、P2、P3
—— 时效闸门口径来自这里，缺了就没法判「超时」
```

**③ `escalate_to` 指向不存在的层级**

```json
{"authority_levels": {"L1_一线客服": {..., "escalate_to": "L9_临时工"}}}
```

```
失败：authority_levels.L1_一线客服.escalate_to 指向不存在的层级「L9_临时工」
——升级路径断了，越权就无处可去
```

## 五、`--grant-cap`：亲手把闸门试出来

```bash
python3 scripts/run.py settle --file 工单.md --card 卡.json --diag 判定.json --grant-cap 0
```

它把**本级实际可批额度**临时改成指定点数。真实场景就是**新人额度被临时收紧**。

**它不绕过层级判定**，只改本级额度 —— 所以：

- `--grant-cap 0` + 任何大于 0 的补偿 → **必被拦**（这是最快的"闸门有没有牙"的验证方式）
- `--grant-cap` 只影响 `settle` / `review` / `run`；`intake` / `diagnose` 上没有这个参数

跑出来是这样：

```
闸门五 · 越权拦截（本包核心）
  补偿合计 5000 点 ≈ ¥50 超出「L1_一线客服」的可批额度 0 点 ≈ ¥0 —— **越权**。
  超权限的补偿不许自作主张，必须升给「L2_二线主管」
  权限矩阵结论：本级 L1_一线客服 上限 0 点 ≈ ¥0，本单合计 5000 点 ≈ ¥50 → **超出，必须升级**
  应升级给：L2_二线主管
→ exit=3
```

## 六、`--json` 契约速查

```bash
# 成功
python3 scripts/run.py policy --json          # 或  python3 scripts/run.py --json policy
# {"ok": true, "mode": "policy", ...}

# 失败
python3 scripts/run.py policy --json --policy 不存在.json
# {"ok": false, "exit": 2, "error": {"kind": "usage", "message": "..."}}
```

规则：

- `--json` 写在子命令**前面或后面都可以**
- stdout **只有一个 JSON**（人读文案走 stderr）
- 退出码语义与非 `--json` 模式**完全一致**
- 未预料的异常 → `kind: "internal"`、`exit: 1`，**完整 traceback 原样打到 stderr**
  （`detail.where` 只给最后一帧的 `文件:行号`，整条栈不进 JSON）

`error.kind` 取值：`internal` / `usage` / `gate` / `call` / `budget` / `interrupt`。
