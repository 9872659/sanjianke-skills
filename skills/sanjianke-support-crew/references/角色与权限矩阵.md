# 角色与权限矩阵

这份文档回答三个问题：**四个角色各自能做什么、不能做什么**；
**权限矩阵为什么要长这样**；**超权限之后升级路径怎么走**。

---

## 一、四个角色的职权边界

### 1）接报

| 项 | 内容 |
|---|---|
| 目标函数 | 用**最快的时间**把工单接住：它是什么类型、多严重、承诺多久回、影响多大 |
| 产出物 | 工单卡：类型 / 等级（P0~P3）/ **承诺时限** / 影响面 / 一句话概述 / 用户诉求 / 待补材料 |
| 权限 | **只有定级权**。不能给任何补偿，也不能替用户下结论 |
| 看得到 | 工单原文（用户提交的原始文字与时间） |
| 看不到 | （它是第一个角色，没有上游） |

**为什么它不能给补偿**：接报是**在信息最少的时候做决定**的阶段。
这个阶段唯一的正确动作是"接住 + 定级"，任何关于钱的判断都应该等
技术判断给出归因之后再说。所以它的提示词里明确写了"不要给补偿、不要给金额"。

**它的产出会被闸门六审两遍**：

1. `sla_minutes` 必须**等于**权限矩阵里「该层级 + 该等级」的分钟数
2. 处置时刻相对工单提交时间的耗时，必须落在那个分钟数之内

### 2）技术判断

| 项 | 内容 |
|---|---|
| 目标函数 | 定位真因并给出**可复现步骤** |
| 产出物 | 判定 + 归因 + 可复现性 + 步骤 + 证据链 + 责任归属 + 排除项 |
| 权限 | **无**。它只能说"是什么问题"，不能说"赔多少" |
| 看得到 | 工单原文 + 工单卡的**类型 / 等级 / 影响面** |
| 看不到 | 接报的自评与整套论述；**任何补偿口径与权限信息** |

**为什么它看不到权限**：如果一个角色既判断责任、又知道"我能批多少"，
它会在定性阶段就悄悄往"能批出来的那个结论"上凑。
把权限信息拿掉，逼它只按技术事实定性。

**归因四分类**（枚举，决定后面的补偿倾向）：

| 归因 | 含义 | 责任 | 补偿倾向 |
|---|---|---|---|
| `product_defect` | 我们自己代码/配置/口径错了，与用户无关 | 我们全责 | 应给补偿，且要复盘防复发 |
| `user_misuse` | 产品行为符合设计与文档，用户用法与文档不符 | 用户侧，但要检查文档 | 通常只做引导；文档没写清才给少量补偿 |
| `environment_issue` | 用户侧网络/浏览器/客户端，或上游第三方临时故障 | 不在双方 | 按商誉酌情，通常给免费重试而非现金 |
| `insufficient_evidence` | 现有信息无法判定归属 | 待定 | 先不做补偿承诺，先取证 |

**`insufficient_evidence` 是刻意的**：没有这一档，模型面对信息不足的工单会被迫
编一个归因出来。有了这一档，"我判不了"是一个**合法且被鼓励**的答案。

### 3）授权（唯一手里有钱的角色）

| 项 | 内容 |
|---|---|
| 目标函数 | 在**权限矩阵之内**决定给什么补偿 |
| 产出物 | 处置方案：是否补偿 / 补偿项（枚举内）/ 金额（点）/ 结论 / 话术 / 升级对象 |
| 权限 | **受权限矩阵硬约束**。超权限必须升级，不许自作主张 |
| 看得到 | 工单原文 + 工单卡 + 技术判定 + **本级权限额度** |
| 看不到 | **别级的额度明细**（只知道自己的额度与升给谁） |

**为什么不让它看别级额度**：知道自己"只能批 50"就够了。
知道"主管能批 300"会诱导它去"帮用户想个办法绕过自己这一关"
（比如拆成两笔、比如写"建议主管批"然后自己先批一部分）。
所以提示词里给的是一张**只含本级**的权限块。

**它的四档结论**（枚举）：

| 结论 | 含义 |
|---|---|
| `当场可批` | 补偿项与金额都在本级权限内，可以现在就执行 |
| `需升级` | 该赔的额度超出本级上限，必须升给上一级 |
| `不予补偿` | 责任不在我方或证据不支持补偿（**必须写理由**） |
| `待补证` | 信息不足以决定，先取证 |

### 4）复盘

| 项 | 内容 |
|---|---|
| 目标函数 | 让同类工单**别再发生** |
| 产出物 | 根因 + 改进项（改文档/改产品/改流程/改口径）+ 同类预警 + 复发指标 |
| 权限 | 无。**不能改这次处置的金额** |
| 看得到 | 工单原文 + 工单卡 + 技术判定 + 处置方案 |
| 看不到 | 各角色的自评与内部打分 |

**为什么它不能改金额**：钱一旦批出去就收不回来了。复盘的价值在于**下一次**，
把它放进"改金额"的位置上，只会让它变成第二个授权角色、多一轮扯皮。

**它有一条特别的检查**：归因是"用户误用"时，也要检查**文档是不是没写清**。
很多"用户误用"其实是文档没写好 —— 那仍然是我们的问题，
只是账记在"改文档"而不是"给补偿"上。

## 二、权限矩阵为什么长这样

### 数字从哪来

默认值是**示例制度**，请按你公司实际情况用 `--policy` 覆盖：

| 层级 | 单张工单可批上限 | 折合 | 定位 |
|---|---|---|---|
| `L1_一线客服` | 5000 点 | ¥50 | 小额、高频、当场结 |
| `L2_二线主管` | 30000 点 | ¥300 | 主管能拍板的日常纠纷 |
| `L3_运营负责人` | 200000 点 | ¥2000 | 涉及批量影响或全额退款 |
| `L4_公司决策` | 不设上限 | —— | 兜底，不再往上升 |

### 三条设计约束

**① 单位统一用「点」。**
平台口径 1 元 = 100 点。补偿金额与 `--budget` 用**同一个单位**，
避免"一个说元、一个说点"的混用事故（1 元被当成 1 点，差 100 倍）。
报告里两者都给（`19800 点 ≈ ¥198`），但**存储与比较只用点**。

**② 补偿项必须枚举。**
自由文本没法做闸门，也说不清"到底给了什么"。八项枚举覆盖了客服场景的
主要处置动作，且每一项都对应一句"它要花多少、谁来执行"：

| 补偿项 | 现金出账 | 什么时候用它 |
|---|---|---|
| `refund_full` | 是 | 完全未交付，且责任在我方 |
| `refund_partial` | 是 | 部分未交付，按比例退 |
| `extend_service` | 否 | 延期能解决问题（会员/订阅/交付周期） |
| `grant_credit` | 否 | 最常用：发可消费的点数余额 |
| `coupon` | 否 | 想让用户**继续下单**时用，比发点更省 |
| `free_retry` | 否 | 任务失败场景的首选：成本可忽略 |
| `manual_repair` | 否 | 只修数据不给钱，成本最低、接受度也高 |
| `apology_only` | 否 | 确认无责，只致歉（**理由必须写清**） |

**枚举之外一律拦**（`unknown_compensation`）。"送个定制玩偶"这种
看似无伤大雅的补偿也会被拦 —— 因为它没有归口部门、没有成本口径、
没有人能执行，批了就是一张空头支票。

**③ 每级必须有升级对象。**
`escalate_to` 是矩阵里**必填**的结构，不是可选的说明文字。
一个层级如果没有上一级可升，越权就无处可去，那张工单会挂死 ——
所以 `load_policy` 会校验它指向的层级存在（或为空串，表示已是最高层）。

## 三、越权之后怎么走

### 拦下来之后必须给的信息

闸门五命中时，本包**要求**处置方案里有 `escalate_to`。没有就再拦一条
（`missing_escalate_to`）。原因很直白：

> 拦下一个越权的决定很容易，但如果只是"拦下"，这张工单就**挂死在原地**了。
> 拦下的同时必须说清"升给谁"，处置流程才继续往前走。

### 升级不是失败

提示词里明确写了这一段：

> 如果按责任该赔的金额**超过你的上限**：不要自己批，也不要拆成两笔绕过去 ——
> 老实设 `requires_escalation=true`、`escalate_to` 写上升给谁、
> `conclusion` 写「需升级」，并把你**建议**的额度写在 `escalate_reason` 里。
> 这是**正确**的做法，不是失败。

**为什么要专门写这句**：模型的默认倾向是"把用户的问题解决掉"。
如果不说清楚"升级也是完成任务"，它就会想办法在自己权限内"做点什么" ——
比如把 19800 点拆成四笔 5000 点。所以提示词要显式堵掉"拆单绕过"这条路，
同时给"老实升级"一个正向的说法。

### 话术在越权时怎么改

越权时**给用户的话术必须写成"已为你申请，需要主管确认"**，
**不许写"已经批了"**。这条写死在提示词里，因为它是客服最容易犯的错：
为了让用户安心，把还没批的事说成已经批了。

### 升级之后

由上一级以新的身份重跑一遍即可：

```bash
python3 scripts/run.py run --file 工单.md --as-role L2_二线主管 --outdir D:/support-l2
```

断点 key 含**层级与实际可批额度**，所以换了层级不会误命中上一级的断点。

## 四、本地算的那份「制度边界」

每次处置，本包都会**独立算一遍**并排在模型建议旁边：

| 项 | 来源 |
|---|---|
| 模型建议额度 | 处置方案里的补偿合计 |
| 本级上限 | 权限矩阵（或 `--grant-cap`） |
| 本地判定 | 比较两者 → `当场可批` / `需升级` |
| 超权限时升给 | 权限矩阵的 `escalate_to` |

**为什么必须本地再算一遍**：权限不能被模型的话术影响。
模型说"建议赔 300"，而本级只能批 50 —— 本地照样判「必须升级」。
模型的措辞再漂亮、理由再充分，都不改变"这笔钱不该由这个角色批"这个事实。

这也是本包与内容类小组最根本的差别：
那些包的闸门审的是**内容**（说得对不对、像不像抄的），
本包的闸门审的是**权限**（这笔钱归不归你批）。
