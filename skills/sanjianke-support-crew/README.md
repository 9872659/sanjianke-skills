# 三剪客 · 客诉处置小组

> L3 产品线 · **第九种形态：处置式（disposition）**
> 版本 1.0.0 · MIT · 只依赖 Python 标准库

一张客诉工单进来，四个角色按流程把它处置完，**一条命令出成品**：

```
接报  →  技术判断  →  授权（受权限矩阵约束）  →  复盘
 │          │              │                      │
 │          │              └─ 超权限 → 升级（exit=3）│
 │          └─ 产品缺陷 / 用户误用 / 环境问题 / 证据不足
 └─ 类型 + P0~P3 + 承诺时限（时限只许来自 policy）
```

---

## 这个包解决什么问题

客诉处置最贵的**不是"话说得不好听"**，是这三件事：

1. **钱批错了** —— 一线为了让用户满意，把超出自己权限的补偿批了出去；
2. **超时了没人管** —— P0 事故压了四个小时，谁都不知道它超了承诺时限；
3. **同一类工单无限来** —— 每次都在救火，没人回答"下次怎么不出现"。

这三件事的共同点是：它们**不是内容质量问题，是流程与权限问题**。
所以本包不评价"这份稿子写得好不好"，它处置"**这张工单该怎么办、谁有权这么办、超了怎么办**"。

## L3 定位：与同族八种形态的分界

L3 的定义是**多角色分工互审、一条命令出成品**。同族已经有八种形态，本包是**第九种**。

| 形态 | 代表包 | 核心机制 |
|---|---|---|
| 流水线式 | `content-team` | 角色顺序接力，打回重写 |
| 对抗评审式 | `review-board` | 立场独立 + 当面对质 + 裁决 |
| 剧组式 | `drama-crew` | 策划 / 编剧 / 分镜 / 出片 |
| 教研式 | `course-crew` | 课程目标 ↔ 考核对齐 |
| 小组式 | `ecom-crew` | 选品 / 文案 / 视觉互否 |
| 跨语言式 | `localize-crew` | 术语统一 + 文化改写 |
| 竞争式 | `bid-crew` | 多方竞争出价 |
| 取证式 | `research-crew` | 逐条求证 + 反驳 |
| **处置式（本包）** | `sanjianke-support-crew` | **权限矩阵 + 时效 + 升级路径** |

### 与 `review-board` 的分界（最容易混的一对，逐项写清）

`review-board` 是八种形态里与本包**最近**的一个：都是"多角色各自独立、最后出一个可执行的结论"。
但两者处理的对象、以及**角色手里有没有权**，完全不是一回事。

| | `sanjianke-review-board`（对抗评审） | **本包（客诉处置）** |
|---|---|---|
| 处理的对象 | 一份**方案 / 稿件** | 一张**客诉工单** |
| 角色的目标函数 | 各自**评价**这份方案行不行 | 各自**推进**一个处置流程 |
| 关键动作 | 对质 → 找真分歧 → 出裁决书 | 定级 → 定性 → 授权 → 复盘 |
| **有没有"花钱"这件事** | **没有**。评价不花钱，说错了顶多意见不合 | **有**。补偿是真要批出去的钱 |
| **谁会拦你** | 立场失效（四席说同样的话） | **越权**（批了超出权限的钱） |
| **有没有时效** | 没有 | **有**。P0/P1 超出承诺时限标红 |
| **有没有升级路径** | 没有。评审没有"上一级" | **有**。超权限必须给 `escalate_to` |
| 产出 | 裁决书 + 条件清单 + 少数派意见 | 处置方案 + 话术 + 复盘 + 升级申请 |
| 终止 | 出裁决（不追求收敛） | 四步走完 |

**一句话分界**：`review-board` 回答"**这事该不该过**"；
本包回答"**这张工单该怎么办、谁有权这么办、超了怎么办**"。

后者的三根支柱 —— **权限矩阵 / 时效 / 升级路径** ——
在前者（以及所有内容类小组）里**结构上不存在**：那些包的角色没有"花钱"这个动作，
所以既不需要额度、也不需要时限、更不需要"升给谁"。这不是"换个输入"，
是**多了一整个约束维度**。

## ⚠️ 边界声明：本包**不接真实支付 / 工单系统**

**这是本包最重要的边界，请先读这一段。**

- 本包**不连**任何支付网关、**不写**任何工单系统的数据库、**不调**任何退款接口。
- 本包唯一的外部调用是 **api.a7w.cn 的大模型端点**（`/api/v1/chat/completions`）与模型清单。
- 它产出的是**处置建议与话术**：补偿项、金额口径、升级对象、给用户的话。
- **真的要退款、要赠额、要延期、要改用户额度，必须由人工在后台执行。**
- 报告里的"19800 点 ≈ ¥198"是**口径**，不是已退款金额，也不是任何形式的支付承诺。

它替代的是**决策与口径**这一段，落地那一段仍然是人。

## 权限矩阵：本包的骨架

单位统一是**点**（平台口径 1 元 = 100 点，与 `--budget` 同一单位 —— 避免元/点混用）。

| 层级 | 单张工单可批上限 | 需上级确认起点 | 超权限升给 |
|---|---|---|---|
| `L1_一线客服` | 5000 点 ≈ ¥50 | 5000 点 | `L2_二线主管` |
| `L2_二线主管` | 30000 点 ≈ ¥300 | 30000 点 | `L3_运营负责人` |
| `L3_运营负责人` | 200000 点 ≈ ¥2000 | 50000 点 | `L4_公司决策` |
| `L4_公司决策` | 不设上限 | —— | —— |

**补偿项枚举**（不许自创补偿）：

| 补偿项 | 名称 | 现金出账 |
|---|---|---|
| `refund_full` | 全额退款 | 是 |
| `refund_partial` | 部分退款 | 是 |
| `extend_service` | 服务延期 | 否 |
| `grant_credit` | 赠额 | 否 |
| `coupon` | 优惠券 | 否 |
| `free_retry` | 免费重试一次 | 否 |
| `manual_repair` | 人工修复数据 | 否 |
| `apology_only` | 仅致歉不改动 | 否 |

**等级 → 承诺时限**（分钟，各层级不同；闸门六的判据**只来自这里**）：

| 层级 | P0 | P1 | P2 | P3 |
|---|---|---|---|---|
| `L1_一线客服` | 15 | 60 | 240 | 1440 |
| `L2_二线主管` | 15 | 30 | 120 | 720 |
| `L3_运营负责人` | 10 | 30 | 120 | 480 |
| `L4_公司决策` | 10 | 30 | 120 | 480 |

### 覆盖权限矩阵

```bash
python3 scripts/run.py policy --policy 我的矩阵.json
```

覆盖文件**只能收窄、不能扩张**：

- `compensation_types` 里出现包里没有的补偿项 → **`exit=2`**
  （能新增就等于把"不许自创补偿"这条闸门关掉了）
- 每个层级必须给全 `P0~P3` 的 `sla_minutes` → 否则时效闸门没有口径可用
- `escalate_to` 必须指向存在的层级或空串 → 升级路径断了，越权就无处可去

## 八道硬闸门

全部在**本地、确定性**判定。命中即 `exit=3`（成本闸门 `exit=5`，包内路径 `exit=2`）。

| # | 闸门 | 判据 | 本包特有？ |
|---|---|---|---|
| 一 | **合规** | 违禁词 + **承诺类话术**（保证解决 / 一定赔偿 / 永久免费…）；「最X」走可枚举上下文豁免 + **句首不豁免** + **SLA 时限口径独立豁免** + **列举序号「第一，」豁免** + **指标口径「100%」豁免**；**产出侧与材料侧口径分开** | 承诺类话术为增补 |
| 二 | 占位符残留 | `{}` / `[待填]` / `XXX` / `TODO`…（空 `{}` 与引用序号 `[1]` 放过，**别误报**） | |
| 三 | 照抄提示词示例 | exact / jaccard ≥ 0.75 / **contain 覆盖度 ≥ 0.60**（带**适用窗口**：目标 ≤ 示例 × 3.0 且示例归一后 ≥ 8 字） | |
| 四 | **锚点到工单原文** | 每条判定/处置必须引用真实句子；编造剔出；未锚定率 > 40% 判定位失败 | |
| 五 | **越权拦截** | 超本级额度 / 补偿项不在枚举 / 越权却没给 `escalate_to` / 层级不在矩阵里 | ✅ **核心** |
| 六 | **时效** | 承诺时限必须等于 policy 口径（自己编的时限被拦）；P0/P1 超出承诺时限**标红** | ✅ |
| 七 | **处置完整性** | 判需补偿却没写补偿项 / 判无需补偿却没写理由 / 结论不在档位 / 话术缺失或超 600 字 | ✅ |
| 八 | 成本上限 + 产出不许进包 | `--budget`（点）；`--outdir` 在包内 → `exit=2` | |

### 闸门五为什么是硬的

内容类小组说错了顶多意见不合；本包说错了是**真的把钱批出去了**。
所以本地**独立算一遍**，而且**不采信模型的措辞**：

```
模型建议额度  vs  本级上限  →  本地判「当场可批 / 必须升级」
```

跑出来是这样（真机实测的对照输出）：

| 项 | 值 |
|---|---|
| 模型建议额度 | 5000 点 ≈ ¥50 |
| 本级上限 | 5000 点 ≈ ¥50 |
| 本地判定 | **当场可批** |
| 超权限时升给 | `L2_二线主管` |

把本级额度临时收到 0 点，**同一份工单、同一个模型输出**立刻变成：

```
闸门五 · 越权拦截（本包核心）
  补偿合计 5000 点 ≈ ¥50 超出「L1_一线客服」的可批额度 0 点 ≈ ¥0 —— **越权**。
  超权限的补偿不许自作主张，必须升给「L2_二线主管」
→ exit=3，authority 维封 0 分
```

**权限不受模型话术影响** —— 这是本包唯一不可替代的机制。

## 四个角色

| 角色 | 目标 | 产出物 | 权限 | 看不到 |
|---|---|---|---|---|
| **接报** | 快速分类定级 | 工单卡（类型/等级/承诺时限/影响面） | 定级 | （第一个角色） |
| **技术判断** | 定位真因 | 判定 + 可复现步骤 + 证据 | **无** | 接报的论述、任何金额与权限口径 |
| **授权** | 决定给什么补偿 | 处置方案（补偿项/金额/口径/话术） | **受权限矩阵约束** | 别级的额度明细 |
| **复盘** | 防复发 | 根因 + 改进项 + 同类预警 | 无 | 各角色的自评 |

**只有「授权」这一席手里有钱** —— 这是本包与所有内容类小组的结构性差别。

### `--grant-cap`：亲手把闸门试出来

```bash
python3 scripts/run.py settle --file 工单.md --card 卡.json --diag 判定.json --grant-cap 0
```

它把**本级实际可批额度**临时改成指定点数（真实场景就是新人额度被临时收紧），
**不绕过**层级判定，只改本级额度。授权角色只要给出任何大于 0 的补偿 → 立刻 `exit=3`。

## 退出码

| 码 | 含义 |
|---|---|
| `0` | 跑完且没有任何硬闸门命中 |
| `2` | 参数/配置错（文件不存在、`--outdir` 在包内、`--policy` 不合法、`--budget` ≤ 0） |
| `3` | **硬闸门命中**（合规 / 占位符 / 照抄 / 锚点 / **越权** / 时效 / 完整性） |
| `4` | 调用失败（网络 / 鉴权 / 点数 / 模型名） |
| `5` | 预算超限，**已就地中止且未发起那次调用** |

## `--json` 契约

给流水线与 agent 消费：

- **成功**：结果对象里多一个 `"ok": true`；顶层是数组时包成 `{"ok": true, "data": [...]}`
- **失败**：stdout 输出 `{"ok": false, "exit": <码>, "error": {"kind": ..., "message": ...}}`
- 只在**本次还没吐过任何 JSON 结果**时才补信封（守住"stdout 只有一个 JSON"）
- **`--json` 写在子命令前面或后面都可以**
- 人读文案照旧走 stderr；**退出码语义一个都不变**
- 未预料的异常 → `kind: "internal"` + **完整 traceback 到 stderr**（报 bug，不藏 bug）

`error.kind` 取值：`internal` / `usage` / `gate` / `call` / `budget` / `interrupt`。

## 实测数据

真机实测（`deepseek-chat`，626 字工单，一张"批量出片 12 条只成功 3 条"的客诉）：

| 阶段 | prompt | completion | finish_reason |
|---|---|---|---|
| 接报 | 1463 | 605 | `stop` |
| 技术判断 | 1287 | 1089 | `stop` |
| 授权 | 1790 | 987 | `stop` |
| 复盘 | 1099 | 1219 | `stop` |
| **合计** | **5639** | **3900** | **9539 token / 4 次调用 / 约 22 秒** |

同一张工单跑三次（`deepseek-chat`）：**9119 / 9365 / 9539 token**。
三次里两次四步全过、一次**授权角色真的越权了** ——
它给出 `refund_partial 14850 点`（12 条里 9 条未交付按比例退），
超出 L1 的 5000 点上限，**本地闸门 exit=3 拦下**，`authority` 维封 0 分，
报告结论直接写「**越权，本单处置不成立**」。
那次它自己其实也标了 `requires_escalation=true` —— 但**字段里那笔钱仍然是超权限的**，
所以照样拦：本地判的是**执行项**，不是模型的自我评价。

断点续跑：同一 `--outdir` 再跑一遍 → **4 步全部断点命中，0 次调用、0 token**。

> `finish_reason` 记进台账是有用的：**只有 `length` 才表示被 `max_tokens` 截断**
> （那就加大 `--max-tokens`）；其它值（`stop` / `None`）说明是模型自己写错了或响应
> 在路上断了，**加大 max-tokens 没用**。**不要用 content 长度判断**。

## 工单怎么写

`键：值` 一行一条，加自由正文。**最重要的是 `提交时间`（时效闸门的 T0）与 `实付金额`**：

```text
工单号：SJK-20260214-0731
提交时间：2026-02-14 09:12
渠道：微信客服
客户：阿灿（短视频矩阵号）
订单：2026-02-13 21:40 下单批量出片 12 条，实付 198 元（19800 点）

（下面是用户原话，逐句保留 —— 锚点闸门要用它校引文）
昨天晚上 9 点 40 …… 12 条里只有 3 条出来了，剩下 9 条全显示「任务失败：上游服务异常」。
我点重试，重试了三次，每次都是同一个错。……
```

时间解析不出来时**不猜** —— 标 `timing_checked=false` 并说明未做超时判定，
而不是默认"没超时"。
