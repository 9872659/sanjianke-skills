# 定位与等待的稳定性写法

> 这份资料只干一件事：让同一个脚本在下个月、在别人的机器上、在页面小改之后，还能跑通。
> 前面讲「怎么写对」，后面讲「等多久、重试几次、失败了怎么办」。

---

## 一、定位器优先级梯度

原则一句话：**优先选「和用户认知一致」或「和数据来源一致」的属性，最次才用「和实现细节绑定」的属性。**

| 档位 | 定位方式 | 为什么稳 | 什么时候用 |
|---|---|---|---|
| 1 | 角色 + 可访问名（`role=button, name=提交`） | 与服务对象一致；改样式、改结构、换组件库都不影响 | 按钮、链接、输入框、标题、列表项等一切有语义的元素 |
| 2 | 标签 / 占位符 / 图注（label、placeholder、alt、title） | 表单的对外契约，改版通常不动 | 表单字段、图标按钮（用 title/alt）、图片 |
| 3 | 显式测试契约（`data-testid` 一类专用于自动化的属性） | 专门为自动化保留，改动需开发者主动破坏 | 语义不明或文案会变的元素；**这是最稳的，但不面向用户** |
| 4 | 稳定业务属性锚点（`data-form="order"`、`name="orderNo"`、`aria-*`、业务 ID） | 有业务含义，不会随样式重构消失 | 角色重复、语义缺失时的兜底 |
| 5 | 元素文案（`text=提交`、正则匹配） | 用户可见，改文案才会坏 | 非交互文本节点；交互元素谨慎使用，文案含 `(2)` 这类动态后缀时要用正则 |
| 6 | 结构路径（`form > div:nth-child(2) > button`） | —— 基本不稳 | **尽量不要用**。只在别无选择时作为最后一档，并接受它随时会坏 |

### 六个反模式，看到一个改一个

| 反模式 | 为什么坏 | 替代写法 |
|---|---|---|
| `.css-1x2y3z`、`.scss-abc123` 这类自动生成的类名 | 构建工具每次发版都会重新哈希，必然失效 | 换角色/文案/测试契约 |
| 纯数字 id（`#\31 23`） | 服务端渲染的序号会变 | 换语义定位 |
| 绝对 XPath（`/html/body/div[3]/div[2]/button`） | 任何一层加个 `<div>` 就废 | 用 `//button[normalize-space()="提交"]` 或直接换角色定位 |
| `nth-child` / 第 2 个按钮 | 列表顺序会变、促销元素会插进来 | 用「名称包含订单号的按钮」这类内容条件 |
| 只按文案匹配、不带上下文 | 页面有好几个「提交」，命中多个 | 先收窄作用域，或加区分性名称 |
| 用索引指向列表项（`.item >> nth=3`） | 分页/排序/新增一行就错位 | 用行内的稳定标识（订单号、ID 属性）组合定位 |

### 唯一命中是硬要求

定位器返回 0 个（还没渲染）或 2 个以上（太宽），都**不可以**直接执行动作。前者会超时，后者会点错——而且点错往往是静默的，直到最后数据对不上你才发现。

```javascript
async function actionSafe(loc, fn) {
  await loc.waitFor({ state: 'visible', timeout: 8000 });
  const n = await loc.count();
  if (n !== 1) throw new Error(`定位不唯一：命中 ${n} 个，必须收窄`);
  await fn(loc);
}
```

**例外**：批量取值时你就是要命中多个（表格行、列表项），这时用 `all()` / `evaluateAll()`，但仍要校验数量是否符合预期（`count() > 0`，或等于某个已知值）。

### 作用域收窄：把「唯一」做出来

页面里有 5 个「编辑」按钮，靠命名不可能区分开。做法是**向上找锚点，向下定位目标**：

```javascript
// 目标：订单号 A-1024 那一行的「编辑」按钮
const row = page.getByRole('row').filter({ hasText: 'A-1024' });
await row.getByRole('button', { name: '编辑' }).click();
```

链条式定位比一次性长选择器更稳，因为每一段都表达了一个业务事实：「这一行是 A-1024 的」「这一行里的编辑按钮」。页面加列、改布局都不会打断它。

## 二、iframe 与 Shadow DOM：找不到元素的第一嫌疑人

### iframe

元素在 iframe 里时，主文档的定位器**完全看不到它**。症状是「明明截图里有这个按钮，定位就是超时」。

```javascript
// 按 iframe 自身的可识别特征进入
const frameLocator = page.frameLocator('iframe[title="支付表单"]');
await frameLocator.getByRole('button', { name: '确认支付' }).click();
```

排查顺序：

1. 先确认它真的是 iframe：在主文档里搜 `iframe`，看有几个、各自 `src` / `title`。
2. 判断跨域：`src` 的域和主页面不同 → 同源策略限制，**能力会下降**（尤其是读取内部 DOM 和注入脚本）。这时优先找站点是否提供了官方接口或弹窗外的等价位。
3. 嵌套 iframe 要逐层进入，不要试图用一条选择器穿透。
4. **iframe 会重新加载**：父页面刷新或 iframe 自己导航后，之前拿到的框架引用可能已作废，重新获取。

### Shadow DOM

Web Components 的内容在 Shadow 根里，普通 CSS 选择器进不去。多数现代库支持穿透组合符（`>>>` / `>>>>` 一类）或提供专门的穿透查询。

```javascript
// 穿透到自定义元素内部的按钮
await page.locator('order-panel >>> button.submit').click();
// 或链式：先拿到宿主，再进入其影子根
await page.locator('order-panel').locator('button.submit').click();
```

排查提示：在浏览器开发者工具里，Shadow 根默认是折叠的，需要显式开启显示——很多人「截图里看不到元素」，其实是没展开影子根。

## 三、候选档位 + 降级链（核心模板）

不要把稳定性寄托在「选一个最好的定位器」上，而是**准备一条有序的候选链**：主档失效时自动降级，全部失效才报错，并且**上报命中的是哪一档**——档位漂移就是页面改版的早期信号。

```javascript
/**
 * 每个候选返回一个定位器；按稳定性从高到低排列。
 * 约定：build(page) -> Locator
 */
const CANDIDATES = [
  { tier: 1, tag: 'role',    build: p => p.getByRole('button', { name: /^提交$/ }) },
  { tier: 2, tag: 'testid',  build: p => p.getByTestId('order-submit') },
  { tier: 3, tag: 'attr',    build: p => p.locator('form[data-form="order"] button[type="submit"]') },
  { tier: 4, tag: 'text',    build: p => p.getByText('提交', { exact: true }) },
];

async function resolve(page, candidates, { totalTimeout = 10000 } = {}) {
  const perTry = Math.max(1500, Math.floor(totalTimeout / candidates.length));
  const tried = [];

  for (const c of candidates) {
    const loc = c.build(page);
    try {
      await loc.first().waitFor({ state: 'visible', timeout: perTry });
      const n = await loc.count();
      if (n === 1) return { loc, tier: c.tier, tag: c.tag, tried };
      tried.push(`${c.tag}:命中${n}个`);
    } catch (e) {
      tried.push(`${c.tag}:${e.name === 'TimeoutError' ? '超时' : '异常'}`);
    }
  }
  throw new Error(`定位降级链全部失败，已尝试 [${tried.join(' | ')}]`);
}
```

### 设计要点

- **每档独立超时**：总预算 ÷ 档数，且给一个下限（否则最后一档只剩几十毫秒，等于没试）。
- **唯一命中才返回**：`count() === 1`。多命中视为该档失败，继续降级（也可以选择「多命中就按最近的上下文收窄再试」，但那已经是重新设计定位了）。
- **不要静默降级**：命中低档位要打日志 / 记指标。今天靠文案兜住，明天文案一改就全线崩，你需要在它崩之前知道。
- **档位不要超过 4 档**：候选太多意味着你没搞清楚页面结构，而且总超时会被稀释。四档以内通常够。
- **档位顺序反映稳定性**，不是反映「哪个最容易命中」。容易命中但不稳定的（比如第几个按钮）不该进候选链。

### 命中率指标：把稳定性变成数字

一个可维护的自动化任务应该能回答「上周哪些定位在漂」。最小可用的埋点：

| 指标 | 采集方式 | 报警阈值（经验值） |
|---|---|---|
| 主档命中率 | 命中 tier 1 的次数 / 总次数 | < 95% 就该看看页面是不是改了 |
| 降级发生率 | 命中 tier ≥ 3 的次数 / 总次数 | > 5% 时，把该元素的主档重写 |
| 全链失败率 | 抛错次数 / 总次数 | > 1% 必须人工介入 |
| 单步耗时 P95 | 每步开始到校验通过的耗时 | 突然翻倍 = 页面变慢或有额外等待 |
| 重试率 | 重试次数 / 总步数 | > 10% 说明等待策略没对齐 |

这些指标不需要复杂基建，把每步的结构化日志按天聚合就够了。**没有指标的自动化，只能靠「今天跑通了吗」来判断健康度，那太晚了。**

## 四、等待策略：把「睡三秒」换成「等一个信号」

### 决策流程

```
需要等 → 问：我在等什么变化？
├── 元素出现 / 可见 / 消失 / 可点击  → 显式状态等待（元素级）
├── 页面跳到新地址                  → 等 URL（导航级）
├── 页面没变但数据刷新了            → 等那个具体接口的响应（网络级）
├── 出现成功/失败提示               → 断言等待（文案/状态）
└── 以上都不是，只能靠时间          → 说明你还没找到真实信号：去找它
```

最后一条是重点：**出现「只能靠时间」的情况，通常意味着你对这个页面的完成条件理解还不够**。多观察几次网络面板和 DOM 变化，信号几乎总是存在的。

### 五类等待的写法与边界

```javascript
// 1) 元素级：等它出现、可见、稳定
await page.getByRole('dialog').waitFor({ state: 'visible', timeout: 10000 });
await page.getByText('正在加载').waitFor({ state: 'hidden', timeout: 15000 }); // 等 loading 消失

// 2) 导航级：URL 是业务成功的强信号
await Promise.all([
  page.waitForURL(/\/orders\/\d+$/, { timeout: 20000 }),
  page.getByRole('button', { name: '提交订单' }).click(),
]);

// 3) 网络级：等那个接口，别等「全网安静」
await Promise.all([
  page.waitForResponse(r => r.url().includes('/api/order/create') && r.status() === 200,
                       { timeout: 20000 }),
  page.getByRole('button', { name: '提交订单' }).click(),
]);

// 4) 断言级：会重试到超时，适合校验
await expect(page.getByRole('status')).toHaveText(/提交成功/, { timeout: 15000 });

// 5) 导航完成条件：明确你等的是哪一档
await page.goto(url, { waitUntil: 'domcontentloaded', timeout: 30000 });
// domcontentloaded 快、但 DOM 可能还没渲染完 JS 内容
// load 等资源加载完，慢
// networkidle 只在请求会停的页面上可靠

// 6) 硬睡：只在调试期
// await page.waitForTimeout(3000);   ← 正式代码里不该出现
```

### 超时预算怎么定

超时值不该拍脑袋，按「这一步正常情况下要多久」的 3~5 倍给，再乘以重试次数，得到这一步的最坏耗时；所有步骤加起来不能超过任务的总预算。

| 步骤类型 | 建议单次超时 | 建议重试 | 说明 |
|---|---|---|---|
| 打开页面 | 30s | 1 次 | 慢站/内网站点可到 60s |
| 等待首屏关键元素 | 15s | 1 次 | 有骨架屏的站点按骨架屏消失算 |
| 单次点击 / 填表 | 8~10s | 2 次 | 自动等待已含内部轮询，别把超时设太短 |
| 等业务结果（提交后） | 20~30s | 1 次 | 后端处理慢的流程要放宽 |
| 下载完成 | 60s | 1 次 | 大文件按体积再加 |
| 素材/整页截图 | 10s | 0 次 | 截图失败通常重试也没用 |

**总预算上限**必须显式设置（比如一个任务 10 分钟）。没有总预算的任务，卡住时会一直占着浏览器进程和你的注意力。

### 何时可以硬睡（很少）

只有这几种情况可接受，且必须写注释说明原因：

1. 页面用 `setTimeout` 做延迟渲染，而没有任何可观测信号（比如某些老后台的 `setTimeout(render, 800)`）。
2. 动画时长固定且必须等它结束才能截图。
3. 节流：两次操作之间必须留最小间隔以满足站点频率要求（**这是合规等待，不是时序等待**，见安全那份）。

即使如此，也要写成「等待 + 条件校验」的组合，而不是「睡完就当成功」。

## 五、重试：分两层，别混在一起

重试不是「再跑一遍整个脚本」。分两层之后，成功率会有质的变化。

### 第一层：动作级重试（治瞬时抖动）

适用于：网络瞬断、元素被短暂遮挡、点击落空、loading 闪过导致的时序错位。

```javascript
async function withRetry(fn, {
  attempts = 3,
  baseDelay = 500,      // 起始退避
  factor = 2,           // 指数因子
  jitter = 0.3,         // 抖动比例，防雪崩
  retryOn = (e) => /Timeout|detached|intercept|Target closed/i.test(String(e.message)),
} = {}) {
  let lastErr;
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn(i);
    } catch (e) {
      lastErr = e;
      if (!retryOn(e) || i === attempts - 1) throw e;
      const wait = baseDelay * factor ** i * (1 + Math.random() * jitter);
      await new Promise(r => setTimeout(r, wait));
    }
  }
  throw lastErr;
}
```

参数建议：`attempts = 3`（1 次原始 + 2 次重试），退避 `500ms → 1s → 2s`，加 30% 抖动。**不要对失败原因不加区分地重试**：

| 该重试 | 不该重试 |
|---|---|
| 超时、元素被遮挡后消失、连接重置 | 401/403（未授权、被拒）、404 不存在 |
| 5xx、网关错误 | 表单校验失败、业务规则拒绝（「库存不足」） |
| 元素 `detached`（重渲染） | 验证码出现、登录墙出现 |
| 目标页面暂时不可用 | 参数错误（重试一万次还是错） |

对不该重试的错误，唯一正确的动作是**停下来并报告**，把上下文（截图 + 快照 + URL + 错误原文）交出去。

### 第二层：步骤级重规划（治状态漂移）

动作级重试解决不了「页面上多了一个公告弹窗」「本次登录后进入的是新版界面」。这类问题需要**重新观察再决策**：

```
步骤失败
├── 重试 N 次仍失败
├── 重新取快照（页面可能已经变了）
├── 判断是否出现可处理的旁路：
│   ├── 弹窗/公告遮罩    → 关掉它，重试该步骤
│   ├── 登录态失效       → 抛「需要重新授权」，不要在这里重登
│   ├── 出现了未预期的中间页 → 记录并考虑把它加入流程
│   └── 页面结构与预期不符 → 降级链已用尽，人工介入
└── 仍失败 → 带三件套上报，终止该任务（不要继续往下点）
```

**关键纪律：失败后不要继续执行后续步骤。** 在错误的页面状态下继续点，造成的副作用（重复提交、误删、错误下单）比直接失败严重得多。宁可停在半路，也不要带着错误状态往下走。

### 幂等与断点续跑

批量任务必须能安全重跑。三条做法：

1. **每步有唯一标记**（订单号、任务 ID），已完成的记录到本地清单，重跑时跳过。
2. **提交类动作先查后做**：先确认「这一条是不是已经存在」，再决定要不要提交——这比依赖自动化的重试更重要。
3. **失败项与成功项分开记录**，支持只重跑失败项，而不是整批重来。

## 六、定位契约的回归自测

页面改版是持续发生的，你的定位链需要一套低成本的体检机制。

| 检查 | 做法 | 频率 |
|---|---|---|
| 冒烟 | 用最小流程（打开 → 定位一个关键元素 → 取值）跑一遍 | 每次部署前 |
| 定位体检 | 只做「解析每个关键定位器并检查唯一命中」，不执行真实动作 | 每天一次 |
| 视觉基线 | 关键页面截图存档，与上次做像素或结构对比 | 页面感觉变了就跑 |
| 结构快照 | 存下关键页面的 ARIA 快照，看角色/名称是否变了 | 每周一次 |

「定位体检」是性价比最高的一项：它不产生任何业务副作用（不提交、不修改），却能提前告诉你哪些定位器已经开始退化。发现某个定位器从「唯一命中 1 个」变成「命中 3 个」，你就知道该改主档了——而不是等到某天任务在半夜静默失败。

### 体检脚本骨架

```javascript
const CONTRACTS = [
  { name: '登录-用户名', url: '/login', make: p => p.getByLabel('用户名') },
  { name: '登录-提交',   url: '/login', make: p => p.getByRole('button', { name: '登录' }) },
  { name: '订单-导出',   url: '/orders', make: p => p.getByRole('button', { name: '导出' }) },
];

const report = [];
for (const c of CONTRACTS) {
  await page.goto(base + c.url, { waitUntil: 'domcontentloaded' });
  const loc = c.make(page);
  try {
    await loc.first().waitFor({ state: 'visible', timeout: 5000 });
    const n = await loc.count();
    report.push({ name: c.name, hits: n, ok: n === 1 });
  } catch {
    report.push({ name: c.name, hits: 0, ok: false });
  }
}
console.table(report);
```

把 `ok: false` 或 `hits > 1` 的行当作待修项，定期清零。

## 七、速查表

| 症状 | 大概率原因 | 先做什么 |
|---|---|---|
| 定位超时，但截图里有这个元素 | 在 iframe 或 Shadow DOM 里 | 确认层级；用框架定位器 / 穿透选择器 |
| 命中 2 个以上元素 | 定位器太宽 | 先收窄作用域（行/表单/区域），再加内容条件 |
| 第一次点成功，第二次报元素已销毁 | 用了元素句柄 | 换成定位器，每次动作重新解析 |
| 点击没报错但页面没变 | 被遮挡（点了遮罩）/ 按钮禁用 / 业务拒绝 | 查遮挡元素；查 `disabled`；查接口返回 |
| 偶尔成功偶尔超时 | 时序不稳（懒加载、动画、接口慢） | 找出真实信号，改用语义等待；加动作级重试 |
| 批量任务越跑越慢 | 页面没关、监听没摘、内存泄漏 | 每步检查页面与监听数量；定期重启上下文 |
