# 安全边界与排错

> 前半部分是这个 Skill 的底线：什么能做、什么不做、做了要承担什么。
> 后半部分是排错：从「超时」这一个症状出发，把它拆成可以逐个排除的原因。

---

## 一、开工前的授权确认清单

浏览器自动化会以你的名义、用你的账号、在你的网络出口上访问目标站点。**动手前先回答这六个问题**，任何一个答不上来，先别写代码。

| # | 问题 | 不合格的表现 |
|---|---|---|
| 1 | 这个站点/系统是谁的？你凭什么访问？ | 「网上搜到的」「公开的应该都能抓」 |
| 2 | 站点条款 / 用户协议是否允许这类自动化访问？ | 从没看过条款；条款明写禁止自动化 |
| 3 | `robots.txt` 与接口文档怎么说的？ | 明知 Disallow 还照抓；有官方 API 却硬爬页面 |
| 4 | 你操作的账号是自有/被授权的吗？ | 借用他人账号；用测试号做生产写操作 |
| 5 | 会不会产生不可逆副作用？ | 批量下单、批量发送、批量删除，却没有二次确认与数量上限 |
| 6 | 抓到的数据里有个人信息/敏感字段吗？ | 全量落盘、明文保存、无脱敏、无删除计划 |

三条实操建议：

- **把结论写下来**（一页纸：站点、授权来源、允许做什么、频率上限、数据保留期）。写不出来的授权，等于没有授权。
- **有官方 API 就用官方 API**。页面结构会变、风控会拦、接口有契约；只有在没有 API 或 API 不具备所需能力时，才用浏览器自动化去补，且优先补成「浏览器操作 + 官方接口取值」的混合模式。
- **写操作要有闸门**：批量任务先跑 dry-run（只走到提交前一步，把要提交的内容打出来），确认清单无误后再放行真实提交。

## 二、我们不做这些（明确的红线）

下面每一行都是**不做**，没有配置项、没有开关、没有「仅在授权情况下可用」的例外。遇到这些情况，正确动作是停下并交回给人。

| 不做的行为 | 为什么 |
|---|---|
| **识别/绕过图形验证码、滑块、点选验证** | 这是站点的准入控制机制。绕过它等于绕过对方的授权判断，且直接违反绝大多数站点条款 |
| **自动接收/转发短信验证码、破解二次验证** | 同上，且涉及通信与身份认证的合规问题 |
| **撞库、口令爆破、遍历他人账号** | 未授权访问计算机信息系统，法律风险明确 |
| **指纹伪装（改 Canvas/WebGL/字体/时区特征）、浏览器特征篡改** | 目的是让站点无法识别自动化行为，本质是规避风控 |
| **代理池 / IP 轮换来绕开限流或封禁** | 规避站点的频控决策 |
| **通过切换账号 / UA 来绕过频控** | 同上 |
| **伪造人类行为轨迹（随机鼠标轨迹、随机打字节奏）以规避检测** | 对抗风控，不是提升可用性 |
| **抓取站点明确声明禁止抓取的数据（付费墙内、隐私数据）** | 越权 + 侵权风险 |
| **对生产系统做未限速的高并发压测式操作** | 影响对方服务可用性 |

### 被拦住了怎么办：三条合规出路

1. **改用官方接口**：申请 API Key、开通开发者权限、走数据合作渠道。这是唯一稳定且体面的路。
2. **人工介入**：把需要人机校验的那一步交回给人（弹出提示、暂停并等待人工完成），脚本负责前后流程。这是最常见的工程解法。
3. **降低频率 / 缩小范围**：如果只是被限流而没有封禁，降速、错峰、减小批量通常能恢复。**降速是合规动作，绕开限流不是。**

站点返回的这些信号，应当被当作**终止条件**而不是**重试理由**：

| 响应 | 含义 | 动作 |
|---|---|---|
| 429 / Retry-After | 频率超限 | 按 `Retry-After` 退避；持续出现就降低整体速率或改期 |
| 403 / 451 | 被拒 / 因法律原因不可访问 | 立即停止该目标，记录并上报 |
| 出现验证码页面 | 触发了人机校验 | 停止自动化，转人工或改官方接口 |
| 跳转到登录页 | 登录态失效或未授权 | 停止，提示重新授权；不要在这里自动重登 |
| 页面内容变成「访问过于频繁」 | 软封 | 停止该目标至少数小时，评估是否合规 |
| 返回空数据但状态 200 | 可能被静默降级 | 校验业务标记，不要当成「真的没有数据」 |

## 三、频率与并发纪律

自动化最容易被投诉的不是「抓了数据」，而是「把站点搞慢了」。给自己定硬上限：

| 维度 | 建议上限 | 说明 |
|---|---|---|
| 单账号并发 | 1~2 | 同一账号并发会互相踢下线、共享状态污染；多数后台不支持并发 |
| 单站点总并发 | 2~4 | 先按最小可行数跑，观察响应时间再决定是否加 |
| 请求间隔 | 1~3 秒 | 列表翻页、连续点击之间留间隔；有明确限速文档就按文档 |
| 单个任务总时长 | 设上限并强制中断 | 卡住的任务会占资源，也容易触发风控 |
| 单日操作总量 | 按业务必要性定 | 「能跑多少」不等于「该跑多少」 |
| 夜间时段 | 尽量避开 | 对方运维值班薄弱的时段出问题影响最大 |

实现上，最省事也最有效的做法是**给上下文加统一的节流器**：所有「导航 + 点击」都经过同一个队列，队列里保证最小间隔。不要指望在每个调用点手动睡一下——那样一定会漏。

```javascript
function throttle(minGapMs = 1200) {
  let last = 0;
  return async () => {
    const wait = Math.max(0, last + minGapMs - Date.now());
    if (wait) await new Promise(r => setTimeout(r, wait));
    last = Date.now();
  };
}
const gate = throttle(1500);
// 每次导航/点击前：await gate();
```

## 四、登录态：当凭证管理，不当缓存文件

登录态存档里装着 Cookie 与本地存储数据，**它的效力通常等同于账号本身**：拿到这个文件的人可以以你的身份访问站点。所以它必须按凭证管理。

### 存储纪律

| 要求 | 做法 |
|---|---|
| 不进版本库 | 存档目录加入忽略规则（如 `.auth/`），提交前扫一遍 |
| 最小权限 | 文件权限设为仅当前用户可读写（Unix 600 一类） |
| 有明确路径 | 固定放在工作目录下的一个子目录，不要散落在临时目录 |
| 有生命周期 | 记录生成时间；超过有效期或任务结束即删除 |
| 不随产物外发 | 打包日志、截图、产物目录时排除存档目录 |
| 不打印内容 | 日志里永远不打 Cookie 原文，要打就打数量和域名的摘要 |

### 复用的正确姿势

```bash
# 1) 一次性准备：人工完成登录那一步
mkdir -p .auth && printf '\n.auth/\n' >> .gitignore
chmod 700 .auth
```

```javascript
// 2) 任务里复用；每次都先验有效性
const context = await browser.newContext({
  storageState: '.auth/user.json',
  viewport: { width: 1440, height: 900 },
  locale: 'zh-CN',
});

await page.goto(base + '/dashboard', { waitUntil: 'domcontentloaded' });
if (/\/login|\/signin/.test(page.url())) {
  throw new Error('登录态已失效：需重新授权，脚本到此停止');
}
```

### 三条关键判断

**判断 1：失效是正常事件，不是 bug。** Cookie 有有效期、Token 会轮换、会话可能被异地登录顶掉。把它当作会过期的缓存：探测失效 → 停止 → 报告「需要重新授权」，**不要尝试在脚本里自动重登**。自动重登会让流程绕过人工确认，也让失败原因变得模糊。

**判断 2：需要人工验证的登录流程，不该被自动化封装。** 短信验证码、扫码、人机校验，都属于「必须有人在场」的环节。正确的设计是：脚本暂停，提示人工完成登录并保存存档，脚本继续下一段。

**判断 3：多账号用多上下文隔离，不要在同一上下文里换账号。** 隔离是免费的，而「清干净」很难——漏掉一个 IndexedDB 或 Service Worker 就可能串号，串号产生的错误数据比任务失败更难发现。

> 补充：也可以使用持久化的用户数据目录（浏览器 profile 目录）来保留登录态，代价是它带有这个浏览器的一切状态，隔离性与可移植性都不如独立的存档文件。**优先用存档文件；只有在站点把大量状态放在存档文件覆盖不到的地方（比如某些设备指纹绑定的场景）才考虑持久化目录。**

## 五、数据、日志与脱敏

| 对象 | 纪律 |
|---|---|
| 截图 | 可能包含手机号、金额、姓名；批量截图前先想清楚落盘位置与保留期 |
| 页面快照 / HTML | 同上；不要把含个人信息的整页 HTML 长期留存 |
| 登录态文件 | 按凭证对待（见上一节） |
| 日志 | 不打 Cookie/Token/密码；账号只打脱敏后的标识（如 `u***@example.com`） |
| 下载的原始文件 | 用完即清理；不要把「中间产物」永久堆在共享目录 |
| 上报给模型的内容 | 只传必要的字段；整页 HTML 交给外部模型前先做字段裁剪与脱敏 |

脱敏的最小实现：取出需要的字段后，对手机号/身份证/邮箱/银行卡做部分掩码；日志里只留掩码后的值。**不要为了「方便排查」而把原文留在日志里**——排查结束后那些日志还在。

保留期建议：调试产物（截图、trace）7 天；业务产物按业务要求；登录态至多到下次任务。写进运行说明里，别只放在脑子里。

## 六、排错总纲：把「超时」拆开

所有浏览器自动化的报错，最终都会收敛成两类：**等不到（Timeout）** 和 **做不成（Action failed）**。第一件事永远是问：**谁在等谁，等的是什么？**

```
报错
├── 超时（Timeout）
│   ├── 定位超时：元素一直没出现
│   │   ├── 元素真的不在页面里 → 层级问题（iframe / Shadow DOM）
│   │   ├── 元素存在但不可见 → 折叠面板 / 懒加载 / CSS 隐藏
│   │   ├── 元素看起来在，实际在另一个同名元素上 → 定位器太宽，命中多个
│   │   └── 页面根本没加载成功 → 网络、代理、证书、被拦
│   ├── 导航超时：waitUntil 条件不满足
│   │   ├── networkidle 遇到长轮询/心跳 → 改等具体接口或 domcontentloaded
│   │   └── 页面确实很慢 → 拉长超时并确认对方站点是否正常
│   └── 动作超时：元素不可交互
│       ├── 被遮挡（弹层/遮罩/吸顶栏）→ 先关掉遮挡物
│       ├── 禁用状态 → 等它启用，或说明前置条件没满足
│       └── 一直在动画 → 等稳定，找动画结束信号
└── 做不成（Action failed / 无异常但无效果）
    ├── 点了没反应 → 业务拒绝 / 被遮挡 / 前端没绑定事件
    ├── 页面跳转到了意外的地方 → 校验 URL，可能是权限或流程变了
    ├── 提交后数据不对 → 取值时机太早 / 字段映射错位
    └── 浏览器崩溃 / 连接断开 → 资源耗尽、内核不匹配、被系统杀掉
```

### 通用取证动作（任何失败都先做这三件）

```javascript
async function dumpFailure(page, tag) {
  const ts = new Date().toISOString().replace(/[:.]/g, '-');
  const dir = `out/fail/${tag}-${ts}`;
  await fs.promises.mkdir(dir, { recursive: true });
  await page?.screenshot({ path: `${dir}/page.png`, fullPage: true }).catch(() => {});
  await fs.promises.writeFile(`${dir}/snapshot.yml`,
    await page.ariaSnapshot().catch(() => '(snapshot failed)'));
  await fs.promises.writeFile(`${dir}/meta.json`, JSON.stringify({
    url: page?.url(), title: await page?.title().catch(() => ''),
    viewport: page?.viewportSize(),
  }, null, 2));
  return dir;
}
```

**结构快照比截图更能定位问题**：截图告诉你「看起来有按钮」，快照告诉你「按钮的可访问名变了」——后者直接指向定位器该怎么改。

## 七、逐条排查表

### 7.1 定位超时：元素找不到

| 检查 | 怎么做 | 结论 |
|---|---|---|
| 它在不在 iframe 里？ | 主文档搜 `iframe`，看 `src` / `title`；用框架定位器进入 | 在 → 用框架定位器；跨域 → 能力受限，找等价位 |
| 它在不在 Shadow DOM 里？ | 开发者工具打开「显示影子根」；用穿透组合符 | 在 → 用穿透写法 |
| 是不是懒加载？ | 滚动到底再看快照；观察触发懒加载的容器 | 是 → 先滚到可见，再等待 |
| 是不是被条件渲染隐藏？ | 展开快照看有没有该节点；比对 `display` / `hidden` | 隐藏 → 先触发显示条件（点标签、展开分组） |
| 定位器是不是太严？ | 用 `count()` 看命中数，把名称换成部分匹配/正则 | 命中 0 → 放宽或换档位；命中 >1 → 收窄 |
| 页面真的加载了吗？ | 看 `page.url()`、标题、截图是否为空白/错误页 | 没加载 → 见 7.5 |
| 是不是文案变了？ | 对比上次的结构快照 | 变了 → 改主档，并检查是否还有其他定位依赖同一文案 |

### 7.2 点击了但什么都没发生

按这个顺序查，八成在第一步就找到原因：

1. **当时页面上有没有遮挡？** 截图 + 快照找弹层、公告、遮罩。有序的关掉它再点。
2. **按钮是不是禁用状态？** 看 `disabled` / `aria-disabled`；被禁用通常意味着前置条件未满足（没选商品、没同意条款、必填未填）。
3. **是不是点到了同名元素？** `count()` 大于 1 就是这个问题，先收窄作用域。
4. **前端事件绑定了吗？** 有些元素需要真实的鼠标事件序列；试试先悬停再点击，或用键盘操作（聚焦后回车）。
5. **是不是业务拒绝了？** 打开网络面板看提交接口的响应体——「点击成功」和「业务成功」是两件事。
6. **是不是 `force` 掩盖了问题？** 如果代码里用了 `force`，先摘掉，让真实的报错浮出来。

### 7.3 有头能跑，无头不能

| 原因 | 处理 |
|---|---|
| 站点对无头环境有额外校验 | 这属于对方的风控策略。**不要用改特征的方式硬绕**；评估是否可改为有头运行（需桌面环境），或改走官方接口 |
| 视口/窗口尺寸不同导致布局不同 | 显式设视口（如 1440×900），别依赖默认值 |
| 字体缺失导致渲染与定位差异 | 容器里补字体；不要依赖文本像素位置 |
| 缺少系统库导致截图/视频失败 | 按运行环境补依赖 |

### 7.4 弹窗、对话框、新窗口

| 类型 | 处理 |
|---|---|
| 浏览器原生对话框（alert / confirm / prompt） | 必须注册对话框处理（接受或关闭），否则它会阻塞页面；注意**注册时机要在触发之前** |
| 新标签页 / 新窗口 | 先等 `page` 事件并用 `Promise.all` 包住点击 |
| 页面内自定义弹层 | 当成普通元素处理：等它可见、关掉它、再继续 |
| 文件选择框 | 不要试图点击它；用「设置 input 文件」的 API 直接给路径 |
| 权限请求（通知、摄像头、地理位置） | 在上下文级别预先授予或拒绝，避免运行时弹窗阻塞 |

### 7.5 页面打不开 / 空白 / 证书错误

```
打开失败
├── URL 错了吗 → 手动访问一次确认
├── 需要代理吗 → 显式配置代理，别指望环境变量自动生效
├── 内部站点的自签证书 → 这是**安全决策**：优先导入企业根证书；忽略证书校验只应作为临时手段并明确记录
├── DNS / 网络不通 → 从运行环境里 ping / curl 一次确认
├── 被 WAF 拦了 → 看到拦截页就停，改走官方接口或联系站点
└── 打开了但内容是空壳 → 前端渲染失败，看控制台错误
```

### 7.6 下载失败或文件是空的

| 排查 | 说明 |
|---|---|
| 是先挂监听再点击吗？ | 顺序反了必然随机丢文件；先 `waitForEvent('download')` 再触发 |
| 拿到文件后及时另存了吗？ | 临时文件在上下文关闭时被清理；必须 `saveAs` |
| 等下载**完成**了吗？ | 拿到事件对象 ≠ 文件写完；`saveAs` 本身会等完成 |
| 是不是被识别成了弹窗/新页面？ | 部分站点用 `window.open` 触发下载，需要同时监听新页面与新窗口 |
| 文件体积是否为 0？ | 空文件通常意味着鉴权失败或参数不对；用同一份 Cookie 手动下载对比 |
| 下载目录有写权限吗？ | 容器里最常见的失败原因 |

### 7.7 越跑越慢 / 内存涨 / 僵尸进程

| 症状 | 原因 | 处理 |
|---|---|---|
| 内存持续上涨 | 页面只开不关；监听器只加不减；每次循环新建上下文不销毁 | 每轮结束关页面；监听器成对移除；上下文复用而非无限新建 |
| 系统里一堆浏览器进程 | 异常退出路径没清理 | `finally` 里 `close()`；进程管理侧加超时强杀兜底 |
| 运行几分钟后卡住 | 某处 `waitForEvent` 没有超时，永远等下去 | 所有等待都必须带超时 |
| 磁盘爆了 | trace / 视频 / 截图无限累积 | 调试产物按天清理；trace 只在调试期开 |
| 上下文太多被系统限制 | 并发无上限 | 显式设并发上限 + 队列 |

### 7.8 结果不对（能跑通但数据错）

这类问题最难发现，因为它不报错。四个高发点：

1. **取值时机太早**：页面骨架先渲染、数据后到。取值前先等承载数据的元素或具体接口。
2. **字段映射错位**：用了 `td:nth-child(n)` 这类位置索引，页面加了一列就全错位。改成「按表头找列索引」或按语义类名/属性取。
3. **分页终止条件错**：把「下一页按钮存在」当继续条件，最后一页按钮仍在但禁用 → 死循环或重复抓取。正确条件是「有下一页且可用且内容确实变了」。
4. **翻页后没等新内容**：地址变了但列表还是旧的。等列表首行内容变化，或等该页接口返回。

```javascript
// 更稳的翻页循环
const seen = new Set();
while (true) {
  await page.locator('table tbody tr').first().waitFor({ state: 'visible', timeout: 10000 });
  const rows = await extractRows(page);
  const fresh = rows.filter(r => !seen.has(r.no));
  if (fresh.length === 0) break;              // 没有新内容 = 真到底了
  fresh.forEach(r => seen.add(r.no));
  // …写入 fresh…

  const next = page.getByRole('button', { name: /下一页/ });
  if (await next.count() !== 1) break;
  if (await next.isDisabled()) break;         // 禁用 = 最后一页
  await Promise.all([
    page.waitForResponse(r => r.url().includes('/api/list') && r.ok(), { timeout: 15000 }).catch(() => {}),
    next.click(),
  ]);
}
```

**用「页码」和「已见集合」双保险**，比单看按钮状态可靠得多。

## 八、上报模板

失败上报时把下面这些字段一次交齐，能省掉一整轮来回：

```
任务：<任务名 / 编号>
目标站点：<域名>（已授权来源：<一句话>）
失败步骤：<第几步 / 做什么>
错误：<异常类型 + 原文前 200 字>
当前 URL：<...>
页面标题：<...>
产物：out/fail/<tag>-<时间戳>/（page.png、snapshot.yml、meta.json）
已尝试：<档位 1/2/3 各自结果；重试次数>
判断：<我怀疑是登录态失效 / 页面改版 / 限流 / 需要人工校验>
需要什么：<重新授权 / 更新定位契约 / 人工处理验证码 / 调整频率>
```

最后两行是关键。**说出你的判断和需要什么**，比贴一大段日志有用得多。
