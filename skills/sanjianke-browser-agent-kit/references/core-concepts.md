# 核心概念与选型

> 这份资料解决两件事：把「浏览器里到底有哪些东西、谁管谁」讲清楚；
> 以及在你动手写第一行代码之前，帮你选出对的那套方案。
> 概念部分与具体库无关，代码片段用最常见的两个库举例，逻辑可以平移。

---

## 一、四层模型：进程 → 上下文 → 页面 → 框架

浏览器自动化里 80% 的「玄学问题」，根因都是没搞清这四层谁是谁。先把它钉死。

```
浏览器进程 (Browser)
└── 上下文 (Context)          ← 身份边界：Cookie / 本地存储 / 缓存 / 权限
    ├── 页面 (Page)           ← 一个标签页：DOM、JS 执行环境、网络
    │   └── 框架 (Frame)      ← iframe：独立的文档与执行环境
    └── 页面 (Page)           ← 同一身份下的第二个标签页
```

### 各层管什么

| 层 | 关键点 | 你操作它做什么 |
|---|---|---|
| 浏览器进程 | 一个进程可服务多个上下文；进程本身不持有登录态 | 启停、选择内核、设全局参数（无头、代理、下载目录）、关闭时清理 |
| 上下文 | **一个上下文 = 一个独立身份**。Cookie、localStorage、sessionStorage、缓存、权限授予都在这里隔离 | 多账号隔离、无痕任务、复用登录态存档、设视口与语言、录制视频 |
| 页面 | 一个标签页，拥有自己的 DOM 与 JS 上下文；页面导航后旧的执行环境作废 | 打开 URL、点击、填表、截图、取值、监听网络与对话框 |
| 框架 | iframe 内部的独立文档；可能跨域 | 定位 iframe 内的元素；跨域时能力受同源策略约束 |

### 四条最常被搞错的规则

**规则 1：不要用同一个上下文跑不同账号。** 上下文隔离是免费的，而清除 Cookie 是有成本的（漏清一项就串号）。多账号任务 = 多上下文，不是多开页面。

**规则 2：页面导航会让旧的元素引用失效。** 页面跳转、局部重渲染、框架重建之后，你之前拿到的元素句柄就指向了一个已经被销毁的 DOM 节点。这就是「为什么我点第一下成功、第二下报 detached」的原因。**定位器（Locator）没有这个问题**，因为它每次动作时重新查一遍 DOM；元素句柄（ElementHandle）有这个问题。优先用定位器，只有在定位器 API 覆盖不到时才退到元素句柄，用完即弃。

**规则 3：新窗口与新标签不是自动接管的。** 点击「在新标签打开」之后，必须显式等待新页面事件并接住它，否则你的脚本还盯着旧页面发呆，然后在旧页面上继续点，超时报错。模式是固定的：

```javascript
const [newPage] = await Promise.all([
  context.waitForEvent('page'),                 // 先挂等待
  page.getByRole('link', { name: '详情' }).click(), // 再触发
]);
await newPage.waitForLoadState('domcontentloaded');
```

**规则 4：多标签任务要归还资源。** 每开一个页面就记一笔，用完 `close()`。一个跑几小时的任务如果只开不关，内存会一路涨到浏览器自己崩掉，而且崩的时候你拿不到任何有用信息。

### 生命周期与善后

```javascript
let browser;
try {
  browser = await chromium.launch({ headless: true });
  const context = await browser.newContext({ /* 身份与视口 */ });
  const page = await context.newPage();
  // …业务…
} catch (err) {
  await page?.screenshot({ path: `out/fail-${Date.now()}.png` }).catch(() => {});
  throw err;
} finally {
  await browser?.close();     // 必须走到；否则留下僵尸进程
}
```

`finally` 里的 `close()` 不是可选项。被 kill 掉的脚本、超时退出的脚本，都会留下孤儿浏览器进程，跑几轮之后机器就满了。

## 二、选型：五条路线，各有它的位置

| 路线 | 它擅长什么 | 它的代价 | 什么时候选它 |
|---|---|---|---|
| **Playwright** | 内置语义定位器（角色/标签/占位符/文案/测试契约）、自动等待与可操作性检查、自动重试断言、多内核统一 API、上下文隔离、内置追踪与录屏、Node/Python/Java/.NET 四语言 | 内核体积较大；生态比另一个老牌库年轻 | **默认首选**。元素定位与等待的地基最扎实，稳定性开箱最好 |
| **Puppeteer** | Node 生态成熟、API 直白、起步极快；新版也提供了带自动等待的定位器与丰富的选择器语法（XPath、文本、ARIA、Shadow DOM 穿透） | 跨语言支持弱；早期写法（`waitForSelector` + 元素句柄）不会自动重试动作，且需要手动释放句柄 | 单语言项目、需要贴近 CDP 的精细控制、或已在用这套栈 |
| **Selenium / WebDriver** | 标准协议、老牌浏览器矩阵覆盖、企业环境与云测平台集成广 | 等待要自己写（显式等待），没有语义定位器；驱动版本管理有额外负担 | 目标环境已被 WebDriver 基础设施绑死，或需要覆盖冷门浏览器 |
| **直接使用 CDP / BiDi 协议** | 最小依赖、可拿到几乎全部底层能力（网络拦截、性能指标、输入事件） | 你要自己处理连接、事件、重连、版本差异；可维护性最差 | 只做一次性的取证、性能采样、或需要某个上层库没暴露的底层能力 |
| **Agent 驱动（模型看页面决策）** | 流程会分叉、页面会改版、步骤无法预先穷举 | 每轮推理有延迟与成本；不确定性高于确定性脚本；出错时定位更难 | 探索型任务、多变的第三方后台、无法预知步骤数的流程 |

### 选型的三条判断线

**第一条：流程是否确定。** 步骤能穷举、分支有限 → 确定性脚本（Playwright / Puppeteer）。步骤依赖页面内容动态决定 → 确定性脚本跑「骨架」，模型只负责需要判断的那几个岔路口。**不要用模型去替代一个本来就很确定的流程**，那是拿成本和不确定性换一个你本来已经有的东西。

**第二条：要不要跨语言。** 只有 Node 一种语言 → Puppeteer 完全可以。需要 Python 做数据、Java 做后端集成 → Playwright 的多语言统一 API 省下的对齐成本远大于它多占的磁盘。

**第三条：稳定性问题出在哪一层。** 如果历史故障以「元素找不到 / 点了没反应 / 时序不对」为主 → 换一个自动等待与语义定位更强的库，收益立竿见影。如果故障是「站点风控 / 限流 / 验证码」→ **换库没有任何用**，见 `safety-and-troubleshooting.md`，那是流程与合规问题。

### 引擎（内核）怎么选

| 内核 | 适用 | 注意 |
|---|---|---|
| Chromium | 绝大多数场景的默认选择，生态与调试工具最全 | 部分站点对无头 Chromium 有额外校验 |
| Firefox | 需要验证跨浏览器行为，或目标站点对 Chromium 表现异常 | API 细节偶有差异，别假设行为完全一致 |
| WebKit | 需要覆盖 Safari 系内核的行为 | 兼容性差异最多，非必要不引入 |

一个常被忽略的点：**你测的内核 ≠ 用户用的内核**。如果你的目标只是「取到数据 / 完成操作」，用一个内核跑通就够；如果目标是「验证这个页面在各浏览器都对」，那内核矩阵是需求本身，不能省。

## 三、自动等待到底保证了什么

这是整份规范里最值钱的一段。理解了它，你就知道什么该等、什么不该等。

现代自动化库在动作前会做一组**可操作性检查（actionability checks）**，全部通过才执行动作；不通过就等到超时，然后抛超时错误。核心检查项与判定标准：

| 检查项 | 判定标准 | 它挡住的真实故障 |
|---|---|---|
| 已挂载 / 可解析 | 定位器能解析出元素 | 元素还没渲染出来 |
| **唯一命中** | 解析结果必须恰好一个 | 定位器太宽，点错了一个看不见的同类元素 |
| **可见** | 有非空边界框，且不是 `visibility:hidden`；`display:none` 不算可见；**`opacity:0` 算可见** | 元素在折叠面板里、还没展开 |
| **稳定** | 连续两帧边界框不变 | 元素正在动画/滑入，点在了移动中的位置 |
| **可接收事件** | 动作坐标上的命中目标就是它，没有被别人盖住 | 弹层、遮罩、吸顶导航挡住了按钮 |
| **可用** | 不是 `disabled`，不在 `[disabled]` 的 `fieldset` 里，不在 `aria-disabled=true` 子树里 | 提交按钮还是灰的 |
| **可编辑** | 可用且非 `readonly` | 输入框是只读的 |

不同动作检查的项不同：点击类要「可见 + 稳定 + 可接收事件 + 可用」；填表类要「可见 + 可用 + 可编辑」但**不检查稳定**；悬停类不检查可用；纯滚动只检查稳定。

### 自动等待的四个盲区

**盲区 1：它不理解业务语义。** 按钮可点了 ≠ 后端已经处理完。自动等待只保证「人能点」，不保证「点了有用」。业务完成信号必须你定义：URL 变了、列表多了一行、成功提示出现、某个接口返回 200。

**盲区 2：它不会重试「业务失败」。** 点击成功但服务器返回「库存不足」，这在自动化的眼里是一次成功动作。失败判定要自己写在动作之后。

**盲区 3：`opacity: 0` 被算作可见。** 靠淡入淡出隐藏的元素，自动等待不会帮你拦。要拦就得断言具体属性（`toBeVisible` 有时也不够，得看 `toHaveCSS('opacity', '1')` 或等动画结束类名）。

**盲区 4：`force` 会关掉检查。** 点击时的 `force` 选项会跳过「可接收事件」等非必要检查——它能让「被遮挡的按钮」点下去，**但也会把「其实点错了元素」这件事一起放过**。`force` 只应作为临时诊断手段，看到它出现在正式代码里，就要问：遮挡到底是谁造成的？

### 五种等待条件，各管一段

| 等待类型 | 等的是什么 | 典型写法 | 该用在哪 |
|---|---|---|---|
| 自动等待 | 动作前元素可交互 | 不需要写，动作自带 | 所有交互动作前，默认就有 |
| 断言等待 | 元素达到某个状态 | `await expect(loc).toBeVisible()` | 校验步骤，会重试到超时 |
| 显式状态等待 | 元素进入某状态 | `await loc.waitFor({ state: 'visible' })` | 动作前想先确认存在、或等它消失 |
| 导航等待 | 页面级状态变化 | `await page.waitForURL(/\/orders\/\d+/)` | 用 URL 作为业务成功的信号 |
| 网络等待 | 某个请求完成 | `await page.waitForResponse(r => r.url().includes('/api/orders') && r.ok())` | 页面本身没变化，但数据刷新了 |
| 硬睡 | 什么都没等，纯计时 | `await page.waitForTimeout(3000)` | **仅调试期**。正式代码里出现硬睡，就是缺一个信号 |

关于「网络空闲」这个条件要特别说明：它在**长轮询、心跳、埋点上报**的页面上永远不会满足，或者会在你以为空闲之后又被新请求打破。它只适合那些「请求会明确停下来」的页面。更可靠的做法是**等那个具体的接口**，而不是等「所有接口都安静」。

## 四、三种取值通道，分工别搞混

让模型或程序理解页面，有三条路。它们的成本、精度、稳定性完全不同。

### 通道 A：DOM 取值（结构化、最省、最精确）

```javascript
// 只取需要的字段，不要整个 innerHTML 拖回来
const rows = await page.locator('table.order-list tbody tr').evaluateAll(trs =>
  trs.map(tr => ({
    no:     tr.querySelector('td:nth-child(1)')?.innerText.trim() ?? '',
    amount: tr.querySelector('td.amount')?.innerText.trim() ?? '',
    status: tr.querySelector('td.status')?.innerText.trim() ?? '',
  }))
);
```

适用：表格、列表、详情字段、属性值。优点：token 便宜、可比对、可入库。缺点：要你事先知道结构。

**注意**：`evaluate` 里跑的是页面环境的代码，取不到 Node 侧的变量；要传参就显式传进函数参数。取值时对可能缺失的节点写 `?.` 兜底，一个空单元格不该让整个任务崩。

### 通道 B：ARIA 语义快照（给模型看，结构 + 角色 + 名称）

把页面的可访问性树压成 YAML 形式的快照，只保留角色、可访问名、状态属性。它比 HTML 短一到两个数量级，而且天然过滤掉样式与包装层——**页面改版只要语义没变，快照就基本稳定**。这是目前 Agent 驱动浏览器的首选通道。

```
- heading "订单列表" [level=1]
- list:
  - listitem: 订单 A-1024
  - listitem: 订单 A-1025
- button "导出对账单"
- textbox "搜索订单号"
```

快照里的节点可以直接反查回定位器，所以「模型读快照 → 回一个语义描述 → 你用定位器执行」这条路是通的，不需要模型输出 CSS 选择器。作用域可以收窄（只对某个区域取快照），大幅压缩 token。

### 通道 C：截图（给人看，给多模态模型看）

适用：页面布局问题、图表内容、验证码出现（用来**报告**而不是识别）、失败现场留证。规则：

- 关键截图前先等元素稳定（连续两帧边界不变），否则截到动画中间态。
- 全页截图在超长页面上会得到一张巨大的图，先算一下尺寸；给模型看的时候优先截相关区域，而不是整页。
- **不要把截图当数据源做数值比较**：缩放、字体渲染、抗锯齿都会让同一段文字看起来不同。数值一律走通道 A。

### 三通道的分工表

| 目标 | 首选通道 | 理由 |
|---|---|---|
| 结构化入库 | A | 精确、便宜、可比对 |
| Agent 决策找元素 | B | 抗改版、token 省、能反查回定位器 |
| 判断「页面对不对」 | B + C | 结构断言 + 视觉留证 |
| 失败取证 | C + B + 日志 | 三件套缺一不可 |
| 图表 / Canvas 内容 | C | DOM 里根本没有这些内容 |

## 五、Agent 驱动的最小闭环

把上面的东西串起来，一个 Agent 操作页面的循环长这样：

```
1. 取快照（通道 B，必要时加通道 C）
2. 压缩：只留可见、可交互、有语义名节点；截断到 N 个（建议 ≤80）
3. 把「目标 + 当前 URL/标题 + 节点列表 + 上一步结果」交给模型
4. 模型回一个结构化动作：{action, target, value}，target 用节点编号
5. 用编号回填到真实定位器 → 执行 → 校验
6. 记录本步结果（成功/失败/新状态），回到 1
```

六条纪律，每条都对应一类真实故障：

1. **编号每轮重算。** DOM 变了编号含义就变了。把上一轮的 id 用到下一轮 = 点错元素。
2. **一次一个动作。** 批量动作会让「哪一步出错」变成不可知，也让模型失去纠错机会。
3. **动作前重取快照。** 延迟一秒钟，页面就可能已经变了。
4. **动作后必须校验。** 只校验「没抛异常」是不够的——点击成功和业务成功是两件事。
5. **设步数上限与总预算。** 没有上限的循环一定会死在某个死循环里，而且烧钱。
6. **每步留痕。** 至少记：步号、动作、目标描述、耗时、结果、截图路径。事后能复盘的循环才可维护。

### 什么时候不该用 Agent 驱动

- 步骤固定、分支可穷举：写确定性脚本，快、便宜、可测。
- 需要高吞吐（每分钟几十上百次操作）：模型的延迟会成为瓶颈。
- 对可复现性要求高（比如需要逐字对齐的财务流程）：模型的不确定性是负债。

Agent 驱动的定位是**处理不确定性**，不是**替代脚本**。两者混合才是常态：脚本走骨架，模型只在歧义处介入。

## 六、可观测性三件套

一个无法复盘的自动化任务，失败一次你就得从头再来。三样东西必须留：

| 产物 | 什么时候开 | 用途 |
|---|---|---|
| 截图 | 常态（关键步骤前后） | 一眼看清页面长什么样、卡在哪 |
| 结构快照（ARIA / DOM 片段） | 常态（失败时必留） | 看清「当时页面上有什么元素」，定位器失效的直接证据 |
| 追踪 / 录屏（trace / video） | 调试期，或高危流程 | 逐步回放每个动作与网络请求，定位时序问题 |

三条实践建议：

- **常态只开截图 + 失败时的快照**，追踪与录屏按需开。追踪文件会在短时间内吃掉几百 MB。
- **日志要结构化**：每行带步号、动作、目标、耗时、结果。不要打一堆自由文本，那样等于没打。
- **失败时按「截图 + 快照 + 日志 + 当前 URL」四件一起打包上报**，缺任何一件都会让排查多花一轮。

## 七、一页速查

| 问题 | 答案 |
|---|---|
| 多账号怎么隔离？ | 一账号一上下文，不要在上下文内清 Cookie 复用 |
| 为什么第二下点击报元素已销毁？ | 用了元素句柄；改用定位器（每次动作重新查 DOM） |
| 新标签页接不住？ | 先 `waitForEvent('page')` 再触发点击，用 `Promise.all` 包住 |
| `networkidle` 一直不返回？ | 页面有长轮询/心跳；改成等具体接口或用 DOM 信号 |
| 按钮能点但没反应？ | 自动等待只管「能点」，业务完成信号得自己定义 |
| `force: true` 能解决问题吗？ | 能绕过遮挡检查，但会掩盖「点错元素」；只当诊断用 |
| 给模型看什么最省？ | ARIA 语义快照（角色 + 名称 + 状态），只留可见可交互节点 |
| 数值对比看图还是看 DOM？ | 永远看 DOM；截图会被缩放和字体骗 |
| 跑完一堆僵尸浏览器进程？ | `finally` 里没 `close()`，或者被 kill 的脚本没清理 |
