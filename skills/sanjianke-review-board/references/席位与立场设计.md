# 席位与立场设计

> 这份文档回答一个问题：**为什么本包必须是"四个立场对抗"，而不是"一个声音多审几遍"。**

---

## 一、先划清三层的分界（做错就是白做）

| 层 | 形态 | 本项目里的代表 |
|---|---|---|
| L1 单点生成型 | 一个输入 → 一个产出 | 标题工坊、一稿多平台改写 |
| L2 智能体型 | **单循环**：抽档 → 写 → 自检 → 迭代（一个声音自我迭代） | 内容质量闭环 |
| L3 多智能体协作型 | **多角色分工互审**，一条命令出成品 | 本包、流水线式内容团队包 |

L3 的关键**不是"调多次模型"**。调多次模型只说明花了更多钱。L3 的判据是：

> **每个角色有自己独立的目标函数，且会互相否掉对方。**

如果四个角色看同一份东西、给出四份措辞不同但结论一致的评审，那不是协作，
是**同一份意见换了四个抬头**。本包为此专门做了闸门五（见下文第五节）。

---

## 二、本包是"对抗式"，不是"流水线式"

同为 L3，还有另一种做法：角色**按顺序接力**——策划 → 写手 → 审稿 → 合规，后一个审前一个。
本包刻意做另一种：

| | 流水线式（角色顺序协作） | **本包（对抗式）** |
|---|---|---|
| 形态 | 角色按顺序接力，后一个审前一个 | 多立场**同时**独立评审，然后**当面对质** |
| 输入 | 一个选题，从零写 | **一份已有方案/稿件**，要判它该不该过 |
| 核心机制 | 打回重写 | **分歧显性化 + 裁决** |
| 产出 | 定稿 | **裁决书**（结论 + 条件清单 + 少数派意见） |
| 信息流 | 单向（向后传） | **先隔离（panel）后合流（clash）** |

一句话：流水线要的是"把稿子改好"，本包要的是"**说清谁反对、争什么、怎么裁**"。

---

## 三、四个席位

每个席位有两个字段决定它的行为：**目标函数**（它在为什么负责）与**天然倾向**（它会去挑什么）。
注意"天然倾向"不是偏见，是**职责**——一个不做自己那份挑剔的席位，等于没上场。

### 第 1 席 · 用户代言人（`user_advocate`）

- **目标函数**：用户看完会不会觉得有用、会不会觉得被骗
- **天然倾向**：挑自嗨、术语堆砌、承诺不清、把内部视角当成用户视角
- **评审视角**：站在一个普通用户的位置上：这段话对他有什么用？他凭什么信？他会不会觉得被绕了？

### 第 2 席 · 竞品分析师（`competitor_analyst`）

- **目标函数**：这东西和市面上已有的比，有没有可被指认的差异
- **天然倾向**：挑同质化、没有声称、随时可被替代、把通用能力当独家卖点
- **评审视角**：把它和市面上已有的同类东西放在一起：哪一句话是别人说不出、或说不动的？

### 第 3 席 · 合规官（`compliance_officer`）

- **目标函数**：法律与平台风险——这份东西发出去会不会出事
- **天然倾向**：挑违禁词、绝对化用语、无依据承诺、资质缺失、刷单与导流话术
- **评审视角**：把这份材料当成即将公开发布的东西来审：哪一句会被平台或监管盯上？

### 第 4 席 · 业务负责人（`business_owner`）

- **目标函数**：投进去的人力和钱，能不能换回可衡量的结果
- **天然倾向**：挑成本过高、链路太长、没有 CTA、没有验收口径、失败没有止损
- **评审视角**：如果这条链路明天就要开工：要几个人、几天、多少钱，什么算成功，什么算止损？

## 四、为什么这四个立场**一定会**互相否掉

不是希望它们吵，而是结构上安排好了对撞点：

| 场景 | 一个席位要 | 另一个席位正好在拦 |
|---|---|---|
| 加转化 | 业务负责人要补 CTA 与验收口径 | 合规官在拦那句承诺（无依据、无法举证） |
| 说人话 | 用户代言人嫌术语堆砌 | 竞品分析师觉得那些术语正是唯一可指认的差异 |
| 讲差异 | 竞品分析师要独家声称 | 合规官不许「独家 / 唯一」这类无依据的排他表述 |
| 砍链路 | 业务负责人要砍掉纯消耗的一步 | 用户代言人说那一步正是用户信任的来源 |
| 补数据 | 业务负责人要补复购率与转化率 | 合规官说无出处的经营数据一律删掉 |

另外每个席位都要回答三个**必答问题**（写进提示词，见 `build_seat_prompt`）：

1. 这份材料在什么条件下值得通过？
2. 什么情况下必须否决它？
3. 你最不能让步的一点是什么？

第 3 条落到 JSON 里就是 `must_have`，第 2 条是 `kill_switch`。这两个字段是**结构性**地逼出差异的：
四个立场不同的角色不可能给出同一句底线。真机实测四席的 `kill_switch` 分别指向
事实口径、差异化、合规、预算对账四个互不重叠的维度。

## 五、信息隔离：机制，不是修辞

`panel` 阶段是 **N 次独立调用**（N = 席位数，默认 4）：

- 每次调用的 system 提示词里**只有本席位的**目标函数、天然倾向、评审视角
- user 提示词里**只有本席位**的视角与关心清单 + **材料全文**
- **没有**席位花名册，**没有**其它席位的任何文字
- 四席的产出`prompt_sha` 各自记账，隔离证据写进产物（`isolation` 字段）

```bash
python3 scripts/run.py panel --file 方案.md --json --out panel.json
# → panel.json 里的 isolation.seats[*].prompt_sha / other_seat_names_found
```

`isolation.stage_inputs` 明确记着每个阶段的输入：

```json
{"panel": ["material"], "clash": ["material", "panel"], "verdict": ["material", "panel", "clash"]}
```

**为什么隔离必须是真的**：如果四席在一次调用里一起答，它们会互相读取、互相妥协，
最后收敛成一段四平八稳的"综合意见"。那样得到的不是四个立场，而是一个立场的四种说法。
隔离之后，四份结论才是四个目标函数**各自算出来的**，对质阶段才有真东西可对。

**隔离只发生在 panel 阶段。** `clash` 阶段**故意**把四份意见放到同一张桌上——
这正是对质的目的。把"隔离"和"合流"分成两个命令、两个阶段，是本包与"一次问四个角色"的
本质区别：前者可以检查，后者只能相信。

## 六、席位组合：`--seats`

默认四席全上。可以只跑其中几席：

```bash
python3 scripts/run.py run --file 方案.md --seats compliance_officer,business_owner
```

两个约束：

1. **至少两席**——一席构不成对质，脚本直接 `exit=2`
2. 席位组合**进断点 key**——四席与两席的产出不是一回事，换组合必须重跑

什么时候该减席位：只关心"能不能发"时用 `compliance_officer,business_owner`；
只关心"用户会不会买账"时用 `user_advocate,competitor_analyst`。
**但不建议长期只跑两席**：四席对撞出来的分歧，两席看不见。

---

## 七、席位只有立场，没有决定权

这是本包最重要的一条设计约束：

- 席位**不能**决定通过与否，它只能给出本席位的 `verdict`（支持 / 有条件支持 / 反对）、
  `acceptability`（0~10）、底线与否决条件
- **裁决由 `verdict` 阶段（主席视角）出**，而且必须：
  - 有席位反对时**不许**判「通过」
  - 带**条件清单**
  - 把**少数派意见原样保留在案**

为什么把"决定权"从席位手里拿走：如果让四个立场投票决定，结果必然是
"多数压少数"，少数派的理由会被丢掉。而本包的交付物恰恰是**少数派意见**——
用户要看到的是"谁在反对、为什么反对、这个反对意见有没有被处理"。

---

## 八、已知边界

1. **席位是提示词级别的角色，不是独立进程**。四个立场共用同一个模型（默认 `deepseek-chat`）。
   隔离靠调用边界与提示词边界实现，不靠不同模型。换模型（`--model`）会整体改变四个立场的表达。
2. **模型仍可能"和稀泥"**。四席都写"建议进一步优化"这种事发生过，处理方式是闸门五 +
   锚点闸门（泛泛之谈引不出原文，会被剔出）。
3. **`--dry-run` 只能预演四席提示词**。对质与裁决的提示词依赖四席产出，
   在没有任何产出之前无法拼出来——这是诚实的，不是缺陷。
