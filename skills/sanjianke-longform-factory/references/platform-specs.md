# 平台规格 · 字数 / 结构 / 配图 / 出图比例

本文件是 `run.py` 里 `PLATFORMS` 表的**人类可读版本**，以及三张实测对照表。
代码里的表是唯一执行口径，本文件与它不一致时以代码为准。

---

## 一、三个平台的正文口径

| 平台 | 键 | 正文字数区间 | 建议配图 | 出图比例 | 结构口径 |
|---|---|---|---|---|---|
| 公众号 | `wechat` | 2500~4500 | 2~5 张 | `16:9` | 开头钩子 + 3~6 个小标题分节 + 结尾引导 |
| 头条 | `toutiao` | 1800~3500 | 3~6 张 | `16:9` | 结论前置 + 分点展开 + 结尾引导 |
| 知乎 | `zhihu` | 2500~6000 | 1~4 张 | `4:3` | 先给判断 + 依据与边界 + 结尾引导 |

`--chars-min` / `--chars-max` 可以覆盖任意平台的区间（`write` 以大纲里的平台为准，`adapt` 用这两个参数）。

### 各平台的调性说明（提示词里逐字用了这些描述）

**公众号**

> 长图文。开头 3 行内必须给出「读完能拿到什么」；小标题要能单独被截图传播；
> 结尾引导偏「在看 / 转发 / 关注」。

**头条**

> 信息流。第一段就要给结论（信息流的读者只看前两屏）；段落短、每段不超过 4 行；
> 结尾引导偏「关注看后续」。

**知乎**

> 问答体。开头必须先给判断（赞同/反对/分情况），再给依据与边界条件；
> 允许更长的推理链；结尾引导偏「收藏 / 追更 / 评论区补充」。

### 为什么不给三个平台用同一个区间

平台的折叠与截断行为不同：

- **公众号**在会话里展开，读者愿意读完，所以下限可以高到 2500；但超过 4500 会被"阅读全文"折叠
- **头条**是信息流，前两屏定生死，所以字数区间整体下移（1800 起），但段落必须更短
- **知乎**允许长推理链，上限放到 6000；下限仍然是 2500，因为低于这个长度的回答会被当"抖机灵"

同一篇稿子不改就发给三个平台，等于放弃其中两个。

## 二、字数计数口径（务必看这一节）

`count_chars()` = **去掉 Markdown 符号与空白后的字符数**，中英文按字符计。

去掉的符号集：`# * > ` - [ ] ( ) | ~` 与所有空白（空格、Tab、换行）。

- **不去掉中文标点**（`，。、；：""''（）`）—— 中文标点占字宽，平台也算
- **不去掉英文标点与数字** —— 同样占位
- 代码块的 ``` 围栏会被去掉，但代码内容本身算字数

和"汉字数"的区别：一段 400 字的英文说明，按汉字数算是 0，按本口径算 400。
平台折叠按视觉长度，所以本口径更接近实际。

## 三、出图比例：上游按 32 对齐

**这不是网关 bug，是扩散模型按 32 对齐的常规做法。**
上游先定总像素，再把每边向下取整到 32 的倍数，所以像素级精确比例不是总能给出来。

### 1K 档 10 种比例实测对照

| 请求 `aspect_ratio` | 实测像素 | 实得比例 | 与请求的偏差 |
|---|---|---|---|
| `1:1` | 1024x1024 | 1.0000 | 0.00% |
| `4:3` | 1184x864 | 1.3704 | 0.00% |
| `3:2` | 1248x832 | 1.5000 | 0.00% |
| `2:3` | 832x1248 | 0.6667 | 0.00% |
| `21:9` | 1536x672 | 2.2857 | 0.00% |
| `16:9` | **1344x768** | 1.7500 | **1.56%** |
| `9:16` | 768x1344 | 0.5714 | **1.56%** |
| `3:4` | 864x1184 | 0.7297 | **2.70%** |
| `4:5` | 896x1152 | 0.7778 | **2.78%** |
| `5:4` | 1152x896 | 1.2857 | **2.86%** |

**5 种精确、5 种偏差 1.5%~2.9%。**

> 本包实测复核了 `16:9` 这一行：两张图都是 **1344x768**，偏差 **1.56%**，
> `want_ratio=16:9` / `real_label=7:4`。这与上表一致。

### 处理方式（三条一起用）

1. **默认容差 3%**：容差内不算"假"，但会**明确打印真实像素与偏差**，不藏
   （`check_ratio()` 的 `why` 字段里带着 `真实像素 1344x768（7:4 = 1.7500），与请求比例偏差 1.56%，在容差内`）
2. **超容差** → 标红 + 计入闸门失败 + 退出码 3
3. **`--snap`**：出图后按请求比例本地裁准，**裁完再读文件头复核**，裁成功才记 exact

### 容差地板 `0.0025`

像素只能是整数，所以"裁到精确比例"本身就有量化误差。
实测：把 2.35:1 裁到宽 864 → 高 368，偏差 0.0925%；相邻整数像素间隔约 0.27%。
所以用户把 `--ratio-tolerance` 调到比 0.0025 还小时，会把**本来就必须存在**的舍入误差
判成不合格。`RATIO_TOLERANCE_FLOOR = 0.0025` 是保守地板，仍能抓住真错：
请求 3:4 却给 2:3 的偏差是 11%，比地板大 40 倍。

### 裁剪优先用 PIL，回落到内置 PNG 裁剪器

- 有 PIL → 用 PIL（支持所有格式）
- 没有 PIL → 回落到内置的 8 位 PNG 裁剪器（只用 `zlib` + `struct`），
  仅支持 `color_type` 2/6（8 位真彩 / 真彩+alpha）
- **两条路都走不通时如实返回失败**，不做"假装裁过"

### 实测任务返回结构（原样摘录）

提交后拿 `task_id`，轮询 `GET /api/v1/tasks/<task_id>`，**completed 的返回长这样**：

```json
{
 "code": 1,
 "msg": "success",
 "data": {
  "task_id": "task_a0cd09827e58bc3df738c4b7",
  "model": "nano_banana/submit",
  "type": "app",
  "call_type": "async",
  "status": "completed",
  "created_at": "2026-09-29T09:17:21Z",
  "result": {
   "data": [ { "prompt": "…", "image_url": "https://…/task_…_1.png" } ],
   "success": true,
   "trace_id": "014e35a8-…",
   "image_url": "https://…/task_…_1.png",
   "upstream_task_id": "8719d9d3-…",
   "results": [ { "prompt": "…", "image_url": "https://…", "transfer_status": "success" } ]
  },
  "usage": { "input_tokens": 0, "output_tokens": 0, "total_tokens": 0, "points_cost": 24 },
  "completed_at": "2026-09-29T09:18:00Z",
  "response_time_ms": 0
 }
}
```

**三处必须记牢的实测事实**：

1. **`status` 在 `data` 顶层，不在 `data.result` 里。** 平台文档写的是 `data.result.status`，
   照文档写会永远读不到状态、一路轮询到超时。
2. **实际扣费只信 `data.usage.points_cost`**（上例是 `24`）。
   平台的 `pricing_matrix` / `tenant_*` 字段我们验证过半数不可信，只当参考、绝不写进结算口径。
3. **图片地址有三处**（`result.image_url`、`result.data[0].image_url`、`result.results[0].image_url`）。
   本包做深度优先搜索把所有 `image_url` 收齐再去重保序，只取第一处也能跑，但结构一变就瞎。

另外：**提交响应里的 `frozen_points` 只是预冻结**，失败全额退回，不是最终扣费。

### 生成应用那层信封

出图走的是**生成应用**链路，返回会包一层 `{"code": 1, "data": {...}}`，`code == 1` 才是成功。
而 **`/chat/completions` 的成功响应不带 `code` 字段** —— 文本链路别拿 `code` 判成功。

## 五、出图成本与计费

| 项目 | 值 | 来源 |
|---|---|---|
| nano_banana `1K` | **24 点/张** = 0.24 元 | **实测**（本包两张图实测扣费 24 点/张，合计 48 点） |
| nano_banana `2K` / `4K` | **没有实测价** | 未实测 → 不给默认值，必须 `--points-per-image`，宁可拒绝估算也不编一个数 |
| 文本模型 | **网关不公布单价** | pricing 表不含文本模型、models 无价格字段、usage 无 points_cost |
| 币值 | 1 元 = 100 点 | 算力集市的充值比例 |

### 成本闸门（`--budget`）的两道

1. **报价阶段**（提交任何任务之前）：预估点数 > `--budget` → 中断，退出码 3
2. **逐张提交前**：已花 + 待花 > `--budget` → 就地停下（前面的真实扣费可能比预估高），退出码 3

出图**不给 `--yes` 时只报价、不提交任何任务**（退出码 4，`kind=usage`）。
`all` 里遇到这种情况会提示：确认后加 `--yes` 重跑；只想先看正文就加 `--images 0`。

### 文本成本只出 token

`cost` 子命令与每次调用的 `cost` 字段里，**文本默认只给 token**：

```json
{
  "calls": 1,
  "prompt_tokens": 755,
  "completion_tokens": 866,
  "total_tokens": 1621,
  "yuan_per_ktok": null,
  "yuan": null,
  "price_source": "unknown",
  "notes": ["网关不公布文本模型单价（pricing 表不含文本模型、models 无价格字段、"
            "usage 无 points_cost），所以这里**只出 token**。"]
}
```

要金额就传 `--yuan-per-ktok <元/千token>`，传了才会出现 `yuan` 与 `points`，
且 `price_source` 变成 `user-supplied`、notes 里明确写"按你自己填的单价折算，是估算不是账单"。

**我们不编一个"看起来合理"的单价**，因为编出来的数字会被当成账单。
