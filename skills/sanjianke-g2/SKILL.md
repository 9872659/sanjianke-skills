# 三剪客 · 统计图表可视化语法

它是一套"用声明式语句描述图表"的 JavaScript 可视化引擎：你给数据和一份图形语法声明，它把柱子、折线、散点、饼图等常规统计图表渲染到 Canvas / SVG / WebGL 上，并自带坐标轴、图例、Tooltip、缩放等交互。当你需要在网页或数据看板里把结构化数据画出来，且不想为每种图表写一套渲染逻辑时用它。

**上游项目**：`G2`　**仓库**：https://github.com/antvis/G2

## 什么时候用 / 不用

**用它**：

- 要在 Web 页面、数据看板或内部工具里渲染常规统计图表：柱状图、折线图、面积图、散点图、饼图、玫瑰图等。
- 数据已经是前端能拿到的数组 / JSON，要的是"声明式画图"而不是"从零写 Canvas 绘制代码"。
- 需要一套统一的图形语法来表达多种图表（mark + encode + scale + transform + coordinate），减少不同图表各写一套的成本。
- 需要图表交互：图例筛选、Tooltip、刷选、缩放平移、数据驱动的动画。
- 需要在 Canvas / SVG / WebGL 之间切换渲染方式，或要在服务端出图（配合相应的 Node 渲染方案）。
- 需要深度定制：自定义 mark、自定义 scale、自定义 transform，或基于这套语法搭自己的图表库。

**不要用它**：

- 目标不是"画统计图表"。流程图、组织架构图、拓扑 / 关系网络图属于 G6、X6 这类工具的领域，别用 G2 硬做。
- 你要的是开箱即用、以配置项为主的常规图表组件，且不想接触图形语法——先看基于它封装的图表库是否更合适。
- 需要交互式地理空间可视化（地图、轨迹、热力）——那是地理可视化库的活。
- 项目栈是 Python / R 做数据分析出图，前端只负责展示静态图片。这种情况用分析侧的绘图库更快。
- 只需要把数据导出成 Excel 表格，或者只是做个简单的 HTML 表格展示。上可视化引擎属于过度设计。
- 团队无法接受引入一套可视化依赖（体积与学习成本）。先把依赖成本算清楚再决定。

## 安装

**npm（v5 系列，当前 npm 上的 latest 为 5.x）**

```bash
npm install @antv/g2
```

```bash
yarn add @antv/g2
```

**注意版本分叉**：包在 npm 上的 latest 标签指向 5.x 系列，仓库另有 `v5`、`v4.0.x`、`v3.5.x` 等分支以及对应的 npm dist-tag。老项目维护时别直接 `npm install @antv/g2` 把大版本升上去，先确认自己在哪个大版本上。要锁定大版本就显式写版本区间，例如 `npm install @antv/g2@^4`，具体可用标签以官方包页与文档为准。

**浏览器直接引入**：包内提供 UMD 构建产物（`dist` 目录下有 `g2.min.js`、`g2.lite.min.js` 等），通过 `<script>` 引入后从全局命名空间取 `Chart`。具体全局变量名与产物路径以实际版本的文件为准。

**本地开发仓库（改源码时才需要）**

```bash
npm install
npm test        # 单元测试
npm run dev     # 起本地 playground
npm run build   # 构建 lib / esm / dist
```

## 常用操作

**1. 最小可用：一张柱状图**

```html
<div id="container"></div>
```

```js
import { Chart } from '@antv/g2';

const data = [
  { genre: 'Sports', sold: 275 },
  { genre: 'Strategy', sold: 115 },
  { genre: 'Action', sold: 120 },
  { genre: 'Shooter', sold: 350 },
  { genre: 'Other', sold: 150 },
];

const chart = new Chart({ container: 'container' });

chart
  .interval()            // 造一个 interval（柱 / 条）标记
  .data(data)            // 给这个标记绑数据
  .encode('x', 'genre')  // 把 genre 列映射到 x 通道
  .encode('y', 'sold')   // 把 sold 列映射到 y 通道
  .encode('color', 'genre');

chart.render();
```

**2. 换图表类型：只改 mark**

折线用 `.line()`、面积用 `.area()`、散点用 `.point()`、饼 / 环用 `.interval()` 配合坐标系变换。G2 不按"图表类型"分类，而是按标记（mark）+ 通道编码（encode）组合，所以换图型通常就是换一个 mark 方法。

```js
const chart = new Chart({ container: 'container' });
chart
  .line()
  .data(data)
  .encode('x', 'date')
  .encode('y', 'value')
  .encode('color', 'series');
chart.render();
```

**3. 配置坐标轴、图例、Tooltip**

在渲染前通过链式 API 配置组件。示例（具体可配置项以官方 API 文档为准）：

```js
chart
  .interval()
  .data(data)
  .encode('x', 'genre')
  .encode('y', 'sold');

chart.axis('y', { title: '销量' });
chart.legend('color', { position: 'top' });
chart.tooltip({ title: 'genre' });
chart.render();
```

**4. 用数据变换做聚合**

G2 内置了 transform 机制，可以在声明里直接做分组、堆叠、排序、归一化等处理，不必先把数据洗成最终形态。示例结构（transform 类型名以官方文档为准）：

```js
chart
  .interval()
  .data(data)
  .transform({ type: 'stackY' })
  .encode('x', 'month')
  .encode('y', 'value')
  .encode('color', 'category');
chart.render();
```

**5. 多视图 / 复合视图**

用 `chart.view()` 在同一个容器里组织多个视图，用于分面、双轴、局部放大等场景。示例结构（以官方 API 文档为准）：

```js
const chart = new Chart({ container: 'container' });
const view = chart.view();
view
  .interval()
  .data(data)
  .encode('x', 'genre')
  .encode('y', 'sold');
chart.render();
```

**6. 响应容器尺寸变化**

容器尺寸变化后需要让图表重新计算布局，调用 `chart.forceFit()` 之类的自适应方法（方法名与行为以官方文档为准），或者销毁重建。别只改 DOM 尺寸而不通知图表，否则会出现内容错位或被裁切。

**7. 销毁图表释放资源**

```js
chart.destroy();
```

在单页应用里切换路由或重渲染组件时，务必销毁旧实例，否则旧图表的监听和画布会残留。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 图表空白，容器有尺寸但没内容 | 容器元素不存在、尺寸为 0，或 `render()` 之前 DOM 还没挂载 | 确认 `container` 选择器能取到元素且宽高非 0；在 DOM 就绪后再创建并渲染 |
| 从仓库 README 复制的示例跑不通 | 默认分支上的 README 示例与 npm 上 latest 的大版本不是同一套 API（v4 与 v5 的写法差异很大） | 以所装版本的官方文档为准，先 `npm ls @antv/g2` 确认实际装到的大版本 |
| 容器缩放后图表被裁切或错位 | 图表按创建时的尺寸算布局，容器变化后没有通知它 | 监听容器尺寸变化并调用自适应方法，或销毁后按新尺寸重建 |
| 图表在弹窗 / 隐藏标签页里初始化后显示异常 | 初始化时容器不可见、宽高为 0，布局算出了 0 尺寸 | 等容器可见后再初始化；或显式传入宽高 |
| 单页应用反复切换页面后内存持续上涨 | 旧图表实例没有销毁，画布和事件监听被保留 | 组件卸载 / 路由离开前调用 `destroy()` |
| 升级依赖后整页图表全挂 | 跨大版本升级（v3 → v4 → v5）API 不兼容 | 锁定大版本区间；升级前先读官方迁移说明，逐个图表改造 |
| 大量数据点导致页面卡顿 | 点数过多或渲染器选择不合适 | 做数据聚合 / 抽样，或切换更合适的渲染方式（Canvas / WebGL），必要时减少动画与交互 |
| 图例、坐标轴文字被截断 | 边距不足或标签过长 | 调整容器尺寸与边距，或配置标签换行 / 省略策略 |
| 服务端渲染时报错找不到 DOM | 默认渲染路径依赖浏览器环境 | 服务端出图需要走官方文档给出的服务端渲染 / 无头环境方案，不要直接复用浏览器写法 |

## 触发场景

- "我要在网页上画一组柱状图和折线图"
- "这份销售数据怎么在前端做可视化"
- "图表要支持图例筛选和 Tooltip"
- "怎么在 Canvas 和 SVG 之间切换渲染"
- "我要自定义一种图表形式，现有图表库满足不了"
- "图表容器大小变了就错位，怎么让图表自适应"

## 能力边界

**覆盖**：

- 常规统计图表的声明式绘制：柱 / 条 / 折线 / 面积 / 散点 / 饼 / 环 / 玫瑰等，通过 mark + encode 组合表达
- 图形语法体系：数据到图形的映射、标度（scale）、坐标（coordinate）、数据变换（transform）、复合视图
- 内置交互与组件：坐标轴、图例、Tooltip、标题等，以及筛选、缩放平移等交互行为
- 多渲染环境：Canvas、SVG、WebGL，以及基于 G 渲染引擎的扩展能力
- 完整 TypeScript 类型定义
- 扩展机制：自定义 mark、scale、transform、坐标系

**不覆盖**：

- 流程图、组织图、关系网络 / 拓扑图的绘制（属于 G6、X6 等工具的方向）
- 地理空间可视化（地图、轨迹、行政区划）
- 数据采集、数据清洗、统计分析——它只负责"把已有数据画出来"
- 服务端数据分析能力（它是前端可视化库，服务端出图需另配渲染方案）
- 后台任务、定时报表、邮件推送等业务编排

## 依赖条件

- 运行环境：浏览器（现代版本）；用 Node 侧渲染时需要有可用的无头渲染环境
- 前端工程：Node.js 与 npm / yarn 等包管理器（仅用于安装依赖与构建）
- 渲染上下文：图表必须挂载到一个存在且有实际宽高的 DOM 容器
- 版本约束：v3 / v4 / v5 语法不兼容，接入前必须确认目标大版本。npm `latest` 标签当前指向 5.x 系列，其余 dist-tag 与各版本对应关系以官方包页为准
- 可选扩展：3D、自动化可视分析等能力通过官方扩展包提供，需要额外安装

## 已知限制

1. 大版本之间 API 不兼容，跨大版本迁移不是改配置项能解决的，需要逐个图改造。
2. 官方 README 示例不一定跟随 npm latest 的大版本，照抄示例容易踩空。
3. 它是一个底层可视化引擎，常规图表要自己写语法声明；如果只想传配置项出图，基于它封装的图表库可能更省事。
4. 关系图 / 拓扑图不是它的目标场景，强行用它做会事倍功半。
5. 渲染性能与数据量、渲染器选择、动画与交互强度强相关，大数据量场景需要先做聚合或换渲染方案。
