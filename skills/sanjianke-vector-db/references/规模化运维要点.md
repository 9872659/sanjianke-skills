# 规模化运维要点：索引、过滤、混合检索、加载与健康检查

向量库从「本机一个文件」走到「集群扛住几十亿条」，用的还是同一套接口。
这份文档把规模化过程中**必须提前决定的事**集中列出来。

---

## 1. 第一块多米诺：embedding 模型与维度

```
GET /api/v1/models   →  挑 embedding 模型  →  记下输出维度  →  建集合时写这个维度
```

| 铁律 | 说明 |
|---|---|
| **维度创建后改不了** | 集合的向量维度是建的时候定死的，事后无法修改 |
| **换模型 = 重建集合** | 换 embedding 模型意味着维度或语义空间变了，必须重建集合、重新灌数据 |
| **维度必须与模型一致** | `dimension` 填错会在插入或检索时报维度不匹配 |
| **落到配置里** | 把模型名与维度写进配置文件，别散落在代码各处 |

验证维度只需要一次调用：

```bash
curl -sS -X POST "https://api.a7w.cn/api/v1/embeddings" \
  -H "Authorization: Bearer $A7W_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"<你挑的 embedding 模型名>","input":["维度自检"]}'
```

返回的 `data[0].embedding` 数组长度**就是** `dimension`。

## 2. 索引类型怎么选

| 索引 | 特点 | 适合 |
|---|---|---|
| **暴力检索（FLAT）** | 结果精确，扫描全量 | 数据量小、要求 100% 召回、或作为对照基线 |
| **图索引（HNSW 一类）** | 召回高、延迟低、内存占用较大 | **在线检索的默认选择** |
| **倒排/聚类索引（IVF 一类）** | 内存友好、可调精度 | 数据量大、内存有限 |
| **量化变体** | 用精度换内存，常见 2~8 倍压缩 | 内存吃紧、可接受少量召回损失 |
| **磁盘索引（DiskANN 一类）** | 向量放磁盘，内存占用小 | 超大规模、延迟要求不极端 |
| **mmap** | 索引文件映射到内存 | 冷数据、按需加载 |

**选择顺序建议**：先用图索引跑通；内存不够再上量化；规模再大一档考虑磁盘索引。
**每换一次都要用同一批查询做召回率对照**，不要凭感觉。

## 3. 元数据过滤与标量索引

向量与标量字段存在一起，才能真正做「**先过滤再检索**」：

```python
hits = client.search(
    collection_name="docs",
    data=query_vectors,
    limit=10,
    filter='tenant_id == "t-001" and ts >= 1700000000',   # 过滤条件按客户端语法写
    output_fields=["text", "subject", "ts"],
)
```

要点：

- **常用过滤字段单独建标量索引**，否则带过滤的检索会明显变慢。
- **先过滤再检索**比「检索完再过滤」快得多，也准得多 —— 后者会浪费 topK 名额。
- `output_fields` **只取你要用的字段**，别把向量本身拉回来，返回体会巨大。
- 范围检索（时间区间、数值区间）依赖标量索引，规划字段时一起想好。

## 4. 混合检索：稠密 + 稀疏

纯语义检索对**专有名词、编号、精确短语**不敏感，所以要叠一路关键词检索：

| 一路 | 负责 | 典型做法 |
|---|---|---|
| 稠密向量 | 「换个说法也能搜到」 | embedding 向量相似度 |
| 稀疏 / 全文 | 专有名词、编号、精确匹配 | BM25 一类关键词打分 |

**上线顺序**：

1. 先确认**两路单独都能召回**（各自跑一次，人工看结果）。
2. 再设融合权重（常见起手是各占一半，再按效果调）。
3. 需要更高精度时加一路**重排模型** —— 重排同样把 `base_url` 指向
   `https://api.a7w.cn/api/v1`、用同一把 Key，**模型名以 `/api/v1/models` 的返回为准**。

**多向量重排**（同一份内容的多路向量，比如标题向量 + 正文向量）适合
「标题很关键但正文很长」的场景。

## 5. 集合加载与健康检查

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 检索报错说集合没有加载 | 有些形态下集合需要**显式加载**才能被检索 | 先执行加载操作，再做 search |
| 重启后查询变慢或部分失败 | 集合需要重新加载进查询节点；大数据集加载本身就耗时 | 重启后显式加载并**等待加载完成**；生产用副本与健康检查兜住 |
| 以为容器起来了就能用 | 容器 `running` ≠ 服务 `healthy` | 打**健康检查端点**，确认状态是 healthy |

**上线自检的最低动作**：

```bash
# 1) 容器/服务状态
docker ps                       # 看状态列是 running 还是 healthy

# 2) 健康检查端点（端口按你的部署改）
curl -f http://localhost:9091/healthz

# 3) 业务自检：写入 1 条 → 检索 1 次 → 删掉
```

**把这三步写进部署脚本**，比任何文档都可靠。

## 6. 版本配对：客户端与服务端要成对升级

客户端与服务端是**分别发版**的，跨大版本混用会出现找不到方法、字段名对不上。

| 规则 | 说明 |
|---|---|
| 成对升级 | 升服务端就同步升客户端，别只升一边 |
| 记录版本矩阵 | 在部署文档里写清「服务端 X 配客户端 Y」 |
| 读 `client --help` | 拿不准某个参数名时，以客户端自身的帮助输出为准 |
| 升级前备份 | 服务端大版本升级前先备份数据卷 |

## 7. 多租户、副本与冷热分层

| 诉求 | 做法 |
|---|---|
| **多租户** | 用标量字段存 `tenant_id` 并在检索时过滤；数据量大时按租户分集合 |
| **副本容错** | 生产节点配副本，避免单点；配合健康检查做自动摘除 |
| **冷热分层** | 近期数据放内存/高速索引，历史数据降精度或落磁盘索引 |
| **限流与配额** | 按租户限制 QPS 与集合大小，避免一个租户拖垮整库 |
| **备份** | 明确数据卷在哪、多久备一次、怎么恢复；**恢复演练比备份本身更重要** |
| **监控** | 至少盯四件事：查询 P99 延迟、召回耗时、内存占用、集合加载状态 |

## 8. 接入 a7w 的两处配置（一句话版本）

```python
# ① embedding：base_url 指向网关，Key 用同一把
#    POST https://api.a7w.cn/api/v1/embeddings
#    {"model": "<从 /api/v1/models 挑的模型名>", "input": ["文本"]}

# ② 生成：检索到片段后回答
#    POST https://api.a7w.cn/api/v1/chat/completions
#    {"model": "DeepSeek-V4-Flash", "messages": [...], "temperature": 0.2,
#     "max_tokens": 800}
```

两处**共用一把 Key、一份账单**，检索侧不花钱、向量化与生成按 tokens 计点。
