# 三剪客 · 即时通讯服务端

当你需要在**自己的机器上**跑一套即时通讯服务，而不是继续按条数买云厂商的 IM 套餐时，这个 Skill 就是干这个的。它把「一台机器先跑起来」到「多节点扛住几十万连接」之间那些真正会踩的坑——长连接端口选型、消息不丢不重、离线补偿窗口、群扩散的 O(N²) 陷阱、集群节点 ID 与互斥——拆成可执行的检查项。

典型场景：给企业内部办公做私有化 IM、给 App 加一套自主可控的聊天底座、给已有业务系统加一个「人和人 / 人和服务」的消息管道。**不适用**于只想接个第三方 SDK 快速上线的场景。

## 快速开始

最小可用路径，四步验证「协议通不通」，不涉及业务二开。

**第 1 步 · 确认运行前提**

| 项 | 要求 |
|---|---|
| 运行时 | Java 8 兼容的 JRE（产物按 Java 8 字节码编译，高版本 JDK 建议用 release 8 编译） |
| 构建 | Maven 3.x；`mvn clean package` 产出打包件位于 `distribution/target/` |
| 数据存储 | 内置嵌入式库（零依赖，适合验证）或 MySQL；用 MySQL 时事务隔离级别需为 `READ-COMMITTED` |
| 内存 | 社区版单节点可低至 128MB 级别启动，验证环境给 512MB 更稳 |

**第 2 步 · 拿到软件包并解压**

源码方式：`mvn clean package` → 取 `distribution/target/` 下的 bundle 压缩包，解压得到 `bin` / `config` / `lib` 三类目录。发行包方式：直接用官方发布的压缩包或 deb/rpm 安装包。

**第 3 步 · 改三个必须先改的配置**

| 配置项 | 为什么必须改 |
|---|---|
| 对外服务 IP / 域名 | 客户端要先访问 HTTP 入口拿到长连接地址，填错客户端永远连不上 |
| 客户端 HTTP 入口端口 | 客户端侧通常硬编码，按你实际发布渠道填，别随意改 |
| 密钥类字段（管理密钥、token 签发密钥） | 默认值是公开示例值，上线前必须替换，否则可被伪造管理调用与 token |

**第 4 步 · 启动并验证**

```
# 打包件方式
./bin/<启动脚本>.sh

# 容器方式（端口按实际发布渠道映射）
docker run -d --name im-server \
  -v /srv/im/config:/opt/im-server/config \
  -v /srv/im/logs:/opt/im-server/logs \
  -p 80:80 -p 1883:1883 -p 8083:8083 -p 8084:8084 -p 18080:18080 \
  im-server
```

验证只需一条：

```
curl -v http://127.0.0.1/api/version
```

返回版本信息 JSON 即代表服务端进程与 HTTP 入口正常。**这一步不通，不要去调客户端。**

> 端口说明：`1883` 是原生客户端长连接端口；HTTP 短连接与管理接口各自独立端口。容器部署时挂载目录必须可写，否则内置库与日志写入失败会导致启动即退出。

## 能力边界

**覆盖**：

- 自建 IM 服务端的**架构与选型判断**：MQTT + Protobuf 组合的适用性、长连接与 HTTP 短连接的分工
- **单机与容器化部署**：环境前提、目录规划、端口规划、嵌入式库与 MySQL 二选一、systemd 托管
- **消息语义**：消息可靠性三要素（不丢 / 不重 / 有序）、离线补偿窗口、漫游开关、撤回时限、黑名单与禁言策略
- **水平扩展**：集群组建、节点 ID 唯一性、状态同步层选型、扩容与缩容顺序
- **运维与安全**：监控指标清单、日志排错路径、备份恢复、传输与存储加密、密钥轮换
- **可执行产物**：部署清单、配置模板、健康检查脚本、巡检脚本

**不覆盖**：

- 不包含任何上游项目的源代码，不提供其源码修改方案
- 不做业务逻辑开发（订单、审批、CRM 等业务系统对接属于你自己的服务职责）
- 不提供音视频媒体服务的部署方案（IM 只承载信令，媒体服务是独立子系统）

- 不承诺具体性能数字：并发能力取决于机器规格、消息大小、群规模与存储介质，必须实测

## 已知限制

- **群规模与性能不是线性关系**，而是接近平方级增长。社区版建议单群人数控制在数百量级；万人级大群需要专门的群组架构，不是调参能解决的。
- **历史消息有保存窗口**。默认会定期清理超期消息；需要长期留存必须先做转储，且转储方案要在上线前设计好，不能等清理跑完再补。
- **数据库隔离级别是硬要求**。MySQL 未设为 `READ-COMMITTED` 时会出现读写异常，这是配置项而非代码问题。
- **消息加密开关一旦开启不可回退**。开启后历史消息按密文读取，中途关闭会读到乱码，必须在上线前决定。
- **集群节点 ID 重复会直接导致数据错乱**，扩容时最容易犯这个错。
- **原生客户端的连接库针对国内网络环境做过优化**，但这不改变跨运营商链路本身的质量问题；跨网访问慢要先查链路，再查服务端。
- 版本跨度较大时升级需按版本说明逐步执行，存在数据库迁移脚本校验和不匹配的历史版本，跨版本升级务必先备份。

## 自检清单

上线前逐项打勾：

- [ ] 对外服务地址填的是**客户端能访问到**的地址（公网或内网，不是 `127.0.0.1`）
- [ ] 客户端 HTTP 入口端口与客户端硬编码一致
- [ ] 管理接口密钥、token 签发密钥**已从默认示例值替换**
- [ ] 管理接口的时间校验已按上线要求收紧
- [ ] `curl http://<host>/api/version` 返回 JSON
- [ ] 数据库隔离级别为 `READ-COMMITTED`（MySQL 路线）
- [ ] 消息加密开关已按最终策略固定，不再变更
- [ ] 历史消息保留策略与转储方案已确认
- [ ] 群最大人数已在数据库与配置两侧对齐
- [ ] 集群部署时每个节点的节点 ID 唯一
- [ ] 日志目录、数据目录、媒体目录均可写且已纳入磁盘告警
- [ ] 备份任务已跑通**并实际恢复验证过一次**
- [ ] 服务器文件句柄上限已上调（长连接服务的关键项）
- [ ] 客户端签名校验按发布渠道配置完毕
