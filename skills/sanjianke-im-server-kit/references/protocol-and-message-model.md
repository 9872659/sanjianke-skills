# 协议与消息模型：消息为什么不丢、不重、不乱序

> 本文是三剪客团队独立编写的实践总结，正文原创。文中配置项名称在不同发行版中可能不同，请以你实际部署版本的配置注释为准。

---

## 一、协议分层：为什么 IM 不用 HTTP 轮询

自建 IM 的协议栈通常是三层组合，理解这个分工才能定位问题：

| 层 | 承载 | 职责 |
|---|---|---|
| 长连接层 | 原生 TCP（常走 MQTT 语义） | 消息实时下发、心跳保活、上下线感知 |
| 传输编码层 | Protobuf | 二进制序列化，体积小、解析快、跨语言 |
| HTTP 短连接层 | REST | 登录换 token、换取长连接地址、管理接口、文件上传凭证 |

**为什么要 HTTP 短连接层**：长连接不适合做「请求-响应」式的配置获取和业务查询，也不适合被 CDN/网关缓存。所以客户端启动顺序是：先 HTTP 拿登录态与长连接参数 → 再建立长连接 → 之后消息全走长连接。

**MQTT + Protobuf 组合的价值**：

- 相比 JSON over WebSocket，同样的消息体积能压到 1/3 甚至更低（字段名不进包、整型用变长编码），流量与电量都省。
- MQTT 的 QoS 与保留消息语义天然适配「消息投递保证」的需求。
- 二进制协议对移动端弱网更友好，重连开销小。

**代价**：不可读、抓包难排错。**必须**在客户端和服务端两侧都保留一份协议定义（`.proto`）并纳入版本管理，否则一次字段变更就能让两端对不上，且无从 diff。

## 二、连接生命周期与心跳

```
客户端启动
  → HTTP: 登录 / 换 token
  → HTTP: 获取长连接地址与端口
  → TCP: 建立长连接
  → 鉴权（token 校验）
  → 上线通知（服务端广播/更新在线状态）
  → 心跳循环（固定间隔 PING/PONG）
  → [断线] → 指数退避重连 → 重新鉴权 → 拉取补偿消息
```

**心跳间隔怎么定**：必须**小于**链路上所有中间设备的空闲连接回收时间。移动网络下的 NAT 网关、运营商防火墙、负载均衡器各有自己的空闲超时（从几十秒到几分钟不等）。取链路中最小的那个超时值，再打对折。

**心跳间隔过大**的典型症状：用户手机锁屏几分钟后收不到消息，解锁后消息才「涌进来」——说明连接早被 NAT 回收了，而客户端还不知道。

**重连必须指数退避**：断线后立刻高频重连会把服务端打垮（尤其是在服务端重启时，几十万客户端同时重连——惊群）。退避策略要带随机抖动，避免所有客户端同步重连。

## 三、消息的可靠性三要素

### 3.1 不丢：三段链路的各自保证

一条消息从 A 到 B 要过三段，任何一段都可能丢：

| 段 | 可能丢的原因 | 保证手段 |
|---|---|---|
| 客户端 A → 服务端 | 网络抖动、进程被杀 | 客户端本地持久化 + 服务端 ACK；收到 ACK 才标记已发送 |
| 服务端内部 | 进程崩溃、落盘前宕机 | 先持久化再投递（或同步落盘），返回 ACK 的语义是「已可靠接收」 |
| 服务端 → 客户端 B | B 离线、连接断开 | 服务端保存待投递消息 + 离线推送 + B 上线后补偿拉取 |

**关键设计原则**：**ACK 的语义必须是「已可靠接收」，而不是「已收到」**。如果服务端在落盘前就 ACK，宕机就丢消息，而客户端以为发送成功了。

### 3.2 不重：去重靠客户端，不靠网络

网络层无法保证 exactly-once。工程上都是 **at-least-once 投递 + 客户端幂等去重**：

- 每条消息携带**全局唯一的消息 ID**（服务端生成，不是客户端生成，避免多端冲突）。
- 客户端维护一个「已处理消息 ID」的滑动窗口（或按会话维护最大序号）。
- 收到重复 ID 直接丢弃并回 ACK，不再触发 UI 更新。

**为什么 ID 必须服务端生成**：多端同时在线时，客户端生成的 ID 会冲突；服务端生成能保证全局唯一且有序可比较。

**对象 ID 建议用 UUID 而非短 ID**：短 ID 位数少、连续可枚举，攻击者能通过遍历 ID 探测用户/群组是否存在。用 UUID 虽然长，但换来不可枚举。

### 3.3 不乱序：用序号而非时间戳

**绝对不要用客户端时间戳排序**。理由：多端时钟不同步；服务端收到顺序与客户端发送顺序可能不一致。

正确做法：**会话内单调递增序号**。

- 服务端为每个会话（单聊 / 群聊 / 聊天室）维护一个自增序号。
- 消息按序号落库并按序号投递。
- 客户端按序号排序；发现**序号跳号**（收到 5 和 7，缺 6）就主动向服务端拉取缺失区间的消息。

**序号跳号是客户端发现丢消息的唯一可靠信号**。没有序号机制的 IM，丢消息只能靠用户反馈。

## 四、离线消息与补偿窗口

### 4.1 三种补偿策略

| 策略 | 行为 | 适用 |
|---|---|---|
| 只补时限内 | 上线只收最近 N 毫秒内未收的消息 | 默认策略，省带宽省内存 |
| 按条数漫游 | 上线同步最近 M 条历史消息 | 办公 IM，需要看到近期上下文 |
| 按会话远程拉取 | 本地读完可继续从服务端下拉该会话历史 | 需要长期会话记录 |

这三者**不是互斥的**，可以组合。配置时的核心权衡：

- 补偿时限越长、条数越多 → 上线瞬间的流量峰值越高、内存占用越大。
- 服务端为每个用户缓存的待投递队列有上限。队列越大，拉取越慢、内存越吃紧；队列越小，长时间离线用户可能丢消息。
- **队列上限必须大于「补偿时限内的最大消息量」**，否则补偿逻辑本身会丢消息。这两个参数要一起调，不能只调一个。

### 4.2 上线补偿的时序陷阱

```
客户端上线
  → 拉取补偿消息 (起点 = 本地最大序号)
  → 建立长连接，开始接收实时消息
```

**如果顺序反了**（先建连接再拉历史），会出现「实时消息已收到，历史消息才拉到」的乱序；更糟的是历史消息里可能包含刚才实时收到的同一条，产生重复。正确做法：

1. 先建立长连接但**暂停 UI 投递**，或在拉取期间把实时消息暂存。
2. 拉取补偿消息并合并去重。
3. 按序号统一排序后一次性提交 UI。

### 4.3 离线推送

用户离线时的通知走独立推送通道（厂商推送或自建推送服务）。要点：

- 推送**只做提醒，不承载消息内容**。用户点开推送后仍从 IM 服务端拉取真实消息，避免推送通道成为消息的第二个副本。
- 推送要有**过期时间**（例如 7 天），长期离线用户的堆积推送没意义，还会浪费推送配额。
- 多端在线时的推送抑制：手机端在线则 PC 端不再推送，反之亦然。这个策略要做成可配置项，因为不同产品的预期不同。

## 五、会话与群扩散模型

### 5.1 单聊

简单：消息落一份，投递给接收方在线连接；离线则入待投递队列。

### 5.2 群聊：O(N) 还是 O(N²)

这是自建 IM **最容易低估的地方**。

- 朴素模型：一条群消息产生 N 条收件箱记录（N = 群成员数），复杂度 O(N)。
- 实际开销：还要叠加**已读回执、成员状态同步、群操作通知**，这些都会随 N 放大。加上客户端侧的成员列表更新与 UI 重绘，实测接近 **O(N²)**。

**结论**：群人数不能线性外推。

| 群规模 | 工程做法 |
|---|---|
| 数百人（普通群） | 逐条扩散可行，这是社区版舒适区 |
| 数千人 | 需要优化扩散路径，客户端要支持增量成员同步 |
| 万人以上 | 必须换成专门的群组架构（读扩散 / 写扩散权衡 + 独立存储），不是调参能解决 |

**写扩散 vs 读扩散**：

- **写扩散**（发消息时写入每个成员收件箱）：读快写慢，适合小群。
- **读扩散**（只写一份，成员各自按游标读）：写快读慢，适合超大群。
- 超大群通常用**读扩散 + 分层缓存**，并单独存储成员列表以支持增量拉取。

### 5.3 聊天室

与群组的本质区别：**聊天室成员不进通讯录、消息不做持久漫游为主、成员规模可极大**。设计上：

- 成员关系是**临时**的，上下线即增删，不写主存储。
- 支持拉取远程历史作为可选项。
- 在线状态与成员列表放**内存/缓存**层，不落库。

## 六、消息类型与行为策略

### 6.1 系统消息 vs 用户消息

**消息类型编号空间**要提前规划并写进协议文档。核心原则：

- **高权限消息类型禁止客户端发送**，只允许服务端下发（例如账户变动、余额变动、系统指令）。否则客户端可以伪造系统消息，这是严重安全漏洞。
- 列表做成**服务端配置项**而非硬编码，方便运营期调整。

### 6.2 撤回

| 参数 | 含义 | 注意事项 |
|---|---|---|
| 撤回时限 | 用户可撤回自己消息的时间窗 | `0` = 禁止撤回；负值 = 无限制；单位通常是秒 |
| 管理特权 | 群主/管理员撤回他人消息 | 通常不受时限约束；但管理员撤回**自己的**消息仍受时限约束 |
| 服务端特权 | 服务端 API 撤回 | 不受时限约束，用于合规场景 |

改撤回时限**必须同步改客户端 UI**：客户端有「是否显示撤回入口」的逻辑，服务端放宽而客户端没改，用户看不到入口；服务端收紧而客户端没改，用户点了报错。

### 6.3 已读回执

- **单聊已读**：接收方上报已读序号，发送方按序号判断。
- **群聊已读**：只上报**序号**，不上报逐条状态。群主查看已读人数时，用「成员已读序号 ≥ 消息序号」来判定，避免 N×M 的状态爆炸。
- 已读回执要能**单独开关**，办公场景需要，社交场景可能不需要且耗电。

### 6.4 黑名单与禁言

| 策略 | 取值 | 影响 |
|---|---|---|
| 黑名单策略 | 发送失败返回错误码 / 发送成功但服务端丢弃 | 前者体验明确，后者对发送方静默 |
| 拉黑后单向还是双向 | 通常单向（你拉黑他，你仍能发给他） | 双向会让用户困惑 |
| 禁言例外类型 | 白名单消息类型 | **必须包含音视频信令等被动响应类消息**，否则被禁言用户连来电都无法接听 |

**禁言例外是高频遗漏项**：禁言一个人之后，他接不到别人的音视频通话，因为信令消息被拦了。上线前务必验证。

## 七、传输与存储加密

| 层面 | 做法 | 注意 |
|---|---|---|
| 传输 | 长连接 AES 加密（密钥协商后对称加密） | 加密强度要**客户端与服务端同时开启**，单边开启直接连不上 |
| 传输（Web） | WSS / TLS | 公网部署必须，证书用可信 CA |
| 客户端本地库 | SQLCipher 等整库加密 | 设备丢失时保护历史消息 |
| 服务端消息内容 | 数据库内加密存储 | **开关一旦开启不可回退**：历史明文与新密文混存会导致读取混乱，必须上线前决定 |
| 服务端搜索 | 关闭服务端全文搜索以避免明文索引 | 与上一条配套；关闭后无法做服务端消息检索 |

**国密/国产化要求**：涉及密评的场景，加密算法与密码模块有明确清单要求，需要与密码厂商和测评机构确认，不能靠改一个开关满足。

## 八、多端同步

现代 IM 要求移动端、PC 端、Web 端、小程序端可能同时在线，且状态同步。要处理：

1. **同一账号多端**：服务端维护「账号 → 在线连接集合」，一条消息投递到该账号的**所有在线端**（或按策略只投部分端）。
2. **已读同步**：A 端读了，B 端未读红点要消失 → 已读上报后服务端**反向同步**到该账号其它端。
3. **撤回同步**：撤回事件同样要同步到所有端。
4. **一方发消息，其它端会话列表要更新**：需要「已发送消息同步」机制，通过该账号的其它在线连接下发。

**协议必须预留「多端同步」的消息类型**。如果协议最初没设计，后期加会让客户端改得很难受。

## 九、本章自检清单

- [ ] 协议定义（`.proto` 等）已纳入版本管理，两端引用同一版本
- [ ] 心跳间隔小于链路上最短的空闲回收超时
- [ ] 重连为指数退避 + 随机抖动
- [ ] 消息 ID 由服务端生成，全局唯一
- [ ] 每个会话有单调递增序号，客户端有跳号检测与补拉逻辑
- [ ] ACK 语义是「已持久化」，落盘先于 ACK
- [ ] 待投递队列上限 > 补偿时限内最大消息量
- [ ] 上线补偿顺序正确（先拉历史再放行实时 UI 投递）
- [ ] 推送不承载消息正文，且有过期时间
- [ ] 高权限消息类型禁止客户端发送
- [ ] 禁言例外类型包含被动响应类消息（音视频信令等）
- [ ] 撤回时限变更已同步客户端 UI
- [ ] 消息内容加密开关已按最终策略固定
- [ ] 多端同步的消息类型已定义并验证
