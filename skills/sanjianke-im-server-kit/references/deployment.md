# 部署：把一套自建 IM 服务端跑起来

> 本文是三剪客团队独立编写的实践总结，正文原创。所有命令与配置项均为通用工程做法，具体默认值以你所部署的发行版本文档为准。

---

## 一、先做形态选型，别急着装

自建 IM 的部署形态由**规模**和**合规要求**共同决定，不是由技术偏好决定。

| 形态 | 适用规模 | 优点 | 代价 |
|---|---|---|---|
| 单机 + 嵌入式库 | 验证、演示、几十到几百人内部群 | 零外部依赖，一条命令起，备份就是拷目录 | 无高可用；数据库随进程，迁移受限 |
| 单机 + 独立 MySQL | 数百到数千活跃用户 | 数据独立可控，能单独备份与调优 | 多一个组件要运维；仍是单点 |
| 多节点集群 + MySQL | 万级以上在线、要求可用性 | 可扩容、可滚动升级 | 需要状态同步层；节点管理有额外约束 |
| 容器化（以上任意形态） | 需要快速复现环境、批量交付 | 环境一致、回滚快、易做多实例 | 卷与网络要规划；镜像分层别塞密钥 |

**决策顺序**：

1. 先问「离线容忍多久」。容忍分钟级 → 单机够用；要求秒级 → 必须集群。
2. 再问「数据留多久、要不要等保」。要 → MySQL/独立库 + 加密 + 审计日志。
3. 最后问「会不会涨到十万连接」。会 → 从第一天就按集群规划目录、端口、节点 ID 命名。

## 二、端口与目录规划（部署前必须定死）

### 端口

自建 IM 服务端通常同时暴露四类端口，职责不同，**不能混用**：

| 端口用途 | 典型值 | 谁访问 | 说明 |
|---|---|---|---|
| 客户端 HTTP 入口 | 80 | 客户端、浏览器 | 客户端从这里换取长连接地址，**客户端侧常硬编码，不要随意改** |
| 原生长连接 | 1883 | 客户端 | MQTT 系长连接入口，TCP 常驻 |
| WebSocket 长连接 | 8083 | Web 客户端 | 浏览器无法裸 TCP，需要 WS 承载同一协议 |
| WebSocket 加密 | 8084 | Web 客户端 | TLS 版本，公网部署必须开 |
| 管理接口 | 18080 | 你的后台/应用服务 | **绝对不要暴露到公网**，至少加白名单 |

**防火墙最小化原则**：对公网只放行 80 / 1883 / 8083 / 8084；18080 只对运维网段或本机开放。管理接口一旦暴露，等于把用户体系交给了扫描器。

### 目录

统一放在一个前缀下（例如 `/opt/im-server`），便于整体备份与迁移：

```
/opt/im-server/
  bin/          启动脚本
  config/       配置文件（含日志配置）
  lib/          依赖 jar
  logs/         运行日志
  h2db/         嵌入式库数据目录（用 MySQL 时不存在）
  media/        内置对象存储数据目录（用外部对象存储时不存在）
```

**权限要求**：`logs/`、`h2db/`、`media/` 必须对运行用户可写。容器部署时这三个目录是**必须挂载**的卷——不挂载会导致容器内写失败、进程启动即退出，且日志随容器销毁，问题无法复盘。

## 三、两条落地路线

### 路线 A：源码编译（可裁剪、可审计）

```bash
# 前提：JDK 8 兼容 + Maven 3.x
mvn clean package
# 产物：distribution/target/ 下的 bundle 压缩包
```

要点：

- 上游产物按 **Java 8 字节码**编译。用 JDK 9+ 构建时，务必让编译器以 release 8 为目标，否则可能链接到高版本 JDK 的 API，产物在 Java 8 运行时报 `NoSuchMethodError`。
- 构建过程会做代码规范检查，规范不通过会**失败而非警告**，这是有意设计。
- 想把依赖仓库换成内网镜像，在 Maven `settings.xml` 里配 mirror，不要改 pom。

### 路线 B：发行包 / 系统包（推荐生产）

发行包提供三种安装形态，按你的运维习惯选：

| 形态 | 安装方式 | 配置文件位置 | 日志位置 |
|---|---|---|---|
| tar 包（手动） | 解压到 `/opt/im-server` | `/opt/im-server/config/` | `/opt/im-server/logs/` |
| deb（Debian/Ubuntu） | `apt install ./im-server.deb` | `/etc/im-server/config/` | `/var/log/im-server/` |
| rpm（RHEL/CentOS） | `yum install ./im-server.rpm` | `/etc/im-server/config/` | `/var/log/im-server/` |

**关键坑**：用 `dpkg -i` 而不是 `apt install ./`，依赖**不会**被自动安装，服务起不来。本地安装必须带 `./` 前缀。

**systemd 托管**（生产必做）：

```bash
sudo cp systemd/im-server.service /usr/lib/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now im-server
sudo systemctl status im-server
journalctl -f -u im-server        # 看控制台日志
```

单元文件里两个设置对长连接服务至关重要，别删：

- `LimitNOFILE=65536` —— 一个连接占一个文件句柄，默认 1024 会在几百连接时就开始拒绝。
- `TimeoutStopSec=infinity` + `SendSIGKILL=no` —— 优雅停机，让服务端把内存中的会话与未落盘消息刷完，别被 systemd 强杀。

**调 JVM 内存**：改 `bin/` 下启动脚本里的 `-Xmx` / `-Xms`，不要只改环境变量就以为生效。容器部署则通过 `JVM_XMX` / `JVM_XMS` 环境变量传入。

## 四、容器化部署

```bash
# 1. 先编译出软件包，拷到 docker 构建上下文
mvn clean package
cp distribution/target/*bundle*.tar.gz docker/

# 2. 构建镜像
cd docker && docker build -t im-server .

# 3. 准备可写目录
mkdir -p /srv/im/{config,logs,h2db,media}

# 4. 运行
docker run -d --name im-server --restart always \
  -v /srv/im/config:/opt/im-server/config \
  -v /srv/im/logs:/opt/im-server/logs \
  -v /srv/im/h2db:/opt/im-server/h2db \
  -v /srv/im/media:/opt/im-server/media \
  -e JVM_XMX=512M -e JVM_XMS=512M \
  -p 80:80 -p 1883:1883 -p 8083:8083 -p 8084:8084 \
  im-server
```

配置目录**必须显式挂载并指定**，容器内的默认配置是调试用配置，直接用于生产会带着示例密钥上线。

用外部 MySQL 时，`h2db` 卷可以不挂；用外部对象存储时，`media` 卷可以不挂——但**都要在配置里显式指向外部服务**，否则服务会尝试写本地目录。

**离线交付**（内网环境）：

```bash
docker save -o im-server.tar im-server     # 在有网机器导出
docker load -i im-server.tar               # 在目标机器导入
```

## 五、数据库选择与调优

| 项 | 嵌入式库 | MySQL |
|---|---|---|
| 事务隔离级别 | 默认即可 | **必须 `READ-COMMITTED`** |
| 设置方式 | — | `set global transaction_isolation='read-committed';` 并写入 my.cnf 持久化 |
| 备份方式 | 停服拷目录 / 在线快照 | `mysqldump` 或物理备份 |
| 适用 | 验证、小规模 | 生产 |

**隔离级别是硬门槛**。默认的 `REPEATABLE-READ` 会让消息读取出现非预期结果（读到旧快照），表现为「消息明明发了却查不到」。这不是 bug，是配置没改。

**连接池**：服务端用连接池访问数据库，池大小要和 MySQL 的 `max_connections` 匹配。多节点集群时按「节点数 × 单节点池大小」核算总量，别把数据库连接打满。

**历史消息清理**：服务端有自动清理开关，会周期性扫描消息表删除超期数据。上线前必须决定：

- 保留期内不需要长期留存 → 开启自动清理，省空间。
- 需要长期留存 → **先建转储任务再开清理**，并确认清理逻辑不会在转储完成前删掉数据。
- 用支持 TTL 的文档型存储时，过期由存储层负责，服务端开关不生效。

## 六、首次启动排错路径

按顺序排查，**不要跳步**：

```
1. 进程在不在？
   ps -ef | grep -i im-server
   → 不在：看 journalctl -f -u im-server 或 logs/ 下的启动日志

2. Java 版本对不对？
   java -version   → 必须能看到 8 兼容版本
   → 报 UnsupportedClassVersionError = JDK 版本不匹配
   → 报 NoSuchMethodError = 用了高版本 API，重新以 release 8 编译

3. 本地 HTTP 通不通？
   curl -v http://127.0.0.1/api/version
   → 通 = 服务端 OK，问题在客户端侧或网络侧
   → 不通 = 往下查

4. 端口在听吗？
   ss -lntp | grep -E ':(80|1883|8083|8084|18080)\b'
   → 没有 = 配置里的端口绑定失败，或被别的进程占用

5. 目录可写吗？
   sudo -u <运行用户> touch /opt/im-server/logs/.t
   → 失败 = 权限问题，容器场景多为卷未挂载

6. 数据库连得上吗？
   看日志里的 JDBC 异常；MySQL 场景先验证隔离级别与账号权限
```

**高频故障对照**：

| 现象 | 根因 | 处理 |
|---|---|---|
| 启动后立刻退出，日志为空 | 数据/日志目录不可写，进程在初始化阶段就挂了 | 修目录权限或补挂载卷 |
| `curl /api/version` 通，客户端连不上 | 对外服务地址填成了内网/`127.0.0.1` | 改成客户端可达地址并重启 |
| 客户端能连但总断线 | 反向代理未透传长连接、或代理超时太短 | 代理改为 TCP 透传 / 调长空闲超时 |
| 升级后启动报数据库迁移校验错误 | 历史版本改动过迁移脚本，校验和不匹配 | 按版本说明执行修复脚本，再启动 |
| 管理接口调用 401/签名失败 | 管理密钥未替换，或时间校验策略与调用方不一致 | 统一密钥与时间校验策略 |
| 几百个连接后新连接被拒 | 文件句柄上限未调 | 上调 `LimitNOFILE`（systemd 单元或 `ulimit`） |

## 七、容量估算方法（不给拍脑袋数字）

并发能力由四个变量决定，任何声称「一台机器扛 X 万」而不给条件的说法都不可信：

| 变量 | 影响 |
|---|---|
| 在线连接数 | 决定内存与文件句柄下限，每连接常驻内存 × N |
| 消息吞吐（条/秒） | 决定 CPU 与数据库写入压力 |
| 群规模 | 决定单条消息的扩散倍数，呈平方级放大 |
| 消息与媒体体积 | 决定磁盘 IO 与网络带宽 |

**估算步骤**：

1. 压测出**单节点**在目标消息大小下的稳定 QPS 与在线连接上限，留 30% 余量。
2. 用「峰值同时在线 ÷ 单节点上限」得出节点数下限。
3. 用「峰值消息速率 × 平均扩散倍数 ÷ 单节点 QPS」再算一次，取两者较大值。
4. 加一个节点做冗余（滚动升级、宕机接管）。

**只有压测数字才是数字。** 上线前至少在接近生产规格的机器上跑一次真实场景压测，别用开发机数据做容量规划。
