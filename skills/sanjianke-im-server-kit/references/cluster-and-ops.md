# 集群与运维：从单节点到多节点，以及日常该盯什么

> 本文是三剪客团队独立编写的实践总结，正文原创。文中不包含任何上游项目源代码；具体配置项名称以你实际部署版本为准。

---

## 一、什么时候必须上集群

不要为了「架构好看」上集群。集群带来状态同步复杂度、节点管理约束和排错难度，这些都是实打实的成本。

**满足以下任一条就该上集群**：

| 触发条件 | 原因 |
|---|---|
| 单节点在线连接数接近压测上限 | 长连接是内存与文件句柄密集型，单机有天花板 |
| 停服维护不可接受 | 单节点升级/重启即全量掉线，客户端集体重连 |
| 要求机房级容灾 | 需要多节点跨可用区部署 |
| 需要滚动升级 | 只有多节点才能「一次升一个，其余继续服务」 |
| 单机磁盘/内存成本已不经济 | 纵向扩容到顶，只能横向扩 |

**不满足就别上**：几百人内部办公 IM 用单机 + 可靠备份，可用性远高于一个配错了的集群。

## 二、集群的组成与状态同步层

集群版和单机版的差别只在一处：**多个服务节点如何共享「谁在线、在哪台机器上」的状态**。

```
        ┌──────────── 负载入口（TCP 透传 / 4 层）────────────┐
        │                                                    │
   ┌────▼─────┐        ┌──────────┐        ┌──────────┐
   │ 节点 1   │◄──────►│ 节点 2   │◄──────►│ 节点 3   │
   │ node_id=1│  状态  │ node_id=2│  同步  │ node_id=3│
   └────┬─────┘  同步层 └────┬─────┘        └────┬─────┘
        │                    │                    │
        └────────────────────┼────────────────────┘
                             │
                    ┌────────▼────────┐
                    │  共享数据库      │
                    │ (MySQL 主从)     │
                    └─────────────────┘
```

**状态同步层**承担三类数据：

| 数据 | 说明 | 一致性要求 |
|---|---|---|
| 在线会话路由 | 用户 → 所在节点 / 连接标识 | 强一致（决定消息能否投到） |
| 群成员缓存 | 群 → 成员列表 | 最终一致（可容忍秒级延迟） |
| 聊天室成员 | 聊天室 → 当前在线成员 | 弱一致（丢了会自愈，因为会重连） |

### 组建方式

状态同步层通常支持两种节点发现方式：

- **组播（multicast）**：开箱即用，但**云环境基本不可用**——VPC 普遍禁组播。所以生产配置里组播一般是**关闭**的。
- **TCP/IP 成员列表**：显式列出所有节点地址，**生产推荐**。云上、跨机房、容器网络都可靠。

**上线前必须确认的事**：组播已关闭且成员列表已填全。如果组播没关而环境又不支持，节点会各自为政——**每个节点都以为自己是集群里唯一的一员**，表现为「同一账号在两台机器登录互相看不见」「群消息只投给本节点用户」。这是最隐蔽的集群故障，因为每个节点自身日志都正常。

### node_id 的硬约束

**每个节点的 `node_id` 必须全局唯一，且重启后保持不变。**

- 重复的 `node_id` 会导致状态同步层把两个节点当成同一个，路由表错乱、消息投错节点。
- 扩容时最容易犯这个错：从镜像/模板克隆虚拟机，忘了改 `node_id`。
- 建议做法：把 `node_id` 与主机名/编排序号绑定，在部署流程里自动生成，而不是人工填。

## 三、负载均衡：4 层透传，不要 7 层终止

长连接对负载均衡的要求与 HTTP 完全不同。

| 要求 | 原因 |
|---|---|
| **TCP 层透传（L4）** | 长连接需要保持会话粘性；7 层终止会打断连接的长期存活 |
| 空闲超时**大于**客户端心跳间隔 | 否则代理会在客户端心跳到达前就断开连接，表现为规律性掉线 |
| 会话保持 | 同一连接必须固定到一台节点 |
| 健康检查走 HTTP 管理端口 | 用 `/api/version` 判断节点是否真的可用 |

**7 层代理的陷阱**：如果必须在 7 层做 WebSocket 转发，务必：

- 显式开启 `Upgrade` / `Connection` 头透传。
- 把 `proxy_read_timeout` 调到远大于心跳间隔。
- 关闭代理侧的缓冲（buffering）。

**代理超时 vs 心跳的配合**（最常见的掉线根因）：

```
代理空闲超时 (例如 60s)  >  客户端心跳间隔 (例如 30s)   ✅ 安全
代理空闲超时 (例如 30s)  <  客户端心跳间隔 (例如 60s)   ❌ 规律掉线
```

## 四、横向扩展与缩容

### 扩容步骤

```
1. 准备新节点：安装相同版本、相同配置模板
2. 分配唯一 node_id（关键！）
3. 配置状态同步层成员列表，加入新节点地址
4. 把新节点地址加入所有存量节点的成员列表（滚动更新）
5. 启动新节点，确认它加入了集群（看日志中的成员列表 / 集群规模）
6. 把新节点挂到负载入口
7. 观察：连接数是否被均摊、跨节点消息投递是否正常
```

**第 4 步是必须的**：只在新节点上配成员列表，存量节点不认识它。成员发现只有单向是不够的（除非用动态发现机制）。

### 缩容 / 下线步骤（顺序不能反）

```
1. 从负载入口摘除该节点（先停止新连接进来）
2. 等待存量连接自然迁移（或主动踢线让客户端重连到其它节点）
3. 确认该节点连接数归零、待投递队列已清空
4. 停止节点进程
5. 从其余节点的成员列表中移除该节点地址
6. 观察集群是否恢复正常规模
```

**直接 kill 进程会丢数据**：内存中的待投递消息与未落盘状态会丢失，用户表现为「消息发了对方没收到」。**永远先摘流量再停进程**。

### 滚动升级

多节点最大的价值就是这个。顺序：

```
摘流量 → 停节点 → 升级 → 起节点 → 验证 → 挂回流量 → 下一个节点
```

每次只动一个节点，**至少保留一个节点在线**。升级前确认数据库迁移脚本是**向前兼容**的——如果新版本改了表结构而旧版本节点还在跑，旧节点会立刻报错。如果不兼容，只能停服升级。

## 五、监控：该盯哪些指标

分四层，缺一层就会在故障时抓瞎。

### 5.1 连接层

| 指标 | 告警阈值建议 | 说明 |
|---|---|---|
| 当前在线连接数 | 接近压测上限的 70% | 核心容量指标 |
| 连接建立速率 | 突增（远高于日常峰值） | 可能是重连风暴 |
| 连接断开速率 | 突增 | 可能是节点故障或代理问题 |
| 鉴权失败率 | > 1% | 可能是密钥配错或被攻击 |
| 文件句柄使用率 | > 70% | 长连接服务的隐形瓶颈 |

### 5.2 消息层

| 指标 | 说明 |
|---|---|
| 消息入队速率 / 投递速率 | 两者持续背离 = 消费能力不足 |
| **待投递队列深度** | 最重要的指标。持续增长 = 消费者跟不上或某节点挂了 |
| 消息投递延迟（P50/P95/P99） | 看 P99，平均值会掩盖长尾 |
| 消息失败率 | 投递失败 / 总数 |
| 离线推送成功率 | 推送通道是否健康 |

### 5.3 存储层

| 指标 | 说明 |
|---|---|
| 数据库连接池使用率 | 接近 100% 会阻塞 |
| 慢查询数 | 消息表查询变慢会连锁影响投递 |
| 磁盘使用率与增长速率 | 消息表增长速率决定扩容提前量 |
| 磁盘 IO 等待 | 落盘变慢 → ACK 变慢 → 客户端体感卡 |
| 主从延迟（集群） | 延迟过大时读到旧数据 |

### 5.4 集群层

| 指标 | 说明 |
|---|---|
| 集群成员数 | **偏离预期值立即告警**。少一个可能是节点挂了，多一个可能是 node_id 重复 |
| 各节点连接数分布 | 严重不均 → 负载入口的会话保持有问题 |
| 节点间通信延迟 | 跨机房部署时关键 |
| 状态同步层内存占用 | 它的数据全在内存，会 OOM |

**集群成员数是必须配的告警项**：它能在用户投诉之前发现节点掉线，也能发现 node_id 重复这类隐蔽故障。

## 六、备份与恢复

### 备份策略

| 对象 | 方式 | 频率 |
|---|---|---|
| 数据库 | 逻辑备份（`mysqldump`）或物理备份 | 每日全量 + 增量/ binlog |
| 配置文件 | 纳入版本管理或单独归档 | 每次变更 |
| 媒体文件 | 对象存储自身版本化 + 跨区复制 | 持续 |
| 证书与密钥 | 加密归档，访问受控 | 每次轮换 |

**配置文件一定要单独备份**：里面有关键密钥（管理密钥、token 签发密钥）。丢了密钥，已签发的 token 全部失效，所有用户需重新登录。

### 恢复演练（比备份本身更重要）

**没有验证过恢复的备份等于没有备份。** 恢复演练流程：

```
1. 在隔离环境准备一台机器
2. 用最近的备份 + binlog 恢复到目标时间点
3. 启动服务端，确认 /api/version 正常
4. 用测试账号登录，验证能拉到历史消息
5. 记录恢复耗时（这是你的 RTO 真实值）
```

**必须记录两个数字**：

- **RPO**（能容忍丢多少数据）→ 由备份频率和 binlog 决定
- **RTO**（多久能恢复）→ 由恢复演练实测决定

没有实测过 RTO 的「高可用方案」只是文档。

### 数据库迁移的备份纪律

**任何版本升级前先做一次全量备份。** 理由：迁移脚本可能失败，而部分迁移是**不可逆**的（改表结构、改数据）。迁移失败后回滚代码不等于回滚数据。

遇到迁移校验和不匹配错误时，说明历史上有人改动过迁移脚本。处理方式是按该版本的说明执行修复语句修正校验和，**不要**手工删除迁移历史表记录——那会让后续迁移全部错乱。

## 七、安全加固

按「攻击面」逐层收紧：

### 7.1 管理接口

| 措施 | 说明 |
|---|---|
| **绝不暴露公网** | 只对本机或运维网段开放，安全组层面限制 |
| 替换默认密钥 | 默认示例值是公开的，不改等于没有鉴权 |
| 开启时间校验 | 签名带时间戳校验，防重放；关掉时间校验会让固定签名永久有效 |
| 调用来源白名单 | 应用服务、后台系统的出口 IP 加白 |
| 独立域账号 | 管理调用用专门账号，便于审计 |

### 7.2 token 与身份

| 措施 | 说明 |
|---|---|
| 替换 token 签发密钥 | 出厂默认值必须改，改了之后旧 token 失效 |
| 设置 token 有效期 | 默认可能无限期。**如果设了有效期，客户端必须实现过期处理**，否则会出现「用着用着突然登不上」 |
| 客户端签名校验 | 移动端校验应用签名，防止第三方客户端冒用你的服务端 |
| 拒绝空签名 | 全部客户端升级完成后改为拒绝，兼容期可先放宽 |

**并发登录策略**要明确：是否允许同账号多端同时在线的上限。不设限会让账号共享变得容易。

### 7.3 消息与数据

| 措施 | 说明 |
|---|---|
| 传输加密 | 长连接 AES + Web 端 WSS |
| 内容加密强度 | 客户端与服务端**同时**开启，单边开会连不上 |
| 本地库加密 | 客户端整库加密，防设备丢失泄露 |
| 敏感词与合规 | 服务端敏感词库、消息留存、审计导出，按属地监管要求配置 |
| 消息留存策略 | 与合规要求对齐，注意自动清理开关会删数据 |

### 7.4 主机与网络

| 措施 | 说明 |
|---|---|
| 最小放行 | 只开放必要端口；管理端口不对公网 |
| 运行用户降权 | 不要用 root 跑服务进程 |
| 文件权限 | 配置文件 `chmod 600`，包含密钥的目录单独控制 |
| 日志脱敏 | 日志里不要打印完整 token、手机号、消息正文 |
| 依赖漏洞扫描 | 定期扫依赖库 CVE，及时升级 |

### 7.5 密钥轮换

**密钥轮换要有序**，否则会引发大规模掉线：

```
1. 确认新密钥已下发到所有需要它的服务（应用服务、后台）
2. 双密钥并行期（如果系统支持）
3. 切换签发密钥
4. 已签发 token 的失效影响评估：是否强制所有用户重新登录？
5. 在低峰期执行
```

token 签发密钥轮换 = **所有已发 token 失效** = 全体用户重新登录。这个动作必须在低峰期、并且提前通知。

## 八、故障排查决策树

### 8.1 全体用户掉线

```
全体掉线
├─ 所有节点同时掉线？
│   ├─ 是 → 查共享依赖：数据库挂了？状态同步层挂了？负载入口挂了？
│   └─ 否 → 查到具体节点
├─ 数据库连不上？
│   ├─ 连接池打满 → 查慢查询、连接泄漏
│   └─ 主库宕机 → 切从库
├─ 状态同步层失联？
│   ├─ 组播没关且环境不支持 → 改 TCP 成员列表
│   └─ 网络分区 → 查节点间连通性
└─ 负载入口故障 → 查代理配置与健康检查
```

### 8.2 部分用户掉线

```
部分用户掉线
├─ 集中在某个地域/运营商？ → 跨运营商链路问题，与 IM 服务端无关，查网络
├─ 集中在某个客户端版本？ → 客户端 bug 或心跳间隔配置差异
├─ 集中在某台节点？ → 该节点故障或代理到该节点异常
├─ 规律性掉线（固定间隔）？ → 代理空闲超时 < 心跳间隔，调代理超时
└─ 移动端锁屏后掉线？ → NAT 回收，缩短心跳或启用推送唤醒
```

### 8.3 消息收不到

```
消息收不到
├─ 发送方 ACK 成功？
│   ├─ 否 → 发送方网络问题，或服务端未正确 ACK
│   └─ 是 → 服务端已收
├─ 接收方在线？
│   ├─ 在线但收不到 → 路由表错乱（node_id 重复？状态同步层数据陈旧？）
│   └─ 离线 → 查待投递队列、离线推送
├─ 补偿逻辑生效？
│   ├─ 队列上限 < 离线期间消息量 → 队列溢出丢消息，调大队列
│   └─ 补偿时限太短 → 调长时限（注意内存代价）
└─ 是否被策略拦截？
    ├─ 黑名单策略
    ├─ 全局禁言 / 群禁言
    └─ 禁止陌生人聊天
```

### 8.4 消息重复

```
消息重复
├─ 客户端是否按消息 ID 去重？ → 没做就补上，这是客户端职责
├─ 上线补偿与实时投递是否重叠？ → 补偿期间应暂停 UI 投递
└─ 重连后是否重复拉取同一区间？ → 游标（最大序号）持久化有问题
```

### 8.5 群消息慢

```
群消息慢
├─ 群人数多少？
│   ├─ 数百人 → 检查扩散路径与数据库写入
│   └─ 数千人以上 → 架构问题，需要专门的大群方案
├─ 已读回执是否逐条上报？ → 应改为按序号上报
├─ 成员列表是否每次全量同步？ → 应改为增量同步
└─ 数据库消息表是否已按会话分区？ → 未分区会导致查询随总量线性变慢
```

### 8.6 启动失败

```
启动失败
├─ 检查进程日志第一处异常（不要看最后一处，通常是连锁反应）
├─ 端口被占用？ → ss -lntp 看
├─ 目录不可写？ → 容器场景查卷挂载
├─ 数据库迁移失败？ → 查校验和错误，按说明修复
├─ Java 版本不匹配？ → UnsupportedClassVersionError
└─ 配置文件语法错？ → 逐项核对，注意空格分隔与等号分隔的差异
```

## 九、日常巡检清单

**每日**

- [ ] 集群成员数 = 预期节点数
- [ ] 各节点连接数分布均衡
- [ ] 待投递队列深度无持续增长
- [ ] 磁盘使用率 < 80%，增长速率正常
- [ ] 无进程重启记录

**每周**

- [ ] 消息投递延迟 P99 趋势
- [ ] 慢查询 Top 10 及其变化
- [ ] 数据库连接池峰值
- [ ] 备份任务成功记录

**每月**

- [ ] 恢复演练（至少一次，实际恢复）
- [ ] 依赖库漏洞扫描
- [ ] 证书与密钥到期检查
- [ ] 容量趋势外推，评估下次扩容时间点
- [ ] 日志中的异常模式排查（不要只看告警）

**每次变更前**

- [ ] 全量备份已完成并验证可读
