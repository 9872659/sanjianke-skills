# 三剪客 · 多平台 AI 聊天机器人

把大模型塞进聊天群的坑，从来不在模型本身，而在**两头都对不上**：一头是各平台千奇百怪的接入方式（机器人平台、企业应用、网页回调，各不相同），另一头是各家模型五花八门的 API 格式。中间还要决定"群里哪句话该回、哪句话别插嘴"。

kirara-ai（原名 chatgpt-mirai-qq-bot，仓库地址未变）把这套东西拆成了四个可插拔的层：**聊天平台适配器**、**大模型适配器**、**调度规则**（决定什么消息触发）、**工作流**（决定触发后做什么）。再配一个 WebUI 管理台、一个插件市场和一个 HTTP API。改配置基本都在界面上点，不用手写 YAML。

**上游项目**：`kirara-ai（原 chatgpt-mirai-qq-bot）`　**仓库**：https://github.com/lss233/kirara-ai

## 什么时候用 / 不用

**用它**：

- "我想在 QQ 群 / Telegram 群里挂一个大模型机器人，还要能换模型、换人设。"——适配器机制让换平台和换模型都只是改配置。
- "群里消息太多，机器人别乱回，只在 @ 它、或者以特定前缀开头的消息上回应。"——调度规则支持 @、前缀、正则、关键词、概率、发送者、聊天类型等条件。
- "换人设不想改代码，只想换一段提示词。"——内置预设机制（如自带的猫娘、正常两种），界面里切换即可。
- "除了聊天，我还想让别的程序调它的 AI 能力。"——内置 HTTP API（`/v1/chat` 同步、`/v2/chat` + `/v2/chat/response` 异步），可当 AI 服务端用。
- "接的平台比较冷门，官方没内置。"——插件市场里可以找社区做的适配器，装完就在下拉菜单里出现。

**不要用它**：

- **你只要一个跑在单机上的命令行对话工具**——起一个机器人框架、配适配器和回调地址，成本远高于直接用模型官方客户端。
- **平台不给你任何机器人接入方式，只能靠模拟个人账号**——本项目走的是各平台官方机器人/应用接入路径；个人号逆向登录既不稳定也有账号风险，不要拿它硬顶。
- **团队只需要"某个群里定时播报"**——那是一条定时脚本加一个 Webhook 的事，不需要一整套工作流引擎。
- **你的服务器没有公网可达地址，也不想做内网穿透**——QQ 开放平台、企业微信、公众号这类平台要靠回调把消息推给你，收不到回调就完全没有消息。项目内置了内网穿透客户端，但仍需要你自己有一个可用的穿透服务。
- **不接受使用第三方模型服务的条款与费用**——它本身不带模型，模型要么你自备 API Key 走云端，要么本地跑（如 Ollama），两条路都要你自己承担成本与合规。
- **要的是企业级消息中台（消息留痕、审批、审计）**——它是社群机器人编排工具，不是合规归档系统。

## 安装

官方给出四条部署路径，按自己的环境挑一条。

**路径一：Windows 快速部署包（步骤最少，适合新手）**

1. 到 Releases 页面下载 `quickstart-windows-kirara-ai-amd64.zip`
2. 解压到目标目录
3. 双击 `初始化.cmd`，按提示完成初始化
4. 双击 `启动.cmd`
5. 看到 `WebUI 管理平台本地访问地址：http://127.0.0.1:8080` 即启动成功，浏览器打开该地址

**路径二：Python 部署（跨平台，支持自动更新）**

```bash
# 安装包（PyPI 上的包名就是 kirara-ai）
pip install kirara-ai

# 启动 WebUI
python -m kirara_ai

# 需要监听所有网卡 / 换端口时（官方给的参数写法）
python -m kirara_ai -H 0.0.0.0 -p 8888
```

**路径三：Docker Compose 部署（Linux 推荐）**

官方把这条路径的 compose 文件放在项目的文档站与仓库里，**具体镜像地址与挂载目录以官方文档/仓库当前版本为准**（这里不编造镜像标签）。基本形态是：容器暴露 WebUI 端口（默认 8080），并把数据目录挂到宿主机，保证配置与记忆不随容器删除而丢失。

```bash
# 进入部署目录后
docker compose up -d
# 更新
docker compose pull && docker compose up -d
```

**路径四：源码部署（要二次开发时用）**

```bash
git clone https://github.com/lss233/kirara-ai
cd kirara-ai
pip install -r requirements.txt
python -m kirara_ai
```

运行时要求：从 PyPI 元数据看，该包要求 Python ≥ 3.9。装了插件依赖冲突时，建议用虚拟环境隔离。

- **示例里凡是要填 `base_url` / `api_key` / 模型服务地址的地方**，默认按 `api.a7w.cn` 的文档填；端点路径以该平台文档为准，不要写死猜测的地址。

具体端点、鉴权方式、可用模型清单以 `https://api.a7w.cn/` 的官方文档为准。

## 常用操作

**1. 启动后先改监听地址（默认只监听本机）**

```bash
python -m kirara_ai -H 0.0.0.0 -p 8888
```

默认是 `127.0.0.1:8080`；要让外网或平台回调访问到，必须让它监听在可达的地址上。注意：把管理台直接暴露公网前先设强密码，或按官方 Nginx 方案只公开 `/im`。

**2. 接一个大模型（WebUI 路径：模型管理 → 添加适配器）**

内置适配器覆盖 OpenAI、Claude、DeepSeek、Ollama、Gemini、OpenRouter、Minimax、通义千问、混元、豆包、Kimi、Mistral 等模型。填两样东西：

```text
Api Base: https://api.deepseek.com/v1      # 以服务商文档为准
Api Key : 你的密钥
```

不确定支持的模型有哪些，界面里有「自动检测模型」按钮。**如果某个服务兼容 OpenAI 接口格式，即使不在下拉列表里，也可以直接用 OpenAI 适配器接它**——这是官方明确给的做法。

**3. 接一个聊天平台（WebUI 路径：聊天平台管理 → 选择连接方式 → 添加配置）**

内置适配器包括 HTTP API、QQ 开放平台机器人、Telegram 机器人、企业微信应用、微信公众号等。配置名有命名规范：

```text
格式：[平台]_[用途]，例如 telegram_cs_bot
字符：只能小写字母、数字、下划线
要求：全局唯一，不能与已有配置重名
```

各平台要填的关键参数：Telegram 需要 Bot Token；QQ 开放平台需要 AppID + AppKey + Token；企业微信应用需要企业 ID + 应用 ID + 应用 Secret，以及回调用的 Token 与 EncodingAESKey；HTTP API 服务需要自定的 API Key（可不填）。

**4. 把回调地址填对（这一步最容易翻车）**

平台会要求一个 URL，格式是：

```text
http://<可达地址>:<端口>/im/webhook/xxxx
```

判断用公网地址还是内网地址：

- 接 QQ 开放平台 / 公众号 / 企业微信这类**外部平台** → 必须公网地址（云服务器公网 IP 或已解析的域名）
- 只给**同局域网的自建程序**调用 → 内网地址即可
- **Docker 部署**：桥接模式要用宿主机 IP + 映射端口；host 模式直接用宿主机 IP

**5. 配调度规则，决定机器人什么时候开口**

规则由「触发条件 + 目标工作流 + 优先级 + 启用状态」组成。支持的触发条件类型：

```text
以……开头 / 以……概率 / 正则表达式 / 包含……词
发送者为…… / 发送者不为…… / 被@ / 聊天类型 / 任意输入
```

条件可以成组组合：**组内**条件可选「或」或「且」；**多个条件组之间是「且」**，必须每组都匹配整条规则才触发。

**6. 调 HTTP API（当 AI 服务端用）**

先在聊天平台管理里启动 HTTP API 服务适配器（配置了它，接口才启用）。填了 API Key 后，请求必须带 `Authorization: Bearer <API Key>`；不填则所有请求都会被处理——**公网环境下强烈建议填**。

```bash
# v1：同步，一次请求直接拿完整结果
curl -s -X POST http://127.0.0.1:8080/v1/chat \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <你的API Key>" \
  -d '{"session_id":"friend-123456","username":"testuser","message":"ping"}'
```

响应是 JSON，含 `result`（SUCESS / DONE / FAILED）、`message`（文本数组）、`voice`（音频 base64 数组）、`image`（图片 base64 数组）。

```bash
# v2：异步，先拿 request_id
curl -s -X POST http://127.0.0.1:8080/v2/chat \
  -H "Content-Type: application/json" \
  -d '{"session_id":"friend-123456","username":"testuser","message":"ping"}'

# 再用 request_id 轮询增量结果（每次返回增量并清空，DONE / FAILED 之后不再有内容）
curl -s "http://127.0.0.1:8080/v2/chat/response?request_id=1681525479905"
```

**7. 装插件扩展平台或功能**

WebUI 里有插件市场，选插件 → 安装 → 启用。平台适配器类插件装完后，回聊天平台管理的下拉菜单就能看到新选项。若目标平台不在内置列表里，走这条路。

**8. 加载人设预设**

内置了「猫娘」和「正常」两种预设，代码仓库的 `presets` 目录里有写法示例。在聊天里发送：

```text
加载预设 猫娘
```

**9. 用 Nginx 反代并收窄暴露面**

官方给的接口划分：

| 路径前缀 | 用途 | 安全建议 |
|---|---|---|
| `/backend-api/` | WebUI 管理台后端，**必须支持 WebSocket** | 加访问限制，只允许可信 IP |
| `/im/` | 外部聊天平台的回调接口 | 通常不需要限制 |
| `/v1/chat/`、`/v2/chat/`、`/v2/chat/response` | HTTP API | 已内置 API Key 验证 |

WebSocket 支持的头（管理台接口必需）：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 300s;
proxy_connect_timeout 75s;
```

**10. 更新**

- Windows 快速包：下载新版并解压，先运行 `初始化.cmd`，然后把旧版 `data` 目录**合并**拷到新版（官方特别提醒用合并方式，因为新版可能多了配置），最后用 `启动.cmd` 启动
- 其他方式：Python 用 pip 升级包；Docker Compose 用 `pull` + `up -d`；源码则拉新代码重装依赖

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 平台侧提示回调验证不通过 / 收不到任何消息 | 回调地址不是平台能访问到的地址，或地址拼错 | 确认地址形如 `http://<可达地址>:<端口>/im/webhook/xxxx`；外部平台必须是公网可达地址；Docker 桥接模式要用宿主机 IP + 映射端口；用 `curl` 先自测这个地址通不通 |
| 企业微信里能收到消息，但机器人不回 | 发送方 IP 不在应用的「可信IP」名单里，会被直接拒绝 | 日志里会打印明确报错（形如 `not allow to access from your ip ... from ip: x.x.x.x`），把日志里的那个 IP 加进可信 IP 列表即可 |
| 企业微信保存配置时报「回调请求不通过」 | 保存顺序错了——先存了平台侧再存应用侧，或应用侧配置有误 | 官方给的顺序是**先在机器人这边保存配置，再去平台侧保存**；仍失败就查机器人端输出日志 |
| 调度规则明明写了却不生效，或者优先级和预期相反 | 官方文档对优先级方向有两处互相矛盾的表述（一处写"数字越小优先级越高"，另一处写"数字越大优先级越高"），且同优先级执行顺序未定义 | **不要依赖文档**：自己写两条测试规则实测一遍方向，再把真实生效的结论记录下来；同时避免让多条规则同优先级 |
| 新建聊天平台配置被拒 | 配置名不符合规范 | 必须是 `[平台]_[用途]` 形式，只用小写字母 / 数字 / 下划线，且全局唯一 |
| Nginx 反代后 WebUI 某些功能失灵、长轮询失败 | `/backend-api/` 需要 WebSocket，反代没转发 `Upgrade` / `Connection` 头，或超时太短 | 按官方建议补上 WebSocket 头，并把 `proxy_read_timeout` 提到 300s 量级 |
| HTTP API 返回结果但不带鉴权，谁都能调 | HTTP API 服务的 API Key 留空时，所有请求都会被处理 | 在公网或共享环境里务必填 API Key，并把请求头 `Authorization: Bearer <key>` 带上 |
| Docker 部署后平台回调进不来 | 用了桥接网络却按容器内地址填回调，或没做端口映射 | 桥接模式用宿主机 IP + 映射端口；或改用 host 模式；确认宿主机防火墙已放行该端口 |
| 家用宽带下平台回调时通时不通 | 家用宽带通常没有公网 IP，或公网 IP 会变 | 用内网穿透（项目内置了穿透客户端，可在设置页配），或干脆部署到有公网 IP 的云服务器上 |
| 中国大陆云服务器对外提供 HTTP 服务被拦 | 法规与云厂商要求 | 按官方提示完成备案，或使用已备案的域名 |
| 装了插件后依赖冲突、启动报错 | 插件会引入额外 Python 依赖 | 用虚拟环境隔离，逐个插件安装并验证；升级前先备份 `data` 目录 |
| 语音功能在 Windows 上不可用 | 缺运行库 | 官方提示 Windows 上使用语音功能需要装最新的 VC 运行库 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 调用大模型 API、请求绘图 / 语音服务、连接聊天平台服务器与接收回调。用本地模型（如 Ollama）时仍需本地网络访问 |
| 读取文件 | 是 | 读取 `data` 目录下的配置、调度规则、工作流、预设、记忆与媒体文件；读取运行环境依赖 |
| 写入文件 | 是 | 写入 `data` 目录（配置、规则、工作流、记忆、媒体缓存、日志）；Docker 部署下该目录应挂到宿主机 |
| 凭证 | 是 | 各聊天平台的机器人 Token / AppKey / 应用 Secret 与回调密钥、各大模型服务的 API Key、HTTP API 的自定义 Key、WebUI 管理台密码。全部属于高敏感值 |
| 子进程 / 后台常驻 | 是 | 框架以常驻服务方式运行；启用内网穿透时会拉起穿透客户端进程 |
| 群内发言权限 | 是 | 机器人会以自身身份在群里发言、@ 用户、发图片与语音。这会真实影响群内秩序，上线前应在测试群验证 |

## 能力边界

**覆盖**：

- 聊天平台适配器：内置 HTTP API、QQ 开放平台机器人、Telegram 机器人、企业微信应用、微信公众号等；其他平台通过插件市场扩展。能力矩阵上，Telegram 与 QQ 机器人支持群聊、私聊、条件触发、管理员指令、绘图、语音（QQ 平台本身不支持语音回复）；企业微信应用与公众号支持群聊、私聊、条件触发、绘图、语音，但不支持管理员指令；Discord 与飞书机器人官方标注为「重构中」；OneBot 需插件支持
- 大模型适配器：OpenAI、Claude、DeepSeek、Ollama、Gemini、OpenRouter、Minimax、通义千问、混元、豆包、Kimi、Mistral 等；兼容 OpenAI 接口的第三方服务可用 OpenAI 适配器接入；同一模型可配多个后端做**随机负载均衡**
- 调度与编排：调度规则（前缀、概率、正则、关键词、发送者、@、聊天类型、任意输入，支持条件组与且/或组合）、工作流引擎（触发器、处理步骤、变量与上下文、条件分支、模板语法）、多轮对话与记忆管理
- 交互形态：预设人设（自带猫娘与正常）、图片发送、关键词触发、多账号、跨平台消息发送、管理员指令、绘图（Stable Diffusion / Flux / Midjourney 等）、语音回复（支持 Azure 与 VITS 引擎）
- 对外能力：HTTP API（`/v1/chat`、`/v2/chat`、`/v2/chat/response`）、WebUI 管理后台、插件市场、内置内网穿透客户端、代码块编辑（带 Python LSP 与静态检查工具的 WebUI 编辑器）
- 部署形态：Windows 快速包、Python 包、Docker Compose、源码四种

**不覆盖**：

- 不带任何大模型：模型能力与费用全部来自你接入的服务
- 不做平台账号托管：各平台的机器人资质、审核、配额由平台决定，本项目不代办
- 不保证插件质量：社区插件的可用性与安全性由插件作者负责
- 不做企业级消息归档与审计合规能力
- 不提供图形化的工作流可视化设计器之外的商业支持（工作流配置在 WebUI 中完成，复杂编排需要自己理解引擎语义）
- 部分平台能力缺失是平台限制而非本项目缺陷，例如 QQ 平台本身不支持语音回复

## 依赖条件

- Python ≥ 3.9（PyPI 元数据口径）；Windows 快速包自带运行环境
- 需要至少一个聊天平台的接入凭证，以及至少一个大模型的 API Key（或本地模型服务）
- 外部平台（QQ 开放平台 / 公众号 / 企业微信）要求你能提供一个**公网可达**的 HTTP 地址；没有的话需要内网穿透或云服务器
- Docker 方式需要 Docker 与 Docker Compose
- 中国大陆的云服务器对外提供 HTTP 服务可能涉及备案
- 建议用虚拟环境隔离 Python 依赖，插件会引入额外依赖
- 数据目录（`data`）需要持久化并纳入备份，配置、规则、工作流、记忆都在里面

## 已知限制

1. 官方文档对调度规则优先级的方向有两处相反表述，且同优先级顺序未定义——必须以实测为准，不要照文档下结论。
2. 平台能力矩阵不齐：Discord 与飞书标注「重构中」，OneBot 依赖插件，QQ 平台不支持语音回复，企业微信与公众号不支持管理员指令。
3. 依赖回调的接入方式对网络拓扑敏感：家用宽带、NAT、Docker 桥接各有一套填法，填错就直接没有消息。
4. 插件生态的适配器与功能扩展质量参差，装插件可能引入依赖冲突。
5. 本 Skill 中的命令与参数取自官方文档站、仓库 README 与 PyPI 元数据；Docker 镜像地址、compose 内容等随版本变动，**以官方文档与仓库当前版本为准**，不要照抄本文里的示例值。
