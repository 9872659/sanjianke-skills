# 角色与职权（四个角色为什么必然互相否）

本包是 **L3 多智能体协作型**。L3 的关键不是"调多次模型"，
而是下面四件事同时成立 —— 少一件，就退化成"一个人写了四遍"。

| L3 的要求 | 本包落在哪 |
|---|---|
| 每个角色有**独立的目标函数与产出物** | 四个系统提示词各写各的目标函数；四份产出契约互不重复 |
| 角色之间**会互相否掉东西** | 视觉打回 → 文案重写；合规打回 → 重开下一轮；合规点名选品卡 → 回传选品重开 |
| **信息不对称** | `role_input()` 是唯一入口，只挑该角色该看到的字段；`run` 把"各角色收到了什么"打进 stderr |
| **裁决与终止机制** | `--rounds` 轮上限；合规三选一（放行/打回/一票否决）；轮次用尽仍在否决 → 如实报未收敛（退出码 3） |

---

## 一、选品

**目标函数**：这个品能不能卖、毛利够不够、资质与合规风险兜不兜得住。

**产出物**：选品卡

| 字段 | 内容 |
|---|---|
| `product` / `category` / `target_platform` | 商品名、类目、目标平台 |
| `sellpoints[]` | 卖点 + 依据 + **原样引文**（引文必须能在商品资料里逐字找到） |
| `margin` | 对本地测算的复核意见（**不许改本地算出来的数字**） |
| `certs` | `held`（材料里明确写了的）/ `required_for_category` / `missing` |
| `risks[]` | 风险 + 等级 + 原样引文 + 为什么 + **谁能解决** |
| `conclusion` | 可主推 / 可测试 / 放弃 |
| `venv_veto` / `veto_reason` | 否决开关与否决理由 |
| `need_materials[]` | 要用户补的真实材料 |

**否决权**：**有，而且有两套**。

1. **模型否决**：`venv_veto=true` + 非空 `veto_reason` → 整条流水线**停在第 0 轮**，
   不会进入文案与视觉。
2. **本地判定线**（不看模型措辞，`check_pick`）：
   - 退货后毛利 / 售价 < 20% → 判放弃
   - 退货率 > 40% → 判放弃
   模型写「可主推」也拦得住。这条是"角色有独立目标函数"最硬的证据：
   否决权不取决于它乐不乐意说，取决于账。

**信息隔离**：它是第一个角色，**只有商品资料**。

---

## 二、文案

**目标函数**：主图与详情页的文字能不能转化，以及能不能被图和平台容下。

**产出物**：主图五位文案 + 详情页文案 + 每位的依据。

**否决权**：**无**。它只能被否 —— 被视觉打回、被合规打回。这是刻意的：
链条上必须有人承担"改"的角色，否则"互否"就会变成互相卡死。

**信息隔离**：
- 拿得到：商品资料、选品卡的**结构化字段**（卖点与证据、本地毛利测算、风险等级）、
  上一轮的打回意见
- 拿不到：选品的自评与长篇论述、视觉的可产性结论、合规的任何口径

为什么只给结构化字段：把上游的完整结论原文传下去，下游会顺着它的措辞复述一遍，
四份产出读起来像一个声音（同族内容团队踩过）。

**硬约束**：每位有字数上限（14 / 40 / 24 / 20 / 30 字），超了被本地闸门拦下。
主图上**不许出现任何"内部状态"的字**（真机实测踩过：模型把
「无真实资质图」写进了第 5 位文案 —— 那是给运营看的，不是给消费者看的）。

---

## 三、视觉

**目标函数**：每张图到底画什么、文字压哪、素材从哪来、**能不能真的做出来**。

**产出物**：五位视觉方案 + 打回清单。

| 字段 | 内容 |
|---|---|
| `scene` | 画面画什么（具体到构图与主体） |
| `assets[]` | 用到的素材，**必须来自素材清单** |
| `asset_gap` | 缺什么素材 |
| `productivity` | `producible` / `producible_with_placeholder` / `not_producible` |
| `reason_code` | 做不出来时的理由码（枚举，见下） |
| `why` / `ask_user` | 为什么做不出来 / 要用户补什么 |
| `text` | 文字位置、字数、上限、样式 |
| `layout` / `platform_note` | 版式与平台适配 |

**否决权**：**有**。对任一位标 `not_producible` 即**打回文案**重写
（一轮内最多 2 次）。改不动、素材又补不上，就在轮次用尽时报未收敛。

### 理由码是枚举的，不是自由文本

| 理由码 | 含义 | 要谁能解决 |
|---|---|---|
| `missing_asset` | 缺真实素材（实物图 / 实拍图 / 包装图） | 用户补拍 |
| `unverifiable_claim` | 画面要呈现的效果无法用现有素材验证（可能变成伪造演示） | 用户补证据或改画面 |
| `no_real_cert` | 该位要求资质，但没有真实持有的资质文件 | 用户补资质 |
| `text_overflow` | 文案字数超出该位可读上限 | 文案改短 |
| `platform_rule` | 该位形态与平台主图规则冲突 | 换位或换平台口径 |

`missing_asset` 还必须写 `asset_gap` 与 `ask_user` —— 说不清缺什么等于没提，闸门会拦。

**信息隔离**：
- 拿得到：商品资料、五位文案的**文字**、素材清单、上一轮自己打回的位
- 拿不到：选品卡的风险清单细节、合规的任何结论、文案的自评

**本包不出图**。视觉只产出文本方案 —— 每张图画什么、文字压哪、素材从哪来。
真出图交给既有电商主图包；包内不允许出现任何图片文件。

---

## 四、合规

**目标函数**：广告法与平台规则 —— 这套物料能不能发出去。

**产出物**：风险裁决

| 字段 | 内容 |
|---|---|
| `verdict` | 放行 / 打回 / **一票否决** |
| `violations[]` | 逐条违规项：原样引文 + 违反哪条 + 等级 + 为什么 + 怎么改 |
| `risk_claims[]` | 无法举证的效果或数据宣称 |
| `forged_evidence[]` | 疑似伪造的销量/评价/资质/检测报告 |
| `required_fixes[]` | 必改项（改哪一处、改成什么方向） |
| `need_materials[]` | 要用户补的真实材料 |
| `veto_reason` | 一票否决时的理由 |
| `pending[]` | 仍未解决的问题（**不许抹平**） |

**否决权**：**一票否决**。否决时整包不许放行。本地闸门保证它"说到做到"：

- 打回/否决却没有 `required_fixes` → 拦
- 一票否决却没有 `veto_reason` → 拦
- 有高等级违规 / 无法举证宣称 / 疑似伪造证据 / `pending` 非空 **却判放行** → 拦
  （这就是**假装谈拢**）

**信息隔离**：只拿到**产出物本身**（白名单字段）。任何角色的自评、内部打分、
依据都不进去。

这条是自测时真抓到的：合规原本拿的是视觉对象**整体**，于是把视觉给自己的 `8.8` 分
一起喂了进去。现在走白名单（`slim_visual_for_review`），自评字段漏不出去。

## 五、裁决与终止条件（谁在什么条件下能否掉谁）

```
                    ┌──────────── 选品 ────────────┐
                    │  venv_veto / 本地判定线        │
                    │  否决 → 停在第 0 轮（退出码 3）│
                    └──────────────┬───────────────┘
                                   │ 通过
                    ┌──────────────▼───────────────┐
              ┌────►│            文案               │
              │     └──────────────┬───────────────┘
              │                    │
      打回文案 │     ┌──────────────▼───────────────┐
    （最多 2 次├─────┤            视觉               │
      /轮内）  │     │  not_producible → 打回文案    │
              │     └──────────────┬───────────────┘
              │                    │ 五位可产
              │     ┌──────────────▼───────────────┐
              │     │            合规               │
              │     │  放行 / 打回 / 一票否决        │
              │     └──────────────┬───────────────┘
              │                    │ 打回或否决
              └────────────────────┘ 且还有轮次
                                   │
                     轮次用尽仍在否决
                                   ▼
                    未收敛（final_status）+ 退出码 3
                    逐轮裁决原样留档，不许假装谈拢
```

**终止条件（写死的）**：

| 条件 | 结果 |
|---|---|
| 选品否决（模型或本地线） | 结束，退出码 3（若闸门命中）或 0；不进入后续角色 |
| 合规判放行且所有闸门通过 | `converged=true`，退出码 0 |
| 轮次用尽仍在打回/否决 | `converged=false`、`final_status=未收敛（…）`、**退出码 3** |
| 预算超限 | 就地中止，**未发起那次调用**，退出码 5 |
| 用户 Ctrl+C | 退出码 130 |

**"谈不拢怎么办"**：如实报未收敛，并在裁决记录里留下每一轮的
`verdict` / `violations` / `required_fixes` / `pending` 与原样引文，
再加上 `not_converged_why` 一句话说明停在哪个结论上、还差什么。
**不输出一份"看起来通过了"的物料。**

### 打回意见的回传路线（上游回传）

真机实测抓到的漏洞：合规第 2 轮的整改要求写的是
「选品卡 `product` 字段还是『麦香低糖代餐奶昔 30 条装』，去掉『代餐』」——
这条**文案改不了**（商品名不在文案手上）。如果不回传，下一轮商品名一字不变，
合规还会打回同一件事，跑到轮次用尽只是"看起来在重开"。

所以 `upstream_fix_items()` 会从整改要求里挑出点名了
`选品卡 / 商品名 / 类目 / 卖点清单 / 资质` 的条目，**回传给选品重开**。
重开时选品仍然看不到合规的完整裁决书，只有那几条要求 —— 隔离照样成立。

## 六、为什么这套设计能真的互否（而不是各写各的）

1. **目标函数不同**：选品要"能卖"、视觉要"能做出来"、合规要"发得出去"。
   三者天然冲突 —— 视觉说缺图，选品说能卖，合规说不能发。
2. **信息不共享**：后一个角色看不到前一个的自评，只能独立判断。
3. **否决有后果**：打回真的送回重写，否决真的不许放行，不是提示一句了事。
4. **有终止与留档**：轮次上限 + 未收敛如实上报 + 逐轮裁决留档。

**如果一次跑下来没有任何打回或否决**，那有两种可能：物料确实干净，
或者这四个角色在"各写各的"。判断方法：看 `interaction_log` ——
它只记录**真实的打回/否决/重开**，不会凭空造一条。若日志里只有
"出文案/判可产性/放行"，就是各写各的，本包会如实这么说（报告里写着
"没有发生任何打回或否决：四个角色各写各的，**这属于假协作**"）。
