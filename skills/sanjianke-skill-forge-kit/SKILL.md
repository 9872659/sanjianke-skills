# 三剪客 · 技能工程

把一个重复流程写成能被正确触发的 Agent Skill：触发面、结构拆分、触发测试、故障排查

你已经有了一件想沉淀的事——每周都要走的发布流程、每次都要照做的排查顺序、每次都要交代一遍的交付口径。现在问题是：**写成文件之后，它真的会在对的时候被用上吗？**

大多数自建技能死在三个地方。写得太像一篇说明文，Agent 读完点点头，然后什么都没做；该触发的时候不触发，用户根本不知道这个技能存在；终于触发了，产出跟没写技能时差不多。这三个问题都不是文笔问题，是**工程问题**——触发面没设计、结构没分层、没测过。

这套 Skill 只管一件事：**从「我有一个想法」到「这个技能真的被触发并且做对了事」的动手环节**。它给你一套描述改写规则、一套拆文件判据、一套触发测试集和一张三类故障的排查路径图。

**读完你会拿到**：3 份参考文件（触发设计、结构设计与测试、故障诊断）、1 张改写前后对照表、1 张结构决策表、1 份 20 条触发测试集模板、1 张三症状排障决策树。

## 触发场景

- 「我写了个技能，它压根不触发，跟没写一样。」
- 「这个 `description` 到底该怎么写？官方说要写清『什么时候用』，我写了还是不对。」
- 「技能该不该拆成好几个文件？`references/` 里放什么？」
- 「怎么验证一个技能真的会触发？我不想靠感觉。」
- 「技能是加载了，但 Agent 读完啥也没干，光跟我确认了一遍。」
- 「触发也触发了，动作也做了，结果就是不对，从哪儿查？」

## 快速开始

最小可用路径是**先定触发面，再拆文件，最后用测试集验一遍**。整个流程 40 分钟能走完一轮，产出是一段改写过的 `description`、一个分好层的目录、一份测试集和一张测试结果表。

**第 1 步 · 定位触发面（10 分钟）**

不要先写正文。先在纸上回答三个问题，写成三行字：

| 问什么 | 写什么 | 示例 |
|---|---|---|
| 它替谁做什么 | 一句能力陈述，第三人称，动词开头 | 把散落的发布步骤固化成固定顺序 |
| 什么情况下才用 | 三条**用户真的会说的话** | 「又要发版了」「上线前该检查啥」 |
| 什么时候别用 | 至少一条反例面，写清归属给谁 | 只改文案不动流程时，不用走这套 |

三行写不齐，说明这事还不该写成技能——它可能只是背景知识，或者根本还没有稳定的做法。写法规则、正反例对照见 `references/trigger-design.md`。

**第 2 步 · 写 description（5 分钟）**

`description` 是**唯一负责触发**的字段。正文写得再好，`description` 没写对，它一辈子不会被加载。

```yaml
description: "<做什么>。<什么情况下用>。<不该用的时候交给谁>。"
```

三条硬规则：

1. **写在第三人称**——「把发布步骤固化成固定顺序」，不是「我能帮你固化成固定顺序」。
2. **把用户的说法写进去**——用户说的是「又要发版了」，就别只在描述里写「发布编排」。
3. **写清不触发的一面**——写「只改文案、不动流程时不要用」，比写「适用于各种场景」有用得多。

**第 3 步 · 决定拆不拆（5 分钟）**

先全都写进 `SKILL.md`，**只有下面三种情况才拆文件**：

| 信号 | 拆到哪 | 拆完正文里留什么 |
|---|---|---|
| 正文超过 500 行，且某一段是「查阅型」内容（表、清单、枚举） | `references/xxx.md` | 一段 2~3 行的摘要 + 指向路径 |
| 有一段内容只在特定分支才用得上（10 次里用 1 次） | `references/xxx.md` | 判断条件 + 跳转 |
| 有一段是确定性的机械操作，且能写成命令 | `scripts/xxx.py` | 一条调用命令 + 输入输出说明 |

**反过来说：这三条不成立就不要拆。** 拆得碎是自建技能最常见的自伤方式——每一份都要加载、都要维护，而 Agent 可能一份都不会翻。完整判据见 `references/structure-and-testing.md`。

**第 4 步 · 跑触发测试（15 分钟）**

光看是看不出触发好不好的。构造 **20 条测试句**，正例 6~8 条、负例 6~8 条、边界 4~6 条，逐条在新会话里跑，记下「有没有加载本技能」。

```text
# trigger-tests.md 的最小格式
| # | 测试句 | 期望 | 实际 | 结论 |
|---|---|---|---|---|
| 1 | 又要发版了，帮我过一遍 | 触发 | | |
| 2 | 帮我把这段文案改短一点 | 不触发 | | |
| 3 | 发布流程好像该更新了 | 边界（记录） | | |
```

**两个数字决定要不要继续改**：正例命中率 **< 80%** 说明触发面太窄，回去改 `description`；负例误触发 **> 10%** 说明描述太宽，去加排除句。别凭感觉调——一次改一处、重跑、对比。测试集怎么构造、怎么判分见 `references/structure-and-testing.md`。

**第 5 步 · 出问题就按症状查（随时）**

不触发、触发了不动作、动作了结果不对——这三类故障的排查路径**完全不同**，别用同一套办法瞎试。先对症状，再走对应分支，见 `references/failure-diagnosis.md`。

## 能力边界

**覆盖**：

- 把一个模糊想法收敛成一句可写的触发面：能力陈述、触发条件、排除条件
- 按可操作规则改写 `description`：第三人称、用户原话入描述、加排除句、控制长度
- 给出 `SKILL.md` / `references/` / `scripts/` 的拆分判据，以及拆完正文里该留什么
- 给出 `references/` 的切分轴、命名、单份长度预算与交叉引用写法
- 给出脚本的采用判据、脚本接口约定（输入输出、退出码、失败信息）与四种「不该写脚本」的替代做法
- 给出 20 条触发测试集的构造口径、跑法、判分阈值与只看不改的单变量原则
- 给出三类故障（不触发 / 不动作 / 结果不对）的排查路径与逐项检查清单
- 给出技能间触发面冲突的处置顺序与降级方案

**不覆盖**：

- **不替你判断这件事值不值得做成技能。** 「该不该沉淀」「怎么按触发面切分一个领域」「团队怎么评审和铺开」是另一套方法论的事，本 Skill 从你已经决定要写的那一刻开始接手。
- **不生成具体业务技能的正文。** 它教你怎么把发布流程写成可触发技能，不会替你写你们发布流程的实际步骤。
- **不代跑测试。** 触发测试必须由真实的模型会话来跑。本 Skill 不调用任何推理接口、不模拟模型判断——它给测试集格式和判分口径，跑的动作归你。
- **不做运行时的强制约束。** 技能是提示词层的约定，Agent 理论上可以不遵守。需要「必须执行」的行为，请落到脚本、钩子或 CI 上。
- **不保证触发。** 最终是否加载一个技能，取决于客户端实现、当前上下文和同场竞争的其他技能。本 Skill 给的是提高概率的方法，不是开关。
- **不覆盖市场发布与分发。** 版本号策略、上架字段、分发渠道不在范围内。

## 依赖条件

- **必需**：一个已经决定要写的技能目标，以及它所在的目录（哪怕是空的）。
- **必需**：能读写 Markdown 的能力。纯文本即可。
- **必需**：一个能加载 `SKILL.md` 的 Agent 运行时，用来跑触发测试。**没有它就只能测到「写」，测不到「触发」**——这一点无法省。
- **推荐**：一个能开新会话的客户端。触发测试必须在**干净的新会话**里跑，复用已有长上下文会严重污染结果。
- **推荐**：git。改一次 `description` 提交一次，回头能看出是哪一处改动带来了命中率变化。
- **不需要**：网络、API Key、数据库、Docker、任何付费服务。

## 已知限制

1. **触发是概率性的，不是确定性的。** 同一段 `description`，换个会话、换种问法，结果可能不同。20 条测试集给的是趋势判断，不是统计显著性——想更稳就把样本加大、把同一句多跑几次。
2. **同一份技能在不同客户端上表现不同。** `description` 的字段名、长度上限、是否额外加载 `summary`，各家实现有差异。跨客户端分发前，请在目标客户端上重跑一遍测试集。
3. **测试会受同场其他技能干扰。** 装了 50 个技能的环境和只有 3 个的环境，命中率不一样。负例误触发很多时候不是你的描述问题，是别人抢了词——这类要按冲突处理，不要一味改自己的描述。
4. **`description` 长度上限是经验值。** 不同客户端的上限不同，超限可能被截断，而截断往往恰好砍掉「什么时候用」那一句——这是最隐蔽的不触发原因。
5. **正例命中率与误触发率是此消彼长的。** 把描述写宽能提高命中，也会带来误触发。两者不能同时拉满，必须按这个技能误触发的代价来取舍。
6. **本 Skill 不含自动化测试工具。** 触发测试没有官方的本地跑法，本 Skill 给的是人工可执行的流程和记分方式，不是测试框架。

## 自检清单

写完一份技能，逐条打勾；任何一条没打上，先别当成做完了。

- [ ] **触发面三行齐**：能力陈述、触发条件（三条用户原话）、排除条件（至少一条）都写出来了
- [ ] **description 第三人称**：动词开头的陈述句，没有「我能」「我将」「帮你」这类第一人称
- [ ] **用户原话入描述**：描述里出现的说法，和用户张口会说的话对得上，不是内部术语
- [ ] **有排除句**：写清了什么情况下不要用这个技能，或交给谁
- [ ] **长度没被截断**：在目标客户端里能看到完整的 `description`，「什么时候用」那一句没被砍掉
- [ ] **拆分有理由**：拆出去的每一份文件都能对应上三条拆分信号之一；没有为了「看起来整齐」而拆
- [ ] **正文留了跳转**：拆出去之后，正文里有明确的判断条件 + 指向路径，不是只写了个文件名
- [ ] **脚本有接口**：每个脚本都写清输入、输出、退出码和失败时的报错形态；跑不了的脚本不如不写
- [ ] **测试集 ≥ 20 条**：正例 6~8、负例 6~8、边界 4~6，且负例与正例是同一个领域里的话
- [ ] **新会话跑的**：每条测试都在干净会话里跑过，没有复用已经装了这个技能的上下文
- [ ] **命中率达标**：正例 ≥ 80%、负例误触发 ≤ 10%；不达标时是**一次只改一处**再重跑
- [ ] **回归过**：修完之后，原先通过的测试句重跑一遍仍然通过
- [ ] **无凭证**：`description`、正文、测试集里没有真实密钥、Token、内网地址、客户名
