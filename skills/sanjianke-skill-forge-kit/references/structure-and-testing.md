# 结构设计与测试

> 这份文件管两件事：**这个技能该有多少个文件**，以及**怎么证明它真的会触发**。
> 前者决定 Agent 能不能读完、你能不能维护；后者决定这个技能到底是活着还是躺着。

---

## 一、结构决策总表

先看这张表，能覆盖 80% 的情况：

| 你现在的情况 | 结构 | 理由 |
|---|---|---|
| 正文 200 行内，只有一条主流程 | 单文件 `SKILL.md` | 拆了就是纯负担 |
| 正文 200~500 行，有一两段「查表」内容 | `SKILL.md` + 2~3 份 `references/` | 主线留正文，查表内容分流 |
| 有几个分支只在特定条件下才用 | `SKILL.md` + 每个分支一份 `references/` | 正文只留「怎么判断走哪条」 |
| 有确定性、机械、可重复的操作 | 加 `scripts/` | 省 token、稳、可复跑 |
| 正文超过 500 行 | 先想**拆技能**，不是拆文件 | 长度问题是职责问题，不是排版问题 |
| 只有一份 800 行的 `SKILL.md`，内容全是步骤 | 大概率拆不动，先砍 | 见第七节反模式 |

**一句话口径**：文件数是为了让 Agent **按需加载**，不是为了让目录好看。每多一个文件，就多一份维护成本和一份永远不会被翻的概率。

## 二、三条拆分信号

**只有下面三条成立时才拆。三条都不成立，全部写在 `SKILL.md` 里。**

### 信号 A · 查阅型内容超过 60 行

**特征**：表格、枚举、清单、参数对照——这些东西的特点是「用的时候要查，不用的时候不用看」。

- 拆到 `references/`
- 正文里留：**2~3 行摘要 + 指向路径 + 什么时候该去翻**

**注意**：不是所有表格都该拆。一段 10 行的判据表留在正文里，比拆出去更省事——因为拆出去之后，Agent 得多跳一次才拿到它。**阈值参考 60 行**，短于此的留在正文。

### 信号 B · 只在某个分支用得上

**特征**：一次执行里大概只有 10%~20% 的概率会走到这段。

- 拆到 `references/`
- 正文里留：**判断条件 + 跳转指令**

```markdown
## 工作流路由

| 情况 | 看哪份 |
|---|---|
| 常规路径（多数情况） | 按本文档第三节直接执行 |
| 遇到 <特定条件> | 读 `references/<分支>.md`，按其中步骤处理 |
| 需要 <另一种产出> | 读 `references/<另一种>.md` |
```

**为什么不能留在正文**：留在正文的代价是**每次加载都要读**。一次执行里用不到的内容，每次都占着上下文，还会稀释主线步骤的注意力。

### 信号 C · 机械且可判定

**特征**：输入输出明确、没有判断空间、跑错了会报错而不是悄悄地错。

- 写成 `scripts/xxx.py`
- 正文里留：**一条调用命令 + 输入输出说明 + 失败时怎么办**

**为什么**：同一件事，写成文字描述让模型每次自己推，结果会飘；写成脚本跑，结果稳定。凡是「能用确定性代码做完」的部分，都不要留给模型现场发挥。

## 三、每份 `references/` 的规矩

拆出去之后，每份文件要满足四条：

| 规矩 | 具体做法 |
|---|---|
| **单主题** | 一份文件只回答一个问题。判断方法：给它起个标题，标题里出现「和」就该再拆 |
| **自包含** | 单独打开这一份就能用，不依赖读者记得正文第三节 |
| **有回指** | 末尾写清「下一步去哪」或「回到正文哪一节」 |
| **控长度** | 单份 150~400 行。低于 100 行考虑并回正文；超过 500 行说明这一份自己又该拆了 |

**命名**：用**读者的问题**命名，不用文档类型命名。

| 差 | 好 | 为什么 |
|---|---|---|
| `details.md` | `trigger-design.md` | 「details」没有信息量，读者不知道要不要翻 |
| `appendix-a.md` | `failure-diagnosis.md` | 附录编号对 Agent 没有任何提示作用 |
| `notes.md` | `script-conventions.md` | 具体主题名能让模型判断相关性 |

**正文里的引用格式**（这条经常被写坏）：

```markdown
<!-- 坏：只说文件名，模型不知道什么时候该翻 -->
详见 `references/trigger-design.md`。

<!-- 好：判断条件 + 这份文件给什么 + 路径 -->
当描述写好了但不触发时，读 `references/trigger-design.md`，
其中第二节是描述三段式公式，第三节是 12 组改写前后对照。
```

## 四、渐进式展开：三层信息深度

技能的信息按「什么时候需要」分三层，各层放的深度不一样。写正文时拿这个当标尺——**放错层**是正文臃肿的主因。

| 层 | 内容 | 放在哪 | 该有多详细 |
|---|---|---|---|
| 第 1 层 | 什么时候用这个技能、什么时候不用 | `description` | 2~3 句 |
| 第 2 层 | 主流程、判据、路由 | `SKILL.md` 正文 | 能照着做完，但**不复述细节** |
| 第 3 层 | 长表、分支细则、对照示例、脚本接口 | `references/` / `scripts/` | 详尽，含完整示例 |

**最常见的放错层**：

- 把第 3 层的对照表塞进正文 → 正文膨胀，主线被淹没
- 把第 2 层的判据写进 `description` → 描述超长被截断
- 第 3 层写成第 2 层的摘要 → 拆了等于没拆，读者还得回正文问

## 五、什么时候该写脚本

**采用判据（四条全中才写）**：

1. **确定**：同样输入必得同样输出，没有「看情况」
2. **机械**：步骤固定，不需要中途判断
3. **高频**：一次执行里会跑，或者跨多次执行反复用
4. **会错**：模型现场做容易漏步骤、算错数、记错参数

**任一条不成立就别写**。特别注意第 4 条——「模型大概能做对」的操作写脚本，是纯粹的负债：多了个文件要维护，还多了一层调用失败的可能。

### 四种「不该写脚本」的替代做法

| 情况 | 别写脚本，改用 |
|---|---|
| 就是一段固定文本/模板 | 直接放 `references/`，让模型照抄 |
| 只是一条命令 | 写在正文里，给出完整命令和参数 |
| 逻辑在变、还没稳定 | 先写成步骤描述，稳定三个月后再固化 |
| 需要网络和密钥才能跑 | 写成「让用户自己跑」的指引，不要内嵌凭证 |

### 脚本接口约定

写脚本时，把接口**写进正文**，不要指望读者去翻代码：

```markdown
## 脚本

`scripts/<name>.py` — <一句话用途>

- 调用：`python scripts/<name>.py --input <路径> --format json`
- 输入：<需要什么文件/参数，什么格式>
- 输出：<stdout 是什么，写到哪个文件>
- 退出码：`0` 成功；`1` 输入不合法；`2` 用法错误
- 失败时：<报错信息长什么样，遇到了下一步做什么>
- 依赖：<仅标准库 / 需要哪些包>
```

**三条硬要求**：

- **退出码要区分**：`0` 成功、非 `0` 失败，且不同失败原因用不同码。模型靠退出码判断要不要重试。
- **失败信息要说人话**：报「输入文件不存在：<路径>」，不报一段堆栈。堆栈对模型没有决策价值。
- **依赖要声明**：需要装包的脚本，把安装命令一起写上，或者干脆只用标准库。

**脚本不能替代正文的判据**。脚本管「做完」，正文管「判断该不该做、走哪条路」——两者是分工，不是替代。

## 六、20 条触发测试集

### 为什么必须测

触发是编排层的一次**语义选择**：把当前请求和所有候选技能的描述比一遍，挑最相关的加载。这个过程你看不见，只能靠外部行为反推。**不测就相当于发布一个没有编译过的程序。**

### 构成：三类句子，缺一不可

| 类型 | 条数 | 作用 | 例子（以发布流程技能为例） |
|---|---|---|---|
| **正例** | 6~8 | 该触发的时候真的触发了吗 | 「又要发版了，帮我过一遍」 |
| **负例** | 6~8 | 不该触发的时候有没有乱触发 | 「帮我把这段文案改短一点」 |
| **边界** | 4~6 | 模糊地带现在表现如何（记录，不判对错） | 「发布流程好像该更新了」 |

**构造负例的关键**：负例不能是随便找的无关请求（「今天天气怎么样」这种测不出任何东西）。负例要**和正例同领域**，只是目标不同：

- 正例：`这批素材帮我出几条短视频`
- 好负例：`这段素材帮我剪短一点，就一条`（同领域、同素材、但规模与目标不同）
- 坏负例：`帮我查一下服务器 IP`（离太远，永远不触发，测了等于没测）

### 边界句怎么用

边界句**不判对错，只记录**。它的价值在于：改完描述之后，边界句的行为变化能告诉你这次改动的方向对不对。

- 改窄之后，边界句从「触发」变成「不触发」→ 方向正确
- 改窄之后，正例也跟着掉 → 改过头了，往回收

### 完整模板

新建 `trigger-tests.md`，照这个格式填：

### 跑法：四条纪律

1. **必须在干净的新会话里跑。** 复用已经加载过这个技能的长上下文，结果等于作弊——技能已经在了，测不出触发。
2. **一次只改一处。** 这一轮只改 `description`，下一轮只改排除句。同时改三处，命中率变了你也不知道是哪处起了作用。
3. **一条一轮。** 每条测试句开一个新会话，不要在一个会话里连着问 20 句——前一句的上下文会污染后一句。
4. **测完记结果，不要凭印象。** 记忆里的命中率永远比实际高，尤其是刚写完的时候。

### 判分口径与阈值

| 指标 | 算法 | 阈值 | 不达标怎么办 |
|---|---|---|---|
| **正例命中率** | 命中数 / 正例总数 | **≥ 80%** | 触发面太窄：把用户的口语说法补进描述第二段 |
| **负例误触发率** | 误触发数 / 负例总数 | **≤ 10%** | 描述太宽：加排除句，或把第一段的能力陈述收窄 |

**两个指标此消彼长**，不可能同时拉满。取舍看这个技能的误触发代价：

- 误触发代价高（会把流程带跑偏、会花掉预算）→ 优先压负例误触发，接受正例命中掉到 70%
- 漏触发代价高（该走流程的没走）→ 优先保正例命中，接受误触发升到 20%

**阈值不是物理定律**，是你自己的取舍基准线。写下来，下次改的时候对照同一套基准。

### 只看行为，不看自我报告

判断「有没有触发」只看**外部行为**：

- ✅ 看它有没有按技能里的步骤动作、有没有用技能里定的产出格式
- ❌ 不要问模型「你刚才用了这个技能吗」

**为什么**：模型对自己是否加载了某个技能的自述**基本不可信**——它可能把一个通用能力误报成技能，也可能加载了却说不清。行为是唯一可靠的观测面。

## 七、结构反模式

| 反模式 | 识别信号 | 代价 | 改法 |
|---|---|---|---|
| **一拆到碎** | `references/` 里有 5 份 30 行的文件 | 每份都可能不会被翻；维护成本翻倍 | 小于 100 行的并回正文 |
| **拆了个寂寞** | 拆出去的文件只是正文的重复摘要 | 读者两边都不满意 | 拆出去就写全，正文只留条件和路径 |
| **正文像词典** | 正文一半是表格和枚举 | 主线步骤被淹没 | 按信号 A 分流到 `references/` |
| **只拆不写路由** | 正文里只有一句「详见 `references/x.md`」 | 模型不知道什么时候该去翻，等于没拆 | 补判断条件 + 这份文件给什么 |
| **为整齐而拆** | 目录里有 8 个文件，但每次执行只用 1 个 | 纯负债 | 按「按需加载」重排，不按「看起来整齐」 |
| **脚本代替判据** | 正文写「运行脚本即可」，没说什么时候该运行 | 遇到边界情况就乱跑 | 正文补判断条件，脚本只负责执行 |
| **附录化命名** | 文件叫 `appendix-a.md` | 模型判断不出相关性 | 改用读者的问题命名 |

## 八、结构自检清单

- [ ] 每份 `references/` 都能对应上信号 A / B / C 之一，没有「为整齐而拆」
- [ ] 单份 `references/` 在 150~400 行之间；低于 100 行的已经并回正文
- [ ] 每份 `references/` 文件名是读者的问题，不是文档类型或附录编号
- [ ] 正文里每一处引用都有：**判断条件 + 这份文件给什么 + 路径**
- [ ] 正文 ≤ 500 行；超出的部分已经按三层深度归位
- [ ] `description` 里只有第 1 层信息，没有搬第 2、3 层
- [ ] 每个脚本都有：调用命令、输入、输出、退出码、失败处理、依赖
- [ ] 每个脚本都满足四条采用判据；不满足的已经改成步骤描述或模板
- [ ] `trigger-tests.md` 已建立，20 条齐全，正例/负例/边界都有
- [ ] 每条测试都在**干净新会话**里跑过，没有复用长上下文
- [ ] 正例命中 ≥ 80%，负例误触发 ≤ 10%（或已按取舍基准线明确接受偏差）
- [ ] 每轮只改一处，改动内容记录在测试文件头部
