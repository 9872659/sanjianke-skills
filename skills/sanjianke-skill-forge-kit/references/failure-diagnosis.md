# 故障诊断

> 技能不work 有三种完全不同的病，**用药不一样**。
> 这份文件给一条分诊路径：先确定你遇到的是哪一类，再走对应分支的检查清单。
> 顺序不能颠倒——**先用错药，会把本来好的部分改坏。**

---

## 一、先分诊：三类症状

| 症状 | 一句话描述 | 你观察到的现象 | 走哪一支 |
|---|---|---|---|
| **A · 不触发** | 技能根本没被加载 | Agent 的行为和你没写这个技能时**一模一样**，步骤、口径、产出格式全都没体现 | 第二节 |
| **B · 触发了不动作** | 技能加载了，但 Agent 只是知道了，没执行 | 它会复述技能里的要点、跟你确认「是否按这个流程走」，然后等你点头；或者干脆只说了句「好的」 | 第三节 |
| **C · 动作了结果不对** | 流程走了，产出不符合技能定义 | 它确实按某个流程做了一遍，但步骤顺序、判据口径、产出格式和技能里写的对不上 | 第四节 |

### 怎么准确区分 A 和 B

这两类最容易看混，因为从用户视角都是「没效果」。**区分方法：看它有没有表现出技能里的独有内容。**

- 技能里有一条你们独有的口径（比如某个必须检查的开关、某个固定的产出格式），Agent **提到了但没做** → 是 B，它加载了。
- Agent 完全没提到这条口径，按通用常识在做 → 是 A，它没加载。

**先做这一步验证**：

```text
技能里写一条非常独特的、凭空想不出来的规则（比如「产出必须以 X 结尾」）。
再跑一次那个请求。
```

- 出现了 X 的迹象但没做完 → **B**
- 完全没出现 X → **A**（也可能是 C 的极端情况，见第四节第 1 步）

**如果 A 和 B 都像**：先按 A 排查。A 的检查成本低（看描述、看长度），而且 A 的问题会导致 B 的假象——模型拿到一份被截断的描述，可能加载了却完全没有可执行内容。

## 二、分支 A · 不触发（7 个检查点）

**按顺序查，前一个通过了再查下一个。** 顺序是按「出现频率 × 排查成本」排的，不要跳。

### A1 · 描述被截断了（最高频，先查这个）

**现象**：本地文件里描述是完整的，客户端加载到的版本少了后半段——通常正好是「什么时候用」那一段。

**怎么验证**：在真实客户端里加载这个技能，然后直接问：「你现在看到的这个技能描述，最后一句是什么？」把它答的和你写的对一遍。或者直接看客户端展示的描述文本。

**怎么修**：

- 把触发条件（第二段）挪到描述**最前面**，能力陈述压到 30 字内
- 删掉形容词、价值主张、作者介绍、「本技能」的重复自称
- 目标：任何截断策略下，损失的都是背景而不是触发条件

### A2 · 描述里没有触发条件

**现象**：描述读起来像一句技能简介——「一套关于 X 的完整方案」，但没有任何「什么时候用」的信息。

**怎么验证**：把描述里的**名词**全部划掉，看还剩什么。如果剩下的只是「能做某事」，说明缺第二段。

**怎么修**：补 2~4 个具体征兆，其中至少一个用引号写出**用户的原话**。用户说「又要发版了」，就把这句话写进去。

### A3 · 措辞和用户的话对不上

**现象**：描述里全是内部术语、缩写、系统名；用户说的是日常说法。

**怎么验证**：拿你的三条正例测试句，逐字去描述里找「有没有对应的说法」。一条都对不上，就是这个问题。

**怎么修**：把用户的口语变体列进第二段，包括中英混说的版本。**不是**改成只写口语——专业名词保留，作为第二组关键词并列。

### A4 · 描述太宽，被别的东西挤掉了

**现象**：不是完全没用过，而是**有时候用、有时候不用**，且什么时候用说不清。

**怎么验证**：看同场环境里有多少个技能的正例面和你重叠。重叠越多，你的描述越不具区分度，被选中概率越低。

**怎么修**：

- 加**领域限定词**（面向 <具体场景> 的 X），提高区分度
- 删掉描述里那些「谁都能用」的通用表述
- 如果重叠的是已有技能，按第五节的冲突处置来办

**注意**：不要靠「重要」「必须」「优先使用」这类词抢注意力，它们对触发决定几乎没有帮助。

### A5 · 技能没有被正确安装 / 重启没生效

**现象**：文件写好了，但客户端根本没扫到。

**怎么验证**：

- 确认技能目录在**客户端实际扫描的路径**下，不是你以为的那个目录
- 确认目录结构和文件名对：`SKILL.md` 全大写、在技能目录根部
- 确认 frontmatter 合法：以 `---` 开头、以 `---` 结束、字段名和缩进没坏
- **重启客户端**（很多实现是启动时扫描一次，新增技能必须重启才可见）

**怎么修**：按上面的顺序逐项确认。frontmatter 坏掉是最隐蔽的一种——文件在、目录对、但解析失败，静默不加载。

### A6 · 当前上下文把它压下去了

**现象**：同一个技能，在某些会话里好用，在某些会话里从来不触发。

**怎么验证**：同一个测试句，在**全新会话**里再跑一次。如果新会话能触发，就是上下文问题。

**怎么修**：

- 触发测试一律在干净会话里跑（这条也是测试纪律）
- 重要流程**不要指望自动触发**——在项目级的 `AGENTS.md` / `CLAUDE.md` 里显式指路，写明「做 X 之前先读 `<技能路径>`」。显式指路比优化描述可靠得多。

### A7 · 描述和实际内容不符

**现象**：触发面写的是 A，正文里讲的是 B。模型判断相关性时看了描述，加载后发现没用。

**怎么验证**：把描述的三段和正文的章节标题对一遍。描述里承诺的能力，正文里有对应章节吗？

**怎么修**：改描述去对齐正文（多数情况），或者改正文去补上描述承诺的内容。**不要两边都留着不一致**——这会让技能在被选中后立刻失效，退化成 A。

## 三、分支 B · 触发了不动作

**判定前提**：已经确认技能被加载了（它提到了技能里的独有内容）。

这一支的根因**几乎全部在写法层**，不在触发层。改描述是无效的——它已经进来了。

### B1 · 通篇是背景知识，没有祈使句

**现象**：正文写得很像一篇介绍文章：「本技能的核心理念是……」「一个好的流程应该包含……」。

**怎么验证**：数一下正文里**祈使句**（动词开头、要求执行）的比例。低于一半就是这个病。

**怎么修**：把「应该」「需要」「建议」改成祈使句，并给每一步一个**可观测的结束判定**。

```markdown
<!-- 改前：像描述，不像指令 -->
一个好的发布流程需要先确认依赖是否就绪，然后才进行构建。

<!-- 改后：指令 + 结束判定 -->
1. 确认依赖就绪：运行 `npm ls --depth=0`，输出无 `missing` 才算通过。
2. 构建：执行 `npm run build`，退出码 0 且产出目录存在才算通过。
```

### B2 · 步骤没有宾语和动作

**现象**：步骤写成「适当处理」「视情况检查」「合理配置」。

**怎么验证**：把每一条步骤念一遍，问「谁、做什么、做到什么算完」。三个里缺一个就是空话。

**怎么修**：每条步骤必须能填进这个句式：**执行 <动作>，输入 <什么>，看到 <什么> 算完成**。填不进去的步骤，要么拆细，要么删掉——**写不出来的判据，模型也执行不出来**。

### B3 · 只有分类，没有执行指令

**现象**：正文是一堆判据和分类（什么时候用 A、什么时候用 B），但没说定下来之后**具体做什么**。

**怎么验证**：找一个分支，问「选了这个分支之后，下一步动作是什么」。如果答案是「去看 `references/x.md`」，那去确认那份文件里是不是真的有祈使句步骤。

**怎么修**：每个分支必须落到动作。判据是**路由器**，不是**执行体**。

### B4 · 被写成了「问用户」而不是「做」

**现象**：正文里说「与用户确认 <某事项> 后再继续」，模型就停在那里等你回复。

**怎么验证**：看触发不动作的时候，它是不是在问你问题。是的话，检查正文里有多少处「确认」「询问」「等待用户」。

**怎么修**：

- 默认不要询问。把「与用户确认 X」改成「按 X 执行；仅当 <罕见的例外条件> 时才询问」
- 必须确认的地方**写清一个明确的问题**，不要让模型现场编一个模糊问题
- 在正文开头加一句执行口径：`本流程默认直接执行，仅在 <条件> 时停下来询问`

**这是自建技能里最容易被忽略的一个坑**：你写「确认」是想让它谨慎，结果它理解成「先问」。

### B5 · 步骤被埋在了长表里

**现象**：正文 400 行，前 300 行是判据表，真正的步骤在很后面。

**怎么验证**：从正文第一行读到第一个祈使句，数一下中间隔了多少行。超过 50 行就是这个问题。

**怎么修**：把**主流程前置**。判据表、背景、对照示例按 `structure-and-testing.md` 的拆分信号分流到 `references/`，正文开头就是「按下面几步做」。

### B6 · 内容自相矛盾，模型卡住或退化成通用做法

**现象**：第三节说「必须先跑测试」，第八节说「时间紧时可以跳过测试」。模型遇到冲突时，常见反应是**两个都不做**，退回通用常识。

**怎么验证**：搜正文里的「但」「例外」「除非」「紧急情况」。每一处都问：这两个说法同时成立吗？

**怎么修**：把例外条件**合并到同一条规则里**，写成带条件的单一规则：

```markdown
跑完整测试再发布。仅当 <明确的例外条件> 时跳过，跳过后必须在 <位置> 记录原因。
```

**不要**让例外散落在文档的不同章节——模型读到的是全文，冲突会直接导致瘫痪。

## 四、分支 C · 动作了但结果不对

这一支最关键的方法是**二分定位**：把流程切成输入 / 中间 / 输出三段，先确定断在哪一段。

### 定位方法：三段二分

```text
输入（它拿到了什么）
   ↓  出问题 → C1 / C2
中间（它按哪条路走了）
   ↓  出问题 → C3 / C4 / C5
输出（它交出了什么）
   ↓  出问题 → C6 / C7
```

**操作方法**：跑一次，把它**实际做了的每一步**记下来，然后和技能里写的逐步对照。差异出现在哪个位置，就往哪一段查。

### C1 · 输入没给全，模型自己补了

**现象**：产出看着完整，但里面有你没提供的假设。

**怎么验证**：逐项对照——技能要求的信息，你这次真的都提供齐了吗？漏了哪项，产出里出现的多半就是它编的。

**怎么修**：

- 如果是技能的锅：**在正文开头加前置检查**——「开始前确认以下 N 项信息都已提供；缺失的项一次性问清，不要自行假设」
- 如果是用户的锅：把缺失项补上重跑，不要靠模型猜

### C2 · 输入格式和技能假设的不一样

**现象**：技能假设输入是结构化数据，你直接贴了一大段自然语言。

**怎么验证**：比对输入的形态和正文里「输入」那一节写的要求。

**怎么修**：正文里写清输入格式，并给一个**最小示例**；如果意图是容忍多种格式，就明确写「以下格式都接受：<列表>」。**没写 = 模型自由发挥 = 每次结果不同。**

### C3 · 分支判断错了，走错了路

**现象**：它做的是流程里的另一条分支。

**怎么验证**：看它实际执行的是哪条分支，再回正文找你为这条分支写的判断条件——那条条件是不是**可以被误读成当前情况**？

**怎么修**：把判断条件写成**互斥且可观测**的：

```markdown
<!-- 改前：两条分支都沾边 -->
- 素材较多时走批量路径
- 素材较少时走单条路径

<!-- 改后：给一个可数的界线 -->
- 素材 ≥ 5 条：走批量路径
- 素材 < 5 条：走单条路径
```

**判据里不出现数字或明确的可观测特征，就一定会有误判。**

### C4 · 步骤跳了或顺序错了

**现象**：漏了中间某步，或者把两步颠倒了。

**怎么验证**：把实际执行顺序和正文步骤编号对一遍，找出第一个偏离点。

**怎么修**：

- 给步骤**编号**（不要用无编号的项目符号列表）
- 在步骤之间加**依赖声明**：「第 3 步必须在第 2 步通过后才能开始」
- 步骤超过 10 条就考虑分组，每组给一个「本组做完的标志」

### C5 · 有步骤没有结束判定，模型自己认为做完了

**现象**：每一步都做了，但做到什么程度算完，是它自己定的。

**怎么验证**：检查每条步骤末尾——有没有「算完成的标志」？

**怎么修**：每条步骤补一个可验证的结束条件（命令退出码、文件存在、字段非空、字数范围）。**没有结束判定的步骤，一定会被提前结束。**

### C6 · 产出格式的约定不够具体

**现象**：内容对，但格式和你期待的不一样——该用表用了列表，该分节没分节。

**怎么验证**：把技能里对产出格式的描述和实际产出并排看。技能里是不是只写了「输出一份报告」？

**怎么修**：给**最小骨架**，不要只给形容词：

```markdown
产出格式（按此骨架）：
## <标题>
- 结论（一句话）
- 依据（3~5 条，每条一行）
- 待办（负责人 · 动作 · 截止）
```

格式约定写得越像模板，产出越稳定。**「写得好一点」不是格式约定。**

### C7 · 上下文被别的技能污染了

**现象**：产出里混合了**别的技能**的口径——格式像 A，步骤像 B。

**怎么验证**：看产出里有没有出现你不认识、但环境里另一个技能定义的规则。

**怎么修**：

- 在正文里写清优先级：「本流程的步骤顺序为准；产出格式按本文件第五节」
- 按第五节的冲突处置切开触发面
- 两个技能确实会同时参与时，在专用技能里显式指路，明确谁说了算

### C8 · 范围蔓延，做多了

**现象**：产出比你要的多——它顺手加了建议、加了附录、改了不该改的东西。

**怎么验证**：对照技能里的「不覆盖」一节，看它有没有越界。

**怎么修**：在正文里加**负向约束**，明确写「不要做 X」。只写「做什么」的技能会自然膨胀；「不做什么」和「做什么」同样重要。

## 五、触发面冲突的处置

两个技能抢同一个触发面时，从用户视角看起来非常像 A4（描述太宽），但**根因不同、改法不同**，要先分辨。

### 分辨方法

| 现象 | 根因 | 走哪支 |
|---|---|---|
| 只有**某一个**技能从不触发 | 它自己的描述区分度不够 | A4 |
| **两个都会触发**，产出各取一半 | 触发面真重叠 | 本节 |
| 每次触发的都是**另一个**技能 | 对方的触发面覆盖了你 | 本节 |

### 处置顺序（从轻到重）

**第 1 步 · 加限定词切开**

给自己的描述加领域限定词，把区分度做出来。改动最小，先试这个。

**第 2 步 · 显式让路**

把自己的重叠部分从描述里**删掉**，并在排除句里写明归属：

```text
<重叠场景> 不要使用本技能，交给 <对方技能>。
```

**注意**：让路不等于放弃这个技能，是让它只在自己真正独有的场景里触发。宁可少触发几次，也不要每次都触发错的那个。

**第 3 步 · 显式指路**

两个必须共存（一个通用、一个专用）时，在**专用的那个**描述末尾写清优先级：

```text
同时符合两者时优先使用本技能；仅当 <专用条件> 不成立时才使用 <通用技能>。
```

**第 4 步 · 降级合并**

上面三步都做不通，说明这两个触发面本质上是一个。**合并成一个技能**，用内部分支区分——一个能触发的技能，胜过一个永不触发的技能和一个老触发错的技能。

**不要做的事**：靠把自己的描述写得更长、更强势来抢词。这会同时拉高两个技能的误触发率，而**产出会退化成「各取一半」，比只用其中一个更差**。

## 六、修复后的回归与固化

改完一处，**不要直接收工**。按这个顺序走一遍：

### 第 1 步 · 单变量重跑

- 这一轮**只改了一处**（一处描述、一句排除句、或一条步骤）
- 在干净新会话里**重跑全部 20 条测试集**，不要只跑不通过的那几条
- 原因：改动 A 常常会同时影响 B 和 C 的触发行为，只跑失败项会漏掉回归

### 第 2 步 · 对比记分

| 指标 | 上一轮 | 本轮 | 判断 |
|---|---|---|---|
| 正例命中 | | | 掉了 → 改过头了 |
| 负例误触发 | | | 升了 → 描述太宽了 |
| 边界句行为 | | | 变化方向符合预期吗 |

**三个数一起看**。只看一个数会得出错误的结论——比如正例命中涨了，但负例误触发也涨了，这通常不是进步，而是把描述写宽了。

### 第 3 步 · 记录判定依据

在 `trigger-tests.md` 末尾追加一小节，写清：

- 本轮改了什么（**原文 → 改后**，一字不差）
- 三个指标怎么变的
- 这次改动保留还是回滚

**为什么必须记**：技能会长期演化。三个月后有人问「这个排除句为什么这么写」，没有这份记录就只能靠猜，猜错就把它删了。

### 第 4 步 · 版本化

- 只改错别字、排版 → 不动版本号
- 改描述、改步骤顺序、改判据 → 升一个位
- 改了触发面（老用法会失效）→ 大步升，并在变更记录里写明「触发条件已变」

### 第 5 步 · 固化防复发

同一个症状修好之后，把**它对应的检查点**加进技能自己的自检清单，并加一条回归测试句。

```markdown
<!-- 在 trigger-tests.md 里加一条 -->
| 21 | 正例（回归） | <这次踩过的说法> | 触发 | | | 防 <症状> 复发 |
```

### 第 6 步 · 排查失败的两条出路

如果同一个症状**修了三轮还没好**，停止调参数，转做这两件事之一：

1. **这个触发面本身立不住**。可能这件事不该独立成一个技能——合并进相邻技能，或者降级成 `AGENTS.md` 里的一句显式指路。
2. **问题不在技能层**。有些行为（必须执行、必须校验）本来就该落到脚本、钩子或 CI 上，提示词层做不到硬约束。这时候继续改描述是在浪费轮次。

**判断信号**：改了描述，命中率在 50% 上下随机跳动、没有趋势——这是「描述层已经没有优化空间了」的典型特征，该换个手段了。

## 七、症状 → 修法 速查表

| 你看到的 | 大概是什么 | 先查 |
|---|---|---|
| 完全没有任何技能痕迹 | 没加载 | A1 截断 → A5 安装 |
| 提到技能里的独有口径但没做 | 加载了不动作 | B1 缺祈使句 |
| 反问你「要不要按这个流程走」 | 写成了问用户 | B4 |
| 步骤做了，做到一半就停 | 缺结束判定 | C5 |
| 产出内容对、格式不对 | 格式约定太虚 | C6 |
| 有时候触发有时候不触发 | 描述太宽 / 上下文 | A4 → A6 |
| 两个技能各出一半 | 触发面重叠 | 第五节 |
| 走错了分支 | 分支判据没有界线 | C3 |
| 产出里混了别的技能口径 | 上下文污染 | C7 |
| 改了描述命中率随机跳、没趋势 | 描述层已到极限 | 第六节第 6 步 |
| 换个人在别的客户端上就不灵 | 客户端差异 | 在目标客户端重跑测试集 |

## 八、排查纪律

1. **先分诊，再用药。** A、B、C 三支混着改，会把已经好的部分改坏。
2. **分支 A 按顺序查，不要跳。** 顺序是按出现频率排的，跳过 A1 去查 A6 是在浪费轮次。
3. **一次只改一处。** 改三处然后命中率变了，你不知道该保留哪一处。
4. **全部用新会话。** 复用长上下文测出来的结果是假的。
5. **记原文。** 改动前后都留一字不差的原文，否则回滚都没法回。
6. **同一症状修三轮无效就换手段。** 不要在第 7 次调描述的时候还以为快好了。
