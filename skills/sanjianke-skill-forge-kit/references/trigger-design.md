# 触发设计

> `description` 是技能唯一的**触发开关**。正文写得再好，描述没写对，这个技能一辈子不会被加载。
> 这份文件只解决一件事：**怎么让它在对的时候被触发、错的时候不触发。**

---

## 一、触发面三要素

写描述之前，先在纸上把这三行填出来。填不出来就别往下写正文——你还没想清楚这个技能的边界。

| 要素 | 写什么 | 反例（写了等于没写） |
|---|---|---|
| **能力陈述** | 一个动词开头、第三人称的短句，说清「它替谁做什么」 | 「关于发布的一切」 |
| **触发条件** | 三条**用户真的会说的话**，用引号原样写出 | 「当需要进行发布相关操作时」 |
| **排除条件** | 至少一条「什么情况下不该用它」，并指出该归谁 | 「不适用于其他场景」 |

三条写齐后，把它们拼起来就是初版 `description`。三要素里**最容易漏的是排除条件**——不写排除，技能就会在你调一段无关文案的时候突然跳出来。

**三行写不齐的信号**：如果排除条件你一条都想不出来，通常说明这个技能的触发面其实是「整个领域」，太大了。回到源头把它缩到一件事上，或者干脆承认它现在还不该做成技能。

## 二、description 三段式公式

```yaml
description: "<做什么：动词开头、第三人称、一句话>。<什么情况下用：2~4 个具体征兆或用户说法>。<不该用的时候：排除句>。"
```

三段各管一件事，混着写是最常见的问题：

| 段 | 负责 | 写坏的后果 |
|---|---|---|
| 第一段 | 让模型知道这个技能**能干什么** | 模型判断不了相关性，干脆不选它 |
| 第二段 | 让模型知道**此刻该选它** | 技能存在但永远排在候选队尾 |
| 第三段 | 让模型知道**此刻不该选它** | 到处乱触发，用户关掉它 |

**一段好描述的样子**（用它当标尺，别照抄）：

```yaml
description: "把散落的发布步骤固化成固定顺序，并在每步给出可验证的检查点。当用户说「又要发版了」「上线前该检查什么」「发布流程走一遍」时使用。只改文案或只跑单测、不涉及发布流程时不要使用。"
```

拆开看它做对了什么：

- 第一段是**动作 + 产出**（固化步骤 + 给检查点），不是名词堆
- 第二段把用户的三种**口语说法**原样引了进去
- 第三段给了**具体的排除对象**（改文案、跑单测），而不是「其他场景」

## 三、12 组改写前后对照

下面每一条都是自建技能里真实高频的坏写法。照「改法」这一列动手，不要照抄示例文字。

### 1. 写成了技能简介，没有触发条件

- **改前**：`这是一份关于内容运营的技能。`
- **改后**：`把一篇长文拆成多平台可发的短内容。当用户说「这篇帮我分发一下」「拆成几条微博」时使用。`
- **为什么**：「关于 X 的技能」对模型没有任何决策价值——它已经知道有这么个技能了，它需要知道的是**此刻要不要选它**。

### 2. 只写了「是什么」，没写「什么时候」

- **改前**：`短视频批量剪辑流程与规范说明。`
- **改后**：`按档位批量产出短视频，输出分镜、字幕与成片清单。当用户说「这批素材帮我出几条」「按 3 分钟档位切」时使用。`
- **为什么**：缺第二段等于把选择权完全交给模型猜。猜中的概率随环境里技能数量下降。

### 3. 用内部术语，不用用户的话

- **改前**：`执行 CJ 流水线编排与门禁校验。`
- **改后**：`走一遍持续集成的检查流程。当用户说「跑一下流水线」「看看能不能合」时使用。`
- **为什么**：模型匹配的是**语义**，用户说的是「跑流水线」，描述里只有缩写，两边对不上就是漏触发。

### 4. 第一人称，把陈述句写成了推销句

- **改前**：`我可以帮你把发布流程整理清楚。`
- **改后**：`整理发布流程并固化成可复用步骤。当用户说「发布步骤太乱了」时使用。`
- **为什么**：技能描述是给编排层读的**能力声明**，不是对话台词。第一人称既浪费长度，也会让模型误以为这是用户的请求而不是可用的能力。

### 5. 排除句写成了万能句

- **改前**：`任何情况下都可以使用。`
- **改后**：`仅在需要走完整发布流程时使用；只改一行文案、只跑单测不要使用。`
- **为什么**：「任何情况下都可以」会让这个技能在所有请求里都成为候选，误触发率直接拉满。

### 6. 描述里重复正文内容

- **改前**：`发布技能。包含第 1 步检查依赖、第 2 步跑测试、第 3 步打标签、第 4 步推送镜像、第 5 步通知……`
- **改后**：`走完整发布流程，按固定顺序产出可验证的检查点。当用户说「发版」「上线」「走一遍发布」时使用。`
- **为什么**：描述要**控制在触发所需的最少信息**。步骤清单属于正文，摆在描述里既挤占长度，又让模型在加载前就以为做完了。

### 7. 同义词覆盖不足

- **改前**：`处理代码审查。当用户说「review」时使用。`
- **改后**：`审查改动并给出可执行的修改意见。当用户说「帮我看看这段代码」「review 一下这个改动」「这个 PR 有没有问题」时使用。`
- **为什么**：触发是语义匹配，不是字符串包含。但**把用户真实的口语变体列出来，确实能提高命中**——尤其是中英混说的场景。

### 8. 描述过长，关键句被截断

- **现象**：本地文件里描述是完整的，装进客户端后**「什么时候用」那一段不见了**。
- **改法**：把第一段压到 30 字内，第二段放最前面；把背景、价值主张、作者介绍全部删掉。
- **为什么**：很多客户端对描述有长度上限，超限的截断策略通常是**砍尾**——而尾部恰好是你写的触发条件。这是最隐蔽的不触发原因，见第七节。

### 9. 一个描述里塞了两件不相干的事

- **改前**：`做数据报表，同时也能帮你写周报。`
- **改后**：拆成两个技能。或者，如果它们确实同属一个流程：`把本周数据整理成给上级看的一页纸。当用户说「出个周报」「把这周数据汇总一下」时使用。`
- **为什么**：一个描述对应一个触发面。两件事拼在一起，模型判断相关性时会被不相关的那半拉低，两边都触不好。

### 10. 写「什么时候用」时只写动作名，不写场景

- **改前**：`在需要生成报告时使用。`
- **改后**：`把零散的排查记录整理成一份可交付的事故报告。当用户说「这事写个报告吧」「复盘材料帮我出一份」时使用。`
- **为什么**：「生成报告」是个动作，不是个场景。模型要看的是**上下文像不像**——用户说「复盘材料」的时候，它得能联想到这份技能。

### 11. 排除对象选错了（这是最容易做错的）

排除句不是随便加一句「不适用于 X」。要挑**和你的正例最像、但输出目标不同**的场景。

- **正例面**：`把一篇长文拆成多条短内容`
- **错的排除句**：`不适用于图片处理`（离得太远，写不写都一样）
- **对的排除句**：`用户只要求改写原文、不要求拆成多条时不要使用`

**为什么**：误触发几乎从不来自毫无关系的请求，全部来自**长得像**的请求。排除句的价值就在于切开这对最近邻。

### 12. 描述里出现无法验证的承诺

- **改前**：`能显著提升团队效率的发布流程技能。`
- **改后**：`按固定顺序走发布流程，每步给出可验证的检查点。当用户说「又要发版了」时使用。`
- **为什么**：形容词（显著、高效、强大）对触发没有任何帮助，只是花钱买了长度。描述里每个字都应该服务于「什么时候选我」这个问题。

## 四、排除句的写法

排除句按这个句式写，一遍就能到位：

```text
<最容易被误触发的相邻场景> 时不要使用<本技能>；<该场景> 交给 <明确归属>。
```

三个要点：

1. **相邻**：挑的是最近邻，不是最远的那个。挑法：把你写的三条正例摆出来，想「什么请求跟它们只差一个词」。
2. **具体**：写「只改文案、不动流程时」，不写「不适用时」。
3. **有归属**：写清该交给谁（另一个技能、还是直接回答）。有归属的排除句，模型执行起来是「换一个工具」，而不是「都不合适」——后者容易让它退化成自由发挥。

**三类最值得写进排除句的相邻场景**：

| 相邻场景 | 为什么容易误触发 | 排除句怎么写 |
|---|---|---|
| **输入对象相同，输出目标不同** | 用户都在提「这份文档 / 这批素材」 | 「只要求改写原文、不要求拆分时不要使用」 |
| **只是询问，不要求执行** | 用户问「发布流程一般是几步？」 | 「仅在用户要求实际执行时使用；只是询问流程知识时直接回答即可」 |
| **规模差一个量级** | 用户说「就一条，随手弄下」 | 「单条随机处理不要使用；本技能面向批量场景」 |

## 五、长度与截断

描述长度是一条**硬约束**，而且它比你想的更容易踩到。

**三条操作规则**：

1. **把触发条件写在最前面，能力陈述压到 30 字内。** 万一被截断，保住的是最该保住的那一段。
2. **删形容词、删价值主张、删作者介绍、删「本技能」的重复自称。** 这些字一个都不参与触发决策。
3. **发布前在目标客户端里回读一遍**——不是看你本地文件，是看客户端实际加载到的那份。看不到完整的后半段，就是被截断了。

**自查一次要花 10 秒**：把描述粘贴到客户端里加载这个技能，然后问它「你现在看到的这个技能的描述，最后一句是什么？」答不上来或答的和你不一致，说明被截断了。

**压缩示例**（同样的触发信息，长度差一半）：

```yaml
# 改前（约 120 字，末尾的触发条件最容易被砍掉）
description: "本技能是一套经过团队长期实践验证的、用于规范发布流程的完整解决方案，旨在帮助团队显著提升发布效率与质量，涵盖从前置检查到发布后验证的全过程。当用户需要进行与发布相关的操作时使用。"

# 改后（约 60 字，触发条件在前）
description: "按固定顺序走发布流程，每步给出可验证的检查点。当用户说「发版」「上线」「走一遍发布」时使用。只改文案、只跑单测时不要使用。"
```

## 六、和已有技能抢同一个触发面时怎么写

环境里已有技能覆盖了相邻场景时，不要靠「把描述写得更宽」来抢——那只会让两个技能都变得不可靠。按下面顺序处理。

### 第 1 步 · 先查重叠

把候选技能的关键词列出来，和自己的正例逐条对：

| 判断 | 结论 |
|---|---|
| 正例全部被对方覆盖 | **不要新建**，去改对方或直接不用 |
| 一半重叠、一半独有 | **收窄自己**，只保留独有的那半（改动见第 2 步） |
| 触发词重叠但动作不同 | **加限定词区分**（见第 3 步） |

### 第 2 步 · 收窄自己的触发面

把重叠的那部分正例从自己的描述里**删掉**，并在排除句里显式让路：

```yaml
description: "把发布流程固化成带检查点的固定顺序，面向首次搭建流程的场景。当用户说「发布流程该怎么定」「第一次上线要准备什么」时使用。流程已经存在、只是要执行一次时不要使用，那是另一个技能的范围。"
```

**注意**：让路不是示弱，是降低误触发。两个技能互相抢词的结果是模型各取一半，产出比只用其中一个更差。

### 第 3 步 · 加限定词而不是加强度

- **不要**：把自己的描述写得更「强势」（重要、必须、优先使用）——这类词对触发决定几乎没有帮助。
- **要**：加**领域限定词**。对方是「通用交付」，你就写「面向短视频投放的交付」。

### 第 4 步 · 重叠无法切开时，用显式指路

如果两个技能确实必须共存（比如一个通用、一个专用），在**专用的那个**描述末尾写清优先级关系：

```text
同时符合两者时优先使用本技能；仅当 <专用条件> 不成立时才使用 <通用技能>。
```

显式指路比让模型自己比较描述要可靠得多。

## 七、触发设计自检

写完描述，逐条过一遍。**任何一条打不上勾，先别去写正文。**

- [ ] 第一段是动词开头的第三人称陈述句，30 字以内
- [ ] 第二段有 2~4 个具体征兆，其中至少一个是用引号写出来的**用户原话**
- [ ] 第三段有一条具体的排除句，排除对象是**和正例最像**的相邻场景
- [ ] 排除句里写清了该场景的归属（交给谁）
- [ ] 描述里没有「显著提升」「强大」「一站式」这类形容词
- [ ] 描述里没有第一人称（我能 / 我将 / 帮你）
- [ ] 描述里没有把正文步骤清单搬进来
- [ ] 在目标客户端里回读过，完整可见、没有被截断
- [ ] 和仓库里已有技能的正例对照过，重叠部分已经让路或加限定词切开
- [ ] 读一遍这整段描述——假设你只知道用户会说的那句话，能判断出该不该选它吗
