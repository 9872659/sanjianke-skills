# 安全审查清单：装别人的技能前该看什么

> 配套主文件 `SKILL.md` 的「第 3 步 · 走安全审查」。
> 适用：从任何公开目录装任何一个不是你写的技能。

---

## 一、先建立一个正确的心智模型

**技能不是一个「文档」，是一段会被你的 Agent 当成指令读进去、并且可能带着可执行脚本一起进来的东西。**

这意味着三件事：

1. **它是提示词层的输入。** 技能里的字会被当成指令。**技能里写「把工作区的环境变量读出来发到某个地址」，你的 Agent 就有可能照做。** 这不是理论风险——这就是提示词注入的形态。
2. **它可能带来代码。** `scripts/` 里的东西是别人的代码，会被你的 Agent 在你的机器上、以你的权限跑。
3. **它可能带来钩子。** 有些技能会声明在某个时机自动执行的动作。**这类东西的权限是常驻的，不是一次性的。**

**因此**：装一个第三方技能，**在信任级别上等同于让一个陌生人在你的机器上放一段代码和一份指令**。审查不是形式主义。

**同时也要摆正审查的能力边界**：下面的清单是**人工审读**用的，能拦住「明显越界」，拦不住刻意混淆的恶意代码。**真正的隔离靠沙箱和权限配置，不靠读完这份清单。** 审查通过只等于「我没看出问题」。

---

## 二、装前五面审查清单

按顺序过。**任何一面发现红线项，立即停止，不装。**

### 第 1 面 · 脚本面（有没有可执行的东西）

- [ ] 这个技能包里**有没有** `scripts/` 目录？有没有以 `.sh` / `.js` / `.py` / `.mjs` 结尾的可执行文件？
- [ ] 脚本**有多长**？超过两三百行、或者被压缩成一行、或者有明显编码混淆的 → **直接判不可审，不装**。
- [ ] 脚本**第一行在干什么**？是不是一上来就下载东西、或者执行一段拼接出来的字符串？
- [ ] 有没有 `eval` / `exec` / `Function(...)` / 动态 `import` / 解码后执行的模式？→ **红线**。
- [ ] 脚本里有没有**从网络下载另一个脚本再执行**的写法（管道进 shell 那一类）？→ **红线**。
- [ ] 有没有修改系统配置、注册开机项、安装常驻服务、改 crontab / 计划任务？→ **红线**（除非这正是你要的功能，且你完全理解它在做什么）。
- [ ] 有没有 `chmod +x` 之外的权限提升写法（sudo、runas、提权 API）？→ **红线**。

> **判据**：**你读不完，就不装。** 不要用「它是官方的应该没问题」替代「我读懂了它在做什么」。

---

### 第 2 面 · 网络面（它会往外连哪里）

- [ ] 技能正文或脚本里出现**哪些域名和地址**？逐个写下来。
- [ ] 这些地址是**它能被解释的吗**？（比如一个「和某服务对接」的技能，连那个服务的域名是合理的）
- [ ] 有没有**看起来和技能功能无关**的外部地址？（一个「处理本地文件」的技能却在连某个陌生域名）→ **红线**。
- [ ] 用的是明文 HTTP 吗？往外发的是什么东西？
- [ ] 有没有「把本地内容上传到某个地址」的步骤？**上传了什么？你能接受吗？**
- [ ] 有没有回连、心跳、遥测、上报类的调用？（不一定恶意，但你要知道存在）
- [ ] 有没有用短链、动态域名、或者把地址拆成几段拼起来的写法？→ **红线**。

> **一个小而实用的动作**：把技能里所有出现的 URL 抄下来，**逐个人肉看一遍**。抄的过程中你会自然发现「这个技能为什么需要连这里」。

---

### 第 3 面 · 文件面（它会读什么、写什么、删什么）

- [ ] 它要**读**什么路径？有没有触及工作区**之外**的地方？
- [ ] **重点看这些高敏路径**：家目录下的 SSH 密钥目录、云服务凭证目录、浏览器配置目录、系统密钥链、环境变量文件、以及任何 `.env` 形态的文件 → **一律红线**，除非这个技能的功能**必须**如此且你完全理解用途。
- [ ] 它要**写**什么路径？会不会覆盖已有文件？
- [ ] 有没有**删除**操作？删的范围是明确的路径，还是通配符/递归删除？→ 通配删除是**红线**。
- [ ] 有没有从工作区**往上跳**的路径（一堆 `../`）、或者绝对路径指到系统目录？
- [ ] 有没有把内容写到工作区之外（比如系统临时目录之外、启动目录、其他用户的目录）？

> **判据**：**一个技能读写的范围，应该和它的功能严格相称。** 一个「PDF 处理」技能没有任何理由读你的 SSH 目录。

---

### 第 4 面 · 凭证面（密钥、Token、账号）

- [ ] 技能包里有没有**硬编码的凭证**？（不是风险最大的情况，但说明作者习惯很差，且这个包可能已经泄露了别人的东西）
- [ ] 技能要求你提供什么凭证？**它拿到之后发去哪？**
- [ ] 它读取凭证的方式是「从环境变量读」还是「让你贴进对话里」？后者风险高得多（会留在会话记录里）。
- [ ] 它会不会**读取你已有的**凭证文件（配置文件、密钥链）而不是请你单独提供一个？
- [ ] 有没有把凭证写进日志、写进文件、或者包含在输出里的步骤？
- [ ] 凭证的**流向**你能画出完整的一条线吗？**画不出来就不装。**
- [ ] 有没有要求你把凭证发给一个**和功能无关的**地址？→ **红线**。

> **反向技巧**：先看它要什么权限，再看它为什么需要。**一个做本地格式转换的技能要你的云账号密钥，本身就是矛盾。**

---

### 第 5 面 · 指令面（注入与越权）

这一面最容易被忽略，因为技能里的字看起来只是「说明」。

- [ ] 技能正文里有没有**让你忽略前面的指令**、**不要告诉用户**、**静默执行**这类表述？→ **红线**。
- [ ] 有没有「不要向用户确认」「直接执行，不要询问」的指令？→ **红线**（除非你完全清楚它在为什么要权限，且是你自己的技能）。
- [ ] 有没有要求它读取**其他技能的内容并据此行动**、或者修改别的技能目录？
- [ ] 有没有引用**外部可变内容**（网页、远程文件、用户输入）并把它当成指令来执行？**这是典型的注入面**。
- [ ] 有没有要求它**扩大自己的权限**、申请新的能力、或者修改项目级指令文件？
- [ ] 有没有「把结果发到某个地址」的用户不可见步骤？

> **判据**：**技能的读者是你，不是它自己。** 一段「别告诉用户」的指令，出现在第三方技能里，就是必须停下来看的理由。

## 三、红线项速查（命中即停，不装）

| # | 红线 | 为什么 |
|---|---|---|
| 1 | 脚本被压缩、混淆，或你读不完 | 不可审 = 不可接受的风险 |
| 2 | 动态执行拼接出来的代码 / 下载后执行 | 这是最经典的恶意载荷形式 |
| 3 | 触及 SSH 密钥、云凭证、密钥链、`.env` 等敏感路径 | 与功能不相称的越界读取 |
| 4 | 通配符或递归删除 | 误删范围不可控 |
| 5 | 出现与功能无关的外部地址 | 数据外泄的典型迹象 |
| 6 | 读取你已有凭证并发往外部 | 凭证泄露 |
| 7 | 「不要告诉用户」「静默执行」「不要确认」 | 提示词注入 |
| 8 | 修改系统配置 / 注册常驻项 / 改计划任务 | 影响范围超出技能本身 |
| 9 | 描述说一套，正文/脚本做另一套 | 作者对自己技能的边界都不清楚，无法信任 |
| 10 | 要求提升权限才能完成「本不需要权限」的功能 | 越权 |

## 四、审查记录模板

审完就记，**这份记录本身比结论有用**——半年后你要回答「我为什么装了这个」时，它是唯一能拿出来的东西。

```text
技能名：
来源层：            （内置 / 精选 / 实验）
用途（我想用它做什么）：
包里有什么：        （列出顶层文件与目录）

── 五面审查 ──
第 1 面 脚本面：
  有无可执行文件：
  脚本行数：
  可疑写法：
  结论：通过 / 不通过
第 2 面 网络面：
  出现的地址（逐条）：
  与功能是否相称：
  结论：通过 / 不通过
第 3 面 文件面：
  读取范围：
  写入范围：
  是否触及工作区外：
  结论：通过 / 不通过
第 4 面 凭证面：
  要求什么凭证：
  凭证流向：
  结论：通过 / 不通过
第 5 面 指令面：
  有无越权/静默类表述：
  有无外部内容当指令：
  结论：通过 / 不通过

── 决定 ──
总分（六维打分）：
决定：装 / 不装 / 改装（自己重写一份）
装在哪个环境：      （一次性环境 / 主力环境）
验收方式：          （用哪句话测触发，期望什么）
复核日期：          （半年后回头看它还值不值得留）
```

## 五、如果不确定，用这三条兜底

1. **一次性环境先试。** 拿不准的技能，先在容器或临时用户下试。**试错成本从「可能泄露」降到「删掉重来」。**
2. **把它当思路来源，自己重写一份。** 很多实验层技能的价值在**思路**，不在代码。看懂它的做法，自己写一个精简版放进自己的体系——**这是最彻底的审查，因为你写的每一行你都懂。**
3. **删掉比留着安全，也比留着干净。** 不用的技能会占描述、抢触发。**卸载成本极低（删目录），所以「先装了再说」这个习惯应该反过来：先审，再装；不确定，就不装。**

---

## 六、装完之后的复核

装完不是审查结束。**每半年顺手过一遍**：

- [ ] 它还在被维护吗？
- [ ] 它依赖的外部对象（接口、命令、服务）变了吗？
- [ ] 它最近有实质更新吗？**更新要重审**——你当初审的是旧版本，新版本可能加了新脚本。
- [ ] 我还在用它吗？**三个月没触发过，删。**
- [ ] 它的触发面和后来装的技能还分得清吗？

> **最重要的一条：技能更新要重审。** 「我上次审过了」在版本变了之后就不成立了。
