# 触发不稳定怎么排查

> 配套主文件 `SKILL.md` 的「技能写了但不触发 / 乱触发」。
> 适用：自己写的技能不触发；装来的技能不触发；两个技能互相抢；同一句话两次结果不一样。

**先把预期摆正**：触发是**概率行为**，不是开关。Agent 是否主动调用一个技能，取决于客户端实现、当前上下文、可用技能的数量、以及技能之间的竞争。**没有任何 description 能保证 100% 触发。** 所以本文件的目标不是「调到必触发」，而是：**把不该有的失灵排掉，把剩下的不确定性用显式指路兜住。**

---

## 一、三步定位法

**不要跳步。** 顺序反了会浪费大量时间：

```text
第 1 步：确认技能被加载了吗？      → 没加载，改描述改到天亮也没用
第 2 步：确认描述被看见了吗？      → 加载了但被截断/被覆盖，等于没写
第 3 步：确认描述匹配了吗？        → 前两步都过了，才轮到讨论措辞
```

### 第 1 步 · 加载确认（2 分钟）

| 检查 | 怎么看 | 不通过怎么办 |
|---|---|---|
| 目录放对位置了吗？ | 技能要放在客户端约定的技能目录下，不是随手放 | 挪到正确位置 |
| 装完重启客户端了吗？ | 大多数客户端**只在启动时扫描**技能目录 | 重启，再测 |
| 目录结构对吗？ | `SKILL.md` 必须在**技能目录的根**，不是嵌在子目录里 | 把 `SKILL.md` 提到根 |
| frontmatter 能解析吗？ | 是否以 `---` 开始并以 `---` 结束；缩进是否被破坏 | 修好格式 |
| 必需字段齐全吗？ | 名称、描述是硬门槛；缺一个整个技能可能被跳过 | 补齐 |

**判定通过**：客户端能列出这个技能，或你能在会话里看到它的元信息。

### 第 2 步 · 可见性确认（3 分钟）

技能加载了，不等于它的描述进入了决策视野。

| 检查 | 症状 | 修法 |
|---|---|---|
| 描述被截断了吗？ | 描述很长，关键场景句被放在后半段 | **把「何时使用」挪到描述最前面** |
| 技能数量过多吗？ | 装了二三十个技能，新增的那个总是不被选 | 删掉不用的。**技能越多，单个被选中的概率越低** |
| 被同名/相近技能盖住了吗？ | 有两个技能名字或描述很像 | 合并、改名、或明确分工 |
| 描述是「我是什么」型吗？ | 通篇介绍功能，没有一句场景 | 改写成「当用户……时使用」 |
| 场景句写得太抽象吗？ | 写的是「处理数据类任务」，你问的是「帮我把这表清洗一下」 | 换成用户真会说的词 |

### 第 3 步 · 匹配确认（5 分钟）

前两步都过了才到这里。**这时的失灵通常不是措辞问题，而是范围问题。**

| 症状 | 根因 | 修法 |
|---|---|---|
| 该触发时不触发 | 描述里的场景词和你的说法对不上 | 把你自己会说的**原话**加进触发场景 |
| 换个说法就不触发 | 描述只覆盖了一种表述 | 加同义说法；但别堆关键词，加**真实用例** |
| 不该触发时乱触发 | 描述太泛，吃掉了相邻任务 | 加限定条件（「且……重要时」「仅在……场景下」） |
| 两个技能轮流被选 | 触发面重叠，模型每次随机选一个 | 见第三节「重叠型失灵」 |
| 同一句话两次结果不同 | 正常波动，不是 bug | 见第五节「稳定性」 |

## 二、失灵速查表

按症状直接查。**表里的「先查」列就是三步定位法里的顺序。**

| # | 症状 | 先查 | 最可能的根因 | 修法 |
|---|---|---|---|---|
| 1 | 完全没反应，像没装 | 第 1 步 | 没放对目录 / 没重启 / `SKILL.md` 不在根 | 挪位置、重启 |
| 2 | 完全没反应，但确认加载了 | 第 2 步 | 描述被截断 | 场景句前置 |
| 3 | 只有用户点名才用 | 第 2 步 | 描述是「我是什么」型，没有何时使用 | 改成场景句开头 |
| 4 | 偶尔触发，不稳定 | 第 3 步 | 描述里的词和用户说法只有部分交集 | 用真实原话替换书面词 |
| 5 | 换个人说就不触发 | 第 3 步 | 触发面绑定了特定措辞，不是意图 | 补 2~3 种同义说法 |
| 6 | 老是跑到别人的活上 | 第 3 步 | 描述太泛 / 缺少限定条件 | 加边界条件，或缩小职责 |
| 7 | 和另一个技能抢 | 第 3 步 | 触发面重叠 | 合并或明确分工（见第三节） |
| 8 | 之前好用，现在不触发 | 第 1 步 | 客户端升级后目录约定变了 / 技能被覆盖 | 重新确认加载 |
| 9 | 触发了但做错 | 不是触发问题 | 正文步骤不可判定 | 去 `writing-a-triggerable-skill.md` 查正文写法 |
| 10 | 触发后只做了一半 | 不是触发问题 | 正文太长，后半段没被读完 | 拆分，长资料挪进 `references/` |

> 注意第 9、10 条：**触发失灵和执行力失灵是两类问题**。触发失灵在 frontmatter 层，执行力失灵在正文层。分开修，别混着改。

## 三、四种失灵类型与对应修法

### 类型 A · 加载型（技能根本没进来）

**特征**：无论怎么说都没反应，且客户端列不出它。

**排查清单**：

- [ ] 目录层级：技能目录的**直接子文件**里有 `SKILL.md` 吗？
- [ ] 位置：在客户端约定的技能根目录下吗（不是子目录、不是别的盘）？
- [ ] 重启：装完重启过吗？
- [ ] 格式：frontmatter 的 `---` 成对吗？YAML 缩进对吗（用了 Tab 会挂）？
- [ ] 字段：名称、描述都在吗？
- [ ] 命名冲突：有没有两个技能同名？

**修法**：全部逐项对齐。**这一层不用改措辞，改了也没用。**

---

### 类型 B · 路由型（进来了但不被选中）

**特征**：能列出它，但它从不自动触发；用户点名才用。

**根因**：description 没有提供**路由信号**。

**修法**（按优先级）：

1. **把「何时使用」写到描述的最前面。** 决策时先读到的是开头。
2. **用用户的原话，不用书面语。** 你写「执行表格结构化提取」，用户说的是「把这表弄干净」——写后者。
3. **加限定条件防止过泛。** 格式：`当用户要 X，且 Y 时使用`。
4. **点出关键手段。** 让模型知道它有办法做，而不是「这技能大概能做但我不知道怎么下手」。
5. **补默认提示词。** 客户端元信息里的默认提示词是**最直接的触发引导**——把用户会说的那句话写进去。

**修完必须重测**，不要一次改五处然后不知道是哪处起的作用。**一次改一处。**

---

### 类型 C · 重叠型（两个技能互相抢）

**特征**：同一句话，有时选 A 有时选 B；或者两个都被加载，结果各做一半。

**这是最伤的一种失灵**——**产出比只用其中一个更差**，因为模型会把两套步骤混起来。

**排查**：

把两个（或多个）技能的 description 各抄一行，并排放在一起：

```text
技能 A：当用户要处理文档格式转换时使用……
技能 B：当用户要处理文档内容提取时使用……
用户会说：「帮我把这份文档弄一下。」
        └─ 同时命中 A 和 B → 抢
```

**修法三选一**：

| 修法 | 适用 | 做法 |
|---|---|---|
| **合并** | 两个技能本质是同一件事的两半 | 合成一个技能，用 `references/` 分层 |
| **明确分工** | 确实是两件事，只是措辞撞了 | 各自加上**排他性限定**：「仅当……时使用」；并在项目级指令里写明「A 管什么、B 管什么」 |
| **删一个** | 其中一个你已经不用了 | 直接删。**重叠没有「留着以防万一」这个选项** |

**注意**：修法二只在你能**用一句话说清分工**时才成立。说不清，就说明它们该合并。

---

### 类型 D · 上下文型（取决于当时在聊什么）

**特征**：同样的句子，在讨论 A 话题时会触发，在讨论 B 话题时不触发。

**根因**：触发决策看的不只是 description，还有**当前上下文**。上下文里的信息会和技能描述竞争。

**这不是 bug，是机制。** 应对方式：

- **重要流程不要指望自动触发。** 在项目级指令文件（如仓库里的 `AGENTS.md` / `CLAUDE.md` 之类）里**显式指路**：「做 X 的时候，读 `skills/<name>/SKILL.md`」。这是最可靠的兜底。
- **把技能收窄**，让它在一个明确的话题里稳定命中，而不是指望它在任何话题里都被想起来。
- **接受它。** 触发不确定的代价，应该由「显式指路」来补，而不是靠把描述写得越来越长——描述越长，越容易引发类型 C。

---

## 四、验证触发的最小方法

**不要用「这个技能能做什么」提问**，那是在考它，不是在测路由。要用**真实任务句**：

| 轮次 | 输入 | 期望 | 记录 |
|---|---|---|---|
| 1 | 第 0 步写下的第 1 句原话 | 选中该技能并执行 | 选中 / 未选中 |
| 2 | 同一件事的**口语化换说法** | 仍然选中 | 选中 / 未选中 |
| 3 | 同一件事的**书面化换说法** | 仍然选中（说明匹配的是意图不是措辞） | 选中 / 未选中 |
| 4 | 一件**相邻但不属于它**的事 | 保持安静 | 安静 / 误触发 |
| 5 | 第 1 句再说两遍 | 三次结果一致 | 一致 / 波动 |

**判定**：

- 1、2、3 全中 → 触发面合格。
- 4 误触发 → 描述过泛，加限定条件（类型 B/C）。
- 5 波动 → 正常。**不要为了消除波动而无限加长描述**，改用显式指路兜底。

**测试纪律**：一次只改一处，改完重跑全部 5 轮。**同时改三处，你永远不知道是哪处起了作用。**

---

## 五、稳定性：能不能做到 100%

**不能。** 说清楚这件事比给一个假的保证有用：

1. **触发是模型决策，不是字符串匹配。** 同一句话在不同上下文里权重不同，结果就可能不同。
2. **技能数量会稀释触发率。** 可用选项越多，单个被选中的概率越低。**控制技能总数是最有效的稳定性手段。**
3. **提高稳定性 ≠ 加长描述。** 描述越长，越容易和别的技能重叠，反而更不稳定。**加长的收益在某个点之后是负的。**
4. **唯一的硬兜底是显式指路。** 项目级指令里点名「做 X 时读 Y」，比任何描述技巧都可靠。

**实操建议**：把技能分成两类——

| 类别 | 策略 |
|---|---|
| **锦上添花型**（触发不到也不影响大局） | 靠自动触发就行，别折腾 |
| **关键流程型**（触发不到会出错） | **必须在项目级指令里显式指路**，不依赖自动触发 |

## 六、排查记录模板

每次排查记一行，三次之后你会看出规律：

```text
日期：
技能名：
症状：            （不触发 / 乱触发 / 抢触发 / 波动）
三步定位走到第几步：
  第 1 步加载：通过 / 不通过 → 原因
  第 2 步可见：通过 / 不通过 → 原因
  第 3 步匹配：通过 / 不通过 → 原因
改了什么：        （只写一处）
重测结果：        （5 轮里中了几轮）
结论：            （修好了 / 改用显式指路 / 删除）
```

**加一列「同类症状之前出现过吗」**——如果同一个症状反复出现，问题不在这个技能，在你写技能的习惯里。
