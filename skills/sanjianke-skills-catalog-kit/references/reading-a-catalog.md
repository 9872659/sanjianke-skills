# 技能目录怎么读与怎么挑

> 配套主文件 `SKILL.md` 的「第 1 步 · 认目录分层」。
> 目标：打开任何一个陌生技能目录，10 分钟内知道**它怎么分的、该从哪一层开始看、一个技能包里有什么**。

---

## 一、目录的三层结构

公开技能目录几乎都长成同一个形状：一个 `skills/` 目录，下面按**筛选强度**分两到三层。层级是你最先要读的信息——它比技能名字重要得多。

### 第 1 层：内置层（随客户端走）

**特征**：目录名常以点开头（如 `.system`），或写在客户端的发行清单里。这类技能**随客户端版本自动可用**，不需要你逐个安装。

**里面通常放什么**：自我扩展类能力——创建新技能、安装别人的技能、生成图片、查官方文档。它们是**生态的地基**，其他技能靠它们进来。

**你怎么处理**：

- 知道它存在，别重复装一个同名的社区版。
- 它们的说明是**学习写技能的最好样本**：一个「教你怎么写技能」的技能，本身就是最规范的技能。
- 升级客户端后回头看一眼——内置层常常在悄悄变强，你以前手写的东西可能已经出厂自带了。

### 第 2 层：精选层（有人筛过）

**特征**：目录名常是 `.curated` 之类，或者干脆平铺在 `skills/` 下。**有人按某个标准筛过一遍**，数量适中（几十个量级），覆盖工具连接、文档处理、部署、安全等常见场景。

**你怎么处理**：

- **优先从这里挑。** 筛选本身替你省掉了大部分「装完发现是垃圾」的试错。
- 但「筛过」不等于「适合你」——它筛的是通用质量和合规，不是你的任务契合度。打分卡照打不误。
- 注意**成组出现**的技能：同一个工具/平台可能拆成好几个技能（连接、查询、生成各一个）。**先问「我需要几个」，而不是「能装几个」**，装多了必然互相抢触发。

### 第 3 层：实验层（未筛选）

**特征**：目录名常是 `.experimental` 之类，或者干脆是一个单独的分支/PR。**未经筛选**，思路新、更新勤，但质量、维护、安全性全是未知数。

**你怎么处理**：

- **可以用，但只在一次性环境里用。** 别在你的主力账号、主仓库、生产路径上试。
- **强制走安全审查**（见 `security-review.md`），且把「可审性」这一维当成一票否决项——读不懂就不装。
- **不要把它当依赖。** 实验层的技能随时可能改名、改结构、被删。要长期用，就把它当作**思路来源**，自己重写一份放进自己的体系。

> **分层的通用识别法**（换一个目录也适用）：不要背目录名，问三个问题——
> 1. **来源是谁？**（客户端官方 / 官方筛选过的第三方 / 任何提交者）
> 2. **谁筛过、按什么标准筛？**（说明书里一般会写；不写就是没筛）
> 3. **装了之后是自动生效，还是要我显式指定？**（需要显式指定的，通常是未经筛选的那一层）

## 二、一个技能包内部有什么

分层看完，再看单个技能包。几乎所有目录都遵循同一套目录约定：

```text
<skill-name>/
├── SKILL.md          # 必需。frontmatter（元信息）+ 正文（步骤与判据）
├── agents/           # 常见。客户端自身的接口元信息，如展示名、一句话简介、默认提示词
├── references/       # 常见。长资料：参考表、清单、API 速查、坑位说明
├── scripts/          # 可选。可执行脚本——安全审查的重点区域
├── assets/           # 可选。图片、模板文件
├── evaluations/      # 少见。作者自带的测试用例
├── examples/         # 少见。完整输入输出样例
└── LICENSE.txt       # 常见。注意：许可证是**逐个技能**给的，不是整个目录一个
```

**读包顺序建议**：先读 `SKILL.md` 的 frontmatter（判断触发面）→ 读 `SKILL.md` 的正文骨架（判断它是流程型还是资料型）→ **如果有 `scripts/`，直接跳过去看脚本**（判断风险）→ 最后才看 `references/`（判断深度够不够）。

不要反过来：先读 references 容易被内容的丰富程度误导，误以为「这么详细一定靠谱」。

### frontmatter 里值得看的字段

| 字段 | 它告诉你什么 | 怎么用 |
|---|---|---|
| `name` | 技能的标识，通常是 kebab-case | 是否自解释？`pdf` 比 `doc-tool-v2` 好 |
| `description` | **触发面**。这是全包最重要的一个字段 | 里面有没有「何时使用」？用的是你说的那种话吗？ |
| `metadata` / 客户端元信息 | 展示名、一句话简介、默认提示词 | `default_prompt` 能看出作者预期你怎么用它 |
| `license` | 授权 | 要商用/再分发就必须看；没写就是不确定 |
| `version` | 版本 | 有没有版本号，本身是维护态度的信号 |

### 一个被低估的信号：description 的写法

留意两种风格的分野：

- **写「我是什么」**：介绍功能、罗列能力。→ 这类技能**依赖你主动点名**才会用。
- **写「什么时候用」**：以「当用户要……时使用」开头，把场景说清楚。→ 这类技能**有机会被自动触发**。

**多技能目录里，第二种明显更常见也更被推荐。** 这条观察直接决定了你自己写技能时该怎么写 description（见 `writing-a-triggerable-skill.md`）。

## 三、安装与生效机制

读目录时把这几条搞清楚，能省掉一半「装了没用」的困惑：

1. **安装方式分两类**：内置层随版本自动到位；其他层需要你显式安装。常见安装渠道是**一个内置的安装器技能**（你用自然语言告诉它装哪个），或**直接给出仓库里的目录地址**。
2. **按名字装 vs 按路径装**：按名字装通常默认从精选层找，要装实验层的**必须显式指定目录**。这本身就是一道防误装的设计。
3. **安装后一般需要重启客户端**才能被识别。说明书里通常明确写了这一点——**没重启就下结论「这技能没用」是最常见的误判**。
4. **许可证是逐个技能的。** 目录根上的说明只管目录本身，单个技能目录里的许可证文件才是那个技能的授权。要再分发，逐个看。
5. **删掉技能 ≈ 删掉目录。** 技能是纯文件，没有注册表、没有后台服务。**这意味着卸载成本极低——所以「装错了」的代价主要是上下文污染，不是系统风险。**

## 四、读目录的四个动作（10 分钟流程）

1. **列分层**（2 分钟）
   不看内容，先把这个目录分成内置 / 精选 / 实验三堆，写下每堆的数量。数量本身有信息量：精选层几十个是正常规模，几百个说明筛选标准很松。

2. **划自己的候选集**（3 分钟）
   只从**精选层**里挑出 3~5 个和你当前任务相关的，写下来。**先不要装。**

3. **读候选集的 description**（3 分钟）
   把每个技能的 description 抄下来排在一起，用你自己的话判断：哪一句最贴近你会说的那句话。**抄下来对比比逐个读完更有效**，因为差异会直接暴露出来。

4. **挑 1~2 个进打分卡**（2 分钟）
   用 `choosing-skills.md` 的六维打分卡给它们打分。**一次只装一个**，装完测触发，再决定下一个。

## 五、常见误读

| 误读 | 实际 |
|---|---|
| 「技能多说明生态强，我多装点」 | 技能数量不是资产，**触发准确率**才是。装 30 个不触发的技能，比装 3 个能触发的差得多 |
| 「精选层的技能就是官方推荐的」 | 「筛过」通常意味着合规与基本质量，**不代表它适合你的任务，也不代表它经过安全审计** |
| 「看目录名就知道是官方的」 | 带点前缀的目录名是一种**排序与筛选约定**，不是所有权证明。看许可证和实际维护者 |
| 「描述写得越详细，技能越强」 | 描述是**路由信号**，不是能力清单。过长、过泛的描述反而会和其他技能抢触发 |
| 「装了没反应就是坏了」 | 先重启客户端，再用真实句子试触发。顺序反了会白排查半天 |

## 六、交接给下一步

读完目录，你应该能回答这三个问题，答不上就回去补：

1. 我打算用的这个技能，**来自哪一层**，那一层的可信度意味着我该做什么动作？
2. 它的 **description 里那句「何时使用」**，具体是什么？
3. 它的包里**有没有 `scripts/`**，如果有，我准备怎么审？

三个都答得出来，就去 `choosing-skills.md` 打分。
