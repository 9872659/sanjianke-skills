# 一个技能从想法到可用

> 配套主文件 `SKILL.md` 的「第 3 步」与「写技能时」自检清单。
> 目标：走完六步，得到一个**能被触发、能被验证、别人也能接手**的技能。

核心判断放在最前面：**技能不是文档，是给 Agent 的执行指令。** 写文档的目标是「讲清楚」，写技能的目标是「让它在对的时候被选中，并且照着做完」。这两个目标的写法差别很大——文档可以铺陈背景，技能必须先说清什么时候用。

---

## 第 0 步（动笔前）· 先找三个具体用例

**不要先想要写什么能力，先想「你会怎么开口」。**

写下三句你**真实会说的话**，越具体越好：

```text
1. 「把这个 PDF 里的表格抽出来存成 CSV。」
2. 「这份 PDF 的排版是不是乱了，帮我看看渲染出来的样子。」
3. 「按这个模板生成一批 PDF 报告。」
```

然后问自己：

- 这三句话**指向同一个技能**吗？如果第 3 句明显是另一件事，说明你要写两个技能（或一个技能加一个 `references/`）。
- 这三句话里，**哪一句是最高频的**？它决定 description 先写哪个场景。
- 这三句话**你现在是怎么做的**？如果答案是「我随便就能做」，那就别写了。

**通过条件**：三句话能归到一个触发面下，且第二句、第三句是同一件事的不同侧面，不是两件事。

**没通过怎么办**：把范围缩到只覆盖最高频的那一句。技能宁可窄而准，不要宽而糊——宽了就会和别的技能抢触发。

---

## 第 1 步 · 定复用边界

**问：哪些内容会被重复用到，哪些只有一次？**

只有一次的内容不要进技能——它会变成噪音，让 Agent 在无关的时候也读到它。

| 内容类型 | 放哪 |
|---|---|
| 每次执行都要走的步骤、判据 | `SKILL.md` 正文 |
| 长资料：参考表、API 速查、坑位清单 | `references/`（用到才读） |
| 需要确定性执行的计算/校验 | `scripts/`（别指望模型每次心算都对） |
| 图片、模板文件、样例 | `assets/` |
| 一次性的背景介绍、项目历史 | **都不放**。不该进技能 |

**一条实用判据**：**「这段内容，如果删掉，Agent 会不会做错？」** 会 → 留下。不会 → 它是背景知识，删掉或挪进 `references/`。

---

## 第 2 步 · 建骨架、起名字

```text
<你的技能目录>/<skill-name>/
├── SKILL.md
├── references/          # 有长资料才建
├── scripts/             # 有确定性步骤才建
└── assets/              # 有模板/图片才建
```

**命名规则**：

- **小写 + 连字符**（kebab-case），不要空格、不要中文、不要驼峰。
- **名字自解释**：`pdf-table-extract` 好过 `doc-tool`，`pdf` 好过 `pdf-skill`。
- **别加版本号后缀**：版本靠版本字段管理，不靠目录名。
- **别用 `my-` / `test-` / `v2-` 这类前缀**：它们不携带信息，还会让触发判断变糊。
- **一个名字一个职责**：如果你需要加 `-and-` 才能说清它做什么，就该拆。

**骨架建议照抄同目录里最规范的那个技能的目录布局**——内置层里「教你怎么写技能」的那个技能，通常就是最好的模板来源（学它的结构，别抄它的正文）。

## 第 3 步 · 写 frontmatter（最关键的一步）

frontmatter 里，**`description` 是唯一的路由信号**，值得花掉你一半的时间。

### description 的写法

**推荐结构**：`何时使用 + 做什么 + 怎么做（点出关键手段）`

```text
✅ 好例子（结构示意）：
   "当用户需要读取/创建/审阅某类文件、且版式与视觉效果重要时使用；
    优先通过渲染成图做视觉核对，生成与抽取用 XX 库完成。"
```

拆解一下它为什么好：

| 成分 | 作用 |
|---|---|
| 「当用户需要……时使用」 | 给路由一个**明确的开启条件**，模型靠这句决定要不要选它 |
| 「且版式与视觉效果重要时」 | 加**限定条件**，防止在不该用的时候被选中 |
| 「优先通过渲染成图做视觉核对」 | 点出**手段**，模型不用猜实现路径 |
| 「用 XX 库完成」 | 点出**工具**，避免模型自创方案 |

### 反例与修法

| 反例 | 问题 | 修法 |
|---|---|---|
| 「帮助处理文档」 | 太泛，接不上任何具体句子 | 写出具体动作与对象 |
| 「这是一个很强大的 PDF 工具，支持 A、B、C、D……」 | 能力清单不是路由信号；越长越容易被误触发 | 砍掉能力罗列，留场景句 |
| 「用于 PDF 相关任务」 | 同义反复，没有增加任何判据 | 写出「什么样的 PDF 任务」 |
| 只写「我是什么」，完全不写何时用 | 只能靠用户点名，无法自动触发 | 补上「当用户……时使用」 |
| 描述里堆满了「仅限」「不要用于」等否定句 | 否定句在触发决策里权重低，写多了只占地方 | 把真正的排他条件写进正文，描述里最多留一条 |

### 其他字段

| 字段 | 建议 |
|---|---|
| `name` | 与目录名一致，避免两处不一致带来的混乱 |
| `version` | 从 `1.0.0` 起。**只在行为变了时升位**：改错别字不动，改步骤/判据/边界要动，破坏性改动走大版本 |
| `license` | 要给别人用就写清楚；不写等于不确定 |
| `metadata` / 客户端元信息 | 展示名、一句话简介、默认提示词。**默认提示词要写你真实会说的那句话**，它是最好的触发引导 |

## 第 4 步 · 写正文

### 正文长度预算

| 部分 | 建议上限 | 超过怎么办 |
|---|---|---|
| 开场（它解决什么、什么时候用） | 3~5 句 | 砍。这里不是写背景故事的地方 |
| 权限与用途说明 | 5~6 行表 | 如实填，别省 |
| 触发场景 | 3~6 条 | 用「用户会怎么说」的口吻，不是「本技能支持……」 |
| 快速开始 | 一条最短可用路径 | 超过 5 步就说明流程太重，考虑拆 |
| 工作流路由表 | 与 `references/` 一一对应 | 表里的每一行都必须指向真实存在的文件 |
| 能力边界 | 覆盖 + 不覆盖 | 「不覆盖」至少 4 条具体项，不能只写「其他」 |
| 已知限制 | 4~6 条 | 写真实的局限，不写免责声明 |
| 自检清单 | 8~12 条可打勾项 | 每条都要能判定真假 |
| **正文合计** | **≈ 500 行以内** | 超出部分全部分流到 `references/` |

### 正文写作的六条硬规则

1. **动词开头，写动作，不写愿望。**
   ✅「先检查依赖是否已装，未装就停下来问用户」
   ❌「应当妥善处理依赖问题」

2. **每个步骤都有可判定的结束条件。**
   ✅「跑通校验脚本，退出码为 0」
   ❌「确认结果正确」

3. **删掉所有「适当」「视情况」「必要时」。** 这些词等于没写指令——模型会自由发挥。

4. **判据要给具体数字或真假条件。**
   ✅「总分低于 70 就不装」「三年内没更新」「两个以上文件」
   ❌「如果感觉不太合适」

5. **不写出版物式的自我指称。** 技能是给执行者读的指令，不是给人通读的文档。直接说做什么，不要用「本文档介绍了……」这类开头。

6. **不出现真实密钥、内网地址、客户名。** 技能会跟着仓库走，读者包括未来所有会话。示例一律用占位符。

### 自由度设定：什么时候写成死步骤

这是新手最容易写错的地方。判据是**容错空间**：

| 情况 | 写法 | 为什么 |
|---|---|---|
| 只有一种正确做法，做错就出事故 | **写死**：具体命令、具体参数、具体顺序；能落脚本就落脚本 | 让模型「灵活处理」等于让它有机会做错 |
| 有多种可选做法，取舍取决于场景 | **给判据**，不给唯一答案 | 写死会逼它在不合适的时候硬套 |
| 需要主观判断（什么算「够好」） | **给检查点**，让它自己判断并汇报理由 | 硬写步骤会得到一份看着完整、实际不可执行的东西 |

**一句话**：**能验证的写死，不能验证的给判据。**

## 第 5 步 · 校验与试触发

### 5.1 结构性校验

- frontmatter 能被正确解析（以 `---` 开头并以 `---` 结束）。
- 必需字段齐全：名称、描述、版本。
- `工作流路由` 表里提到的每个 `references/` 文件都真实存在。
- 正文里没有遗留的待填占位标记（脚手架生成的 `<!-- 待填 -->` 一类注释要全部清掉）。
- 没有 `_research/` 这类本地缓存目录被打进包里。

### 5.2 触发校验（最关键）

**别用「这个技能能做什么」去测，要用你第 0 步写下的那三句真实的话去测。**

| 测什么 | 怎么测 | 通过标准 |
|---|---|---|
| 该触发 | 说出第 0 步的第 1 句 | 它被选中，且按步骤执行 |
| 该触发（换个说法） | 换一种口语说法说同一件事 | 仍然被选中（说明不是在匹配关键词） |
| 不该触发 | 说一件**相邻但不属于它**的事 | 它保持安静 |
| 稳定性 | 把第 1 句再说两遍 | 三次结果一致 |

**四类里任意一类不过，就去 `trigger-troubleshooting.md` 定位。** 不要靠「再改改描述」瞎试。

### 5.3 让一个没读过的同事走一遍

把技能给一个完全不知道背景的人（或一个全新会话的 Agent），只说那句话，不给任何额外提示。**他卡住的地方就是技能没写清楚的地方。**

---

## 第 6 步 · 迭代与版本

**迭代的触发条件**（不是凭感觉改）：

- 试触发时出现了新的、你没预料到的用例 → 补进触发场景。
- 某个步骤被反复跳过 → 说明它写得像背景知识而不是动作，重写。
- 某条判据被反复误用 → 判据不够具体，加数字或真假条件。
- 依赖的外部对象变了 → 更新，并升版本。

**版本纪律**：

| 改动类型 | 动作 |
|---|---|
| 错别字、排版 | 不动版本号 |
| 补充判据、调整步骤、扩写边界 | 升次版本（1.0.0 → 1.1.0） |
| 改触发面、删步骤、老用法会失效 | 升大版本（1.x → 2.0.0） |
