# 运维、成本与合规

上线只是开始。这份文件管三件事：**系统别倒、账单别炸、合规别漏**。

---

## 一、许可义务：上线前必须确认的第一件事

### 1.1 为什么单列一节

技术团队习惯把许可当成「上法务流程时再说」的事，但对创作台这类
**必然对外提供网络服务**的系统，许可类型会直接决定部署形态。
事后才发现问题，返工代价可能是重做整个对外服务架构。

### 1.2 强著佐权许可的义务边界

| 使用形态 | 是否可能触发源码披露义务 |
|---|---|
| 仅内部使用，不对外网络访问 | 通常不触发 |
| 对外提供网络服务 | **AGPL-3.0 下通常触发** |
| 分发修改版二进制 | 通常触发 |
| 分发未修改版二进制 | 通常需随附许可与源码获取方式 |

**AGPL 与 GPL 的关键差别**：AGPL 明确覆盖「通过网络交互」这一使用方式。
因此「我们只是部署在自己服务器上，没有分发」**不足以**成为免责理由——
只要外部用户能通过网络访问，就可能落入义务范围。

### 1.3 落地动作

- [ ] 读到 `LICENSE` **原文**，记录确切版本号（不要只写「AGPL」）
- [ ] 判断是否存在网络服务条款
- [ ] 明确当前与规划中的使用形态（内部 / 对外）
- [ ] 若涉及对外服务，评估披露范围与实现方式
- [ ] 由法务或合规负责人**书面**确认，不由工程师口头拍板
- [ ] 把确认结果与日期存入项目档案

### 1.4 若确实触发义务，通常的做法

具体以法务意见为准，工程侧常见配合方式：

1. 在服务显著位置提供「获取源代码」入口
2. 维护一份与线上运行版本**严格对应**的源码快照
3. 每次发布同步更新快照，版本号可追溯
4. 保留许可与版权声明，不删除原作者声明

> **本节仅提示风险点，不构成法律意见。** 正式商用前请咨询专业法务。

### 1.5 生成内容的合规

除软件许可外，AI 生成内容本身还有一层要求：

- 生成的视频、图片、音频可能需要添加**显式标识**
- 面向公众传播的内容可能需要**备案或审核**
- 素材的**版权来源**必须可追溯（尤其是二创场景）
- 不得生成违法违规内容，需有内容审核环节

这一层与软件许可无关，**不要因为许可过关就以为合规过关**。

## 二、上线检查项

按组过一遍，全部勾选再对外。

**安全**

- [ ] 数据库、缓存均未直接暴露到公网
- [ ] 所有默认口令已修改（数据库、后台账号、服务端口）
- [ ] 代码库中无明文凭据
- [ ] 对象存储访问来源限制为服务端与 CDN
- [ ] 后台管理入口有访问限制或额外认证
- [ ] 已启用 HTTPS，且证书有效期在观测范围内

**功能**

- [ ] 单个镜头全链路可跑通
- [ ] 整集合成产出的文件可正常播放
- [ ] 音画时长对齐正常，无明显跳音或画面停滞
- [ ] 失败任务可重试且重试成功
- [ ] 中文标题、台词、提示词存取无乱码

**运维**

- [ ] 服务已配置开机自启与崩溃自动重启
- [ ] 日志有切割策略，不会无限增长
- [ ] 磁盘余量告警已配置（建议阈值 20%）
- [ ] 数据库备份任务已配置，**且实际恢复验证过一次**
- [ ] 已能回答：出故障时谁收到通知、多久内响应

**合规**

- [ ] 许可义务已书面确认
- [ ] 生成内容标识要求已确认
- [ ] 素材来源与授权可追溯

## 三、日常巡检

建议固定频率，纳入例行工作。

| 巡检项 | 建议频率 | 观察点 | 异常信号 |
|---|---|---|---|
| 任务队列 | 每日 | 排队数、执行中数量 | 排队持续增长不下降 |
| 任务失败率 | 每日 | 失败占比 | 超过 5% 需查因 |
| 服务日志 | 每日 | 错误与异常关键字 | 同一错误反复出现 |
| 磁盘使用率 | 每日 | 数据盘余量 | 单日增长异常 |
| 缓存可用性 | 每周 | 连通与内存占用 | 内存接近上限 |
| 备份有效性 | 每周 | 备份文件是否生成 | 连续两次无新备份 |
| 证书有效期 | 每月 | 剩余天数 | 少于 30 天 |
| 依赖版本 | 每季度 | 安全公告 | 出现高危漏洞 |

**磁盘增长异常要立刻查**：通常意味着中间素材没清理，或日志没切割，
两者都会在几天内吃光磁盘并导致服务不可用。

## 四、成本对账

### 4.1 四笔账分开记

混在一起记，出问题就找不到原因。

| 账目 | 计费方式 | 波动特征 | 优化方向 |
|---|---|---|---|
| 模型调用 | 按次 / 按量 / 按秒 | 与出片量强相关 | 减少废片、先出小样再放大 |
| 对象存储 | 按容量 | 缓慢单调增长 | 中间素材设生命周期 |
| 回源带宽 | 按流量 | 与预览量相关 | 上 CDN、压缩预览码率 |
| 转码算力 | 按机器时长 | 与合成量相关 | 合并任务、避免空转 |

### 4.2 模型调用是最容易失控的一笔

因为它和「重试」直接挂钩。**没有重试上限的任务队列等于没有预算上限。**

必须设置：

- 单个任务重试次数上限
- 单日 / 单项目调用总量上限
- 单价较高的能力（通常是视频生成）单独设额度
- 异常放量告警

### 4.3 用测算脚本先算清量级

```bash
# 估算 30 集、每集 2 分钟的存储、带宽与生成成本
python scripts/cost_estimate.py --episodes 30 --minutes 2 \
  --gen-image 40 --gen-video 30 --gen-tts 30

# 只看存储与带宽，不计生成成本
python scripts/cost_estimate.py --episodes 30 --minutes 2 \
  --gen-image 0 --gen-video 0 --gen-tts 0
```

**脚本中的单价是占位示例值，必须替换成当期真实报价再采信结论。**
测算结果用于判断量级与结构（哪一块占比最大），不用于精确预算。

## 五、故障定位顺序

### 5.1 通用四步

出问题按这个顺序查，**不要跳步**：

1. **看任务状态**：卡在哪个环节？排队、生成中、还是合成？
2. **看日志**：错误信息指向本机还是外部？超时还是拒绝？
3. **看依赖**：数据库、缓存、对象存储、模型服务是否都可达？
4. **看资源**：CPU、内存、磁盘、带宽是否触顶？

**先定位到环节，再谈修复。** 直接改配置是最常见的错误做法。

### 5.2 按现象查

| 现象 | 可能环节 | 排查方向 |
|---|---|---|
| 任务一直排队不动 | 调度 | 工作进程是否存活、并发数是否为 0 |
| 生成中长时间不结束 | 外部模型 | 是否拿到任务号、轮询是否正常 |
| 任务失败但日志无详细信息 | 异常处理 | 外部返回体是否被记录、错误是否被吞掉 |
| 合成报错 | 多媒体工具 | 输入文件是否存在、编码是否支持 |
| 成片音画不同步 | 对齐逻辑 | 配音与视频时长差、对齐策略 |
| 画面中角色不一致 | 生成环节 | 参考图是否传入、参考图数量是否超限 |
| 素材 404 | 存储 | 对象是否存在、域名是否有效、跨域是否配置 |
| 服务频繁重启 | 资源 | 内存溢出、进程被系统杀掉 |

### 5.3 音画不同步专项

这是创作台最典型的质量问题，成因通常不是「对齐算法写错了」，
而是**输入就不对**：

1. 配音文本与最终台词不一致（改过台词但没重新配音）
2. 生成视频的实际时长与请求时长不符（模型侧限制）
3. 转码时帧率或采样率被隐式改变
4. 拼接时未按顺序，或某个片段缺音频轨

**处理顺序**：先核对输入，再检查转码参数，最后才怀疑对齐算法。

### 5.4 缺乏日志时的补救

若目标项目失败信息不完整，**优先补日志再谈其它优化**。
一个只记录「任务失败」而不记录外部返回体的系统，
每次排障都需要人工复现，长期成本极高。

## 六、备份与恢复

**没恢复过的备份等于没有备份。**

| 对象 | 备份方式 | 频率 | 保留 |
|---|---|---|---|
| 数据库 | 逻辑导出 | 每日 | 30 天 |
| 对象存储成品 | 跨区域复制或定期同步 | 每日 | 长期 |
| 配置文件 | 版本化存储（不含明文密钥） | 变更时 | 长期 |
| 密钥 | 独立密文保管 | 变更时 | 长期 |

```bash
# 逻辑备份示例（配合定时任务执行）
mysqldump --single-transaction --routines \
  -u drama_app -p drama_studio > /backup/drama_$(date +%F).sql

# 恢复演练：在独立库上恢复，验证备份可用
mysql -u drama_app -p drama_studio_restore < /backup/drama_2026-01-01.sql
```

**恢复演练至少每季度一次**，并记录：耗时、遇到的问题、是否能正常起服务。

## 七、日志规范

- **必须记录**：外部任务号、本地记录号、提交时间、完成时间、耗时、失败原因
- **禁止记录**：完整 API Key、数据库口令、对象存储密钥、用户敏感信息
- **建议记录**：模型名称、耗时、是否重试、是第几次重试

日志要能回答一个问题：**这一笔钱花在了哪个分镜的哪一次调用上**。
回答不了，成本就无法优化。

## 八、升级策略

上游项目迭代快，升级前按这个顺序：

1. **读变更说明**：重点看数据库结构、配置项、接口路径是否有变
2. **备份数据库**：升级前必备份，且确认备份文件完整
3. **在测试环境先升**：不要在唯一的生产环境上试
4. **验证最小闭环**：升级后重跑一遍单镜头全链路
5. **保留回退包**：旧版本的可运行产物留一份，直到新版本稳定

**配置项变更是升级后最常见的故障源**：新版可能新增必填配置，
缺失时服务启动失败或功能静默失效。升级后逐项核对配置是必要动作。

## 十、持续改进的三个指标

只盯这三个就够，其余都是衍生：

| 指标 | 含义 | 目标方向 |
|---|---|---|
| 单集综合成本 | 一部剧总支出 ÷ 集数 | 下降 |
| 任务一次成功率 | 首次提交即成功的比例 | 上升 |
| 废片率 | 生成后未被采用的素材占比 | 下降 |

**废片率最容易被忽略，但往往是成本优化的最大空间**：
先出小样验证，再批量生成，能显著降低废片率。
