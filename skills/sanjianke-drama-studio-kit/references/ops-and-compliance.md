# 运维、成本与合规

上线那天不是终点，是另一段工作的起点。这份文件就管三件事：
**服务别倒、账单别炸、合规别漏**。

---

## 一、许可这件事，办在上线之前

### 1.1 为什么它排在第一位

工程团队的习惯是把许可留到「走法务流程的时候再说」。但对创作台这类
**注定要对外提供网络服务**的系统，许可类型会反过来决定你的部署形态。
等到上线之后才发现问题，代价可能是把整个对外架构重做一遍。

### 1.2 什么形态会触发披露义务

| 你怎么用它 | 会不会被要求披露源码 |
|---|---|
| 只在内部用，外网访问不到 | 一般不会 |
| 对外提供网络服务 | **AGPL-3.0 下一般会** |
| 分发改过的二进制 | 一般会 |
| 分发没改过的二进制 | 一般要随附许可和源码获取方式 |

**AGPL 和 GPL 的差别就在这一行**：AGPL 把「通过网络交互」明确算作使用方式。
所以「我们只是部署在自己的服务器上，并没有分发」**不足以**免责——
只要外部用户能通过网络用到它，就可能已经在义务范围里了。

### 1.3 要留下的证据

- [ ] 读到 `LICENSE` **原文**，记下确切版本号（别只写「AGPL」）
- [ ] 判断这份许可里有没有网络服务条款
- [ ] 写清现在的使用形态，以及规划中的形态（内部 / 对外）
- [ ] 如果涉及对外服务，评估披露范围与实现方式
- [ ] 由法务或合规负责人**书面**确认，不要让工程师口头拍
- [ ] 结论连同日期，一起存进项目档案

### 1.4 真的触发了，工程上通常这么配合

具体怎么做以法务意见为准，工程侧常见的动作有四种：

1. 在服务里放一个显眼的「获取源代码」入口
2. 留一份源码存档，内容必须与线上正在跑的那一版**逐行对得上**
3. 每次发版同步更新存档，版本号可追
4. 许可与版权声明原样保留，不要删掉原作者的声明

> **本节只提示风险点，不构成法律意见。** 正式商用前请咨询专业法务。

### 1.5 还有一层：生成内容本身

软件许可之外，AI 生成出来的东西另有要求：

- 生成的视频、图片、音频，可能都要带**显式标识**
- 面向公众传播的内容，可能需要备案或审核
- 素材的**版权来源必须能追溯**，做二创时尤其重要
- 不能生成违法违规内容，得有一个内容审核环节

这一层跟软件许可没有关系，**别以为许可过了就等于合规过了**。

## 二、上线检查表

四组过一遍，全勾上再对外开放。

**安全**

- [ ] 数据库、缓存都没有直接暴露在公网
- [ ] 所有默认口令都改过了（数据库、后台账号、服务端口）
- [ ] 代码库里没有明文凭据
- [ ] 对象存储只允许服务端与 CDN 访问
- [ ] 后台管理入口有访问限制或额外认证
- [ ] 已经启用 HTTPS，证书有效期也在监控范围内

**功能**

- [ ] 单个镜头全链路跑得通
- [ ] 整集合成出来的文件能正常播放
- [ ] 音画时长对得上，没有明显跳音或画面停顿
- [ ] 失败的任务能重试，且重试能成功
- [ ] 中文标题、台词、提示词存取都不乱码

**运维**

- [ ] 服务配了开机自启和崩溃自动重启
- [ ] 日志有切割策略，不会无限长
- [ ] 磁盘余量告警配好了（建议阈值 20%）
- [ ] 数据库备份任务配好了，**而且真的恢复验证过一次**
- [ ] 能回答：出故障时谁收到通知、要求多久响应

**合规**

- [ ] 许可义务已经书面确认
- [ ] 生成内容的标识要求已经确认
- [ ] 素材来源与授权可以追溯

## 三、日常巡检

固定频率，编进例行工作里：

| 看什么 | 多久看一次 | 观察点 | 什么算异常 |
|---|---|---|---|
| 任务队列 | 每天 | 排队数、执行中数量 | 排队只涨不降 |
| 任务失败率 | 每天 | 失败占比 | 超过 5% 就该查原因 |
| 服务日志 | 每天 | 错误与异常关键字 | 同一个错误反复出现 |
| 磁盘使用率 | 每天 | 数据盘余量 | 单日增长异常 |
| 缓存可用性 | 每周 | 连通性、内存占用 | 内存快顶到上限 |
| 备份是否有效 | 每周 | 备份文件有没有生成 | 连着两次没新备份 |
| 证书有效期 | 每月 | 剩余天数 | 少于 30 天 |
| 依赖版本 | 每季度 | 安全公告 | 出现高危漏洞 |

**磁盘涨得快，立刻查。** 十有八九是中间素材没清理，或者日志没切割；
这两种情况都会在几天内把盘吃满，然后服务直接不可用。

## 四、把四笔账分开记

### 4.1 混在一起就找不到原因

| 账目 | 按什么计费 | 账单长什么样 | 怎么省 |
|---|---|---|---|
| 模型调用 | 按次 / 按量 / 按秒 | 跟出片量强相关 | 少出废片，先出小样再放大 |
| 对象存储 | 按容量 | 缓慢但单调上涨 | 中间素材设生命周期 |
| 回源带宽 | 按流量 | 跟预览量相关 | 上 CDN，压低预览码率 |
| 转码算力 | 按机器时长 | 跟合成量相关 | 合并任务，别让它空转 |

### 4.2 最容易失控的是模型调用那一笔

因为它直接挂在「重试」上。**一个没有重试上限的任务队列，等于一个没有预算上限的队列。**

至少要有这四道闸：

- 单个任务的重试次数上限
- 单日 / 单项目的调用总量上限
- 单价高的能力（一般是视频生成）单独给额度
- 用量异常放大时能报警

### 4.3 先用脚本把量级算出来

```bash
# 估算 30 集、每集 2 分钟的存储、带宽与生成成本
python scripts/cost_estimate.py --episodes 30 --minutes 2 \
  --gen-image 40 --gen-video 30 --gen-tts 30

# 只看存储与带宽，不计生成成本
python scripts/cost_estimate.py --episodes 30 --minutes 2 \
  --gen-image 0 --gen-video 0 --gen-tts 0
```

上面的默认单价是**示例值**，只用来判断量级和结构（哪一块占比最大），不能当预算用。
要按平台字段价估，先取一份真实单价再算：

```bash
# 到 api.a7w.cn 现拉真实单价（GET /api/v1/pricing + 各应用的 tenant_* 字段价）
python scripts/run.py pricing --probe image --out a7w-prices.json
python scripts/cost_estimate.py --episodes 30 --minutes 2 \
  --price-file a7w-prices.json --a7w-video-resolution 1080P \
  --clip-seconds 6 --tts-chars 24

# 或者省掉快照这一步，直接现拉现算
python scripts/cost_estimate.py --episodes 30 --minutes 2 --a7w-live
```

平台按点数计费：**1 元 = 100 点**，先冻结后结算，任务失败全额退回。
所以「充值金额」和「实际消耗」之间会有一段时间差，对账时按 `usage.points_cost`（同步接口
有时是 `usage.actual_points`）逐条核，不要按提交时的冻结额核。

## 五、出问题按什么顺序查

### 5.1 四步，别跳

1. **先看任务状态**：卡在哪一环？排队中、生成中、还是合成中？
2. **再看日志**：报错指向本机还是外部？是超时还是被拒绝？
3. **看依赖**：数据库、缓存、对象存储、模型服务，四个是否都可达？
4. **最后看资源**：CPU、内存、磁盘、带宽，哪个触顶了？

**先把范围缩到某一环，再动手修。** 上来就改配置，是最常见的错误动作。

### 5.2 按现象对号

| 现象 | 可能在哪一环 | 往哪查 |
|---|---|---|
| 任务一直排队不动 | 调度 | 工作进程活着吗、并发数是不是被设成 0 |
| 生成中长时间不结束 | 外部模型 | 任务号拿到了吗、轮询还在跑吗 |
| 任务失败但日志没有细节 | 异常处理 | 外部返回体记了吗、错误是不是被吞了 |
| 合成报错 | 多媒体工具 | 输入文件在不在、编码支不支持 |
| 成片音画不同步 | 对齐逻辑 | 配音与视频的时长差、对齐策略 |
| 画面里角色前后不一致 | 生成环节 | 参考图传了吗、参考图数量超限了吗 |
| 素材 404 | 存储 | 对象是否存在、域名还有效吗、跨域配了吗 |
| 服务频繁重启 | 资源 | 内存涨爆了、进程被系统清理掉 |

### 5.3 音画不同步专项

这是创作台最典型的质量问题，而且成因**通常不是「对齐算法写错了」**，
是输入本身就不对：

1. 台词改过，但配音没重做
2. 模型实际生成的时长，跟你要的时长不一样
3. 转码过程中帧率或采样率被悄悄改掉
4. 拼接没按顺序，或者某个片段压根没有音轨

**处理次序是：先核输入，再看转码参数，最后才去怀疑对齐算法。**
反过来查，通常要绕一大圈才回到起点。

### 5.4 日志不全，先补日志

如果手上这个项目失败信息不完整，**优先级最高的是补日志，不是别的优化**。
一个只写「任务失败」、不写外部返回体的系统，每次排障都得人工复现一遍，
这个成本会一直堆下去。

## 六、备份和恢复演练

**没恢复过的备份，等于没有备份。**

| 备份对象 | 怎么备 | 多久备一次 | 留多久 |
|---|---|---|---|
| 数据库 | 逻辑导出 | 每天 | 30 天 |
| 对象存储里的成品 | 跨区域复制或定期同步 | 每天 | 长期 |
| 配置文件 | 版本化存储（不含明文密钥） | 变更时 | 长期 |
| 密钥 | 单独用密文保管 | 变更时 | 长期 |

```bash
# 逻辑备份示例（配合定时任务执行）
mysqldump --single-transaction --routines \
  -u drama_app -p drama_studio > /backup/drama_$(date +%F).sql

# 恢复演练：在独立库上恢复，验证备份可用
mysql -u drama_app -p drama_studio_restore < /backup/drama_2026-01-01.sql
```

**恢复演练至少每季度做一次**，并且记下三件事：花了多久、遇到什么问题、服务能不能正常起来。

## 七、日志里该有什么

- **必须有**：本地记录号和外部任务号怎么对应、什么时候提交的、什么时候结束的、花了多久、为什么失败
- **绝对不能有**：完整 API Key、数据库口令、对象存储密钥、用户敏感信息
- **建议加上**：调的是哪个模型、这一跳是不是重试、已经是第几次

日志要能回答一个问题：**这笔钱花在了哪个分镜的哪一次调用上？**
答不上来，成本就永远优化不动。

## 八、升级

上游项目迭代快，升级之前按这个顺序走：

1. **读变更说明**：重点看数据库结构、配置项、接口路径有没有变
2. **备份数据库**：升级前必备份，并且确认备份文件是完好的
3. **先在测试环境升**：不要把唯一的生产环境当试验场
4. **验最小闭环**：升完重跑一遍单镜头全链路
5. **留回退包**：旧版本的可运行产物留着，直到新版本稳定

**升级后最常见的故障源是配置项变更**：新版本可能多出必填配置，
缺了要么服务起不来，要么功能静默失效（这种最麻烦，因为它不报错）。
升完逐项核对配置，是省不掉的步骤。

## 十、只盯三个指标

其余的指标都是这三个的衍生，不用铺开看：

| 指标 | 怎么算 | 想让它往哪走 |
|---|---|---|
| 单集综合成本 | 一部剧总支出 ÷ 集数 | 降 |
| 任务一次成功率 | 首次提交就成功的比例 | 升 |
| 废片率 | 生成出来但没被采用的素材占比 | 降 |

**废片率最容易被忽略，但它往往就是最大的省钱空间。**
先出小样验证，确认了再批量生成，废片率能明显下来。
