# 选型打分与决策

自建一套 AI 短剧创作台，真正的风险不在工期，而在方向：**底座挑错了，后面每一行代码都在给错误加杠杆**。
这份文件只做三件事——帮你判断该不该自己搭、该挑哪一个、许可是不是已经把它一票否决了。

排查顺序有讲究：**先查许可，再算成本，最后比功能**。原因是许可属于「不合格就直接出局」的硬条件，
而功能好坏只是同样能跑的两个方案之间的小分差。把硬条件放最后查，等于白做前面的功课。

---

## 一、你属于哪一类使用方

同样一份代码，装在自己机房和开给客户用，是两个完全不同的项目。先对号入座，
后面才有讨论的意义：

| 使用方 | 真正关心的事 | 该重点看的维度 |
|---|---|---|
| 内容工作室，片子自己用 | 今天能不能按时出片 | 运维可承受、故障恢复速度 |
| 技术团队，要长期改 | 能不能加功能、代码读不读得懂 | 可扩展性、技术栈是否对得上 |
| 服务商，要开给客户 | 账号隔离、配额、审计、追责 | 许可义务、集成成本 |
| 预算有限，先试水 | 最小的钱能不能验证模式 | 能否先跑通一个镜头再谈其他 |

**只要涉及「给外部的人用」，许可义务基本就是决定项**，别的维度打得再高也绕不过去。

## 二、五个维度打分

每项给自己打 1–5 分，右边的权重是建议值。权重可以按你的实际情况调，
但**别把量级调乱**：许可这种「一票否决」的维度，不该和界面好不好看放在同一个重量级上。

| 维度 | 打 5 分的样子 | 打 1 分的样子 | 建议权重 |
|---|---|---|---|
| 许可与商用可行 | 许可宽松，商用不附带额外义务 | 强著佐权，且对外提供服务要披露源码 | 0.30 |
| 集成与改造成本 | 有清晰的接口层，换供应商只动一处 | 供应商名字写死在业务代码里 | 0.25 |
| 团队匹配度 | 现有人手当天就能上手改 | 得为它专门招一个人 | 0.20 |
| 可扩展性 | 有适配器 / 插件机制 | 想加东西必须动核心 | 0.15 |
| 运维可承受 | 一台机器跑起来，日志看得懂 | 要上集群、要专职运维 | 0.10 |

打分算 **Σ(单项分 × 权重)**，然后对判定线：

| 加权总分 | 该怎么走 |
|---|---|
| ≥ 4.0 | 可以自建，按正常节奏推进 |
| 3.0 – 3.9 | 能自建，但先把拖后腿的项解决掉，并登记为风险 |
| 2.0 – 2.9 | 更建议买成熟产品，自建只留给非核心环节 |
| < 2.0 | 别自建了，直接用 SaaS |

**出现单项 1 分要单独拎出来说**，哪怕总分够了。1 分意味着有个环节会长期消耗团队的注意力，
它的伤害不是线性的。

## 三、许可：当成一票否决项先筛一遍

### 3.1 三种许可，义务差别很大

| 许可类型 | 常见代表 | 自己内部用 | 挂到网上给别人用 |
|---|---|---|---|
| 宽松型 | MIT、Apache-2.0 | 基本没有额外义务 | 基本没有额外义务，保留版权声明即可 |
| 强著佐权 | GPL 家族 | 一般没有对外义务 | **可能被要求披露源码** |
| 网络服务型 | AGPL-3.0 | 一般没有对外义务 | **只要对外提供服务就可能被要求披露** |

AGPL 的特殊之处在于它把「通过网络交互」也算进了使用方式。
所以「东西装在我们自己服务器上，又没有对外分发」这句话**不构成免责**——
外部用户能通过网络访问到，就已经落在它的射程里了。这一点和很多人对 GPL 的直觉完全不同，
也是自建团队翻车最多的地方。

### 3.2 动手确认的四步

1. **读原文**：打开仓库根目录的 `LICENSE`，不要看 README 上的徽章，两者冲突时以 `LICENSE` 为准。
2. **记版本**：带网络服务条款的是 v3，把确切版本号记下来，别只写「AGPL」两个字。
3. **定形态**：纯内部用、对外提供服务、把改过的版本再分发出去——这三种义务是逐级加重的。
4. **走流程**：结论进风险登记表，由法务或合规负责人签字，**不要让工程师在群里口头拍板**。

### 3.3 四个听起来有理、其实站不住的判断

| 常听到的说法 | 实际情况 |
|---|---|
| 「内部用，不对外，没事」 | 内部用通常确实没事；但只要你开始给客户开账号，性质就变了 |
| 「我们一行代码没改」 | 改没改不是重点，重点是你把它用在了什么形态上 |
| 「只开 API，不给界面」 | 条款盯的是「通过网络交互」这个行为，跟你有没有做页面无关 |
| 「前端是我们自己写的」 | 义务范围取决于它与受许可部分结合到什么程度，需要专业判断，不能自己拍 |

> 本节只负责把风险点摆出来，**不构成法律意见**。真要商用，请找专业法务出一份书面结论。

## 四、自建、买私有部署、还是用 SaaS

| 对比项 | 自建 | 买私有部署 | 用 SaaS |
|---|---|---|---|
| 起步投入 | 高（人力 + 服务器一起投） | 中（授权费 + 实施费） | 低 |
| 量做大之后的边际成本 | 可控，量越大越划算 | 取决于授权怎么算 | 跟着用量线性涨 |
| 数据放在哪 | 完全自己手里 | 自己手里 | 在厂商那边 |
| 能改到什么程度 | 想怎么改怎么改 | 受厂商接口限制 | 基本不能改 |
| 多久能上线 | 数周起步 | 几天到几周 | 当天 |
| 技术风险谁扛 | 自己扛 | 和厂商分 | 厂商扛 |
| 许可义务谁处理 | 自己确认 | 厂商处理 | 厂商处理 |

落到选择上，就三句话：

- 每月出片量不大、主要想验证模式能不能跑 → **先用 SaaS 试**，别急着买服务器。
- 出片量大、有稳定的技术团队、数据不能出门 → **自建**。
- 有合规要求但没人手 → **买私有部署**。

## 五、看一个候选项目要取哪些证

下面这份清单是**取证清单**，不是感受清单。每一项都要能看到实物，
「文档里写了」「看起来支持」不算数：

- [ ] `LICENSE` 原文读过，确切版本号记下来了
- [ ] README 声称的技术栈，与仓库里实际的目录结构对得上
- [ ] 存在独立的模型适配层：换一家供应商不需要改业务代码
- [ ] 依赖列得全：数据库、缓存、多媒体工具、运行时版本都在
- [ ] 有建表语句或迁移脚本，字符集写明了
- [ ] 开发配置与生产配置分开，密钥没有硬编码在文件里
- [ ] 任务状态是明确的（排队 / 执行中 / 成功 / 失败 / 能不能重试）
- [ ] 有日志或任务记录，失败时能追到具体是哪个环节
- [ ] 近期还有提交，提的 issue 有人回
- [ ] 作者留了联系方式或社区入口

**缺哪一项，就在风险登记表里写一项。** 别自己替它脑补补齐。

## 六、最容易估错的地方

| 事情 | 团队通常怎么估 | 实际会怎样 |
|---|---|---|
| 接模型 | 「不就是调个 API」 | 文本 / 图片 / 视频 / 配音四类各有各的异步流程和重试策略 |
| 合成视频 | 「FFmpeg 一行命令的事」 | 时长怎么对齐、字幕怎么烧、片段按什么顺序拼，全是坑 |
| 存储开销 | 「这个以后再说」 | 素材和成片会一直涨，回源带宽也是持续支出 |
| 并发能力 | 「不够就加机器」 | 转码吃 CPU、生成走外部 API，两边的瓶颈根本不在同一处 |
| 许可合规 | 「上线前再说」 | 事后才发现的代价可能是把对外服务架构整个重做 |

把这张表贴进项目启动文档里，能省掉后面大量的返工。

## 七、结论要怎么讲

给用户的输出按这个骨架写，别含糊：

```
结论：建议自建 / 买私有部署 / 用 SaaS
加权得分：x.xx（许可 x，集成 x，匹配度 x，扩展性 x，运维 x）
决定性理由：1~2 条
必须先解决：1~3 条，按优先级排
风险登记：条目 + 责任人 + 截止时间
下一步：一个具体动作
```

**「都可以，看你们需求」这类话不要出口。** 选型这件事的价值，就在于有人敢下判断。
