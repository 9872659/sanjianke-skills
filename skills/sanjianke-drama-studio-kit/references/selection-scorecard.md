# 选型打分与决策

这份文件回答三个问题：**该不该自建、选哪个底座、许可会不会拦路**。
顺序不能颠倒——许可这一关能否掉整个方案，先过它最省时间。

---

## 一、用之前先分类

不同身份的判断标准完全不同，先归位再打分：

| 身份 | 核心诉求 | 最该在意的维度 |
|---|---|---|
| 内容工作室，自产自用 | 出片速度、稳定性 | 可维护性、故障恢复速度 |
| 技术团队，要二次开发 | 扩展点是否够、代码是否读得懂 | 可扩展性、技术栈匹配度 |
| 服务商，要给客户开账号 | 多租户、配额、隔离、审计 | 许可义务、集成成本 |
| 预算敏感的试水者 | 先验证再投入 | 是否可以先小成本跑通 |

**给外部客户开账号这一类，许可义务几乎总是决定性因素**，其余维度打分再高
也要先解决它。

---

## 二、五维打分表

每项 1–5 分（5 最好），右侧为权重。权重可按自身情况改，但**建议保持量级**：
许可与集成成本是「一票否决型」维度，不该和界面美观度同权。

| 维度 | 5 分标准 | 1 分标准 | 权重 |
|---|---|---|---|
| 许可与商用可行 | 宽松许可，商用无附加义务 | 强著佐权且对外服务需披露源码 | 0.30 |
| 集成与改造成本 | 有清晰接口层，替换供应商成本低 | 供应商写死在业务代码里 | 0.25 |
| 团队匹配度 | 与现有技能栈一致，能立刻上手 | 需要新招一个岗位 | 0.20 |
| 可扩展性 | 有明确适配器 / 插件层 | 改动必须改核心 | 0.15 |
| 运维可承受 | 单机可跑，依赖少，日志清晰 | 需要集群与专职运维 | 0.10 |

**加权总分** = Σ(单项分 × 权重)。

| 总分 | 结论 |
|---|---|
| ≥ 4.0 | 可以自建，按标准流程推进 |
| 3.0 – 3.9 | 自建可行，但必须先解决拖后腿项，并写入风险登记 |
| 2.0 – 2.9 | 倾向采购成熟方案，自建只用于非核心环节 |
| < 2.0 | 不要自建，直接选 SaaS |

**注意**：单项出现 1 分时，即使总分达标也要单独提出来——1 分通常意味着
某个环节会持续吞掉团队时间。

## 三、许可风险识别（最容易被忽略的一步）

### 3.1 先分清两类许可

| 类型 | 典型代表 | 自用 | 对外提供服务 |
|---|---|---|---|
| 宽松型 | MIT / Apache-2.0 | 基本无义务 | 基本无义务，注意保留版权声明 |
| 强著佐权 | GPL 系列 | 通常无对外义务 | **可能触发源码披露义务** |
| 网络服务型 | AGPL-3.0 | 通常无对外义务 | **提供服务即可能触发披露义务** |

AGPL 的设计初衷就是覆盖「不分发、只提供网络服务」这种使用方式，
所以**把它部署到公网给用户用，和分发二进制在义务上差别不大**。
这一点与 GPL 的直觉完全不同，也是自建团队最常踩的坑。

### 3.2 落地前的四个动作

1. **找到许可原文**：以仓库根目录的 `LICENSE` 文件为准，
   README 徽章可能过期，两者不一致时信 `LICENSE`。
2. **确认版本号**：只有 v3 才带网络服务条款；记下确切版本，不要只写「AGPL」。
3. **判断使用形态**：纯内部使用、对外提供服务、还是把修改版再分发？
   三者义务递增。
4. **写进风险登记**：由法务或合规负责人签字确认，**不要让工程师口头拍板**。

### 3.3 常见误区

| 误区 | 实际情况 |
|---|---|
| 「我们只是内部用，没问题」 | 内部用通常没问题，但一旦给客户开账号就变了 |
| 「我们没改代码，不用管」 | 未修改也可能触发披露义务，重点在使用形态 |
| 「只提供 API 不提供界面」 | 网络服务条款看的是「通过网络交互」，不是界面形态 |
| 「前端是我自己写的就没事」 | 义务范围取决于与受许可部分的结合程度，需专业判断 |

> 以上仅提示风险点，**不构成法律意见**。正式商用前请咨询专业法务。

## 四、自建 / 采购 / SaaS 三路线取舍

| 对比项 | 自建 | 采购私有部署 | SaaS |
|---|---|---|---|
| 首期投入 | 高（人力 + 服务器） | 中（授权 + 实施） | 低 |
| 长期边际成本 | 可控，量大后更低 | 受授权模式影响 | 随用量线性增长 |
| 数据落点 | 完全自控 | 自控 | 在厂商侧 |
| 定制自由度 | 最高 | 受厂商接口限制 | 最低 |
| 上线周期 | 数周起 | 数天到数周 | 当天 |
| 技术风险 | 自己承担 | 厂商分担 | 厂商承担 |
| 许可义务 | 需自行确认 | 由厂商处理 | 由厂商处理 |

**选择建议**：

- 每月产出量小、只想验证模式 → **先 SaaS 试水**，别急着买服务器
- 产出量大、有稳定技术团队、数据不能外流 → **自建**
- 有合规要求但技术人手不足 → **采购私有部署**

## 五、底座评估的实操清单

拿到一个候选项目，用下面这张清单过一遍，**每项都要有证据**，不接受
「看起来支持」：

- [ ] `LICENSE` 文件已读到原文，并记录确切版本
- [ ] README 中的技术栈声明与仓库实际目录结构一致
- [ ] 存在独立的模型适配层（能替换供应商而不改业务代码）
- [ ] 依赖清单完整（数据库、缓存、多媒体工具、运行时版本）
- [ ] 有建表语句或迁移脚本，且字符集明确
- [ ] 配置文件区分了开发与生产，密钥不硬编码
- [ ] 任务状态机明确（排队 / 执行中 / 成功 / 失败 / 可重试）
- [ ] 有基本日志或任务记录，失败能定位到具体环节
- [ ] 最近有提交活动，issue 有人回应
- [ ] 作者给出了明确的联系方式或社区入口

**任何一项缺失都要记入风险，不要自行脑补补齐。**

## 六、容易高估与低估的地方

| 项目 | 团队常见预估 | 实际情况 |
|---|---|---|
| 模型接入 | 「接个 API 而已」 | 四类能力（文本/图片/视频/配音）各有异步流程与重试策略 |
| 视频合成 | 「FFmpeg 一行命令」 | 时长对齐、字幕烧录、拼接顺序都是坑 |
| 存储成本 | 「先不考虑」 | 出片素材的存储与回源带宽会持续增长 |
| 并发能力 | 「加机器就行」 | 转码吃 CPU、生成走外部 API，两者瓶颈不同 |
| 许可合规 | 「上线再说」 | 事后返工可能要重做部署形态 |

把这张表贴进项目初始文档，能省掉后面大量返工。

## 七、决策输出模板

给用户结论时按这个结构讲，避免含糊：

```
结论：建议自建 / 采购 / SaaS
加权得分：x.xx（许可 x，集成 x，匹配度 x，扩展性 x，运维 x）
决定性理由：1~2 条
必须先解决：1~3 条，按优先级排序
风险登记：条目 + 责任人 + 截止时间
下一步：一个具体动作
```

**不要给出「都可以，看你们需求」这类结论。** 选型的价值就在于敢下判断。
