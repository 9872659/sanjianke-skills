# 三剪客 · 企业 ERP 与 CRM

一门生意到某个阶段，客户、报价、订单、发票、库存、账目会散在微信、Excel 和几个互不相通的系统里，对不上账。它是一个自托管的开源 ERP / CRM：把客户与供应商、商机与报价、销售与采购订单、发票与收款、库存与仓储、日程与账目放进同一套数据库，自带权限体系和按需开启的模块。

它的特点不是「功能最多」，而是「按需拼装」：几百个模块可以先只用客户、报价、发票三块，跑顺了再开库存、采购、财务。代价是要你自己维护这套 PHP 服务和数据库，所以它更适合有运维能力的企业后台，而不是想开箱即用就交给别人的场景。

**上游项目**：`Dolibarr`　**仓库**：https://github.com/Dolibarr/dolibarr

## 什么时候用 / 不用

**用它**：

- 要把客户档案、报价、订单、发票、收款串成一条线，摆脱 Excel 和多套系统对不上账。
- 需要一套自托管、数据留在自己服务器上的企业后台，不接受把经营数据放第三方。
- 团队规模不大但流程已成型，想要一套模块可开可关、按需付费（零授权费）的 ERP / CRM。
- 要对接电商、财务或自研系统：需要 REST 接口把订单和发票数据接出去。
- 已经在用开源 ERP 但因授权或功能受限想换方案，希望数据自己能导出。

**不要用它**：

- 只想要一个轻量 CRM 或只记客户联系方式——模块太多，配置成本不成比例。
- 没有 PHP 运维能力也不打算托管服务器，希望厂商全程兜底；它不提供官方 SaaS 托管。
- 需要多法人、复杂多组织合并报表这类重型集团财务能力，得先评估模块是否覆盖。
- 已深度使用某商业 ERP 且迁移成本高，只是觉得「开源免费」——数据迁移才是主要成本。
- 只是要给店铺做前台展示页或小程序商城，它不是这个用途。

## 安装

Dolibarr 是 PHP + 数据库的 Web 应用，官方主推两种落地方式。

### 方式一：Docker（最快跑通）

用官方镜像 `dolibarr/dolibarr` 配一个数据库容器即可。镜像支持通过环境变量做首次自动安装（数据库地址、库名、管理员账号等），具体变量名、必填项与 compose 写法以 Docker Hub 上该镜像的说明和官方文档为准，不要照搬旧版本的变量名：

```bash
# 拉取官方镜像
docker pull dolibarr/dolibarr

# 简单试跑：把容器内的 Web 端口映射到本机 8080
docker run -d --name dolibarr -p 8080:80 dolibarr/dolibarr
```

正式用请用 `docker-compose.yml` 把数据库和 Dolibarr 放在同一网络里，并把数据库端口只对本网络开放；数据目录与数据库数据都要挂载到宿主机卷上，否则容器重建就丢数据。

```bash
# 起停与看日志
docker compose up -d
docker compose logs -f
docker compose down
```

### 方式二：传统 LAMP / LEMP 部署

1. 准备 PHP 运行环境和数据库（MySQL / MariaDB 或 PostgreSQL），下载 Dolibarr 安装包解压到站点根目录。
2. 浏览器打开站点地址，进入 Web 安装向导（`/install/`），填写数据库连通信息。
3. 向导会生成配置文件 `htdocs/conf/conf.php`；如果 Web 服务器用户对该目录没有写权限，需要手工创建这个文件并授予写权限，装完再收紧回来。
4. 向导里创建管理员账号，安装完成后**务必删除或移走安装目录**，否则等于把重装入口留在线上。
5. 站点根目录应指向 `htdocs/`，不要把仓库根目录直接暴露成网站目录。

PHP 扩展、最低版本与目录权限要求随版本变化，以官方文档 `https://www.dolibarr.org/` 上的安装说明为准。

## 常用操作

**1. 打开安装向导（首次部署，装完请立即移除该目录）**

```bash
# 浏览器访问
# http://<你的域名或IP>/install/
```

**2. 用 REST 接口读一条数据**（先在后台「设置 → 模块/应用」里启用 API/Web 服务模块，再为该用户生成 API Key）

```bash
curl -s "https://<你的域名>/api/index.php/thirdparties?limit=5" \
  -H "DOLAPIKEY: <你的APIKEY>" \
  -H "Accept: application/json"
```

**3. 用 REST 接口新建一条数据**（以第三方/客户为例，字段名以官方 API 文档为准）

```bash
curl -s -X POST "https://<你的域名>/api/index.php/thirdparties" \
  -H "DOLAPIKEY: <你的APIKEY>" \
  -H "Content-Type: application/json" \
  -d '{"name":"示例客户","client":1,"code_client":"-1"}'
```

**4. 看容器日志定位 500 / 白屏**

```bash
docker compose logs -f --tail=200
```

**5. 备份数据库（自托管方案里最要紧的一条）**

```bash
docker compose exec <数据库服务名> sh -c \
  'exec mysqldump -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"' \
  > dolibarr-backup-$(date +%F).sql
```

> 定时任务（计划作业 / cron）的示例命令行由后台「计划作业」页面生成，按它给出的路径与 PHP 二进制填进 crontab 即可；不同版本路径略有差异，以页面上的示例为准。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 打开网页白屏或报 500 | PHP 报错被隐藏了，或者扩展没装全 | 先打开 PHP 错误日志/显示错误，确认是缺扩展还是目录权限问题，再对症处理 |
| 安装向导提示无法写入配置文件 | Web 服务器用户对 `htdocs/conf/` 没有写权限 | 手工创建 `conf.php` 并临时授予写权限，装完把权限收回；不要让整个目录长期可写 |
| 装完能登录，但过一阵被重装/被扫描 | 安装目录没删 | 安装完成后立即删除或移出 Web 根目录下的安装目录 |
| 线上被改配置、被上传文件 | 目录权限给太宽（如 777） | 按官方建议设权限：代码只读、仅必要目录可写，不要图省事全开 |
| 网站能开但样式图片全丢 | 站点根目录指错了，或 URL 重写/子目录部署没配对 | 让站点根目录指向 `htdocs/`，子目录部署要按官方说明调整 |
| 中文、货币、日期显示乱码 | 数据库字符集不是 UTF-8 系列，或建库时用了默认编码 | 建库时显式指定 UTF-8 字符集与排序规则，再重装初始化 |
| API 调用一律 403 | 没启用 Web 服务模块，或用户没有 API Key，或 Key 权限不足 | 后台启用模块、生成 Key，并检查该用户的权限与模块授权 |
| 定时任务不跑，邮件/提醒不发 | 没配 cron，或 CLI 版 PHP 路径不对 | 用后台「计划作业」页给出的示例命令行配 crontab，注意用 CLI 的 php 而非 Web 版 |
| 邮件发不出去 | PHP 的邮件发送方式未配置（sendmail 缺失或 SMTP 未填） | 在后台邮件设置里改用 SMTP 并填对端口与加密方式 |
| 升级后报错、页面错乱 | 直接覆盖代码但没跑数据库升级脚本 | 先备份数据库，再按官方升级流程覆盖代码并执行升级脚本 |
| 模块开了却看不到菜单 | 没给当前用户的群组授权 | 到用户/群组权限里勾选对应模块权限，重新登录 |
| 数据量上来后列表页很慢 | 默认列表分页过大或缺少索引维护 | 调小每页条数、按需精简自定义字段，必要时按文档做数据库维护 |

## 能力边界

**覆盖**：

- 部署思路：官方 Docker 镜像跑通、传统 PHP 站点部署的关键步骤与权限要求。
- 首次安装后的必做动作：删安装目录、创建管理员、收紧目录权限。
- 核心业务域：客户与供应商、报价与订单、发票与收款、库存与仓储、日程与账目。
- REST 接口的启用方式与基本调用形态，以及定时任务、邮件发送这两类常见配置。
- 常见故障的定位方向（白屏、权限、乱码、API 403、cron 不跑）。

**不覆盖**：

- 不提供托管服务，也不承担服务器运维：备份、监控、安全加固要自己落实。
- 具体环境变量名、PHP 扩展清单、最低版本随版本变化，一律以官方文档为准。
- 不包含行业专用流程的落地设计（如特定行业的多级审批或复杂成本核算）。
- 不覆盖从旧系统迁数据的具体映射方案，这取决于源系统结构。
- 不保证第三方模块与主题在各版本下都兼容。

## 依赖条件

- Web 服务器（Apache / Nginx 等）与 PHP 运行环境，所需扩展与最低版本以官方文档为准。
- 数据库：MySQL / MariaDB 或 PostgreSQL；建议建库时就指定 UTF-8 字符集。
- 若走 Docker：本机装好 Docker 与 Compose，并能拉取官方镜像。
- 服务器需能常驻 Web 服务与数据库进程；要发邮件还需可用的 SMTP。
- 无必需的外部 SaaS 账号；一切数据都在自己的服务器上。

## 已知限制

- 它是自托管软件，出问题需要自己查日志、自己恢复，没有官方运营团队兜底。
- 模块数量多，配置项分散，「全开」会让后台难用，需要按业务裁剪。
- 界面与配置术语偏 ERP 语境，新用户上手有学习成本。
- 升级有明确的先后顺序（备份 → 覆盖代码 → 跑升级），顺序错了恢复麻烦。
- 二次开发是 PHP，改造前需要熟悉其目录结构与数据模型。
