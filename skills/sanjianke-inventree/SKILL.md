# 三剪客 · 开源库存与物料管理系统

电子元件、备件、半成品、成品堆在货架上，谁手里有多少、放在哪个仓位、这批货是哪家供应商的、装在哪个产品上——靠 Excel 记，三个月一定乱。它是一套自托管的库存与物料管理系统：物料与分类、库存条目与库位、BOM 与组装单、采购单与销售单、供应商与客户、条码与标签，全都围绕一条可追溯的链路组织起来。

它的强项是「追溯 + 组装」：每个库存条目能追到采购来源和去向，BOM 能算出还缺多少料，扫码就能完成入库、出库、盘点。代价是它按制造业思路建模，学一遍术语（物料、变体、库位、批次）才能用顺。适合有实物库存、要管 BOM 的团队，不适合只卖虚拟商品或纯代发的店铺。

**上游项目**：`InvenTree`　**仓库**：https://github.com/inventree/InvenTree

## 什么时候用 / 不用

**用它**：

- 有实物库存要管：物料、库位、批次、序列号，需要知道「现在有多少、在哪、从哪来」。
- 要管 BOM 和组装：算出装配一台成品还缺哪些料，并记录组装消耗与产出。
- 要做采购与销售单据流转：从供应商采购入库，到给客户发货，整条链路可查。
- 需要条码 / 标签：扫码入库、扫码出库、扫码盘点，减少手工录入错误。
- 硬件、电子、机械类团队要自托管一套数据留在自己手里的库存系统。

**不要用它**：

- 纯虚拟商品、纯代发、不持有实物库存的电商店铺——库位与批次这套建模用不上。
- 只想要一个简单的「进货出货流水表」，不需要 BOM 与追溯。
- 没有部署与运维能力，也不打算托管服务器；它需要常驻服务与数据库。
- 只是想做店铺前台与购物车，它不是面向消费者的商城系统。
- 目的是财务记账或税务合规，它的重点在物料与库存，不是会计核算。

## 安装

官方主推 Docker 生产部署，也是最短路径。

### 方式一：Docker 生产部署（推荐）

先把官方部署用的 compose 配置与 `.env` 模板拿到本地，编辑环境变量（数据库密码、对外端口、密钥等），再按顺序初始化：

```bash
# 1. 取得官方 docker 部署配置（compose 文件与 .env 模板）
#    见 https://docs.inventree.org/ 的 Docker 安装章节，拿到后放进同一个目录

# 2. 编辑 .env：改掉数据库密码、确认对外端口，再执行下面的初始化

# 3. 初始化数据库结构并创建管理员账号
docker compose run --rm inventree-server invoke update
docker compose run --rm inventree-server invoke superuser

# 4. 启动全部服务
docker compose up -d

# 5. 看日志确认起没起来
docker compose logs -f
```

默认从浏览器访问服务地址即可进入 Web 界面，用上一步创建的管理员账号登录。具体服务名、镜像标签、环境变量名以官方文档与 compose 文件为准，不要照抄旧版本的写法。

### 方式二：裸机 / 开发环境

官方另提供裸机安装与开发环境两条路径，需要自行准备 Python 环境、数据库与前端构建环境，并用 `invoke` 工具完成初始化：

```bash
# 官方推荐用 invoke 统一管理任务；先安装它
pip install invoke

# 查看当前项目定义了哪些任务
invoke --list
```

数据库结构初始化、创建管理员、启动开发服务等都在这些任务里，任务名以 `invoke --list` 的实际输出为准。

### 方式三：在线试用

不想部署就先试功能：官方提供在线演示站点，注册一个演示账号即可，地址见 https://docs.inventree.org/ 的 Demo 章节。

## 常用操作

**1. 初始化 / 升级数据库结构**（每次升级镜像后都要执行）

```bash
docker compose run --rm inventree-server invoke update
```

**2. 创建管理员账号**（首次部署）

```bash
docker compose run --rm inventree-server invoke superuser
```

**3. 起停服务**

```bash
docker compose up -d
docker compose down
```

**4. 看日志定位启动失败**

```bash
docker compose logs -f --tail=200 inventree-server
```

**5. 用 API 拉物料列表**（先在 Web 界面里为用户生成 API Token）

```bash
curl -s "http://<你的地址>/api/part/?limit=10" \
  -H "Authorization: Token <你的TOKEN>" \
  -H "Accept: application/json"
```

**6. 把数据导出成 JSON 做备份**（官方推荐的数据备份方式之一）

```bash
docker compose run --rm inventree-server invoke export-records -f /home/inventree/data/backup.json
```

> 第 6 条的参数名与导出路径以 `invoke --list` 与官方文档为准；`invoke` 的任务清单随版本变化，先 `--list` 再执行。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 页面能开但报数据库错误 | 数据库容器还没就绪，或 `.env` 里的连接信息不对 | 先看数据库容器日志与健康状态，确认 `.env` 的库名/用户/密码与之匹配，再重启服务 |
| 升级镜像后页面报错、字段缺失 | 只换了镜像，没跑数据库迁移 | 每次升级都先跑一次 `invoke update`，再启动服务 |
| 首次部署进去登录不了 | 没创建管理员账号 | 用 `invoke superuser` 创建账号后再登录 |
| `docker compose run` 报服务名不存在 | 服务名跟你手上的 compose 文件不一致 | 用 `docker compose config --services` 列出实际服务名，别照抄别处的名字 |
| 数据在容器重建后丢了 | 数据库与上传目录没挂到宿主机卷 | 在 compose 里把数据库数据目录与附件/上传目录都挂出来，重建前先确认卷还在 |
| 上传的图片、附件重启后消失 | 只挂了数据库，没挂媒体目录 | 媒体/附件目录必须持久化，否则数据库里有记录、文件已丢 |
| `invoke` 提示找不到任务 | 装的是别的版本，或不在项目根目录执行 | 在项目根目录执行 `invoke --list` 看真实任务名；虚拟环境要对准同一套依赖 |
| `pip install invoke` 后命令仍不可用 | 装到了另一个 Python 环境 | 确认用的是同一个解释器/虚拟环境，必要时用 `python -m invoke` |
| 条码扫不出来 | 打印机分辨率或条码尺寸不匹配，或扫码枪输入模式不对 | 先在预览里确认条码能扫，再调整标签尺寸与打印机 DPI |
| 组装单算出的缺料不对 | BOM 里用量、单位或可选件设置不对 | 检查 BOM 行的用量与单位、是否标记为可选/可替换，再重算 |
| 多人同时操作后库存数不一致 | 有人手工改数、有人走单据，绕过了库存记账 | 统一走库存操作单据，禁止直接改数量字段；配合盘点校正 |
| 对外网开放后出现异常扫描 | 直接暴露了服务端口，没做访问控制 | 放到反向代理后并启用 HTTPS，配合限制来源或仅内网访问 |

## 能力边界

**覆盖**：

- Docker 生产部署的完整顺序：准备配置 → 初始化数据库 → 建管理员 → 启动服务。
- 升级路径：换镜像后必须先跑数据库迁移再启动。
- 核心业务域：物料与分类、库存条目与库位、批次与序列号、BOM 与组装单、采购与销售、条码与标签。
- API 的基本鉴权方式与调用形态，以及官方推荐的数据导出备份做法。
- 常见故障定位方向（数据库未就绪、迁移未跑、卷未挂、invoke 环境不对）。

**不覆盖**：

- 不提供托管服务，运维、备份、监控与安全加固由使用者负责。
- 不覆盖店铺前台、在线支付、消费者购物车这类电商面向用户的功能。
- 不包含财务核算与税务申报能力。
- 不保证 `invoke` 任务名、环境变量名在各版本间不变，一律以 `invoke --list` 与官方文档为准。
- 不覆盖具体行业（如电子元器件）的编码规范与命名体系设计。

## 依赖条件

- Docker 与 Docker Compose（走容器部署时），并能拉取官方镜像。
- 裸机部署需自备 Python 环境、数据库（官方支持的数据库类型以文档为准）与前端构建环境。
- 磁盘空间要留给数据库、附件与标签模板；生产环境建议单独挂载数据卷。
- 需要能常驻运行 Web 服务、数据库与后台任务进程的机器或容器平台。
- 条码功能需要标签打印机或扫码设备；邮件通知需要可用的邮件服务。

## 已知限制

- 建模偏制造业与硬件团队，术语体系（物料、变体、库位、批次）需要先学一遍。
- 部署与升级有一定运维门槛，顺序错了容易造成数据与文件不一致。
- 标签与报表为自渲染模板体系，深度定制需要理解其模板语法。
- 数据备份需要数据库与附件一起考虑，只备份数据库会丢文件。
- 面向消费者的前台能力不是它的目标，需要另做前端或接入其他系统。

## 自检清单

执行前：

- [ ] 确认 Docker 与 Compose 可用，磁盘空间够放数据库与附件。
- [ ] 确认 `.env` 里数据库密码等敏感项已改掉默认值。
- [ ] 确认数据库数据目录与附件目录都挂了宿主机卷。
- [ ] 确认对外端口与访问控制策略（是否只在内网暴露）。

执行后：

- [ ] `invoke update` 与 `invoke superuser` 均执行成功。
- [ ] 浏览器能登录，能创建一条物料与一条库存记录。
- [ ] 重启容器后数据与上传的附件都还在。
- [ ] API Token 能成功调用一次查询。
- [ ] 数据导出备份跑通一次，并知道怎么恢复。
