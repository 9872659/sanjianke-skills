# 留痕模板与实战示例

留痕的目的只有一个：**让没参与执行的人，能独立判断「做到哪了、靠不靠得住」。**

这和个人笔记不一样。个人笔记可以写「搞定了」「差不多了」；留痕必须写成能被核验的形式——别人拿着它，不用问你，就能自己跑一遍检查、自己看产物、自己得出和你一样的结论。

判断一条留痕合不合格，用这个测试：**把它发给一个完全不了解这个任务的同事，他能说出「哪几段确定完成了、哪一段有问题、下一步该干什么」吗？** 不能，就不合格。

---

## 一、留痕文件结构

一个任务一个目录，不要把所有任务写进一个巨大的日志文件。

```text
progress/
├── 00-plan.md              # 计划原文（冻结版，改了要留变更记录）
├── 01-log.md               # 执行流水（唯一按时间追加的文件）
├── 02-checkpoints.md       # 检查点决议
├── 03-open-items.md        # 未决项 / 阻塞项 / 旁支清单
└── evidence/
    ├── S1-inventory.md     # 每段的证据，一段一个文件
    ├── S2-tests.txt
    ├── S3-grep.txt
    └── S5-regression.txt
```

要点：

- **`01-log.md` 只追加，不修改历史行。** 写错了另起一行更正，并注明「更正：上面那行的 X 应为 Y」。可核验性建立在「历史不可篡改」上。
- **`evidence/` 里的文件是原始输出，不做美化。** 命令输出、diff、测试报告原样贴或原样重定向保存。**不要手动编辑证据文件**——一旦编辑，它就不再是证据。
- **`00-plan.md` 是冻结版。** 改计划时不要直接改它，而是追加一节「变更记录」，写清新旧差异。这样旧留痕才对得上。

## 二、段记录格式（`01-log.md` 的最小单元）

每一段至少五条。缺一条，这一段在核验上就是不可信的。

```text
### S3 · 迁移第一批调用方
- 区间：2026-03-11 14:05 → 14:52（时间盒 60 分钟，实耗 47 分钟）
- 进入条件：E1 ✅（S2 证据见 evidence/S2-tests.txt）· E4 范围=清单第 1–3 项 ✅
- 动作：改 src/a.ts、src/b.ts、src/c.ts，改用 loadConfig()
- 产物：commit 4f2a1c9；diff 见 evidence/S3-diff.txt
- 退出检查：grep 旧路径 → 3 处已清零（evidence/S3-grep.txt）✅
- 意外：无
```

五条固定字段：**区间 / 进入条件 / 动作 / 产物 / 退出检查**。意外与旁支另起一行，没有就写「无」——写「无」比省略更有价值，它排除了「忘了记」的可能。

### 失败记录的写法

失败也要记，而且要比成功记得详细一点。这是留痕最容易被省掉、也最有价值的部分。

```text
### S3 · 迁移调用方（第 3 次尝试）
- 区间：2026-03-11 15:10 → 15:41
- 退出检查：已迁移 11/12，剩 1 处为动态 key ❌
  - 期望：12/12（来自 00-plan.md 的段定义）
  - 实际：src/dynamic.ts 的 key 在运行时拼接，静态替换会改变行为
  - 证据：evidence/S3-grep.txt（第 14 行）
- 分诊：目标理解错 → 本段目标需细化，拆出 S3.1
- 处置：插入 S3.1「确定动态 key 的处理策略」，限时 30 分钟
```

关键在「期望 / 实际 / 证据」三行。**没有「期望」的失败记录无法核验**——别人不知道你是拿什么标准判定的。

### 意外与旁支的记录格式

```text
! 意外 2026-03-11 14:35 · S2
  实况：getConfig() 在配置文件缺失时抛异常，而非计划假设的返回默认值
  影响：S2 用例需增加一个分支
  处置：本段内处理，不改变段目标 → 判定不构成偏离

+ 旁支 2026-03-11 14:38 · 日志格式与文档不一致
  预估：20 分钟 | 处置：记入 03-open-items.md，本轮不做
```

符号约定：`!` 意外、`+` 旁支、`?` 未决、`#` 阻塞。这样一眼 grep 就能扫出来：`grep -n "^[!+?#]" progress/01-log.md`。

## 三、检查点决议格式（`02-checkpoints.md`）

检查点要留的不是「我们讨论了一下」，而是**结论 + 依据 + 分流**。

```text
### P3-1 · 2026-03-11 15:45 · 触发信号 B1（发现计划外工作）
- 冻结于：S3 第 3 次尝试失败，状态=可运行，最后提交 4f2a1c9
- 重述目标：把所有配置读取统一到一个 Loader 入口，行为不变
  · 与 00-plan.md 对照：一致 ✅
- 被推翻的前提：
  | 假设 | 状态 | 证据 |
  |---|---|---|
  | 所有 key 都是静态字面量 | 已证伪 | src/dynamic.ts:14 |
  | 迁移是纯机械替换 | 已证伪 | 同上 |
- 分流：补段（漏项 < 1 个时间盒，不影响 S4/S5 的前提）
- 结论：插入 S3.1，限时 30 分钟，退出检查=12/12 且行为对比通过
- 新回退点：4f2a1c9
```

**「被推翻的前提」这张表是整套留痕里信息密度最高的一块。** 它把「为什么改主意」变成了可复核的事实，而不是事后叙述。

## 四、未决项格式（`03-open-items.md`）

每一项都要有「谁/什么时候决定」，否则它会永久停在那里。

| ID | 内容 | 类型 | 记录时间 | 决定期限 | 决议 |
|---|---|---|---|---|---|
| O1 | 日志格式与文档不一致 | 旁支 | 03-11 14:38 | 本任务结束时 | 待定 |
| O2 | 动态 key 是否保留旧行为 | 未决 | 03-11 15:41 | S3.1 内 | 保留兼容分支 |
| O3 | 等待 B 组新版 schema | 阻塞 | 03-11 16:00 | 03-12 10:00 | 未解除 |

阻塞项要有**升级路径**：到期未解除怎么办。写「问一下」不算升级路径，写「到期后联系 X 且把 S4/S5 排到其他任务之后」才算。

## 五、进度摘要格式（给外部看）

留痕是给核验的，摘要才是给人快速看的。放在 `01-log.md` 顶部，每次检查点后更新——**只更新这一段，不动下面的流水**。

```text
## 进度摘要（更新于 2026-03-11 16:10）
计划段数：5（另插入 1 段 S3.1）
已通过退出检查：S1 S2 S3.1（3 段，另有 S3 失败 2 次后由 S3.1 覆盖）
进行中：S4
未开始：S5
阻塞：O3（等待外部 schema，期限 03-12 10:00）
回退点：4f2a1c9（S3.1 全部通过的提交）
偏离：1 次（P3-1，分流=补段）
原始时间估值：4 小时 ｜ 当前预估：5.5 小时（+1.5 小时，来自 S3 的 3 次尝试）
```

三件事必须写：**已通过的段有哪些（含证据位置）、阻塞与期限、时间估值的差额来源**。第三条最常被省，但它恰恰是外部最想知道的——「为什么慢了」不该靠追问。

判断摘要合格的测试：把它单独发给别人，不附带 `evidence/` 和流水，他能说出「现在到哪了、卡在哪、什么时候能有结果」吗？

## 六、实战示例一 · 半天任务：接口字段重命名

背景：某内部接口的字段 `user_id` 要统一成 `userId`，涉及 1 个服务、3 个调用方。预估 3 小时。

**`00-plan.md`（节选）**

| 段 | 目标 | 退出检查 |
|---|---|---|
| S1 | 盘点全部出现点 | `grep -rn "user_id" --include=*.ts . \| wc -l` 得到一个确定的 N |
| S2 | 服务端支持双字段读取 | 新旧两条用例全绿 |
| S3 | 迁移 3 个调用方 | 3 个调用方均为新字段，旧字段引用为 0 |
| S4 | 服务端下线旧字段 | 全量回归通过 |

**`01-log.md`（节选）**

```text
### S1 · 盘点出现点
- 区间：09:05 → 09:22（时间盒 20 分钟）
- 进入条件：E1 ✅（首段）· E4 范围=仓库内所有 *.ts ✅
- 动作：全仓搜索并分类（代码/测试/文档/配置）
- 产物：N=27（代码 9 / 测试 14 / 文档 4），清单 evidence/S1-inventory.md
- 退出检查：清单条目数 = grep 行数 ✅

### S2 · 服务端双字段读取
- 区间：09:25 → 10:20（时间盒 45 分钟，超 10 分钟）
- 进入条件：E1 ✅ · E4 范围=schemas/user.ts + handlers/user.ts ✅
- 动作：读取层先取 userId，回退 user_id；写回只写 userId
- 产物：commit 8b3e0f1，用例 +6
- 退出检查：pytest tests/test_user.py -q → 22 passed ✅
- 意外：! 写入路径原来会同时写入两个字段，计划未预计 → 处置：本段内统一为只写新字段
- 旁支：+ 文档里的字段说明已过期（预估 15 分钟，记 O1，本轮不做）

### S3 · 迁移 3 个调用方（第 1 次尝试）
- 区间：10:25 → 11:30
- 退出检查：3 个调用方已改 2 个，第 3 个是外部仓库，无写权限 ❌
  - 期望：3 个调用方全部迁移（来自 00-plan.md）
  - 实际：第 3 个调用方属于另一个仓库，本任务无写权限
  - 证据：evidence/S3-grep.txt（第 31 行）
- 分诊：依赖不满足（E3 型）→ 标阻塞 O2，不构成本段失败
- 处置：S3 判定为 2/3 通过，剩余部分排入外部协调后的补段
```

**`02-checkpoints.md`（节选）**

```text
### P2-1 · 11:35 · 中点核对
- 核问题：S1–S3 拼起来是否仍指向「统一字段名」？
- 结论：指向一致，但 S4（下线旧字段）的前提依赖外部仓库完成迁移
- 分流：改计划 —— 把 S4 拆为 S4（内部回归）+ S5（外部协调后再下线）
- 新时间估值：3 小时 → 4 小时（+1 小时，来自外部协调等待）
- 新回退点：8b3e0f1
```

**这个例子的看点**：S3 的失败被正确分诊成了「依赖不满足」而不是「实现错误」——如果分诊错了，接下来会去反复改自己的代码，而问题在权限。留痕里「期望 / 实际 / 证据」三行让这个判断变得可复核。

## 七、实战示例二 · 多天任务：把一批文档拆成技能包

背景：把 12 个主题各写成一份 Agent Skill，预估 3 天，5 个执行者并行。

**拆段策略**：不按「12 个主题」拆成 12 段（粒度太粗，一个主题可能要半天），而是按**加工阶段**拆，每个阶段对所有主题统一执行：

| 段 | 目标 | 退出检查 |
|---|---|---|
| S1 | 12 个主题各写一份大纲 | 12 份大纲齐，且每份含触发场景 + 边界 |
| S2 | 用同一模板生成 12 份骨架 | 12 个目录齐，校验脚本通过 |
| S3 | 填正文（分 3 批，每批 4 个） | 每批：无 TODO 残留 + 校验通过 |
| S4 | 校验与交叉查重 | 全部通过 + 无重复覆盖清单 |

**为什么按阶段拆**：按主题拆会让「模板不一致」这个问题在最后才暴露，那时返工成本是 12 倍。按阶段拆让问题在第 2 段就集中暴露一次。

**`01-log.md`（节选）**

```text
### S3-a · 填正文（第 1 批 4 个）
- 区间：D2 09:00 → 12:10
- 进入条件：E1 ✅（S2 校验通过）· E4 范围=批次清单 4 个 slug ✅
- 动作：4 个执行者各写 1 份正文 + 3 份 references
- 产物：4 个目录，共 16 个文件
- 退出检查：grep -rn "TODO" → 0 命中 ✅；校验脚本 4/4 通过 ✅
- 意外：! 同一份资料被两个主题重复引用，写成了两个版本
  → 处置：本段内合并为一份，另一处改为引用（不改变段目标）
- 旁支：+ 模板缺「已知限制」小节（预估 10 分钟，处置：本段末统一补模板）
```

**`02-checkpoints.md`（节选）**

```text
### P2-2 · D2 12:20 · 第 1 批完成后
- 核问题：第 1 批的产出形态，是否是后面两批想要的东西？
- 证据：抽查第 1 批 1 份正文，对照验收标准逐条过
- 发现：C3 型信号 —— 4 份中 2 份的「能力边界」写成了功能列表，
  不满足「不覆盖」要求；完成度自评 100%，实际不达标
- 分流：改计划 —— 不重排段，而是给 S3-b/S3-c 增加一条前置：
  写作前先看第 1 批的达标样本 1 份（10 分钟）
- 结论：S3-a 判定为「通过但需返工 2 份」，返工并入 S3-b 的第一小时
- 新回退点：S2 结束时的目录状态（骨架可复用，正文可重写）
```

**这个例子的看点**：C3 信号（完成度与可用产物不符）被抓住的方式是**抽查 1 份 + 对照验收标准**，不是看自评完成度。12 份文档的自评都是「已完成」，但其中 2 份不达标——这就是留痕里必须留「退出检查的实际判定标准」，而不只是打勾的原因。

## 八、实战示例三 · 小任务：一次线上问题定位

背景：某接口错误率突增，需要在 2 小时内定位到根因，预估 2 小时。

**特殊之处**：这类任务的目标是「找到原因」，不是「改代码」，所以段的目标是**排除假设**，退出检查是「某个假设被证实或排除，且有证据」。

| 段 | 目标 | 退出检查 |
|---|---|---|
| S1 | 确认影响面与起始时间 | 拿到起始时间点 + 受影响请求比例，有监控截图 |
| S2 | 排除「最近一次发布」 | 发布点早于起始时间 或 发布后有对照数据 |
| S3 | 排除「下游依赖变慢」 | 下游耗时曲线与错误率曲线不同步，有图 |
| S4 | 定位到根因或升级 | 根因有复现证据 / 或已按升级路径转交 |

**`01-log.md`（节选）**

```text
### S2 · 排除「最近一次发布」
- 区间：14:10 → 14:35（时间盒 25 分钟）
- 进入条件：E1 ✅（S1 给出起始时间 13:47）· E4 范围=当天的发布记录 ✅
- 动作：拉发布记录，比对时间点；对比发布前后的错误率
- 产物：evidence/S2-release-timeline.txt（发布 11:20，早于 13:47 两小时 27 分）
- 退出检查：发布点早于起始时间，且发布后 2 小时错误率平稳 ✅
- 结论：假设「最近发布导致」被**排除**
- 意外：无

### S3 · 排除「下游依赖变慢」
- 区间：14:40 → 15:05
- 退出检查：下游 P99 在 13:47 前后无变化（evidence/S3-dep-latency.png）✅
- 结论：假设被**排除**
- 旁支：+ 有个下游重试配置看起来偏大（记 O2，事后处理）
```

**`02-checkpoints.md`（节选）**

```text
### P4-1 · 15:05 · 时间盒检查
- 已用：55 分钟 / 预估 120 分钟
- 已排除：发布、下游依赖（2 个假设，均有证据）
- 剩余假设：本服务内部连接池耗尽
- 判断：进度正常，继续
- 但触发 A4 检查：连续两段无可展示产物 → 实际有（时间线文件 + 延迟图），不构成问题
```

**这个例子的看点**：定位类任务的留痕，价值在**排除记录**。事后复盘时，「我们当时排除了哪几个可能、依据是什么」比「最后找到了什么」更有用——它决定下次能不能更快。所以每条排除都要留证据文件，不能只写「排除了」。

## 九、留痕自检清单

写完一段留痕，过一遍：

- [ ] 五条固定字段齐：区间 / 进入条件 / 动作 / 产物 / 退出检查
- [ ] 退出检查写的是**命令或明确判定**，不是「确认无误」
- [ ] 有产物路径或提交号，别人能直接打开
- [ ] 失败的记录也留了，且含「期望 / 实际 / 证据」三行
- [ ] 意外和旁支用了 `!` `+` 前缀，未决和阻塞进了 `03-open-items.md`
- [ ] 证据文件是原始输出，没有被手工编辑过
- [ ] 里没有真实密钥、内部域名、客户名、个人手机号
- [ ] 进度摘要的三要素齐：已通过段（含证据）、阻塞与期限、时间差额来源
- [ ] 把这一段单独发给不了解任务的人，他能说出「做到哪了、下一步做什么」

前六条保证**可核验**，第七条保证**可外发**，八九条保证**可用**。三条缺一条，留痕就退化成了个人日记。
