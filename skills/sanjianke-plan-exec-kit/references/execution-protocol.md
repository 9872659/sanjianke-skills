# 执行协议：把计划拆成可执行段

计划跑偏，很少是因为计划写得不对，多半是因为**计划没有落到「段」这一层**。

一份像样的计划通常长这样：「重构配置加载 → 补测试 → 灰度 → 全量」。它读起来完整，但它没有回答执行者每分钟该做什么、做到什么算完。于是执行者只能自己猜边界，猜着猜着就偏离了。

执行协议要补的就是这一层：把计划里每一行，翻译成一段有**入口、动作、出口**的闭环。

---

## 一、段的定义与粒度

### 什么是「一段」

一段是执行协议的最小单位，必须同时满足四条：

1. **单一意图**：一句话能说完它要达成什么，不用「并且」「顺便」。
2. **有可观察产物**：结束时会产生一个能被别人看到的东西——文件、提交、命令输出、一段已迁移的数据。不是「我理解了」。
3. **有退出检查**：有至少一条命令或一次核对，能判定它成没成。
4. **失败可回退**：出问题时知道退回到哪个状态。

四条缺一条，就不是一段，是「一小块模糊的活」。

### 粒度怎么定

粒度用**退出检查的时间间隔**来定，不用代码行数、不用文件数。

| 计划总时长 | 一段的时长 | 典型段数 | 说明 |
|---|---|---|---|
| ≤ 1 小时 | 10–20 分钟 | 3–5 | 太短会频繁停下来，反而慢 |
| 半天（约 4 小时） | 30–60 分钟 | 5–8 | 最舒服的区间 |
| 1–3 天 | 1–3 小时 | 6–12 | 每段都要有一次能给人看的产出 |
| ≥ 1 周 | 拆成「天」再按天拆 | — | 不要直接排到段，先按天分段 |

**自检粒度是否合适**：问自己「如果现在被打断两小时，回来时我知道该从哪儿接吗」。答不上就是段划得太粗；答得太细（「我在改第 37 行的括号」）就是太细。

### 段的编号与命名

段号用 `S<序号>`，稳定不变——**段号是留痕和回退的锚点，一旦分配就不再复用**。中途插进来的新段用 `S<前一段序号>.<序号>`（如 `S3.1`），不要重排后面的段号。

命名格式：`S<序号> <动词> <对象> <边界>`。

```text
S1  盘点配置读取点，产出清单
S2  抽出 Loader 接口，跑通现有测试
S3  迁移第一批 3 个调用方
S4  迁移剩余调用方
S5  删除旧路径，跑全量回归
```

不要写成「S1 配置重构」——那是计划里的一行，不是一段。

## 二、进入条件（Entry Gate）

**进入条件没满足就开始，是偏离的主要来源，而且是那种事后很难归因的偏离。**

每一段动工前，逐条过这张门禁表。**任意一条不过，就不要开始动手**——要么补齐，要么把这段拆分，要么把它标成阻塞。

| # | 进入条件 | 不满足时的处理 |
|---|---|---|
| E1 | 上一段的退出检查已通过，且**证据已落盘** | 回去补上一段的检查，不要往下走 |
| E2 | 这一段的目标能用一句话说清，且不包含「并且」 | 拆成两段 |
| E3 | 需要的外部资源已就位：权限、数据、依赖版本、他人交付物 | 标为阻塞，记录阻塞项，跳到不依赖它的段 |
| E4 | 需要改动的范围已圈定——具体是哪几个文件 / 哪张表 / 哪几个接口 | 先花 5–15 分钟做一次盘点，产出清单，再作为独立一段 |
| E5 | 如果这段失败了，你知道退回到什么状态（回退点） | 补一个回退点；补不出来说明这段太大 |
| E6 | 时间盒已设定（默认按上面粒度表） | 现设一个 |

E4 是最常被跳过的一条。跳过它的代价是：动手之后才发现「还有 6 个地方也调了这个接口」，于是段边界失控，退出检查失效，这段实际上是没做完的。

### 进入条件的记录方式

进入条件不满足时，不要口头说一句就算了。在留痕里写清三件事：

```text
S4 未进入 · 2026-03-11 14:20
阻塞项：等待 B 组提供新版 schema（E3 不满足）
影响：S4、S5 无法开始
已做：先执行 S6（不依赖 schema），预计 60 分钟
```

这样任何人看留痕都知道「为什么现在在做 S6」。

## 三、执行动作（Action）

### 三条纪律

**A1 · 只做这一段的事。** 执行中发现的「顺手能修的小问题」，一律记进「旁支清单」，不要当场动手。旁支清单在段末统一处理（见第五节）。顺手修是偏离的第一号来源：它单次成本小，但它让段的退出检查失去意义——你没法判断这段到底做完没有。

**A2 · 先跑通，再做好。** 每段内部按「最小可验证闭环」推进：先让它能动，再优化。反过来做的话，段末可能得到一个「处处精致但根本跑不起来」的产物。

**A3 · 遇到意外先记录，不先改计划。** 执行中撞上和计划不符的现实（接口行为不一样、数据比预期脏），先把它记成**意外条目**，继续在本段内找绕法。改计划是段末检查点的事（见 `references/checkpoints-and-drift.md`）——在段的中间改计划，等于把「偏离」当成常态。

### 意外条目的格式

执行中随手记，一行一条，不要写成段落：

```text
! 意外 2026-03-11 14:35 · S2
  实况：getConfig() 在无文件时抛异常而不是返回默认值
  影响：S2 的用例要加一个分支
  处置：本段内加分支处理；是否保留旧行为留到段末决定
```

`!` 开头便于在留痕里一眼扫出来。**意外条目不算偏离，它是正常信息**；偏离是「意外改变了段的目标或边界」。

### 旁支清单

执行中冒出来的额外发现，一律进这张表，不现场动手：

| 发现时间 | 内容 | 预估成本 | 处置（段末定） |
|---|---|---|---|
| 14:38 | 日志格式和文档不一致 | 20 分钟 | 待定 |
| 15:02 | 有个未使用的 import | 1 分钟 | 本段末顺手清 |

段末统一分诊：本轮做 / 排进后续段 / 记入待办 / 丢弃。**只允许「本段末顺手清」这一档在现场处理**，且只能有一条，避免滚雪球。

## 四、退出检查（Exit Check）

退出检查是执行协议里唯一**不允许在自己心里完成**的部分。它必须产生一个外部可读的结果。

### 四类退出检查

| 类型 | 判定方式 | 例子 |
|---|---|---|
| 命令型 | 跑一条命令，看退出码或输出 | `pytest -q`、`tsc --noEmit`、`git diff --stat` |
| 计数型 | 数一个明确的量，和计划里的数字对 | 清单里 12 个调用方，已迁移 12 个 |
| 清单型 | 逐条打勾，勾完算完 | 进入条件表、验收标准表 |
| 对照型 | 拿产物和一段预期描述逐字对 | 生成的报告是否包含要求的 5 个字段 |

**命令型优先**。能写成命令的检查，就不要写成「我确认了一下」。

### 退出检查的三条硬规则

1. **检查必须在产物产出之后立刻做**，不要攒到段末或一天结束再统一验。攒着验等于把误差累积到无法归因。
2. **检查不通过时，不能进入下一段**。哪怕「只差一点点」。差一点点的段，往往是方向已经错了。
3. **检查结果必须留痕**（格式见 `references/evidence-and-examples.md`），包括**不通过的那次**。只记成功结果的留痕，对第三方没有核验价值。

### 退出检查不通过时的四种情况

先分诊，再动手：

| 情况 | 判定 | 处理 |
|---|---|---|
| 实现错误 | 目标没错，做法错了 | 在本段内修，重跑检查。允许重试 2 次 |
| 目标理解错 | 做出来的东西不是想要的东西 | **停下**，回到计划确认这一段的目标，可能要改计划 |
| 依赖不满足 | 卡在外部 | 标为阻塞，跳过，先做不依赖它的段 |
| 检查本身不对 | 检查写得太严或太松 | 修检查，并在留痕里注明「检查在 X 时点被修订」 |

第三种和第四种最容易搞混。判别方法：**如果检查的期望值来自计划文档，而现实是合理的，那多半是检查不对；如果现实本身不合预期，那是依赖问题。**

## 五、段边界交接（Handoff）

段与段之间必须有明确的交接动作，尤其是**跨人或跨 Agent 会话**的时候。三方（你、下一个人、未来的你）都要能接着走。

交接清单：

1. **落盘当前状态**：产物在哪个路径、哪个分支、哪个提交。
2. **关掉旁支清单**：分诊完，没分诊的不要留到下段。
3. **更新留痕**：补全本段的退出检查结果（含失败记录）。
4. **预告下一段**：写清下一段的段号、目标、进入条件里还差什么。
5. **回退点确认**：写清「如果下一段失败了，回到哪个提交/状态」。

交接完成后，**新的一段从进入条件重新过一遍门禁**——不要因为「刚才是连续做的」就跳过。

### 中断处理

执行中被意外打断（会议、下班、上下文切换），按这个顺序收尾，5 分钟内做完：

```text
1. 把当前正在改的东西写到可运行状态（实在不行就 git stash，并记下 stash 名字）
2. 在留痕里写一行「中断点」：S<n> 进行中，已到 <具体位置>
3. 写清恢复时要做的第一个动作
4. 提交一次（哪怕是 WIP 提交）
```

中断点儿戏不得：统计上，**没有落中断点的中断，恢复成本平均是 20–40 分钟**；有的话是 3–5 分钟。这是执行协议里投入产出比最高的一条纪律。

## 六、完整走一遍：一个最小例子

计划原文（一句）：**「把项目里的配置读取统一到一个入口。」**

拆成段：

| 段 | 目标 | 进入条件要点 | 退出检查 |
|---|---|---|---|
| S1 | 盘点所有配置读取点 | 有仓库读权限 | `grep -rn "process.env" src/ \| wc -l` 得到数字 N，清单落盘 |
| S2 | 建 Loader 入口，保持旧行为 | S1 清单存在 | 新增用例全绿，旧测试全绿 |
| S3 | 迁移调用方 | S2 通过 | 清单中已迁移数 = N，且无旧调用残留（grep 结果为 0，白名单除外） |
| S4 | 删除旧路径 | S3 通过 | 全量回归通过，净减行数为正 |

执行过程中：

```text
S1 退出检查：N=12，清单见 evidence/S1-inventory.md   ✅
S2 进入条件：E1 通过、E4 范围=新增 src/config/loader.ts ✅
! 意外 S2：某调用方在模块顶层读 env，Loader 初始化时序要调整
S2 退出检查：用例 14 通过 / 0 失败                        ✅
S3 进入条件：E4 范围=清单中 12 处                        ✅
S3 退出检查（第 1 次）：已迁移 11/12，剩 1 处为动态 key   ❌
  → 分诊：属于「实现错误 + 需要设计取舍」，就地补一段 S3.1
S3.1 目标：确定动态 key 的处理策略并落地
S3.1 退出检查：12/12 迁移完成，grep 残留为 0              ✅
S4 退出检查：回归 210 通过 / 0 失败，净减 46 行           ✅
```

注意 S3 那次**失败也留了痕**。这条记录后来成了这个项目最有用的东西：它解释了为什么 Loader 里有一段看着多余的动态 key 兼容逻辑。

## 七、协议速查卡

```text
进入段之前：
  E1 上一段过了吗（有证据）    E2 一句话能说清吗
  E3 资源齐吗                  E4 范围圈定了吗
  E5 回退点在哪                E6 时间盒设了吗
  → 有不过的：补 / 拆 / 标阻塞

执行之中：
  A1 只做这段的事（旁支进清单）
  A2 先跑通再做好
  A3 意外先记录，不改计划
  → 被打断：落中断点 + 提交

退出段之前：
  跑退出检查（命令型优先）
  产物先出，检查立刻做，不攒
  不过 → 四种情况分诊，不硬闯
  结果留痕（失败的也留）

交接：
  落盘 + 关清单 + 补留痕 + 预告下段 + 回退点
```

配套阅读：`references/checkpoints-and-drift.md`（什么时候必须停下重新对计划）、`references/evidence-and-examples.md`（留痕格式与三个完整实例）。
