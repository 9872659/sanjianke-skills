# 三剪客 · 跨平台聊天机器人框架

你想在群里放一个能干活的小助手——能回话、能查东西、能定时提醒、能对接内部系统——但难点往往不在业务逻辑，而在于「每个聊天平台的接入方式都不一样」。Koishi 解决的就是这一层：你写一份逻辑，它同时挂到 QQ、Telegram、Discord、飞书、KOOK、Slack、邮件等平台上，一个应用还能接多个平台、每个平台多个账号。

它的第二个价值是**网页控制台**。插件装在哪个分组、哪条指令要什么权限、机器人现在活着没有、日志报了什么错，都在一个浏览器页面里点，不必记一堆命令行参数。第三个价值是**插件生态**：官方和社区的插件覆盖平台适配、数据库、资源存储、图片渲染、状态管理等常见需求，多数场景不用从零写。

**上游项目**：`Koishi`　**仓库**：https://github.com/koishijs/koishi

## 什么时候用 / 不用

**用它**：

- 用户说「我想做个聊天机器人」，并且要求**同时支持多个平台**，或者以后可能换平台。
- 要把群聊消息接进自己的业务系统：收到消息触发查询、写库、调接口，再把结果发回群里。
- 需要**非开发人员也能维护**机器人：装插件、改文案、开关功能都在网页控制台里完成。
- 要在一台服务器上跑多套机器人配置（多账号 / 多实例），并希望有守护、状态查看、依赖修复这套运维动作。
- 想用 TypeScript 写插件、要热重载和类型提示，把机器人当正经工程做。
- 需要一个内置的**沙盒**来试插件：不接真实账号、不怕风控，先把功能跑通。

**不要用它**：

- **只要接一个平台、一个简单回调**。如果需求就是「一个 webhook 收到消息回一句话」，直接写几十行服务端代码更轻，引一整套框架属于过度设计。
- **想要开箱即用的成品机器人**。它给的是框架和插件市场，具体业务能力（比如某个垂直场景的完整功能）仍要自己装插件或自己写。
- **指望它替你解决平台侧的资质问题**。平台开发者账号、企业认证、公网服务器、回调地址这些准备工作，框架不代劳。
- **不想碰 Node.js 生态**。安装包里虽然带运行环境，但自定义插件、依赖排查、版本升级都在 npm 体系里，完全不碰命令行不现实。
- **把它当多租户 SaaS 平台**。单个应用面向一套配置，硬要拿它做互不干扰的多客户托管会很别扭。
- **安装来源不明的第三方插件还指望官方兜底**。非官方插件的安全性没有任何保证。

## 安装

官方提供四种安装方式，按「谁用」来选：给非开发者用启动器，给服务器用 Docker，给开发者用模板项目，嵌进已有 Node 工程用依赖调用。

### 方式一：启动器（图形化安装包，最推荐给最终用户）

- **Windows**：下载官方 `.msi` 安装包，双击后一路 Next。安装程序会自动处理大部分环境问题；官方提示在部分电脑上安装可能耗时十分钟以上，属正常现象。装完从开始菜单启动，控制台会自动打开。
- **Linux**：下载官方 `.AppImage`，赋予执行权限后运行，然后在浏览器访问 `http://localhost:5140`。
- **macOS / Android**：官方文档同样给出对应安装包，以官网当前页面为准。

启动器自带命令行工具 `koi`，用于在无图形界面的机器上管理实例：

```bash
koi ps                 # 查看运行状态
koi daemon start       # 启动守护
koi start default      # 启动名为 default 的实例
koi restart default    # 重启该实例
koi yarn -n default    # 修复该实例的依赖
```

如果你拿到的是 `koi-xxx.appimage` 这类文件名，把上面的 `koi` 换成该文件名即可。

### 方式二：Docker / Podman（服务器部署）

官方镜像已预装 Chromium，因为不少插件依赖它做图片渲染；如果觉得镜像太大，官方另提供不带 Chromium 的轻量标签：

```bash
# 标准镜像
docker run -p 5140:5140 koishijs/koishi

# 轻量版（latest-lite），不含预装 Chromium
docker run -p 5140:5140 koishijs/koishi:latest-lite

# 需要持久化：把数据目录映射出来
docker run -p 5140:5140 -v /some/place:/koishi koishijs/koishi

# 需要校正时区
docker run -p 5140:5140 -e TZ=Asia/Shanghai koishijs/koishi
```

容器启动后控制台绑定在 5140 端口，用浏览器访问 `http://宿主机地址:5140` 即可装插件。官方说明：持久化之后更新容器只会更新 Chromium 和 Node.js 这类运行时，本体和插件在控制台里就能更新。用 Podman 的话命令同形，把 `docker` 换成 `podman`。

### 方式三：模板项目（开发者首选，官方最推荐）

要求本机已装 Node.js，官方要求最低 v18、推荐 LTS。官方同时建议：项目路径不要太长、不要出现中文或空格，Windows 上推荐 `C:\dev` 或 `D:\dev`。

```bash
# 可选：用 yarn 代替 npm
npm i -g yarn

# 国内网络建议换镜像源加速
npm config set registry https://registry.npmmirror.com

# 创建项目（进入一个干净的父目录后执行）
npm init koishi@latest

# 之后再次启动
npm start
```

模板项目自带完整控制台，支持直接加载 TypeScript、插件热重载，也能用来联调别人的插件。

### 方式四：作为依赖调用（嵌进已有 Node 工程）

```bash
npm init

npm i koishi \
      @koishijs/plugin-server \
      @koishijs/plugin-console \
      @koishijs/plugin-sandbox \
      @koishijs/plugin-echo

# 想用 TypeScript 就再装这些（不用可跳过）
npm i typescript @types/node esbuild esbuild-register -D
```

新建入口文件，把插件逐个挂到应用上下文上：

```ts
import { Context } from 'koishi'
import server from '@koishijs/plugin-server'
import console from '@koishijs/plugin-console'
import * as sandbox from '@koishijs/plugin-sandbox'
import * as echo from '@koishijs/plugin-echo'

const ctx = new Context()

ctx.plugin(server, { port: 5140 })   // 后端服务
ctx.plugin(console)                  // 网页控制台
ctx.plugin(sandbox)                  // 调试沙盒
ctx.plugin(echo)                     // 回声指令
```

```bash
node -r esbuild-register .
```

社区插件按 `koishi-plugin-foo` / `@koishijs/plugin-foo` / `@your-scope/koishi-plugin-foo` 这类命名发布在 npm 上，装完同样用 `ctx.plugin()` 加载。

## 常用操作

**1. 在沙盒里不接真号先跑通**

控制台左侧进「沙盒」，点「添加用户」建一个虚拟用户，输入 `help` 看当前装了哪些指令，再输入 `echo 你好` 验证插件确实生效。想模拟群聊就多加几个用户并切到群聊模式；指令有权限要求时，可以在「用户设置」里调该用户的权限等级。

**2. 在控制台里装插件并启用**

进「插件市场」搜索插件名 → 点「添加」→ 在弹窗里选版本 → 「安装」。**装完不会自动跑**，要再到「插件配置」页面点右上角「启用插件」；配置项有必填没填会在左侧标红，改过没保存会标紫，点「启用插件」或「保存配置」才落盘。

**3. 让插件只在指定群 / 平台生效（过滤器）**

插件详情页顶部有过滤器设置，点「添加条件」按平台 / 用户 / 群组 / 频道 / 机器人来包含或排除。加完第一个条件后按钮会变成「添加『与』条件」和「添加『或』条件」：内层多个条件之间是「与」，外层多个条件组之间是「或」。

**4. 设置指令触发前缀，避免群里误触**

全局设置里有 `prefix` 和 `nickname`。把 `prefix` 设为 `/`、`nickname` 设为某个昵称后，群聊里能被触发的形式是：`/echo hello`、`昵称, echo hello`、`@机器人 echo hello`。私聊没有这个限制，不带前缀也能触发。

**5. 加密钥与配置（不要硬编码到配置里）**

配置文件 `koishi.yml` 支持环境变量插值，也可以放在 `.env.local` 里（该文件默认已被忽略，适合放隐私信息）：

```yaml
plugins:
  adapter-discord:
    token: ${{ env.DISCORD_TOKEN }}
```

还可以用环境变量做条件启用，例如让某个插件只在特定启动方式下生效：

```yaml
plugins:
  desktop:
    $if: env.KOISHI_AGENT?.includes('Desktop')
```

**6. 公网访问控制台**

默认只能本机访问。要让局域网 / 公网访问，去「插件配置」找到 server 插件，把 `host` 改为 `0.0.0.0`，然后点「重载配置」。有域名并对外暴露时，还要把 `selfUrl` 改成外部能访问到的地址。上公网前**务必**配合登录插件限制控制台访问。

反代示例（同机反代时不需改 `host`）。Caddy：

```
:80 {
  reverse_proxy http://127.0.0.1:5140
}
```

nginx 需要显式处理 WebSocket 升级：

```
map $http_upgrade $connection_upgrade {
  default upgrade;
  '' close;
}

server {
  location / {
    proxy_pass http://127.0.0.1:5140/;
    proxy_redirect off;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Host $http_host;
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
  }
}
```

**7. 自己写一段消息逻辑**

不想为一个小功能发插件，可以直接监听消息事件；想收纳得整齐一点，就写成一个插件文件再 `ctx.plugin()` 加载：

```ts
import { Context } from 'koishi'

export const name = 'my-reply'

export function apply(ctx: Context) {
  ctx.on('message', (session) => {
    if (session.content === '在吗') {
      session.send('在的，你说')
    }
  })
}
```

```ts
import * as myReply from './my-reply'
ctx.plugin(myReply)
```

**8. 依赖服务要用 `inject` 声明，不要靠 if 判断**

需要数据库、资源存储、控制台这类服务时，用 `inject` 声明依赖关系：必需依赖会让插件等该服务就绪后才加载、服务变化时自动回滚重载；只在运行时判断用法的依赖放 `optional`；只影响部分功能的依赖用 `ctx.inject()` 拆成子插件。

```ts
export const name = 'dialogue'

export const inject = {
  required: ['database'],
  optional: ['assets'],
}

export function apply(ctx: Context) {
  ctx.inject(['console'], (ctx) => {
    ctx.console.addEntry('/path/to/extension')
  })
}
```

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 插件装了也启用了，但一直不工作 | 它依赖的服务没有实现（比如要用数据库，却没装任何数据库服务插件） | 声明了 `inject` 的插件会等所依赖服务就绪才加载。先去「插件市场」装并启用对应服务插件（如 database-sqlite 这类，具体名字以市场当前搜索为准），再回来看插件状态 |
| 在插件市场点了「安装」，机器人却没有任何反应 | 安装和启用是两步，新装插件默认不启用 | 到「插件配置」页面找到它，点右上角「启用插件」；配置项标红的必填项补齐后才能启动 |
| 同一频道里有好几个机器人，只有其中一个回话 | 这是有意的受理人（assignee）机制，用来防重复发送和循环触发 | 正常情况下由第一个收到该频道消息的机器人担任受理人。要切换就用 admin 插件提供的 `assign` 指令指定；想让某频道不被响应，用 `assign -r` 移除受理人 |
| 群聊里裸写 `echo` 没反应，或者到处误触 | 群聊受触发前缀约束 | 在全局设置里配 `prefix` / `nickname`，用 `/指令`、`昵称, 指令` 或 `@机器人 指令` 触发；私聊不受限制 |
| 配了多个 `prefix` 之后，前缀匹配结果和预期不一致 | prefix 是按顺序匹配的列表 | 空串 `''` 表示「无前缀也能触发」，必须放在列表最后；清空列表会导致所有指令都无法通过 prefix 触发（但仍可用私聊或 @机器人 触发） |
| 反代之后控制台能打开但很快断开 / 状态不刷新 | 控制台有 WebSocket 长连接，反代没有转发升级请求 | 按上面 nginx 示例补上 `Upgrade` / `Connection` 与 `proxy_http_version 1.1`；用 Caddy 时 `reverse_proxy` 已能处理 |
| 控制台挂到公网后心里没底 | 默认没有登录限制 | 先装并配置好登录（auth）插件，再改 `host` 暴露；设置好 `selfUrl`；国内服务器按需补备案信息类插件 |
| Windows 上 `yarn` 报「无法加载文件 yarn.ps1，因为在此系统上禁止运行脚本」 | PowerShell 执行策略限制 | 以管理员身份重开终端，执行 `Set-ExecutionPolicy RemoteSigned` |
| `koishi.yml` 手改之后应用起不来 | YAML 语法错误；缩进、`~` 前缀、`$` 元信息都有含义 | 手改前先备份；不确定就改回用控制台操作（控制台会把改动写回配置文件）；注意 `~插件名` 表示不启用 |
| 同一插件想同时启用两份配置却只有一份生效 | 通常情况下一个插件同时只能运行一份配置 | 用插件名的别名后缀区分多份配置，或参考官方的多份配置方案；插件本身是否可重用由它的 `reusable` 属性决定 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 连接各聊天平台收发消息；从 npm 源拉取插件与依赖；控制台对内 / 对外提供网页与 WebSocket 服务；图片渲染类插件会访问 Chromium 或外部资源 |
| 读取文件 | 是 | 读取应用目录下的 `koishi.yml`、`.env.local`、插件代码；读取数据库文件与日志 |
| 写入文件 | 是 | 创建和更新项目目录、写回插件配置、写入数据库文件与日志、更新依赖（控制台「依赖管理」会改动本地依赖树） |
| 凭证 | 是（环境相关） | 各平台适配器需要机器人 token、App ID / Secret 等；这些必须由使用者自备并妥善保管。本 Skill 不内嵌任何密钥，也不要写进会提交到版本库的文件 |
| 子进程 / 后台常驻 | 是 | 它本身就是长期运行的服务：启动器用守护进程托管，Docker 用容器托管，服务器上通常交给 systemd 或同类进程管理器 |
| 监听端口 | 是 | 控制台与后端服务默认使用 5140 端口；公网 / 局域网开放前必须先做访问控制 |

## 触发场景

- 「帮我搭一个 QQ / Telegram / 飞书 机器人的框架」
- 「一个机器人要同时上好几个平台，有什么现成框架」
- 「群里收到特定消息就触发我的接口，怎么做」
- 「机器人怎么装插件、怎么在网页上配」
- 「服务器上怎么用 Docker 部署一个聊天机器人，还要能持久化」
- 「Koishi 插件启用了但不生效，帮我看看」

## 能力边界

**覆盖**：

- 跨平台适配：官方维护钉钉、Discord、KOOK、飞书、LINE、邮件、Matrix、QQ、Slack、Telegram、微信公众号、企业微信、WhatsApp、Zulip 等适配器插件；一个应用可同时接多个平台、每个平台可配多个账号。
- 网页控制台：插件市场、插件配置（含分组与启用停用）、依赖管理、指令管理、本地化文案编辑、沙盒对话、状态监控与日志。
- 插件化架构：插件可声明配置构型、可热重载、可声明 `reusable`，也可通过 `fork` 事件在不可重用插件内提供可重用逻辑。
- 服务与依赖：`inject` 声明必需 / 可选依赖，服务可自定义并由插件提供；`ctx.inject()` 把部分功能拆成子插件。
- 会话治理：触发前缀、过滤器（平台 / 用户 / 群组 / 频道 / 机器人，与 / 或两级组合）、计算属性、用户权限等级（0–4 级，登录插件可拿到 5 级管理员）。
- 数据与国际化：数据模型、数据库服务（由具体实现插件提供）、用户 / 频道级语言偏好与文案覆盖。
- 部署形态：图形化启动器（含 `koi` 命令行）、Docker 镜像（含轻量版）、模板项目、作为依赖嵌入已有工程。

**不覆盖**：

- 不替代各平台的准入工作：开发者账号、企业认证、回调域名、公网服务器与备案，都要使用者自己准备。
- 不提供某个垂直业务的成品功能；业务能力来自你选的插件或自己写的插件。
- 不托管服务：没有官方云托管，想要省事要用第三方托管方案（属另一套产品与计费）。
- 不做多租户隔离：一个应用对应一套配置，不面向「一套系统服务多个互不可见的客户」这种形态。
- 非官方插件的正确性与安全性不做任何保证，第三方插件的坑要自己担。
- 不负责平台的风控结果：接入方式不当、发送频率过高导致的账号风险由使用者承担。

## 依赖条件

- **Node.js**：最低 v18，推荐 LTS。模板项目与依赖调用两种方式需要你自行安装。
- **包管理器**：npm 自带即可，官方也推荐 yarn；国内建议配置镜像源。
- **Chromium**：很多插件靠它渲染图片。官方 Docker 标准镜像已预装；启动器和模板项目按所用插件的说明准备。
- **数据库**：需要持久化用户 / 频道数据时要额外选择并安装数据库服务插件，框架本体不自带。
- **平台侧**：接入真实平台需要该平台的机器人凭据或账号，部分平台还要求公网可达的回调地址。
- **端口与网络**：默认 5140；对外提供服务前要处理防火墙、反代与访问控制。
- **运维环境**：长期运行建议用启动器守护、Docker 或 systemd 之类的方式托管。

## 已知限制

- 通常情况下**一个插件同时只能运行一份配置**；需要多份配置要借助插件别名等机制。
- 非官方插件不保证安全性与可用性，部分插件会被标记为「不安全」，装了这类插件不会得到官方群支持。
- 插件依赖的服务由别的插件实现，缺哪个服务就缺哪块能力，功能是否可用取决于当前装的插件组合。
- 配置文件的结构官方标注为**未来可能变化**；控制台能覆盖绝大多数配置，少数项仍需手改文件。
- 启动器对各操作系统的版本支持是有清单的，不在清单里的系统官方不背书（可用社区版本或模板项目代替）。
- 上游在持续演进，具体版本号、命令行参数与插件包名请以官网文档与 `koi` 帮助输出为准，本文不做版本断言。
