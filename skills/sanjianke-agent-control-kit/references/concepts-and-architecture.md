# 概念与架构：loopx 到底控制了什么

> 上游项目：[loopx](https://github.com/huangruiteng/loopx)（Apache-2.0）。本文为三剪客团队按自身使用经验整理的概念说明，不是上游文档的翻译。

## 1. 一句话定位

loopx 是跑在 agent harness **之上**的一层本地控制平面。harness 负责「干」，loopx 负责「记住干到哪、下一步谁动、什么必须等人点头、证据在哪、还准不准继续」。

它既不替换 harness，也不是又一个 agent 框架，更不是某种 provider 专属的编排运行时。这个边界很关键：把 loopx 当成调度器去驱动模型，一定会失望；把它当成长任务的账本与闸门，它就非常值。

## 2. 它到底解决什么问题

### 2.1 会话中断后的状态丢失

一次会话能完成一个任务，但长周期工作不是这样运作的：目标会变、中途冒出需要人拍板的决策、证据会过期、Agent 之间要交接、定时器可能在没有有效进展时继续烧算力。聊天记忆加一个定时器，管不住这些。

loopx 的做法是把控制状态压成一层紧凑的持久数据，落在项目目录里：

- 活跃目标与当前授权范围
- 有序的用户待办与 agent 待办，含归属、认领、租约
- 具体的用户闸门（不是含糊的「等 owner」）
- 紧凑的运行历史、验收结论、阻塞原因、已接受的回写
- 配额、能力声明、安全回退、调度建议、停止条件

### 2.2 长任务被定时唤醒切碎

心跳自动化的价值是让目标活着，但高频唤醒会把工作切成一堆「只报状态」的小步。loopx 用一个派生信号来表达这件事（见第 7 节），让宿主知道最近这轮看起来是**卡住、真在跑、步子偏碎、还是产出了实质进展**。

### 2.3 跨 harness 的可迁移性

同一份治理结果要在换 harness 或换外部服务后依然成立，所以 loopx 把架构边界写死成四层（见第 4 节）。换掉执行者，控制状态和闸门定义不需要重写。

### 2.4 无人值守时的算力治理

长任务最贵的失败模式不是「跑错」，而是「一直在跑但没推进」。所以 loopx 把「这一轮该不该跑」独立成一个必须先问的机器契约，而不是让每轮自己决定。

## 3. 和「直接跑 Agent」的差别

| 维度 | 直接跑 Agent | 挂上 loopx 之后 |
|---|---|---|
| 状态放在哪 | 会话上下文里，关掉即散 | 项目 `.loopx/` + 运行根 `~/.codex/loopx/`，跨会话存活 |
| 换 harness | 基本等于重来，要重新交代背景 | 控制状态不变，换执行者即可接着跑 |
| 「下一步做什么」 | 每轮由模型当场判断 | 由待办队列与认领/租约决定，顺序可审计 |
| 需要人决策时 | 容易退化成「等待用户确认」 | 必须落成一个具体的闸门问题 |
| 「跑完了」的依据 | 模型说完成了 | 证据 + 验收 + 回写才计入，未验证不算成功 |
| 自动轮的成本 | 只要定时器醒了就烧 | 先过 `quota should-run`，跳过的轮不记账 |
| 多 Agent 协作 | 靠人分工，容易撞车 | 注册身份 + 认领 + 租约，冲突有据可查 |
| 审计与交接 | 翻聊天记录 | `review-packet` / `history` / `evidence-log` 直接产出 |
| 失败恢复 | 人肉回忆 | 备份、回滚、历史索引重建都有明确入口 |

一句话：**直接跑 Agent 优化的是「单轮质量」，loopx 优化的是「跨轮正确性」。**

## 4. 四层边界

这四层描述的是不同的责任边界，不是四种可互换的插件：

| 边界 | 归谁管 | 干什么 |
|---|---|---|
| **Kernel（内核）** | loopx 本体 | 持有持久的目标、待办、闸门、证据、配额、恢复与调度真相 |
| **Capability（能力）** | loopx 本体 | 定义稳定、与 provider 无关的契约：从控制状态出发产出一个有界、可验证的调用方结果 |
| **Provider（提供方）** | 可选扩展 | 调用外部系统或本地实现，返回有界观察、效果结果与读回 |
| **Extension（扩展）** | 可选扩展 | 把某个 provider 打包并运维起来：安装、就绪、启用、升级、停用、回滚 |

执行路径是 `Agent -> Capability -> Provider`；控制路径回到 `Provider 读回 -> Capability 状态转换 -> Kernel`。**扩展不是新的控制权所有者**，它只是让一个可选 provider 变得可管理。

注意：像 `--available-capability shell` 这种宿主声明，说的是**这台机器观察到具备哪种执行支撑**，它是运行时容量，既不是产品能力，也不等于授权。真正的能力在提议状态变更前还要自己过一遍策略和授权检查。

## 5. 控制平面的五个问题

内核把所有机制收敛成五个问题，每问对应一条跨 harness 都成立的产品承诺：

| 问题 | loopx 让它保持可见的东西 |
|---|---|
| 目标是什么？ | 活跃目标、显式范围、当前授权 |
| 下一步是什么？ | 有序的用户/agent 待办、归属、认领、租约 |
| 哪里需要人判断？ | 具体的用户闸门，而不是模糊的等待 |
| 证据变了什么？ | 紧凑运行历史、验收、阻塞、已接受回写 |
| 还能继续吗？ | 配额、能力、安全回退、调度建议、停止条件 |

## 6. 状态存在哪：八个存储

| 存储 | 归属 | 谁读 | 谁写 | 用途 |
|---|---|---|---|---|
| 项目 registry | 项目目标 | CLI、执行者、status | `connect`、`bootstrap`、少量项目设置 | 声明目标身份、仓库、适配器、授权、守卫 |
| 活跃目标状态 | 项目目标 | 执行者、适配器、人 | 合格的 peer 或操作者 | 持久上下文、最新进展、下一步动作、验收面 |
| 共享全局 registry | 本地控制平面 | status、看板、任意项目 shell | `connect`、`refresh-state`、`sync-global` | 多项目发现，不必手工拷 registry 条目 |
| Run 载荷 | 目标运行时 | 执行者、本地复核者 | 适配器、`refresh-state`、`read-only-map` | 单次运行的完整私有证据 |
| 紧凑 run 索引 | 目标运行时 | status、看板、心跳 | 适配器、reward 覆盖写入器 | 可公开的安全时间线与最新状态 |
| 配额 / 花费账本 | 目标运行时或 registry | status、看板、自动化 | `quota` 系列命令、控制器回写、操作者决策 | 自动轮的占空比或加权份额策略 |
| status 导出 | CLI / status 层 | 看板、预检、心跳 | `loopx status` | 面向 agent 的机器契约与看板输入 |
| 看板 UI 状态 | 浏览器会话 | 人 | 浏览器 URL / 搜索状态 | 筛选、选中目标、选中轮次；**不是持久目标真相** |

落到磁盘上，一个连好的项目长这样：

```text
your-project/
  .loopx/registry.json
  .codex/goals/<goal-id>/ACTIVE_GOAL_STATE.md

~/.codex/loopx/
  goals/<goal-id>/runs/
```

这三处都是有状态的本机运行数据，必须进 `.gitignore`：

```gitignore
.loopx/
.codex/goals/
.opencode/goals/
goals/**/ACTIVE_GOAL_STATE.md
```

要提交的只有脱敏后的模板或示例，绝不能提交某个控制器的**活跃** `ACTIVE_GOAL_STATE.md`。

## 7. 事件账本与节拍信号

### 7.1 四类不可丢的事件

loopx 把「紧凑 run 索引 + 配额/奖励覆盖」当作长任务的事件账本。当前状态是对这些事件的**投影**：投影可以为提示词和看板压缩旧细节，但不能悄悄替换掉让某个决策可审计的那条原始事件。需要保留的事件类别：

- **工作事件**：`refresh-state`、只读地图、适配器 tick、进展分类——说清变了什么、怎么验收的
- **决策事件**：操作者闸门、检查点恢复契约、批准、推迟，以及绑定到具体轮次的人工奖励
- **记账事件**：`quota_slot_spent` 这类配额花费行
- **证据事件**：评估、CI、产物、阻塞、失败、完成，或只读的证据轮询观察

`loopx status` 通过 `event_ledger_summary` 暴露这个边界：抽样统计记账、决策、证据、状态、工作五类事件的数量。

由此得到一个**持久执行边界**：Codex 线程是可替换的工人，干完一段有界转换就写事件；控制平面从账本派生派发、配额、闸门和最新状态投影。心跳提示词应当保持很薄——去查 status、quota、review packet 和活跃状态，而不是把项目历史背在身上。

### 7.2 节拍信号（cadence hint）

这是一个小型派生信号，`schema_version` 为 `cadence_hint_v0`，用来提示宿主或控制器「最近的进展形态」：

| 字段 | 取值 | 含义 |
|---|---|---|
| `signal` | `blocked` / `active_work` / `thin_progress` / `material_progress` / `unknown` | 最近的控制平面证据说明什么 |
| `recommendation` | `wait` / `widen` / `keep` | 给宿主/控制器的轻量建议 |
| `reason_codes` | 紧凑字符串数组 | 机器可读的解释 |
| `authority` | 可选 | 最终做裁决的权威，用于解释早期兼容性建议被改写 |
| `superseded` | 可选 | 被替代的早期信号，留作诊断 |

典型组合与应对方式：

- `blocked` + `wait`：不要放宽范围；把具体闸门或阻塞点摆出来
- `active_work` + `keep`：跟随最终的 agent 作用域交互与调度决定；`superseded` 只用于诊断
- `thin_progress` + `widen`：下一轮合格的动作应当争取产出一个内聚的产物加验收/回写，否则就要写明为什么放宽不安全
- `thin_progress` + `keep`：上一轮确实小，但连续次数还不够，先不强行改变节拍
- `material_progress` + `keep`：最近产出了更完整的产物、验收或里程碑
- `unknown` + `keep`：元数据不足，别做激进的自动化变更

这个信号是**派生建议，不是调度策略**。配额、闸门、目标边界、权限、公私边界扫描，以及人和控制器的决定，仍然是真相来源。「进展偏碎」的检测刻意保守：它基于 agent 的回写元数据，而不是对真实运行时长的精确测量——一段很短但已验收的修复可能很有价值，一轮很长的执行也可能只是在打转。

## 8. 配额模型（数字口径）

配额回答的是「自动轮现在可不可以跑、允许跑哪种」，不是策略。

| 项 | 默认/口径 |
|---|---|
| 计算量 `quota.compute` | 默认 `1.0`；registry 里缺失时，status 按 `1.0` 处理，保证老目标仍能跑 |
| 单槽时长 `slot_minutes` | 可选，默认 `1`，即默认粒度下一槽等于一分钟算力 |
| 观察窗口 | 连续 24 小时窗口内是否持续合格 |
| 关掉自动轮 | `loopx configure-goal --quota-compute 0`；负值会被拒绝 |
| 完成待办后复查节拍 | 标准与细粒度 Turn 模式默认都是 **5**；可用 `--execution-replan-after-todos N` 覆盖，`--clear-execution-replan-after-todos` 恢复继承 |
| 内部控制平面自修复 | `control_plane.self_repair.enabled` 默认 `false` |
| 记账粒度 | 粗粒度控制器应按调度分钟数花槽，例如 `--slots 1` |

到阈值后，下一次 `quota should-run` 会给出复查结论而不是继续闷头跑。这个「复查节拍」没有隐藏默认之外的魔法：设成 3 就是每 3 个完成待办后插入一次重新规划。

## 9. 多 Agent 怎么定位彼此

已注册的 Agent 是**对等体**（`agent_model=peer_v1`）：不存在一个持久的 leader 身份，谁动由认领、租约、任务边界、能力和有类型的续跑决定。

- 任何写仓库的 peer，在任务或目标策略要求时必须使用独立 worktree；隔离缺失时 `workspace_guard` 会 fail closed
- 小的、符合 AGENTS 规范且已验收的改动，可以带着明确的 loopx 证据自行合并
- 风险更高的改动应当创建独立的后续者，或走普通 `independent_handoff`（`action_kind=review`）
- 需要强制执行者分离时，才使用 `excluded_agents`

## 10. 选型判据

**适合上**：

- 跨天/跨周的工程、研究、基准或实验目标
- 必须保住范围、证据和复核状态的 issue / PR 循环
- 周期性的心跳或监控工作
- 存在 owner、安全、发布或私有数据闸门的项目
- 对等 Agent 团队，归属、租约、交接真的会影响结果
- 进展必须让非工程背景的操作者看懂的内容或运营流水线

**不适合，或者需要先缩范围**：

- 一次会话就能收尾的短任务——上控制平面是纯负担
- 期望它「自己把项目做完」的诉求——它不是自主生产控制器
- 需要它批准危险操作、代你发布、发放凭证的场景——这些永远留给人
- 想把未经验证的运行直接当成成功证据的场景——它明确不干这事

## 11. 关键命令地图

```text
loopx doctor                                  安装与宿主材料健康
loopx status                                  目标、闸门、注意力队列、下一步
loopx diagnose --goal-id <id>                 给 agent 用的紧凑证据包
loopx quota should-run --goal-id <id>         这一轮要不要跑（含 spend 策略）
loopx todo claim / todo update                认领与回写
loopx refresh-state --goal-id <id>            本地状态或文档变化后追加一次刷新
loopx history --goal-id <id>                  紧凑运行历史
loopx review-packet --goal-id <id>            交接或复核用的包
loopx backup-state --project .                迁移/修复前的状态归档预览
```

`diagnose` 是刻意做成「给 agent 看的证据包」的：它收集紧凑的 status、`quota should-run`、待办、交互契约和边界信号，再给 agent 一张推理清单。**最终判断由 agent 用自然语言做出，loopx 的机器信号只是证据，不是判决。**
