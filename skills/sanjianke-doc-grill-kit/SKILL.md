# 三剪客 · 带资料追问

先把资料读成事实索引，再基于索引逐条追问，标出矛盾与缺口

一团资料摆在面前时，最没用的提问方式是「这个项目的风险是什么」——它逼着模型用常识去编，而不是用你的资料去答。
有用的提问方式长得不一样：「F-0117 说灰度只覆盖 5% 用户，F-0242 说全量已上线，这两条哪个为准？」

这套方法把追问拆成前后两段。前一段只做一件事：把资料摊成一张**事实索引**，每条事实一张卡，带原文锚点，
不带任何评价。后一段才允许提问，而且规定每个问题必须挂上索引里的编号，或者明确承认「这是我发现的缺口」。

这样做换来三件实在的东西：问题指得回原文、答案错得起疑、矛盾露得出来。适合资料多、时间跨度长、
换了不止一拨人、同一件事在不同文件里说法不一致的场景。

|---|---|---|
| 网络访问 | 不需要 | 全程离线可跑。资料由你提供，不抓取、不上传、不联网核对。若你要补充外部资料，由你自己贴进来或放进工作区 |
| 读取文件 | 需要 | 只读你明确指定的资料目录（`_data/` 及其子目录）。不主动遍历工作区其它位置，不读与本次无关的文件 |
| 写入文件 | 需要 | 只在资料目录旁的 `_grill/` 工作区新建文件（索引、问题卡、矛盾台账、缺口台账）。不修改、不删除你的任何原始资料 |
| 凭证 | 不需要 | 不索取、不读取、不存储任何账号、密钥、Token 或数据库口令。资料里若含凭证，检索时一律打码，只保留「此处有凭证」这一条记录 |
| 子进程 / 后台常驻 | 不需要 | 不装后台服务、不常驻进程。目录扫描用一次性命令完成 |

本 Skill 不内嵌任何密钥，也不调用任何第三方服务。所有产物都是纯文本 Markdown 与 JSON，你用任何编辑器都能打开、检索、进版本库。

资料里可能夹带个人信息、客户名单、合同条款或未公开的经营数据。索引与问题卡是对原文的重述，
**默认按资料本身的密级处理**，不要把它们复制到聊天窗口、外部工具或公开仓库里。

## 触发场景

- 「这堆资料你先看一遍，然后问我点有用的，别再问那种百度一下就知道的问题。」
- 「三个月的会议纪要都在这里，帮我找出哪里前后不一致。」
- 「方案 V1 到 V7 我全给你，问问我哪些决定其实是被后面的版本推翻了。」
- 「代码仓库的说明文档和实际口径对不上，你帮我列出来，我去问负责人。」
- 「我要跟老板过一遍这个项目，你先当一遍审稿人，问题要能指到原话。」
- 「这个需求文档写得很漂亮，我想知道哪些地方其实是空的。」

## 快速开始

最小可用路径：先立工作区，再走两趟——先建索引，再追问。

**第 1 步：立工作区**

```text
_data/                      # 你放资料的地方，本 Skill 只读
├─ 会议纪要/
├─ 方案/
└─ 代码说明/
_grill/                     # 本 Skill 写的所有产物，都在这
├─ 01-资料总览.md           # 每份资料的来源、时间、版本、可信度初判
├─ 02-事实索引.md           # 一条事实一行，带编号与原文锚点 ← 核心产物
├─ 02-事实索引.json         # 同内容的机读版，供检索与差集
├─ 03-问题卡.md             # 每个问题一张卡，挂事实编号
├─ 04-矛盾台账.md           # 资料之间冲突的地方
└─ 05-缺口台账.md           # 资料没说、但绕不过去的地方
```

**第 2 步：分诊**——给资料按权威等级（L0~L4）和时效排个队，拿到索引优先级。
看 `references/01-资料预处理与事实索引.md`。

**第 3 步：建索引**——逐份抽事实，每条必须能回指到具体出处。抽完先做一轮**人眼抽检**，
随机挑 10 条比对原文，抽检不过就重抽，不要带着错误索引往下走。

**第 4 步：追问**——只准用索引里的编号提问。问法、排序与验收判据看 `references/02-基于索引的追问流程.md`。

**第 5 步：找矛盾与缺口**——按清单逐类扫一遍，矛盾不要当场裁决，列出来交给人。
看 `references/03-矛盾点与缺口检查清单.md`。

一个最小示范（三份资料、八条事实就能跑）：

```text
资料：立项书.docx、9月周会纪要.md、接口说明.md
索引：F-0001 目标用户为中小商家（立项书 §1，L1）
      F-0002 首期只做 PC 端（立项书 §3，L1）
      F-0003 移动端已排进 9 月迭代（9月周会 09-12，L2，日期：09-12）
追问：Q-003（对 F-0002 与 F-0003）——「首期范围到底含不含移动端？
      若以周会为准，立项书 §3 的范围描述需要改；若以立项书为准，周会这条排期依据是什么？」
```

注意这个问题**没有**问「你们为什么不做移动端」，因为资料里没有这个信息——那属于缺口，进 `05-缺口台账.md`，不要混进问题里编。

## 能力边界

**覆盖**：

- 对指定资料目录做结构化摘要：来源、时间、版本、权威等级、覆盖主题
- 抽取并编号事实卡，每条带出处定位（文件 → 章节/页码/行号/时间戳）与原文短引
- 建立机读索引，支持按关键词、按主题、按时间、按权威等级检索
- 基于索引生成追问，每个问题挂事实编号，并给出「资料里已有的答案」与「资料里缺的部分」
- 标出资料之间的矛盾，区分「真冲突」与「口径差异」，给出核对建议与优先级
- 建立缺口台账，把「资料没说」和「资料说了但没落实」分开记
- 输出问题卡，可直接拿去开会、找负责人核、写进评审记录

**不覆盖**：

- 不替你判断业务对错，也不替你决定哪一方口径为准。矛盾一律列出来，裁决留给人
- 不补全资料。任何索引里没有的内容，宁可标为缺口，也不推测填充
- 不保证抽取没有遗漏。抽样抽检能压低错误率，不等于零错误；关键决策请对原文件复核
- 不解析加密文件、扫描件图片、手写批注与无法解码的二进制格式；这类内容需你先转成文本
- 不替代法务、财务或合规意见。合同条款、金额口径、责任划分的最终解释权不在本方法内
- 不做多人协作调度与权限管理，产物就是本地文件，谁改了什么得靠你自己的版本管理

## 依赖条件

- 一份明确的资料清单（目录路径或文件列表），以及一句本次追问想解决的核心问题
- 资料已被转成可读文本（Markdown / txt / docx 导出文本 / 可复制的 PDF 文本层皆可）
- 一个可读写的本地目录，用于放 `_grill/` 工作区
- 想跑通「人眼抽检」这一步，需要一个愿意花十分钟比对原文的人（这步不建议省）
- 不需要网络、不需要 API Key、不需要安装任何第三方服务

## 已知限制

- **大资料量的召回衰减**：索引条数上千后，对索引中段的引用会变得不稳定。请用 `01` 里的两段式法（先分诊索引、再按主题细抽），不要一次灌全部
- **跨文件拼接的事实容易抽错**：同一条事实被拆在文件 A 的背景段和文件 B 的结论段时，容易抽成两条互相打架的卡。分片时保留重叠段落并在卡上标注 `跨片`
- **口径差异常被误判为矛盾**：「6 月目标 3000 万」与「7 月目标 5000 万」不是矛盾，是时点不同。`03` 里的矛盾分型就是为了拦住这类误报
- **时间信息缺失的资料**：没有落款日期的纪要，时效判断只能靠上下文推断，索引里会标 `日期：未标`，请不要当成可信时点使用
- **重述天然有损耗**：事实卡是原文的重述，措辞与原文不会完全一致。凡涉及数字、日期、人名、金额、条款号，以原文为准，索引只作导航
- **索引错了后面全错**：索引建偏时，所有追问都会建立在错误前提上。抽检是这套方法唯一的人工闸门，跳过它整套流程的可信度会明显下降

## 自检清单

**建索引阶段收尾时逐条打勾：**

- [ ] 每份资料都在 `01-资料总览.md` 里有来源、时间、版本与权威等级
- [ ] 每条事实都有唯一编号、出处定位与原文短引，没有「据我了解」这类无锚点条目
- [ ] 区分了「原文直接说」与「我从中推断」，推断项已标记
- [ ] 随机抽检 10 条比对原文，错误率可接受
- [ ] 资料里的凭证、密钥、口令已打码，未进入索引

**追问阶段收尾时逐条打勾：**

- [ ] 每个问题都挂了事实编号，或明确标为缺口问题
- [ ] 没有出现「资料里找不到依据」的问题被当成正常问题混进去
- [ ] 每个问题都能答上「这条资料里已经说了什么」
- [ ] 问题的排序让最影响决策的排在最前

**找矛盾阶段收尾时逐条打勾：**

- [ ] 每条矛盾都写了两侧的原文出处，不是转述
- [ ] 每条矛盾都判了类型：真冲突 / 口径差异 / 时点差异 / 版本替换 / 归属不清
- [ ] 每条矛盾都给了核对对象与核对渠道，可以拿去直接问
- [ ] 缺口台账里，资料没说与说了没做分开记
- [ ] 没有对任何一条矛盾自行下结论
