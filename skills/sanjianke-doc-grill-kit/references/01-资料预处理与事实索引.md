# 资料预处理与事实索引

这一份解决三个问题：怎么把一堆格式不一的资料变成能排序的工作清单（分诊）、
怎么把正文里的信息抽成带锚点的事实卡（抽取）、怎么证明抽出来的东西真的在原文里（锚定与抽检）。

顺序不能换。跳过锚定直接抽取，得到的就是一份看起来很整齐、但没法核对的伪索引，
后面所有追问都会建在沙子上。

---

## 一、输入前置检查

在动手抽任何一条事实之前，先花十分钟过一遍这五关。任何一关不过，先补料再开工。

| 检查项 | 判据 | 不过怎么办 |
|---|---|---|
| 可读性 | 文本能被直接读取，不是扫描图或加密文档 | 请你先转成文本；扫描件需 OCR 后再进流程 |
| 编码 | 打开后中文不乱码 | 换编码另存一次，不要带着乱码抽事实 |
| 完整性 | 文件能打开到底，不是截断的半份 | 标为「残件」，其内容只作线索，不作依据 |
| 重复度 | 同一份内容没有多个副本 | 用正文前 100 字做指纹，重复的只留最新版本，旧版记为历史版本 |
| 边界 | 资料范围与本次核心问题大致相关 | 完全不相关的先移出 `_data/`，避免稀释索引 |

**重复副本的处理**尤其容易出错：`方案-V3.md`、`方案-V3(1).md`、`方案-V3-最终.md`
经常是三次不同的改动。不要按文件名判重，按正文指纹判重；确实内容不同但名字相近的，
在台账里写清三者差异，否则后面会把「版本替换」误报成「真冲突」。

## 二、资料分诊：先排序，再动手

一份合同和一条群聊记录，在追问里的分量完全不同。分诊就是把这个分量显式写下来。

### 2.1 权威等级（L0~L4）

| 等级 | 资料类型 | 在追问中的默认用法 |
|---|---|---|
| L0 | 合同、监管文件、正式批复、已发布的标准 | 最高依据。与任何其它资料冲突时，默认以 L0 为准（仍需人确认） |
| L1 | 立项书、正式方案、架构决策记录、已发布接口文档 | 作为范围与设计的依据；被 L0 覆盖时让位 |
| L2 | 会议纪要、评审记录、邮件结论 | 作为过程与决议依据；注意其只对某一时点有效 |
| L3 | 群聊记录、个人笔记、口头承诺的转述 | 只作线索，不作依据；引用时必须同时给出待核对象 |
| L4 | 外部公开资料、竞品说明、二手转述 | 只作参考；不得用来覆盖 L0~L2 |

**同等级冲突时**，按「更晚的版本 > 更早的版本」排，但要注意：晚不等于对。
一个后写的纪要可能只是复述了某个错误理解，真正生效的仍是更早的正式方案。
所以同等级冲突一律进矛盾台账，不要自动裁决。

### 2.2 时效窗口

每条资料登记一个时间字段，取值只有三种写法：

```text
日期：2026-03-14          # 原文有明确日期
日期：约 2026 Q1          # 只能从上下文推断，必须带「约」
日期：未标                # 无法判断，此资料不作为时点依据
```

时间字段决定了这条资料「说的是哪个时刻的世界」。凡涉及数字目标、排期、人员安排，
时点是事实的一部分，不是附属信息。丢时点等于丢一半信息。

### 2.3 覆盖矩阵

把所有资料按主题横向摊开，一眼看出哪些主题只有一份资料撑着——那些位置就是追问的重点。

| 主题 | L0/L1 | L2 | L3/L4 | 覆盖风险 |
|---|---|---|---|---|
| 目标用户与场景 | 立项书 §1 | 9月周会 09-12 | — | 低 |
| 首期功能范围 | 立项书 §3 | 9月周会 09-05 | 群聊 08-30 | **高：正式文档与周会口径不同** |
| 上线时间 | 立项书 §6（3月） | 9月周会（推迟） | — | 中 |
| 数据合规 | — | — | — | **缺口：全无覆盖** |

「覆盖风险」列只填 低 / 中 / 高 与一句原因，不要在这里写结论。

### 2.4 索引优先级

分诊的产出是排序，不是评价。排序规则按顺序比较：

1. L0/L1 且时间明确 → 先抽
2. L1 但时间未标 → 次之，抽的时候额外留意上下文时间线索
3. L2 且落在核心问题时间窗内 → 再次
4. L3/L4 → 最后，只抽能被引用的具体句子，不抽观点

## 三、分片策略

分片的目的是让每一片都「自成语境」——单独拿出来也能看懂这句话在说什么。

| 资料类型 | 分片单位 | 建议片长 | 重叠 |
|---|---|---|---|
| 会议纪要 | 一次会议 → 一个议题 | 300~800 字 | 议题切换处留 1 段重叠 |
| 方案 / 立项文档 | 一级章节 → 一个决策点 | 400~1200 字 | 章节边界留 1~2 段重叠 |
| 代码库说明 | 一个模块 → 一个对外接口 | 按接口切，不按行数 | 涉及上下游调用时带上对手方接口段 |
| 邮件往来 | 一个话题 → 一个结论 | 整条话题链一起 | 不要单独切出中间一封 |
| 合同 / 条款 | 一条条款 | 单条 | 条款间的引用关系单独登记 |

三条硬规则：

- **不要把一句话切两半**。分片边界落在段落或条目边界上，宁可片长不均。
- **跨片事实必须标 `跨片`**。同一条事实的因在前片、果在后片时，两张卡都要标，
  并在卡上互指编号，否则后面会被当成两条独立事实，甚至被判成矛盾。
- **图表、表格、附件清单要显式登记**。正文写「见附表 3」而附表没给，这是一个缺口，
  不是一个可以忽略的引用。见 `03` 的缺口清单。

## 四、事实卡规范

事实卡是这套方法的最小积木。一张卡只说一件事。

### 4.1 字段定义

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 事实编号，格式 `F-0001`，全库唯一，不复用 |
| `claim` | 是 | 一句话事实陈述，主语明确，不加评价词 |
| `quote` | 是 | 原文短引，8~40 字，必须逐字一致（可用 `…` 省略） |
| `src.file` | 是 | 文件名，相对 `_data/` 的路径 |
| `src.loc` | 是 | 定位：章节号 / 页码 / 行号 / 时间戳，至少给一个精确值 |
| `kind` | 是 | `原文事实` / `数值` / `决议` / `推断` |
| `level` | 是 | 权威等级 L0~L4 |
| `date` | 是 | `2026-03-14` / `约 2026 Q1` / `未标` |
| `topics` | 是 | 主题标签，1~3 个 |
| `cross` | 否 | `跨片`，并写互指编号 |
| `note` | 否 | 抽取时的疑问，如「此处与 F-0091 的表述不同」 |

### 4.2 编号法

```text
F-0001 … F-9999       事实卡，顺序编号，一经分配永不复用
Q-001  … Q-999        问题卡，见 references/02
C-001  … C-999        矛盾条目，见 references/03
G-001  … G-999        缺口条目，见 references/03
```

**永不复用**这条要严格。删掉一条事实时，编号留空位并记一行「F-0032 已撤销，原因：误抽」，
不要让 F-0032 出现在别处。编号复用会让所有已经发出去的问题卡瞬间失效。

### 4.3 抽取五条纪律

1. **能用原词就用原词**。把「大概三成」改写成「30%」是加工，不是抽取。
   确实需要归一化时，写在 `claim` 里，`quote` 必须是原文。
2. **每条必须有锚点**。写不出 `src.loc` 的条目不许进索引，直接进缺口台账。
3. **推断必须显式标记**。`kind: 推断` 的卡，`note` 里要写清「依据 F-00xx + F-00yy 推出」。
   推断卡可以参与追问，但不能当作依据引用。
4. **数值单独成卡**。凡是带了数字、日期、金额、比例、人月数的句子，
   一律单独抽一张 `kind: 数值` 的卡，并且把数字原样保留（含单位与口径）。
   「营收 3000 万」和「GMV 3000 万」是两张不同的卡。
5. **凭证打码**。资料里出现密钥、口令、内网地址、个人手机号时，
   `quote` 里替换为 `[已打码]`，`note` 写「原文此处含凭证/个人信息」。

### 4.4 四种卡的性格

| `kind` | 特征 | 在追问里怎么用 |
|---|---|---|
| `原文事实` | 客观陈述，无争议 | 可直接作为问题依据 |
| `数值` | 带单位与口径 | 追问口径、来源与更新时点 |
| `决议` | 「会议决定…」「确认…」 | 追问执行状态与责任人 |
| `推断` | 由多条推出 | 只能作为问题的起点，不能作为结论依据 |

## 五、两段式索引流程（资料多时必用）

索引超过 300 条还是一次性抽，后段质量会明显下滑。用两段：

**第一段：侦察索引（每份资料 3~8 条）**

只抽三类东西：这份资料是什么、覆盖哪些主题、哪几句是核心决策或关键数字。
目的是拿到一张全局地图，以及决定第二段抽哪些片。

```text
输出：_grill/01-资料总览.md 的「核心条目」列
判断：哪些主题只有一份资料？哪些主题多份资料打架？→ 决定第二段顺序
```

**第二段：主题细抽（一次只抽 1~2 个主题）**

按 `2.3 覆盖矩阵` 里「覆盖风险：高」的主题优先。每次只抽一个主题，
把这个主题在所有资料里的相关片全捞出来一起看，抽完再换下一个。

这样做的理由很实际：同一主题散在不同文件里的表述放在一起看，
矛盾与时点差异会自己浮出来；分文件抽则很容易先入为主，把第一份的说法当成基准。

**第三段（可选）：反向补齐**

细抽完，拿 `02-事实索引.json` 过一遍去重与差集：

- 去重：`claim` 语义重复的合并，保留锚点最精确的那条，其余在 `note` 里互指
- 差集：按主题统计卡数，卡数为 0 的主题——那不是沉默，是缺口，进 `05-缺口台账.md`

## 六、机读索引格式

`02-事实索引.json` 用最朴素的结构，一行一条，方便你用脚本做检索和差集：

```json
{
  "index_version": "1",
  "built_at": "2026-03-20",
  "source_root": "_data/",
  "facts": [
    {
      "id": "F-0001",
      "claim": "目标用户为中小商家，首期不做个人用户",
      "quote": "本产品首期面向中小商家，暂不覆盖个人用户",
      "src": { "file": "方案/立项书.md", "loc": "§1 目标用户" },
      "kind": "原文事实",
      "level": "L1",
      "date": "2026-03-14",
      "topics": ["目标用户"],
      "cross": null,
      "note": null
    }
  ]
}
```

维护纪律：`02-事实索引.md` 与 `.json` 必须同源。改一处就两处一起改，
或者只改 `.json` 再重新渲染 `.md`。两份内容不一致时，后面的追问会引用到不存在的编号。

**字段顺序不要随心情变**。差集脚本、去重脚本都按固定字段读，顺序一变就得改脚本。

## 七、抽检与验收

抽检是这套方法唯一的人工闸门，不可跳过。做法很简单：

1. 从索引里**随机**抽 10 条（不是挑你最有信心的 10 条）
2. 逐条打开原文，比对三件事：`quote` 是否逐字一致、`claim` 是否忠于原意、`src.loc` 是否指对位置
3. 记下错误条数与错误类型

**错误分型：**

| 错误类型 | 表现 | 处理 |
|---|---|---|
| 锚点错 | 引文存在，但位置指到了另一处 | 修正 `loc`，不算严重 |
| 引文错 | `quote` 与原文有增删字 | 必须改；说明抽取时在改写而非摘录 |
| 语义漂移 | 原文「可能」被抽成「会」，「部分」被抽成「全部」 | **严重**，全批重抽 |
| 凭空生成 | 原文里根本没有这条 | **最严重**，全批重抽并逐条回查 |
| 归属错 | 把 A 文件的话记到 B 文件头上 | 修正文件字段，回查同批 |

**通过线：** 10 条里 `引文错 + 语义漂移 + 凭空生成` 合计为 0，
锚点错不超过 1 条（修正即可）。达不到就重抽，不要带着 2 条漂移往下走——
抽检放大到全体，那意味着索引里可能有两成是歪的。

**抽检记录要留档**：在 `01-资料总览.md` 末尾追加一行
「抽检 10 条，锚点错 1，语义漂移 0，凭空生成 0，结论：通过」。

## 八、完整小样例

资料（三份，总长约 4000 字）：

```text
_data/方案/立项书.md
_data/纪要/2026-09-12 周会.md
_data/代码/接口说明.md
```

`01-资料总览.md` 片段：

| 文件 | 时间 | 等级 | 核心条目 | 覆盖主题 |
|---|---|---|---|---|
| 方案/立项书.md | 2026-03-14 | L1 | 首期只做 PC 端；目标中小商家 | 目标用户、范围、排期 |
| 纪要/2026-09-12 周会.md | 2026-09-12 | L2 | 移动端排进 9 月迭代 | 排期、范围 |
| 代码/接口说明.md | 未标 | L1 | 订单接口含移动端字段 | 接口 |

`02-事实索引.md` 片段：

```text
F-0001 | 目标用户为中小商家，首期不做个人用户
       | 引：「本产品首期面向中小商家，暂不覆盖个人用户」
       | 源：方案/立项书.md §1 目标用户 | 原文事实 | L1 | 2026-03-14 | 目标用户

F-0002 | 首期功能范围只包含 PC 端
       | 引：「首期仅交付 PC 端功能」
       | 源：方案/立项书.md §3 范围 | 原文事实 | L1 | 2026-03-14 | 功能范围

F-0003 | 移动端已排进 9 月迭代计划
       | 引：「移动端排进 9 月这批迭代」
       | 源：纪要/2026-09-12 周会.md 09-12 议题二 | 决议 | L2 | 2026-09-12 | 排期,功能范围

F-0004 | 订单接口已预留移动端字段
       | 引：「device_type 字段取值含 ios / android」
       | 源：代码/接口说明.md 订单接口 | 原文事实 | L1 | 未标 | 接口,功能范围
```

到这里就应该看出来：F-0002 与 F-0003 是**范围口径不一致**，
F-0004 是一个旁证——接口已经为移动端留了字段，说明工程侧的口径跟周会一致。
这三条正好凑成一个矛盾条目（C-001）和一连串可追问的点。

**注意这里什么都没下结论**。索引阶段只负责把摊平的事实摆好，
判断「到底哪个为准」是追问阶段要问给人的问题。

## 九、辅助：扫描与统计脚本（可选）

不想手动盘点目录时，用一次性命令列出文件清单与字数，方便决定分片顺序：

```bash
# 列出资料清单：路径 / 字节数 / 行数
find _data -type f \( -name '*.md' -o -name '*.txt' \) -print0 \
  | xargs -0 -I{} sh -c 'printf "%s\t%s\t%s\n" "{}" "$(wc -c <"{}")" "$(wc -l <"{}")"' \
  | sort -k2 -nr
```

Windows PowerShell 下等价写法：

```powershell
Get-ChildItem _data -Recurse -File -Include *.md,*.txt |
  Select-Object FullName, Length, @{n='Lines';e={(Get-Content $_.FullName).Count}} |
  Sort-Object Length -Descending
```

按主题统计卡数（需要 `jq`）：

```bash
jq -r '.facts[].topics[]' _grill/02-事实索引.json | sort | uniq -c | sort -nr
```

卡数为 0 的主题就是缺口候选。这个命令跑完，`03` 里的缺口扫描会轻松很多。

脚本只用来盘点，不用来抽事实。事实必须由人（或模型）读原文抽取，
脚本算出来的词频、相似度不能当作事实卡的任何字段。
