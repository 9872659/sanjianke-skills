# 矛盾点与缺口检查清单

这一份干两件事：把资料里**互相打架的地方**系统地扫出来，把资料里**该有而没有的部分**系统地扫出来。

两件事必须分开做，也必须分开记。矛盾的解法是「找人裁决」，缺口的解法是「补料」。
混在一张表里，最后会变成一堆没人认领的待办。

**贯穿全篇的一条纪律：本方法只发现、不定性。**
「哪一方为准」是业务判断，不是资料判断。发现矛盾的人没有裁决权，
这不只是谨慎，也是让结论能被追责的唯一办法。

---

## 一、先排除误报：五型分类

同一件事出现两种说法，不一定就是矛盾。先分型，再决定要不要报。

| 型 | 特征 | 是不是真矛盾 | 处理 |
|---|---|---|---|
| **A 真冲突** | 同一主语、同一时点、同一口径，取值不同 | **是** | 进矛盾台账，标 P0/P1 |
| **B 口径差异** | 数字不同，但统计范围/单位/含税口径不同 | 通常不是 | 先追问口径，口径一致后仍不同才算 A |
| **C 时点差异** | 说法不同，但资料时间不同，且后一份在处理前一份 | 不是 | 记入「演进轨迹」，不作为矛盾上报 |
| **D 版本替换** | 同一文档不同版本，新版本明确修订了旧版本 | 不是 | 旧版标 `已失效`，保留在台账里作历史 |
| **E 归属不清** | 说法不冲突，但没人认领 / 指向不明 | 不是矛盾 | 进缺口台账的「归属缺口」 |

### 判定顺序（不要跳步）

```text
1. 主语是不是同一个？   否 → 不是矛盾，可能是并列的两件事
2. 时点是不是同一个？   否 → 大概率是 C 时点差异，查演进轨迹
3. 口径是不是同一个？   否 → 大概率是 B 口径差异，先追口径
4. 是不是同一文档的前后版本？ 是 → D 版本替换
5. 以上都通过 → A 真冲突
```

### 三种最常被误报的情况

- **「目标 3000 万」vs「目标 5000 万」**：大概率 C。查两份材料的时间与是否写了「上调」。
- **「覆盖 5% 用户」vs「已全量」**：可能是 A，也可能是时点差异（灰度 → 全量是正常演进）。
  关键看有没有写清时间，没写清的，两边都要打问号——这本身就是个时点缺口。
- **「只做 PC 端」vs「移动端排期」**：看着是 A，其实常是**范围描述未更新**。
  判定要看有没有范围变更记录；没有的话，是 A，但根因是流程缺口。

## 二、矛盾扫描的六个触发信号

不用读全文去「感觉」矛盾。按信号扫，扫描更快也更全。

| 信号 | 扫描动作 |
|---|---|
| 同一术语出现多次 | 用关键词把全库该术语的卡捞出来横向对比 |
| 数值类卡密集 | 把所有 `kind: 数值` 按主题分组，同主题内两两比 |
| 出现「更新」「调整」「改为」「推迟」 | 这些词附近必有口径变化，重点核查前后是否同步了别处 |
| 出现「另行通知」「以最新为准」 | 这是**延迟矛盾**：文档自己承认存在未同步状态，必报 |
| 同一事实在不同权威等级出现 | 高等级与低等级说法不同，必报（哪怕看似是时点差异，也要人来判） |
| 标题含版本号（V2/V3/终版/定稿） | 按正文指纹判重，确认是替换还是并存 |

**扫描的执行顺序**：先扫「出现更新/调整/改为」和「以最新为准」这两类，
它们命中率最高；再扫数值类；最后扫术语一致性。

## 三、矛盾台账模板

一条矛盾一行，字段如下：

```markdown
### C-001 PC 端范围 vs 移动端排期

- **类型**：A 真冲突（已排除 B/C/D/E）
- **A 侧**：F-0002「首期仅交付 PC 端功能」— 方案/立项书.md §3（L1，2026-03-14）
- **B 侧**：F-0003「移动端排进 9 月这批迭代」— 纪要/2026-09-12 周会.md 议题二（L2，2026-09-12）
- **旁证**：F-0004 订单接口 `device_type` 含 ios/android（代码/接口说明.md，日期未标）
- **为什么是 A 不是 C**：两侧的差异不是「范围随时间自然扩大」，
  而是立项书从未被修订，也没有范围变更记录，属于同一范围描述在同一时点的两种口径
- **影响面**：排期、测试范围、接口兼容、对外承诺
- **优先核对**：项目负责人 → 范围口径；技术负责人 → 排期依据
- **核对渠道**：周会当面确认，确认后补一份范围变更记录并回写索引
- **状态**：待核
```

**A 侧 / B 侧的原文一定要照抄，不要转述。** 转述过的矛盾，看到的人无法判断真假，
最后还得回去核一遍，等于白做。

**「为什么是 A 不是 C」这一栏不能省。** 它是对本次判型的自证，
也是复核者最先看的地方。

## 四、缺口扫描：八类清单

缺口比矛盾更容易被漏掉，因为缺口没有「两句话打架」这种显眼信号。
只能靠逐个主题过清单。

### 4.1 时间缺口

- 资料时间跨度里有没有明显空档？（连续例会突然断了两个月）
- 有没有资料指向某个时间段的事件，但那个时间段的材料完全缺失？
- 有没有落款日期为「未标」但内容涉及关键决策的材料？

### 4.2 主题覆盖缺口

拿 `01` 的覆盖矩阵过一遍，逐个主题问：

```text
这个主题：有几份资料覆盖？等级最高的是哪份？
只有 L3/L4 覆盖的主题 → 高优先缺口（依据太弱）
零覆盖的主题 → 若与核心问题相关，直接进 P0
```

常见的零覆盖主题（按行业通用清单扫）：数据合规与隐私、成本与预算、验收标准、
异常与回滚预案、对外承诺与法务口径、依赖的第三方服务条款。

### 4.3 引用悬空缺口

资料里提到但没提供的对象：

- 「见附表 3」「详见附件」「参考 XX 方案」→ 附件在不在？
- 引用了某个会议、某份邮件、某个外部文档 → 有没有原件？
- 代码说明里提到某个设计文档 → 那个文档存在吗？

**处理**：悬空引用一律登记，不要替它猜内容。悬空引用是高价值缺口，
因为它说明资料本身有断链。

### 4.4 数值缺口

- 出现数字但没写单位、统计周期、数据来源
- 出现比例但没写分母
- 出现金额但没写含税/不含税、币种
- 出现「大幅」「显著」「成倍」却没有基数

### 4.5 归属缺口

- 决议没有责任人
- 有责任人但没有交付时间
- 有责任人和时间，但没有验收标准
- 出现「相关部门」「有关同事」这类模糊主体

**扫描方式**：把全部 `kind: 决议` 的卡捞出来，逐条问三件事——
谁、什么时候、怎么算完成。三缺一就是缺口。

### 4.6 前提假设缺口

- 方案里用了某个前提，但前提本身没有任何资料支撑
  （例：「假设用户会主动上传数据」「假设 Q3 有 5 个开发」）
- 依赖了某个外部条件，但没写条件不成立时的替代路径

### 4.7 过程缺口

- 有一个结论，但找不到产生这个结论的过程记录
- 有一个决策，但没有任何备选方案或对比
- 有一个版本变更，但没有变更原因

这一类和过程留痕直接相关：**结论有、过程无**，是资料体系里最常见的结构性缺口。

### 4.8 边界与例外缺口

- 只写了正常流程，没写失败/超时/冲突怎么办
- 只写了首期做法，没写后续演进路径
- 只写了适用对象，没写排除对象（谁不能用、什么情况不适用）

## 五、缺口台账模板

```markdown
### G-002 数据合规主题全库零覆盖

- **类型**：主题覆盖缺口
- **发现方式**：关键词检索「合规 / 隐私 / 授权 / 个人信息」，
  6 份资料、118 条事实卡中零命中；覆盖矩阵该行为空
- **为什么算缺口**：核心问题涉及用户数据采集，但没有任何一份材料给出授权与留存口径
- **影响面**：上线前的合规审查；数据留存策略；对外隐私声明
- **补料方向**：合规接口人的书面口径 / 法务出具的检查项 / 现行隐私声明
- **与追问的关系**：已转为 Q-004（缺口类）
- **状态**：待补料
```

缺口条目要写清 **发现方式**（查了什么、查了哪些范围、命中多少）。
不写发现方式的缺口，看起来和「我觉得应该有」没区别。

## 六、优先级与核对渠道

### 6.1 优先级

| 级别 | 判据 | 处置节奏 |
|---|---|---|
| P0 | 影响已发出的对外承诺、上线时间、合规、金额 | 当天核，核完立刻回写索引 |
| P1 | 影响内部排期、测试范围、接口兼容 | 本周内，随下次例会一并确认 |
| P2 | 影响文档一致性、后续维护成本 | 迭代结束前批量修 |
| P3 | 措辞、格式、编号类不一致 | 顺手修，不进台账 |

**矛盾一律不低于 P1，缺口可到 P3。** 理由是矛盾会误导后来者做出错误决定，
而缺口的代价是「不确定」，不确定是可以暂时容忍的，误导不行。

### 6.2 核对渠道对照表

| 矛盾/缺口类型 | 首选核对对象 | 备注 |
|---|---|---|
| 范围口径 | 项目负责人 | 结果需落成一份带日期的书面记录 |
| 排期 | 技术负责人 | 顺便确认依赖的外部条件 |
| 数值口径 | 数据/财务接口人 | 必须同时拿到单位、周期、来源 |
| 接口行为 | 接口维护人 | 以代码与线上行为为准，不以文档为准 |
| 合规与授权 | 法务/合规接口人 | 不自行解释条款 |
| 归属与责任 | 上一级负责人 | 责任不清时不要找当事人自己定 |
| 历史决策原因 | 当时的与会者 | 找不到人就在台账里记为「原因不可考」 |

**「原因不可考」是一个合法结论。** 硬要给历史决策编一个理由，
比承认不知道危害大得多——它会把一个虚构的动机写进后续所有判断里。

## 七、扫完之后的收尾动作

1. **矛盾汇总成一张表**，按 P0→P3 排，一页能看完
2. **缺口汇总成一张表**，按「补料成本」再排一次（容易补的放前面）
3. **把与核心问题直接相关的条目转成问题卡**（见 `references/02`）
4. **回写索引**：裁决结果、补料结果都新增事实卡，原卡标记失效而不删除
5. **留一份扫描记录**：扫了哪些信号、用了哪些关键词、命中多少条

这一步最容易被省，但它是下一次追问的起点——
三个月后再做一次，用同一份关键词扫，差集就是这期间新增的变化。

## 八、自检清单

输出台账前逐条打勾：

- [ ] 每条矛盾都明确判了型，并用「为什么不是 B/C/D/E」自证
- [ ] 每条矛盾的两侧都是**原文照抄**，不是转述
- [ ] 每条矛盾的「影响面」都已填写
- [ ] 每条矛盾都指定了核对对象与核对渠道
- [ ] **没有对任何一条矛盾自行下结论**
- [ ] 八类缺口逐类扫过，扫过的关键词与范围有记录
- [ ] 缺口台账里，资料没说（缺失）与资料说了没做（未落实）分开记
- [ ] 「原因不可考」这类结论已如实记录，没有编造动机
- [ ] 矛盾与缺口没有混在同一张表里
- [ ] P0 条目已单独列出并说明了为什么是 P0
- [ ] 扫描记录已留档，下次可用同一关键词重扫做差集
