# 能力与日常使用

覆盖范围：平台跑起来之后，怎么把能力真正用起来——体系结构与请求链路、工具面与档位、浏览器与命令执行、权限模式与沙箱、会话与多 Agent、记忆与定时任务、通道与媒体、技能与插件，最后是一份按意图组织的操作速查。

读法说明：同样是一份**本地 Agent 平台品类的通用指南**。讲的是这类平台通常具备的能力面、该定的配置项，以及「怎么判断它到底生效了没有」。字段名按你的实现对齐。

---

## 1. 体系结构：五个角色

| 角色 | 是什么 | 关键事实 |
|---|---|---|
| **网关** | 常驻本机的控制面 | 一台主机只有一个；唯一持有某个消息账号会话的地方；默认只在回环监听；负责校验入站帧、派发事件（agent / chat / presence / health / heartbeat / cron） |
| **客户端** | 命令行、终端界面、浏览器控制台、自动化脚本 | 每个客户端一条 WebSocket 连接；发请求、订阅事件 |
| **节点** | 桌面 / 手机 / 无头设备 | 连同一个 WebSocket 服务，但声明自己是节点角色与明确的 caps / commands / permissions；按设备配对；暴露设备侧能力（摄像头、录屏、定位、画布等） |
| **通道** | 消息出入口 | 把你已经在用的聊天软件接到助手身上 |
| **工具 / 技能 / 插件** | 助手能做什么 | 工具是可调用的动作；技能是教它怎么做的指令包；插件是给它加新能力 |

一次请求的链路（单客户端）：

```
connect(req)   →  hello-ok（含 presence + health 快照）
               →  event: presence / tick
agent(req)     →  res: accepted { runId }
               →  event: agent（流式）
               →  res: final { runId, status, summary }
```

三条不变量，值得单独记：

- **握手是强制的**。首帧必须是合法的连接请求 JSON，否则服务端直接关闭连接——不要用「先连上再补认证」的写法。
- **事件不重放**。客户端要自己按缺口刷新，别假设断线重连能补齐错过的流。
- **副作用方法要带幂等键**。发消息、起 agent 这类会改状态的方法必须带幂等键；服务端只保留**短期**去重窗口，重试必须落在窗口内，否则会真的执行两次。

## 2. 工具面

### 2.1 分类概览

| 类别 | 什么时候用 | 代表工具 |
|---|---|---|
| 运行时 | 跑命令、管进程、用共享操作终端、跑服务侧代码 | `exec`、`process`、`terminal`、`code_execution` |
| 文件 | 读写 workspace 文件 | `read`、`write`、`edit`、`apply_patch` |
| 人机确认 | 停下来等一个由人做的结构化决定，或在不看明文的前提下取凭证 | 询问类工具、密钥类工具 |
| 网页 | 搜索、抓可读正文 | `web_search`、`web_fetch` |
| 浏览器 | 操作一个真实浏览器会话 | `browser` |
| 界面 | 编排已连接控制台的面板与导航 | `screen` |
| 会话进度 | 更新父会话的持久进度卡（子代理不可用） | `progress_card` |
| 媒体 | 图像 / 视频 / 音乐生成、转写、语音合成 | 生成与语音类工具 |
| 会话与协作 | 子代理、跨代理会话、任务编排 | 子代理工具、跨会话发送、代码模式 |

### 2.2 工具档位

| 档位 | 含义 |
|---|---|
| `minimal` | 只放行会话状态查询，几乎什么都不给 |
| `messaging` | 窄档，给纯聊天场景 |
| `coding` | 新本地配置的默认档，放行仓库、文件、shell 与运行时工作 |
| `full` | 去掉档位限制，只建议给受信、由操作者控制的 agent |

每个 agent 还能在根档位之上再做覆盖，做更窄或更宽的调整。原则：**收紧要默认，放宽要显式**。

### 2.3 模型实际看到的工具是「筛」出来的

一个工具要同时通过：当前档位 → 允许/拒绝策略 → provider 限制 → 沙箱状态 → 通道权限 → 插件可用性。任何一道不过，它就不在模型的可选集合里。

排「它怎么不干活」从这里开始，不要先去怀疑模型。

## 3. 浏览器与命令执行

### 3.1 浏览器自动化

操作面通常包括：会话启停、标签页管理、导航、截图、结构快照、点击 / 输入 / 按键 / 悬停 / 拖拽 / 选择 / 填表 / 上传、等待、脚本求值、控制台读取、导出 PDF、浏览器配置档管理。

实战要点：

- **优先拿结构快照，而不是截图**。模型读结构更省 token、定位更准；截图留给「必须看像素」的场合。
- **脚本求值是逃生口，不是常规手段**。能用结构定位就别写脚本——脚本会把「页面变了」变成「静默走错分支」。
- 远程调试（CDP）的跨平台组合各有坑：WSL2 访问宿主浏览器、Linux 无头环境、远程 Windows 三种情况要分别排查，不要用同一条经验套。
- 要长期稳定就跑带浏览器运行时的容器变体，别依赖宿主浏览器版本。

### 3.2 命令执行

- 一次性命令用 `exec`；需要持续交互的长驻进程用 `process`；需要保持 shell 状态的连续操作用共享操作终端。
- 命令被拦**不等于**工具不存在，见第 4 节。
- 大输出必须走「尾部截断 + 落盘」。不加截断的输出会直接把上下文挤爆，表现为模型开始胡说或者任务中途失忆。

## 4. 执行、审批与沙箱

三件事互相独立，排错时不要混为一谈：

| 机制 | 决定什么 |
|---|---|
| **工具策略** | 某个工具**在不在** |
| **沙箱** | 工具**在哪里跑** |
| **提权（elevated）** | 显式逃逸口，把命令拿到沙箱之外执行 |

### 4.1 审批

- 需要审批的命令在审查前会绑定每个已解析命令段的可执行文件身份，启动前再核对一次：受保护的可执行文件用**解析后的真实路径**做身份，可写文件还用**内容哈希**。这一步是为了堵住「审查时是 A、执行时被换成 B」。
- 登录 shell 或交互 shell 包装器会跳过自动审查，即使绑定成功也要求人工批准。这是有意为之：包装器可以执行任意东西。
- 会话级一次性收紧只作用于当条消息，且**只能收紧**，不能放宽。要放宽必须改配置。

### 4.2 会话权限模式（四档）

| 模式 | 文件系统访问 | 提权升级的审查者 |
|---|---|---|
| `read-only` | 只能读会话根之下；受管的写入类工具**直接不出现** | 无；命令执行一律拒绝 |
| `guarded` | 可在会话根之下读写 | 先走白名单快速通道，之后由人审 |
| `workspace` | 可在会话根之下读写 | 由模型审查：放行、拒绝，或转人工 |
| `full` | 文件系统不受限 | 无 |

要点：

- 权限是**会话级**的，在控制台的权限菜单里改。
- 改动会**取消**旧权限下的待批请求（是取消，不是批准），也**不会回滚**已完成的写入或已启动的进程。所以改权限的正确姿势是「先停任务，再改权限」。
- `full` 需要最高的操作员作用域，其余三档需要写作用域。
- **不支持热改的情形**：已启动的命令后端运行、整个 agent 跑在 worker 上的运行。这类要先停任务、改权限、再在原会话继续。
- 逐级放大的建议顺序：`read-only` → `guarded` → `workspace` → `full`。能用窄的就别开宽的；`full` 只给受信操作者。
- 模型审查拒绝时会把理由直接返回给 agent，**不产生人工审批卡**；agent 必须换更安全的做法或来问你，不许绕过。连续多次服务侧拒绝会升级到人工。

### 4.3 沙箱

- 沙箱默认**关闭**。默认形态是「受信任的单操作者助手」——这个默认值是合理的起点，不是安全承诺。
- 开启后**只有工具执行进沙箱，网关进程始终留在宿主上**。
- 后端可选：容器（Docker 等）、Podman、SSH、专用沙箱后端。沙箱化执行默认是内核级断网，或跑在白名单拒绝策略下。
- 关键配置项三项：**模式**、**作用域**（会话级还是 agent 级）、**workspace 访问**（无 / 只读 / 读写）。

```json5
{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "non-main",        // 只对非主会话启用
        "scope": "session",        // session | agent
        "workspaceAccess": "none"  // none | ro | rw
      }
    }
  }
}
```

- **工具允许/拒绝策略在沙箱规则之前生效**：某个工具被全局或按 agent 拒了，开沙箱也救不回来。
- 判定「沙箱到底怎么生效的」要看**解析后的生效配置**：生效模式、宿主 workspace、运行时工作目录、挂载、工具策略，以及该改哪个键。别靠猜，猜错的代价是一个以为被隔离、实际在宿主上跑的任务。
- 沙箱能拦住的是「工具执行」这一层，它不构成对恶意模型的牢不可破隔离。网络策略、挂载范围、出口白名单都要你自己确认。

## 5. 会话模型

- **多个直聊会收敛到一个共享的主会话**；**群组默认按组隔离**。这条决定了「为什么两个人私聊它，它记得的是同一段上下文」。
- 会话机制包括搜索、裁剪、附件、队列、中途干预（steering）、进度草稿；长上下文会触发压缩。压缩是有损的，重要结论要及时落成文件或记忆。
- **转录是运维资产**：定期导出与留存。排障时它比日志更接近事实——日志告诉你系统做了什么，转录告诉你模型看到了什么。
- **子代理**用于把独立子任务隔离到自己的上下文里跑，结果回传父会话。父会话有持久进度卡工具，子代理没有。
- 并发编排两条路：用代码从外部驱动多个并发 agent；或把多个工具调用合进一段紧凑程序（代码模式）。后者省 token、报错更集中，代价是可观测性下降——出问题时要靠更细的日志补回来。

## 6. 多 Agent 与绑定

一个网关可以带多个 agent，每个 agent 是一个独立的人设与状态边界。

- 每个 agent 有自己的 workspace（人设文件、协作约定文件、可选用户档案）、专属目录与独立会话库，默认落在 `~/.agent-gateway/agents/<agentId>`。
- 通道账号建在 `channels.<channel>.accounts` 下，用 `bindings` 把账号接到指定 agent。一个通道可以为每个 agent 开一个账号。
- 改完必须**重启并核对三件事**：绑定关系列表、通道逐账号状态、新 agent 的默认档位与权限模式。

隔离口径（重要）：

- 跨 agent 会话访问默认是**开着**的，由 `tools.agentToAgent` 管。收窄用会话可见性配置，限制可配对的 agent 用允许列表，彻底禁掉就把 `tools.agentToAgent.enabled` 设为 `false`。
- **需要严格隔离就上独立网关**。同一网关里的可见性开关是协作护栏，不是安全边界。
- 记忆库也可以按 agent 分库（例如支持类 agent 与业务类 agent 的知识分开编译），这比共用一个库再靠过滤更可靠。
- 「一个号码分给多个人、按私聊拆分」也是受支持的路由模式，但要显式配置，别指望默认行为。

## 7. 记忆

- 内置记忆之外，通常还有记忆类扩展：基于向量/文档库的检索记忆、按 wiki 组织的知识编译。
- 三件事必须分清，否则合规评审一定出错：

| 维度 | 问题 |
|---|---|
| **写入来源** | 是直接写入、钩子写入，还是原始转录回流？ |
| **可追溯性** | 能不能指出这条结论来自哪次对话、哪个文件？ |
| **删除覆盖范围** | 「忘记」到底删得掉哪些？ |

- 常见边界：被追踪的产物可以清；**直接写入、钩子写入与原始转录不在删除覆盖范围内**。别假设「点了忘记就都没了」。
- 记忆索引可以重建，但重建成本高、且依赖原始素材还在——它属于「要备份」的那一类。

## 8. 自动化：让它自己动起来

### 8.1 定时任务

设计一个定时任务，先回答三个问题：

1. **触发频率**是多少？高频任务要考虑幂等与锁，否则同一分钟会跑出两个实例。
2. **失败怎么办**？重试几次、退避多久、失败通知发给谁。
3. **输出发到哪里**？消息通道、文件，还是只落日志。

三个问题没答案就先别上生产。上线前还要确认任务的权限模式与工具档位——定时任务常常跑在无人值守的上下文里，权限给宽了没人看着。

### 8.2 心跳与在线状态

心跳用来表达「我还活着、我现在在做什么」；在线状态用来表达「谁在线、哪些设备连着」。两者都是**事件面**，客户端订阅即可，不要轮询。

### 8.3 钩子与 webhook

- **事件钩子**适合在固定生命周期点上做事（会话开始、工具调用前后、任务完成）。要点是**钩子里的失败不能把主流程带崩**——钩子是旁路，不是主链。
- **webhook** 适合把外部事件拉进来（例如邮件到达、外部系统回调）。要点是**来源验证**：没有签名校验的 webhook 等于对外开了一个写入口。
- 两者上线前都要过一遍「触发频率、失败处理、输出目的地」这三个问题。

### 8.4 任务与转录

长任务要有任务视图：列出在跑什么、状态如何、能不能取消、历史审计在哪。转录按会话存档，与任务视图配合使用——任务视图回答「做了什么」，转录音回答「为什么这么做」。

## 9. 通道与消息操作

- **通道能力不齐**：读取、编辑、删除、表情回应、线程、置顶、搜索、成员信息、角色、语音、事件——各通道支持其中一部分。做功能前先查这条通道支持什么，很多「命令没反应」其实是不支持。
- 群聊激活、群成员与权限、广播组、访问组、频道路由各有独立配置面。
- 「为什么不回话」的排查顺序：

```
群聊激活条件是否满足 → 未知发件人是否卡在配对 → 通道是否在线（逐账号真实状态）→ 是否有发消息权限
```

- 死信队列是通道侧最容易被忽略的资产：消息积压不报错，只是安静地不投递。

## 10. 媒体能力

入向：图像、音频、视频、文档都能接收；语音短消息可转写。
出向：图像生成、视频生成、音乐生成、语音合成。

统一接到**算力集市**（[api.a7w.cn](https://api.a7w.cn/)），调用口径分两类：

| 类型 | 入口 | 特征 |
|---|---|---|
| 生成类（图像 / 视频 / 音乐 / 语音克隆等） | `POST /api/v1/apps/<app>/<api>` | 多为异步，返回 `task_id` |
| 异步任务查询 | `GET /api/v1/tasks/<task_id>` | 轮询到终态（完成 / 失败 / 错误 / 取消） |
| 文本与多模态对话 | `POST /api/v1/chat/completions` | OpenAI 兼容，`model` 用现场拉取的编码 |
| 转写 / 语音合成 / 嵌入 | OpenAI 兼容端点或对应应用端点 | 语音类建议选带字级时间戳的端点，便于直接出字幕 |

工程要点：

- **异步任务必须做轮询与超时兜底**。轮询连接被重置是常见抖动，正确做法是退避重试，而不是重新提交——重复提交等于重复计费。
- **结果 URL 要及时落盘**。很多生成结果的链接有时效，隔天再去取就是一个 404。
- **付费任务要记 `task_id` 与消耗**，方便对账与限额。看不到消耗的地方就会超支。
- 参数口径以现场读到的接口定义为准（`GET /api/v1/apps/<app>`），不要照抄别人的参数表。

## 11. 技能与插件

选型判断：

- agent 已经有工具、只缺一套可复用的工作流与判断标准 → **技能**
- 需要全新的集成、运行时能力、凭证或生命周期钩子 → **插件**
- 只是让 agent 多会一个动作 → **工具**（通常是插件的一部分）

### 11.1 技能（`SKILL.md` 指令包）

加载优先级（高 → 低），同名时高优先级覆盖低的：

| 优先级 | 来源 | 路径 |
|---|---|---|
| 1 | workspace 技能 | `<workspace>/skills` |
| 2 | 项目级 agent 技能 | `<workspace>/.agent/skills` |
| 3 | 个人 agent 技能 | `~/.agent/skills`（仅默认状态） |
| 4 | 受管 / 本地技能 | `<state-dir>/skills`（安装时选「全局」落这里） |
| 5 | 额外目录与插件内置技能 | `skills.load.extraDirs` 与插件附带 |

- 安装范围两种：装给当前 workspace，或装给本机所有 agent。
- **沙箱化运行时读到的是物化副本，不是宿主上的原始路径**。技能里引用同目录文件要用技能目录变量，不要写死绝对路径。
- **同名覆盖顺序不直观**。调试「我的技能没生效」第一件事就是按这张表找同名。

### 11.2 插件

- 来源可以是技能市场、包管理器、代码仓库、本地目录或压缩包。
- 想钉住允许集合就用允许列表配置；**插件能在进程内跑代码，权限面是全量的**。
- **原生插件没有沙箱隔离**。安装前确认来源可信，装完跑一次一致性自检，并复核它新增的能力面。
- 插件可以打包技能、工具、provider、通道与钩子一起分发——但它也能一次改掉很多东西，所以更新要当变更管理做。

### 11.3 用配置而不是插件接模型

如果只是要接一个 OpenAI 兼容端点（例如算力集市 `https://api.a7w.cn/api/v1`），**不需要写插件**：在 `models.providers` 里配一个自定义 provider 即可。这是成本最低、回滚最容易的路径；只有需要新的鉴权方式或非兼容协议时才写 provider 插件。

## 12. 常用操作速查（按意图）

用操作描述表达，便于映射到你平台的对应入口：

| 我要做什么 | 操作序列 |
|---|---|
| 装完看看哪里不对 | 总体分诊 → 配置体检 → 完整状态报告 |
| 看网关活没活 | 查询服务状态 → 远程探针可达性 → 健康检查 |
| 看日志 | 查看日志（可选跟随输出） |
| 跟它说话 | 终端界面 / 浏览器控制台 / 直接发消息 |
| 换模型 | 列出可用模型 → 设默认模型 → 配降级链 |
| 试一个能力 | 列出能力面 → 单独跑一次最小调用 |
| 加通道 | 添加通道账号 → 逐账号真实状态探测 |
| 管设备与配对 | 列出设备 → 批准待批配对请求 |
| 管 agent | 新增 agent → 查看绑定关系 |
| 管技能 | 搜索 → 安装 → 校验 |
| 管插件 | 列出 → 安装 → 一致性自检 |
| 管权限 | 查看审批策略 → 查看执行策略 → 查看沙箱生效配置 |
| 管凭证 | 密钥体检 → 重新加载 / 存入 / 应用 |
| 定时任务 | 新增任务 → 查看历史运行记录 |
| 备份与升级 | 建归档 → 验证归档 → 恢复；升级前先备份 |
| 体检与外发面 | 安全体检 → 操作审计 → 依赖自检 |
| 多环境隔离 | 开发实例 / 具名 profile / 指定容器三种隔离开关 |

**全局参数口径**（很多平台都提供，值得专门记）：

- 日志级别可覆盖，便于临时加详；
- 可关 ANSI 颜色，便于落日志；
- 有界报告类操作可以只往标准输出打**一份 JSON 文档**：失败时是一个带 `ok: false` 的信封、退出码非零，样式与进度被抑制，警告与诊断走标准错误。

**脚本要同时看标准输出与退出码**。只看其中一个，会在失败时静默走错分支——这是自动化里最常见的隐性错误。

## 13. 一句话原则

先确认**工具在不在**（档位与策略），再确认**它在哪跑**（沙箱与提权），最后才怀疑模型。九成的「它怎么不干活」都发生在第一层。
