# 平台落地与配置

覆盖范围：把一套本地 Agent 平台从「能跑起来」推到「可长期运维」——部署形态选型、目录与端口规划、服务化常驻、配置与环境变量优先级、模型 provider 接入与 Key 轮换、消息通道与配对、远程接入、备份与升级策略、验收口径。

读法说明：这是一份**本地 Agent 平台 / 本地 AI Agent 网关品类的通用落地指南**。它讲的是一个这样的平台通常需要哪些能力面、该定哪些配置项、每项的默认口径与判断依据。你的实现字段名可以不同，按语义对齐即可。

---

## 1. 先把平台拆成四层

| 层 | 职责 | 「这一层健不健康」的判断依据 |
|---|---|---|
| 控制面（网关） | 常驻本机、单实例，持有会话与通道连接，对外暴露类型化接口 | 绑定端口在监听；远程探针可达；只有一个实例持有账号会话 |
| 运行时 | 工具执行、命令与浏览器子进程、沙箱后端 | 工具能被调用；沙箱容器状态与镜像匹配；执行策略是你预期的那个 |
| 通道接入 | 消息平台账号，路由到指定 agent | **逐账号的真实传输状态**，而不是配置摘要 |
| 客户端 | 命令行、终端界面、浏览器控制台、桌面伴侣、手机/无头节点 | 首帧握手通过；设备配对已批准；订阅到了事件 |

三条设计不变量，后面多处会用到：

- **控制面单实例**：同一台主机、同一个消息账号，只能由一个网关进程持有其会话。第二个实例会抢锁或直接拒启——这不是 bug，是防止消息被两个进程分叉处理。
- **默认只绑回环**：监听地址默认 `127.0.0.1`，端口自选一个专用高位端口。端口本身没有魔力，**全平台统一登记**比选哪个更重要。
- **首次连接必须先握手**：WebSocket 首帧必须是带身份的连接请求帧，设备身份需要配对批准；先连上再补认证的写法会被直接断开。

## 2. 部署形态怎么选

| 你的约束 | 建议形态 | 判断依据 |
|---|---|---|
| 单人单机、想最快稳定 | 原生常驻进程 + 系统服务托管 | 依赖最少，出问题时最容易看见 |
| 不想在宿主留任何东西、要能整块丢弃 | 容器化网关（状态全落挂载卷） | 镜像可整块替换，回滚等于换镜像 |
| 团队共用、要审计 | 一台专用主机上的单网关 + 每 agent 独立 workspace | 一个网关就是一个信任域，边界清晰 |
| 内网隔离 / 无外网 | 先在可出网环境拉全镜像与依赖，再离线导入；模型走内网可达的 OpenAI 兼容端点 | 离线部署的失败几乎都发生在「少拉了一个东西」 |

三条取舍原则：

- **信任域按「一个网关」划，不按「一个 agent」划**。同一网关里的可见性开关是协作护栏，不是隔离机制；多人多租户要一租户一网关。
- **沙箱与容器化是两件事**。工具执行是否进沙箱，与你是否把网关本身跑在容器里无关。两个开关，分别决策。
- **进程要可丢弃，状态要可备份**。凡是把状态写在容器可写层或临时目录里的部署，都是不可运维的部署。

## 3. 目录与端口规划

### 3.1 状态目录布局

推荐一个集中的状态根（下文以 `~/.agent-gateway` 为示例；Windows 下为 `%USERPROFILE%\.agent-gateway`）：

| 内容 | 路径 | 是否必须备份 |
|---|---|---|
| 主配置 | `~/.agent-gateway/config.json` | 是（不含明文密钥时） |
| 网关分片配置 | `~/.agent-gateway/gateway.json` | 是 |
| 各 agent 目录（人设、专属配置、独立会话库） | `~/.agent-gateway/agents/<agentId>` | 是 |
| workspace（工作文件、技能） | `~/agent-workspaces/<agentId>`（可另选盘位） | 视内容而定 |
| 会话库与转录 | `~/.agent-gateway/sessions`、`~/.agent-gateway/transcripts` | 是 |
| 记忆索引 | `~/.agent-gateway/memory` | 是（可重建，但重建成本高） |
| 凭证与认证资料 | `~/.agent-gateway/secrets` | 是，且单独收紧权限 |
| 日志 | `~/.agent-gateway/logs` | 否，但要留保留窗口 |
| 备份归档 | `~/.agent-gateway/backups` | 归档必须另拷一份 |
| 环境变量文件 | `~/.agent-gateway/.env` | 是 |

规划要点：

- **workspace 与状态目录分开**。workspace 会长得很大（附件、产物），状态目录要小而可备份。把两者塞进同一个目录，最后就是「备份太慢所以不备」。
- Windows 上避开长路径与网盘同步目录。数据库文件被同步客户端抢占会造成锁冲突，表现为随机启动失败。
- 多实例隔离用**并列根目录**（例如具名 profile 落到 `~/.agent-gateway-<name>`），不要靠手改子路径来隔离——手改的路径会被后续操作按规范路径覆盖。

### 3.2 端口规划

一个网关通常只对外暴露**一个** HTTP + WebSocket 端口，其余管理面挂在同一端口的路径下。

| 用途 | 示例端口 | 绑定 | 说明 |
|---|---|---|---|
| 网关主端口（HTTP + WebSocket） | 8787 | 127.0.0.1 | 唯一必须记住的端口 |
| 托管控制台静态资源 | 同主端口路径 | 127.0.0.1 | 不额外开端口 |
| 沙箱内工具执行 | 动态 | 容器内网 | 不进宿主监听表 |
| 指标与可观测导出 | 8790 | 回环或内网 | 导出面单独授权 |
| 开发 / 演练实例 | 8788 | 127.0.0.1 | 与生产实例的状态目录、端口都错开 |

规则：

- 端口号本身随意，**登记表必须有**。排障时「这台机器上到底该开哪个端口」不一致，是最低级的耗时项。
- 绑定地址是安全边界的第一个开关。改绑定范围之前先跑一次安全体检。
- 只绑回环时不需要额外 TLS；一旦跨主机，协议与鉴权沿用同一套，并对 WebSocket 开 TLS。

## 4. 服务化常驻

前台运行只适合调试：终端一关就停，退出码也留不下来。要长期可用必须托管给系统服务。

| 平台 | 托管方式 | 注意事项 |
|---|---|---|
| macOS | 用户级 LaunchAgent；无人登录也要跑则用守护进程 | 用户级 agent 依赖登录会话 |
| Linux / WSL2 | systemd 用户单元（`systemctl --user`） | 要在无人登录时运行，需启用 lingering |
| 原生 Windows | 登录时触发的计划任务，或服务包装器 | 计划任务被策略拒绝时回退到「启动」文件夹登录项，**要核对回退是否真的生效** |

服务化是否成功的判断口径：

- 重启机器后，不需要人工登录就自动起来；
- 进程崩溃能被托管器拉起，或至少留下可查的退出码与日志；
- 服务账户对状态目录与 workspace 有读写权限，且与交互式账户看到的是同一份状态；
- **服务环境不加载你的 shell profile**。手工运行能用、服务化后失效，九成是这个原因——环境变量必须显式写进服务定义或 `.env`。

## 5. 配置文件与环境变量

### 5.1 优先级

从高到低：

```
进程环境变量 → ./.env → ~/.agent-gateway/.env → config.json 的 env 块 → 配置内联默认值
```

两条实操结论：

- 已存在的非空进程环境变量不会被 `.env` 覆盖。要改生效值就改**最早的那一层**，改最后一层只会白忙。
- 直接写进配置的凭证类字段（网关 token、通道 token）通常走单独的解析路径，优先级高于环境变量兜底值。改完先确认生效的是哪一层，再动手查别的。

### 5.2 常用环境变量

| 变量 | 作用 |
|---|---|
| `AGENT_GATEWAY_HOME` | 内部路径解析用的根 |
| `AGENT_GATEWAY_STATE_DIR` | 覆盖状态目录 |
| `AGENT_GATEWAY_CONFIG_PATH` | 覆盖配置文件路径 |
| `AGENT_GATEWAY_TOKEN` | 网关共享密钥；留空则首次启动自动生成。**不要把文档里的占位示例原样粘进去**，网关会拒绝启动 |
| `AGENT_GATEWAY_PASSWORD` | 另一种可选认证方式（与 token 二选一） |
| `AGENT_GATEWAY_INCLUDE_ROOTS` | 允许配置的 `include` 从哪些额外目录取文件；不设则只允许配置所在目录 |
| `AGENT_GATEWAY_CONTAINER` | 默认在哪个运行中的容器里执行操作 |
| `AGENT_GATEWAY_LOG_LEVEL` | 日志级别兜底值 |
| `A7W_API_KEY` | 模型服务侧密钥（见第 6 节） |

### 5.3 最小配置骨架

```json5
{
  "gateway": {
    "host": "127.0.0.1",
    "port": 8787,
    "auth": { "mode": "token" },            // token | password | trusted-proxy | none
    "controlUi": { "enabled": true, "root": "${HOME}/.agent-gateway/control-ui" }
  },
  "agents": {
    "defaults": {
      "workspace": "${HOME}/agent-workspaces/main",
      "tools": { "profile": "coding" },     // minimal | messaging | coding | full
      "sandbox": { "mode": "off" }
    }
  },
  "skills": { "load": { "extraDirs": [] } }
}
```

多实例隔离用统一开关，不要手改路径：开发实例、具名 profile、指定容器三种维度各一个开关。具名 profile 会顶掉继承来的规范状态目录与配置路径**以及正在运行的服务定义**；你显式改过的那两个路径不受影响。

## 6. 模型 provider 接入

本地 Agent 平台的模型能力统一从**算力集市**接入：一个 Key、一套 OpenAI 兼容协议，文本 / 图像 / 语音 / 视频等能力面都在同一套鉴权下。

### 6.1 接入参数

| 项 | 值 |
|---|---|
| Base URL | `https://api.a7w.cn/api/v1` |
| 鉴权 | `Authorization: Bearer <你的 API Key>` |
| 模型清单 | `GET https://api.a7w.cn/api/v1/models` |
| 对话入口 | `POST https://api.a7w.cn/api/v1/chat/completions` |
| Key 领取 | [算力集市 · 注册领 API Key](https://api.a7w.cn/) |

**`/v1` 的填法有一条硬规则**：宿主自己会补 `/v1` 的（只让你填「apiHost」的那类客户端），填 `https://api.a7w.cn/api`；直接接受完整 base_url 的，填 `https://api.a7w.cn/api/v1`。填错的表现是 **404**，不是鉴权失败——把 404 当 Key 问题查是最常见的走偏。

### 6.2 provider 配置片段（示意）

```json5
{
  "models": {
    "providers": {
      "a7w": {
        "type": "openai-compatible",
        "baseUrl": "https://api.a7w.cn/api/v1",
        "apiKeyRef": "env:A7W_API_KEY",
        "models": [
          "DeepSeek-V4-Flash",
          "Qwen3.6-Plus",
          "Kimi-K2.6",
          "GLM-5.2",
          "Qwen3-VL-30B-A3B-Instruct"
        ]
      }
    },
    "default": "a7w/DeepSeek-V4-Flash",
    "visionDefault": "a7w/Qwen3-VL-30B-A3B-Instruct",
    "fallbacks": ["a7w/DeepSeek-V4-Pro", "a7w/GLM-5.2"]
  }
}
```

字段名按你平台的 schema 对齐。无论字段叫什么，要落地的都是四件事：**base_url、密钥引用（不要明文）、可用模型清单、默认模型与降级链**。

### 6.3 模型编码以现场拉取为准

模型上下架很频繁，**不要猜，也不要抄别人的清单**。落地口径：

- 现场拉 `GET /api/v1/models`，取其中的模型编码字段（例如 `model_code`）作为请求里的 `model` 值，**逐字一致、大小写敏感**；
- 常见可用编码举例：`DeepSeek-V4-Flash`、`DeepSeek-V4-Pro`、`Qwen3.6-Plus`、`Kimi-K2.6`、`GLM-5.2`，读图用 `Qwen3-VL-30B-A3B-Instruct`；
- 响应里的 `model` 字段可能被规范化成小写，**别拿它做精确匹配**。

按任务选型，不按名气选型：

| 场景 | 建议 |
|---|---|
| 日常问答、批量处理、Agent 多步调用 | `DeepSeek-V4-Flash` |
| 复杂推理、评审、定稿 | `DeepSeek-V4-Pro`、`GLM-5.2` |
| 长文档、长上下文 | `Kimi-K2.6` |
| 读图 / 多模态输入 | `Qwen3-VL-30B-A3B-Instruct` |

### 6.4 推理模型的参数口径

部分编码是推理模型：token 会先花在思维链上，再产出正文。表现是 `max_tokens` 给小了（例如 8）时 `content` 返回空、`finish_reason` 为 `length`。口径：

- Agent 类调用把 `max_tokens` 设到 256 以上；
- 思维链字段名在不同线路上可能叫 `reasoning` 或 `reasoning_content`，做流式解析时两个都要兼容。

### 6.5 验证与错误码

接入后必须用**一次真实补全**验证，而不是只看 Key 存不存在。

| 现象 | 判断 |
|---|---|
| HTTP 401 | Key 无效或过期——换 Key，不是换 base_url |
| HTTP 402 / 业务码 402 | 点数不足——到控制台充值后重试，不是模型不存在 |
| HTTP 404 | 大概率 base_url 多写或少写了一段 `/v1` |
| 连接重置 / 超时 | 长异步任务轮询会被网关重置连接，属正常抖动；客户端要退避重试（4xx 不重试，5xx 与网络类错误重试） |

### 6.6 生成类能力面的调用口径

图像、视频、音乐、语音合成这类能力走应用端点：`POST /api/v1/apps/<app>/<api>` 提交，返回 `task_id` 的即为异步任务；随后 `GET /api/v1/tasks/<task_id>` 轮询到终态（完成 / 失败 / 错误 / 取消）。接口与参数定义可以从 `GET /api/v1/apps/<app>` 现场读到。

接入要点：

- **提交成功不等于产出成功**。必须有轮询与超时兜底，否则失败会静默变成「没结果」。
- 付费任务在轮询抖动时**不要重复提交**——靠 `task_id` 续查，重复提交等于重复计费。
- 结果 URL 有时效，拿到就落盘。

## 7. Key 轮换与凭证管理

### 7.1 轮换的触发条件

轮换不是例行公事，是被事件触发的：401、402、429 持续出现、持续超时、Key 到期、人员变动。

### 7.2 多 Key 写法与语义

```
A7W_API_KEY=sk-primary
A7W_API_KEY_1=sk-a
A7W_API_KEY_2=sk-b
A7W_API_KEYS=sk-a,sk-b
```

语义要点：

- **增加一组认证不会改变默认模型**。认证决定「能不能调」，默认模型决定「用哪个」，这两件事分开配、分开查。
- 轮换顺序是可配的，且要**显式确认**——不要假设「配了就一定按你写的顺序用」。
- **Key 轮换与模型降级链是两回事，都要配**：前者应对单把 Key 不可用，后者应对单个模型不可用。

### 7.3 凭证存放口径

- 明文不入库、不进版本库、不写进脚本；用环境变量或密钥引用（`env:` / 系统钥匙串 / 受管密钥目录）。
- 状态目录里的凭证文件权限收到最小（POSIX `0600`，Windows 限当前用户）。
- 定期跑密钥体检：确认没有把 Key 写进配置、日志或会话转录。
- 备份归档里若含凭证，**归档本身要加密存放**。

## 8. 消息通道添加与配对

### 8.1 添加一条通道的判断顺序

1. 这条通道是核心自带，还是需要先装扩展？（决定前置动作）
2. 它要什么凭证：Bot Token、OAuth，还是扫码登录态？（决定后续过期怎么续）
3. 它支持哪些消息动作？（读 / 写 / 编辑 / 表情 / 线程 / 成员管理，各通道不同）
4. 接给哪个 agent？（bindings 路由，见 `references/capabilities-and-usage.md`）

### 8.2 账号与路由

通道账号建在 `channels.<channel>.accounts` 下，再用 `bindings` 把账号接到指定 agent。一个通道可以为每个 agent 开一个账号（一个 agent 一个机器人），这样权限、人设与配额互不干扰。

### 8.3 配对：把陌生人挡在外面

- 未知发件人默认需要配对：先进入待批列表，人工批准后才建立信任。
- 本地回环连接可以被自动批准；**局域网与 tailnet 上的连接（包括同一主机上的 tailnet 绑定）仍然需要显式批准**。
- 设备侧同样有完整生命周期：列出、批准、拒绝、轮换、吊销、移除、清空。
- 群聊默认靠 @ 提及激活；私聊另有白名单与配对两道控制。这两条是「它为什么不回话」的第一顺位原因。

### 8.4 通道健康判定

只看配置摘要会骗你。**逐账号的真实传输状态**才算数；通道不可达时会退回只读配置摘要，看起来「都正常」，其实什么都没连上。通道还要看死信队列——积压的消息处理完要显式重投。

## 9. 远程接入

优先级：**组网工具（如 Tailscale）/ VPN > SSH 隧道 > 直接暴露**。

### 9.1 两条推荐路径

- **组网工具**：把网关主机与你的设备放进同一个私有网络，绑定范围仍可保持回环或私有网段。带身份的模式可以从组网工具注入的请求头取认证。
- **SSH 隧道**：

  ```
  ssh -N -L 8787:127.0.0.1:8787 user@gateway-host
  ```

  隧道上沿用同一套握手与鉴权；远端场景可对 WebSocket 开 TLS 与可选证书固定。

### 9.2 鉴权模式

| 模式 | 取值来源 | 适用 |
|---|---|---|
| `token` | 共享密钥 | 默认推荐 |
| `password` | 共享口令 | 需要人记的场合 |
| `trusted-proxy` | 请求头身份（必须是非回环 + 可信代理前置） | 反向代理 |
| 身份型（组网工具身份） | 请求头 | 私有网络内 |
| `none` | 无 | **只允许私有入口**，等于关掉共享密钥认证 |

补充约束：

- 带身份的模式从**请求头**取认证，而不是从连接参数里的认证字段取。这两条路径容易混，混了就会表现为「明明配了却认证失败」。
- 所有连接都要对服务端下发的挑战 nonce 签名；签名负载的版本还会绑定平台与设备族。**跨版本客户端要一起升**，否则旧客户端连不上新服务端。
- 非本地连接一律需要显式批准。

### 9.3 暴露到公网之前

先跑安全体检，再想清楚三件事：谁能连上（绑定范围与鉴权）、连上能做什么（作用域）、出事看哪里（审计与日志）。默认只绑回环不是限制，是帮你把这个决策推后到真正需要的时候。

## 10. 备份与恢复

### 10.1 备份什么

- **必须**：配置、各 agent 目录、会话库与转录、记忆索引、凭证目录。
- **可选**：workspace 大文件、日志。
- **不要**：缓存与可重建的临时目录——备份它们只会让恢复变慢。

### 10.2 三条口径

- **备份要验证**。没有做过恢复演练的备份不算备份。
- **备份要异地**。归档只留本机，等于没备份。
- **状态库带 schema 版本**。恢复要经迁移流程，不要手工改库文件。

### 10.3 恢复顺序

停服务 → 恢复状态目录 → 跑依赖与配置自检 → 拉起服务 → 用一次真实对话验收。

恢复后**必须核对四项**：默认模型、通道账号、权限模式、绑定范围。这四项最容易被旧归档带回错误值，而且都不会报错，只会安静地用错。

## 11. 升级策略

升级的重点不是「怎么敲」，而是四件事：

| 项 | 口径 |
|---|---|
| 触发 | 有明确收益（安全修复、必需能力）才升；不追新 |
| 前置 | 先备份并**验证归档可用**；记录当前关键配置（模型、档位、权限模式、端口、绑定地址） |
| 灰度 | 先在非关键 agent 或演练实例上跑通，再整体切 |
| 回滚 | 回滚路径 = 恢复上一个归档 + 回到上一个版本。**回滚方案要在升级前写下来**，不是等出事再想 |

两类要特别留意：

- **配置 schema 变更**：新版本可能不再读取旧键（例如旧的会话级执行策略），要经自动修复/迁移流程处理；限制性策略在迁移时不会自动放宽，别指望它帮你兜底。
- **跨机器迁移**：用平台提供的迁移流程，不要直接拷状态目录。路径、凭证与平台相关字段要按新机器重建。

升级后自检：依赖与配置自检 → 网关在监听 → 通道逐账号可达 → 默认模型仍是你要的那个 → 发一句话拿到真实回复。

---

## 12. 装完的验收顺序

1. **依赖自检**：无阻塞性配置或服务错误。
2. **服务状态**：进程在跑、端口在监听、绑定地址是你预期的那个。
3. **探针可达**：远程探针返回可达。读作用域不足导致的「降级」不等于不可达，别误判。
4. **控制台可用**：能打开、能登录。
5. **通道逐账号探测**：要真实传输状态，不是配置摘要。
6. **发一句话，拿到真实回复**——这是唯一有意义的「装好了」。

任何一步不对，跳到 `references/extend-and-troubleshoot.md` 的四类故障排查阶梯。
