# 三剪客 · 自建 IM 服务端与消息中台

你要在自己的 App 或业务系统里长出"聊天"这个功能——单聊、群聊、离线消息、已读回执、多端同步——又不想从零写消息投递和会话管理。OpenIM 就是这层地基：一个纯后端的即时通讯服务端，配一套客户端 SDK 和一套 REST API，把"发消息"变成调接口。

**它不是一个能直接装来聊天的成品 App。** 它没有面向普通用户的成品聊天界面，你需要自己写客户端，或者用上游提供的示例前端；同时也正因为如此，它能塞进你自己的账号体系和业务流程里。它内部是微服务架构（网关 + 一组 RPC 服务），依赖 MongoDB、Redis、etcd、Kafka、MinIO 这一整套组件，所以"装起来"这件事本身就是一次中等规模的服务端部署。

**上游项目**：`OpenIM`　**仓库**：https://github.com/openimsdk/open-im-server

## 什么时候用 / 不用

**用它**：

- 自研 App / 小程序 / 内部系统要嵌一套即时通讯，需要单聊、群聊、会话列表、离线消息这类完整能力，而不只是一个 WebSocket 广播。
- 需要从服务端侧主动发消息：运营推送、订单通知、系统告警直接推到用户的会话里。
- 需要在发消息前后插入自己的业务逻辑（例如风控、审计、机器人回复），也就是要能挂回调钩子。
- 数据必须留在自己机房，不能走第三方 IM 云服务。
- 要按自己的用户体系做鉴权：用户 ID、令牌、群组关系都由你的后端发放和管理。

**不要用它**：

- 想给团队找一个开箱就能聊天的工具（像 Slack 那样的成品）——这不是它的定位。
- 只需要"服务端单向推一条通知给浏览器"——用 WebSocket / SSE 自建更简单，杀鸡不必用牛刀。
- 团队里没有能长期维护容器编排、数据库、消息队列的人——这套组件栈是它的成本项，不是它的赠品。
- 打算在低配机器上跑生产——组件数量摆在那里，资源不足会表现为各种奇怪的超时。
- 需要现成的音视频会议、文件协同编辑、办公套件——它只管消息与关系链路。

## 安装

**以官方文档与 `--help` 为准。** 官方给了源码、Docker、Kubernetes 三条路，下面写的是仓库里真实存在的入口。

### 方式一：Docker Compose（最容易复现）

```bash
git clone https://github.com/openimsdk/open-im-server.git
cd open-im-server

# 先按 .env 里的说明改好组件口令与端口等参数
# 再拉起全部容器
docker compose up -d

# 看状态
docker compose ps
```

`docker compose up -d` 会一并拉起 MongoDB、Redis、etcd、Kafka、MinIO 与前端容器。带 `m` profile 启动会额外拉起监控组件：

```bash
docker compose --profile m up -d
```

**组件口令必须对齐**：`.env` 里给的是容器组件的口令，`config/` 下各服务配置里给的是服务连接组件时用的口令，两边不一致会表现为"容器全在跑但服务连不上"。一键安装脚本里有一个专门按 `.env` 刷新两侧口令的步骤，Docker 手工部署时请自己核对。

### 方式二：一键安装脚本（脚本会自行下载最新发行包）

```bash
bash install.sh --help          # 先看全部可用参数
sudo bash install.sh -i         # 按默认参数安装
sudo bash install.sh -i -cn     # 走国内代理加速拉取
```

脚本支持的参数以 `install.sh --help` 输出为准，包括 `-u/--user`、`-p/--password`、`-e/--endpoint`、`-a/--api`、`-d/--directory`、`-t/--tag`、`-r/--release`、`-g/--go-version`、`--install-dir`、`--cpu`、`-gt/--github-token` 等。默认用户 `root`，默认口令与默认 endpoint 见脚本头部注释。

### 方式三：源码编译

```bash
bash bootstrap.sh        # 安装 mage 构建工具并下载依赖
make install V=1         # 编译并安装各服务二进制
make check               # 检查安装结果
```

源码方式需要 Go 环境、`make`、`jq` 等基础工具，且需要在 `config/` 下准备好各组件的连接配置。构建入口由仓库内的 magefile 定义，可用目标以你所用版本为准。

## 常用操作

以下端口与配置项均来自仓库 `config/` 下的默认配置文件，**具体以你部署版本的配置文件为准**。

```bash
# 1. 整体起停
docker compose up -d
docker compose down

# 2. 看日志（服务名以 docker compose ps 输出为准）
docker compose logs -f

# 3. 带监控组件启动
docker compose --profile m up -d

# 4. 源码方式：编译安装、启动、自检
make install V=1
make check
```

部署后默认的对外端口（取自仓库默认配置）：

| 用途 | 默认端口 | 来源 |
|---|---|---|
| API 服务（业务后端调它做用户/群组/消息管理） | `10002` | `config/openim-api.yml` |
| WebSocket 长连接（客户端连它收发消息） | `10001` | `config/openim-msggateway.yml` |
| 对象存储（图片/文件） | `10005` | `install.sh` 中的默认 endpoint |
| 示例前端页面 | `11001` | `docker-compose.yml` |
| MongoDB / Redis / etcd / Kafka 映射到宿主机的端口 | `37017` / `16379` / `12379` / `19094` | `docker-compose.yml` |

最小可用调用链示意（**接口路径与请求字段随版本变化，务必查你所用版本的官方接口文档，不要照抄**）：

```bash
# 1) 拿管理员令牌
curl -X POST http://127.0.0.1:10002/auth/get_admin_token \
  -H 'Content-Type: application/json' \
  -d '{"secret":"<配置中的管理员密钥>","userID":"<管理员用户ID>"}'

# 2) 带令牌调用业务接口（令牌放置位置以官方文档为准）
curl -X POST http://127.0.0.1:10002/user/get_users_info \
  -H 'Content-Type: application/json' \
  -H 'token: <上一步拿到的 token>' \
  -d '{"userIDs":["user1","user2"]}'
```

**挂业务回调**：编辑 `config/webhooks.yml`，把需要在事件前后回调的地址填进去，业务服务器即可在消息发送、群组变更等节点插入自己的逻辑（可挂的事件见该文件内的注释）。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 服务全在跑，但一个消息都发不出去 | Kafka 对外通告地址写成了 `localhost`，其他机器连不上 | 换成部署机的实际可达地址（对应 compose 文件里 `KAFKA_CFG_ADVERTISED_LISTENERS` 一类的设置） |
| 手机/其他机器上的 App 收不到图片 | `ENDPOINT` 还是 `127.0.0.1:10005`，只有本机能访问 | 改成设备能访问到的 IP 或域名，并确认对应端口已放行 |
| 容器都健康，服务日志报连不上 Mongo / Redis | `.env` 与 `config/` 两侧口令不一致 | 两边一起改；若组件数据卷已按旧口令初始化过，需要先停掉并清掉组件数据再重建 |
| `--profile m` 起监控直接报错 | 监控组件依赖 `config/prometheus.yml`、`config/alertmanager.yml` 等文件，缺失或路径不对 | 先确认 `config/` 下监控配置文件齐全且在位，再带 profile 启动 |
| 首次启动 MongoDB 相关组件反复重启 | MongoDB 需以单节点副本集方式初始化，初始化需要时间 | 等初始化完成再看状态；不要在半初始化状态下反复重启打乱流程 |
| 拉镜像极慢或超时 | 依赖的镜像来自海外仓库 | 用 `install.sh` 的国内代理参数，或按 `.env` 里的注释换用国内镜像源 |
| 改了宿主端口后某组件连不上 | 组件之间用容器内的服务名与容器内端口互通，宿主机端口只影响外部访问 | 不要为避让端口冲突去改容器内监听端口，优先改宿主机映射 |
| 挂载目录用相对路径，换目录启动后数据"丢了" | `DATA_DIR` 默认是 `./`，与启动位置绑定 | 显式指定绝对路径的大容量目录，并确认它保持不变 |
| 公网上线后被打 / 被刷 | 默认是便于开发的口令与配置，没有额外防护 | 上线前改掉全部默认口令、只暴露必要端口、在 API 前面加网关与限流 |

## 能力边界

**覆盖**：

- 即时通讯服务端的部署与运维：源码、Docker Compose、Kubernetes 三种方式，含组件依赖与端口规划。
- 服务端能力：用户管理、好友关系、群组管理、会话处理、消息收发与多端同步，面向大群与海量消息场景。
- 微服务形态：网关加一组 RPC 服务，支持集群模式。
- 与业务系统集成：REST API 由业务后端调用，Webhook 在事件前后回调业务服务器。
- 客户端接入：面向各平台的 SDK（含 Go SDK 与多语言 gRPC 绑定）、WebSocket 长连接协议。
- 生产向考量：监控组件、对象存储接入与各服务的连接配置。

**不覆盖**：

- 不提供开箱即用的成品聊天 App；界面要么用示例前端，要么自己开发。
- 不替代你的账号体系：用户注册、登录、令牌签发仍由你的业务后端决定。
- 不负责部署环境本身（服务器采购、域名备案、TLS 证书申请）。
- 不做内容审核策略的实现，只提供挂钩子的位置。
- 不包含音视频会议、文档协同、办公审批这类协作套件能力。

## 依赖条件

- Linux / Windows / macOS 均可，支持 ARM 与 AMD 架构；容器方式需 Docker 与 Docker Compose v2。
- 组件依赖：MongoDB、Redis、etcd、Kafka、MinIO（compose 会一并拉起，自备时需按 `config/` 填连接信息）。
- 源码编译方式另需 Go 工具链、`make`、`jq` 等。
- 资源建议：留给这套组件的 CPU / 内存 / 磁盘要够（尤其磁盘，消息与媒体会持续增长）。
- 对外提供服务时需要能被客户端访问的 IP 或域名，以及放行的 API、WebSocket、对象存储端口。
- 生产部署需要一份安全规划：口令、密钥、端口暴露面、限流与网关。

## 已知限制

- 组件多、链路长，出问题时需要逐层排查（宿主机 → 容器 → 组件 → 服务 → 客户端），不是单进程排障。
- 默认配置面向快速跑通，直接上公网等于把后台敞开；默认口令必须改。
- Kafka 对外通告地址、对象存储 endpoint 这类设置一旦写错，表现是"服务全绿但客户端不可用"，容易误判。
- REST API 接口路径与字段随版本演进，跨版本升级需要对照变更说明逐项核对。
- 上游能力以仓库当前状态为准，部分商业化能力不在开源版内。

## 自检清单

执行前：

- [ ] 确认目标机器资源足够，Docker 与 Compose v2 可用，磁盘有充足余量。
- [ ] 确认要暴露的端口清单（API、WebSocket、对象存储，必要时前端），并规划好防火墙。
- [ ] 确认已想清楚用户 ID 规则与令牌签发在哪一端做。
- [ ] 确认 `.env` 中的口令不会被提交到代码仓库。

执行后：

- [ ] `docker compose ps` 里各组件均为运行状态，日志无持续报错。
- [ ] 能从 API 端口拿到管理员令牌，并用它调通一个查询接口。
- [ ] 用示例前端（或自研客户端）从**另一台机器**登录并成功互发一条消息。
- [ ] 从外部网络上传一张图片并成功在客户端显示（证明对象存储 endpoint 配对了）。
- [ ] 重启整个 compose 后数据仍在，客户端能重新登录。
- [ ] 默认口令与默认密钥已全部更换。
