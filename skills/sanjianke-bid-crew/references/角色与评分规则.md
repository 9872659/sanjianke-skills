# 角色与评分规则

本文件说明：四个参与者的职权边界、"竞争"与"协作"的分界、
**为什么评分维度必须在提案之前公示**，以及三组为什么必然会争起来。

---

## 一、四类参与者

| 参与者 | 目标函数 | 产出物 | 权限 |
|---|---|---|---|
| **提案组 A / B / C** | 各自赢下这个名额 | 方案（**三组信息隔离，互不可见**） | 无 |
| **评委团**（3 席，不同侧重） | 按公示维度打分 | 打分表 + 理由 | **风险与合规评委有一票否决** |
| **质询主持** | 逼出差异 | 质询记录 | 无 |
| **裁决人** | 出结论 | 获胜方案 + 合并建议 + 落选原因 | **终裁** |

一句话分工：**三组抢，评委量，主持逼，裁决定。**
四个角色的目标函数是结构性地错开的 —— 提案组要"赢"，评委要"按尺子量"，
质询主持要"让差异见光"，裁决人要"给个能执行的结论并回收落选稿的可用部分"。

---

## 二、三个提案组：取胜路线必须真的不一样

| 组 | 取胜路线 | 天然倾向 | 最不能让步的一点 | 为了赢肯牺牲 |
|---|---|---|---|---|
| **A 组 · 成本快打** | 用最少的钱和最短的时间把事做成 | 抠单价、砍链路、砍到只剩主干 | 总成本与工期必须可核算 | 包装、视觉、长尾优化、品牌叙事 |
| **B 组 · 差异化造势** | 做别人做不出来的东西 | 追独特卖点、记忆点、传播 | 必须给出可指认的差异化声称 | 成本、周期、毛利 |
| **C 组 · 稳控兜底** | 把风险与不确定性压到最低 | 追可控、可回滚、可验收 | 必须给可验收口径与兜底动作 | 出彩、速度、成本 |

**为什么这样设计：** 三组的"肯牺牲什么"正好是别人的强项。
A 组省钱必然在差异化上吃亏，B 组砸差异化必然在成本上吃亏，
C 组求稳必然在"出彩"上吃亏。三组在同一张评分表上各有长短，
**这样"竞争"才真实存在** —— 如果三组都四平八稳，那它们本来就是同一份方案。

每组还带一句 `must_have`（最不能让步的一点）。这一条是硬性的：
A 组写不出算式、C 组写不出验收口径，都是没交作业。

---

## 三、评委团：三席不同侧重 + 一票否决

| 评委 | 侧重 | 否决权 | 对什么最不宽容 |
|---|---|---|---|
| **成本与落地评委** | 钱和人天 | 无 | "说不清"：数字对不上账 |
| **差异与传播评委** | 可指认的差异 | 无 | 把通用能力当独家卖点 |
| **风险与合规评委** | 能不能上、兜不兜得住 | **有** | 合规硬伤 —— 直接出局 |

**为什么只给一席否决权：** 否决权是"这份方案不能上"的权力，不是"我不喜欢"的权力。
三席都给否决权，竞标就变成"只要有人不高兴就全否"，等于没有竞标。
把否决权只给合规这一席，语义才是清的：**否决 = 踩了红线的硬伤**，
而不是"这个维度分低"。

否决**仍然要过本地校验**：

- 没有否决权的评委写的 `vetoes` 不计入否决名单（原样保留在案，标注原因）；
- 没给理由的否决不计入；
- **没锚到那一组方案原文**的否决不计入（编造引文不算否决）。

被否决的组不能被判获胜 —— 这一条由闸门六判，见下。

---

## 四、公示的评分维度与权重

| 维度 | id | 权重 | 评什么 |
|---|---|---|---|
| **成本** | `cost` | 0.30 | 端到端总花的钱与人力，能不能核算到单价 × 用量 |
| **可行性** | `feasibility` | 0.25 | 以现有人力、时间与资源，能不能真的按期做出来 |
| **差异化** | `differentiation` | 0.25 | 有没有可指认、可验证、别人抄不走的差异 |
| **风险** | `risk` | 0.20 | 合规与执行风险的暴露面，以及翻车之后兜不兜得住 |

权重合计 **1.00**。每个维度的 10 分与 0 分都给了**可操作的定义**
（例如成本 10 分 = 把总成本拆到环节级并给出算式；0 分 = 只有"成本可控"这类说法）。
没有这两个端点，打分就只能在 6~8 之间飘。

总分 = 各维度分数 × 权重，逐项相加。**总分由本地按公示权重重算**，
不采信模型自报的加权分；裁决自报的分与评委团重算的分差超过 1.0 会被闸门六点出来。

### 为什么维度和权重是**代码里的常量**

竞标的公正性全押在"尺子先定"这一件事上。让模型在看过任务书之后现编一套维度，
等于每次竞标换一把尺子：跨场不可比、也无法解释"为什么这条赢了"。
所以尺子是常量 + 版本号（`RUBRIC_VERSION`），`rubric` 子命令只负责公示与存档。

## 五、顺序不可倒：**维度必须在提案之前公示**

```
rubric   →  三组提案  →  评委打分  →  交叉质询  →  裁决
（尺子先定）  （各写各的）  （按尺子量）   （逼出差异）  （出结论）
```

`score` 的第一步就是查 `rubric.json`：没有 → `exit=2`，且**不发任何调用**。
`challenge` 没有 `panel.json` → `exit=2`；`award` 没有 `challenge.json` → `exit=2`。

**为什么这条是硬闸门而不是建议：** 顺序倒了，整场竞标的性质就变了。
先看方案后定尺子，评委就是在**为已经写出来的东西找理由** ——
那叫"打分"，不叫"竞标"。这两种东西的产物长得一模一样，区别只在于尺子出现的时间。

## 六、三组为什么会真的争起来

| 场景 | 一组要 | 另一组正好在争 |
|---|---|---|
| 压成本 | A 组把链路砍到只剩主干 | B 组说砍掉的那一环正是差异化的来源 |
| 造差异 | B 组砸钱做别人抄不走的东西 | C 组说这条链路没有兜底、翻车就全废 |
| 求稳妥 | C 组给每一步加兜底与验收口径 | A 组说这些兜底就是纯消耗、预算翻倍 |
| 抢工期 | A 组报三天跑通主干 | C 组说三天跑通的版本没有验收口径，等于没交付 |

`roles` 子命令会把这张表原样打出来（零成本），方便先确认打法再花钱。

## 七、裁决人：终裁必须交付三件东西

```
获胜组      谁赢了 + 凭什么（要落到维度与方案原文上，带锚定引文）
落选原因    逐组给：输在哪一维度、输在方案的哪一处（带原样引文）
合并建议    逐条给：从哪一组拿什么、补进获胜方案的哪一处、补上什么缺口
```

外加 `score_detail`（每个组的每个维度得分）与 `dissent`（异议与被否决意见，原样保留）。

**为什么"合并建议"是必填：** 竞标最大的浪费不是选错，而是
**落选稿里有好东西却因为"它输了"被整份丢掉**。B 组的人物原话、C 组的验收清单，
都不该因为比分低就消失。所以"从落选方案里拿什么补进获胜方案"是交付物的一部分，
缺了就拦（`exit=3`）。
