# 计费、预算与错误码排查

## 1. 点数模型

- 计价单位是**点数**，**1 元 = 100 点，1 点 = ¥0.01**。
- 点数**永久有效**，不按月清零。
- 消费顺序：**先扣会员点数，不足再扣充值额度**。
- 计费节奏：**先冻结、后结算**——提交任务时按预估价冻结，完成后按实际用量**多退少补**。
- **失败不计费**：调用失败直接退款；异步任务失败会把**冻结的点数全额退回**，只有成功产出才结算。
- **调价不追溯**：上游调价会同步调整，但**不影响已充值的点数余额**。
- **余额不足返回 402，不产生欠费**。
- 价格页 / 模型市场 / 接口文档展示的报价**即为实际扣费口径**（所见即所付）。
- 查计费规则表：`python3 scripts/client.py pricing` → `GET /api/v1/pricing`（**注意：这是规则表，不是逐接口价目表**，见第 4 节）。

## 2. 计费单位随能力变化

按能力分类计量，全部在接口文档中标注：

| 能力类型 | 计费口径 | 说明 |
|---|---|---|
| 文本大模型 | 点 / 百万 Token | 输入、输出**分别计价**；流式与非流式同价 |
| 图像生成 / 编辑 | 点 / 张，或按参数档位 | 按模型与分辨率档位计点，支持参考图编辑 |
| 视频生成 / 超分 | 点 / 秒（按分辨率档位） | 提交时冻结，完成后按实际时长结算、多退少补 |
| 数字人 / 对口型 | 点 / 次 或按时长 | 平台弹性 GPU 调度，失败不计费 |
| 语音 TTS / 克隆 | 点 / 千字 | 按合成文本字符数计点；异步合成同价 |
| 语音识别 ASR | 点 / 分钟 | 按音频时长计点 |
| 工具类（水印消除等） | 点 / 次 | 同步返回，调用失败不计费 |

所以「这个接口多少钱」这句话本身是不完整的——必须连着**用量口径**一起看（多少 token、多少张、多少秒、多少千字、多少分钟）。

## 3. 两套价格字段（最容易算错的地方）

平台在每个接口上同时给两套价格：

| 字段 | 含义 | 用途 |
|---|---|---|
| `fixed_price` / `input_price` | **标准价**（公示价） | 对外展示、横向比价 |
| `tenant_fixed_points` / `tenant_points_per_1k_input` | **你所在租户的实际结算价** | **做预算只能用它** |

两者可能差很多。用几个真实快照说明为什么要看 `tenant_*`：

| 接口 | 公示标准价 | 实际结算价 | 差距 |
|---|---|---|---|
| `seedsvc/submit` | 100.00 | 0.10 | 实收远低于公示 |
| `voice_tts/model` | 50.00 | 200.00 | 实收高于公示 4 倍 |
| `flashvsr/submit` | 0.00 | 0.10 | 公示为 0，实收不为 0 |
| `music_generation/create` | 65.00 | 65.00 | 一致（也可能一致） |

**结论：任何按公示价做的预算都可能错一个数量级。** 预算一律读 `tenant_*`，且**以实际扣费为准**（报错信息与任务详情里会写明本次消耗）。

> 上表是某次快照的示例，仅用来说明两套价格确实会不一致。你自己的真实价请用 `python3 scripts/client.py schema <app>` 现场读取。

## 4. `/api/v1/pricing` 的实际覆盖范围（别被宣传口径误导）

价格页说可以「实时查询任意模型或应用接口的当前价格规则」，但**实测该端点只返回 6 条规则**——一条全局默认加 5 条特例，**并不覆盖全部接口**（`voice_tts` 就不在里面）：

| 键 | 内容（实测） |
|---|---|
| `*` | 默认规则 `{mode: flat, cost: 0, markupPercent: 20}` |
| `/api/v1/apps/full_video/submit` | 按分辨率：480P 10 点/秒 · 768P 20 · 1080P/2K/4K 40 |
| `/api/v1/apps/asr/asr` | 语音识别 2.4 点/分钟（源头 2 点/分钟 +20%） |
| `/api/v1/apps/flashvsr/submit` | 源价 × 1.2（固定 +20%） |
| `/api/v1/apps/action_transfer/*` | 固定 30 点/秒（走 likeadmin 通道，不随档位变） |
| `/api/v1/apps/person_replacement/*` | 固定 30 点/秒 |

响应是**裸对象**（无 `code/msg` 外壳）：`{currency, markupPercent, note, pricing}`，`markupPercent: 20` 表示「用户价 = 上游点数 × (1 + markup%)」。

**结论：查规则用 `pricing`，查某个接口到底多少钱要用 `schema <app>` 读 `tenant_*`。**

## 5. 预算估算步骤

```bash
# ① 拉计费规则表（全局 markup 与少量特例）
python3 scripts/client.py pricing
python3 scripts/client.py pricing --filter full_video

# ② 拿某应用每个接口的真实价（这才是完整口径）
python3 scripts/client.py schema music_generation

# ③ 看最近任务的真实消耗（字段是 actual_points）
python3 scripts/client.py tasks --page-no 1

# ④ 试算：按次价 × 次数，或按千字价 × 千字
```

实测消耗参考：`DeepSeek-V4-Flash` 一次普通问答约 **0.74~0.99 点**；极小调用（`max_tokens=8`）为 **0.00 点**。

估算时记住三条：

1. **按 `tenant_*` 算，不按公示价。**
2. **同步接口也要花钱**——查询类（`query`）通常为 0，但生成类同步接口照收。
3. **重试也要花钱**。任何失败后的重提，都可能是第二次计费（见下节）。

## 6. 重试与重复计费

| 情况 | 会不会扣费 | 怎么办 |
|---|---|---|
| HTTP 4xx（参数错、余额不足、无权限） | 不会真正执行任务 | 修好参数/权限再发 |
| HTTP 5xx（服务异常） | 通常未扣费 | 退避重试 |
| 提交超时（没收到响应） | **可能已冻结** | **先查任务再决定重提** |
| 任务 `completed` 后你又提了一次 | **会** | 提交前落盘记录，按 `task_id` 去重 |
| 回调被重试（平台 1–10 次） | 任务不重复计费，但**你的下游可能重复登记** | 消费端按 `task_id` 幂等 |

> **最贵的一类 bug：把「没收到响应」当成「没提交成功」，于是重提。**
> 提交类调用要么先落盘、要么先查、要么用回调 + 幂等消费端，三者选其一。

## 7. 错误码全表

| HTTP | code | 含义 | 处理 |
|---|---|---|---|
| 400 | `invalid_request` | 参数缺失或格式错误 | `schema <app>` 核对参数名与必填项 |
| 401 | `auth_failed` | API Key 缺失或无效 | 重建 Key 后 `client.py login` |
| 402 | `insufficient_points` | **账号**点数余额不足 | 充值；错误里含本次所需点数 |
| 402 | `key_quota_exceeded` | **该 Key 的**点数额度打满 | 调高/重置 Key 的 quota，**不用充值** |
| 403 | `permission_denied` | 该 Key 无权调用此模型/应用 | 检查模型是否已开通、Key 是否被限权 |
| 404 | `not_found` | 模型 / 应用 / 任务不存在 | 用 `apps` / `models` 拿真名（应用代码用下划线） |
| 429 | `queue_limit_exceeded` | 排队任务已达上限 | 降并发，退避后重试 |
| 5xx | `server_error` | 服务异常 | 退避重试；持续失败换模型/线路 |

## 8. 排查决策树

```
调用失败
├─ 退出码 3（网络层）
│    → 到不了 api.a7w.cn：检查内网/代理/防火墙，确认 DNS 与 443 出口
├─ 401 auth_failed
│    → Key 过期/写错/带了多余空格。client.py whoami 复核
├─ 402
│    ├─ insufficient_points → 账号余额不足，去充值
│    └─ key_quota_exceeded  → 只是这个 Key 的额度满了，别去充值
├─ 403 permission_denied
│    → Key 没开该模型/应用权限，与余额无关
├─ HTTP 200 但 code:0
│    → 接口/应用不可用。最常见是用中文 name 当接口代码，应该用 code 字段
├─ HTTP 404 且响应体为空
│    → 应用代码拼错（用了连字符？）先跑 apps --brief 拿真名
├─ 400 invalid_request
│    → 参数名或必填项不对；注意 params_schema 有 properties 与扁平两种形态
└─ 429 queue_limit_exceeded
     → 并发太高。把批量任务改成有限并发 + 指数退避
```

客户端已经把这张表编进错误处理：失败时 stderr 会直接给出「含义 → 下一步」，并且**退出码可用脚本判断**（见 `client-cli.md`）。

## 9. 建议的重试策略

- **4xx 一律不重试**（除了 429）。参数、权限、余额类问题的重试只是浪费请求。
- **429 / 5xx 才重试**，用指数退避 + 抖动，例如 1s → 2s → 4s → 8s，上限 5 次。
- **提交类调用（可能已冻结）不要裸重试**，先查 `task_id` 或任务列表。
- 批量出片类任务建议**有限并发**（3–5 路），既避开 429，也让队列稳定消化。
- 每批结束后用 `client.py tasks --page-size 50` 核对 `usage`，与用户中心流水对账。

## 10. 对账

用户中心提供**用量统计与流水导出**，按如下顺序核对：

1. 每批任务的本地记录（`task_id` + 提交时间）
2. `client.py tasks --page-no 1` 返回的 `actual_points` 汇总
3. 用户中心流水的实际扣点

三者对不上的常见原因：**重复提交**（同一任务两条流水）、**回调重试导致下游重复登记**（流水只有一条，但你的记录有两条）、**把标准价当实收价做预期**。
