# 三剪客 · Java Agent 框架

给 Java 团队用的一套「AI Agent 框架落地作业流程」。主角是 Agents-Flex —— 一个 Java 原生、
按模块拆分的 AI Agent 开发框架，本包把「该不该用、怎么接进去、接到哪一步会翻车」讲成可执行的步骤。

它真正想解决的问题只有一个：**别在框架选型和坐标依赖上还债**。上游仓库里写的版本号与
Maven 中央仓库上能拉到的版本号，可能压根不是一个东西；1.x 和 2.x 的产物命名也不是一套。
这两个坑踩下去，半天时间就没了。所以本包把「接入前先核对事实」放在第一步。

本包不重复上游的 API 清单，而是给出**模块分层怎么看、责任链怎么排、运行时怎么落地、
选型怎么比**这四件事的判断依据，再配一张上线前自检表和一份排错清单。

## 触发场景

- 「Java 服务要接大模型，Agents-Flex / Spring AI / LangChain4j 到底选哪个？」
- 「pom 里照着示例写了 2.x 版本，本地 `Could not resolve`，或者拉下来是 1.x 的老包名」
- 「工具模型不调用，或者反过来调用了一个不存在的工具，上一轮的工具还泄漏到这一轮」
- 「同步调用跑通了，换流式就报错，回调里的消息结构还对不上」
- 「要接 MCP server、文件系统 Skills、智能问数（Text2SQL），不知道入口在哪一层」
- 「想给多个模型做负载均衡 + 熔断 + 链路追踪，不想自己造一套」

**不适用于**：只想调一次 HTTP 接口拿个回答（那不需要 Agent 框架）、要把现成模型做训练或
微调、在前端或移动端做同类选型。

## 快速开始

按下面四步走，不要跳步。**第一步能省掉后面 80% 的返工。**

```bash
# 1. 核对工程侧前提：JDK 与构建工具
java -version          # 上游多数模块要求 JDK 8+，但 MCP 模块要求 JDK 17+
mvn -v

# 2. 核对坐标现实（关键步骤）
#    groupId 是 com.agentsflex，但「仓库里写的版本」≠「中央仓库能拉到的版本」。
#    先查中央仓库实际有哪些版本，再决定用哪个版本线、要不要自建。
#    查询入口：https://search.maven.org/ ，按 groupId 过滤。
#    经验事实：中央仓库上可见的最新版本停在 1.0.0-rc.6（2025-02 之后未再发布），
#    而上游仓库根 pom.xml 的 revision 已经到 2.2.9。

# 3. 确认版本号来源（上游把版本写在根 pom 的 revision 属性里）
git clone --depth 1 https://gitee.com/agents-flex/agents-flex.git
#    然后在 agents-flex/pom.xml 里查 revision 属性的当前值

# 4. 只引你要的模块，别默认拉整个 BOM
#    BOM 适合多模块项目统一版本；单个服务接一个模型，引最小集合就够
```

四步之后的作业顺序：

1. **定运行形态**：纯 Java 服务 / Spring Boot / 其它 JVM 技术栈 —— 决定用不用 starter。
2. **定模型来源**：OpenAI 兼容端点、自建 Ollama、还是某个云厂商 —— 决定引哪个 `chat-*` 适配模块。
3. **定要不要 Agent 运行时**：只有单轮问答，引 core + chat 即可；要多轮工具审批、断点恢复，
   才需要 Agent 运行时模块，并且**同时准备好持久化后端**（JDBC 或 Redis）。
4. **定可观测**：生产环境建议一开始就打开 OpenTelemetry 开关，事后补埋点成本高得多。

## 能力边界

**覆盖**：

- 上游框架的**模块地图与抽象分层**：模型层（Chat / Embedding / Image / Rerank）、提示词层、
  工具层、记忆与存储层、运行层各自负责什么，边界在哪
- **工具的两种构建路径**：注解声明式（扫描类上的工具注解）与编程式构建（运行时拼装），
  以及什么时候该用哪一种
- **工具组按输入动态挂载**的思路：命中才进请求体、按最后一轮用户消息重新匹配，避免工具泄漏
- **拦截器责任链的 order 语义**、按请求条件激活（matcher）、以及「为什么改不动请求体」的原因
- **Agent 运行时的能力盘点**：单轮推进、工具审批、挂起与恢复、快照、版本 CAS、Middleware、统一事件
- **RAG 全链路**：文档模型 → 加载/解析/切分 → Embedding → 向量存储 → 检索 → Rerank
- **MCP / Skills / Text2SQL / 网络搜索 / LLM Wiki** 的定位差异与接入口
- **模型路由与可观测**：多实例组合、负载均衡策略、重试、熔断半开、OpenTelemetry 开关
- 与 Spring AI、LangChain4j 的**维度化对比**（按维度给判断依据，不给「谁最好」的结论）

**不覆盖**：

- 不收录取用上游项目的源码、构建产物或文档原文，不做二次分发
- **不替你拍板选型**。给出的是判断维度与代价清单，最终结论要结合你团队已有的技术栈
- 不涉及前端、移动端、模型训练与微调、GPU 推理部署
- 不为任何云厂商或模型服务做效果背书；模型效果、限流与计费以厂商为准
- 不保证上游 API 在 2.x 之后保持兼容 —— 本包给的是**核对方法**，不是永久快照
- 不执行任何生产变更：不写库、不发消息、不改线上配置

## 已知限制

这一节是**核对结果**，请务必读完再动手：

- **仓库版本 ≠ 中央仓库版本**。中央仓库 `com.agentsflex` 下可见的版本只有 `1.0.0-rc.1`
  到 `1.0.0-rc.6`，最后一次发布在 2025-02；而上游仓库根 pom 的 `revision` 已到 `2.2.9`。
  结论：**2.x 无法直接靠中央仓库拉到**，要么自行构建安装到本地/私服，要么使用上游另行
  提供的仓库地址。本包不假设你一定拉得到 2.x。
- **1.x 与 2.x 的产物命名不是一套**。1.x 时期走 `agents-flex-llm-*`、`agents-flex-document-parser*`
  这类命名；2.x 的模块名变成了 `agents-flex-chat-*`、`agents-flex-doc-extractor` 等。
  照抄网上示例，很容易拿到一个「名字对不上」的坐标，然后误判成镜像或网络问题。
- **上游迭代快**，本包记录的事实以核对时点为准；动手前请用快速开始第 2 步重新核一遍。
- 本包未在本机复现上游全部模块的构建与运行，示例侧重**结构与调用关系**，具体签名请以你
  引入的那个版本的源码为准。
- 选型对比部分是**通用工程判断**，不针对某个具体小版本的行为差异；三个框架都在演进，
  版本号一换，某些差异项可能就不成立了。

## 自检清单

上线前逐条打勾，任何一条打不上就先别合：

- [ ] 目标工程 JDK 版本覆盖了要引模块的要求（尤其别用 8 去引 MCP 模块）
- [ ] 每个坐标都在中央仓库或私服**实际解析通过**，没有 `Could not resolve`
- [ ] 产物名与版本线匹配（2.x 用 `chat-*` 线命名，没混进 1.x 的 `llm-*` 命名）
- [ ] 版本号统一（用 BOM 或 `dependencyManagement` 收口，没有各模块各写一个版本）
- [ ] API Key 走环境变量或配置中心，没有落在代码、测试或仓库里
- [ ] 同步与流式**两条路径都实跑过**，流式的回调时机与消息结构确认无误
- [ ] 模型可见的工具清单与实际注册的一致；未命中的工具组不该出现在请求体里
- [ ] 工具数量做过成本与准确性评估（工具一多，调用错误率与 token 成本一起涨）
- [ ] 需要多轮/审批/恢复时，持久化后端（JDBC 或 Redis）已就绪并测过重启恢复
- [ ] 路由与熔断参数有压测或灰度依据，不是照抄默认值
- [ ] 可观测开关按需打开，导出间隔与采样成本评估过
- [ ] 有回滚方案：依赖版本可退回、配置可回切
