# 选型对比与排错

> 两部分：**A. 框架怎么选**（给判断维度与代价，不给结论）；**B. 出了事怎么查**（按症状定位）。
>
> 对比部分的定位是**通用工程判断**，不针对任何一方某个具体小版本的行为差异。
> 三个项目都在快速演进，版本号一换，某些差异项可能就不成立了 —— 结论要自己复核。

---

# A. 选型对比

## A0. 先把三个候选摆清

| 框架 | 一句话定位 |
|---|---|
| **Agents-Flex** | Java 原生的轻量级 AI 应用框架，按模块拆分能力，不强绑应用框架；功能面铺得宽（RAG、MCP、Skills、Text2SQL、图像音频视频、多模型路由） |
| **Spring AI** | Spring 官方体系的 AI 抽象层，靠自动配置与 Spring Boot 生态吃饭；适合已经在 Spring 里的团队 |
| **LangChain4j** | 受 LangChain 思路影响的 Java 库，以声明式接口和丰富的集成为卖点；抽象层次较多 |

三个都是 Apache-2.0 或同级别宽松许可（各自以仓库 `LICENSE` 为准），所以**许可证这一项基本
不构成差异**，别在这上面纠结太久。

---

## A1. 按维度对比

| 维度 | Agents-Flex | Spring AI | LangChain4j |
|---|---|---|---|
| 生态归属 | 独立框架，不强绑容器 | Spring 官方体系 | 独立库，另有 Spring 集成 |
| 接入成本（非 Spring 工程） | 低，普通 Java 程序可直接用 | 偏高，脱离 Spring 不顺手 | 中，直接当库引 |
| 接入成本（Spring Boot 工程） | 中，有 starter 但覆盖面有限 | 低，自动配置最全 | 低到中，有 starter |
| 与 Spring 版本节奏的耦合 | 弱 | 强（版本跟随 Spring 体系） | 弱 |
| 模型适配广度 | 宽（含图像、视频、音频、OCR） | 中到宽，以官方支持为准 | 很宽，社区集成为主 |
| 工具调用（Tool Calling） | 注解声明 + 编程式构建，另有"工具组按输入动态挂载" | 注解声明为主 | 注解声明 + 声明式接口 |
| 多轮/复杂编排 | 有独立 Agent 运行时（快照、CAS、审批、事件） | 以对话与顾问链为主 | 有链式与 Agent 抽象 |
| 运行时状态持久化 | 内建（JDBC / Redis） | 需自行实现 | 部分需要自行实现 |
| RAG 组件完整度 | 很完整（解析→切分→Embedding→存储→检索→Rerank） | 完整 | 完整，且有多种实现可选 |
| 向量库适配数量 | 多（十种以上） | 多 | 多 |
| MCP 支持 | 有（stdio / http-sse / http-stream） | 有 | 有 |
| 多模型路由（负载均衡/熔断） | 内建 | 需自行组合或借助基础设施 | 部分需自行组合 |
| 可观测 | 内建 OpenTelemetry | 与 Micrometer/OTel 体系贴合 | 有监听与集成点 |
| 文档与社区资料量 | **相对少**，部分内容需读源码 | 多，官方文档体系完整 | 多，示例丰富 |
| 版本与坐标可得性 | **要自己核对**（仓库版本与中央仓库不一致，见下） | 官方发布，坐标稳定 | 官方发布，坐标稳定 |
| 上手心智负担 | 中（模块多，但分层清楚） | 低（Spring 用户熟悉那套） | 中到高（抽象层次多） |

### 关于「版本与坐标可得性」这一行

这是 Agents-Flex 最需要提前知道的一项，也是本包反复强调的：

- 中央仓库 `com.agentsflex` 上可见版本停留在 `1.0.0-rc.6`（2025-02 后未再发布）
- 上游仓库根 pom 的 `revision` 已到 `2.2.9`
- 也就是说新版本**要么自建、要么用上游另行提供的仓库**

**后果不在技术上，在流程上**：你需要为这个依赖安排构建与升级责任（谁构建、谁发布到私服、
升级怎么回归），而不是像引一个官方发布物那样直接写版本号。

## A2. 各自的适合与代价

### Agents-Flex

**适合**：Java 技术栈但不一定在 Spring 里；想要"能力按需取用"而不是被一个大框架绑住；
需要一次性要齐多模态模型接入（图像/视频/音频/OCR）、MCP、Skills、智能问数；
需要内建的多模型负载均衡与熔断；能接受读源码、自己核对坐标。

**代价**：中文以外的资料较少，遇到细节问题多半要读源码；依赖版本要自己规划（见 A1 最后一行）；
模块多，团队需要先花时间建立分层认知（本包的 `core-concepts.md` 就是干这个的）。

### Spring AI

**适合**：已经是 Spring Boot 体系，希望 AI 能力像其它 Spring 组件一样用配置接进来；
团队希望"少引入新概念"；需要官方文档与较长周期的版本管理。

**代价**：与技术栈强绑定，脱离 Spring 用起来不顺手；部分框架外的能力（例如非官方的模型
供应商、某些向量库）需要自己补；版本节奏跟随 Spring，升级时要做整体回归。

### LangChain4j

**适合**：喜欢声明式接口（把"提示词 + 工具 + 输出结构"写成一个接口，让库去实现）的团队；
需要大量第三方集成；从 Python 的 LangChain 迁过来、概念可以平移。

**代价**：抽象层次多，链路长，出错时定位要往下钻好几层；不同集成的质量参差，需要自己验证；
部分生产级能力（如执行状态持久化、路由熔断）要自己补。

---

## A3. 决策路径：问自己五个问题

按顺序问，第一个"是"基本就定了，后面的问题用来验证。

1. **团队已经在 Spring Boot 上，且希望 AI 能力和其它 Spring 组件用同样的方式管理吗？**
   → 是：优先评估 Spring AI。
2. **需要大量第三方集成、且团队接受较重的抽象层（声明式接口风格）吗？**
   → 是：优先评估 LangChain4j。
3. **需要"一个服务同时接多家模型 + 内建路由熔断"，或者需要 RAG、MCP、Skills、智能问数、
   多模态一次性铺开吗？**
   → 是：优先评估 Agents-Flex。
4. **有非 Spring 的 Java 工程（老服务、中间件、工具类项目）要接 AI 吗？**
   → 是：Agents-Flex 或 LangChain4j 比 Spring AI 顺手。
5. **团队能接受"依赖需要自己构建/私服发布"这类额外流程成本吗？**
   → 否：把 Agents-Flex 的评估结论往后放，或者先按 A1 的方案 A（用中央仓库能拉到的版本线）
   做概念验证，再决定是否投入自建。

### 一个不要做的事

**不要为了选型而选型**。如果只是"调一次模型拿个回答"，一个 HTTP 客户端加一个 JSON 解析就够，
引框架反而增加依赖与升级负担。框架的价值在多模型统一、工具编排、RAG 链路、运行时状态这些
**复杂性真实存在**的地方。

---

## A4. 组合使用（不是只能选一个）

三者可以在同一个系统里并存，常见分层：

| 层 | 可以放什么 | 理由 |
|---|---|---|
| 模型接入层 | 统一收口，用哪个框架的适配都行 | 业务不直接依赖具体供应商 |
| 能力层（工具/RAG） | 谁的组件好用用谁的 | 工具本质是函数，跨框架复用成本低 |
| 业务编排层 | 选一个作为主框架，别混两个编排模型 | 两套状态模型混用会带来灾难性调试成本 |

**红线**：**同一业务流程里不要混用两个框架的编排/状态模型**。工具和模型适配可以混，
"谁负责推进这一轮"必须只有一个答案。

---

## A5. 迁移成本清单

如果要换框架，按这个清单估工作量，别只算"改多少个类"：

- [ ] 模型配置与密钥管理方式是否改变（配置键名、环境变量约定）
- [ ] 提示词模板的语法差异（占位符写法、多模态消息拼装）
- [ ] 工具定义的改写（注解名、参数声明方式、返回值约定）
- [ ] 拦截器/中间件的等价物是什么（有没有、顺序怎么排）
- [ ] 向量库中已有数据的兼容性（Embedding 模型与维度能否沿用）
- [ ] 多轮会话状态的存储结构（换框架常要换存储结构 → 要写数据迁移）
- [ ] 可观测的埋点与看板（指标名、Span 名会变）
- [ ] 测试用例与回归基线（回答质量不可比时，需要人工评估样本）

**最容易被低估的是第 6 项**：会话状态结构一变，历史数据就要迁移，而这通常牵扯最久。

# B. 排错

## B0. 通用方法：二分法定位

出现问题时，按这个顺序缩小范围，别一上来读框架源码：

1. **最小工程复现**：只引 `core` + 一个模型适配，能跑通再说。
2. **逐层加回**：流式 → 一个工具 → 一个工具组 → 一个拦截器。哪一步坏了就是哪一步。
3. **关掉所有扩展点**：先关拦截器、再关工具组、最后关工具。回到"裸问答"还能不能跑。
   这一步能直接区分"是框架配置问题"还是"是你的扩展代码问题"。
4. **对齐日志**：把框架日志级别调高，和你的业务日志按请求 ID 对齐看。
5. **换端点验证**：换一个已知可用的 OpenAI 兼容端点。能跑通说明是原端点兼容性问题，
   不是框架问题。

**一条经验**：报错信息指向的地方，往往不是根因。`ClassNotFoundException` 多半是版本错配，
`NullPointerException` 在流式回调里多半是增量对象结构理解错了。

---

## B1. 坐标解析失败（`Could not resolve` / 找不到构件）

**症状**：`mvn compile` 直接失败，或 IDE 里依赖飘红。

**排查顺序**：

| 步骤 | 动作 |
|---|---|
| 1 | 确认版本是不是**只存在于仓库、不存在于中央仓库**（见快速开始第 2 步）。这是最高频原因 |
| 2 | 确认**产物名与版本线配套**：2.x 用 `agents-flex-chat-*` / `agents-flex-doc-extractor`；1.x 是 `agents-flex-llm-*` / `agents-flex-document-parser*`。混用必然失败 |
| 3 | 确认企业内网私服/镜像是否同步了该 groupId（很多镜像只代理常用库） |
| 4 | 确认没有把 `<type>` 写错（BOM 是 `pom` 且要 `scope=import`） |
| 5 | 确认本地库没有半损坏的缓存：删掉 `~/.m2/repository/com/agentsflex/` 下对应目录重拉 |

```bash
# 看 Maven 到底去哪找的
mvn -X compile 2>&1 | findstr /I "agentsflex"

# 只查这个 group 的解析结果
mvn -q dependency:tree -Dincludes=com.agentsflex
```

---

## B2. 版本线错配（编译过了，运行时炸）

**症状**：编译通过，启动或调用时报 `NoSuchMethodError` / `NoClassDefFoundError` /
`AbstractMethodError`。

**原因**：同一个工程里混进了两条版本线的构件，或者某个传递依赖把版本降回去了。

**处理**：

```bash
# 定位到底解析到了哪个版本
mvn -q dependency:tree -Dverbose -Dincludes=com.agentsflex

# 统一收口：用 BOM
# 或在 dependencyManagement 里显式钉住每个 com.agentsflex 构件
```

**纪律**：`com.agentsflex` 下所有构件**必须来自同一条版本线**。这个 group 的模块互相依赖，
混版几乎必然出问题。用 `dependencyManagement` 或 BOM 统一，不要各模块各写版本。

---

## B3. JDK 与构建期问题

**症状**：`UnsupportedClassVersionError`、`invalid target release`、MCP 模块相关代码编译不过。

**排查**：

- 核对**模块级**要求：上游多数模块 JDK 8+ 可跑，**MCP 模块要求 JDK 17+**
- 若工程在 8 上：要么不用 MCP 模块，要么整体升 JDK（别只给一个模块设高版本，容易出兼容问题）
- 检查父 pom 或插件配置里的 `maven.compiler.source/target` 是否被别处覆盖
- 检查是否被别的依赖的 `--release` 或 `maven-toolchains` 影响

```bash
java -version
mvn -v
mvn -q help:evaluate -Dexpression=maven.compiler.source -DforceStdout
```

---

## B4. 同步能跑，流式不行

**症状**：同步调用正常，流式报错、内容重复、内容不完整、或者干脆没有回调。

**排查顺序**：

| 可能原因 | 判断方法 |
|---|---|
| 把每次回调当成完整回答 | 打印每次回调的增量长度。如果每次只有一小段，那就是增量，必须自己拼接 |
| 结束条件判断错 | 打印回调次数与结束标志。流结束还在等 → 阻塞；提前退出 → 内容少 |
| 提示词不是同一套 | 对比同步与流式两条路径构造的提示词对象，确认用的是同一个 |
| 端点不支持流式 | 换一个已知支持流式的端点试。有些兼容实现只做了非流式 |
| 网络/代理缓冲 | 回调长时间无输出然后一次性全来 → 中间有缓冲层（代理、网关），关掉缓冲 |

**一条实务建议**：把"拼接逻辑"写成一个独立可测的小组件，单独用假的增量序列测它。
流式问题里相当一部分其实是拼接逻辑自己的 bug。

---

## B5. 拦截器不生效

**症状**：注册了拦截器但行为没变化。

**逐一核对**：

1. **是不是想改 Body？** 请求规格对象只含 URL、Header、重试配置，**不暴露 Body**。
   想改内容必须走提示词或对话参数。
2. **改的位置对不对？** 修改必须发生在 `chain.proceed()` **之前**。放在之后改的是
   已经发出去的请求的记录，不是请求本身。
3. **matcher 命中了没有？** 条件是运行到该注册项时求值的。加一行日志打印条件判断结果。
4. **order 有没有被别的拦截器覆盖？** order 小的先执行，后来的拦截器可以覆盖前面的修改。
   如果你设了温度但下游又设了一次，你的就白设了。默认约定：可观测 `-1000`、普通 `0`、
   请求准备 `1000`。
5. **是不是只注册到了某一个模型实例上？** 给某个实例注册的拦截器，不会作用于别处新建的实例。
   要给之后所有实例生效，用全局注册入口。

## B6. 工具相关（不调用 / 乱调用 / 成本暴涨）

### B6.1 模型完全不调用工具

| 原因 | 处理 |
|---|---|
| 工具描述太模糊 | 描述里写清"什么时候该用"，不只是"做什么" |
| 必填参数没标或描述缺格式 | 标上必填，参数描述里给格式与示例 |
| 用错了提示词对象 | 工具要挂在**实际发出去的那个**提示词对象上；挂了但没发等于没挂 |
| 工具组没命中 | 打印每轮的命中结果。关键词不在用户消息里就不会命中 |
| 工具太多，模型挑不出来 | 减少可见工具数量（工具组），或用渐进式工具发现 |

### B6.2 调用了一个不存在的工具 / 参数对不上

- 工具名重复：盘点一遍全量工具名（本地 + MCP + Skills），重名的先改名
- MCP 远程工具与本地工具冲突：这也是重名问题，做一次启动期校验
- 参数类型与描述不一致：模型按**描述**填参，不按你的 Java 签名。描述说"日期字符串"，
  模型就不会传时间戳

### B6.3 工具泄漏到不相关的轮次

如果出现"上一轮的工具这一轮还在"，按这个顺序查：

1. 确认用的是**工具组**（按最后一轮用户消息重新匹配）而不是全量挂载
2. 确认用的是**同一个提示词对象跨轮复用**时的行为 —— 多轮场景推荐每轮重建或让记忆对象
   统一管理，不要手工留状态
3. 打印每轮实际进入请求体的工具清单，和预期对比

### B6.4 成本与错误率一起涨

这是工具数量过多的典型信号：

- 工具清单本身占 token，几十上百个工具时开销可观
- 可选项一多，模型选错的概率上升，重试又推高成本
- **处置**：按业务域拆工具组、按输入动态挂载、或改用渐进式工具发现（先检索再调用）

**别忘了给工具调用循环设最大轮次上限**。工具持续失败时会反复"要求调用 → 执行失败 → 再要求"，
没有上限就是无底洞。

## B7. RAG 召回为空或答非所问

**症状**：回答看起来还行，但其实是模型自己编的；或者答得很离谱。

**第一件事：把检索结果打印出来看**。只看最终回答判断不出检索是否工作 —— 模型可能靠自己的
知识答对了，掩盖了检索为空的事实。

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 检索结果恒为空 | Embedding **维度与向量库索引维度不一致**（换过 Embedding 模型最容易发生） | 确认维度；不一致就重建索引。这个错误常常**不报错**，只是查不到 |
| 检索结果恒为空 | 索引/集合名写错，或数据写进了另一个库 | 核对库名、索引名、命名空间 |
| 检索结果恒为空 | 写入与查询用了不同的 Embedding 模型 | 两者必须同一个模型，且同一版本 |
| 召回了但答不好 | 切分粒度不对（片段太碎缺上下文，或太大混噪声） | 先按标题层级切，再调；把召回片段打出来人工看一眼 |
| 召回了但答不好 | 没有接 Rerank | 接上 Rerank。通常比继续调切分参数收益更直接 |
| 多租户串数据 | 检索没带租户过滤 | 元数据里带租户标识，检索时强制过滤 |
| 文档解析乱码 | PDF 是扫描件（需要 OCR）或版式复杂 | 扫描件走 OCR 模块；复杂版式换解析器 |

**排错小工具**：写一个只做"写入一条 → 查同一条"的最小测试。跑不通就是链路问题，
跑得通就是数据与策略问题。这一步能把范围砍一半。

## B8. Agent 运行时的状态问题

| 症状 | 原因 | 处理 |
|---|---|---|
| 重启后状态全丢 | 只引了运行层，没引存储层；状态在内存 | 引 JDBC 或 Redis 存储实现，并初始化持久化结构 |
| 版本 CAS 冲突报错 | 同一会话被并发推进（这是**正确行为**，防覆盖） | 上层处理失败：会话级加锁、或提示重试；不要绕过 CAS |
| 任务卡住不动 | 工具审批没配或没人处理 | 明确哪些工具要审批；审批未决要有超时与兜底 |
| 恢复后行为异常 | 快照里缺执行所需的外部状态（例如工具依赖的临时数据） | 让可恢复状态自包含，别把关键状态放在进程内存里 |
| 事件收不到 | 事件是统一模型，但订阅方式/时机不对 | 先确认订阅建立时机在事件发生之前；加最简打印验证 |

**架构提醒**：引入运行层意味着**你的服务从此有状态了**。要相应准备：持久化后端的运维、
状态数据的清理与归档策略、多实例部署时的并发控制。这是引入运行层的真实成本，选型时要算进去。

## B9. 可观测不生效 / 性能问题

| 症状 | 排查 |
|---|---|
| OTel 开关没作用 | 这些是**系统属性**，要放在 JVM 启动参数（`-D...`）里；放应用的 yaml/properties 里不一定读得到 |
| 有 Span 但没有内容 | 导出器类型没设对（日志 / OTLP / 自定义），或后端地址没配 |
| 指标数据量过大 | 导出间隔太密。先按默认跑一版，看实际开销再调 |
| 开了可观测后延迟上升 | 采样率与导出方式都要评估；高并发下同步导出会拖慢请求 |
| 想把追踪数据落库 | 有专门的导出实现支持持久化到 JDBC，注意表结构与清理策略 |

**建议**：生产环境**一开始就打开**可观测。事后补埋点的成本远高于一开始就开 ——
你需要的是线上出问题那一刻的链路数据，而不是复现出来的。
