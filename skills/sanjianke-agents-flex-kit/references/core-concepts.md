# 核心概念：模块分层与机制

> 本文件解释 Agents-Flex 的结构与机制，用于建立判断依据。
> 文中模块名与类名是**核对到的公开标识**；具体方法签名请以你实际引入的那个版本为准，
> 上游迭代较快，签名变动的概率不低。

---

## 一、这套框架的定位

一句话：**面向 Java 生态的轻量级 AI 应用开发框架，按模块拆分能力，不绑定某个应用框架或运行时。**

它和「一个大而全的 AI 应用平台」的区别在于取舍方向：

| 取向 | 表现 |
|---|---|
| 拆得开 | LLM 调用、工具、Agent、RAG、向量存储、图像、音频、MCP、Skills、Text2SQL 各自独立成模块 |
| 不强绑 | 核心模块在普通 Java 程序里就能用，不是必须挂在 Spring 容器上 |
| 可替换 | 模型、向量库、搜索引擎都以接口形式接入，能换实现而不动上层业务 |
| 组件齐全 | RAG 从文档解析到 Rerank 都有现成件，不用自己拼装胶水 |

它适合的场景：智能客服、企业知识库、智能问数、Agent 工作流、模型网关、插件式工具系统，
以及**一个 Java 服务要同时接多个模型厂商**的情况。

## 二、模块地图

按职责分成五组来看，比按字母顺序背模块名有用得多。

### 1. 地基

| 模块 | 职责 |
|---|---|
| 核心模块 | 最基础的抽象：Chat、Prompt、Message、Tool、Memory、Document、Store、可观测接口 |
| Spring Boot 启动器 | 自动配置，覆盖常用模型与向量存储 |
| 可观测模块 | OpenTelemetry 的 Span 与 Metric 导出，支持把数据落到 JDBC |

### 2. 模型适配层

| 模块 | 覆盖范围 |
|---|---|
| 对话模型 | OpenAI 兼容接口、Qwen、Ollama、DeepSeek、LiteLLM |
| Embedding | OpenAI、Ollama、Qwen |
| 图像 | OpenAI、Gemini、阿里云、Gitee、火山引擎 |
| 视频 | 异步视频生成与编辑：阿里云百炼、火山引擎方舟 |
| 音频 | 语音识别与语音合成：阿里云、腾讯云、火山引擎 |
| OCR | 百度智能云、Gitee AI、MinerU |
| Rerank | 默认实现与 Gitee Rerank |

> 注意「异步」二字：视频一类是长耗时任务，走的是**提交后轮询**的协议，不是同步返回。
> 这条链路由异步任务模块 + 异步任务存储模块（JDBC / Redis）承担。

### 3. 知识与存储层

| 模块 | 职责 |
|---|---|
| 向量存储 | Redis、Qdrant、Chroma、Pgvector、MariaDB、Milvus、OpenSearch、Elasticsearch、阿里云、腾讯云 |
| 搜索引擎 | Lucene、Elasticsearch、以及通用搜索服务接口 |
| 文档提取 | 从 PDF、Office、HTML、邮件、压缩包、输入流和 URL 中提取 Markdown 风格内容 |

### 4. 能力层（Agent 的"手脚"）

| 模块 | 职责 |
|---|---|
| 通用工具集 | 文件系统、Shell、Grep、Glob、WebFetch、Python、JavaScript |
| 工具检索 | 渐进式工具发现，支持内存与自定义搜索提供方 |
| MCP 客户端 | 连外部 MCP Server，把远程工具包装成本框架的 Tool |
| Skills | 基于文件系统的技能加载与渐进式披露 |
| Skills 安装包存储 | 技能包的版本化存储（文件系统或对象存储） |
| Skills 沙箱 | 隔离执行技能脚本的运行时聚合，含两种沙箱实现 |
| 子 Agent | 通用 Subagent 工具，提供后台任务执行与结果获取 |
| 智能问数 | Text2SQL 工具集，含表结构渐进披露、只读校验、拦截器链 |
| 网络搜索 | Brave、Bocha、百度千帆与自定义搜索提供方 |
| LLM Wiki | 把知识组织成可导航的层级 Wiki 树，支持按路径读取与渐进式披露 |

### 5. 运行层

| 模块 | 职责 |
|---|---|
| Agent 运行时 | 持久化的 Agent 执行：运行状态、快照、版本 CAS、审批、Middleware、事件 |
| Agent 存储 | 运行、命令、事件与产物的持久化（JDBC / Redis） |
| 异步任务 | 可靠跟踪与调度供应商侧的异步任务 |
| 异步任务存储 | 异步任务状态、调度索引、Worker 租约的持久化（JDBC / Redis） |

## 三、抽象分层：五层心智模型

把框架想成五层，遇到"这个能力该放哪"的问题就不会乱：

```
运行层     Agent 运行时：推进轮次、审批、挂起恢复、持久化
  ↑
能力层     Tool / ToolGroup / MCP / Skills / Text2SQL / 搜索 / Wiki
  ↑
模型层     ChatModel / EmbeddingModel / ImageModel / RerankModel
  ↑
提示词层   Prompt / Message / Memory / 拦截器
  ↑
存储层     Document / VectorStore / DocumentStore / Memory / 各类持久化
```

**分层的关键约束**：能力层的东西最终都要落到模型层的 `Tool` 抽象上。也就是说 MCP 来的工具、
Skills 加载的能力、Text2SQL 的工具集，在模型眼里是同一类东西 —— 这是它能"组合"的原因。
判断一个新需求该怎么接，先问：**它最终是不是变成一个 Tool，然后挂到 Prompt 上？**

---

## 四、模型层：四个接口收口多厂商

框架用 `ChatModel`、`EmbeddingModel`、`ImageModel`、`RerankModel` 这组接口把不同厂商的能力
收口。对业务代码的意义是：

- 换供应商 = 换一个构造配置，业务侧调用方式不变
- 多厂商并存 = 注册多个实例，用路由层组合（见第九节）
- **同步与流式共用同一套提示词、参数、拦截器与上下文机制** —— 不是两套 API

最后一条是它一个比较实用的设计点：你不必为流式单独维护一套提示词拼装与拦截逻辑。

## 五、提示词层与工具挂载

### Prompt 的两种常见形态

| 形态 | 适用 |
|---|---|
| 简单提示词 | 一次性问答、单轮任务 |
| 带记忆的提示词 | 多轮对话，需要维护消息历史 |

工具通过提示词对象挂载上去，两条路径：

1. **注解声明式**：在业务方法上打工具注解（`@ToolDef` 声明工具名与描述，`@ToolParam` 声明
   参数名、描述、是否必填），然后用扫描器扫这个类，一次性挂上去。
2. **编程式**：工具来自运行时配置、插件系统或工作流节点时，用构造器动态拼装。

**选择标准**：工具集合在编译期就固定 → 注解式，可读性好；工具集合随配置或用户变化 → 编程式。

### 工具组（ToolGroup）：按输入动态挂载

工具一多，全量塞进请求体会同时推高成本和调用错误率。工具组解决这个：

- 一个工具组 = 一组工具 + 该组的系统提示词 + 一个匹配条件
- 匹配条件可以是"提示词里包含某些词"、"提示词匹配某个模式"，也可以是自定义策略
- **每一轮请求都基于最后一条用户消息重新匹配** —— 上一轮命中的工具不会泄漏到后续不相关的轮次
- **未命中的组不出现在请求体中**，所以省 token 是实打实的

配套的还有**渐进式工具发现**模块：不把所有工具一次暴露给模型，而是让模型先"搜"工具。
工具数量到几十上百个时，这个模式比工具组更合适。

## 六、拦截器：责任链与 order 语义

拦截器是框架里最容易被误用的部分。要点有四个：

### 1. 请求体在责任链末端才构建

Chat 请求的 Body 是在所有拦截器都执行到责任链末端之后才拼出来的。这带来一个容易踩的结果：

- 在 `intercept` 里调用 `chain.proceed()` **之前**修改提示词或对话参数，能直接影响最终请求
- 但请求规格对象（RequestSpec）**只含 URL、Header 和重试配置，不暴露 Body**
- 所以**拦截器改不了原始 Body**，要影响内容就得走提示词、参数这类结构化信息

看到"我在拦截器里改了 Body 但没生效"，先回想这条设计约束 —— 这不是 bug，是刻意的。

### 2. 按请求条件激活

拦截器可以带一个匹配条件注册，只有条件成立时该拦截器才进入责任链。条件是**在注册项运行到
责任链当前位置时**求值的，因此它能读到前面拦截器对上下文做的修改。这给了很实用的组合能力：
按租户、按套餐、按用户等级决定是否走审计、限流、降级逻辑。

### 3. order 决定顺序，且语义是"从小到大稳定排序"

- 每次请求按 order 升序做**稳定排序**；order 相同的保持注册顺序
- 框架给的默认值只是**推荐值，不是边界**：可观测性类给 `-1000`，普通拦截器给 `0`，
  工具组解析这类请求准备逻辑给 `1000`
- 应用可以用任意整数，把拦截器放到可观测之前或工具组解析之后

### 4. 全局注册

需要给"之后创建的所有 ChatModel"都挂上条件拦截器时，有全局注册入口。原来那个始终生效的
注册方法仍然保留，等价于一个条件恒真的注册项。

### 排序设计建议

| 位置 | 放什么 |
|---|---|
| 很小（先于默认可观测） | 需要在埋点之前就确定的信息，如租户解析、trace 上下文注入 |
| `0` 附近 | 业务侧常规处理：参数裁剪、敏感词、审计 |
| 大值（工具组解析之后） | 依赖"最终工具清单已确定"的逻辑，如工具级配额 |

## 七、运行层：Agent 运行时到底给什么

如果只做单轮问答，**不需要**运行层。一旦出现下面任意一条，才值得引入：

- 一轮回答里可能连续多次调用工具
- 某些工具执行前需要人工审批
- 长任务需要挂起，稍后从断点恢复
- 服务重启后不能丢执行状态

运行层提供的能力可以归成五块：

| 能力 | 说明 |
|---|---|
| 单轮推进 | 一个执行器负责推进一个 Agent 轮次，含工具调用 |
| 审批 | 工具执行前的人工确认环节 |
| 挂起与恢复 | 中途停下、之后接着跑 |
| 快照与版本 CAS | 状态可快照；用版本比对（CAS）避免并发覆盖 |
| 事件与中间件 | 统一的 Agent 事件流 + Middleware 扩展点 |

**落地的前提**：运行状态要持久化，所以必须同时准备好 JDBC 或 Redis 后端（运行存储模块）。
只引运行层不引存储层，等于把状态放在内存里，重启即失忆。

### 与子 Agent 的分工

- **运行层**：管理"当前这个 Agent 怎么一步步执行" —— 是执行模型
- **子 Agent 工具**：给主 Agent 一个"派活给后台、稍后取结果"的工具 —— 是能力（Tool）

两者常一起用，但不是同一件事。别因为名字像就以为引了一个就不需要另一个。

## 八、RAG 与知识组织的两条路线

### 路线一：传统 RAG（切片段检索）

链路固定为六步：

```
文档加载 → 解析 → 切分 → Embedding → 写入向量库 → 按问题检索 → （可选）Rerank → 交给对话模型
```

框架在这个链路上的组件分布：

| 环节 | 组件 |
|---|---|
| 文档模型 | 文档、向量数据、元数据 |
| 文本处理 | Loader、Parser、Splitter、文档提取器 |
| 向量化 | 各厂商 Embedding 模型 |
| 存储 | 十种以上向量库适配 |
| 检索 | 检索包装器、文档存储、向量存储 |
| 排序优化 | Rerank 模型 |

### 路线二：LLM Wiki（层级导航）

把知识组织成带**路径、标题、摘要、正文、子页面**的树，而不是切成互不相干的扁平片段。
机制是渐进式披露：

- 先只把**当前可用子页面的摘要**给模型看
- 模型判断需要哪一页，再用工具按路径读取该页内容（`get_wiki_content(path)`）

**代价与收益很清楚**：结构化程度高的文档体系（章节关系明确、目录稳定）用 Wiki 路线，
上下文占用显著更省；文档本身散乱、没有目录结构的，传统 RAG 更实在。

两条路线不互斥，Wiki、RAG、网络搜索、Skills 可以一起用 —— 让模型自己决定查哪一路。

## 九、路由与可观测

### 模型路由

把多个模型实例组合成一个路由模型，支持的策略：

- 最少活跃数负载均衡
- 加权随机负载均衡
- 标签路由（按标签把请求导向特定模型）
- 自动重试
- 熔断与半开恢复
- 运行时指标统计

路由同时覆盖对话模型与 Embedding 模型。**适用场景**：多供应商容灾、按租户分级（高价值
租户走强模型）、灰度新模型、控成本（低价模型兜底）。

### 可观测

基于 OpenTelemetry，支持链路追踪与指标采集，可用系统属性切换导出方式：日志、OTLP 或自定义
导出器，另可设置指标导出间隔。可观测模块还支持把数据持久化到 JDBC。

**两个实务提醒**：

1. 这些是**系统属性**，要放在 JVM 启动参数里（`-D...`），放在应用的配置文件里不一定读得到
2. 导出间隔别设太密，指标采集本身有成本；先按默认跑一版，看实际开销再调

## 十、Spring Boot 接入的覆盖范围

自动配置目前覆盖两块：

| 类别 | 覆盖 |
|---|---|
| 对话模型 | OpenAI、Qwen、Ollama、DeepSeek |
| 向量存储 | 阿里云、Chroma、Elasticsearch、OpenSearch、腾讯云 |

**两点必须知道**：

1. 覆盖面**小于**框架总能力。上面没列的模型或向量库，仍然可以手动构造实例使用，
   只是没有自动配置帮忙读配置。
2. 配置项的**准确键名以 starter 里那个版本的自动配置元数据为准**。可靠做法：
   在依赖里找到该 starter，读它的 `spring-configuration-metadata.json` 或配置属性类，
   不要照抄二手示例 —— 键名跨版本改过。

## 十一、概念对照表（迁移用）

从别的框架或通用术语迁过来时，按下表对应：

| 本框架的说法 | 通用叫法 | 备注 |
|---|---|---|
| ChatModel | LLM 客户端 / Chat Client | 同步与流式同一套抽象 |
| Prompt | 提示词对象 | 工具挂在它上面 |
| Tool / ToolGroup | 函数调用 / 工具集 | 工具组多了"按输入命中"这一层 |
| 拦截器（责任链） | Middleware / Filter | order 语义与"末端构建 Body"是两个关键差异 |
| Agent 运行时 | Agent Executor / Graph Runner | 带快照、CAS、审批 |
| 文档 / 向量存储 | RAG 组件 | 组件划分比多数框架更细 |
| LLM Wiki | 层级知识库 | 与扁平片段检索相对 |
| Skills | 技能包 / 渐进式能力披露 | 文件系统加载 |
| MCP 客户端 | 工具协议客户端 | 外部工具转成本框架 Tool |

## 十二、看源码时的建议顺序

想快速建立准确认知，按这个顺序读比重头读文档快：

1. 根 `pom.xml` 的模块列表与 `revision` 属性 —— 先确认版本与模块全集
2. 核心模块里的几个接口（模型、提示词、工具）—— 建立抽象边界
3. 拦截器与请求规格相关类 —— 理解"末端构建 Body"的约束
4. 运行层的事件与快照相关类 —— 理解状态模型
5. 你实际要用的那个适配模块 —— 看配置项与构造方式

**核对纪律**：任何类名与方法签名，都以你**本机实际拉到的那个版本**的源码为准。
本文件描述的是结构与机制，结构比签名稳定得多。
