# 三剪客 · 开源可视化数据库与多维表格

一堆人同时在改同一张表，还要按不同视角看同一批数据——这是表格软件和数据库之间的空档。APITable 填的就是这个空档：看起来是电子表格（网格视图、拖拽列、行内编辑），底下是数据库（表结构、行级与列级权限、全栈 API、自动化与仪表盘）。同一份数据你可以开网格、画廊、看板、甘特、日历、脑图等不同视图给不同的人看。

它对你最实际的两个价值：**一是能把业务数据交给非技术同事自己维护**，不用为每个小需求排期改系统；**二是它的 API 面板能直接把"这张表"变成接口**，嵌进自己的软件里当后台配置中心或数据底座。

**上游项目**：`APITable`　**仓库**：https://github.com/apitable/apitable

## 什么时候用 / 不用

**用它**：

- 团队想要一个能自托管的在线多维表格 / 轻量项目管理 / 客户线索表，且数据不出自己机房。
- 业务方需要可视化维护数据，IT 只需要把这张表通过 API 接进系统，不必为每次字段调整发版。
- 要把一张视图以"镜像"的方式分享出去，只让人看到自己那几行（行级权限）。
- 需要把表格能力嵌进已有产品界面里（嵌入视图 / 分享链接）。
- 需要一个可扩展的低代码底座：自定义字段类型、自定义公式、自动化机器人、仪表盘。

**不要用它**：

- 只要一个纯本地的个人表格文件，或只需要做数据透视和计算——用电子表格软件或数据分析工具更直接。
- 需要强事务、复杂 SQL、高并发写入的在线交易型数据库——它是面向协作的表格层，不是 OLTP 数据库的替代品。
- 组织内有硬性的信创 / 合规清单要求，且该清单与本项目技术栈不匹配——技术栈是前端 TypeScript 系加后端 Java 系，要按自己的准入标准先评估。
- 只想试用一下功能——官方有托管版本可用，不必先折腾自托管。
- 机器只有 2 核 4G 却想承载团队日常使用——部署要求见下，资源不够会以"打开慢、操作卡"的形式表现出来。

## 安装

前置条件（官方明示）：装有 Docker 与 Docker Compose v2 的机器；建议 4 CPU / 8GB 内存以上；一个带 curl 等基础工具的 bash 环境。原生 arm64（Apple Silicon）容器镜像尚不完善，性能可能很差。

### 方式一：官方安装脚本（推荐）

```bash
curl https://apitable.github.io/install.sh | bash
```

跑完用浏览器访问 `http://localhost:80`。服务全部启动可能需要几分钟。

### 方式二：all-in-one 镜像（仅用于演示或测试）

```bash
sudo docker run -d -v ${PWD}/.data:/apitable -p 80:80 --name apitable apitable/all-in-one:latest
```

这个镜像只有 amd64（x86_64）；在 arm64 或 Apple Silicon 上可能出现很差的性能。**不要用于企业或生产环境。**

### 方式三：直接用仓库里的 Compose 编排自行部署

仓库自带 `docker-compose.yaml` 与一份 `.env` 参数模板，编排里包含 Web 服务、后端服务、Room 服务、数据总线服务、网关、MinIO、MySQL、Redis、RabbitMQ 以及两个初始化容器。做法是先按自己的环境改好 `.env`（口令、端口、时区、对外域名等都是变量），再在仓库根目录执行：

```bash
docker compose --env-file .env -f docker-compose.yaml up -d
```

外层网关默认把宿主机 80 / 443 映射进容器（对应 `.env` 里的 `NGINX_HTTP_PORT` / `NGINX_HTTPS_PORT`）。**具体变量名与默认值以仓库当前 `.env` 与 `docker-compose.yaml` 为准。**

### 方式四：本地开发环境

仓库提供开发指南，路径见仓库 `docs/` 下的贡献文档；开发模式涉及前端与后端两套工具链，日常使用请优先走容器方式。

## 常用操作

```bash
# 1. 官方脚本一键安装，装完访问 http://localhost:80
curl https://apitable.github.io/install.sh | bash

# 2. 用仓库自带的 Compose 起停（在仓库根目录，参数文件与编排文件按实际路径填）
docker compose --env-file .env -f docker-compose.yaml up -d
docker compose -f docker-compose.yaml down

# 3. 看服务日志与状态
docker compose -f docker-compose.yaml ps
docker compose -f docker-compose.yaml logs -f

# 4. 只重建某个组件（例如后端），以实际服务名为准
docker compose -f docker-compose.yaml up -d --force-recreate backend-server
```

进入界面之后的典型动作：

1. **建空间与表**：以"空间"为隔离单位组织表，在一个空间里可以建多张表并相互关联，跨表关联可以做到无限层级。
2. **换视图**：同一张表可以开网格、画廊、看板、甘特、日历、脑图等视图；视图可以切成"镜像"，从而实现只让别人看到符合条件的行。
3. **配权限**：列级权限、行级权限（通过镜像视图）、文件夹与文件权限分层设置。
4. **取 API**：点界面右上角的 API 按钮打开 API 面板，面板会直接给出当前表的调用示例。查询用的是它自己的类 SQL 查询语言，具体语法以官方开发者文档为准。
5. **做自动化**：用自动化机器人按触发条件执行动作；也可以与外部的 n8n / Zapier 之类编排工具对接。
6. **嵌出去**：分享视图或以 HTML 片段嵌入到别的页面里。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 访问 `http://localhost` 打不开或一直转圈 | 服务还在启动中，尤其是首次初始化数据库 | 等几分钟再看；用 `docker compose ps` 确认初始化容器已成功结束、后端健康检查通过 |
| 在 Apple Silicon / arm64 上慢到不可用 | 原生 arm64 镜像未就绪，跑的是模拟 | 换 amd64 机器部署；官方也明确不建议在此架构上跑 |
| 数据看起来"消失了" | `DATA_PATH` 是相对路径（默认 `.`），换目录启动后挂载点变了 | 把 `DATA_PATH` 改成绝对路径的大容量目录，并确认 MySQL / MinIO / Redis / RabbitMQ 的卷都在它下面 |
| 上传的文件/图片显示不出来 | 存储相关配置与对外访问地址不匹配（MinIO 凭据、桶名、对外 endpoint、网关转发之一没对齐） | 对照 `.env` 逐项核对存储相关变量，再确认网关能把存储请求转发到 MinIO |
| 改了口令后组件起不来、日志报认证失败 | 组件数据卷已按旧口令初始化，与新的 `.env` 不一致 | 要么保留旧口令，要么清掉对应数据卷重新初始化；改口令前先备份 |
| 从别的机器通过域名访问，登录或实时协作异常 | 对外域名、跨域来源、Socket 地址等仍指向容器内网地址或 `localhost` | 把对外域名与跨域相关变量改成真实对外地址，并让反向代理正确转发 |
| 初始化容器反复失败 | MySQL 未就绪，或初始化参数与数据库实际状态不符 | 先单独确认 MySQL 健康，再重跑初始化容器；`init-db` 的动作模式按需选择 |
| 注册被要求校验而收不到邮件 | 邮件相关配置默认未启用 | 按需配置邮件服务；测试环境可调整注册校验相关开关，生产务必打开 |

## 能力边界

**覆盖**：

- 自托管的部署与运维：安装脚本、演示用 all-in-one 镜像、仓库自带的 Compose 编排、本地开发环境。
- 表格与数据库混合能力：表的增删改查、字段操作（排序、筛选、分组、隐藏、行高）、多种视图、无限跨表关联。
- 协作与权限：多人实时协作、行级 / 列级 / 文件夹级权限、镜像视图做行权限。
- 对外集成：全栈 API（数据与元数据）、API 面板、类 SQL 查询语言、表单、嵌入与分享、自动化机器人、仪表盘、
  与外部编排工具的对接、可扩展的组件体系。
- 存储与运行形态：容器化部署、对象存储接入、多语言界面。

**不覆盖**：

- 不做通用 OLTP 数据库：不替你做强事务、复杂 SQL 与超高并发写入的场景设计。
- 不提供托管服务本身：托管版本是另一条产品线，本包只讲自托管。
- 不负责服务器采购、域名备案、证书申请与网络规划。
- 不替你写业务集成代码；API 怎么用、数据怎么建模仍需自己设计。
- 不保证第三方集成（外部编排工具、第三方登录等）的开箱可用性，需逐个验证。

## 依赖条件

- Docker 与 Docker Compose v2；建议 4 CPU / 8GB 内存以上；bash 环境带 curl 等基础工具。
- 一套完整部署会拉起 Web、后端、Room、数据总线、网关、MinIO、MySQL、Redis、RabbitMQ 等容器，另有初始化容器。
- 磁盘要按数据量与附件量规划；附件默认存放在对象存储容器里。
- 对外提供服务时需要域名、反向代理或网关配置，以及正确的对外访问地址变量。
- 邮件、短信、第三方登录等能力需要各自的账号与配置，默认不启用。

## 已知限制

- 架构支持不对称：amd64 是主路径，原生 arm64 镜像未就绪，Apple Silicon 上性能差。
- 部署组件多、变量多，`.env` 里任何一项与运行环境不匹配都可能表现为"页面能用但某个功能不对"。
- 对外域名与存储 endpoint 这类配置错了不会报错，只会在客户端表现异常，排查成本较高。
- 演示用 all-in-one 镜像只适合试功能，不适合生产。
- 类 SQL 查询语言的语法和能力边界以官方文档为准，不要按标准 SQL 的预期去写。

## 自检清单

执行前：

- [ ] 确认机器架构是 amd64，CPU / 内存 / 磁盘满足建议值。
- [ ] 确认 Docker 与 Compose v2 可用，80 / 443 端口未被占用或有替代映射。
- [ ] 确认 `.env` 里的全部口令已改为自己的强口令，且不会提交到仓库。
- [ ] 确认 `DATA_PATH` 是绝对路径且磁盘充足。
- [ ] 明确对外访问地址（域名或 IP），并准备好反向代理或网关配置。

执行后：

- [ ] 浏览器能打开首页，能完成注册与登录。
- [ ] 新建一张表，加几种字段类型，切一次视图，刷新后数据仍在。
- [ ] 上传一张图片并在表内正常显示（证明对象存储与转发链路通畅）。
- [ ] 从另一台机器通过对外地址访问，验证实时协作与附件下载均正常。
- [ ] `docker compose down` 后再 `up`，数据仍在。
- [ ] 已按需配置邮件等服务，且生产环境未留测试用的宽松开关。
