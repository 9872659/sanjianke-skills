# 核心概念：模块分层与机制

> 本文件讲的是 **Java 生态 AI Agent 框架这一类东西的结构与机制**，用来建立判断依据，
> 不绑定任何某一个具体实现。
>
> **代码与坐标的书写约定**（本包三份文件统一遵守）：
>
> | 占位 | 含义 |
> |---|---|
> | `<your-groupId>` / `<your-artifactId>` | 你实际使用的那套框架的 Maven 坐标，填你自己的值 |
> | `<base-pkg>` | 你实际的 Java 包名根，例如 `com.example.agent` |
> | `<VERSION>` | 你核对通过的那个版本号 |
>
> 类名与接口名是**这一类框架里常见的概念标识**，写法接近但可能与你手上的实现有出入；
> **方法签名一律以你本机实际引入的那个版本为准**。结构比签名稳定得多，本文件讲结构。

---

## 一、这一层能力的定位

一句话：**把「调模型」升级成「可编排的 Agent 能力」，同时不把业务绑死在某个应用框架或某个模型供应商上。**

它和「一个大而全的 AI 应用平台」的区别在取舍方向：

| 取向 | 表现 |
|---|---|
| 拆得开 | LLM 调用、工具、Agent 运行时、RAG、向量存储、图像、音频、MCP、Skills、Text2SQL 各自独立成模块 |
| 不强绑 | 核心模块在普通 Java 程序里就能用，不是必须挂在 Spring 容器上 |
| 可替换 | 模型、向量库、搜索引擎都以接口形式接入，能换实现而不动上层业务 |
| 组件齐全 | RAG 从文档解析到 Rerank 都有现成件，不用自己拼胶水 |

适合的场景：智能客服、企业知识库、智能问数、Agent 工作流、模型网关、插件式工具系统，
以及**一个 Java 服务要同时接多个模型供应商**的情况。

**什么时候不需要它**：只是"调一次接口拿个回答"。一个 HTTP 客户端加一个 JSON 解析就够，
引框架反而多背一份依赖与升级负担。框架的价值在多模型统一、工具编排、RAG 链路、
运行时状态这些**复杂性真实存在**的地方（判断标准见 `selection-and-troubleshooting.md`）。

## 二、模块地图

按职责分成五组来看，比按字母顺序背模块名有用得多。

### 1. 地基

| 模块 | 职责 |
|---|---|
| 核心模块 | 最基础的抽象：Chat、Prompt、Message、Tool、Memory、Document、Store、可观测接口 |
| 应用框架启动器 | Spring Boot 自动配置，覆盖常用模型与向量存储 |
| 可观测模块 | OpenTelemetry 的 Span 与 Metric 导出，支持把数据落到 JDBC |

### 2. 模型适配层

这一类框架的做法是：**每种能力一个接口，每个供应商一个适配模块**。

| 能力 | 典型覆盖 |
|---|---|
| 对话模型 | OpenAI 兼容接口（一个适配吃下所有兼容端点）、Qwen、Ollama、DeepSeek、LiteLLM |
| Embedding | OpenAI 兼容、Ollama、Qwen |
| 图像 | OpenAI 兼容、Gemini、阿里云、火山引擎 |
| 视频 | 异步视频生成与编辑：阿里云百炼、火山引擎方舟 |
| 音频 | 语音识别与语音合成：阿里云、腾讯云、火山引擎 |
| OCR | 百度智能云、MinerU |
| Rerank | 默认实现与供应商实现 |

> **「OpenAI 兼容」是这一层最重要的一列。** 只要目标服务对外暴露 OpenAI 协议，
> 一个适配模块就能吃下它 —— 换供应商从"接一个新 SDK"退化成"改一个 base_url"。
> 这是把模型侧统一指向一个兼容网关（本包用 `https://api.a7w.cn/api/v1`）能成立的前提。
>
> **注意「异步」二字**：视频一类是长耗时任务，走的是**提交后轮询**的协议，不是同步返回。
> 这条链路由异步任务模块 + 异步任务存储模块（JDBC / Redis）承担。

### 3. 知识与存储层

| 模块 | 职责 |
|---|---|
| 向量存储 | Redis、Qdrant、Chroma、Pgvector、MariaDB、Milvus、OpenSearch、Elasticsearch、各类云托管 |
| 搜索引擎 | Lucene、Elasticsearch，以及通用搜索服务接口 |
| 文档提取 | 从 PDF、Office、HTML、邮件、压缩包、输入流和 URL 中提取 Markdown 风格内容 |

### 4. 能力层（Agent 的"手脚"）

| 模块 | 职责 |
|---|---|
| 通用工具集 | 文件系统、Shell、Grep、Glob、WebFetch、Python、JavaScript |
| 工具检索 | 渐进式工具发现，支持内存与自定义搜索提供方 |
| MCP 客户端 | 连外部 MCP Server，把远程工具包装成本框架的 Tool |
| Skills | 基于文件系统的技能加载与渐进式披露 |
| Skills 包存储 | 技能包的版本化存储（文件系统或对象存储） |
| Skills 沙箱 | 隔离执行技能脚本的运行时聚合，含多种沙箱实现 |
| 子 Agent | 通用 Subagent 工具，提供后台任务执行与结果获取 |
| 智能问数 | Text2SQL 工具集，含表结构渐进披露、只读校验、拦截器链 |
| 网络搜索 | 多家搜索服务与自定义搜索提供方 |
| 层级 Wiki | 把知识组织成可导航的 Wiki 树，支持按路径读取与渐进式披露 |

### 5. 运行层

| 模块 | 职责 |
|---|---|
| Agent 运行时 | 持久化的 Agent 执行：运行状态、快照、版本 CAS、审批、Middleware、事件 |
| Agent 存储 | 运行、命令、事件与产物的持久化（JDBC / Redis） |
| 异步任务 | 可靠跟踪与调度供应商侧的异步任务 |
| 异步任务存储 | 异步任务状态、调度索引、Worker 租约的持久化（JDBC / Redis） |

## 三、抽象分层：五层心智模型

把整套东西想成五层，遇到"这个能力该放哪"的问题就不会乱：

```
运行层     Agent 运行时：推进轮次、审批、挂起恢复、持久化
  ↑
能力层     Tool / ToolGroup / MCP / Skills / Text2SQL / 搜索 / Wiki
  ↑
模型层     ChatModel / EmbeddingModel / ImageModel / RerankModel
  ↑
提示词层   Prompt / Message / Memory / 拦截器
  ↑
存储层     Document / VectorStore / DocumentStore / Memory / 各类持久化
```

**分层的关键约束**：能力层的东西最终都要落到模型层的 `Tool` 抽象上。MCP 来的工具、
Skills 加载的能力、Text2SQL 的工具集，在模型眼里是同一类东西 —— 这是它能"组合"的原因。

所以判断一个新需求怎么接，先问一句：**它最终是不是变成一个 Tool，然后挂到 Prompt 上？**
是，就走能力层；不是（比如是上下文的组织方式），就往提示词层或存储层放；
再不是（比如是"这一轮怎么跑"），才动运行层。

## 四、模型层：四个接口收口多供应商

用 `ChatModel`、`EmbeddingModel`、`ImageModel`、`RerankModel` 这组接口把不同供应商的能力收口。
对业务代码的意义是三件事：

- **换供应商 = 换一个构造配置**，业务侧调用方式不变
- **多供应商并存 = 注册多个实例**，用路由层组合（见第九节）
- **同步与流式共用同一套提示词、参数、拦截器与上下文机制** —— 不是两套 API

最后一条是这类框架里比较实用的一个设计点：你不必为流式单独维护一套提示词拼装与拦截逻辑。
反过来，如果你发现自己的同步与流式行为不一致，第一嫌疑就是**你手工绕开了这套共用机制**
（排查手法见排错文件的第三类）。

## 五、提示词层与工具挂载

### Prompt 的两种常见形态

| 形态 | 适用 |
|---|---|
| 简单提示词 | 一次性问答、单轮任务 |
| 带记忆的提示词 | 多轮对话，需要维护消息历史 |

工具通过提示词对象挂载上去，两条路径：

1. **注解声明式**：在业务方法上打工具注解（一个注解声明工具名与描述，
   参数注解声明参数名、描述、是否必填），然后用扫描器扫这个类，一次性挂上去。
2. **编程式**：工具来自运行时配置、插件系统或工作流节点时，用构造器动态拼装。

**选择标准**：工具集合在编译期就固定 → 注解式，可读性好；
工具集合随配置或用户变化 → 编程式。

### 工具组（ToolGroup）：按输入动态挂载

工具一多，全量塞进请求体会同时推高成本和调用错误率。工具组解决这个：

- 一个工具组 = 一组工具 + 该组的系统提示词 + 一个匹配条件
- 匹配条件可以是"提示词里包含某些词"、"提示词匹配某个模式"，也可以是自定义策略
- **每一轮请求都基于最后一条用户消息重新匹配** —— 上一轮命中的工具不会泄漏到后续不相关的轮次
- **未命中的组不出现在请求体中**，所以省 token 是实打实的

配套的还有**渐进式工具发现**：不把所有工具一次暴露给模型，而是让模型先"搜"工具。
工具数量到几十上百个时，这个模式比关键词命中更合适。

## 六、拦截器：责任链与 order 语义

拦截器是这一层最容易被误用的部分。要点有四个。

### 1. 请求体在责任链末端才构建

Chat 请求的 Body 是在所有拦截器都执行到责任链末端之后才拼出来的。这带来一个容易踩的结果：

- 在 `intercept` 里调用 `chain.proceed()` **之前**修改提示词或对话参数，能直接影响最终请求
- 但请求规格对象（RequestSpec）**只含 URL、Header 和重试配置，不暴露 Body**
- 所以**拦截器改不了原始 Body**，要影响内容就得走提示词、参数这类结构化信息

看到"我在拦截器里改了 Body 但没生效"，先回想这条设计约束 —— 这不是 bug，是刻意的：
把可改的东西收敛到结构化的提示词与参数上，才能在同步/流式两条路径上得到一致行为。

### 2. 按请求条件激活

拦截器可以带一个匹配条件注册，只有条件成立时该拦截器才进入责任链。条件是
**在注册项运行到责任链当前位置时**求值的，因此它能读到前面拦截器对上下文做的修改。
这给了很实用的组合能力：按租户、按套餐、按用户等级决定是否走审计、限流、降级逻辑。

### 3. order 决定顺序，语义是"从小到大稳定排序"

- 每次请求按 order 升序做**稳定排序**；order 相同的保持注册顺序
- 常见的约定值只是**推荐值，不是边界**：可观测性类给 `-1000`，普通拦截器给 `0`，
  请求准备逻辑（工具组解析这类）给 `1000`
- 应用可以用任意整数，把拦截器放到可观测之前或请求准备之后

### 4. 全局注册

需要给"之后创建的所有 ChatModel"都挂上条件拦截器时，要有全局注册入口。
给单个实例注册只对该实例生效，这是排查"拦截器不生效"的第二个高频原因。

### 排序设计建议

| 位置 | 放什么 |
|---|---|
| 很小（先于默认可观测） | 需要在埋点之前就确定的信息，如租户解析、trace 上下文注入 |
| `0` 附近 | 业务侧常规处理：参数裁剪、敏感词、审计 |
| 大值（请求准备之后） | 依赖"最终工具清单已确定"的逻辑，如工具级配额 |

## 七、运行层：Agent 运行时到底给什么

如果只做单轮问答，**不需要**运行层。一旦出现下面任意一条，才值得引入：

- 一轮回答里可能连续多次调用工具
- 某些工具执行前需要人工审批
- 长任务需要挂起，稍后从断点恢复
- 服务重启后不能丢执行状态

运行层提供的能力可以归成五块：

| 能力 | 说明 |
|---|---|
| 单轮推进 | 一个执行器负责推进一个 Agent 轮次，含工具调用 |
| 审批 | 工具执行前的人工确认环节 |
| 挂起与恢复 | 中途停下、之后接着跑 |
| 快照与版本 CAS | 状态可快照；用版本比对（CAS）避免并发覆盖 |
| 事件与中间件 | 统一的 Agent 事件流 + Middleware 扩展点 |

**落地的前提**：运行状态要持久化，所以必须同时准备好 JDBC 或 Redis 后端。
只引运行层不引存储层，等于把状态放在内存里，**重启即失忆**。

### 与子 Agent 的分工

- **运行层**：管理"当前这个 Agent 怎么一步步执行" —— 是执行模型
- **子 Agent 工具**：给主 Agent 一个"派活给后台、稍后取结果"的工具 —— 是能力（Tool）

两者常一起用，但不是同一件事。别因为名字像就以为引了一个就不需要另一个。

## 八、RAG 与知识组织的两条路线

### 路线一：传统 RAG（切片段检索）

链路固定为六步：

```
文档加载 → 解析 → 切分 → Embedding → 写入向量库 → 按问题检索 →（可选）Rerank → 交给对话模型
```

这条链路上各组件的分布：

| 环节 | 组件 |
|---|---|
| 文档模型 | 文档、向量数据、元数据 |
| 文本处理 | Loader、Parser、Splitter、文档提取器 |
| 向量化 | Embedding 模型（走兼容端点即可，不必自部署） |
| 存储 | 各种向量库适配 |
| 检索 | 检索包装器、文档存储、向量存储 |
| 排序优化 | Rerank 模型 |

### 路线二：层级 Wiki（导航式检索）

把知识组织成带**路径、标题、摘要、正文、子页面**的树，而不是切成互不相干的扁平片段。
机制是渐进式披露：

- 先只把**当前可用子页面的摘要**给模型看
- 模型判断需要哪一页，再用工具按路径读取该页内容（例如 `get_wiki_content(path)`）

**代价与收益很清楚**：结构化程度高的文档体系（章节关系明确、目录稳定）用 Wiki 路线，
上下文占用显著更省；文档本身散乱、没有目录结构的，传统 RAG 更实在。

两条路线不互斥，Wiki、RAG、网络搜索、Skills 可以一起用 —— 让模型自己决定查哪一路。

## 九、路由与可观测

### 模型路由

把多个模型实例组合成一个路由模型，常见策略：

- 最少活跃数负载均衡
- 加权随机负载均衡
- 标签路由（按标签把请求导向特定模型）
- 自动重试
- 熔断与半开恢复
- 运行时指标统计

路由通常同时覆盖对话模型与 Embedding 模型。**适用场景**：多供应商容灾、
按租户分级（高价值租户走强模型）、灰度新模型、控成本（低价模型兜底）。

**和"换 model 字符串"的关系**：如果一个网关已经把 75 个在架模型收口在一个 base_url 后面，
那么"换供应商"这件事在网关侧就解决了，路由层要解决的是**同一供应商内的多实例容灾与分级** ——
两件事不要混在一起设计。

### 可观测

基于 OpenTelemetry，支持链路追踪与指标采集，可用系统属性切换导出方式：日志、OTLP 或自定义
导出器，另可设置指标导出间隔。也可把数据持久化到 JDBC。

**两个实务提醒**：

1. 这类开关常是**系统属性**，要放在 JVM 启动参数里（`-D...`），放应用的配置文件里不一定读得到
2. 导出间隔别设太密，指标采集本身有成本；先按默认跑一版，看实际开销再调

## 十、Spring Boot 接入的覆盖范围

自动配置通常只覆盖"最常用"的那一档，例如：

| 类别 | 典型覆盖 |
|---|---|
| 对话模型 | OpenAI 兼容、Qwen、Ollama、DeepSeek |
| 向量存储 | 云托管、Chroma、Elasticsearch、OpenSearch |

**两点必须知道**：

1. 覆盖面**小于**框架总能力。上面没列的模型或向量库，仍然可以手动构造实例使用，
   只是没有自动配置帮忙读配置项。
2. 配置项的**准确键名以你依赖里那个版本的自带元数据为准**。可靠做法：
   在依赖里找到该启动器，读它的 `META-INF/spring-configuration-metadata.json`
   或配置属性类，**不要照抄二手示例** —— 键名跨版本改过。

## 十一、概念对照表（迁移用）

从别的框架、别的语言、或通用术语迁过来时，按下表对应：

| 本层的说法 | 通用叫法 | 备注 |
|---|---|---|
| ChatModel | LLM 客户端 / Chat Client | 同步与流式同一套抽象 |
| Prompt | 提示词对象 | 工具挂在它上面 |
| Tool / ToolGroup | 函数调用 / 工具集 | 工具组多了"按输入命中"这一层 |
| 拦截器（责任链） | Middleware / Filter | order 语义与"末端构建 Body"是两个关键差异 |
| Agent 运行时 | Agent Executor / Graph Runner | 带快照、CAS、审批 |
| Document / VectorStore | RAG 组件 | 组件划分通常比"一个大而全的类"更细 |
| 层级 Wiki | 层级知识库 | 与扁平片段检索相对 |
| Skills | 技能包 / 渐进式能力披露 | 基于文件系统加载 |
| MCP 客户端 | 工具协议客户端 | 外部工具转成本框架 Tool |
| 子 Agent 工具 | 后台任务派发 | 是 Tool，不是执行模型 |

## 十二、读源码时的建议顺序

想快速建立准确认知，按这个顺序读比重头读文档快：

1. **根构建文件的模块列表** —— 先确认你拿到的是哪一套模块全集
2. **核心模块里的几个接口**（模型、提示词、工具）—— 建立抽象边界
3. **拦截器与请求规格相关类** —— 理解"末端构建 Body"的约束
4. **运行层的事件与快照相关类** —— 理解状态模型
5. **你实际要用的那个适配模块** —— 看配置项与构造方式

**核对纪律**：任何类名与方法签名，都以你**本机实际引入的那个版本**的源码为准。
本文件描述的是结构与机制，结构比签名稳定得多。
