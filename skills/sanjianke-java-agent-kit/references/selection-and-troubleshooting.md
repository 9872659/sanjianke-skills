# 选型对比与排错

> 两部分：**A. 框架怎么选**（给判断维度与代价，不给结论）；**B. 出了事怎么查**（按症状定位）。
>
> 对比部分的定位是**通用工程判断**，不针对任何一方某个具体版本的行为差异。
> 任何一套 Java Agent 框架都在快速演进，结论要自己复核。

---

# A. 选型

## A0. 先把候选摆清

Java 生态里做 AI Agent 能力，实际就那么几条路：

| 候选 | 一句话定位 |
|---|---|
| **Spring AI** | Spring 官方体系的 AI 抽象层，靠自动配置与 Spring Boot 生态吃饭 |
| **LangChain4j** | 受 LangChain 思路影响的 Java 库，以声明式接口和丰富的集成为卖点 |
| **模块化的独立 Agent 框架** | 独立于应用框架、按能力拆模块、自带 Agent 运行时与 RAG 组件的那一类 |
| **自己拼** | HTTP 客户端 + JSON 解析 + 自己的编排代码 |

**注意第三条不是某一个具体项目，而是一个类别。** 这一类的共同特征是：核心模块不强绑容器、
模型与向量库以接口收口、RAG 与运行时按模块提供。你评估候选时，先问它属不属于这一类，
再拿下面六个维度去比对。

**自己拼什么时候是对的**：只需要"调一次模型拿个回答"。一个 HTTP 客户端加一个 JSON 解析就够，
引框架反而增加依赖与升级负担。框架的价值在多模型统一、工具编排、RAG 链路、运行时状态这些
**复杂性真实存在**的地方。

---

## A1. 六个判断维度

不要问"谁最好"。按这六项各自打分，再看你的短板在哪一项。

### 1. 模块分层与抽象边界

| 看什么 | 为什么重要 |
|---|---|
| 能力是按模块拆开，还是集中在一个大而全的入口 | 拆得开才可能"按需取用"，不被一个框架绑住整条技术栈 |
| 模型、向量库、搜索引擎是不是接口形式接入 | 接口化才谈得上"换实现不动上层业务" |
| 有没有清晰的分层（模型层 / 提示词层 / 能力层 / 运行层 / 存储层） | 分层清楚，新人建立认知快，出问题能定位到层 |

**判断动作**：拿你真实的一个需求（比如"给客服加一个查订单的工具"），在候选框架里找
"这个能力该写在哪一层"。找得到、且只有一种合理答案 → 分层清楚；三种写法都能糊上去 → 边界模糊。

### 2. 成本

成本不只是 token 钱，是四笔账：

| 成本项 | 怎么估 |
|---|---|
| 接入成本 | 非 Spring 工程引 Spring 体系的抽象层会明显更费劲；反之亦然 |
| 学习成本 | 抽象层次越多、链路越长，出错时定位要往下钻的层数越多 |
| 迁移成本 | 见 A4 清单 —— 最容易被低估的一项 |
| 运行成本 | 工具清单占的 token、工具调用循环的轮次上限、可观测采集的开销 |

**省钱的两个杠杆和一个前提**：

- 杠杆一：**模型分级**。摘要/分类用便宜的模型，推理/评审用强的。
  这要求"换模型"的成本足够低 —— 如果模型侧统一收口在一个 OpenAI 兼容的 base_url 后面，
  换模型就是换一个 `model` 字符串，同一把 Key、同一份账单。
- 杠杆二：**工具可见范围**。工具一多，光工具清单本身就能吃掉可观的输入 token，
  同时推高模型选错的概率。按输入动态挂载工具组，或改用渐进式工具发现。
- 前提：**别把"换模型"做成需要改代码、改配置、重新部署的动作**。那样杠杆就用不起来。

### 3. 生态

| 看什么 | 说明 |
|---|---|
| 模型适配广度 | 是否覆盖你实际要用的那几家（含图像、视频、音频、OCR 这类多模态） |
| 向量库适配广度 | 是否支持你已经在运维的那套向量库 —— **能用现有的就别新建中间件** |
| 应用框架集成 | 有没有 starter / 自动配置，覆盖面到哪一档 |
| 与 Spring 版本节奏的耦合 | 耦合强意味着升级时要做整体回归 |

**一个减法**：如果你的模型侧统一走 OpenAI 兼容端点（把 base_url 指向
`https://api.a7w.cn/api/v1`），那么"模型适配广度"这一项的权重可以降低 ——
一个兼容适配就吃下了所有在架模型，不需要框架为每家厂商各写一个适配模块。
此时的权重应该转移到**向量库适配**与**运行时能力**上。

### 4. 运行时能力

这是分水岭：**只做单轮问答的，不需要运行时；一旦要工具编排，运行时能力就是硬指标。**

| 能力 | 没有它会怎样 |
|---|---|
| 单轮推进（含工具调用循环） | 你得自己写循环，还得自己处理失败重试与轮次上限 |
| 工具审批 | 高危工具没有人工确认环节，等于没有防线 |
| 挂起与恢复 | 长任务只能一直占着连接，或者干脆做不了 |
| 快照与版本 CAS | 重启丢状态；并发推进同一个会话时互相覆盖 |
| Middleware 与统一事件 | 想插一段逻辑（审计、计费、脱敏）只能改框架代码 |

**判断动作**：写下你三个月内一定会有的那个最复杂流程，问"它需要跨请求保存状态吗"。
需要 → 运行时能力是选型的必选项，不是加分项。

### 5. 可观测

| 看什么 | 说明 |
|---|---|
| 是否内建链路追踪与指标 | 基于 OpenTelemetry 的可以直接接你现有的后端 |
| 导出方式是否可切换 | 日志 / OTLP / 自定义导出器 |
| 开关的形式 | **如果是系统属性，就得放 JVM 启动参数里**，放 yaml 里不一定读得到 |
| 采集开销是否可控 | 导出间隔、采样率要能调 |

**建议：生产环境一开始就打开可观测。** 事后补埋点的成本远高于一开始就开 ——
你需要的是线上出问题那一刻的链路数据，而不是复现出来的。

### 6. 迁移成本

见 A4。这一项在选型阶段就要算，因为它决定了你**能不能换**。

## A3. 决策路径：按顺序问五个问题

按顺序问，第一个"是"基本就定了，后面的问题用来验证。

1. **团队已经在 Spring Boot 上，且希望 AI 能力和其它 Spring 组件用同样的方式管理吗？**
   → 是：优先评估 Spring AI。

2. **需要大量第三方集成、且团队接受较重的抽象层（声明式接口风格）吗？**
   → 是：优先评估 LangChain4j。

3. **需要"一个服务同时接多家模型 + 内建路由熔断"，或者需要 RAG、MCP、Skills、智能问数、
   多模态一次性铺开吗？**
   → 是：优先评估模块化的独立 Agent 框架这一类。

4. **有非 Spring 的 Java 工程（老服务、中间件、工具类项目）要接 AI 吗？**
   → 是：独立框架或 LangChain4j 比 Spring AI 顺手。

5. **只是"调一次模型拿个回答"吗？**
   → 是：**别引框架**。HTTP 客户端 + JSON 解析，加上把 base_url 指向一个兼容网关，
   足够且负担最小。

### 一个不要做的事

**不要为了选型而选型。** 也不要把"模型供应商"当成选型维度 —— 模型侧统一走 OpenAI 兼容端点
（例如把 base_url 指向 `https://api.a7w.cn/api/v1`）之后，换模型是一行配置的事，
框架该比的是**编排、状态、可观测**这些它真正负责的东西。

## A4. 组合使用（不是只能选一个）

多个方案可以在同一个系统里并存，常见分层：

| 层 | 可以放什么 | 理由 |
|---|---|---|
| 模型接入层 | 统一收口，用哪个方案的适配都行 | 业务不直接依赖具体供应商 |
| 能力层（工具 / RAG） | 谁的组件好用用谁的 | 工具本质是函数，跨方案复用成本低 |
| 业务编排层 | **选一个**作为主框架，别混两个编排模型 | 两套状态模型混用会带来灾难性调试成本 |

**红线**：**同一业务流程里不要混用两套编排 / 状态模型**。工具和模型适配可以混，
"谁负责推进这一轮"必须只有一个答案。

---

## A5. 迁移成本清单

要换框架，按这个清单估工作量，别只算"改多少个类"：

- [ ] 模型配置与密钥管理方式是否改变（配置键名、环境变量约定、base_url 写法）
- [ ] 提示词模板的语法差异（占位符写法、多模态消息拼装）
- [ ] 工具定义的改写（注解名、参数声明方式、返回值约定）
- [ ] 拦截器 / 中间件的等价物是什么（有没有、顺序怎么排）
- [ ] 向量库中已有数据的兼容性（Embedding 模型与维度能否沿用）
- [ ] 多轮会话状态的存储结构（换框架常要换存储结构 → 要写数据迁移）
- [ ] 可观测的埋点与看板（指标名、Span 名会变）
- [ ] 测试用例与回归基线（回答质量不可比时，需要人工评估样本）

**最容易被低估的是第 6 项**：会话状态结构一变，历史数据就要迁移，而这通常牵扯最久。

# B. 排错：Java 接大模型的九类常见故障

## B0. 通用方法：二分法定位

出现问题时，按这个顺序缩小范围，别一上来读框架源码：

1. **最小工程复现**：只引 `core` + 一个模型适配，端点填 `https://api.a7w.cn/api/v1`，
   能跑通再说。
2. **逐层加回**：流式 → 一个工具 → 一个工具组 → 一个拦截器。哪一步坏了就是哪一步。
3. **关掉所有扩展点**：先关拦截器、再关工具组、最后关工具。回到"裸问答"还能不能跑。
   这一步能直接区分"是框架配置问题"还是"是你的扩展代码问题"。
4. **对齐日志**：把框架日志级别调高，和你的业务日志按请求 ID 对齐看。
5. **换端点验证**：换一个已知可用的 OpenAI 兼容端点。能跑通说明是原端点的兼容性问题。

**一条经验**：报错信息指向的地方，往往不是根因。`ClassNotFoundException` 多半是版本错配，
`NullPointerException` 在流式回调里多半是增量对象结构理解错了。

---

## B1. 依赖解析失败（`Could not resolve`）

**症状**：`mvn compile` 直接失败，或 IDE 里依赖飘红。

**排查顺序**：

| 步骤 | 动作 |
|---|---|
| 1 | 确认这个坐标在**你的获取渠道**上真的存在：公共仓库能查到？私服同步了？自建库 install 过？（见 `integration.md` 第一步） |
| 2 | 确认**产物名与版本线配套**：同一套框架换大版本时模块命名常整体改过（`*-llm-*` → `*-chat-*`，`*-document-parser*` → `*-doc-extractor`）。混用必然失败 |
| 3 | 确认企业内网私服/镜像是否同步了该 groupId（很多镜像只代理常用库） |
| 4 | 确认没有把 `<type>` 写错（BOM 是 `pom` 且要 `scope=import`） |
| 5 | 确认本地库没有半损坏的缓存：删掉 `~/.m2/repository/<your-groupId 对应的路径>/` 下对应目录重拉 |

```bash
# 看 Maven 到底去哪找的（把 <your-groupId> 换成实际值）
mvn -X compile 2>&1 | findstr /I "<your-groupId>"

# 只查这个 group 的解析结果
mvn -q dependency:tree -Dincludes=<your-groupId>
```

**一个易错点**：坐标能在公共仓库首页搜到，不等于**你的私服代理了它**。
这是内网环境里最高频的一类"看起来是网络问题、其实是仓库策略问题"。

---

## B2. 包名 / 坐标错配（编译过了，运行时炸）

**症状**：编译通过，启动或调用时报 `NoSuchMethodError` / `NoClassDefFoundError` /
`AbstractMethodError` / `ClassNotFoundException`。

**两类原因，分开处理**：

**原因一：同一个坐标混进了两条版本线。** 或者某个传递依赖把版本降回去了。

```bash
# 定位到底解析到了哪个版本
mvn -q dependency:tree -Dverbose -Dincludes=<your-groupId>

# 统一收口：用 BOM，或在 dependencyManagement 里显式钉住每个构件
```

**纪律**：同一个 group 下的所有构件**必须来自同一条版本线**。这类框架的模块互相依赖，
混版几乎必然出问题。用 `dependencyManagement` 或 BOM 统一，不要各模块各写版本。

**原因二：`import` 写的包名和你依赖里的实际包名不是一套。**

换大版本时，Java 包名常常一起改过（`com.a.b.core` 变成 `com.c.core` 这种）。
IDE 的"自动导入"在这种场景下会添乱 —— 它可能从**另一个传递依赖**里帮你导了一个同名但
不同来源的类，编译通过，运行时不兼容。

**核对动作**：

```bash
# 看这个类到底来自哪个 jar（把 <base-pkg> 换成你写的那段包名）
mvn -q dependency:build-classpath -Dmdep.outputFile=cp.txt
# 然后对着 cp.txt 里的 jar 清单，确认该类只来自一个地方
```

**处置**：以你实际依赖的那个版本里的包名为准，全局搜一遍 `import` 语句改齐；
不要依赖 IDE 的自动导入，改完再 `mvn -o compile` 验一次。

## B3. 同步能跑，流式不行（两条路径不一致）

**症状**：同步调用正常，流式报错、内容重复、内容不完整、或者干脆没有回调。

**排查顺序**：

| 可能原因 | 判断方法 |
|---|---|
| 把每次回调当成完整回答 | 打印每次回调的增量长度。如果每次只有一小段，那就是增量，必须自己拼接 |
| 结束条件判断错 | 打印回调次数与结束标志。流结束还在等 → 阻塞；提前退出 → 内容少 |
| **两条路径的提示词不是同一套** | 对比同步与流式两条路径构造的提示词对象，确认用的是同一个对象、同一套拼装逻辑 |
| 端点不支持流式 | 换一个已知支持流式的端点试。有些兼容实现只做了非流式 |
| 网络/代理缓冲 | 回调长时间无输出然后一次性全来 → 中间有缓冲层（代理、网关），关掉缓冲 |

**两条路径不一致是这一类里最隐蔽的子问题**，因为两边单独看都能跑通，只是行为不同。
根因通常是你自己绕开了框架共用的提示词/参数机制（见 `core-concepts.md` 第四节）。

**一条实务建议**：把"拼接逻辑"写成一个独立可测的小组件，单独用假的增量序列测它。
流式问题里相当一部分其实是拼接逻辑自己的 bug。

## B4. 工具不触发 / 工具泄漏

### B4.1 模型完全不调用工具

| 原因 | 处理 |
|---|---|
| 工具描述太模糊 | 描述里写清"什么时候该用"，不只是"做什么" |
| 必填参数没标或描述缺格式 | 标上必填，参数描述里给格式与示例 |
| 用错了提示词对象 | 工具要挂在**实际发出去的那个**提示词对象上；挂了但没发等于没挂 |
| 工具组没命中 | 打印每轮的命中结果。关键词不在用户消息里就不会命中 |
| 工具太多，模型挑不出来 | 减少可见工具数量（工具组），或用渐进式工具发现 |

### B4.2 调用了一个不存在的工具 / 参数对不上

- **工具名重复**：盘点一遍全量工具名（本地 + MCP + Skills），重名的先改名
- **MCP 远程工具与本地工具冲突**：这也是重名问题，做一次启动期校验
- **参数类型与描述不一致**：模型按**描述**填参，不按你的 Java 签名。描述说"日期字符串"，
  模型就不会传时间戳

### B4.3 工具泄漏到不相关的轮次

"上一轮的工具这一轮还在"，按这个顺序查：

1. 确认用的是**工具组**（按最后一轮用户消息重新匹配）而不是全量挂载
2. 确认跨轮复用的是**同一个提示词对象**时的行为 —— 多轮场景推荐每轮重建，
   或让记忆对象统一管理，不要手工留状态
3. 打印每轮实际进入请求体的工具清单，和预期对比

### B4.4 成本与错误率一起涨

这是工具数量过多的典型信号：

- 工具清单本身占 token，几十上百个工具时开销可观
- 可选项一多，模型选错的概率上升，重试又推高成本
- **处置**：按业务域拆工具组、按输入动态挂载、或改用渐进式工具发现（先检索再调用）

**别忘了给工具调用循环设最大轮次上限**。工具持续失败时会反复"要求调用 → 执行失败 →
再要求"，没有上限就是无底洞。

## B5. 上下文与记忆丢失

**症状**：多轮对话里模型"忘了前面说过的话"；或者反过来，无关的历史被反复带进请求，成本上涨。

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 第二轮就忘了第一轮 | 每轮都新建了提示词对象，历史没带过去 | 用带记忆的提示词对象，或每轮显式把历史消息拼进去 |
| 历史带了但顺序乱 | 消息列表被并发修改 | 会话级串行化；不要在多个线程里共享同一个提示词对象 |
| 上下文超长被截断 | 没有做历史裁剪 | 设消息条数/字符数上限；旧消息做摘要压缩 |
| 该记住的没记住（跨会话） | 记忆只存在于进程内存 | 记忆要落到存储层（库或缓存），并按用户/会话维度检索回来 |
| 不相关的历史一直带 | 历史全量累积 | 按相关性检索历史，而不是无脑全带 |
| 多租户串上下文 | 会话标识没带租户维度 | 会话 key 里带租户 ID，并做强制过滤 |

**核对动作**：把每一轮**实际发出去的完整消息列表**打印出来。绝大多数"记忆丢失"看一眼就明白 ——
要么历史压根没进请求，要么进的是别的会话的。

## B6. 向量库连接与 RAG 召回为空

### B6.1 连接层

| 症状 | 排查 |
|---|---|
| 启动就连不上 | 地址、端口、认证三件套；先用手头的 CLI 直连同一套参数验一次 |
| 内网能连，容器里连不上 | 容器网络、DNS、安全组；别在宿主机通就以为容器也通 |
| 连接池打满 / 超时 | 池大小、空闲回收、超时；高并发下默认池常常偏小 |
| 时好时坏 | 看是不是走了负载均衡或代理，多节点版本的兼容性是否一致 |

### B6.2 召回层

**第一件事：把检索结果打印出来看**。只看最终回答判断不出检索是否工作 —— 模型可能靠自己的
知识答对了，掩盖了检索为空的事实。

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 检索结果恒为空 | Embedding **维度与向量库索引维度不一致**（换过 Embedding 模型最容易发生） | 确认维度；不一致就重建索引。这个错误常常**不报错**，只是查不到 |
| 检索结果恒为空 | 索引/集合名写错，或数据写进了另一个库 | 核对库名、索引名、命名空间 |
| 检索结果恒为空 | 写入与查询用了不同的 Embedding 模型 | 两者必须同一个模型，且同一版本 |
| 写入成功但查不到 | 距离度量与归一化方式不匹配（余弦 vs 内积 vs 欧氏） | 建索引时定的度量要和你算向量的方式一致 |
| 召回了但答不好 | 切分粒度不对（片段太碎缺上下文，或太大混噪声） | 先按标题层级切，再调；把召回片段打出来人工看一眼 |
| 召回了但答不好 | 没有接 Rerank | 接上 Rerank。通常比继续调切分参数收益更直接 |
| 多租户串数据 | 检索没带租户过滤 | 元数据里带租户标识，检索时强制过滤 |
| 文档解析乱码 | PDF 是扫描件（需要 OCR）或版式复杂 | 扫描件走 OCR；复杂版式换解析器 |

**排错小工具**：写一个只做"写入一条 → 查同一条"的最小测试。跑不通就是链路问题，
跑得通就是数据与策略问题。这一步能把范围砍一半。

## B7. 并发与线程池

**症状**：压测时吞吐上不去、请求互相干扰、偶发串数据、或者线程数一直涨。

| 症状 | 原因 | 处理 |
|---|---|---|
| 吞吐上不去，线程都在等 | 模型调用是阻塞 IO，占着业务线程 | 给模型调用单独一个线程池，别和业务线程池共用 |
| 偶发两个请求的回答串了 | 提示词/上下文对象被跨线程共享 | 每个请求独立构造上下文对象；不要做成 Spring 单例字段 |
| 线程数持续上涨 | 流式回调没在结束时释放，或回调里又提交了新任务 | 给流式链路设总超时；回调里不做阻塞操作 |
| 并发推进同一会话互相覆盖 | 会话状态没有版本控制 | 用快照 + 版本 CAS（见 B8），或会话级串行化 |
| 池满后大量拒绝 | 队列无界、池太小 | 有界队列 + 明确的拒绝策略；别用无界队列把内存撑爆 |

**一条纪律**：模型调用、向量检索这两个都是**网络 IO**，它们的线程池要和 CPU 密集型的
业务线程池分开。混在一起时，一次模型抖动就能把整个服务的线程吃干。

## B8. 超时与重试

**症状**：偶发失败、雪崩、重复扣费、长任务卡死。

| 症状 | 原因 | 处理 |
|---|---|---|
| 没有超时，请求一直挂着 | 只设了连接超时，没设读超时/整体超时 | 三层都设：连接、读写、整体请求 |
| 重试把服务打崩 | 失败时全量重试，没退避 | 指数退避 + 抖动；并对重试总量设上限 |
| 重试导致重复副作用 | 对非幂等操作也重试了 | 只对幂等操作重试；写操作靠业务幂等键兜底 |
| 长任务（视频/长文）中途断 | 轮询长连接被网关或代理重置 | 轮询做退避重试；记录任务 ID，断了凭 ID 继续查 |
| 熔断没恢复 | 只配了熔断，没配半开探测 | 配半开恢复；探测失败要能再回到熔断 |
| 重试放大成本 | 流式请求中途失败也重试 | 流式要区分"还没出内容"和"已经出了一半"：后者重试会产生重复内容 |

**判断依据**：

```java
// 形状示意：只对幂等调用开启重试，并给整体设上限
retryPolicy.maxAttempts(3)
           .backoff(base, multiplier, jitter)
           .retryOn(IOException.class)      // 只重试网络类
           .build();
```

**和模型侧的关系**：把模型侧统一指向一个兼容网关之后，网关本身可能有自己的重试与限流行为。
你**不要在自己这侧再叠一层激进重试**，否则一次抖动会被放大成三倍请求量。
先看网关返回的错误码语义，再决定哪一类值得重试。

## B9. 密钥硬编码

**症状**：Key 出现在代码、配置文件、测试用例、日志、或 git 历史里。

| 检查点 | 动作 |
|---|---|
| 仓库里有没有明文 | 全仓搜 `sk-`、`Bearer `、`apiKey`、`api_key`、`base_url` 后面跟着的字面值 |
| 测试与示例代码 | 示例里也必须是 `System.getenv(...)`，不能是字面量 |
| 配置文件的默认值 | `application.yml` 里写 `${A7W_API_KEY}`，不写默认明文 |
| 日志 | 确认没有任何地方打印完整 Key；异常堆栈里也可能带出来 |
| 构建产物 | 打包进 jar 的 resources 里不能有 Key |
| git 历史 | 如果曾经提交过，**必须轮换 Key**，只删文件是不够的 |

**处置顺序（顺序不能反）**：

1. **先轮换 Key**（作废旧的、发新的）—— 历史泄露的 Key 删代码删不掉
2. 再把代码里的写法改成走环境变量或配置中心
3. 再补一条 CI 检查：仓库里 grep `sk-` 这类特征串，命中就拦住提交

**放到哪**：本地开发用环境变量；线上用部署平台的密钥管理或配置中心；
容器环境用 Secret 注入。**任何时候都不要写进 git**。

## B10. 上线前自检清单

按这个清单走一遍，任何一条打不上就先别合：

- [ ] 每个坐标都在**你的获取渠道**上实际解析通过，没有 `Could not resolve`
- [ ] 同一 group 下的构件版本一致（BOM 或 `dependencyManagement` 收口过）
- [ ] `import` 的包名与实际依赖的版本配套，没有靠 IDE 自动导入蒙进来的类
- [ ] JDK 版本覆盖了要引模块的要求（尤其别用 8 去引要求 17+ 的模块）
- [ ] 模型侧 base_url 指向 `https://api.a7w.cn/api/v1`，Key 走环境变量
- [ ] 模型编码是从模型清单接口现场取的真实值，不是猜的
- [ ] 同步与流式**两条路径都实跑过**，且用的是同一套提示词拼装
- [ ] 模型可见的工具清单与实际注册的一致；未命中的工具组不出现在请求体里
- [ ] 工具调用循环设了最大轮次上限；高危工具走审批
- [ ] RAG 链路跑过"写入一条 → 查同一条"的最小闭环
- [ ] Embedding 维度与向量库索引维度一致，换过模型索引已重建
- [ ] 模型调用与向量检索有独立的线程池，且有界队列 + 明确拒绝策略
- [ ] 连接 / 读写 / 整体三层超时都设了，重试有退避与上限
- [ ] 需要多轮/审批/恢复时，持久化后端已就绪并测过重启恢复
- [ ] 可观测开关按需打开，导出间隔与采样成本评估过
- [ ] 没有明文密钥，且 CI 有特征串拦截
- [ ] 有回滚方案：依赖版本可退回、配置可回切、持久化结构变更向后兼容
