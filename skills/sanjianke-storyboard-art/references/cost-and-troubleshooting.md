# 计费口径、实测数据与排错

这份文档里的每一个数字都是**真机跑出来的**，不是从平台文档抄的。
抄文档那部分我们单独标注了「文档价」，并且**从来不拿它做成本前置**。

---

## 一、实测单价

| 项 | 实测值 |
|---|---|
| `nano_banana` · `1K` 出图 | **24 点/张**（= 0.24 元） |
| 充值比例 | 1 元 = 100 点 |
| 提交时的 `frozen_points` | **31.2**（预冻结） |
| 完成后的 `usage.points_cost` | **24** |
| 任务失败 | 全额退回 |
| `action=generate` 与 `action=edit` | 实测同价（各 24 点/张） |

### 冻结 ≠ 结算

提交响应里就有 `frozen_points`，实测 **31.2**，比最终扣费高 **30%**。
它只是**预冻结**：任务失败或超时会把差额退回，**不能拿它算账**。

真正的结算价只有一个来源：任务完成响应里的
`data.usage.points_cost`。本包全程只认它，
`--report` 产出的证据文件里逐格记着它。

### 为什么不信平台的价格字段

同族包逐个验证过平台的 `pricing_matrix` / `tenant_*` / `fixed_price` 字段，
结论是**半数不可信**：

| 应用 | 字段写的 | 实测实扣 |
|---|---|---|
| `image_human` | 1.5 / 2 / 4 / 8 点/秒 | 2 / 3 / 6 / 12 点/秒 |
| `voice_tts` / `stt` | 30 点 | 40 点 |

`schema` 的 `api_doc` 里确实有一张官方模型的价格表：

| 模型 | 文档价 | 我们的态度 |
|---|---|---|
| `nano-banana` | 1K = 24 点/次 | ✓ 与我们实测一致，可以用 |
| `nano-banana-2` | 1K = 38 点/次 | 文档价，**未实测** |
| `nano-banana-pro` | 1K = 45 点/次 | 文档价，**未实测** |
| `nano-banana:official` | 1K = 28.03 点/次 | 文档价，**未实测** |
| `nano-banana-2:official` | 1K/2K/4K = 35.76 点/次起 | 文档价，**未实测** |
| `nano-banana-pro:official` | 1K/2K/4K = 61.52 点/次起 | 文档价，**未实测** |

**本包不拿这些数字做成本前置。** 道理很简单：成本闸门的作用是"别让你超预算"，
用一个没验证过的数去算，闸门就是假的。所以：

- `nano-banana` + `1K` → 用 24 点/张（有实测）
- 其它模型，或 `2K` / `4K` → **拒绝估算，退出码 3**
- 确实想估 → 自己给 `--points-per-image <点数>`，本包会把来源标成 `override`

```bash
python3 scripts/run.py cost --count 12
# 预估成本：12 张 × 24 点 = 288 点 = 2.88 元

python3 scripts/run.py cost --count 12 --resolution 2K
# 预估成本：无法估算（2K 档没有实测单价…）→ 退出码 3

python3 scripts/run.py cost --count 12 --resolution 2K --points-per-image 36
# 预估成本：12 张 × 36 点 = 432 点 = 4.32 元（来源：override）
```

### 文本（抽设定卡 / 出分镜表）怎么算钱

平台不公开大模型单价，所以本包**只报 token 数，不报金额**——
`--json` 或 `--report` 里能看到 `usage.prompt_tokens / completion_tokens / total_tokens`。

实测参考（不构成报价）：

| 步骤 | token | 耗时 |
|---|---|---|
| `characters`（6 千字剧本，4 个角色） | prompt 926 + completion 521 = **1447** | **3.4 秒** |
| `shots`（4 格分镜） | 约 3k 级 | **5.5 秒** |

按常见的文本单价量级，一次完整"抽卡 + 分镜"是**分级钱**，可以忽略不计。
真正花钱的只有出图。

### 一组格数的成本参考

| 格数 | 点数 | 金额 |
|---|---|---|
| 2 | 48 | 0.48 元 |
| 4 | 96 | 0.96 元 |
| 8 | 192 | 1.92 元 |
| 12 | 288 | 2.88 元 |
| 24（一话短条漫） | 576 | 5.76 元 |

注意这是**一次性全出**的价。实际做分镜会反复改：改一格提示词就只重出那一格
（断点 key 的提示词维度变了），其余格不动。所以迭代成本 ≈ 改动格数 × 0.24 元。

## 二、断点 key：为什么是八维

出图是**异步 + 按次扣费**的。一次抖动、一次 Ctrl+C、一次改参数，
都可能让"已经冻结了点数的任务"悬在那里；没有正确的断点记录，重跑会把同一格再买一遍，
或者更糟——**静默复用过期产物**。

同族踩过三个坑，本包一次给全：

| 踩过的写法 | 后果 |
|---|---|
| key 只有 `id` | 改了提示词也不重出 → 拿到旧图 |
| key 是 `id + 提示词前 N 个字符` | 只改第 25 字之后 → key 不变 → **静默复用旧图** |
| key 只有 `id + 提示词摘要`（不含 `resolution`） | 1K 出了图，改 `--resolution 4K` 重跑 → 复用 1K 的图 |
| key 不含角色设定卡 | 改了角色的脸型/疤痕 → 复用旧脸的图 |

所以本包的 key 是**八维**：

```
sb:<格号>:<sha1(提示词全文摘要 + 比例 + resolution + 模型 + action
             + 角色设定卡摘要 + 参考图摘要)[:16]>
```

明细：

| 维度 | 为什么必须进 key |
|---|---|
| 格号 | 同一套提示词用在不同的格，是两件事 |
| **提示词全文摘要** | 改一个字就要重出；取全文摘要，**绝不截断前 N 字符** |
| 比例 `aspect_ratio` | 3:4 与 9:16 是完全不同的画面 |
| `resolution` | 1K / 2K / 4K 是不同的产出，不能互相冒充 |
| 模型 | 换模型 = 换画风与细节 |
| `action` | `generate` 与 `edit` 的输出性质不同 |
| **角色设定卡摘要** | 只取**本格出场角色**的卡片内容，改了本格角色的字就重出 |
| **参考图摘要** | 参考图变了，产出就变了（`image_urls` 是真实输入） |

### 二次兜底：key 命中也要比对内容

断点文件可能是手工改过的、或由旧版本生成的。所以命中 key 之后还会逐项比对：
提示词 / 分辨率 / 模型 / action / 角色设定卡摘要 / 参考图，**任一项不一致就不复用**，
并在 stderr 明确写出是哪一项不一致 → 重新出图。

这条兜底的意义在于：**静默复用旧产物比多扣一次费危险得多**——
多扣费用户立刻会发现，复用旧图不会。

### 改了 `--snap` 口径怎么办

裁剪是**本地后处理**，不该为了换个裁法把同一张图重买一遍。所以：

- 断点记录里存了 `orig_file`（裁剪前的原始下载）与 `snap_mode`
- 重跑时若 `--snap` / `--snap-exact` 口径变了 → **从 `orig_file` 本地重裁**（零成本），
  stderr 会打印"本地重裁（零成本）"
- 旧版断点里没有 `orig_file` → **明确警告**"无法本地重裁，这一格仍是旧口径的产物；
  要按新口径拿到图只能加 `--force`（会重新扣费）"

不警告就是静默沿用旧产物，那是本包最防的失败形态。

### 文本步骤的断点（`all`）

`all` 还会给文本步骤做断点：key = 剧本全文摘要 + 模型 + 风格 + 格数。
**剧本没变就不重抽设定卡**——这一步比出图更省钱，因为改了设定卡会让全部格重出。
`--force` 会全部重跑（并重新扣费）。

## 三、`--report` 证据文件怎么读

`images --report ev.json` 产出的是本次的完整证据，对账就看它：

| 字段 | 含义 |
|---|---|
| `estimate` | 跑之前的预估（点数、单价来源、注意事项） |
| `points_cost_this_run` | **本次真花的点数** |
| `points_cost_total` | 累计（含断点续跑跳过的、上次已经扣过的） |
| `yuan_this_run` | 本次折算人民币 |
| `refs_used` | 参考图用法统计（上一格 / 锚点 / 无参考 各几格） |
| `completed[].request` | **实际发出去的请求体**（prompt / action / image_urls / resolution / model / aspect_ratio） |
| `completed[].points_cost` | 该格实扣点数（来自 `usage.points_cost`） |
| `completed[].image_url` | 上游返回的图片地址（**这也是下一格参考图的来源**） |
| `completed[].first_check` | **裁剪前**的真实像素与比例偏差（上游到底给了什么） |
| `completed[].snap` | 裁剪方式 / 裁剪框 / 裁后复核；没裁就是 `null` |
| `completed[].raw_task` | 任务查询响应原文（含 `data.status` 与 `usage`） |
| `ratio_failed[]` | 比例不合格的格与原因 |
| `failed[]` | 失败格与阶段（submit / poll / task / no_url / download） |
| `consistency` | 角色一致性结论（漏词清单） |

`consistency --report rep.json` 单独产出一致性明细：逐格逐角色的
`feature_ratio` / `missing` / `palette_ratio`，以及扁平化的 `missing_words` 清单。

## 四、排错手册

### 鉴权与账号

| 报错 | 原因 | 处理 |
|---|---|---|
| `鉴权失败（401）` | Key 无效/过期/写错 | 到 https://api.a7w.cn/ 重新领取；确认没把 `Bearer` 重复写进环境变量 |
| `点数不足（402）` | 点数用完 | 充值后重试 |
| `没有找到 API Key` | 三种方式都没配 | `--key sk-xxx` / `export A7W_API_KEY=…` / `python3 scripts/a7w.py login --key sk-xxx` |

### 网关与上游

| 报错 / 现象 | 原因 | 处理 |
|---|---|---|
| HTTP 200 但 `code: 0` | **网关信封里 `code == 1` 才是成功**，不是 0 | 看 `msg`；脚本已按这个口径判断，别改成 `code == 0` |
| 轮询一直读不到状态 | **`status` 在 `data` 顶层**，不在 `data.result` 里（平台文档写错） | 脚本按实测结构取；自己写脚本别照文档写 |
| `当前请求未命中可用计费规格` | `model` + `resolution` 组合不支持 | 普通 `nano-banana` 只有 `1K`；要高清档换 `nano-banana-2:official` 之类 |
| 上游 `502` / `upstream timeout` | 网关到上游的瞬时抖动，**实测很频繁** | 脚本内置退避重试（4 次）；连续失败就换模型或降低批次 |
| 任务卡在 `processing` | 任务卡住 | `--poll-timeout`（默认 600 秒）到点会报出来并保留 `task_id`；续查：`python3 scripts/a7w.py task <task_id>` |
| `参考图最多 12 张` | 超过 schema 的 `max_reference_images` | 减少 `--anchor` / `--ref-urls` |
| `action=edit 时必须提供 image_urls` | `--ref-mode anchor` 但没给锚点 | 给 `--anchor id=URL`，或把 `anchor_urls` 写进设定卡 |

### 闸门（退出码 3）

| 报错 | 原因 | 处理 |
|---|---|---|
| `命中违禁词「…」` | 广告法绝对化用语等 | 改文案；确实要用才加 `--allow-prompt-hits` |
| `残留了模板占位符` | 模型留了 `{}` / `[待填]` / `XXX` | 改掉后重跑 |
| `提示词有 N% 的内容来自示例` | 照抄了提示词里的示例 | 换写法；检查模板里是不是留了可复制的示例 |
| `真实像素 … 与请求比例 … 偏差 …%` | 上游按 32 对齐 | `--snap-exact` 裁准，或放宽 `--ratio-tolerance` |
| `第 N 格结构问题：景别 … 不在枚举里` | 写了"看得见人"这类非景别 | 改成八档枚举之一 |
| `第 N 格结构问题：画面描述只有 X 个字` | 描述太短 | 补到 8 字以上（建议 30~80 字） |
| `分镜表格数为 0` | 没有格 | 先跑 `shots` 出分镜表 |
| `第 N 格 · X（id）漏了特征词「…」` | 模型没复述全部特征词 | 重跑 `shots`；或手改那一格 `prompt`（只重出这一格） |
| `预估 N 点超过 --budget` | 超预算 | 提高预算或用 `--count` 少出几格 |
| `2K 档没有实测单价，拒绝凭猜估算` | 我们没有 2K/4K 实测价 | 给 `--points-per-image`，或先用 1K |
| `模型 … 没有实测单价` | 换模型就没实测价 | 同上 |

### 退出码 4 / 2 / 5

| 退出码 | 场景 | 处理 |
|---|---|---|
| `4` | 没加 `--yes`（**这是保护，不是错误**） | 看完报价再加 `--yes` |
| `2` | `--outdir` 在 Skill 包内 | 换到包外（`./out`、`%TEMP%\…`）。包内放图片会让上传 400 |
| `2` | 输入文件读不动 / 不是合法 JSON | 检查 `characters.json` / `shots.json` 是否被手工改坏 |
| `5` | 达到 `--max-seconds` | 已完成都在断点里，直接重跑续 |

### 拼页相关

| 报错 | 原因 | 处理 |
|---|---|---|
| `缺图的分镜格：3、4` | 那几格还没出图 | 先 `images` 补出来（断点续跑，已有的不重复扣费） |
| `第 N 格读不进来：内置解码器只支持 8 位非隔行 PNG` | 图片不是这个格式（可能是 JPEG/WebP 被存成 `.png`） | 装 Pillow（它读 JPEG/WebP），或用 PNG 档重出 |
| 页尺寸不对 | 参数组合算出来的 | 页尺寸 = 边距×2 + 格×行列 + 间距；核对 `--panel-w/--panel-h/--cols/--rows/--gutter/--margin` |
| 拼出来的画质偏脏 | 没装 Pillow，缩小走了最近邻/盒式均值 | 装 Pillow 会走 LANCZOS；产出里标注了用了哪一个 |

### 环境

| 现象 | 原因 | 处理 |
|---|---|---|
| Windows 控制台中文乱码 | 代码页不是 UTF-8 | 先 `chcp 65001`，或设 `PYTHONIOENCODING=utf-8` |
| `PermissionError` 写文件 | 目标路径是目录或没有权限 | 检查 `--out` / `--report` 指向的是文件而不是目录 |
| 中文路径出问题 | 部分系统区域设置 | 用 `--outdir` 指到纯英文路径（如 `%TEMP%\storyboard-out`） |

## 五、对账建议

1. **跑之前**：`cost --count N` 看预估；带 `--budget` 让脚本替你兜底
2. **跑的时候**：看 stderr 里每一格的"扣费 X 点"
3. **跑之后**：`--report ev.json`，
   把 `completed[].points_cost` 加起来，与 `points_cost_this_run` 对一下
4. **横向核**：拿同一把 Key 在平台控制台的账单页核对总量
5. **不要**用 `frozen_points`、也不要用平台价格字段对账——只认 `usage.points_cost`

**不要在报错信息或截图里带上你的 API Key。**
