# 三剪客 · 任务交接文档 Skill

把进行中的任务整理成一份交接文档，让另一个 Agent 或另一个人能无损接手

---

## 前置条件

- 一个**正在进行中、还没做完**的任务。已经收尾的任务不需要交接文档，需要的是变更日志。
- 一个**存放位置**，保证接手方能拿到。放仓库里跟着代码走版本最稳；放协作平台也行，但要能给链接。
- 能读写 Markdown 的任意编辑器。**纯文本即可，不装任何工具。**
- 推荐（非必需）：git。能拿到准确的分支名、提交号、未提交改动清单，「现状」字段的可信度会高一个档次。

---

## 使用

**1. 判断该用哪一档**

| 场景 | 档位 | 长度 |
|---|---|---|
| 换会话继续、交接给旁边的人 | 轻量档 | ≤ 25 行 |
| 多人协作、跨几天、有交付节点 | 标准档（默认） | 40~80 行 |
| 跨周、跨子系统、正式移交或长期存档 | 完整档，或拆成多份 | 100~200 行 |

**2. 先冻结状态，再动笔**

```bash
git status --short
git rev-parse --short HEAD
git branch --show-current
git diff --stat
```

把关键几行贴进「现状」。**未提交的改动单独说明去向**——这是交接事故的头号来源。

**3. 按顺序写字段**

先写「下一步」和「踩过的坑」，这两节决定交接成败。其余六字段是给它们做支撑的：

```
元信息 → 现状 → 下一步 → 已完成 → 未完成
       → 关键决定与理由 → 踩过的坑 → 待确认问题 → 相关文件索引
```

骨架直接抄 `references/handoff-template-and-examples.md` 的第一节。

**4. 过裁剪判据**

逐句问：**「删掉这句，接手方的行为会变吗？」** 不会变的就删。四种膨胀症状（流水账、代码转贴、覆盖性免责、防御性叙述）见 `references/handoff-spec.md` 第五节。

**5. 走四问验收**

交给接手方前自测：它读了之后能不能说清**① 自己在哪 ② 下一步做什么 ③ 哪些路不用走 ④ 该找谁**。任何一问卡住，回去补对应字段，**不要靠加字数糊过去**。

**6. 交出去，要一个回执**

明确说一句：「你看完告诉我第一步打算做什么。」对方的复述就是这次交接的验收信号。**复述不出来，是文档的问题，不是对方没认真读。**

**7. 重要任务花 5 分钟复盘**

用 `references/handoff-quality-checklist.md` 第四节的复盘模板。重点关注「接手方实际问了什么」——它问的每一个问题都是文档的空白。

## 依赖

**必需**：无。纯 Markdown，不需要网络、API Key、数据库、Docker 或任何付费服务。

**推荐**：

| 依赖 | 用途 | 没有会怎样 |
|---|---|---|
| git | 取分支名、提交号、未提交改动清单 | 「现状」只能手写，可信度下降 |
| 一个读交接文档的接手方（人或 Agent） | 回执与四问验收 | 只能自己隔一天再读，用「扮演接手方」代替 |

---

## 安全

- **不内嵌任何密钥**，不要求你提供凭证，不接入任何外部服务。
- **不写凭证内容。** 文档里涉及访问权限时，只写「在哪拿、由谁发放」，绝不写密钥、Token、密码、Cookie 的内容。
- **交接文档会被整篇读进另一个 Agent 的上下文**，也可能被转发给不在这个项目里的人。贴日志、报错堆栈、内部域名、客户名、真实姓名之前先过一遍脱敏。
- **文档会长期留在仓库里。** 写完就当它会被未来的所有人看到——包括你没想到的那些人。
- **不覆盖已有文件。** 目标路径已存在同名交接文档时，先停下来给你看差异，由你决定是新建带日期的文件还是合并。
- **不常驻任何进程**，不装依赖，不注册定时任务，不改动系统配置。仅在取分支名和提交号时执行一次性只读命令。
