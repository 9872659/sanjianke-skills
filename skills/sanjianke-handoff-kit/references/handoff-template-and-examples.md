# 填写模板与示例

这份文件给三样东西：**可直接复制的空模板**、**逐字段的写作提示**、以及**两份填好的完整样例**。

字段的定义和判据见 `handoff-spec.md`，这里只管「怎么把它填出来」。

---

## 一、空模板（标准档）

整段复制，按需删行。中方括号 `【】` 是提示，填完要全部删掉。

```markdown
# 交接文档：<任务名>

| 项 | 内容 |
|---|---|
| 交接时间 | 【YYYY-MM-DD HH:MM】 |
| 交接双方 | 【从谁到谁；Agent 交接就写会话标识】 |
| 任务状态 | 【进行中 / 阻塞 / 待评审 / 近完成】 |
| 交接原因 | 【会话长度上限 / 轮班 / 换人 / 暂停等】 |
| 权限与约束 | 【哪些能改、哪些只读、哪些不能碰】 |

## 现状

- 坐标：【分支名 / 提交号 / 当前产出物版本】
- 进度一句话：【任务走到哪一步了】
- 未提交的改动：【有什么、在哪、打算保留还是丢弃；没有就写「无」】
- 阻塞：【卡在什么外部条件上、由谁推动；没有就写「无」】

## 下一步

1. 【对哪个文件的哪个位置做什么动作】
   - 验证：【跑什么、看到什么算成了】
   - 不成的话：【看哪条坑 / 问谁】

## 已完成

- 【产出物 + 落到哪（文件/提交/交付物）+ 验证到什么程度】

## 未完成

- 【未完成项 + 为什么还没做（没时间 / 卡住了 / 等外部条件 / 主动排除）】

## 关键决定与理由

1. 【决定了什么】
   - 为什么：【约束是什么】
   - 否掉了什么：【另一个看起来合理的方案 + 被否的原因】

## 踩过的坑

1. 【坑的标题】
   - 现象：【看到什么报错 / 什么反常表现】
   - 原因：【真实原因】
   - 为什么不显然：【第一眼为什么会误判】
   - 怎么绕：【正确做法，带路径或行号】

## 待确认问题

- 【问题 + 为什么悬着 + 该问谁 / 该看哪里】；没有就写「暂无」

## 相关文件索引

| 路径 | 为什么看 |
|---|---|
| 【具体路径，必要时带行号或函数名】 | 【在这个文件里看什么】 |
```

## 二、轻量档模板

换会话继续同一件事、或交接给坐在旁边的人，用这个。**别多写，多了对方不读。**

```markdown
# 交接：<任务名>（<日期>）

**下一步**：【一句话，一个动作 + 一个验证方式】

**现状**：【分支 / 提交号】·【任务走到哪一步】·【阻塞（没有就写无）】
**未提交改动**：【在哪、要不要留；没有就写无】

**已经做完（别重做）**：
- 【产出物 + 验证程度】

**还没做**：
- 【未完成项 + 为什么】

**坑（别再踩）**：
- 【现象】→【原因】→【怎么做才对】

**悬着的问题**：【该问谁】；没有就写无
```

## 三、逐字段写作提示

每个字段给一组**填空句式**。卡住的时候照着套，比对着字段名发呆有用。

### 交接元信息

| 项 | 填空句式 |
|---|---|
| 任务名 | 「<动词><对象>」——「导出模块大文件超时修复」比「导出相关工作」强 |
| 任务状态 | 从四个选项里挑：进行中 / 阻塞 / 待评审 / 近完成。**不要写「顺利推进中」**，那不是状态 |
| 交接原因 | 一句话，说明紧迫度：「会话接近上限，希望今天内接上」 |
| 权限与约束 | 「可改 ____；____ 只读；____ 不能碰，因为 ____」 |

### 现状

- 坐标句式：「分支 ____，提交 ____，工作区（干净 / 有 N 处未提交改动）」
- 进度句式：「____ 已 ____，____ 还没 ____，卡在 ____」
- 阻塞句式：「阻塞在 ____（由 ____ 推动），拿到之后才能 ____」

### 下一步

- 动作句式：「把 ____ 里的 ____ 从 ____ 改成 ____」
- 验证句式：「跑 ____，看到 ____ 就算成了」
- 退路句式：「如果还是 ____，看『踩过的坑』第 N 条」

### 已完成

- 句式：「____ 已完成（落在 ____），验证到 ____ 程度」
- 验证程度的三个档：**写完未跑** / **跑过一次** / **通过完整测试**。前两档要慎用「已完成」这个词。

### 未完成

- 句式：「____ 未做，因为 ____（没时间 / 卡住 / 等外部条件 / 主动排除）」
- 主动排除的要补一句：「不是遗漏，是决定不做，理由见『关键决定』第 N 条」

### 关键决定与理由

固定三行：

```markdown
1. 决定了：____
   - 为什么：____（约束：性能 / 兼容 / 时间 / 外部依赖）
   - 否掉了：____，因为 ____
```

**如果写不出「否掉了什么」，说明这不算一个决定**——它只是一个顺手的做法，不用写进交接文档。

### 踩过的坑

固定四行：

```markdown
1. 坑：____
   - 现象：____（报错原文首行 / 反常表现）
   - 原因：____
   - 为什么不显然：____
   - 怎么绕：____（路径:行号）
```

**自检**：「为什么不显然」写不出来的坑，通常别人自己也会很快发现，可以不写。

### 待确认问题

固定三行：

```markdown
1. 问题：____
   - 悬着的原因：____（缺什么数据 / 缺谁的确认）
   - 该问：____ 或该看：____
```

### 相关文件索引

- 句式：「`____` —— 在这个文件里看 ____」
- 只列**接手方动手时会打开**的文件。判断方法：想象它照着「下一步」开始干，会点开哪几个。

## 四、样例 A：Agent 交接（导出超时修复任务）

**场景**：一个 Agent 会话接近长度上限，任务进行到一半，要交给新会话。这份文档会作为一个新会话的输入。

```markdown
# 交接文档：导出模块 CSV 大文件超时修复

| 项 | 内容 |
|---|---|
| 交接时间 | 2026-02-14 18:30 |
| 交接双方 | 会话 A → 新会话 |
| 任务状态 | 进行中（阻塞在对象存储临时凭证） |
| 交接原因 | 会话接近长度上限，任务只完成约一半 |
| 权限与约束 | 可改 `src/export/` 与 `test/`；`src/db/migrations/` 只读，本次不改表结构 |

## 现状

- 坐标：分支 `feature/export-fix`，提交 `a1b2c3d`，工作区干净
- 进度一句话：流式写入已实现，12 条单测过 6 条，第 7、9、12 条失败；大文件路径未处理
- 未提交的改动：无
- 阻塞：需要一个对象存储的临时凭证来做 >2GB 的实测，已向运维同事提出，等待回复。**这个阻塞不影响先修单测**，单测用本地 mock

## 下一步

1. 把 `src/export/csv.ts` 里 `writeChunk` 的批次上限常量从 5000 降到 1000，重跑 `npm run test:export`
   - 验证：12 条用例全绿；并且 `logs/export-time.log` 里每条用例的「单批最大耗时」< 200ms
   - 不成的话：如果只有第 7 条失败，看「踩过的坑」第 1 条——它不是批次大小的问题
2. 第 7 条过了之后，再处理第 9、12 条：这两条的失败原因相同，都是超大字段的转义问题
   - 验证：跑 `npm run test:export -- -t "escape"`，3 条转义用例全绿

**注意：只做 1 和 2，不要提前动大文件路径。** 那条路已经选定了方案但需要凭证才能验证，见「关键决定」第 3 条。

## 已完成

- `src/export/csv.ts` 的流式写入实现完成（提交 `a1b2c3d`），已通过 6/12 条单测——**验证程度：跑过单测，未做真实数据实测**
- `logs/export-time.log` 的耗时记录逻辑接好（提交 `a1b2c3d`）——**验证程度：只在 mock 数据上跑过，单批耗时 40~80ms，还看不出趋势**
- 目标格式确认完毕，定义见 `docs/export-format.md`（无需重看）

## 未完成

- 大文件（>2GB）路径未做——当前实现会把整块载入内存，需要改成流式分块。**属于「未做」而不是「做坏」**：方案已定，缺的是凭证和实测时间
- 第 7、9、12 条单测未修（本次会话时间不够）
- 未做端到端压测

## 关键决定与理由

1. 决定用**流式分块写入**，而不是「整块读入再切片」
   - 为什么：目标文件峰值 4GB，整块读入会 OOM。已在 2GB 数据上实测，进程被系统杀掉
   - 否掉了：切片批量写（它能省内存），因为需要额外的偏移量管理，而且当前数据源不支持按偏移量重读。**别改回批量读**，除非数据源先支持随机读
2. 决定**不改数据库表结构**
   - 为什么：本次是导出链路的问题，动表结构会把发布周期拉长到下一轮
   - 否掉了：加一张导出任务表（它能更好地跟踪进度），因为当前没有多个并发导出的需求，属于过度设计
3. 决定大文件路径用**「读一段、写一段、释放一段」**而非全量缓冲
   - 为什么：内存占用与文件大小解耦
   - 否掉了：跑到独立进程里做（能彻底避免 OOM），因为要额外处理进程通信与错误回收，当前时间不够。**如果后续压测发现内存仍然超标，这条是最先该重新考虑的方向**

## 踩过的坑

1. 坑：**单测第 7 条随机失败**
   - 现象：`test:export` 第 7 条时过时不过，日志里是 `ECONNRESET`
   - 原因：测试用的 mock 服务在用例之间没有重置连接池，上一条用例的残留连接被复用
   - 为什么不显然：报错指向网络层，第一反应会去查超时配置。我在这上面花了近两小时，改了三次超时值都没用
   - 怎么绕：在 `beforeEach` 里重置连接池，参考 `test/export.spec.ts:24`
2. 坑：**耗时日志看起来「没有规律」**
   - 现象：单批耗时在 40~80ms 之间跳，看不出与数据量的关系
   - 原因：日志记录的是「这一批从开始到结束」，包含了 mock 服务的固定延迟；mock 延迟随机波动 ±30ms，把真实信号盖住了
   - 为什么不显然：会以为是批次大小的影响，从而去调那些无关的常量
   - 怎么绕：只看「单批最大耗时」这个聚合值，不要看每批的瞬时值；或者把 mock 延迟固定成 0 再测
3. 坑：**`npm run test:export` 有时候整个超时**
   - 现象：偶尔整套用例跑到 5 分钟被强杀，但不报具体是第几条
   - 原因：第 7 条失败时连接没被释放，后续用例排队等连接
   - 为什么不显然：看起来像「测试框架本身不稳定」
   - 怎么绕：先修第 7 条（坑 1），这个现象会自己消失

## 待确认问题

1. 问题：导出格式是否要兼容旧版 `v1` 表头？
   - 悬着的原因：现有客户里有 3 家在用 v1，但我拿不到他们的版本使用数据，无法判断影响面
   - 该问：（产品负责人角色）。他手上有客户版本分布；或者在（内部数据平台）查 `export_version` 字段的调用分布
2. 问题：对象存储的临时凭证怎么拿、有效期多久？
   - 悬着的原因：已在对接群里提出，等待回复
   - 该看：（对接群）里我 18:10 发的那条消息；或者直接问运维对接人

## 相关文件索引

| 路径 | 为什么看 |
|---|---|
| `src/export/csv.ts` | 主要修改点。`writeChunk` 是下一步的目标；`MAX_ROWS` 常量在文件顶部 |
| `test/export.spec.ts:24` | 坑 1 的修复位置（`beforeEach` 里重置连接池） |
| `docs/export-format.md` | 目标格式定义。**动手前先看**，转义规则在第 3 节 |
| `logs/export-time.log` | 耗时验证的数据来源，看「单批最大耗时」列 |
| （任务单链接） | 需求原文与验收标准 |
```

**这份样例里值得注意的三个写法**：

1. 「下一步」里**显式禁止了一件事**（「不要提前动大文件路径」）。对 Agent 接手方来说，明确的不做清单和做清单一样重要——否则它会顺手重构。
2. 「已完成」每条都标了**验证程度**。同样的「已完成」，跑过单测和只在 mock 上跑过，可信度差一个数量级。
3. 坑都写了**「为什么不显然」**。这是让人判断「这个坑值不值得记住」的关键信息。

## 五、样例 B：人交接（服务告警排查）

**场景**：值班同事要下班，把一件正在排查的线上问题交给下一班。文档要短，因为对方只会跳读。

```markdown
# 交接：支付回调偶发 502 排查（02-14 20:00）

**下一步**：看一眼 `app/logs/pay-callback.log` 里 20:00 之后有没有 `upstream timeout`。有 → 直接按下面「坑 1」的绕过方式加白名单；没有 → 这件事可以在 22:00 前先放着，优先看新进来的工单。

**现状**：分支 `hotfix/callback-log`，提交 `7f8e9a1`。已定位到与上游网关的连接复用有关，根因**还没确认**。无阻塞。

**已经做完（别重做）**：
- 已确认不是我们这边超时配置的问题：把超时从 3s 提到 10s 后，502 频率没变（20:00 的数据）
- 已加上回调日志，能区分「上游超时」和「我们处理失败」

**还没做**：
- 根因确认。目前的推断是上游网关的连接池在低峰期回收后没重建——**这是推断，没验证过**
- 没有为客户侧准备话术（如果 22:00 前还有告警，客服会问）

**坑（别再踩）**：
- 别去翻网关那台的监控——**权限上周被收回了**，你打不开会浪费十分钟。要找他的值班人走临时授权
- 日志时间戳是 UTC，比本地时间晚 8 小时。我第一次看的时候把 12:00 当成中午了

**悬着的问题**：上游网关的低峰期连接回收策略，该问上游对接人。他那边的答复最快明天上午
```

**对比样例 A 看出来的取舍**：

- **字段砍到五个**。没有「关键决定」，因为这里还没有真正的决定；没有「文件索引」，因为只有一个日志文件，直接写在「下一步」里了。
- **「下一步」顶在最前面**，因为人只读开头。
- **坑只写了两条**，都是「会让你白费十分钟」的那种。别的坑不值得占这个位置。

## 六、填完之后：三分钟自查

不要跳过这一步。填完立刻做，隔一天再看你会失去判断力。

1. **出声读一遍「现状」+「下一步」。** 读起来卡壳的地方，就是接手方也会卡壳的地方。
2. **把「已完成」里每一条的验证程度念出来。** 出现「应该没问题吧」的，改成「未验证」并挪进「未完成」。
3. **数一下行数。** 标准档超 80 行、轻量档超 25 行，回去过一遍 `handoff-spec.md` 第五节的四种膨胀症状。**不要靠删减措辞来压行数——要删掉整条不改变行为的信息。**
4. **检查三个禁令**：有没有真实密钥或内网地址？有没有「继续优化」这类无法执行的方向句？有没有把推断写成了事实陈述？
5. **问自己最后一句**：「如果接手方只读我的『下一步』，它做的会是我想让它做的那件事吗？」

完整的质量清单和四问验收法见 `handoff-quality-checklist.md`。
