# 交接文档规范

这份文件定义交接文档的**八字段标准**、判断一条信息该不该写进去的**判据**，以及交接文档与周报、变更日志、代码注释之间的分工。

全部内容是通用作业规范，不针对特定工具或平台。

---

## 一、交接文档到底在解决什么问题

接手方拿到的处境是固定的，先把它说清楚，后面的字段才有依据：

1. **它没有你的对话历史。** 你上下文里那些「我们聊过」「刚才试过」全部不存在。
2. **它可能有仓库读写权限。** 所以能从代码里读出来的事实，不需要你抄一遍。
3. **它不知道你的偏好和约束。** 你心里那些「这里不能这么改」「那位同事不认这个方案」对它来说是隐形的。
4. **它会在信息不足时自行脑补。** 空白不会让接手方停下来问你，会让它按最常见的方式猜——而最常见的往往正是你已经试过并否掉的那条路。

于是交接文档的目标可以被精确表述为：

> **让接手方在没有你的对话历史的情况下，不重复你已经排除的路，直接做出你已经想清楚的那个下一步。**

注意它**不**包含「让接手方了解项目全貌」。全貌是它自己去读代码和文档的事。交接文档只负责那部分**无法从仓库重建、且会改变接手方行为**的信息。

这句话是整个规范的根，后面所有判据都是从它推出来的。

---

## 二、八字段总览

八个字段分两组。**控制面**三个字段决定接手方能不能开工；**信息面**五个字段决定它开工后会不会走弯路。

| # | 字段 | 回答接手方的哪个问题 | 组别 | 必要性 |
|---|---|---|---|---|
| 0 | 交接元信息 | 这份文档现在还可信吗？交的是谁、什么时候交的、我能动什么？ | 控制面 | 必写 |
| 1 | 现状 | 现在到哪一步了？我该基于哪个状态开始？ | 控制面 | 必写 |
| 2 | 下一步 | 我现在具体该做什么？做完怎么算做对了？ | 控制面 | 必写 |
| 3 | 已完成 | 哪些不用重做？ | 信息面 | 必写 |
| 4 | 未完成 | 哪些还没做？为什么没做？ | 信息面 | 必写 |
| 5 | 关键决定与理由 | 为什么是现在这个样子？为什么不能换别的做法？ | 信息面 | 必写 |
| 6 | 踩过的坑 | 哪些路已经证明走不通？看到什么现象说明我在踩这个坑？ | 信息面 | 必写 |
| 7 | 待确认问题 | 我拿不准的、需要问人的，该问谁？ | 信息面 | 写不出就明说「暂无」 |
| 8 | 相关文件索引 | 我该看哪些文件？ | 信息面 | 必写 |

**为什么「待确认问题」允许空**，而其他七个不许：其他七个字段如果空着，接手方一定会做错事（不知道起点、不知道该干嘛、重复已完成的工作）。而「待确认问题」空着，只说明这个任务确实没有悬而未决的疑问——这很正常。但**必须显式写「暂无」**，因为留空分不清是「没有」还是「忘了写」。

## 三、字段逐条定义

### 字段 0 · 交接元信息

**回答**：这份文档现在还可信吗？权限边界是什么？

**必须包含**：

| 项 | 说明 | 示例 |
|---|---|---|
| 任务名 | 一句话，具体到能认出是哪个任务 | 「导出模块 CSV 大文件超时修复」 |
| 交接时间 | 精确到日，必要时到小时 | `2026-02-14 18:30` |
| 交接双方 | 从谁到谁 | 「（场景描述）会话 A → 新会话」 |
| 任务状态 | 进行中 / 阻塞 / 待评审 / 近完成 | 进行中（阻塞在第三方接口） |
| 交接原因 | 为什么现在交接 | 会话长度上限 / 轮班 / 换人 |
| 权限与约束 | 哪些能改、哪些只读、哪些不能碰 | 可改 `src/export/`；不要动 DB 迁移 |

**颗粒度**：六行以内，表格最好。

**反例**：省略「交接原因」。理由是接手方会误判优先级——「因为会话太长」和「因为我休假两周」意味着完全不同的紧迫度。

---

### 字段 1 · 现状

**回答**：现在到哪一步了？我该基于哪个状态开始？

**必须包含**：

- **可定位的坐标**：分支名、提交号、文件路径；如果任务不在代码上，就写「当前产出物是哪一版」。
- **一句话说清任务卡在哪**：不是「进行中」，而是「接口写完了、单测没过、卡在第 7 条用例」。
- **未提交 / 未落地的改动**：单独列出来，说明它是什么、在哪个位置、是否打算保留。这是交接事故的第一来源。
- **当前阻塞**：如果有，写清阻塞在什么外部条件上、这个条件由谁推动。

**颗粒度**：3~6 行。**必须能被接手方用来复核**——也就是说，照着这几行，它能自己确认「文档说的和现实一致」。

```bash
# 交接那一刻取坐标，把输出里的关键行贴进文档
git status --short
git rev-parse --short HEAD
git branch --show-current

# 未提交的改动不要只写「有一些改动」，导出成可读的清单
git diff --stat
```

**反例**：

- ✗ 「代码写得差不多了。」——接手方不知道从哪开始，只能重看一遍。
- ✗ 「当前在 `feature/export` 上。」——没有提交号，等它接手时分支可能已经变了，而它无法判断文档是否过期。
- ✓ 「分支 `feature/export-fix`，提交 `a1b2c3d`。接口层改完，单测 12 条过 6 条，第 7、9、12 条失败。工作区干净。阻塞：需要运维开通对象存储的临时凭证，已跟（对接人）提了，等他回复。」

---

### 字段 2 · 下一步

**回答**：我现在具体该做什么？做完怎么算做对了？

**必须包含**：

- **一个动作**（不是一句方向）：动哪个文件的哪个位置、改成什么。
- **一个验证方式**：跑哪条命令、看什么现象、看到什么就算成了。
- **一个失败的退路**：如果这一步不成立，看哪个字段（通常是「踩过的坑」第 N 条）。

**颗粒度**：1~3 步。**只写最近的 1~3 步**，不要写完整路线图——三步之后的事情你现在判断不准，写了反而会误导接手方。

写法公式：

```
下一步：<对哪个对象的哪个位置> 做 <什么动作>
验证：跑 <命令 / 操作>，看到 <期望现象>
不成的话：看「踩过的坑」第 N 条 / 问 <某角色>
```

**反例**：

- ✗ 「继续把剩余用例修通。」——修正的方式有十种，接手方会挑你不认同的那一种。
- ✗ 「优化一下性能。」——优化到什么指标？用什么手段？边界在哪？
- ✓ 「下一步：把 `src/export/csv.ts` 里 `writeChunk` 的 `MAX_ROWS` 从 5000 降到 1000，重跑 `npm run test:export`。验证：12 条用例全绿，且 `export-time.log` 里单批耗时 < 200ms。不成的话：如果第 7 条还失败，看『踩过的坑』第 2 条——它八成不是批次大小问题。」

---

### 字段 3 · 已完成

**回答**：哪些不用重做？

**必须包含**：

- **产出物 + 状态**：做完了什么，落到哪个文件 / 哪个提交 / 哪个交付物上。
- **验证到什么程度**：只是写完了？跑过一次？通过了完整测试？**没验证过的不要说「已完成」**。
- **如果是探索性的**：明确写「试过但没留下代码，结论在『踩过的坑』里」。

**颗粒度**：每条一行，3~8 条。超过 8 条说明该按子系统分组，或该拆成多份交接。

**关键点**：这个字段的主要价值不是邀功，是**防止接手方重做**。所以对「已完成」的定义要严格——**没验证过的一律归到「未完成」**，哪怕代码已经写完了。

**反例**：

- ✗ 「导出的主体逻辑写完了。」——「主体」是指哪部分？验证过没有？
- ✓ 「`csv.ts` 的流式写入已实现并通过 6/12 条用例（提交 `a1b2c3d`）。`export-time.log` 的记录逻辑已接好，只是还没在高数据量下实测（→ 归入未完成）。」

---

### 字段 4 · 未完成

**回答**：哪些还没做？为什么没做？

**必须包含**：

- **未完成项清单**，每条带上「为什么还没做」：没时间 / 卡住了 / 等外部条件 / 本来就不在范围里。
- **区分「没做」和「做了但没好」**——后者往往比前者更危险，因为接手方会以为它是完成的。
- **如果是主动排除的**（决定不做），要标明并指向「关键决定与理由」，别让接手方又把它捡回来。

**颗粒度**：每条一行，与「已完成」一一呼应。

**反例**：

- ✗ 「还有一些边界情况没处理。」——哪些情况？接手方得自己找。
- ✓ 「大文件（>2GB）路径未处理——当前实现会整块载入内存，需要改成流式，属于未做（不是做坏）。原因是这次会话时间不够，方案已经想清楚，见『关键决定与理由』第 3 条。」

---

### 字段 5 · 关键决定与理由

**回答**：为什么是现在这个样子？为什么不能换别的做法？

**必须包含**：每条决定写成三件事：

| 要素 | 说明 |
|---|---|
| 决定了什么 | 一句话，可验证的事实 |
| 为什么 | 约束是什么——性能、兼容、时间、外部依赖 |
| 否掉了什么 | **另一个看起来同样合理的方案，以及它被否的原因** |

第三条是这个字段存在的全部理由。**只写「我们用了方案 A」等于没写**——接手方看到 A 觉得别扭，就会换成 B，把你好不容易排除的路再走一遍。

**颗粒度**：只写**会改变接手方行为的**决定。有 3 条就写 3 条，不要凑数。判断方法：如果接手方换个做法也能达到同样结果、且代价可接受，那这条决定就不必写。

**反例**：

- ✗ 「我们决定用流式写入。」——为什么？换缓冲批量写不行吗？
- ✓ 「决定用流式写入而非『整块读入再切片』（提交 `a1b2c3d`）。理由：目标文件峰值 4GB，整块读入会 OOM，实测在 2GB 时进程被系统杀掉。否掉了切片批量写：它能省内存，但需要额外的偏移量管理，且当前数据源不支持按偏移量重读。**别改回批量读**，除非数据源先支持随机读。」

---

### 字段 6 · 踩过的坑

**回答**：哪些路已经证明走不通？看到什么现象说明我在踩这个坑？

**必须包含**：每条坑写四件事：

1. **现象**：看到什么报错 / 什么反常表现（这一步最重要，是接手方的识别器）
2. **原因**：真实原因是什么
3. **为什么不显然**：为什么第一眼会误判
4. **怎么绕**：正确做法是什么

**颗粒度**：只写**「复现成本高」或「误导性强」**的坑。花五分钟就能自己发现的坑不必写——接手方自己会撞上，那不是浪费。

这是整份文档里**最不可替代的字段**。所有能从仓库重建的信息都不值钱，坑不行：它分散在几十次失败的尝试里，重来一遍的代价就是几十次失败的尝试。**宁可这一节写长，也不要为了篇幅把它压掉。**

**反例**：

- ✗ 「缓存那边有点问题。」——接手方不知道是什么问题、什么时候会遇到。
- ✓ 「坑 1：**单测在第 7 条随机失败**。现象：`test:export` 第 7 条时过时不过，日志里是 `ECONNRESET`。原因：测试用的 mock 服务在用例间没重置连接池，上一条用例的残留连接被复用。为什么不显然：报错指向网络层，第一反应会去查超时配置（我在这上面花了快两小时，改了三次超时值都没用）。怎么绕：在 `beforeEach` 里重置连接池，见 `test/export.spec.ts:24`。」

---

### 字段 7 · 待确认问题

**回答**：我拿不准的、需要问人的，该问谁？

**必须包含**：每条问题写三件事——**问题本身 + 为什么悬着 + 该问谁 / 该看哪里**。

**没有就写「暂无」**，不要留空。

**颗粒度**：1~5 条。超过 5 条往往说明任务本身还没到能交接的状态——先把问题问清楚再交接，比交接一堆问号更有用。

**为什么必须带负责人**：没有负责人的问号等于把皮球踢给接手方。它既不知道问谁，也不好意思问，最后要么猜、要么卡住。

**反例**：

- ✗ 「不确定要不要兼容旧格式。」——该问谁？为什么不确定？不兼容的代价是什么？
- ✓ 「问题 1：导出格式是否要兼容旧版的 `v1` 表头？悬着的原因：现有客户里有 3 家在用 v1，但我拿不到他们的使用数据，无法判断影响面。该问：（产品负责人角色）——他手上有客户版本分布；或在（内部数据平台）查 `export_version` 的调用分布。」

---

### 字段 8 · 相关文件索引

**回答**：我该看哪些文件？

**必须包含**：一张表，每行是**具体路径**加**一句为什么看它**。

| 路径 | 为什么看 |
|---|---|
| `src/export/csv.ts` | 主要修改点，`writeChunk` 是下一步的目标 |
| `test/export.spec.ts:24` | 坑 1 的修复位置 |
| `docs/export-format.md` | 目标格式定义，动手前先看 |
| （任务单链接） | 需求原文与验收标准 |

**颗粒度**：3~8 行。**只列接手方真的需要打开的**，不要把整个模块目录列一遍。

**关键点**：这个字段的判据是**「能不能直接定位」**。写路径不够，要写清**在这个文件里看什么**。

**反例**：

- ✗ 「相关代码在 `src/` 下面。」——等于没说。
- ✗ 「导出相关文件见仓库。」——同上。
- ✓ 见上表。

## 四、必要性的唯一判据

判断一条信息该不该写，只有一个问题：

> **接手方缺了这条信息，会不会卡住、做错、或者重做？**

会，就写。不会，就删。就这么简单。

但如果只有这一句，实操时依然会犹豫。下面把它展开成五个具体的问法。

### 五问判据

| # | 问法 | 答「是」→ | 答「否」→ |
|---|---|---|---|
| 1 | 缺了它，接手方会**卡住不动**吗？ | 必须写（起点、坐标、阻塞） | 继续问 |
| 2 | 缺了它，接手方会**重复已完成的工作**吗？ | 必须写（已完成、未完成） | 继续问 |
| 3 | 缺了它，接手方会**选错方案 / 重走错路**吗？ | 必须写（关键决定、踩过的坑） | 继续问 |
| 4 | 缺了它，接手方**花时间也能自己查到**吗？ | **可不写**，只给指针 | 继续问 |
| 5 | 缺了它，接手方的行为**完全不变**吗？ | **不写** | 写成一句结论 |

第 4 问和第 5 问是最常被忽略的两条。人们的默认反应是「多写点总没错」，但**交接文档的敌人不是遗漏，是稀释**：关键的那三句被埋在六十行背景介绍里，接手方（尤其是 Agent）会只读到一半，或者按错误的重点执行。

### 必须写 / 可不写 对照表

| 类型 | 必须写 | 可不写（给指针即可） | 绝对不写 |
|---|---|---|---|
| 状态 | 分支、提交号、未提交改动、阻塞项 | 完整的 `git log` | 逐日时间线 |
| 代码 | 改动的**意图**与**位置** | 改动内容的粘贴 | 大段代码复制 |
| 决定 | 决定了什么 + 为什么 + 否掉了什么 | 行业通用做法 | 没有结论的讨论过程 |
| 错误 | 现象 + 原因 + 绕过方式 | 完整的报错堆栈（除首行） | 「有问题」「注意一下」 |
| 计划 | 最近 1~3 步 + 验证方式 | 三步之后的路线图 | 「继续优化」「完善一下」 |
| 背景 | 会影响判断的业务约束 | 项目简介、行业背景 | 从官方文档抄来的定义 |
| 人 | 该问谁、该等谁 | 团队分工介绍 | 评判同事的表达 |
| 凭证 | 在哪拿、由谁发放 | — | **任何密钥、Token、密码内容** |

### 三个概念辨析

实操里最容易写错的三种东西，它们的正确处理方式完全不同：

**否定性事实 vs 待办事项。** 「我试过 A 方案，不行」不是待办，是坑。写成待办会让接手方误以为还要去做。**否定性事实要归到「踩过的坑」，不能混进「未完成」。**

**决定 vs 偏好。** 「用流式写入」是决定（有约束支撑）。「我觉得变量名该短一点」是偏好。偏好不该写进交接文档——它不改变接手方能否做成这件事，只会让它觉得被挑剔。

**共识 vs 猜测。** 只有**确认过**的事实才能写成陈述句。你自己的推断要显式标注：「我推断（未验证）：……」。**未标注的猜测会被当成事实执行**，这是比信息缺失更严重的交接事故。

## 五、文档膨胀的四种症状

写完之后扫一遍，命中任何一条就动手裁。

| 症状 | 长什么样 | 代价 | 修法 |
|---|---|---|---|
| **流水账** | 「上午看完需求，下午开始改接口，晚上发现缓存问题」 | 掩盖了真正的状态；接手方以为在了解进度，其实什么都没记住 | 全部删掉，只保留「现状」里那个可复核的坐标 |
| **代码转贴** | 把 diff、函数体、报错堆栈整段贴进文档 | 行数暴涨，而且**会过期**——代码一改，文档就在骗人 | 只留路径 + 行号 + 一句「改什么、为什么」，代码去仓库看 |
| **覆盖性免责** | 「由于时间关系，可能还有一些细节没覆盖到，具体请自行判断」 | 零信息量，还占了读者注意力 | 要么写成具体的未完成项，要么删掉 |
| **防御性叙述** | 反复解释「当时我也是没办法才这样」 | 把交接文档写成自我辩护，接手方抓不到重点 | 换成「关键决定与理由」里的那三要素，不带情绪 |

**目标长度参考**：标准档 40~80 行，轻量档 10~25 行。**超过 100 行的交接文档，接手方（不管人还是 Agent）都只会跳读**——这时候问题不在写法，在你该做分级交接。

---

## 六、分级交接：三档怎么选

不是每个任务都值得一份完整文档。**写一份用不上的长文档，和没写一样糟。**

| 档位 | 什么时候用 | 长度 | 字段 |
|---|---|---|---|
| **轻量档** | 单点任务、一个人接着干、半天内能说完；或只是换会话、换人继续同一件事 | ≤ 25 行 | 元信息 + 现状 + 下一步 + 踩过的坑（有则写） |
| **标准档** | 多人协作、任务跨几天、有明确交付节点；**默认用这一档** | 40~80 行 | 全八字段 |
| **完整档** | 任务跨周、跨子系统、要长期存档或正式移交 | 100~200 行，或拆成多份 | 全八字段 + 分段进度 + 风险与依赖 + 决策记录附录 |

**怎么降档**：如果一件事只交接一次、接手方就是坐在你旁边的人，用轻量档。多写的部分它不会读。

**怎么升档**：出现下面任一情况就升档——接手方**不在同一时区**（要异步、要自解释）、任务**会被多个人依次接手**（要有决策记录，否则每个人的理解都会漂移一点）、或者任务**要存档超过一个月**（现状会过期，必须写得足够自足）。

**文档装不下怎么办**：拆。优先按「子系统」或「阶段」拆，拆完在每份的开头用两行写清它属于哪条线、前后是哪份。**不要按时间拆**——时间线是最难用的索引。

---

## 七、和其他协作文档的分工

同一件事被反复写三遍是常见的浪费。划清边界：

| 文档 | 读者 | 回答的问题 | 不回答 |
|---|---|---|---|
| **交接文档** | 接手这个任务的人 / Agent | 我现在该做什么，怎样才能不重走错路 | 项目整体进展、远期规划 |
| **周报 / 进度汇报** | 上级、周边协作方 | 这个周期整体推进了什么 | 具体怎么动手、技术细节 |
| **变更日志** | 下游使用者、后续排查的人 | 行为变了什么（对外可见的部分） | 内部实现路径、走过的弯路 |
| **提交信息** | 未来排查问题的人 | 这一次改动为什么必要 | 整个任务的上下文 |
| **代码注释** | 读这段代码的人 | 这里的实现为什么是这样 | 任务层面的判断和取舍 |
| **任务单 / 需求文档** | 需求提出方与实现方 | 要做成什么样、验收标准是什么 | 做到一半时的实际状态 |

**由此推出的实用规则**：

- 交接文档**不重复**需求文档的内容，只写一个链接加一句「验收标准在那份里」。
- 交接文档**不重复**变更日志的条目，只说「已完成的部分已记在变更日志的哪一版」。
- 交接文档里的决定，如果值得长期留存，应该**同时**进决策记录；交接文档只是这次的快照。
- **一个任务的交接文档应该只有一份、一个写作者。** 两个人各写一份必然冲突，冲突的合并成本高于交接本身。

## 八、交接的时机与动作

### 该交接的四个信号

出现任一条，就该拿出这套规范：

1. **对话长度接近上限**——别等到被截断才写，那时你已经写不全了。
2. **任务要转给另一个人或另一个 Agent**——不管交接时间有多短，坑和决定都得落纸。
3. **任务要停超过两天**——未来的你自己也是接手方，而且比谁都更容易高估自己的记忆力。
4. **两个人要并行改同一个任务**——先约定边界和接口，把边界写进「关键决定的约束」里，否则必然互相覆盖。

### 交接方：交出去之前的四个动作

1. **冻结状态**。取分支名、提交号、未提交改动清单。决定未提交改动的去向：提交、暂存、还是明确标注为「不要的试验」。
2. **先写「下一步」和「踩过的坑」**。这两节决定交接成败，放在最前面写能逼自己想清楚。其余字段是给它们做支撑的。
3. **过裁剪判据**。逐句问「删掉它，接手方的行为会变吗」，然后看长度是否落在档位区间内。
4. **要一个回执**。交接时明确说：「你看完告诉我第一步打算做什么。」**对方的复述就是验收信号**。

### 接手方：开工之前的四步复核

交接文档是快照，会过期。接手方不要直接照着干，先做这四步：

1. **核对坐标**：文档里的提交号还在吗？分支还是那个分支吗？工作区和文档说的一致吗？不一致就**先问，别猜**。
2. **复核「已完成」**：挑一条已完成项，把它的验证方式重跑一遍。过了，说明文档可信；没过，整份文档的可信度都要打折。
3. **确认「未完成」的当前状态**：未完成项里，有没有其实已经被别人做掉了的？
4. **把待确认问题排在动手之前**：这些问题的答案可能会改变「下一步」本身。**先问，再动手。**

## 九、四种场景的差异

同一套字段，四种场景的侧重不同。

### Agent → Agent（换会话、子任务交回主任务）

**特点**：接手方没有对话历史，也不会追问；它会把文档当成全部事实，然后直接开干。

- **必须显式写出「哪些信息已经丢失」**。你对话里那些「我们讨论过」的内容，对接手方是真的不存在。凡是只存在于对话历史里的结论，必须落纸，否则等于没说过。
- **「下一步」要写成带命令的**，Agent 可以直接执行。
- **「关键决定」要写明「别改成什么」**，因为 Agent 很容易按它认为更优的方式重构。
- **不确定的要标 `推断（未验证）`**。Agent 不会像人一样对模糊表述保持警惕，它会直接当成事实。

### 人 → Agent

**特点**：你的隐式知识（行业惯例、团队默契、老板的偏好）对接手方完全隐形。

- 把你认为「这不是常识吗」的东西**显式写下来**——对 Agent 来说它们不是常识。
- 给**明确的验收命令**，不要给「看着没问题就行」。
- 「待确认问题」宁可多写几条：Agent 不会去打听，但它可以按你给的指向去查。

### Agent → 人

**特点**：人不会逐字读完，只会跳读；而且它会追问。

- **把「下一步」放最前面**，甚至单独一句话顶在文档开头。
- 长度更要克制：**人读 20 行是上限**，超了就该口头讲。
- **必须留一次口头答疑**。文档负责让口头沟通变短，不负责替代它。

### 人 → 人（并行协作）

**特点**：双方都能读代码，但会同时改同一片区域。

- 「关键决定」里补上**边界约定**：谁改哪个目录、哪个文件不要两个人同时动。
- 「现状」里补上**对方需要知道你正在做什么**——避免你还在改的地方被对方重构掉。
- 约定**只有一个人写交接文档**，另一人只读。

## 十、自检：如果接手方只能做一件事，你的文档该指向哪

这是一组快速定位问题出在哪个字段的诊断表。**拿一份写好的交接文档，逐行对照。**

| 如果你发现接手方会…… | 说明缺的是 | 回去补 |
|---|---|---|
| 不知道该干什么，在原地打转 | 起点 | 「现状」+「下一步」 |
| 重复做已经做完的事 | 进度 | 「已完成」（且要严格区分是否验证过） |
| 重新纠结你早就定好的事 | 依据 | 「关键决定与理由」里的「否掉了什么」 |
| 又踩了一遍你踩过的坑 | 陷阱 | 「踩过的坑」（重点补「现象」） |
| 找不到该改的文件 | 导航 | 「相关文件索引」（补「在这个文件里看什么」） |
| 不知道自己能改什么、不能改什么 | 边界 | 「交接元信息」的权限与约束 |
| 把不确定的东西当确定的事实执行 | 置信度 | 给推断加 `（未验证）` 标注 |
| 把整个任务重做一遍 | 起点 + 进度 | 「现状」的坐标 + 「已完成」清单 |
| 卡在一个你本来就知道答案的问题上 | 悬置 | 「待确认问题」+ 负责人 |
| 读了两遍还是不知道重点在哪 | 稀释 | 过一遍第五节的四种膨胀症状，砍掉一半 |

**判据用一句话收尾**：

> **交接成功 = 接手方不问你任何问题，就能开始做，而且做的正是你想让它做的那一步。**

做不到，就是某个字段没写透。**不要靠加字数补救，要回去查是哪个字段。**
