# 交接质量自检清单

这份文件解决一个问题：**怎么知道这次交接成了没有。**

分三层：**四问验收法**（5 分钟，交接完立刻做）、**24 条清单**（交接前逐条打勾）、**事故对照表**（出问题了回来查是哪一条漏了）。

---

## 一、四问验收法

交接是否成功，不看文档写得多漂亮，看**接手方能不能只靠它开工**。四问就是这个判断的操作化。

四问按顺序做，任何一问过不去，就停下回去补对应字段——**别往下走**，因为后面三问都建立在第一问通过的基础上。

### 第 1 问 · 定位问题（它知道自己在哪吗）

> 把文档给一个没参与这个任务的人或 Agent，只让它读文档、**不许看代码**，然后问：「这个任务现在走到哪了？」

**通过标准**：它说出的话里包含一个**可复核的坐标**——分支名、提交号、或明确的当前产出物版本。

**不通过的长相**：「正在开发中」「在改导出模块」「应该快好了」——这些都不是坐标，是印象。

**回去补**：「现状」字段。补上分支、提交号、以及未提交改动的清单。

### 第 2 问 · 行动问题（它知道下一步做什么吗）

> 接着问：「你打算做的第一件事是什么？」

**通过标准**：它说出的是一句**能照着做的动作**——改哪个文件的哪个位置、改成什么、跑什么命令验证。

**不通过的长相**：它说出了方向（「先把测试修好」），但说不出**具体动什么**。这说明它得自己重新设计一遍方案——你已经想清楚的事情被丢了。

**回去补**：「下一步」字段。把「方向」改写成「动作 + 验证 + 退路」。

**这一问是四问里最重要的一问。** 它不通过的交接，等于没交接。

### 第 3 问 · 避坑问题（它知道哪些路不用走吗）

> 接着问：「你觉得有哪些看起来可行、但其实已经试过不行的做法？」

**通过标准**：它能说出至少一条你写下的坑，或者一条你否掉的方案，**并说出为什么**。

**不通过的长相**：它提出一个明显是你已经试过的方案，或者对限制条件一无所知。

**回去补**：「踩过的坑」和「关键决定与理由」里的「否掉了什么」。注意：**只写「我们用了 A」不算通过**——必须写出「为什么不用 B」，否则接手方看到 A 觉得别扭就会换成 B。

### 第 4 问 · 求助问题（它知道该找谁吗）

> 接着问：「有哪些事是你自己做不了决定的？你打算怎么处理？」

**通过标准**：它至少能指出一个「待确认问题」，并说出该问谁 / 该看哪里。

**允许不通过的情况**：如果这个任务确实没有悬而未决的问题，它可以回答「没有要问的」。但这时你要反过来验证一下——**真的有任务一个悬置问题都没有吗**？通常至少会有「验收标准谁来确认」这类问题。

**回去补**：「待确认问题」字段，以及每条问题后面的负责人。**没有负责人的问号等于把皮球踢给对方。**

### 四问结果怎么读

| 通过情况 | 说明 | 动作 |
|---|---|---|
| 四问全过 | 交接成功 | 交出去 |
| 第 1 问不过 | 接手方连起点都不知道 | 补「现状」。**这是硬伤，必须补** |
| 第 2 问不过 | 交接失败 | 补「下一步」。其他字段写得再好也救不回来 |
| 第 3 问不过 | 会重走错路 | 补「踩过的坑」的「现象」，和「关键决定」的「否掉了什么」 |
| 第 4 问不过 | 会卡在悬置问题上 | 补「待确认问题」和负责人 |
| 第 2 问单独过、其余不过 | 能开工但会走弯路 | 可以交，但明确告诉对方「坑和决定我写得少，你遇到反常多问我」 |

### 自己当接手方（拿不到回执时）

如果对方不配合复述，退而求其次：**隔一天再读自己的文档**。具体要求：

1. 只读文档，**不看代码、不看自己的记忆**。
2. 出声回答上面四问。
3. 卡在哪一问，就是哪个字段没写透。

隔一天读很有用，因为你对这个任务的「残存记忆」会衰减到接近接手方的水平。**当天写完当天读，你会不自觉地补上文档里没写的东西**，测不出来。

## 二、24 条清单

交接前逐条打勾。按字段分组，最后四条是跨字段的红线。

### 元信息（3 条）

- [ ] 任务名具体到能认出是哪一个任务，不是「XX 相关工作」
- [ ] 任务状态从「进行中 / 阻塞 / 待评审 / 近完成」里选了一个，**没写「顺利推进」这类形容词**
- [ ] 权限与约束写清了：哪些能改、哪些只读、哪些不能碰，**并给出了「不能碰」的理由**

### 现状（3 条）

- [ ] 有可复核的坐标（分支名 / 提交号 / 产出物版本），接手方能自己核对
- [ ] 进度是「什么做完了、什么还差、卡在哪一步」，不是一句「进行中」
- [ ] 未提交 / 未落地的改动单独列了出来，并说明了**去向**（提交 / 暂存 / 丢弃）；确实没有则显式写「无」

### 下一步（3 条）

- [ ] 写的是动作（动哪个位置、改成什么），不是方向（「优化一下」「继续做」）
- [ ] 带验证方式：跑什么、看到什么算成了
- [ ] 只写最近 1~3 步，**没有把三步之后的路线图也写进来**

### 已完成 / 未完成（4 条）

- [ ] 「已完成」每一条都标了验证程度（写完未跑 / 跑过一次 / 通过完整测试）
- [ ] **没验证过的东西没有被写成「已完成」**——它应该出现在「未完成」里
- [ ] 「未完成」每条都写了为什么还没做（没时间 / 卡住 / 等外部条件 / 主动排除）
- [ ] 主动排除的事项标明了「不是遗漏」，并指向了对应决定

### 关键决定与理由（3 条）

- [ ] 每条决定都配了「为什么」（约束是什么）
- [ ] **每条决定都写了「否掉了什么」以及被否的原因**——这是这个字段存在的理由
- [ ] 只写了会改变接手方行为的决定，**没有把顺手的做法也包装成「决定」**

### 踩过的坑（3 条）

- [ ] 每条坑都写了**现象**（看到什么报错 / 什么反常表现），接手方靠它才能识别
- [ ] 每条坑都写了「为什么不显然」——写不出来的坑通常不值得写
- [ ] 每条坑都给了绕过方式，并带上路径或行号

### 待确认问题与文件索引（3 条）

- [ ] 每个待确认问题都配了负责人或查询入口，没有光留问号
- [ ] 确实没有悬置问题时，**显式写了「暂无」**，不是留空
- [ ] 文件索引给的是具体路径（必要时带行号 / 函数名），并且写了「在这个文件里看什么」

### 跨字段红线（4 条）

- [ ] **零凭证**：没有任何真实密钥、Token、密码、Cookie、内网地址、客户名、真实姓名
- [ ] **零猜测冒充实测**：所有推断都标了 `（未验证）` / 「我推断」，没有任何未标注的猜测写成陈述句
- [ ] **零时间线**：删掉了「上午做 A、下午做 B」这类改变不了接手方行为的内容
- [ ] **长度守约**：轻量档 ≤ 25 行，标准档 ≤ 80 行；超了已经做过裁剪或分级，而不是靠压缩措辞

## 三、常见交接事故对照表

出问题了回这里查。**左列是接手方真实会说的话**，从这些话反推是哪一条漏了。

| 接手方会说的话 | 真实原因 | 漏掉的字段 / 条目 |
|---|---|---|
| 「我不知道从哪开始。」 | 没给起点坐标 | 现状 · 坐标 |
| 「我先看一下代码吧。」 | 「现状」太抽象，它只能自己去读 | 现状 · 进度一句话 |
| 「这个功能我实现了……咦，已经有了？」 | 已完成项没写，或没标验证程度 | 已完成 |
| 「我按我的想法重构了一下。」 | 决定没写理由，或没写否掉了什么 | 关键决定与理由 |
| 「这个报错我查了两小时。」 | 坑只写了结论，没写现象 | 踩过的坑 · 现象 |
| 「我不知道该问谁。」 | 待确认问题没配负责人 | 待确认问题 |
| 「我找到相关代码花了好久。」 | 文件索引写成「在 src 下面」 | 相关文件索引 |
| 「这跟文档里说的不一样啊。」 | 文档过期，或未提交改动没交代 | 现状 · 未提交改动 |
| 「我改了一个文档说不能改的地方。」 | 权限约束没写，或没写理由 | 元信息 · 权限与约束 |
| 「我以为那个是确认过的。」 | 推断没标注，被当成了事实 | 跨字段红线 · 零猜测冒充实测 |
| 「这份文档我读了两遍还是抓不到重点。」 | 文档膨胀，关键信息被稀释 | 裁剪（四种膨胀症状） |
| 「我把整个任务重做了一遍。」 | 现状 + 已完成都不可用 | 现状 + 已完成 |
| 「我改完之后发现和你已经改的地方冲突了。」 | 并行协作用了人交接模板，没写边界约定 | 场景差异 · 人 → 人 |

**这张表的用法**：每次交接完之后，如果接手方说了上面任何一句话，回来把对应的字段补进**下一次**的交接里。**事故清单比规范条文更容易记住**，几轮之后这套规范就变成你的习惯了。

## 四、交接后复盘模板

重要任务的交接（完整档）值得花 5 分钟复盘。落成几行字，下次交接直接受益。

```markdown
# 交接复盘：<任务名>（<日期>）

**交接档位**：轻量 / 标准 / 完整
**实际交接耗时**：__ 分钟

## 四问验收结果

| 问 | 结果 | 卡在哪 |
|---|---|---|
| 1 定位 | 过 / 不过 | |
| 2 行动 | 过 / 不过 | |
| 3 避坑 | 过 / 不过 | |
| 4 求助 | 过 / 不过 | |

## 接手方实际问了什么

- 【它真的来问的问题；没有就写「一次都没问」】

## 文档缺了什么

- 【复盘时发现该写没写的】

## 文档多了什么

- 【接手方明确说不需要、或者明显没读的部分】

## 下次改一条

- 【只写一条最该改的；写多了等于没改】
```

**「接手方实际问了什么」这一栏是整份复盘里最值钱的。** 它问的每一个问题，都是文档某处的空白——而这些问题是你自己测不出来的，因为**你不知道自己不知道什么**。

**「下次改一条」为什么只写一条**：交接文档的质量提升靠的是几条真正被执行的规则，不是一份完美的清单。写五条你一条也不会记住。

---

## 五、给别人的交接挑毛病：三条快速判断

如果别人把一份交接文档递给你，你要在 30 秒内判断它靠不靠谱，看这三个地方：

**第一眼 · 找「下一步」。** 找不到，或者找到的是一句方向描述——**直接打回**。这一条不过，其他都不必看。

**第二眼 · 找「否掉了什么」。** 在「关键决定」里搜否定词（「没有选」「不用」「排除」）。一条都没有，说明这份文档只写了结果没写约束，你一定会在某个地方重新纠结一遍。

**第三眼 · 找数字和路径。** 分支名、提交号、文件路径:行号、命令。全是抽象描述的文档，说明作者其实没在具体地做这件事——或者它懒得把已经清楚的东西写清楚。

**三条全过**，这份交接可以接。**过两条**，可以接，但接之前把缺的那一块当面问清楚——**别对着文档猜**。
