# 三剪客 · 任务交接文档

把进行中的任务整理成一份交接文档，让另一个 Agent 或另一个人能无损接手

上下文是会丢的，而且丢得比你以为的早。会话窗口滚过去就回不来了，换个人接手时「他脑子里的那部分」根本传不过去，多个人并行改同一个任务时，谁也不知道对方试过什么、为什么放弃。真正的代价不是重写那几行代码，是**把已经排除的错路又走一遍**。

这套 Skill 给的不是一份文档模板，而是一套**交接协议**：八个字段各自回答接手方心里的哪个问题、什么信息必须落到纸上、什么信息写上去只会稀释重点、交接完怎么验收「这次交接算不算成功」。

**读完你会拿到**：3 份参考文件（字段规范 / 模板与示例 / 自检清单）、1 个可复制的文档骨架、1 张「必须写 / 可不写」判据表、1 套 15 分钟交接流程。

## 触发场景

- 「这个对话太长了，我们开个新的继续——先把现在的情况写下来。」
- 「我要下班 / 休假 / 换项目了，这块活交给别人，怎么交代清楚？」
- 「上次那个 Agent 试了半天，我不知道它改了什么、为什么那些路走不通。」
- 「两个人同时在改这个任务，互相覆盖了，想定个分工和交接规矩。」
- 「这个任务卡住了，我要把它转给另一个 Agent 接手，得给它一份能直接开干的说明。」
- 「任务做了一半要延期，先存个档，下周回来我自己都忘了当时在想什么。」

## 快速开始

最小可用路径是**先写结论，再补事实**。全程 15 分钟，产出是一份能让接手方直接开工的交接文档，不是一份项目周报。

**第 0 步 · 先冻结（2 分钟）**

在动笔之前，把「现在这一刻」钉住，否则你边写边改，文档写完就已经和现实对不上了。

```bash
# 记录交接时刻的准确状态：分支、提交号、工作区是否干净
git status --short
git rev-parse --short HEAD
git branch --show-current
```

把命令输出里的关键几行直接贴进文档的「现状」字段。**未提交的改动要单独说明**：它在哪、改了什么、是否打算保留——这是交接事故的头号来源。

**第 1 步 · 写「下一步」和「现状」（最重要，5 分钟）**

按 `references/handoff-spec.md` 的字段表，先写这两个字段。原因：**接手方只要拿到这两个字段就能不卡壳地开始**，剩下的字段是让它可以少走弯路。先写它们，能逼你在一开始就想清楚「这次交接到底要交给对方做什么」。

「下一步」必须写成**可执行动作**，不是方向描述：

- ✗ 「继续优化一下同步逻辑。」
- ✓ 「下一步：把 `sync.ts` 里第 3 个分支的重试次数从 3 提到 5，然后跑 `npm run test:sync`。预期 12 条用例全绿；如果第 7 条仍失败，看『踩过的坑』第 2 条。」

**第 2 步 · 补完其余六字段（5 分钟）**

已完成 / 未完成 / 关键决定与理由 / 踩过的坑 / 待确认问题 / 相关文件索引。每个字段的边界、常见写法和反例见 `references/handoff-spec.md`。

**第 3 步 · 过裁剪判据（1 分钟）**

逐条问：「删掉这句，接手方的行为会变吗？」不会变的就删。判据表和「文档膨胀」的四种典型症状见 `references/handoff-spec.md`。**一份 300 行的交接文档不如一份 60 行的**——长文档里真正关键的那三句会被冲淡。

**第 4 步 · 走验收清单（2 分钟）**

用 `references/handoff-quality-checklist.md` 里的**四问验收法**自测。四问里任何一问卡住，说明对应字段还没写透，回去补那一节，不要靠加字数糊过去。

**第 5 步 · 交出去，并要一个回执**

把文档给接手方时，明确说一句：「读完告诉我你准备做的第一步是什么。」对方的复述就是这次交接的验收信号——**复述不出来，就是没交接成功，不是对方没认真读**。

## 能力边界

**覆盖**：

- 给出交接文档的**八字段规范**：每个字段回答接手方的哪个问题、写到什么颗粒度算够
- 给出**必须写 / 可以不写**的判据，以及把「工作日志」裁剪成交接文档的具体手法
- 提供可直接复制的**文档骨架**、逐字段写作提示，以及 Agent 交接、人交接两份完整样例
- 提供**交接质量自检清单**（24 条）与**四问验收法**，用来交接前自测、交接后复盘
- 提供**分级交接**策略：按任务规模选轻量 / 标准 / 完整三档，避免小任务写成长文
- 给出交接文档与周报、变更日志、代码注释、提交信息的**分工边界**，减少重复书写

**不覆盖**：

- **不替你判断任务该不该交接、交给谁。** 谁合适、要不要拆成两个人接，是管理判断，本 Skill 只解决「交出去的信息怎么不丢」。
- **不生成任务本身的技术方案。** 它不会告诉你那个 bug 该怎么修、架构该怎么选；它只确保你**已经做过的判断和试过的事实**不丢失。
- **不做状态同步工具。** 没有守护进程、没有看板集成、不监听仓库变化。「现状」字段靠你在交接那一刻手工冻结，工具只帮你取分支名和提交号。
- **不做权限与访问控制。** 文档放在哪、谁能看，取决于你的仓库和协作平台设置，本 Skill 不做脱敏自动化检查。
- **不替代代码评审和测试。** 交接文档是给人读的上下文，不是质量门禁。要拦错误还得靠 CI、类型检查和测试。
- **不保证 Agent 一定照做。** 交接文档属于提示词层的约定，接手方理论上可以不遵守。需要硬约束的，请写进任务单的分派规则或自动化流程。

## 依赖条件

- **必需**：能读写 Markdown 文件。纯文本即可，不需要额外工具链。
- **必需**：一个你说了算的存放位置。放仓库里跟着代码走版本是最稳的；放协作平台也可以，但要保证接手方拿得到链接。
- **推荐**：git。能拿到准确的分支名、提交号、未提交改动清单，「现状」字段的可信度会高一个档次。
- **推荐**：一个会读交接文档的接手方——人或 Agent 都行。**人交接时要口头过一次「下一步」**，因为人不会逐字读完 60 行。
- **不需要**：网络、API Key、数据库、Docker、任何付费服务。

## 已知限制

1. **交接文档是快照，不是实时状态。** 文档写完的那一刻就开始过期。交接和接手之间隔得越久，「现状」字段越不可信，接手方必须自己复核一遍分支和提交号。
2. **隐性经验仍然会丢。** 「我感觉这个方案不太对但说不上来」这类判断很难落纸。写下来也可能被接手方当成噪音。这类信息建议在交接时**口头补一句**，别指望文档。
3. **长任务写不进一份文档。** 超过两三周、跨多个子系统的任务，硬塞进一份文档会得到一份没人读完的长文。必须按 `references/handoff-spec.md` 的分级策略拆成多份，或只交接当前的「作战面」。
4. **八字段不是万能骨架。** 它是通用任务的默认形状。研究型、设计型、纯沟通型任务可能需要增删字段——**判据（删掉会不会改变行为）比字段表本身重要**。
5. **四问验收依赖接手方配合。** 如果对方没有复述，你就拿不到验收信号。这时退而求其次：自己扮演接手方，只读文档、不看代码，看能不能说出下一步。
6. **不做多份交接文档的合并。** 两个人各自写了一份交接、内容冲突时，怎么合并不是本 Skill 解决的问题；建议交接前先约定只有一个写作者。

## 自检清单

交接文档交出去之前，逐条打勾。完整的 24 条清单和四问验收法见 `references/handoff-quality-checklist.md`，这里是最关键的 12 条。

- [ ] **下一步可执行**：写的是一个动作加一个验证方式，不是一句方向描述
- [ ] **现状被冻结**：带分支名 / 提交号 / 时间点，未提交的改动单独说明了去向
- [ ] **完成与未完成成对**：「未完成」不是「其他」，而是接手方要接着干的那几项
- [ ] **决定带理由**：至少写了「为什么没选另一个方案」，否则接手方会重新纠结一遍
- [ ] **坑带现象**：写的是「看到什么现象说明踩了哪个坑」，不是「某某模块有问题」
- [ ] **待确认带负责人**：每个悬而未决的问题都写了该问谁 / 该看哪里，没有光留问号
- [ ] **文件索引能定位**：给的是具体路径（必要时带行号或函数名），不是「相关代码在项目里」
- [ ] **凭证零内容**：只写「在哪拿、由谁发放」，没有任何真实密钥、Token、内网地址、客户名
- [ ] **无时间线流水账**：删掉了「上午做了 A，下午做了 B」这类改变不了行为的内容
- [ ] **长度守约**：标准档 ≤ 80 行，轻量档 ≤ 25 行；超了说明该裁剪或该分级
- [ ] **接手方能复述**：把文档给一个没参与的人 / Agent，它能说出第一步做什么
- [ ] **不用剧透也能读**：文中出现的每个代号、缩写、文件名，接手方第一次看到就懂
