# 版式与规格

> 这份文档给的是**数字口径**：画布多大、版心在哪、字号多少、上限怎么来的。
> 命令与参数见 `SKILL.md`；为什么这么设计见 `slide-design-method.md`。

## 一、画布

| 项 | 值 |
|---|---|
| 比例 | `16:9` |
| 目标像素 | **1920 × 1080** |
| 出图比例 | `16:9`（nano_banana 实查支持） |
| 格式 | PNG |

**产出的每一张 slide 都恰好是 1920×1080**——渲染后会**再用 `imgprobe` 复量一次**
真实像素并写进 `AUDIT.md`，不信"应该是对的"。

> 为什么不用 PPT 的 960×540 / 1280×720？投影仪与录屏的实际分辨率普遍是 1080p，
> 1920×1080 是**不缩放**的那个尺寸，文字边缘最锐利。

## 二、版心（safe area）

版心是**相对宽高**的比例，不是绝对像素：

| 边 | 比例 | 避开什么 |
|---|---|---|
| 上 | 7.0% | 课程 LOGO / 角标 |
| 下 | 8.6% | 页码与录制水印 |
| 左 | 5.4% | 投影裁边 |
| 右 | 5.4% | 投影裁边 |

换算到 1920×1080：**left = 104px，right = 1816px，top = 76px，bottom = 987px**。

选比例的而不是像素的理由：换画布尺寸（比如做成 4K）时版心自动跟着走，
不会出现"字号变了、版心忘了改"的不一致。

## 三、分区（两种版式）

### 3.1 有图版式（内容页）

```
┌──────────────────────────────────────────────────────┐
│  left=104                                    right=1816│
│  ┌────────────────────────┐   ┌──────────────────────┐│
│  │ 标题区                  │   │                      ││
│  │ ─── 强调短线            │   │   配图区             ││
│  │ ▪ 要点一                │   │   x: 1046 → 1816     ││
│  │ ▪ 要点二                │   │   y: 76   → 987      ││
│  │ ▪ 要点三                │   │                      ││
│  └────────────────────────┘   └──────────────────────┘│
│  文字区 x: 104 → 969（占 50.5%）  图区 1046 → 1816     │
│  三剪客 · 课程名                                4 / 7  │
└──────────────────────────────────────────────────────┘
```

- **文字区**：`x ∈ [104, 969]`，即画布宽的 **50.5%**；宽 **865px**
- **配图区**：`x ∈ [1046, 1816]`，即画布宽的 54.5%~94.6%；宽 **770px**，高 **911px**
- 文字区与图区之间留 **77px** 的呼吸位

### 3.2 无图版式（没配图的页）

- 文字区：`x ∈ [104, 104 + 1920×0.70]` = **[104, 1448]**；宽 **1344px**
- 图区不存在

> ⚠️ **为什么是 70% 而不是更宽**：早期放宽到 82%（≈35 字/行）时发现
> **闸门六（文字溢出）在无图版式下几乎永远不可能触发**——6 条 × 48 字也只排 12 行，
> 911px 的版心装得下。**一个打不响的闸门等于没有闸门**，
> 所以收到 70%（≈30 字/行）。这既让版面读得动，也让"内容太多"如实暴露出来。

### 3.3 居中版式（cover / section / summary）

- 文字区：`x ∈ [104+77, 1816−77] = [181, 1739]`；`y ∈ [76+65, 987−65] = [141, 922]`
- 配图**铺满整幅画布**（cover-fit 后居中裁），再叠一层**压暗层**（alpha 150）
- 标题与要点**整块居中**，块内**每条要点左对齐**、标记点对齐成一列

> 真机踩过：早期写成"每条要点各自居中"，结果标记点参差不齐、整页像没排版——
> 而闸门与像素检查全绿，**只有肉眼看图才发现**。

## 四、字号

| 用途 | 字号 | 字重来源 |
|---|---|---|
| 封页标题（`cover`） | **92px** | 系统字体本身（优先 `msyhbd.ttc` 粗体） |
| 章节页 / 小结页标题 | **71px**（= 62 × 1.15） | 同上 |
| 内容页标题 | **62px** | 同上 |
| 居中版式要点 | **40px** | 同上 |
| 内容页要点 | **42px** | 同上 |
| 页脚（品牌 + 页码） | **24px** | 同上 |

**字号是固定档位，不是"塞得下就无限放大"**——产出可复现。
塞不下就**拦截**，不缩字号（见第六节）。

### 行距与间距

| 项 | 算法 |
|---|---|
| 标题行距 | `glyph_height(font) + 10` |
| 要点行距 | `glyph_height(font) + 14` |
| 标题与要点之间 | `title_size × 0.52`（居中版式 `× 0.44`） |
| 要点之间 | `body_size × 0.42` |
| 要点标记宽度 | `body_size × 1.15` |

`glyph_height()` 用的是字形的**实际高度**（拿"字测国"三个满格汉字量），
**不是** `font.getmetrics()` 的 `ascent + descent`。

> ⚠️ 同族踩过：用 `ascent+descent`（实测 76px 字给 85+21=106）当行距，
> 而排版框按字形高（80）算 —— 两套口径，两行字就比框高出 26px、画到框外面去。
> 所以**框高与行距必须走同一个函数**。

## 五、上限与自洽性

| 项 | 上限 | 来源 |
|---|---|---|
| 页标题字数 | **30 字** | 30 × 62px = 1860px > 865px，所以 30 字一定会断行；两行是标题的上限 |
| 标题行数 | **2 行** | 三行标题会把要点挤出版心 |
| 每页要点条数 | **6 条** | 6 × 2 行 = 12 行，已接近版心容量的上限 |
| 单条要点字数 | **48 字（硬限）/ 40 字（建议）** | 见下 |
| 讲稿备注 | **80~400 字** | 少于 40 字告警；`--strict-notes` 下缺备注直接拦 |
| 配图意图 | **200 字** | 太短的画面描述出不了好图 |

### 硬限 48 字 vs 建议 40 字的来历

有图版式的可用断行宽度 = `865 − 48(marker) = 817px`。
42px 字号下一个汉字宽约 42px，所以 **≈19 字/行**。

- 40 字 → 3 行（19+19+2）→ 6 条 = 18 行 × 56px + 5 × 18px ≈ **1098px > 911px**（溢出）
- 48 字 → 也是 3 行

也就是说 **40 字以上在 6 条满编时必定溢出**。所以：
- **48 字是"结构闸门"的硬限**（单条超过它必拦，报出多出的那部分）
- **40 字是"写内容时的建议"**（提示词里要求模型遵守）

两道一起用：提示词让它别写长，闸门保证它写长了也进不了成品。

## 六、闸门六（文字溢出）到底怎么算

`plan_page()` 在**渲染之前**做一次确定性的排版预算：

```
可用高度 = bottom − top                          = 987 − 76 = 911px
标题高   = 标题行数 × (字形高 + 10)
间隔     = title_size × 0.52
要点高   = Σ(每条要点断行数) × (字形高 + 14) + 条数间空隙
需要高度 = 标题高 + 间隔 + 要点高
```

`需要高度 > 911px` → **拦截**，并逐条报出：

- 是标题的原因（断成几行 / 某一行实际多少像素）
- 还是某条要点的原因（实际多少字 / 多出哪几个字）
- 还是整块的原因（**实际需要多少 px、可用多少 px、超出多少 px**）

**绝不静默截断，也绝不自动缩字号。**

> 事故来源（同族刚翻过的车）：`sanjianke-xhs-note-factory` 1.0.4 及以前写的是
> `cover_text[:20]` —— 静默截断。用户改了文案、付了钱重出图，只有第 21 字之后被砍掉，
> 图看起来一模一样，用户以为"我的改动生效了"。本包从一开始就照修好的口径做。
>
> 而"自动缩字号"是同一个错误的变体：字缩到看不清，用户同样以为改动生效了。
> 所以本包连缩字号也不做——**只报数字，让你改内容**。

## 七、配色主题

| 主题 | 背景 | 标题 | 正文 | 强调 | 压暗层 | 适用 |
|---|---|---|---|---|---|---|
| `ink`（默认） | `#FAFAF8` | `#161A22` | `#3E4450` | `#CD4A36` | `#080A0E` α150 | 投影 / 打印 / 讲义 |
| `night` | `#12141A` | `#F6F7FA` | `#CCD2DE` | `#FF8C58` | `#000000` α150 | 录屏 / 直播间 |
| `warm` | `#FDF7F0` | `#3A281C` | `#68503E` | `#BE582A` | `#1C1008` α150 | 知识付费课程 |

居中版式压在图上时，标题与要点自动切到"图上色"（近白）+ 3px 深色描边 + 2px 投影偏移，
保证**压在照片上也读得清**。

## 八、配图规格与比例真伪

### 8.1 上游实测像素（1K 档）

上游**不是按比例给像素**，而是先定总像素、再把每边向下取整到 **32 的倍数**。
所以 10 种比例里有 5 种给不出像素级精确比例：

| 请求 | 真实像素 | 实际比例 | 与请求的偏差 | 是否精确 |
|---|---|---|---|---|
| `1:1` | 1024×1024 | 1.0000 | 0% | ✅ |
| `4:3` | 1184×864 | 1.3704 | 0.0% | ✅ |
| `3:2` | 1248×832 | 1.5000 | 0% | ✅ |
| `2:3` | 832×1248 | 0.6667 | 0% | ✅ |
| `16:9` | **1344×768** | **1.7500** | **1.56%** | ❌ |
| `9:16` | 768×1344 | 0.5714 | 1.6% | ❌ |
| `21:9` | 1536×672 | 2.2857 | 2.0% | ❌ |
| `3:4` | 864×1184 | 0.7297 | 2.7% | ❌ |
| `4:5` | 896×1152 | 0.7778 | 2.8% | ❌ |
| `5:4` | 1152×896 | 1.2500 | 0% | ✅ |

**这不是网关 bug**，是扩散模型按 32 对齐的常规做法。但它意味着
「请求比例 == 产出比例」这个断言对一半的比例天然不成立。

### 8.2 三条处理方式（缺一条闸门就会变成天天误报的噪音）

| # | 做法 | 说明 |
|---|---|---|
| a | 默认容差 **3%** | 容差内不算"假"，但**明确打印真实像素与偏差**，不藏 |
| b | 超容差 → 标红 + 退出码 3 | 真错必须拦（请求 `16:9` 却给 `1:1`，偏差 43.75%） |
| c | `--snap` 居中裁准 | 按请求比例精确裁掉多余像素 |

容差还有一条**地板 0.25%**：像素只能是整数，所以"裁到精确比例"本身就有量化误差
（16:9 裁后偏差 0.0925%，相邻整数像素间隔约 0.27%）。地板仍能抓住真错——
请求 `16:9` 却给 `4:3` 的偏差是 25%，比地板大 100 倍。

### 8.3 为什么 render 还要再读一次

`render` 是**最后一道防线**：图可能是别人给的、可能是断点里翻出来的旧文件、
也可能被手工替换过。所以 `render` **不信任 `images` 的结论**，
自己用 `imgprobe` 再读一次文件头的真实像素，不合格就**一张 slide 都不写**。

## 九、改了画法要做什么

**改任何画法（字号 / 间距 / 对齐 / 配色 / 分区），必须把源码里的
`LAYOUT_VERSION` +1。**

它进了 `render_state_key`，所以：
- 不 bump → 断点会把改之前的旧 slide 当成"已渲染"直接复用，
  你会以为改了、其实图还是旧的（这正是同族"死参数"事故的形态）；
- bump 了 → 所有 slide 重新渲染（渲染是零成本的，随便 bump）。

源码里这行有醒目注释，就是给下一次改画法的人看的。
