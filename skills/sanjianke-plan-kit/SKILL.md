# 三剪客 · 执行计划拆解

把复杂目标拆成有顺序、有检查点、每步都能独立验证的执行计划

"把这事做了"这一类目标之所以难落地，不是因为工作量太大，而是因为**没人说得清做到哪一步算做完了**。
于是进度汇报永远是"差不多了""快了"，验收时才发现方向从一开始就偏了。

这套方法解决的就是这件事：把一个模糊的大目标，切成若干**能被单独验证的小步**——
每一步都写明产出物是什么、用什么动作去验、验不过该怎么办。
它和普通待办清单的区别只有一条，但是决定性的：**待办清单写"做什么"，执行计划写"怎样才算做完"。**

## 触发场景

- "这个项目太大了，不知道从哪下手，帮我拆一下"
- "我要做一个 XX，给我列个计划，别是那种泛泛的待办清单"
- "计划写完了，但我担心做到一半发现漏了东西"
- "这几件事哪些能同时做、哪些必须排队？"
- "团队里两个人对『做完了』的理解不一样，怎么定清楚"
- "这个计划跑偏过两次了，帮我看问题出在拆解还是执行"

**不适用于**：只想要一句话答案的小事；已经拆完、只需要排期和盯进度的场景
（那是执行与检查点的活，不是拆解的活）；目标本身还没定的情况——目标都没定，
拆出来的步骤一定是错的。

## 快速开始

不要一上来就问"要分几步"。按下面五步走，每一步都有明确的输入和输出：

1. **钉目标**：把用户口中的目标改写成一句可判真假的话，
   并列出 3~5 条成功判据（验收时逐条打勾的那种）。
2. **先切层再切步**：先分 2~4 个里程碑（阶段），再在每个里程碑下切步骤。
   跳过里程碑直接列步骤，几乎必然出现"步骤之间没有先后关系"的一盘散沙。
3. **补验证**：给每一步写"产出物 + 验证动作 + 通过标准"三件套。
   写不出来的步骤，说明它还没拆到底。
4. **排依赖**：标出每步的前置步骤，抽掉不影响他人的步骤，
   找出关键路径，把可以并行的步骤并到同一批。
5. **埋风险**：对关键路径上的每一步，写"最可能怎么失败"和"失败了回退到哪"。

五步的详细操作、判断依据和检查点，见 `references/decomposition-method.md`。

**最小可用路径**：如果用户只给了 5 分钟，至少做完第 1 步和第 3 步。
一个目标清楚、验证明确的粗糙计划，远胜一个结构漂亮但没人知道怎么算完的精致计划。

## 五条硬规矩

这五条是这套方法的骨架，任何一条破了，计划就会退化成待办清单。

### 1. 目标必须能被判真假

"提升用户体验""优化系统性能"不是目标，是愿望。改写成
"首页首屏加载时间从 3.2s 降到 1.5s 以内""新用户 7 日留存从 18% 提到 25%"，
才有资格进入计划。判据的标准是：**一个没参与项目的人，拿着这句话能不能给出是或否。**

目标的写法、判据的三种类型（数值型 / 事件型 / 清单型）见
`references/decomposition-method.md` 第一节。

### 2. 每一步都要有一个"唯一的验证动作"

不是"检查一下有没有问题"，而是**一个具体的人，执行一个具体动作，得到一个具体结果**：

| 模糊写法 | 可验证写法 |
|---|---|
| 检查接口是否正常 | 用 curl 打 3 个用例，返回码全为 200 且响应体字段齐全 |
| 确认文案没问题 | 把文案发给运营，对方回复"可发"二字 |
| 测试一下流程 | 用新注册账号走完下单全流程，订单出现在后台列表第 1 行 |

判断标准很硬：**这个动作做完，结果是"通过"还是"不通过"，不需要再讨论。**
需要再讨论的，就是还没写清。

### 3. 一步的完成态只有两种，没有中间态

允许的完成状态：**做完了** / **没做完**。不允许："基本完成""大概 80%""除了 XX 都好了"。

如果一步总是出现"除了 XX 都好了"，说明这一步混进了两件事——
把它按 XX 切开，XX 单独成步。**"做完了一半"是拆解失败的信号，不是执行的常态。**

### 4. 有产出物的才叫步骤

每个步骤必须留下一个可以指认的东西：一份文件、一个提交、一张截图、
一条部署记录、一段环境配置。指认不出来的，说明它要么是别人的步骤的一部分，
要么根本不是步骤（比如"思考一下架构"——思考的产出物是架构文档）。

产出物的类型清单和命名建议见 `references/template-and-example.md`。

### 5. 风险要挂在步骤上，不要挂在计划末尾

"本项目风险有：时间紧、人手不足"——这种写法没有任何用。
正确的写法是挂在具体步骤上：**哪一步可能失败、失败时怎么看出来、失败了退回哪一步。**
回退点必须是一个已经完成并通过验证的步骤编号，不能是"重新开始"。

## 拆解的三个层次

拿到一个目标，心里要先有这三层的概念，否则容易在同一层里反复横跳。

| 层次 | 粒度 | 数量级 | 回答的问题 |
|---|---|---|---|
| 里程碑 | 阶段 | 2~4 个 | 到哪一步算翻篇了？ |
| 步骤 | 一次可交付 | 每个里程碑 3~8 个 | 谁做、做什么、留下什么？ |
| 子动作 | 步骤内部的顺序 | 每步 2~5 个 | 这一步具体怎么操作？ |

**只在"步骤"这一层写验证。** 里程碑用整体验收（所有步骤的验证都过了就过），
子动作用来自查（写给自己看，不用写进计划文档）。把三层混在一起写，
是计划文档变得又长又没人看的主要原因。

三层之间怎么对齐、里程碑怎么切才算切对，见 `references/decomposition-method.md` 第二节。

## 依赖排序与并行识别

排依赖不是画好看的关系图，是为了回答两个实际问题：**哪条路决定了最短工期**
（关键路径），**哪些活可以同时开工**（并行批）。

识别并行的三条判据，必须**同时满足**才能并：

1. **无数据依赖**：A 不需要 B 的产出物才能开始；
2. **无资源冲突**：两者不需要同一个人 / 同一台机器 / 同一份额度；
3. **无同一产物的写冲突**：两者不改同一份文件的同一部分。

常见误判：把"我希望它们并行"当成"它们可以并行"。
如果两条步骤都要找同一个人确认，那它们其实是串行的，只是你把它画成了并行。

依赖表格式、关键路径的找法（含一个 9 步的真实排序过程）、
以及"该串行却并行"造成的典型返工，见 `references/decomposition-method.md` 第三、四节。

## 风险与回退点

每一步都要回答三个问题，写在计划里就是一个三列表格：

| 问题 | 例子 |
|---|---|
| 最可能的失败方式 | 第三方接口不返回预期字段 |
| 怎么最早发现 | 第 4 步的验证动作会直接失败，不用等到联调 |
| 回退到哪一步 | 退回第 2 步，改用本地 mock 数据先跑通 |

**回退点只能指向已经验证通过的步骤**，这是硬约束。
指向一个没验证过的步骤，等于把不确定性叠加了一次，风险不是降低而是放大。

对关键路径上的步骤，还要多写一句"如果这一步延期 N 天，后面对策是什么"
（砍范围 / 加人 / 改验收标准），三选一，不要写"加班赶回来"。

## 能力边界

**覆盖**：

- 把模糊目标改写为可判真假的目标与成功判据
- 按可验证性切分里程碑与步骤，给出颗粒度判断依据
- 依赖排序、并行识别、关键路径查找
- 为每一步定义产出物、验证动作与通过标准
- 风险识别与回退点设计
- 输出一份完整、可交接、可验收的 Markdown 计划文档
- 对已有计划做拆解质量审查，指出具体哪一步不可验证

**不覆盖**：

- 不写排期和工时估算（拆解与估时是两件事，估时依赖团队历史数据）
- 不做执行阶段的进度跟踪与检查点管理
- 不做人员分工与组织安排（只标出步骤需要的角色能力，不指定人）
- 不替代需求文档：目标从哪来、为什么要做，属于更上游的事
- 不产出甘特图、看板等可视化物料（结构是文本，渲染交给用户的工具）

## 依赖条件

- 用户能说清**最终想让什么发生变化**。说不清的情况下，本 Skill 会先花一轮
  把目标问清楚，而不是硬拆——硬拆出来的计划一定要返工。
- 需要用户提供目标的基本约束：时间上有没有死线、资源上有没有硬边界、
  有没有不能碰的东西（合规、兼容性、既有用户习惯）。
- 无软件依赖。产出物是 Markdown 文本，任何编辑器都能打开。

## 已知限制

- **颗粒度没有唯一正解**。本 Skill 给的是判据（能否被独立验证、能否指认产出物），
  不是固定层数。同一个目标，5 人团队和 1 人做，切法本来就该不同。
- **无法验证目标本身是否正确**。拆解只能保证"按这个目标走，路径是清楚的"，
  保证不了"这个目标值得做"。目标错了，计划越严谨错得越整齐。
- **对未知领域只能拆到已知边界**。遇到完全没做过的事情，前几步往往只能写成
  "调研并产出可行性结论"这种形态——这是诚实的写法，不要为了好看假装知道后面几步。
- **不处理人的因素**。谁不配合、谁能力不够、跨部门卡审批，这类问题不在拆解范围内，
  但会在计划里体现为"等待外部输入"的步骤，需要用户自己补上等待时限。

## 自检清单

计划交付前，逐条过一遍。任何一条不过，就不要交付。

1. 目标能不能被判真假？拿给一个局外人看，他能不能回答"是"或"否"？
2. 成功判据有没有 3~5 条，每条是不是都能打勾？
3. 里程碑是不是 2~4 个？有没有出现"一步就跨完"或"分了 8 个阶段"？
4. 每一步是否都有唯一可指认的产出物？
5. 每一步是否都有验证动作？这个动作是不是一个具体的人做一件具体的事？
6. 通读一遍，有没有"基本完成""差不多了"这类词？有就是漏拆。
7. 有没有哪一步拆开其实是两件事？判断法：把它写成两句，读起来顺不顺。
8. 并行批次是否三条判据都满足？有没有把同一个人的两项活画成并行？
9. 关键路径找出来了吗？它上面的步骤是否都已经识别过风险？
10. 每个回退点是否指向一个已经验证通过的步骤？
11. 有没有"等待外部输入"的步骤？是否写明了等谁、等到什么时候？
12. 一个没参与过的人拿这份计划，能不能独立判断当前做到哪了？

完整的自检表（含常见错误的对照修正）见 `references/self-check-and-pitfalls.md`。
