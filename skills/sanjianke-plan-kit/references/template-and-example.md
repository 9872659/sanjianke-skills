# 模板与填写示例

这份资料给两样东西：一份可以直接复制的六段式模板，和一份从头填到尾的完整示例。
示例选的是"内容后台批量导入"这个不大不小的目标，因为它足够真实——
有前后端协作、有依赖、有风险，又在一个人能理解的范围里。

---

## 一、六段式模板

复制下面整段，把方括号里的内容换掉即可。**六段缺一不可**，
缺哪段，验收时就会在哪段扯皮。

```markdown
# [计划名]：一句话说清要达成什么

## 0. 元信息

- 目标一句话：
- 负责人：
- 计划周期：YYYY-MM-DD ~ YYYY-MM-DD
- 本版计划：v1（改版时递增，并写明改了什么）
- 参与角色：（列角色，不列人名）

## 1. 目标与成功判据

**目标**：[对象] 从 [现状] 到 [期望]，在 [口径/范围] 下成立。

**成功判据**
| # | 判据 | 类型 | 怎么测 |
|---|---|---|---|
| J1 | | 数值/事件/清单 | |
| J2 | | | |
| J3 | | | |

**什么不算成功**：
- [堵住"技术上做到了但实际不能用"的情况]

**范围外**（明确不做的）：
- [防止后期无限扩大]

## 2. 里程碑

| 里程碑 | 结束时对外能交代什么 | 包含步骤 | 预计完成 |

| M1 | | S1~S3 | |
```

### 逐字段填写说明

**元信息**：负责人必须是一个具体的人，不是"团队"。
"参与角色"写角色不写人名，因为人员会变、角色不会。

**目标**：按"对象 + 从多少到多少 + 口径"三件事写全。
缺口径的典型症状是验收时双方各测一遍、结果不一样。

**判据表**：3~5 条。每条都要有"怎么测"，"怎么测"这一列空着的判据等于没写。
三种类型（数值 / 事件 / 清单）尽量都覆盖到——只有数值型判据的计划，
容易出现"数达标了但东西不能用"。

**里程碑**：2~4 个，看"结束时对外能交代什么"这一列。
如果这一列填不出来（比如写"第一阶段完成"），说明这个里程碑是个步骤。

**步骤表**：核心。八列中"验证动作"和"通过标准"是最容易偷懒的两列。
自检方法：把"验证动作"念给一个外人听，他能不能照着做一遍？
不能就是还太模糊。

**并行批次**：分批而不是画箭头。批次天然表达了"同批可并行、跨批有先后"。
注意判据：批次内任意两步之间必须同时满足无数据依赖、无资源冲突、无写冲突。

**关键路径**：必须显式写出来，不能只在脑子里。它决定了资源分配和风险覆盖的重点。

**风险表**："最早发现点"这一列最有价值。如果某条风险最早只能在很后面发现，
就应该调整验证动作把它提前。

**等待与外部输入**：所有需要别人给东西的步骤都放这里。
关键是"最晚需要时间"和"超时怎么办"——没有这两列，"等待"会变成无限期。

**假设清单**：把"我们默认成立但没验证的事"写下来。
假设被推翻时，能立刻知道影响哪几步。这是防止计划静默失效的关键。

**变更记录**：计划一定会改。有变更记录的版本，才能回答"为什么当初这么定"。

## 二、完整填写示例

### 目标

内容运营团队每月要手工录入约 4000 条内容，平均每条 45 秒，
且人工录入的字段错误率约 3%。要做的是把这个环节自动化。

### 填好的计划

```markdown
# 内容后台批量导入：让运营用 Excel 一次性导入内容，取代逐条手工录入

## 0. 元信息

- 目标一句话：内容后台支持 Excel 批量导入，运营月录入耗时从 50 小时降到 5 小时以内
- 负责人：内容平台负责人
- 计划周期：2026-03-02 ~ 2026-03-27
- 本版计划：v1
- 参与角色：后端、前端、内容运营（提供样例数据）、测试

## 1. 目标与成功判据

**目标**：内容后台的内容录入方式，从逐条手工录入改为 Excel 批量导入，
在运营日常使用场景下，单月录入耗时 ≤ 5 小时，字段错误率 ≤ 0.3%。

**成功判据**

| # | 判据 | 类型 | 怎么测 |
|---|---|---|---|
| J1 | 单次导入 200 行，成功率 100%（合法数据） | 数值 | 用运营提供的 200 行真实样例跑 3 次，取全部成功 |
| J2 | 含错误的 200 行导入后，错误行全部被列出且定位到行号与列名 | 事件 | 手工在样例里植入 5 处错误（缺必填、格式错、超长、重复、非法枚举），看结果页是否 5 处全列出 |
| J3 | 单次导入 1 万行在 60 秒内完成 | 数值 | 脚本生成 1 万行，测 3 次取中位数 |
| J4 | 运营能不看文档独立完成一次导入 | 事件 | 让一位没参与开发的运营同学照模板操作，全程不提问即成功 |

**什么不算成功**：

- 导入成功了但需要开发手工修数据库
- 导入失败的提示只写"导入异常"，不指到具体行
- 只能导入全新内容，不能处理已存在内容的更新

**范围外**（明确不做的）：

- 不做复杂的导入规则配置界面（规则写死在配置文件中）
- 不做导入历史记录与回滚（本期只记录日志）
- 不支持除 CSV / XLSX 外的格式

## 2. 里程碑

| 里程碑 | 结束时对外能交代什么 | 包含步骤 | 预计完成 |
|---|---|---|---|
| M1 规则可用 | 字段映射与校验规则文档定稿，运营确认无误 | S1、S2、S3 | 03-06 |
| M2 链路打通 | 后端能收文件并返回结果，前端能看到结果页 | S4、S5、S6 | 03-17 |
| M3 可交付 | 端到端通过、压测通过、上线且回滚演练完成 | S7、S8、S9 | 03-27 |

## 3. 步骤表

| 编号 | 步骤 | 所属 | 产出物 | 验证动作 | 通过标准 | 前置 | 被依赖 |
|---|---|---|---|---|---|---|---|
| S1 | 盘点上月真实录入数据的字段情况 | 一页字段盘点表（字段名、出现频率、异常样例） | 随机抽 200 条真实数据，逐字段统计空值率与格式分布 | 200 条全覆盖统计；空值率 >5% 的字段已标出 | — | S4 |
| S2 | 产出字段映射与校验规则文档 | 规则文档 v1（含每个字段的类型、必填、长度、枚举、冲突规则） | 运营负责人逐字段确认并回复"确认" | 对方书面回复确认，且提出意见已全部处理或记录 | — | S3、S6、S7 |
| S3 | 确定导入失败的展示与重试策略 | 一页决策记录（失败行怎么展示、能否部分成功、重试入口在哪） | 把决策记录发给前端与运营各一份，收集回复 | 两方均无异议，或异议已解决并记录 | S2 | S5 |
| S4 | 后端导入接口实现 | 可调用接口 + 单元测试 | 用 200 行样例调接口 3 次 | 3 次均返回成功，且返回结构含成功数、失败行明细 | S1、S2 | S7、S8 |
| S5 | 导入结果页（成功数 / 失败行明细） | 页面 + 3 张截图（全成功、部分失败、全失败） | 打开页面，比对截图与接口返回 | 三种情形的展示均与接口返回一致，失败行含行号与列名 | S3 | S7 |
| S6 | 模板文件与填写说明 | 模板.xlsx + 一页说明 | 让一位未参与开发的运营照模板填 5 行 | 5 行填写无格式错误 | S2 | S7 |
| S7 | 端到端联调（200 行正常 + 200 行含错） | 联调记录（两个用例的实际结果） | 在测试环境完整走两遍 | 两个用例结果符合 J1、J2 | S4、S5、S6 | S9 |
| S8 | 大数据量压测（1 万行） | 压测报告（耗时、内存、错误率） | 执行 3 次取中位数 | 中位数 ≤60s，无内存溢出，错误率 0 | S4 | S9 |
| S9 | 上线与回滚演练 | 上线记录 + 回滚演练记录 | 生产上线后在测试环境演练一次回滚 | 回滚后后台可正常录入，耗时 ≤10 分钟 | S7、S8 | — |

**并行批次**：

- 批次 1：S1、S2（S2 的规则需参考 S1 的盘点，但字段清单来自运营既有认知，可先启动，
  S1 结果用于修正 S2 —— 这是本计划里唯一一处刻意的弱依赖，风险已记录）
- 批次 2：S3、S4、S6（无资源冲突：分别是运营侧、后端、文档）
- 批次 3：S5、S8（前端做结果页，后端做压测，互不冲突）
- 批次 4：S7
- 批次 5：S9

**关键路径**：S2 → S3 → S5 → S7 → S9（5 层）
次长链路：S1 → S4 → S7 → S9（4 层），余量 1 层。

## 4. 风险与回退点

| 步骤 | 最可能的失败方式 | 最早发现点 | 影响面 | 回退点 | 延期对策 |
|---|---|---|---|---|---|
| S2 | 运营对规则有分歧（如某字段是否必填），反复确认 | 运营回复中出现"再讨论一下" | 直接卡住关键路径全部下游 | 退回 S1，用数据分布作为依据再谈一轮 | 加资源：拉一位资深运营做仲裁，2 天内定稿 |
| S3 | 决策反复，前端按 A 方案做完又改 B 方案 | 前端开始实现 S5 时规则仍未确认 | S5 返工，影响 S7 | 退回 S3，先用最小方案（只展示失败行文本） | 砍范围：本期不做重试入口 |
| S4 | 真实数据的脏格式超出预期（如全角半角混用） | S4 的 200 行样例测试 | S4 延期，S7、S8 顺延 | 退回 S2，把脏格式的处理规则补进规则文档 | 改验收标准：本期不支持脏格式，输出到失败行 |
| S5 | 1 万行失败明细一次渲染卡死浏览器 | S8 压测（注意：这是本计划中最早发现点最晚的一条风险） | S5 需要分页改造 | 退回 S5，改为分页 + 只展示前 500 行 | 砍范围：失败明细改为可下载文件 |
| S8 | 1 万行导入超时（>60s） | S8 压测 | S9 延期 | 退回 S4，改批量插入为分批提交 | 改验收标准：改为分片导入，单次上限 5000 行 |

**风险 S5 的处置说明**：S5 的问题最早只能在 S8（批次 3）发现，
但它属于关键路径下游。为此在 S4 阶段就额外加一个 1 万行的接口层测试
（不含前端渲染），把"数据量"这一类风险的最早发现点从 S8 提前到 S4。

## 5. 等待与外部输入

| 等待什么 | 找谁 | 最晚需要时间 | 超时怎么办 |
|---|---|---|---|
| 200 行真实样例数据（需脱敏） | 内容运营 | 03-04 | 先用本人构造的 200 行数据开工，真实数据到位后补测一次 |
| 生产数据库只读权限 | 运维 | 03-18 | 先用测试库快照代替，上线前必须补齐 |
| 字段规则确认 | 运营负责人 | 03-06 | 按数据分布自行定稿，标注为待确认，S7 前必须确认 |

## 6. 假设清单

- 假设 1：运营提供的样例数据能代表日常数据分布。
  如果不成立 → S4 的脏格式处理规则需要重做，S2 的规则文档要修订。
- 假设 2：生产数据库允许新建导入日志表。
  如果不成立 → S9 的日志方案改为写文件，范围外条款需同步更新。
- 假设 3：单次导入上限 1 万行够用（运营实际最大批次约 6000 行）。
  如果不成立 → 需要引入异步任务与进度查询，工期至少 +5 天。

## 变更记录

| 版本 | 日期 | 改了什么 | 为什么改 |
|---|---|---|---|
| v1 | 03-02 | 初版 | — |
```

## 三、这份示例里值得注意的四处

**1. S5 的风险处置是这份计划的亮点。**
风险表本来只是记录，但"最早发现点"这一列暴露出 S5 的问题要到 S8 才能发现，
于是补了一个接口层测试。这就是把风险从事后补救变成事前拦截的具体做法。

**2. 弱依赖被显式写出来了。**
批次 1 里 S1 和 S2 存在弱依赖（S2 会参考 S1 的结果），
计划里没有假装它们完全独立，而是写明"这是刻意的弱依赖，风险已记录"。
**承认弱依赖，比假装没有更安全。**

**3. 判据 J4 是事件型而非数值型。**
"运营能不看文档独立完成一次导入"这条判据，测的是能不能用，
不是性能指标。很多计划只有数值型判据，结果交付时才发现没人会用。

**4. 假设清单里的每一条都写了"不成立的影响"。**
这是假设清单的正确写法。只写假设不写影响，等于列了一堆废话。

## 四、按场景裁剪

模板不是每段都要写满，按场景裁剪：

| 场景 | 保留 | 简化或省略 |
|---|---|---|
| 个人小项目（1~3 天） | 目标与判据、步骤表、假设清单 | 里程碑（直接就是步骤）、风险表可并进步骤表的备注列 |
| 跨团队协作 | 全部六段 | 不简化。"等待与外部输入"这段最关键 |
| 探索型任务（不知道能不能做） | 目标与判据、里程碑（按风险消除切）、假设清单 | 步骤只写第一批（"调研并产出可行性结论"），后面等结论出来再补 |
| 例行重复工作（如每月出报表） | 目标与判据、步骤表、自检清单 | 风险表可简化为"上次踩过的坑"清单 |

**唯一不能省的是"目标与成功判据"和"验证动作"两处。**
这两处省略，计划就退化成待办清单了。

## 五、交付格式建议

- **用 Markdown**：纯文本可 diff，改版时能看清改了什么；表格在多数工具里能直接渲染。
- **一个文件，不要拆成多个**：拆开后没人会全部读完；模板本身就不到 100 行。
- **表格列宽控制在 8 列以内**：太宽的表在聊天窗口里没法看，也没人愿意改。
- **步骤编号用 S1、S2**：不要用 1.1.1 这种层级编号，改版时会全部错位。
- **每一版存一个文件或明确记录版本**：计划改到第三版后，
  没人记得第一版为什么那么定，变更记录就是为了这个。
