# 拆解方法：从模糊目标到可验证步骤

这份资料回答四个问题：目标怎么钉死、切到多细才够、顺序怎么排、风险怎么埋。
每一节都给出判断依据（看到什么算对），而不是只给结论。

---

## 一、目标与成功判据

### 1.1 目标的可判真假改写

几乎所有"拆不出来"的目标，问题都出在第一步。先做一次改写：

| 原始说法 | 问题 | 改写后 |
|---|---|---|
| 优化一下系统性能 | 优化到什么程度？谁说了算？ | 首页首屏加载从 3.2s 降到 1.5s 以内（P75 真机） |
| 把用户留存做起来 | 留存指哪个口径？起来是多少？ | 新用户 7 日留存从 18% 提到 25%（自然流量） |
| 提升团队效率 | 谁的效率？哪件事变快了？ | 发版流程从 2 天缩到 4 小时，且回滚可一键完成 |
| 内容质量要好一些 | 好是相对什么？ | 每篇初稿至少经 2 轮审读，事实性错误 0 |

**判断标准（拿局外人测）**：把改写后的句子给一个完全不参与项目的人看，
问他"现在做到了没有"，他必须能回答"是"或"否"。
如果他的回答是"这得看情况"，这句目标还没写完。

### 1.2 改写公式

原始说法 + 三件事 = 可判真假的目标

1. **对象**：什么东西会变化（哪个页面、哪个流程、哪份产物）
2. **方向与幅度**：从多少到什么多少，或者"从无到有"
3. **口径**：在什么范围、什么条件下成立（哪些用户、哪个环境、什么时间窗）

三缺一都不行。"从 3.2s 到 1.5s"缺口径（哪个环境测的）；"P75 真机"补上口径才成立。

### 1.3 三类成功判据

目标写完了，还要拆出 3~5 条判据。判据分三类，好的计划通常三类都有：

| 类型 | 形态 | 例子 | 何时用 |
|---|---|---|---|
| 数值型 | 指标跨过阈值 | 加载时间 ≤ 1.5s | 有现成指标可以测 |
| 事件型 | 某件事发生了 | 新账号能走完下单全流程并出现在后台 | 目标是打通流程 |
| 清单型 | 清单项全部满足 | 5 个兼容性用例全部通过 | 目标是消除已知缺陷 |

**数值型要有测量方法**，否则验收时必然扯皮。写"加载时间 ≤1.5s"时，
同一行就要写"用 Lighthouse 移动端模拟、取 5 次中位数"。

**事件型要写清触发路径**，写"全流程跑通"没用，要写"用什么账号、从哪个入口、
走到哪一步结束、在哪看结果"。

**清单型要写清单本身**，不要写"各项指标达标"——那就是把判据藏起来了。

### 1.4 反面判据：什么不算成功

写判据时顺手写一条"不算成功的情况"，能省掉大量后期争论：

- 加载快了但首屏内容错位 → 不算成功
- 流程跑通了但需要手工改数据库 → 不算成功
- 留存涨了但全部来自投放买量 → 不算成功

这一条不需要很长，它存在的意义是提前堵住"技术上做到了但实际不能用"的解释空间。

## 二、三层粒度：里程碑 / 步骤 / 子动作

### 2.1 为什么必须先切层

直接列步骤的人，产出物通常是一张 20 行的清单，彼此之间没有先后关系，
也没人知道走到第 8 行意味着什么。原因是缺了中间层——**里程碑回答"翻篇了没有"**。

### 2.2 里程碑怎么切

一个里程碑 = 一个可以独立对外交代的状态。切法有三个依据，任选其一：

| 依据 | 切法 | 例子 |
|---|---|---|
| 按可交付 | 每一段结束时有东西可以拿给别人看 | 原型可点 → 内测可玩 → 上线可放量 |
| 按风险消除 | 每一段结束时消灭一类不确定性 | 技术可行性确认 → 数据可用性确认 → 全链路打通 |
| 按依赖收口 | 每一段结束时前置条件全部就位 | 素材齐备 → 环境就绪 → 内容产出 |

数量控制在 **2~4 个**。只有 1 个说明没分层；超过 4 个，通常是把步骤当里程碑了。

**里程碑的验收方式**：它下面所有步骤都通过各自验证，里程碑即通过。
不需要额外设计验证动作——如果你觉得需要，说明这个里程碑其实是一个步骤。

### 2.3 步骤切分：四个切口

拿到一个里程碑，用下面四个问题切步骤，比凭感觉列清单可靠得多：

1. **产出物切口**：这次要交出哪几样东西？一样东西至少一步。
2. **角色切口**：需要几个不同角色参与？角色一换，通常就是一步的边界
   （因为要交接，交接点必须有明确的产出物）。
3. **环境切口**：本地能做的 / 要上测试环境才能做的 / 只有生产能验的，分开。
4. **验证切口**：如果一段工作里有两个互相独立的验证动作，它就该是两步。

一个里程碑下 **3~8 步**。少于 3 步，基本是里程碑没切好；
多于 8 步，先看能不能再分一层（有时候是漏了一个里程碑）。

### 2.4 子动作只在脑内

步骤内部的操作顺序（先建表还是先写接口、先备份还是先改配置）属于子动作，
**写进计划只会让文档变长，不会让它更有用**。

判断一个内容该不该写进计划：**换个人来做，他会因为看不到这条而做错吗？**
会，就写；不会（他自然会那么做），就不写。

### 2.5 颗粒度自测：三问法

对每一个步骤，问三个问题，任一答不上来就是颗粒度不对：

1. **能指认吗**：这一步做完，我指得出一个东西吗？（不能 → 太粗，或不是步骤）
2. **能验证吗**：我能用一个动作判定它过没过吗？（不能 → 太粗）
3. **是一件事吗**：把它写成两句话，读起来是不是两件事？（是 → 太粗，要切）
4. **值得单列吗**：换个人做，他会做错吗？（不会 → 太细，并进上一步）

在实际使用中，"太粗"的出问题概率远高于"太细"。**拿不准的时候往细切一步**，
因为细了只是多写一行，粗了要返工整段。

## 三、依赖排序

### 3.1 依赖的三种来源

| 来源 | 表现 | 例子 |
|---|---|---|
| 数据依赖 | 我需要别人的产出物才能开始 | 接口契约定了才能写前端 |
| 资源依赖 | 我们需要同一个人 / 同一台机器 | 两个都要设计师出图 |
| 决策依赖 | 我需要一个结论才能往下走 | 技术方案定稿才能开工 |

识别的时候按顺序过三遍：先找数据依赖（最容易漏），再找资源依赖（最容易被忽略），
最后找决策依赖（最容易被当成"再想想"混过去）。

**决策依赖必须显性化成一步**，不能挂在某个人的脑子里。
"等方案定了"要写成"产出技术方案文档并通过评审"——否则它永远不会被安排进时间线。

### 3.2 依赖表的写法

| 步骤 | 依赖 | 依赖类型 | 被谁依赖 | 备注 |
|---|---|---|---|---|
| S3 接口契约 | S1 需求范围确认 | 决策 | S4、S5 | 契约变更会同时冲击前后端 |
| S6 数据迁移脚本 | S2 数据源盘点 | 数据 | S8 | 需要生产数据样本，注意脱敏 |

三个字段是必须的：**依赖谁、依赖类型、被谁依赖**。
只写"依赖 S1"是不够的——被谁依赖决定了这一步延期时的影响范围，
也决定了它是不是关键路径上的节点。

### 3.3 一个 9 步排序过程

假设目标：给内容后台加"批量导入"功能。

| 步骤 | 内容 | 前置 |
|---|---|---|
| S1 | 产出字段映射与校验规则文档 | — |
| S2 | 盘点导入源的字段实际情况 | — |
| S3 | 确定导入失败的展示与重试策略 | S1 |
| S4 | 后端导入接口实现 | S1、S2 |
| S5 | 导入结果页（成功/失败明细） | S3 |
| S6 | 模板文件与填写说明 | S1 |
| S7 | 端到端联调（含 200 行、含错误行两个用例） | S4、S5、S6 |
| S8 | 大数据量压测（1 万行） | S4 |
| S9 | 上线与回滚演练 | S7、S8 |

排序过程（不是一次成型，按依赖逐层抽出）：

1. **无前置的**：S1、S2 → 第 1 批，可并行（不同产出物、不同人可做）。
2. **只依赖第 1 批的**：S3（依赖 S1）、S4（依赖 S1+S2）、S6（依赖 S1）。
   三者产出物互不重叠 → 第 2 批，可并行。
3. **依赖第 2 批的**：S5（依赖 S3）、S8（依赖 S4）→ 第 3 批，可并行。
4. **依赖前面多个的**：S7（依赖 S4、S5、S6）→ 第 4 批。
5. **依赖第 4 批的**：S9 → 第 5 批。

得到的批次：`[S1,S2] → [S3,S4,S6] → [S5,S8] → [S7] → [S9]`，共 5 层。

### 3.4 关键路径

关键路径 = **从起点到终点最长的那条依赖链**。它决定了最短可能工期。

在上面例子中，链长统计（每步算 1 个单位）：

- S1→S3→S5→S7→S9 = 5 步
- S1→S4→S7→S9 = 4 步
- S2→S4→S8→S9 = 4 步

最长是 5，即关键路径为 `S1→S3→S5→S7→S9`。

**关键路径的三个用途**：

1. **资源优先给它**。路径外的步骤延期，只要不超过它的余量，不影响交付。
2. **风险优先给它**。关键路径上任何一步失败都会直接推后交付日，
   所以风险与回退点必须覆盖关键路径的每一步。
3. **优化优先给它**。想缩短工期，只能在关键路径上动手；
   优化非关键路径上的步骤，工期一天都不会少。

**余量（Slack）** 的算法很简单：某步骤的最晚开始时间 − 最早开始时间。
非关键路径步骤通常有余量，但要注意**余量会被消耗**——
上游延期时，下游的余量最先被吃掉，原本非关键的步骤可能变成关键。

## 四、并行识别

### 四条判据（必须同时满足）

1. **无数据依赖**：A 不需要 B 的产出物；
2. **无资源冲突**：不需要同一个人 / 同一台机器 / 同一份额度；
3. **无写冲突**：不改同一份文件的同一部分（改不同部分也可能冲突，视工具而定）；
4. **无决策依赖**：不需要等同一个尚未确定的结论。

第 4 条最容易漏。两个步骤都在等"技术方案定稿"，那它们虽然互不依赖，
也只能在方案定稿之后才能开始——这不是并行，是共同等待。

### 四种典型误判

| 误判 | 真相 | 后果 |
|---|---|---|
| 两件事都要找同一个人确认 | 资源冲突，实为串行 | 排了并行但没人能同时干，整体延后 |
| 都在等同一个决定 | 决策依赖，实为共同等待 | 决定迟迟不定，两条线一起卡住 |
| 改同一份文档的不同章节 | 写冲突风险，合并成本被低估 | 反复解决冲突，比串行还慢 |
| 一方"顺便"看一眼对方的产出 | 隐含数据依赖 | 返工，且返工点很难定位 |

**判据口诀**：并行不是"我希望它们一起做"，而是"拿掉其中一个，另一个照样能开工"。
把某一步临时删掉，如果另一步也能独立完成，它们才真的可以并行。

### 并行的代价

并行不是免费的，它换来三个成本：

- **协调成本**：两边要对齐接口、命名、约定，可以提前固化契约来降低。
- **返工风险**：发现方向不一致时，两条线都要改，损失是串行的两倍。
- **验证复杂度**：并行产物汇合时的问题往往最难查（两边单独都对，合起来不对）。

**所以并行的判断是**：当两条线的工作量明显大于协调成本时才并。
两条各半天的小活，串行做完再并行，反而更快。

## 五、风险与回退点

### 5.1 风险挂在步骤上

风险不能列在文档末尾当装饰。正确挂法：挂在**关键路径的每一步**上，
每条风险写四个字段：

| 字段 | 要求 | 反例 |
|---|---|---|
| 失败方式 | 具体到能想象出画面 | "可能有问题" |
| 最早发现点 | 哪个验证动作会先失败 | "联调时发现" |
| 影响面 | 影响哪几步、影响多大 | "影响进度" |
| 回退点 | 退到哪个已通过的步骤 | "重新开始" |

**"最早发现点"是最有价值的字段**。它把风险从事后补救变成事前拦截：
如果某条风险最早只能在联调时发现，那就要考虑把验证动作提前——
比如先用 mock 数据跑一遍接口，把发现点从联调提前到接口完成。

### 5.2 回退点的三条硬约束

1. **必须指向已经验证通过的步骤**。指向未验证的步骤，是把不确定性叠加一次。
2. **必须是单步回退，不是整段重来**。如果一个失败要退回三个里程碑之前，
   说明步骤切得太粗，或者中间缺少检查点。
3. **回退动作要写清楚做什么**。写"退回 S2"不够，要写"退回 S2，
   改用本地 mock 数据方案，预计影响 S4、S5 各 1 天"。

### 5.3 延期对策三选一

关键路径上的步骤延期时，只有三种真实有效的对策，必须选一个并写下来：

| 对策 | 适用 | 代价 |
|---|---|---|
| 砍范围 | 判据可以协商，核心目标不动 | 交付的功能少一块，要提前跟需求方对齐 |
| 加资源 | 步骤可以拆给多人且协调成本可控 | 引入协调与返工风险 |
| 改验收标准 | 原标准在当前约束下不现实 | 效果打折，必须书面记录原因 |

**"加班赶回来"不是对策**，它是把风险转嫁给个人并推迟暴露。
写这三个字，等于这一步没有对策。

## 六、拆解完成的判定

一份拆解合格的计划，通读一遍应该能回答下面六个问题。有一个答不上来就没完成：

1. 目标是什么，怎么判定达成？（第一节）
2. 分几个阶段，每个阶段结束意味着什么？（第二节）
3. 一共几步，每步留下什么东西？（第二、三节）
4. 每步怎么验，谁来验，验不过怎么办？（第一节 + 第五节）
5. 哪些能同时做，最短工期取决于哪条链？（第三、四节）
6. 最可能在哪里翻车，翻车后退到哪？（第五节）

拿到这六个答案，计划就可以交给别人执行了。
