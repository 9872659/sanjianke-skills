# 播客对话稿方法 · 从提纲到成品稿

这份文档讲的是 `outline` 与 `script` 两个子命令背后的**口径**：
一期播客的稿子长什么样、字数怎么折成时长、为什么对话稿结构要拿闸门拦。

---

## 一、提纲（`outline`）要回答的五个问题

一期节目录之前必须能回答出来，答不出来就会录成一堆"正确但没用"的聊天：

| 字段 | 要回答的问题 | 不合格的样子 |
|---|---|---|
| `title` | 这期讲什么、给谁听 | 「聊聊 AI 剪辑」——没有信息量 |
| `angle` | 为什么**现在**值得讲 | 「因为 AI 很火」——不是理由 |
| `audience` | 听众是谁、他卡在哪 | 「所有对 AI 感兴趣的人」——等于没说 |
| `hook` | 片头能不能让人留下来 | 只报节目名再寒暄 |
| `outro` | 能不能给出一句被转述的结论 | 道个别就完事 |
| `chapters[].points` | 每章 2~4 条要点，且**章与章递进** | 四章并列罗列，删掉两章也不影响 |

`outline` 的产出会被 `script` 当作唯一输入，所以**提纲不好，后面的配音与配乐都救不回来**。

### 章与章要递进，不是并列

提示词里写死了这一条：**前一章留下的问题由后一章回答**。
实测达标的一期提纲是这样的（4 章，8 分钟）：

```
1. 省时间的承诺从哪来            2.0 分钟
2. 省下的时间去了哪：转移而非消失   2.5 分钟
3. 谁真的省了：流水线位置决定收益   2.0 分钟
4. 把 AI 放对位置：一张可自测的时间账 1.5 分钟
```

四章是一条推理链：**拆开承诺 → 时间去哪了 → 谁得谁失 → 怎么给听众用**。
如果是"工具介绍 / 使用技巧 / 常见问题 / 总结"这种并列结构，听众听第二章时
就已经知道第三章要说什么了。

## 二、字数 ↔ 时长的换算

播客是**按时长卖**的。脚本阶段拿不到真实音频时长，只能用字数估：

```
估计时长（分钟） = 正文对白字数 ÷ 语速（字/分钟）
```

**默认语速 265 字/分钟**，可以用 `--chars-per-minute` 改。这个数字是两条口径的共同来源：

| 目标时长 | 折算字数 | 配音成本（50 点/千字） |
|---|---|---|
| 8 分钟 | 2120 字 | 106 点 ≈ 1.06 元 |
| 30 分钟 | 7950 字 | 398 点 ≈ 3.98 元 |
| 60 分钟 | 15900 字 | 795 点 ≈ 7.95 元 |

### 时长闸门：偏离超过 ±25% 就拦

```
[时长] 按 265 字/分钟估，约 3.5 分钟；目标 8.0 分钟，容差 25%（6.0~10.0 分钟）
```

容差取 ±25% 的理由：同一个话题快讲和慢讲实测能差 15% 左右，
25% 留了余量，同时又能拦住"目标 8 分钟结果只有 3.5 分钟"这种真问题。

**音频阶段的真实时长由 `mix` 报出来**（`timeline.md`），与脚本阶段的估算不一致时人工看得到。

## 三、逐章字数配额（这一段是被闸门逼出来的）

只在提示词末尾写一句「合计约 2120 字」，实测模型只写了 **1035 字**（3.5 分钟），
被时长闸门拦下。改成把配额挂在每章后面那一行，仍然没对齐（3.9 分钟）。
最终改成**独立的逐章配额块**，并把配额换算成模型能直接对齐的粒度：

```
篇幅配额（这是硬指标，本地闸门会按总字数估算时长并核对）：
  第 1 章：本章对白不少于 600 字，不少于 15 条台词
  第 2 章：本章对白不少于 751 字，不少于 19 条台词
  ...
  合计不少于 2014 字。
```

配额算法：

- 按各章 `minutes` 占比分摊目标字数，**乘 1.08 留余量**（宁多不少，多了只是稍长）
- 台词条数按**实测每条台词约 40 字**折算：`max(6, round(本章字数 / 40))`
- 输出格式里同时约束「一条 40~90 字、一到三句，口语」

实测这一版**一轮就把总字数打进了闸门区间**（1997 字 / 63 句 / 7.5 分钟）。

> **通用教训**：给模型的约束要落在**它能逐项对齐的粒度**上。
> 写在括号里的总目标，它不当回事。

## 四、对话稿的形态：两个角色，交替发言

### 为什么这是硬闸门

播客与"一篇文章"的分水岭就是**两个人在说话**。一份单角色的稿子：

- 字数对 ✅
- 时长对 ✅
- 合规干净 ✅
- 读起来也顺 ✅

**它在任何一道常规检查里都是合格的**，但配出来只是朗读，不是播客。
发出去才发现形态不对——这类"表面上完全正确的错误"正是闸门存在的理由。

### 判定口径（全部命中才算过）

| 检查 | 阈值 | 说明 |
|---|---|---|
| 台词行数 | ≥ 6 | 太短的稿子谈不上结构 |
| 角色数 | **恰好 2** | `--allow-multi-role` 才放宽到 ≥2 |
| 每个角色台词数 | ≥ 3 | 拦"配角化 / 独角戏" |
| 相邻同角色占比 | ≤ 20% | 这是"交替发言"的机器口径 |
| 无角色标注的发言行 | 0 | 拦"整篇没有角色标注" |

实战一期的实测值（8 分钟）：

```
turns=63, roles=[主持人, 嘉宾], 每人 33/30 句,
same_speaker_ratio=0.032, unlabeled_lines=[]
```

### 判定读的是**成品稿**，不是模型自报字段

`script` 产出的 `script.md` 长这样：

```markdown
## 第 1 章　省时间的承诺从哪来

> 本章主线：先拆开"AI剪辑省时间"这句话，看它默认比较的是哪两步。

**主持人**（平稳开场）：如果你用 AI 剪过片，可能发现总时间没少，甚至更累。

**嘉宾**（认真）：对，很多人一上来就问"AI 剪辑能省多少时间"，但这个问题本身就有个陷阱。
```

闸门用正则 `^\*\*(角色)\*\*（语气）：台词$` 去**读这份成品稿**，
而不是信模型 JSON 里的 `role` 字段。依据是本库吃过的亏：
只信模型自报值的那一版，闸门成了假绿。

顺带的好处：**手工改过的 `.md` 稿子也能进配音**——改完照样过闸门。

### 角色名可以换

`--role-a` / `--role-b` 改名字（默认「主持人」「嘉宾」）。
角色 → 音色的映射按**首次出现顺序**：`--voice-a` 给第一个角色，`--voice-b` 给第二个。

## 五、口语稿的写法（提示词里写死的几条）

1. **每句都自带语气标注**（一个词或短语）：平稳 / 加快 / 笑着 / 停顿一下。
   这不只是给配音用的，也是给剪辑用的——语气标注是"这一句该重录"的线索。
2. **句子是口语**：允许短句、追问、自我纠正，不许写成书面长句。
3. **两个角色的分工不同**：
   - 主持人——负责**推进**：铺垫背景、提出疑问、把跑偏的话题拉回来、做小结
   - 嘉宾——负责**内容**：给出判断、解释原因、举可核查的例子、承认不确定性
4. **不许编**：不指名具体的人、机构、论文、基金、真实数据；
   需要举例时只能用可核查的泛指表述。

## 六、配音时为什么要把连续台词合并

同章节内、**同角色的连续台词合并成一块**（≤ 500 字），理由有两条：

1. **省钱不存在的问题**：实测配音**无最低消费**（50 点/千字，21~57 字五组样本逐条线性），
   合并不会多花一分钱，但能把调用次数从几百次压到几十次。
2. **调用次数直接决定失败率与重试成本**：一次网络抖动就得重试一整块，
   块越小重试的浪费越小——但块太多，抖动撞上的概率也越高。500 字是个平衡点，
   它同时是平台对同步接口的建议上限。

超过 500 字的块再按句末标点拆开。**不能靠上游截断**——
音频少一句但看不出来，是最坏的情况。

## 七、检查清单（自己审稿时用）

- [ ] 提纲四章之间是递进关系，删掉任何一章都会断链
- [ ] `hook` 能让人在 15 秒内知道"听完能拿到什么"
- [ ] `outro` 能给出一句可以被单独转述的结论
- [ ] 总字数落在 `目标分钟 × 265 × [0.75, 1.25]` 区间里
- [ ] 两个角色交替出现，没有一段超过 3 句的独白
- [ ] 每句都有语气标注
- [ ] 通读一遍：有没有哪一句是"写出来的"而不是"说出来的"
- [ ] 关掉字幕只听音频：能不能听出是谁在说
