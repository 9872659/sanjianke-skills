# 三剪客 · 可视化 Agent 工作流

「把这个流程做成一个大模型应用」——文本进、过一遍知识库检索、让模型判断要不要调工具、最后按固定格式吐出来——如果纯写代码，光是串节点、管状态、做重试就够折腾半天。Dify 的答案是：给你一块画布，把这件事拖出来。

它同时覆盖了做一个 LLM 应用需要的大多数零件：可视化工作流、RAG 流水线、Agent 能力与内置工具、Prompt IDE、模型管理、可观测性，而且**所有能力都对着一套 API**，所以既能在界面上快速验证，也能把成品接进自己的业务系统。

**上游项目**：`Dify`　**仓库**：https://github.com/langgenius/dify

## 什么时候用 / 不用

**用它**：

- 用户说「帮我搭一个知识库问答」「把这段话术接个模型自动回复」「做一个能调工具的助手」。
- 需要一个**可视化、可调试**的编排界面，让不写代码的人也能改流程和提示词。
- 要把多个模型供应商混着用（商用 API 与自托管模型并存），并统一在界面里管理。
- 想把已有的文档做成 RAG：上传、切片、检索、带引用回答。
- 需要把一个 LLM 应用**发布成 API** 给别的系统调用，而不是自己从零写服务层。
- 想对比不同提示词和模型的效果，并留下运行日志用于持续优化。

**不要用它**：

- **只想本地跑个模型**。那是模型运行时的活，Dify 是应用编排平台，自身不训练也不推理模型。
- **追求零依赖轻量部署**。它是多服务架构（后端、worker、前端、数据库、缓存、向量库等），跑起来需要 Docker Compose 或 Kubernetes 级别的环境。
- **这台机器资源很紧张**。官方给的最低要求是 CPU ≥ 2 核、内存 ≥ 4 GiB，低于这个就别硬上。
- **不需要编排，只想要个聊天窗口**。单纯要个对话界面有更轻的选择。
- **完全不想碰容器和运维**。自托管意味着升级、备份、环境变量、数据卷都是你的责任；不想承担就用官方云服务。

## 安装
自托管最快的方式是 Docker Compose。前置条件：装好 Docker，且 Docker Compose 版本 **2.24.0 或更高**。

```bash
cd dify
cd docker
cp .env.example .env
docker compose up -d
```

启动完成后，在浏览器打开 `http://localhost/install` 进入初始化流程。

安装前先确认机器满足最低要求：**CPU ≥ 2 Core、RAM ≥ 4 GiB**。

该 compose 文件位于仓库的 `docker/docker-compose.yaml`。除 Docker Compose 外，官方还支持 Kubernetes 等方式，具体以官方自托管文档为准。

```bash
# 停止
docker compose down

# 查看服务状态与日志
docker compose ps
docker compose logs -f
```

如果是要参与开发或做二次开发，官方另有一份「从源码部署」的指引，步骤与上者不同。

## 常用操作

**1. 起服务、进初始化、确认状态**

```bash
cd dify/docker
cp .env.example .env
docker compose up -d
docker compose ps
```

然后访问 `http://localhost/install` 完成管理员初始化。首次进入需要设置账号。

**2. 配置模型供应商**

在界面里进入模型供应商设置，填入对应厂商的 API Key 或自托管服务的地址与凭证。官方维护了一份支持的模型供应商清单，接入前先确认你的模型在不在列表里；任何 OpenAI API 兼容的服务通常都能通过兼容方式接入。

**3. 搭应用：从模板或空白画布开始**

界面上按应用类型创建（如对话型、工作流型），然后在画布上拖节点：输入、知识库检索、LLM、条件分支、代码执行、工具调用、输出。搭完直接在右侧对话调试，改一版试一版。

**4. 建知识库做 RAG**

上传文档 → 选择切片与清洗策略 → 等待索引完成 → 在工作流里挂上「知识库检索」节点。官方对 PDF、PPT 等常见文档格式提供开箱即用的文本抽取能力。

**5. 发布并调 API**

应用发布后会拿到对应的 API 凭证与访问入口。所有 Dify 的能力都有配套 API，可按官方 API 文档把应用接进自己的业务逻辑。

```bash
# 交互式 API 文档（自托管默认入口，具体路径以你部署的版本为准）
# http://<你的域名>/v1/
```

**6. 升级**

```bash
cd dify/docker
docker compose pull
docker compose up -d
```

升级前务必先备份数据库与数据卷。跨大版本的升级步骤、需要改动的环境变量，以官方升级文档为准。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| `docker compose up` 报错说 compose 版本过低 | 官方要求 Docker Compose 2.24.0 或更高 | 升级 Docker Compose 后重试 |
| 服务起来了但页面打不开、或提示连不上后端 | 前端、API、worker 是不同容器，任何一个没起来都会表现为「打不开」 | 用 `docker compose ps` 看每个容器状态，再 `docker compose logs` 定位是哪个服务挂了 |
| 宿主机 80 端口被占用，起不来 | 默认通过反向代理暴露在标准端口 | 改 `.env` 里的对外端口映射，或先腾出该端口；改完要重建容器 |
| 改了 `.env` 但行为没变 | 环境变量是容器启动时注入的，改文件不会热加载 | 改完执行 `docker compose up -d` 重建受影响的服务 |
| 升级后数据丢失或旧数据读不出来 | 数据库/向量库/对象存储都在数据卷里，直接删容器或换 compose 配置会丢数据 | 升级前备份数据库和数据卷；不要用会移除卷的方式清理 |
| 上传的文档检索不到内容 | 索引还没跑完，或切片策略把内容切碎了，或文件本身是扫描件没有文本层 | 等索引完成；调整切片与清洗策略；扫描件先做 OCR 再上传 |
| 工作流在界面上跑得好，调 API 却报错 | 应用没发布，或调的是未发布的草稿版本，或凭证不对 | 确认应用已发布；核对 API 凭证与调用地址 |
| 容器跑一段时间后磁盘被吃满 | 日志、镜像层、上传的文件与向量数据都在累积 | 定期清理无用镜像与日志，给数据目录留足空间，并确认上传文件用的是持久化存储 |

## 能力边界

**覆盖**：

- 可视化工作流编排：在画布上搭建并调试 AI 流程。
- 多模型接入：覆盖多家推理供应商的自有与开源模型，以及任何 OpenAI API 兼容的模型。
- RAG 流水线：从文档摄入到检索的完整链路，含 PDF、PPT 等常见格式的文本抽取。
- Agent 能力：基于 LLM Function Calling 或 ReAct 定义智能体，可挂内置工具或自定义工具。
- Prompt IDE：编写提示词、对比模型表现，并为对话型应用附加语音等能力。
- LLMOps：应用日志与性能监控、基于线上数据与标注持续改进提示词、数据集与模型。
- Backend-as-a-Service：各项能力均有对应 API，便于嵌入自有业务。

**不覆盖**：

- 不自带模型权重，也不做模型训练或微调；模型能力来自你接入的供应商。
- 不是通用后端框架，不替你做业务系统的鉴权、计费、订单等逻辑。
- 不自带 GPU 推理能力；要跑本地模型得另外部署模型服务再接入。
- 不提供模型效果评测基准，不给横向跑分结论；LLMOps 给的是你自己的运行数据。
- 社区版与企业版功能范围不同，企业向能力不在社区版覆盖内。

## 依赖条件

- Docker 与 Docker Compose **2.24.0+**（自托管方式的前提）。
- 最低硬件：CPU ≥ 2 Core、RAM ≥ 4 GiB。
- 磁盘空间要能容纳数据库、向量库、上传文件与镜像。
- 需要至少一个可用的大模型来源：外部供应商的 API Key，或自托管且可被容器网络访问的模型服务。
- 服务器需要能联网拉取镜像；内网离线部署需要自行准备镜像与依赖，以官方文档为准。
- 官方 Docker Hub 组织为 `langgenius`；镜像与 tag 详情以官方为准。

## 已知限制

- 多服务架构意味着真实的运维成本：升级、备份、端口、环境变量都需要自己维护。
- 默认通过反向代理对宿主机暴露服务，生产环境必须自行加上 HTTPS、访问控制与网络隔离。
- 知识库的检索效果高度依赖文档质量与切片策略，扫描件必须先解决文本层问题。
- 不同版本之间的环境变量与升级路径存在差异，跳版本升级风险较高。
- 社区版与企业版的能力边界不同，具体差异以官方定价与版本文档为准。
- 上游迭代非常快，界面布局、API 路径与环境变量名都可能变化；执行前以官方文档与当前版本的实际行为为准。
- 具体版本号、发布日期与 star 数请以仓库页面实时信息为准，此处不做断言。
