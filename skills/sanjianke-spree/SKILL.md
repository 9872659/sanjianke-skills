# 三剪客 · 开源无头电商平台

想把商城的「后端那一半」握在自己手里时，问题通常不是「选哪个前端框架」，而是商品、库存、价格、订单、支付、税费、退款这套东西有没有一个能自己跑、能自己改的内核。Spree 就是这套内核：它是一个**自托管**的电商后端，对外输出 REST API，商品与目录、购物车与结账、库存与定价、支付会话、促销与礼品卡、物流与税费、多销售渠道、跨境市场这些都在里面。

它的关键判断点是**无头（headless）**：仓库里没有一个最终的消费者界面等着你开箱即用——你要么接官方那个独立的 Next.js 店面工程，要么自己写前端。所以「能不能用」取决于你手里有没有前端，而不取决于 Spree 本身功能多不多。

这套内核是开源版；同一套代码之上还有收费的企业版，两者功能差异要提前分清，不然会做了半天发现想要的能力根本不在开源版里。

**上游项目**：`spree`　**仓库**：https://github.com/spree/spree

## 什么时候用 / 不用

**用它**：

- 要一个**自托管**的电商后端，代码、数据、基础设施都留在自己这边，不接受按交易抽成的 SaaS 模式。
- 业务形态超出「普通零售」：跨境多市场、多销售渠道、B2B 批发与阶梯价、多卖家 marketplace 这类需求。
- 已经决定**前端自己写**（或直接接官方 Next.js 店面），只需要一个语义清晰的 REST API 加 SDK 来提供数据与交易能力。
- 想用命令行把这个后端管起来——启停开发栈、跑生成器与迁移、直接用 `get/post/patch/delete` 调用管理 API，方便写脚本或交给 Agent 执行。
- 团队是 Ruby 技术栈，或愿意接受 Rails 生态，希望按自己的方式扩展商品、定价、结账等模型。
- 需要把支付做成**多家可选**的抽象层，而不是绑死在某一个支付服务商上。

**不要用它**：

- **非开发者想直接拿来开店**。这是后端平台不是成品店铺，装完不会自动出现一个可用的商城界面。
- **需要一个开箱就好看的前台**。仓库不含消费者界面，前端要另找工程或自己写；接不上前端就只有 API 能用。
- **想要的是企业版功能**（买家审批链、ERP 对接、多租户 SaaS 运营层、SSO 与审计）。这些在收费版里，开源版没有，别指望加个配置就出来。
- **只卖几个商品、不想碰服务器**。自托管意味着数据库、容器、备份、扩容都要自己负责，量小的时候这套运维成本不划算。
- **只需要订单数据做二次分析**。那直接读数据源或调平台 API 更轻，不必为此跑一套完整后端。

## 安装

**路径 A：一键脚手架（推荐先走这条）**

前置是 Node 环境加一个正在运行的 Docker——后端容器由它拉起。

```bash
npx create-spree-app@latest my-store
```

命令行会交互式问你两件事：是要「后端 + Next.js 店面」的全栈形态还是只要后端；要不要顺带灌入示例数据（商品、分类、图片）。跑完之后后台默认可以在 `http://localhost:3000/admin` 打开；如果本机 `3000` 已被占用，实际端口会不同，以命令输出的地址为准。

**路径 B：手动装到 Rails 工程里**

适合想要完全掌控安装过程、或者要把 Spree 加进一个已有的 Rails 项目。前置三样：Ruby、图像处理库 vips、以及 Rails。

```bash
gem install rails
rails new my_store -m https://raw.githubusercontent.com/spree/spree/main/spree/template.rb
```

要指定数据库时给 `rails new` 传 `-d` 参数；具体支持的数据库与写法以官方安装文档为准。

**单独安装命令行工具**

用脚手架创建的项目里已经自带；其他情况下可以全局装：

```bash
npm install -g @spree/cli
spree <command>
```

不想装到全局也可以用 `npx @spree/cli ...` 直接跑。

**上线部署**

官方提供 Docker 镜像与 Dockerfile，云主机、自建服务器、容器平台都能部署；前端可以放到任意支持 Node.js 的托管环境。具体步骤以官方部署文档为准。

## 常用操作

**1. 启动开发栈（前台运行，`Ctrl+C` 停止）**

```bash
spree dev
```

在项目目录里执行。首次运行会自动把初始化流程补齐；如果工程里存在 `apps/dashboard`，它会把对应开发服务一并带起来。配套的还有 `spree stop`（停服务）、`spree logs`（看日志）、`spree console`（进 Rails 控制台）。

**2. 查询管理 API（订单为例）**

```bash
spree api get /orders -q status_eq=complete --limit 10
```

`-q` 传过滤条件，`--sort` 排序，`--limit` 限条数；单条资源可以直接拉取并展开关联：

```bash
spree api get /orders/ord_x8k2J9aQ --expand items,payments
```

**3. 创建一条商品数据**

```bash
spree api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'
```

写操作需要**显式创建的密钥**并带写权限（见常见坑第 1 条），本地首次使用自动生成的那把是不够的。

**4. 离线探索有哪些端点与字段**

```bash
spree api endpoints --search refund
spree api schema "POST /orders/{id}/refunds"
```

这两条不需要网络请求业务数据，`endpoints` 用来找路径，`schema` 用来看某个端点的请求体结构，写脚本前先跑一遍能省掉大量猜测。另有 `spree api status` 用来确认当前凭证与目标主机是不是通的。

**5. 生成代码骨架（模型 / API 资源 / 迁移）**

```bash
spree generate api_resource Brand name:string description:rich_text
```

给一个资源名和字段列表，生成对应的接口、模型与数据库结构，再按业务往里填。

**6. 远程店铺的凭证配置**

```bash
spree auth login --profile prod --base-url https://store.example.com
spree api get /orders --profile prod -q "status_eq=complete"
```

密钥通过提示输入，不写在命令行里。CI 或脚本环境走环境变量：`SPREE_API_KEY`，需要指向远程时再配 `SPREE_BASE_URL`；只给密钥时默认打向 `http://localhost:3000`。

**7. 生产镜像构建**

```bash
spree build --production
```

把 Spree API 与你的后台面板打进同一个生产镜像。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 自动生成的密钥调 `post` / `patch` 报权限不足 | 本地自动生成的密钥只带只读范围，写入必须用显式创建的密钥 | 用 `spree api-key create` 创建带写范围的密钥；后台里也有 API 密钥入口 |
| `spree api` 报没有凭证 | 没有在项目目录里执行，或环境里既无密钥也无项目凭证 | 在项目目录内执行让工具自动生成只读密钥；远程场景设 `SPREE_API_KEY`（配合 `SPREE_BASE_URL`） |
| 换了主机后密钥「打错地方」 | 密钥与主机是成对解析的，不会因为换了地址就自动改指向 | 要重新指向就用 `--base-url`，或成对设置 `SPREE_BASE_URL` 与 `SPREE_API_KEY` |
| `npx create-spree-app` 失败 | Node 版本不够，或 Docker 没在运行 | 两条路径的前置不同：一键路径要 Node 与运行中的 Docker；Rails 路径要 Ruby 与 vips |
| 后台打不开，或提示端口被占用 | 默认 `3000` 被别的程序占了 | 以命令输出的实际地址为准，或先释放端口 |
| 上传商品图片报缺少图像库 | 手动安装路径漏了图像处理依赖 | 按官方安装文档装上 vips（`libvips`） |
| 容器起不来 / 磁盘很快被写满 | 容器与数据卷占空间，清理策略没定 | 提前规划数据目录位置，定期清理无用镜像与卷 |
| 升级后行为跟原来不一样 | 版本变了，旧的定制点或配置已不适用 | 用 `spree update` 拉取新镜像并自动跑迁移，升级前先看官方发布说明 |
| 从预构建镜像切到本地构建后命令不生效 | 还处在镜像模式 | 用 `spree eject` 切换到基于 `backend/` 目录构建的模式 |
| 多店铺 / 多渠道场景数据互相串 | 渠道、市场、价格表三层的层级关系没理清就建数据 | 先把「一个后端多个渠道」的结构想清楚，再建市场与价格表 |
| 生产环境数据丢失 | 本地默认存储不适合生产，数据没落到持久化存储 | 生产用外部数据库与持久化卷，不要沿用本地默认配置 |
| 以为开源版含企业能力 | 买家审批链、ERP 连接器、多租户 SaaS、SSO 与审计在收费版 | 先对照官方给出的开源版 / 企业版能力清单，再决定要不要走这条路线 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 拉取 npm gem 与 Docker 镜像；调用后端 REST API；对接支付、税务、搜索、分析、营销等外部服务 |
| 读取文件 | 是 | 读取项目源码与配置、模板文件、`.env` 与凭证文件；读取要上传的商品素材 |
| 写入文件 | 是 | 安装依赖、构建产物、生成器落盘、数据库迁移产生的文件、本地日志 |
| 凭证 | 是 | 管理 API 密钥（本地自动生成的只读密钥、显式创建的读写密钥、远程店铺密钥）、数据库账号密码，以及第三方支付 / 税务 / 搜索服务密钥。**本 Skill 不内嵌任何密钥**，请用环境变量或密钥管理服务 |
| 子进程 / 后台常驻 | 是 | Docker 容器常驻（Web 与后台任务进程、数据库、缓存）；CLI 会以子进程方式启停与查看这些服务 |

## 触发场景

- 「想自己搭一套电商后端，数据不放别人那里」
- 「要支持跨境多市场，不同国家不同货币和支付方式」
- 「B2B 要分客户等级给不同价格」
- 「前端我们自己做，只要一个靠谱的 REST API」
- 「本地起不来 / 接口 401，帮我看看配置」
- 「用命令行批量拉订单、批量建商品」

## 能力边界

**覆盖**：

- 商品与目录：商品与变体、选项与属性、分类与标签、媒体、元字段、CSV 导入导出、批量操作、数字商品。
- 交易链路：购物车与结账、订单生命周期、地址、发货、调整项、退货退款相关的订单操作。
- 价格与库存：基础价与价格表（按地区、按 B2B / 批发的分层定价）、库存与库存位置、客户分组与目录。
- 支付与资金：支付会话抽象层，官方插件覆盖主流支付服务商，并支持按支付服务商 SDK 自行扩展；礼品卡与购物金。
- 促销：基于规则的促销引擎。
- 渠道与市场：单后端多销售渠道（多个店面、门店、B2B 面板、移动端各自独立配置），市场把货币、语言、支付方式、运费规则按国家打包。
- 开放能力：REST API（含发布密钥、限流、OpenAPI 规范）、TypeScript SDK、事件总线、Webhook、后台的角色权限、搜索集成、分析与营销集成。
- 开发者体验：`@spree/cli` 的项目管理与管理 API 客户端（含离线端点探索与结构查询）。

**不覆盖**：

- 不自带面向消费者的商城界面；前端要自己写或接官方独立的店面工程。
- 不含企业版能力：买家审批链、ERP / 采购对接、多租户 SaaS 运营层、企业级 SSO 与审计、SLA 支持。
- 不提供商品主图、详情文案、视频素材等任何内容生产。
- 不代你申请支付商户号、税务登记、物流账号等资质。
- 不提供服务器、数据库、对象存储等云资源与容量规划。

## 依赖条件

- 一键路径：Node.js（官方要求 20 以上）+ 正在运行的 Docker。
- 手动路径：Ruby、vips（图像处理）、Rails；按所选数据库准备对应驱动与实例。
- 运行期：数据库与缓存（容器方式会一起拉起），以及可用的容器环境或一台能跑 Docker 的服务器。
- 业务侧：做线上收款要准备支付服务商账号；要自动算税、做商品搜索、接分析或营销工具时，准备对应服务账号与密钥。
- 客户端：想直连 API 时可选装 TypeScript SDK，或只用 `spree api` 命令。
- 部署：Docker 兼容主机均可（云主机、自建服务器、容器平台）；店面可部署到支持 Node.js 的托管环境。

## 已知限制

- 本地默认配置面向开发环境，账号口令与存储方式都不适合直接上生产。
- 命令行为本地项目自动生成的密钥只有只读范围，写入操作必须另建带写权限的密钥。
- 开源版与收费企业版存在明确功能差异，选型前必须逐条确认目标能力落在哪一侧。
- 作为无头平台，前端必须由使用方提供与维护，Spree 自身不解决界面问题。
- 上游迭代较快，命令、参数与配置项可能变化；**执行前请以官方文档与本地实际安装版本为准**。
- 本 Skill 不对具体版本号与发布日期做断言。
