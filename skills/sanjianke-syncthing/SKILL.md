# 三剪客 · 跨设备文件持续同步

几台机器上的同一批文件要一直保持一致，又不想把数据先传到别人的云盘上——Syncthing 解决的就是这件事。它在每台设备上跑一个常驻进程，设备之间直接点对点交换数据块，只把变化的部分传过去，不经过中心服务器中转。装好之后你不用管它，文件改动几分钟内自己就落到其他设备上。

**上游项目**：`Syncthing`　**仓库**：https://github.com/syncthing/syncthing

## 什么时候用 / 不用

**用它**：

- 你有多台自己的机器（家里台式、笔记本、公司电脑、NAS、手机），想要同一批工作文件在哪台都是最新的。
- 明确要求数据不经第三方云盘中转，或者所在网络不方便用公有云同步盘。
- 目录很大、但每次只改少量文件：它按块传输，只传变化的那几个块，不是整份重传。
- 需要给某个目录留历史版本，误删或改错了能翻回来（开文件版本控制即可）。
- 想在服务器之间、或者容器与宿主机之间做持续单向/双向投递，又不想自己写 rsync 定时任务。
- 需要程序化控制同步（启停文件夹、查看状态），它自带 REST API，可以接进自己的流程。

**不要用它**：

- 你要的是**备份**：同步会把源端的删除动作也复制到对端，删错了就是两边一起没了。备份要用只增不删的方案。
- 你要的是**把自己的文件传给别人**、或者做网盘分享链接：那是文件传输/分享工具的事，不是同步。
- 两边是**同一台机器上的两个目录**：本地目录镜像用 `rsync` 这类工具更直接，Syncthing 的设备模型在这里是负担。
- 想要**实时**（秒级）落盘：它感知变更本身有累积延迟，删除事件的延迟更长，别拿它当实时消息通道用。
- 目标是**手机上刷别人分享的大文件、或者看电影**：这类点播需求要用流媒体/下载工具。
- 你需要**多人协作的权限体系**（谁能看哪个子目录、审计谁改了什么）：它的信任模型是「设备对设备全量共享一个文件夹」，没有细粒度权限。

## 安装

先装好，再决定用哪种方式常驻。

**Windows（winget）**

```powershell
winget install --id Syncthing.Syncthing -e
```

也提供 MSI / 便携 zip，以及社区维护的托盘启动器，均可在官方下载页取。

**macOS（Homebrew）**

```bash
brew install syncthing
brew services start syncthing
```

**Debian / Ubuntu**

```bash
sudo apt install syncthing
```

**Fedora / RHEL 系**

```bash
sudo dnf install syncthing
```

**Arch 系**

```bash
sudo pacman -S syncthing
```

**容器（镜像在 ghcr 上）**

```bash
docker run -d --name syncthing \
  -p 8384:8384 -p 22000:22000/tcp -p 22000:22000/udp -p 21027:21027/udp \
  -v /srv/syncthing/config:/var/syncthing/config \
  -v /srv/syncthing/data:/var/syncthing/data \
  ghcr.io/syncthing/syncthing:latest
```

具体卷路径与端口映射以官方容器文档为准，不同版本可能调整。

**以服务方式常驻**：Linux 上发行版包通常自带 systemd 单元（用户级或系统级），也可以用 `systemctl --user enable --now syncthing` 这类方式交给用户会话；Windows 上可用 `syncthing serve --no-console` 配合计划任务。命令与单元名以所装版本自带的文件为准，不要照搬别的发行版。

装完不必手写配置——第一次启动会自动生成配置目录、设备证书和默认文件夹，并打印出 GUI/API 地址。

## 常用操作

**1. 前台先跑一次，拿到设备 ID 和 GUI 地址**

```bash
syncthing serve --no-browser
```

日志开头几行会给出 GUI/API 地址（默认 `127.0.0.1:8384`）和本机设备 ID。

**2. 打印本机设备 ID（用于在别的设备上添加入口）**

```bash
syncthing device-id
```

**3. 看配置与数据库目录在哪**

```bash
syncthing paths
```

**4. 直接指定 GUI 监听地址和 API Key（适合改成非本机可见或无头机）**

```bash
syncthing serve --gui-address=0.0.0.0:8384 --gui-apikey='<你的APIKey>' --no-browser
```

注意 `0.0.0.0` 会让局域网内其他机器都能打开管理界面，务必先设好管理密码或只绑内网地址。

**5. 改端口/开机自启之外，日常控制走子命令（服务已在后台跑着）**

```bash
# 列出文件夹状态
syncthing cli config folders list
# 暂停 / 恢复全部同步
syncthing cli config options set paused true
syncthing cli config options set paused false
```

子命令树随版本演进，先用 `syncthing cli --help` 看当前版本支持哪些。

**6. 走 REST API 做脚本化查询**

```bash
curl -s -H "X-API-Key: <你的APIKey>" http://127.0.0.1:8384/rest/system/status
curl -s -H "X-API-Key: <你的APIKey>" http://127.0.0.1:8384/rest/db/status?folder=<文件夹ID>
```

端点与参数以 `https://docs.syncthing.net/` 的 REST API 章节为准。

**7. 忽略不想同步的东西**

在共享文件夹根目录放 `.stignore`：

```
// 依赖目录不跨机同步
node_modules
__pycache__
// 支持通配
*.tmp
```

改完文件不用重启，界面里让它重扫一次即可。

**8. 预留空间水位（避免把磁盘塞满）**

Web 界面里给每个文件夹设「最小可用空间」；磁盘剩余低于该值时会暂停该文件夹的同步，而不是把盘写爆。

## 常见坑

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 新配好之后卡着不动，两边都显示「等待确认」 | 首次建立共享需要双方各自确认一次对方设备 | 在 A 上添加 B 的设备 ID 并共享文件夹，再到 B 的界面上接受；只在一端操作不会同步 |
| 出现一堆 `xxx.sync-conflict-<日期>-<时间>-<设备>.<扩展名>` | 同一文件在两台设备上都被改过，内容确实不同，它把改动时间较早的那份重命名保留下来 | 先比对两份内容再决定留哪份；直接把冲突文件删掉就是丢掉那一次改动 |
| 明明删了文件，它却还在传/还在被同步 | 变更事件有累积延迟，删除事件延迟更长；外部程序写入也可能不被文件系统通知捕捉 | 别把「刚删完就看不到」当检验标准；必要时手动触发重扫，并保留周期性全量扫描 |
| 传得很慢，状态里显示走中继 | 两端没有打通直连，退回到公网中继转发 | 两端做端口转发（默认 TCP/UDP 22000）与本地发现放行（默认 UDP 21027），能用同一局域网就优先直连 |
| 磁盘里冒出一堆 `.syncthing.` / `~syncthing~` 开头的文件 | 它从不直接写目标文件，都是写临时副本再改名就位；中断时临时文件会留下最多一天 | 这是正常现象；但**别用这两个前缀命名自己的文件**，这些名字属于它的命名空间，会被自动忽略 |
| 同步状态总显示有文件「不同步」，提示大小写冲突 | 对端存在仅大小写不同的两个文件名，而本机文件系统不区分大小写 | 在所有相关设备上统一文件名，只能人工改，工具不会替你猜哪个对 |
| 同一目录既用 Syncthing 又用别的同步盘（或两边互为镜像） | 两个同步器各自重写文件，互相触发，冲突文件越滚越多 | 一个目录只交给一个同步器；需要多层时用不同目录分别管 |
| 把缓存/虚拟磁盘/数据库目录共享出去 | 这类文件频繁改写且常常是稀疏/巨大文件，重扫与重传开销极大 | `.stignore` 里排除掉；虚拟机镜像这类不要跨机同步 |
| 加了手机端后发现目录里出现了系统相册的隐藏文件 | 移动端会把媒体库目录一起纳入 | 在移动端单独指定共享的子目录，不要把整个相册根目录给出去 |
| 误在文件系统层面直接删了它的数据库文件 | 索引数据库被清掉后需要重新扫描建立索引 | 停服务后再动配置/数据目录；重建索引期间会大量读盘，避开业务高峰 |
| 升级后旧配置读不进来 | 配置由更新版本写过，默认拒绝加载 | 先备份配置目录；确认版本匹配后再启动，不要靠强制开关长期绕过 |
| 把管理界面暴露到公网却没设密码 | GUI 默认监听本机，一旦用 `--gui-address=0.0.0.0:8384` 就等于开放管理面 | 必须设管理密码或加在前面加反向代理并做访问控制；只用内网地址最省事 |

## 权限与用途说明

| 能力 | 是否申请 | 用途 |
|---|---|---|
| 网络访问 | 是 | 设备之间直连、本地发现（UDP 21027）、必要时走公网中继；GUI/API 在本机监听 |
| 读取文件 | 是 | 扫描被共享目录，读文件内容算块哈希，只在改动时才重读 |
| 写入文件 | 是 | 在共享目录写入接收到的数据块与临时副本，并原子改名就位；开启版本控制时写入历史目录 |
| 凭证 | 是 | 设备证书/私钥与 GUI 管理口令存在配置目录；REST API 需 `X-API-Key`。不要把配置目录提交到版本库或打进镜像层 |
| 子进程 / 后台常驻 | 是 | 需要以服务或守护进程方式常驻，才能持续同步；容器方式则是容器内常驻 |

## 能力边界

**覆盖**：

- 多设备之间共享目录的双向持续同步，按块比对与传输，只传变化部分。
- 文件夹级版本控制（含回收站式保留），用于误删误改回退。
- 单一二进制 + 内嵌 Web 管理界面，配置目录可整体搬迁；自带 REST API 便于脚本化和集成。
- 通过 `.stignore` 做同步范围排除；按文件夹设定最小可用空间水位，避免写满磁盘。
- 跨平台：Windows / macOS / Linux / 各类 NAS 与移动端。

**不覆盖**：

- 不做备份与归档：没有只增不删的语义，源端删除会传播到对端。
- 不做云端文件分享、外链、在线预览；也不解决「把文件发给同事」这件事。
- 不做细粒度多人权限、审计和协作；信任单元是设备，共享单元是整个文件夹。
- 不做实时消息/秒级同步通道；也不做断点续传到任意 HTTP 目标（那是传输工具的领域）。
- 不做文件内容转换、去重压缩、加密归档等加工动作。

## 依赖条件

- 操作系统：Windows 10 及以上、macOS、主流 Linux 发行版，或支持容器的 NAS 系统。
- 运行方式二选一：后台服务/守护进程常驻，或容器常驻；容器方式需要能映射 8384、22000、21027 端口。
- 磁盘：每个共享目录所在分区要留出余量，建议显式配置最小可用空间水位。
- 网络：设备之间至少要能通过中继互通；要做直连需放行 22000（TCP/UDP）与本地发现的 21027（UDP），或自行配置静态地址。
- 无需账号或云端 Key；不依赖任何第三方注册。

## 已知限制

- 全量扫描默认约每小时一轮，文件系统事件通知还有累积延迟，删除事件延迟更长，因此变更不会瞬时可见。
- 大小写冲突只能人工解决，工具不会自动决定保留哪一个。
- 扫描大目录时 CPU 与磁盘 IO 会有明显尖峰，尤其是首次建立索引和数据库重建期间。
- 社区中继只保证连通性，带宽与稳定性不作承诺；大文件长期依赖中继体验很差。
- 移动端受系统后台限制，前台不在时同步可能长时间不推进。
- 配置与索引数据库跨大版本升级时可能不兼容，升级前必须备份配置目录。

## 自检清单

执行前：

- [ ] 确认这是**同步**需求而不是**备份**需求（对端要不要跟着删）。
- [ ] 确认要共享的目录里没有数据库、虚拟机镜像、依赖缓存这类高频改写文件。
- [ ] 记录本机设备 ID，并确认对端设备 ID 拿到了。
- [ ] 确认 GUI 没有被暴露到不可信网络，或者已经设好管理密码。

执行后：

- [ ] 两端文件夹状态都到了「已同步 / Up to Date」，而不是只有一端。
- [ ] 在 A 端新建一个测试文件，确认几秒到几分钟内出现在 B 端，然后两边都删掉。
- [ ] 检查目录里没有新增 `sync-conflict` 文件。
- [ ] 确认 `.stignore` 生效（被排除的目录没有出现在对端）。
- [ ] 确认服务/容器重启后能自动恢复同步。
